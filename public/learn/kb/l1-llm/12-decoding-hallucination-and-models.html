解码策略、幻觉、长上下文与模型选型 ​

覆盖知识点：L1-10 L1-20 L1-21 L1-22 L1-23 L1-24 ｜ 面试频率：高 ｜ 建议学时：19h

一句话说清 ​

这一页把「模型怎么吐出 token」到「怎么选模型、怎么控制它的不确定性」这条链路一次讲完：解码策略（greedy / beam / temperature / top-k / top-p / 重复惩罚）决定从 logits 到下一个 token 的采样规则；logprobs 是模型不确定性的直接读数，也是你项目里拒答阈值与检索打分的现实抓手；幻觉不是 bug 而是「用似然目标优化一个没有真值信号的任务」的必然产物，只能靠系统层缓解；长上下文的失效有明确机制（注意稀释、位置编码、训练长度），所以「窗口大」不等于「会用」；模型选型要按约束表而不是排行榜；推理模型把算力从训练搬到了推理时，代价是思考 token 也要计费。

为什么必须学 ​

这一页是 L1 里和你的项目耦合最深的一页。前面几页讲的是模型内部怎么算；这一页讲的是你在工程里真正能拨的旋钮：

  • 你给生成设的 temperature / top_p 是哪一组？为什么？
  • 你的拒答机制靠什么判断「不知道」？—— 这一页会告诉你 logprobs 是比「让模型自己说不知道」更可靠的一条路。
  • 你的评测集里有「不可回答」样本，这直接对应幻觉的分类与缓解。
  • 你的切块档位与上下文预算，对应长上下文失效的机制。
  • 你走 OpenAI 兼容协议，所以模型选型是可替换的——这一页给出一张可操作的选型表。
  • 推理模型的思考 token 会进入你的成本报告，这是你成本核算里最容易漏掉的一大块。

L1-10 解码策略：从 logits 到下一个 token ​

完整流水线（顺序很重要） ​

模型前向得到的是最后一个位置的 logits（形状 [B, V]， 是词表大小），解码要做的是把它变成「选哪个 token」：

  → ④ top-p 截断        （保留累积概率达到 p 的最小集合）
  → ⑤ 重新归一化 + 采样

顺序为什么不能随便换：温度是对分布形状的缩放 —— 先截断再调温，与先调温再截断，得到的候选集不同（ 会改变 softmax 后的相对大小，进而改变累积概率，从而改变 top-p 的边界）。这个细节说出来就是加分项。

六种策略的适用面 ​

策略做什么特点该用在什么场景
Greedy每步取概率最大的 token确定、可复现；容易退化（重复循环、平庸、无多样性）抽取式任务、需要可复现的场景
Beam Search同时保留 条路径，选整体似然最高的提升序列的整体概率，但输出趋于保守平庸、多样性低；计算与显存成本 × 机器翻译、摘要等有明确目标序列的任务
Temperaturelogits 除以 再 softmax 分布更尖（更确定）； 更平（更随机）； 等价于 greedy通用旋钮，用来调「创造性」
Top-k只从前 个候选采样固定候选数； 不随分布形状自适应 —— 分布很平时可能仍截进一堆坏候选简单可控
Top-p（nucleus）取累积概率达到 的最小候选集自适应候选数：分布尖时集合小，分布平时集合大最常用的默认策略
Repetition Penalty对已出现 token 的 logits 做惩罚抑制复读；过强会导致语义漂移或语法错误长文本生成

三条必须能说清的判断：

  1. Beam Search 为什么不适合开放生成？ 因为「整句似然最高」≠「人类觉得最好」。语言模型的似然与人类偏好并不一致（这是 RLHF 存在的根本原因），而且 beam 的搜索会收敛到安全、平庸、重复的表达。「似然最大化不等于质量最优」这句话是这一节的题眼。
  2. Top-p 为什么比 top-k 好？ 因为它是自适应的：在模型很确定的位置（分布尖锐）自动收缩候选集，在模型犹豫的位置（分布平坦）自动放宽。top-k 做不到这一点。
  3. 温度与 top-p 是耦合的：先调温度再截断（或反之）会改变候选集。实践中常见做法是固定一个 top-p，只调温度，避免两个旋钮互相干扰 —— 这也是消融实验该有的纪律。

一条关于「可复现性」的纪律（直接关系到你的评测门禁）：greedy（或 极小）是唯一能保证同一输入得到同一输出的设置。 如果你的评测跑在采样模式下、又不固定随机种子，那么「分数涨了」可能只是采样噪声。要做配对检验，就必须先控制生成的不确定性。 这条纪律下一段还要展开。

L1-20 文本生成采样与不确定性（logits / logprobs） ​

logits、概率、logprob 的关系 ​

量定义取值范围说明
logits模型最后一层的原始输出未归一化，只有相对大小有意义
probabilitysoftmax 之后，全词表和为 1归一化后
logprob概率的自然对数概率 1 对应 0，概率越小越负
perplexity（PPL）越低越好；跨 tokenizer 不可比

为什么用 logprob 而不是概率：因为概率在长序列上连乘会下溢到 0，而对数上连乘变相加（），数值稳定。序列级 logprob 是逐 token 累加的 —— 这一条在 DPO 那页是长度偏差的来源，在这里是「长回答的 logprob 天然更负」的原因。

logprobs 能做什么（这是你最该拿走的工程抓手） ​

① 校准「拒答」判断。 与其依赖模型自己说「我不知道」（这个行为需要训练，且不稳定），不如直接看概率读数。若模型在生成关键 token 时的 logprob 很低（或多条候选的 logprob 接近），说明它没有把握。这可以与检索分数叠加，构成一个更稳的拒答判据。

② 消歧与置信度排序。 在分类式任务（你的 9 类意图分流）里，如果你让模型输出类名，那么各类名的 logprob 分布直接给出置信度：最高项与次高项差距小 → 这个样本值得进入人工复核。

③ 检索重排的补充信号。 有些工作用「给定 query 时，文档片段的条件对数似然」作为相关性信号（本质是让语言模型给片段打分）。注意这是与 cross-encoder 重排同类的思路（交叉编码），与你的 dense / sparse 检索是不同层级的手段。

④ 评测与调试。 logprobs 能让你看到「模型在哪个位置最犹豫」，这比只看最终输出有用得多。

必须说清的边界：logprob 是「模型内部的一致性」，不是「事实正确性」的度量。 模型可以对一个错误答案给出很高的概率。所以 logprobs 只能用来做「不确定性」的代理，不能用它判断对错。 把这一点说清楚，能防止你把它当成万能答案。

还有一个现实约束：不是所有 API 都返回 logprobs（OpenAI 兼容生态里的实现差异较大），能否拿到、以及能否拿到 top-k 候选，需要实际确认。如果你的接口不返回，退路是用本地小模型复现同一批样本，或者改用自洽性投票（多次采样看一致性）。

采样不确定性的两个工程后果 ​

后果一：评测的可复现性问题。 如果生成带随机性，两次跑同一个评测集就会得到不同结果。做法：评测时用 temperature = 0（或极小值），或固定随机种子；并且无论如何都要用配对比较 + 统计检验（你的门禁已经在做这件事）。「先控制方差，再做均值比较」是评测的基本纪律。

后果二：自洽性（self-consistency）是一种可用的免费提升。 对同一个问题采样多次，取多数答案，往往比单次贪心更准 —— 代价是 token 成本翻倍。这是一个「用钱换准确率」的旋钮，在你的成本语境里可以直接量化：多采样 次，成本 × ，准确率提升多少（用你的评测集测）。能做这条曲线，说明你在做工程权衡而不是在背技巧。

L1-21 幻觉的机制性原因 ​

先纠正一个提法：「幻觉是模型的 bug」是不准确的。幻觉是用似然目标优化一个没有真值信号的任务的必然产物。 这句话是这一节的总纲。

成因（六条，都是机制性的，不是「模型不聪明」） ​

#成因机制
1训练目标是似然，不是真值模型被训练成「生成看起来像训练数据的文本」。语料里频繁共现的模式会被高置信度生成，无论它是否真实
2没有「我不知道」的训练信号语料里几乎不存在「我不知道」这种回答。所以模型在缺信息时没有「拒绝」这个动作可学，只能继续补全
3长尾知识被平坦化训练中只见过几次的事实没有被稳定记住。模型会用语义相似的常见模式去填补 —— 这正是「细节错误但形似」的典型幻觉形态
4暴露偏差（exposure bias）训练时每步都喂真实的前缀（teacher forcing），推理时喂的是自己生成的前缀。一旦早期出现小错误，后续会基于错误上下文继续生成，错误被放大
5上下文与参数知识的冲突模型既从上下文读信息，也从参数里回忆。两者冲突时不保证以上下文为准 —— 这只能靠训练（指令微调）引导，不是结构上的保证
6SFT 的表述风格副作用如果 SFT 数据里的回答总是自信、详尽、结构完整，模型在缺信息时也会保持同样的自信语气。语气自信与内容正确是两件独立的事

第 5 条是 RAG 系统里最要紧的一条，值得单独记住：「模型会读你的上下文」不是结构保证，是训练出来的倾向。 这就是为什么所有严肃的 RAG 系统都要有引用核验与拒答闸门，而不是把「请只根据以下材料回答」这句话当作保证。

幻觉的分类（面试里能分类就是加分） ​

类型表现归属
闭卷幻觉模型没有外部材料时编造事实参数知识不足 + 成因 1/3
忠实性幻觉（faithfulness）给了材料，回答与材料矛盾成因 5（未优先服从上下文）
引用幻觉引用了不存在的文档、页码、段落、或把 A 的说法挂在 B 上生成与检索的绑定不严格
指令幻觉要求输出 JSON，格式对但字段是编的格式约束与内容忠实是两件事

你项目二的主要风险在前两类，项目一的风险在第三类（引用与出处）。能把自己项目的风险对号入座，比泛泛说「幻觉很危险」强得多。

缓解手段（按你在项目里能做的顺序） ​

手段作用机制在你项目里的位置
检索增强（RAG）把事实放进上下文，减少「靠参数填空」你的混合检索 + 重排
强约束的 prompt明确要求「只依据材料」「材料不足则说明找不到」你的答案生成 prompt
引用核验生成后机械核对引用是否真的在检索结果里建议补的 guard 步骤
拒答闸门检索分数 / 覆盖率 / logprob 低于阈值时不生成答案你已有 guard 模块
结构化输出强制 JSON schema，避免自由发挥你的工具调用与 pydantic 校验
多采样自洽性多次采样取多数可选，成本 × k
温度调低减少低概率 token 被采中你已有参数设置
换更强的模型更强的模型通常更少幻觉你用 OpenAI 兼容协议，换模型是低成本操作

一条重要的判断：RAG 降低幻觉，但不消除它，而且它引入了一类新的幻觉（忠实性幻觉） —— 模型忠实于它的参数而不是你的材料。这个「RAG 不解决全部问题、还新增一类问题」的认识，是区分「用过 RAG」和「想过 RAG」的分界线。

L1-22 上下文窗口与长上下文失效 ​

核心判断：窗口变大 ≠ 模型会用它。 这是这一节的总纲，「lost in the middle」是它的典型表现。

四条失效机制 ​

#机制说明
1注意稀释注意力要在更多位置间分配（softmax 权重和为 1）。位置越多，单个位置分到的权重越少，关键信息可能被淹没在大量无关文本中
2位置编码的分布外RoPE 等在超过训练长度后进入未见过的位置区间，相对位置的分辨能力退化 —— 这是为什么外推需要专门的方法（改基底、位置插值），不是把窗口设大就自动成立
3训练长度与宣称窗口不一致有的模型宣称的窗口来自外推配置，而训练长度更短。宣称支持 ≠ 在满长时有效
4成本随长度非线性上升注意力分数矩阵是 （训练时尤甚），KV Cache 随 线性增长并挤压并发 —— 固定算力预算被摊到更多 token 上

关于「lost in the middle」的正确表述：模型对开头与结尾的信息利用得更好，中间部分容易被忽略。这个现象的幅度与模型、任务、以及评测方式都相关，不要报一个具体数字；但「把最关键的证据放在开头或结尾」是一条代价为零、方向正确的工程建议。

对工程的直接推论（三条可执行的） ​

  1. 别把「装满窗口」当目标。塞进无关文本会主动降低性能（注意稀释 + 干扰）。「少而准」通常优于「多而杂」 —— 这句话直接支持你的 rerank 与 top-k 调参。
  2. 信息位置要设计。关键证据放前部或尾部；如果要放中间，就在 prompt 里显式指出「请重点看第几段」。
  3. 切块与窗口是两个旋钮，不是同一个。你的 512 / 1024 / 2048 三档消融同时影响检索粒度的精度与单次请求的上下文占用（进而影响成本与并发能力）。把这两个视角一起说出来，是这一页与你项目最强的连接点。

MoE 必须单独讲清（这是最容易问到的架构话题）：

L1-24 推理模型与 Thinking / Reasoning 范式 ​

核心思想：把算力搬到推理时（test-time compute） ​

传统路径是靠训练时更大的模型 / 更多数据提升能力。推理模型的路径是让模型在回答前生成一段更长的思考过程，用推理时更多的计算量换更好的答案。这被称为 test-time compute scaling，其思想基础与 CoT 那页一致：模型的串行计算量正比于它生成的 token 数。

实现层面的两条路线 ​

路线做法特点
提示式 CoT用 prompt 要求「先思考再回答」（或 few-shot 展示带推理的回答）零训练成本；模型可能不遵守、或思考质量不稳定
训练出的推理行为用可验证的奖励（例如数学题答案对错、代码能否通过测试）做 RL，训练模型自发产生长思考；或在 SFT 中用带思考轨迹的数据效果更稳；需要可验证的任务与大量算力
推理预算控制提供 reasoning_effort 之类的开关，或显式限制思考 token 数让成本与质量可调

三条必须知道的工程事实 ​

① 思考 token 是 token —— 要计费、要延迟。 这是和你项目直接相关的一条：走 API 时，思考过程产生的 token 通常按输出 token 计费，而且首 token 延迟显著增加（用户要等思考完才开始看到回答）。如果你的成本报告或延迟基准没有把这一项算进去，它会是一个严重的低估。 在流式输出下，你还需要决定思考内容是否对用户可见（多数场景应该过滤掉）。

② 推理预算调度的纪律：不是所有问题都值得开高预算。 意图分类、格式抽取、简单 FAQ 这类任务不需要长思考，开了纯粹是浪费 token 与延迟。正确做法是按任务分档配置推理预算 —— 这和你项目里「9 类意图分流到 5 个出口」的架构思想完全一致：用分流把简单请求和复杂请求分开，各自用不同的算力预算。 这是一个可以直接说进面试的类比。

③ 长思考的失败模式。

  • 不收敛：在预算内没给出答案就截断；
  • 过度思考：简单问题上绕圈，反而更容易出错；
  • 思考与答案不一致：模型说了一套推理、给了另一个答案（模型不一定「忠实」地按它的思考行事）。「思维链不一定是真实计算过程的记录」这条认识很重要 —— 它可以用来提示过度信任 CoT 的风险。

推理模型改变了什么、没改变什么 ​

改变了没改变
推理类任务（数学、代码、多步逻辑）的效果上限事实性：思考不会让模型知道语料里没有的事实
成本结构（推理时算力成为主要开销）幻觉的机制：它仍可能编造，只是可能更少
「该用多大模型」的判断（小模型 + 长思考 ≈ 大模型 + 短思考）需要检索的知识问题：仍要靠 RAG

一句话总结：推理模型把「推理能力」和「模型规模」部分解耦了，但它没有解决事实性问题。 这条边界必须说清，否则会被追问「那是不是不需要 RAG 了」。

和你自己的项目对上号 ​

① 你的拒答机制有两个可用的信号源，而你只用了其中一个。 你现在的 guard 依赖检索分数（Milvus 的相似度 / RRF 融合后的分数）来判断「找没找到」。logprobs 是第二个独立信号：即使检索回来的片段分数不低，模型在生成答案时的关键 token logprob 可能很低 —— 这说明它在「硬编」。两个信号的组合（检索分数低 或 生成置信度低 → 拒答）比任何单一路径都稳。 注意说清边界：logprob 只在你的 API 端点返回它时才可用，需要实际确认；如果不能拿到，退路是用本地小模型复现同一批样本做对照。

② 你的评测门禁与解码不确定性直接冲突，必须显式处理。 配对 t 检验 / Wilcoxon + Holm 校正的假设前提是观测的差异反映真实差异。如果生成带随机性，同一配置跑两次的分数波动会被误当成改进。做法：评测时 temperature = 0（或固定种子），并且把生成参数当成评测配置的一部分冻结下来写进报告。这是一条必须补进你评测文档的纪律 —— 它比多跑几个消融实验更能提升可信度。

③ 你的「不可回答」测试集，正好可以量化幻觉缓解手段的真实收益。 你项目二天然拥有这个集合。这是一个别人很难复制的资产 —— 大多数人的评测集只有「该答对的题」，没有「该拒答的题」。建议做一个四组对照：① 无检索；② 有检索无引用核验；③ 有检索 + 引用核验；④ 加上 logprob 拒答信号。指标用拒答准确率（该拒的拒了）+ 误拒率（该答的没答） 两个，做配对检验。

判据与解读：如果出现「拒答准确率上升但误拒率也上升」，说明阈值需要标定（这是一个经典的精确率-召回率权衡），而不是方法无效；如果 ④ 明显优于 ③，logprob 信号的价值就被你自己的数据证明了 —— 这比引用任何论文都有说服力。

④ 你的三档切块（512 / 1024 / 2048）在这个视角下是「质量 vs 上下文占用」的双目标消融。 更小的块：检索更精准、单块更聚焦，但可能截断上下文导致信息不完整，需要更多块 → 更长的拼装上下文。更大的块：信息完整，但引入无关内容（注意稀释）且单次请求更长。你可以在现有消融数据上补一个维度：记录每一档的平均拼装上下文 token 数与端到端延迟 / 成本，把「质量 - 成本」两条曲线画在一起。这是把 L1 原理落到你成本报告上的最直接动作。

⑤ 模型选型：你已经具备最强的工具。 你走 OpenAI 兼容协议 + 有分层评测集 —— 换一个模型只需要改配置 + 跑一遍评测。建议做一个最小选型实验：对 2–3 个候选模型跑同一套评测，记录准确率、拒答表现、延迟、token 成本四项。注意成本口径：如果候选里有推理模型，必须把思考 token 计入输出 token，否则对比会失真。这份表格可以直接放进简历的项目描述里 —— 「做过模型选型对比」比「用过某某模型」强得多。

⑥ 推理模型的使用要有分流纪律。 你项目一的 9 类意图里，kb_faq / service_ops 这类简单路径不该开高推理预算；而涉及复杂退款的 refund_flow 可能需要更多推理。「按意图分档配置推理预算」是你现有架构的自然延伸 —— 你已经有分流图，只需要给不同出口配不同的模型与预算。这能同时降低成本和延迟，是一个非常具体的优化动作。

面试怎么问 ​

Q1：temperature、top-k、top-p 分别是什么？你怎么设？

A（要点）：三者都是把 logits 变成采样分布的规则。temperature 缩放 logits（除以 ）： 更尖更确定， 更平更随机， 等价于 greedy。top-k 保留概率最高的 个候选。top-p（nucleus） 保留累积概率达到 的最小候选集，候选数自适应（分布尖时小、平时大），所以比 top-k 更常用。重复惩罚对已出现 token 的 logits 做惩罚。

顺序有讲究：通常是「重复惩罚 → 温度 → top-k → top-p → 归一化 → 采样」。先截断再调温与先调温再截断会得到不同的候选集，因为温度改变了归一化后的累积概率，从而改变 top-p 的边界。

加分句：「我在项目里的纪律是固定一个旋钮：固定 top-p、只调温度，避免两个参数互相干扰。而且做评测时用 temperature = 0，否则同一配置跑两次的分数波动会被误当成改进 —— 这会让配对检验失去意义。」

别说：「temperature 越高创造力越强所以效果越好。」它是随机性旋钮，不是质量旋钮。

Q2：为什么不用 beam search？

A（要点）：因为 beam search 优化的是「整句似然最高」，而语言模型的似然与人类认为的「好回答」并不一致。这有两个后果：① 输出趋于保守、平庸、复读，多样性低；② 计算与显存成本随 beam 宽度线性增长。「似然最大化不等于质量最优」正是 RLHF 存在的理由 —— 如果似然就等于质量，那就没必要用人类偏好去优化了。

加分句：「所以 beam search 适合的是有明确目标序列的封闭任务，比如机器翻译、摘要 —— 那里『n-gram 似然高』与人类评价相关性较好。开放对话不适合。」

别说：「beam search 太慢了。」慢是次要的，根本原因是目标函数不对。

Q3：logprobs 有什么用？能用来判断答案对不对吗？

A（要点）：logprob 是概率的自然对数（范围 ，概率 1 对应 0），用它是因为长序列的概率连乘会下溢，而对数把连乘变相加。它能做四件事：① 不确定性读数 —— 关键 token 的 logprob 低说明模型没把握，可以和检索分数叠加做拒答判据；② 分类置信度 —— 类别的 logprob 接近就送人工复核；③ 自洽性投票；④ 调试与评测 —— 看到模型在哪里犹豫。

边界必须说：logprob 衡量的是模型的内部一致性，不是事实正确性 —— 模型可以高置信度地说错。所以它只能当不确定性的代理，不能当正确性判据。还有一个现实约束：并非所有 API 都返回 logprobs，可用性要实际确认。

加分句：「我的拒答逻辑想用两个独立信号：检索分数低 或 生成置信度低 —— 任何单一路径都会漏。单一信号的问题是，检索回来的片段分数不低但内容其实不解决问题时，只看检索分数就会漏掉。」

别说：「logprob 低就说明是幻觉。」反例很清楚：模型对某些错误答案会非常自信。

Q4：幻觉的根本原因是什么？RAG 能解决吗？

A（要点）：根本原因是用似然目标优化一个没有真值信号的任务。具体机制有六条：训练目标是似然不是真值（共现频繁的模式被高置信度生成）；没有「我不知道」的训练信号（语料里几乎不存在这种回答，所以模型缺信息时没有拒绝这个动作可学）；长尾知识被平坦化（用语义相似的常见模式填空）；暴露偏差（推理时喂自己生成的前缀，早期错误被放大）；上下文与参数知识冲突时不保证以上下文为准；以及 SFT 表述风格的副作用（语气自信与内容正确是两件独立的事）。

RAG 降低幻觉但不消除，而且引入一类新幻觉 —— 忠实性幻觉：给了材料，模型还是按参数里的记忆回答，或者引用挂在错误的位置上。所以严肃的 RAG 必须有引用核验与拒答闸门 —— 「请只根据以下材料回答」这句话不是结构保证，只是训练出来的倾向。

加分句：「我在项目二里正好做了这个对照：有检索、有引用核验、再加 logprob 拒答信号，三档在拒答准确率与误拒率两个指标上分别测。因为我有天然不可回答的测试集，这个对照能做出真实数字，而不是引用别人的结论。」

别说：「RAG 就解决了幻觉。」这是最常见的过度承诺。

Q5：上下文窗口很大，是不是就不需要 RAG 和切块了？

A（要点）：不是。窗口变大不等于模型会用。四条失效机制：① 注意稀释 —— softmax 权重和为 1，位置越多单个位置分到的越少，塞入无关文本会主动降低性能；② 位置编码的分布外 —— 超过训练长度后相对位置分辨能力退化，需要专门的外推方法，不是把窗口设大就自动成立；③ 训练长度与宣称窗口不一致 —— 宣称支持不等于满长有效；④ 成本非线性上升 —— 分数矩阵随长度平方（训练尤甚），KV Cache 随长度线性增长并挤压并发。

加分句：「而且有个反直觉的结论：少而准通常优于多而杂。我的切块三档消融本质上在扫这条曲线 —— 更小的块检索更精准但可能信息不完整，更大的块信息完整但引入无关内容并抬高成本。所以切块粒度与上下文占用是两个不同的旋钮，不能混为一谈。」

别说：「窗口够大就不需要检索了。」事实性、可更新性、可溯源三件事都不会因为窗口变大而解决。

Q6：你怎么选模型？

A（要点）：按约束选，不按排行榜选。四个维度：① 能力是否覆盖任务（用自己的评测集测，不看通用榜单，因为领域语料是长尾的）；② 成本与延迟（推理成本大致与激活参数量相关）；③ 中文与领域适配；④ 可替换性。

各系列的取向：Qwen 覆盖面广、中文强项；LLaMA 定义现代开源解码器架构、微调生态最庞大；DeepSeek 在 MoE 与推理模型方向上有代表性工作；GLM 是国内生态的对话模型备选；Mistral 是小规模高性价比取向、以滑动窗口注意力为标志性设计。具体规格以官方模型卡为准 —— 我不背可能过期的数字。

加分句：「MoE 的取舍我会特别看：它让总参数量很大但每个 token 的激活参数量很小，所以计算量不随总参数线性增长；但显存要装下全部专家（显存看总参数量），而且路由负载均衡与通信开销都是成本。所以它省的是算力，不是显存。」

别说：「用排行榜第一的。」排行榜与你的任务相关性有限。

Q7：推理模型的思考过程会计入成本吗？对你项目有什么影响？

A（要点）：会计入。思考 token 通常按输出 token 计费，而且首 token 延迟显著增加（用户要等思考完才看到回答）。所以：① 成本报告与延迟基准必须把思考 token 算进去，否则是严重低估；② 流式输出时要决定思考内容是否对用户可见（多数场景应过滤）；③ 按任务分档配置推理预算 —— 意图分类、格式抽取、FAQ 不需要长思考，开了纯浪费。

加分句：「这和我项目的架构是同一个思想：用分流把简单请求和复杂请求分开、各配不同算力预算。我项目一已经有 9 类意图到 5 个出口的分流图，给每个出口配不同的模型与推理预算是一个很自然的优化 —— 能同时降成本与延迟。」

别说：「思考越久越好。」简单问题上过度思考反而更容易出错，而且成本是真实的。

Q8：CoT 是模型真实计算过程的记录吗？

A（要点）：不一定是。模型可能存在「说了一套推理、给了另一个答案」的情况 —— 也就是思考内容与最终输出不完全一致。所以：① CoT 可以作为提升效果的机制（串行计算量正比于生成 token 数），但不能当作可审计的证明；② 在一些需要可解释性的场景下，需要额外的核验（例如让模型输出结构化结论再机械校验），而不是直接相信它写出来的推理过程。

加分句：「所以我在项目里的做法是把可核验的东西留在系统层：引用核验是机械比对的，不依赖模型的自我说明。能被机械校验的才叫审计，模型自己写的推理过程不算。」

别说：「CoT 就是模型的思考过程，看它就能知道模型怎么想的。」这个假设已经在研究里被反复质疑。
