Tokenizer 与分词算法：BPE / WordPiece / Unigram ​

覆盖知识点：L1-02 ｜ 面试频率：高 ｜ 建议学时：5h

一句话说清 ​

Tokenizer 是模型唯一的入口和出口，它把字符串切成子词（subword）、映射成整数 id。今天几乎所有主流模型都用子词分词，因为它同时避开了 word-level 的 OOV 与词表爆炸、以及 char-level 的序列过长。三大算法回答的是同一件事——词表怎么选：BPE 自底向上合并高频相邻符号对，WordPiece 按似然增益合并，Unigram 自顶向下按概率剪枝。它决定了三件工程事实：上下文窗口的有效容量、API 计费口径、以及你的切块策略到底切了多少东西。

为什么必须学 ​

面试官问 tokenizer 的频率远高于它在教材里的篇幅占比，原因是它是唯一一个同时连接算法与账单的组件。三个必考角度：

  1. 「为什么不用按词分？为什么不用按字分？」 —— 考你对训练/推理两边约束的整体理解，答不上来会被判定为只会调 API。
  2. 「中文一个字几个 token？」 —— 这题是陷阱题。答案是「取决于词表覆盖率，不能一概而论，要实测」。如果你张口报一个数字，面试官会立刻抓你编造；如果你答「我实测过，方法是……」，这一题就从送命题变成加分题。
  3. 「上下文 128k 能放多少字」 —— 这题背后是你的显存估算与截断策略，直接连着 KV Cache 那一页。

还有一层：你项目里所有关于「成本」「截断」「切块档位」的数字，只有换成 token 才能互相比较。按字符说的 512 和按 token 说的 512，在中文语料上会差出数倍。

核心内容 ​

子词分词的动机：为什么不是 word-level 也不是 char-level ​

word-level 的两个死结：

  • OOV：测试时遇到训练词表里没有的词，只能映射成 <UNK>，信息直接丢失。英文的形态变化（run / running / ran / runs）各自占一个词表位，互不共享统计量；中文更麻烦——词的边界本身就有歧义（「研究生命起源」怎么切）。
  • 词表规模：要覆盖足够多的词，词表会到百万量级。而 embedding 与输出层的参数量是 量级（权重共享时是 ）， 涨一倍，这一块参数就涨一倍。

char-level 的两个死结：

  • 序列长度爆炸：一段 500 字的文本变成 500 个 token（甚至更多，见下文的中文问题）。注意力成本是 ， 涨 4 倍，注意力分数矩阵涨 16 倍。
  • 单 token 语义太弱：模型要把大量容量花在「怎么把字拼成词」这件低层事情上，等效于降低了有效深度。

subword 的位置：常见词保持整词（the、中国），罕见词拆成可复用的片段（un + believ + able）。共享统计量是这个设计的核心收益 —— running 和 runs 共享 run 的学习信号。

BPE：从字节对压缩到子词词表 ​

训练阶段（自底向上合并）：

  1. 初始化：把所有词拆成最小单位（字符级，或字节级），并统计每个「词」的频次。
  2. 统计所有相邻符号对的频次：(l, o)、(o, w)、(e, s) ……
  3. 合并频次最高的那一对，把它作为新符号加入词表。
  4. 重复 2–3，直到词表达到目标大小。

编码阶段（最容易被误解的地方）：

编码时不再看任何全局频次，只按训练阶段学到的 merge 顺序依次尝试应用。

换句话说，训练得到的不是一张「词表」那么简单，而是一个有序的合并规则列表（merge rules）。遇到训练时没见过的词，就按规则的先后顺序能合就合。这是 BPE 与「查表切分」的本质区别，也是面试官最常拿来分辨「真的写过」还是「看过介绍」的一问。

为什么生产 tokenizer 多是字节级 BPE：字符级 BPE 需要维护一张完整字符表，遇到表外的 emoji 或生僻字仍会 OOV；字节级把所有文本先转成 UTF-8 字节序列（256 个符号打底），永远不会 OOV，且能无损还原任意字符串。GPT-2 系的做法是先做一次 byte-to-unicode 映射，把不可打印字节映射到可打印区间，避免控制字符污染输出。

WordPiece 与 Unigram：三个算法的判据差异 ​

WordPiece（BERT 系）的合并判据不是频次，而是似然增益。 对一对候选 ，它比较的是

即「合并后一起出现」相对于「各自独立出现」的比值——优先合并那些单独出现得很频繁、但一起出现得更频繁的对。一个高频词对如果两个符号本来就各自极常见，得分反而低。这比纯频次多了一层「意外性」权重。

WordPiece 的编码用最长匹配优先（greedy longest-match-first）：从词首开始，尝试最长的能匹配词表的前缀，匹配不到就回退一格。续接子词用 ## 前缀标记（playing → play + ##ing），用来告诉模型「这个片段是接在后面的，不是词首」。

Unigram（T5 / SentencePiece 的一种模型类型）方向相反 —— 自顶向下剪枝：

  1. 用一个大得多的初始词表开始；
  2. 用 EM 算法在当前切分下估计每个子词的概率；
  3. 计算「删掉某个子词后总似然的损失」，删掉损失最小的一批；
  4. 重复直到词表降到目标大小。

解码时用 Viterbi 找概率最大的那条切分路径。所以：

BPEWordPieceUnigram
方向自底向上合并自底向上合并自顶向下剪枝
合并判据相邻对频次最大似然增益最大删除后似然损失最小
编码方式按 merge 秩依次应用最长匹配优先Viterbi 最大概率路径
概率模型无显式概率无显式概率每个子词有概率
采样能力不可不可可按概率采样多个切分（正则化）
代表模型GPT 系、RoBERTaBERTT5（SentencePiece unigram）

「BPE 是合并、Unigram 是剪枝」这句对比是这一节的考点，能接着说出「所以只有 Unigram 能做 subword regularization（同一句话采样出不同切分，作为数据增强）」就超出平均线了。

SentencePiece：把空格也当成符号 ​

前面两个算法的前提都是「先按空格预分词」。这对中文、日文、泰语不成立（没有空格），而且不同语言需要不同预处理，很难维护。

SentencePiece 的做法是把输入当作原始字符流，不做任何语言相关的预分词：

  • 空格被当成一个普通符号，在文本里显式表示成 ▁（U+2581，下划线块字符）。Hello world 在内部是 ▁Hello▁world。
  • 支持 unigram 与 bpe 两种模型类型（选哪个是超参，不是两套框架）。
  • 可逆：因为空格被显式编码了，decode 能原样还原空格与换行，不需要额外的「去子词标记」逻辑。

这是它相对「按空格切 + BPE」的关键差别：后者一旦遇到无空格语言或异常空白，还原就会出问题。

特殊 token 与 chat template 的接缝 ​

特殊 token 不是普通 token，它们在词表里占固定 id，且必须被 tokenizer 当作不可分割的原子。

BERT 系[CLS] [SEP] [PAD] [MASK]句首聚合位、句边界、填充、掩码
LLaMA 系<s> </s>BOS / EOS
ChatML 系`<im_start

BOS / EOS 在自回归生成里各有硬作用：BOS 给「序列开头」一个可学习的表示（否则第一个 token 没有左侧上下文可用）；EOS 是停止信号——解码时一旦采样出 EOS 就终止，否则模型会把所有上下文窗口都填满。

原子性为什么会咬人：如果某个特殊 token 没被注册（或用了不匹配的 tokenizer），它会被切成一串普通 token。例如 <|im_end|> 会被切成 < | im _end | > 这类片段。此时：

  • 你的停止符字符串匹配可能仍然生效（因为原文恢复后一样），但
  • 你的对话模板解析会崩：模型学到的 <|im_end|> 是一个原子标记，现在它看到的是一堆散片，位置与语义都对不上。

在流式（SSE）场景下还有一个真实工程坑：<|im_end|> 的字符可能被拆在两个 chunk 的边界上。如果你每收到一个 chunk 就做一次 if "<|im_end|>" in buffer，这个 token 会被漏掉，停止条件失效，生成一直跑到 max_tokens。正解是维护一个滚动缓冲区并做跨 chunk 的尾部拼接匹配。

加新特殊 token 的代价：vocab_size 必须与权重的 embedding 行数一致。手动加 token 会让 len(tokenizer) 与 model.get_input_embeddings().weight.shape[0] 不一致，必须 resize 模型 embedding，且新 token 的向量初始是随机的，需要用数据训练，不能期望它开箱可用。

词表大小对模型的连带影响 ​

这是一个两头都疼的权衡：

  • 词表变大：embedding 与输出层参数变大（V × d_model 量级）；低频 token 的向量训练不充分（出现次数太少，梯度信号弱）。
  • 词表变小：同一段文本被切成更多 token，序列变长 → 注意力 成本上升、KV Cache 变大、有效上下文变短。

所以词表大小不是「越大越好」也不是「越小越省」，而是在参数预算与序列长度预算之间取平衡。这个结论能直接说出口。

中文与多语言的 token 效率 ​

UTF-8 编码下，ASCII 字符占 1 字节，而常用汉字占 3 字节。这会带来两个连锁反应：

  1. 字节级 BPE 下，一个汉字至少要 3 个字节符号起步；如果该汉字所在的组合在词表里没有覆盖，就会被切成多个 token。
  2. 词表覆盖率高（中文语料占比大）的 tokenizer，能把常见汉字或常见词直接映射成 1 个 token；覆盖率低的 tokenizer（纯英文预训练）会把一个汉字切成 2–3 个 token。

关键纪律：不要凭感觉报数字。 正确说法是：「用 tokenizer 实测过，同一个句子里中文的 token 化倍率与英文不同，具体倍率取决于该 tokenizer 的词表覆盖，我的方法是……」

三个连带后果，每一个都对应你项目里的一个决策：

  • 上下文容量：标称 128k token 的窗口，装中文时能装的字数比装英文少。截断策略必须按 token 算，不能按字符算。
  • 计费口径：按 token 计费时，中文请求的实际成本高于「按字数估」的直觉值。成本报告必须用 tokenizer 数出来的真实 token 数，而不是 len(text)。
  • 切块策略：按 512 字符切与按 512 token 切，在中英混合语料上得到的块大小完全不同。消融实验的三档长度必须先统一换成 token 再比较，否则不同档位之间的语言构成差异会污染结论。

片段 A：从零手写 BPE 的训练与编码（GPT-2 风格，含词尾标记）

python
from collections import Counter

def get_stats(ids_list, counts=None):
    """统计所有相邻符号对的频次。每个 id 序列后面拼一个 '</w>' 表示词尾。"""
    counts = Counter() if counts is None else counts
    for ids in ids_list:
        for pair in zip(ids, ids[1:]):
            counts[pair] += 1
    return counts

def merge(ids, pair, new_id):
    """把序列里所有出现的 pair 替换成 new_id。"""
    out, i = [], 0
    while i < len(ids):
        if i < len(ids) - 1 and ids[i] == pair[0] and ids[i + 1] == pair[1]:
            out.append(new_id)
            i += 2
        else:
            out.append(ids[i])
            i += 1
    return out

def train_bpe(corpus, vocab_size):
    """按空白预分词，词尾加 </w>，然后反复合并最高频的相邻对。"""
    words = [list(w) + ['</w>'] for w in corpus.split()]
    symbols = sorted({s for w in words for s in w})
    vocab = {s: i for i, s in enumerate(symbols)}
    merges = {}                                   # (a, b) -> 新 id
    ids_list = [[vocab[s] for s in w] for w in words]

    while len(vocab) < vocab_size:
        stats = get_stats(ids_list)
        if not stats:
            break
        pair = max(stats, key=stats.get)          # 打破平局时用 max 的字典序保证可复现
        new_id = len(vocab)
        vocab[f"{vocab_inv(vocab, pair[0])}+{vocab_inv(vocab, pair[1])}"] = new_id
        merges[pair] = new_id
        ids_list = [merge(ids, pair, new_id) for ids in ids_list]
    return vocab, merges

def vocab_inv(vocab, idx):
    """id 反查符号。真实实现里应该维护双向字典，这里为了短写成函数。"""
    for k, v in vocab.items():
        if v == idx:
            return k
    raise KeyError(idx)

def encode(text, vocab, merges):
    """编码：先按空白与词尾拆成符号，再按 merge 的先后顺序依次应用。"""
    out = []
    for word in text.split():
        ids = [vocab[s] for s in list(word) + ['</w>']]
        for pair, new_id in merges.items():       # dict 保持插入顺序 = 合并先后顺序
            ids = merge(ids, pair, new_id)
        out.extend(ids)
    return out

def report(name):
    tok = AutoTokenizer.from_pretrained(name)
    print(f"== {name} ｜ vocab_size={tok.vocab_size} ==")
    for text in CORPUS:
        ids = tok.encode(text)
        n_chars = len(text)
        print(f"  chars={n_chars:4d}  tokens={len(ids):4d}  "
              f"chars_per_token={n_chars / len(ids):.2f}")
        print("   ", tok.convert_ids_to_tokens(ids)[:20])

for model_name in ["bert-base-chinese", "gpt2"]:
    report(model_name)

和你自己的项目对上号 ​

① 项目二的三档切块消融（512 / 1024 / 2048）必须先统一到 token 才能比。 你的论文语料是中英混合（RL / USV / 控制方向，正文英文居多但摘要与术语常带中文）。同一个 token 数对应的字符数在两种语言上完全不同：512 token 在英文里约等于几百个单词，在中文里对应的字符数更少。如果不同档位之间的语料语言构成有差异，你的消融结论里就混进了一个「语言」变量。

可执行的换算脚本思路：遍历全部 PDF 抽出的文本，对每一篇用 bge-m3 的 tokenizer 分别统计「字符数 / token 数」与「中文字符占比」，然后取分位数（中位数、p10、p90）而不是平均数——因为中英混排的分布是双峰的，平均数会给出一个两种语言都不代表的数。

② jieba 与 subword 是两条并行路线，不能混用。 YYHelp 的稀疏路用 jieba 做中文分词建 BM25 倒排，稠密路用 bge-m3 自带的 subword 分词。为什么不能互换：

  • BM25 的检索单位是词，靠的是词频与逆文档频率的统计意义。如果把 subword id 直接当检索单位，##ing 这种片段会跨词聚合，词频统计失真，IDF 也失去意义。
  • 反过来，把 jieba 切出的词喂给 bge-m3 也不成立——稠密模型只认自己的词表，喂进去的词会被它自己的 tokenizer 再切一遍。

这就是你「Milvus 单库双路 dense + sparse」结构里最容易讲错的一点：双路不是两种索引同一个词表，而是两套切分 + 两套打分，RRF 融合发生在打分层面，不是在 token 层面。把这句话说准，就说明你真的理解了自己搭的那套东西。

③ 成本报告必须按 token 算。 你项目二的成本报告如果用的是 len(text) 或字数，那它只能算「量级参考」。换成真实 token 数只需在预处理阶段多存一个字段（每篇文档、每个 chunk 的 token 数），之后所有成本与截断决策都有据可依。

④ 上下文预算是一道可以真加上的闸门。 在 FastAPI 层用 tokenizer 做一次预检，把 prompt 模板 + 检索片段 + 会话历史 + 生成预留四部分分别计数，超预算就先截断检索片段或降级会话历史。这道闸门的好处是错误在入口暴露，而不是等模型返回一个长度超限的报错。这是你 YYHelp 里一个成本很低但很能讲的工程点。

⑤ 流式 + 特殊 token 的坑（SSE 场景）。 你的主力 Agent 走流式输出 + ReAct 循环 + 工具调用。停止符（如 <|im_end|>）可能在 SSE 的 chunk 边界被切开。按 chunk 做 in 判断会漏判，导致生成跑满 max_tokens。正解是维护滚动缓冲区，把上一 chunk 的尾部若干字符与当前 chunk 拼接后再匹配。这个细节在面试里非常能打——它证明你真的调试过流式，而不是只看过文档。

可执行的小实验：写一个脚本，把 YYHelp 的 20 条测试 query 各跑一遍，分别统计 len(text) 与 len(tokenizer.encode(text))，打印两者比值的分布。再把同样的事情对你的论文摘要做一遍，对比中英文的两个分布。这份对比表可以直接进你的成本报告。

面试怎么问 ​

Q1：为什么用子词分词，不用词也不用字？

A（要点）：两端都有硬约束。word-level 有 OOV 与词表爆炸（词表百万级时 embedding 与输出层参数不可接受），且形态变化无法共享统计量；char-level 序列太长，注意力 成本被撑爆，且单 token 语义太弱。subword 让常见词保持整词、罕见词拆成可复用片段，在参数预算与序列长度预算之间取平衡。

加分句：「subword 的真正收益是共享统计量 —— running 和 runs 共享 run 的学习信号。这让低频词的表示质量不至于随词频线性下降。」

别说：「因为子词效果好/是主流做法」——这是描述现象不是解释原因。

Q2：BPE 的编码阶段是怎么工作的？

A（要点）：训练产出的是一张有序的合并规则表（merge rules），不是一张简单的词表。编码时按规则的先后顺序依次尝试应用，不再看任何全局频次。所以「用全语料的频次去切一句新句子」是错的——那是最常见的误解。

加分句：「这也解释了为什么 BPE 对同形词的切分是稳定的：同一个字符串拿到的 id 序列由规则顺序唯一决定，不依赖批大小或上下文。」

别说：「BPE 就是按词频把常用词整块切出来。」这是把 BPE 说成了词典匹配。

Q3：BPE 和 Unigram 有什么区别？

A（要点）：方向相反。BPE 自底向上合并（从字符开始，合并高频相邻对）；Unigram 自顶向下剪枝（从大词表开始，按 EM 估计概率，删掉似然损失最小的子词）。编码也不同：BPE 按 merge 秩应用，Unigram 用 Viterbi 找最大概率路径。

加分句：「因为 Unigram 给每个子词显式概率，它才能做 subword regularization —— 同一句话采样出不同的切分作为数据增强，这能提升模型的鲁棒性。BPE 没有这个能力。」

别说：「都是子词算法，差不多。」判据差异正是这题的分。

Q4：一个汉字算几个 token？

A（要点）：取决于该 tokenizer 的词表覆盖率，不能一概而论。 底层原因是 UTF-8 下常用汉字占 3 字节，字节级 BPE 至少要从 3 个字节符号开始合并；如果该汉字或它所在的常见组合在词表里被覆盖，就能压到 1 个 token，否则会切成 2–3 个。

加分句：「我的做法是实测：拿自己语料跑一遍 chars_per_token 分布，中英分开统计取分位数。因为我做成本报告和切块消融，都必须用 token 数而不是字符数——按字符算的 512 和按 token 算的 512 在中英混排语料上差很多。」

别说：「中文一个字一个 token」或「中文一个字两个 token」。这是本页最容易翻车的地方：报一个确定数字，等于告诉面试官你的数字是编的。

Q5：如果我想给模型加一个新的特殊 token 要做什么？

A（要点）：三件事。① 在 tokenizer 里注册，让它占一个固定 id，并确认它不会被切分；② vocab_size 与 embedding 行数必须一致，所以要 resize 模型的 embedding（输入侧和输出侧如果未共享权重，两侧都要处理）；③ 新 token 的向量初始是随机的，必须用带该 token 的数据训练过才有意义，不能假设加完立刻可用。

加分句：「还有一个坑是流式场景：停止符可能被拆在两个 chunk 边界上，用字符串匹配判断停止会漏判。我维护了一个滚动缓冲区做跨 chunk 拼接匹配。」

别说：「在 tokenizer 里加一行就行。」会立刻被追问「那模型的 vocab_size 呢」。
