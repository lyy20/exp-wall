指令微调 SFT 与 LoRA / QLoRA ​

覆盖知识点：L1-15 L1-17 ｜ 面试频率：高 ｜ 建议学时：9h

一句话说清 ​

SFT 用「指令-回答」配对数据做一次分布切换，把基座模型变成会听话的助手；它的目标函数与预训练完全相同，差别只在数据形态与损失范围。LoRA 解决的是「微调太贵」这个问题：它冻结原权重，只在每个线性层旁边加一个低秩增量 ，训练参数量降到原来的千分位量级；因为 可以在推理前合并回原权重，所以不增加推理延迟。QLoRA 在此基础上把冻结的基座模型量化到 4-bit 存储，让单卡微调大模型成为可能。

为什么必须学 ​

这一页是「你懂不懂训练」这条分界线上的核心考点，而且它是你项目里最可能被追问的假设性问题：面试官看到你的简历全是 API 调用，很可能会问「如果让你微调一个模型来优化你的意图分类，你会怎么做」。答不出 LoRA 的秩、显存估算、以及「该微调什么、不该微调什么」，这道题就是零分。

三个高频考法：

  1. 「SFT 和继续预训练有什么区别？」 —— 考你是否知道目标函数相同、差别在数据与损失范围。
  2. 「LoRA 为什么有效？秩怎么选？」 —— 低秩假设 + 参数量公式 + 实践选择依据。
  3. 「QLoRA 是怎么省显存的？省的是哪一部分？」 —— 这是区分「听说过」和「算过显存」的关键题。答案不是「量化了一下」，而是基座权重的存储精度与优化器状态这两大块的具体变化。

核心内容 ​

L1-15 指令微调 SFT ​

数据形态：从「文本」到「指令-回答配对」 ​

预训练数据是连续文本；SFT 数据是结构化的配对。最常见的两种组织方式：

  • 单轮指令：{"instruction": "...", "input": "...", "output": "..."}（Alpaca 风格）。
  • 多轮对话：{"messages": [{"role": "system", "content": "..."}, {"role": "user", ...}, {"role": "assistant", ...}, ...]}（OpenAI / ChatML 风格）。
维度预训练SFT
数据形态连续无标注文本指令-回答配对 / 多轮对话
目标函数下一 token 预测（交叉熵）完全相同
损失范围整条序列通常只在 assistant 回答的 token 上
数据规模万亿 token 量级数万到数十万条样本
目的获取知识与语言能力对齐格式与行为

「目标函数相同」这一点必须先说清：SFT 不是一种新算法，它是一次分布切换。模型的能力没有新增，只是被引导到「按指令作答」这个分布上。这就是为什么少量高质量数据就能显著改变行为。

chat template：SFT 的隐性接口 ​

上面那些 role 字段在送进模型之前，必须被渲染成一个带特殊 token 的字符串，这个过程就是 chat template。以 ChatML 风格为例（示意）：

三条硬约束：

  1. 特殊 token 必须原子化：<|im_end|> 必须是一个 token，不能被切成散片（见 Tokenizer 那页）。
  2. 训练与推理必须用同一套模板：包括换行、空格、边界 token 的位置。模板漂移会让模型认不出角色边界，表现为「回答里混入用户口吻」或「把格式说明当回答输出」。这是最常见的隐性故障。
  3. loss 只在 assistant 段计算：即把 system 与 user 的 token 标签设成忽略值。若对 prompt 也算损失，模型会学着「生成用户的提问」，明显损害对话质量。

SFT 的实践要点 ​

  • 数据质量 > 数据量：少量高质量、格式一致的样本，通常优于大量噪声样本。噪声会教坏格式这一最脆弱的部分。
  • 灾难性遗忘：SFT 数据分布过窄会削弱基座模型的其他能力。缓解手段是混入通用指令数据或少量预训练数据。
  • 数据配比本身是能力旋钮：推理、代码、多语言、拒答四类样本的比例会直接塑造模型的能力结构。
  • 一条最容易忽略的：SFT 也可能「教出」幻觉的表述风格。如果训练数据里的回答总是自信、详尽的，模型在缺信息时也会保持同样自信的语气 —— 这是第 12 页幻觉话题的一条重要来源。

SFT 的局限（为什么还需要偏好优化） ​

SFT 是模仿学习：它在最大化「给定指令时，标注回答的似然」。所以它只能说「这个回答是对的」，不能说「回答 A 比回答 B 更好」。而「更好」是比较判断，难以写成唯一的标准答案 —— 这是偏好优化（第 10 页）的动机。

动机：全参数微调的显存账 ​

为什么 LoRA 不增加推理延迟（这一节的关键句） ​

因为 可以在推理前合并进原权重：

合并后就是一个普通的 矩阵，前向计算与原始模型完全一致，没有任何额外算子、没有额外的 kernel launch、没有额外的内存读取。这就是 LoRA 相对 adapter 类方法（在层间插入额外模块，会串行增加延迟）的决定性优势。

但要补上那个常被忽略的反面：合并的前提是「只服务一个任务」。如果你想同时服务多个不同的 LoRA（多租户场景），就不能合并，只能在推理时动态切换适配器 —— 这时会有额外的调度成本。这个取舍说出来是加分项。

该把 LoRA 加在哪一层 ​

位置说明
（注意力投影）最经典的配置，覆盖注意力机制的全部线性变换
FFN 的三个矩阵（含 SwiGLU 的 gate/up/down）有些实践认为收益更大，因为 FFN 是参数与容量的大头
Embedding / LM Head通常不加：参数量大（），低秩近似的收益低且容易过拟合

实践规律：把 LoRA 施加到更多的层（而不是只加在 ）通常比单纯提高秩 更有效。这个「广度优于深度」的结论说出来很有说服力 —— 它的直觉是：适配需要的是在多个子空间生效，而不是在一个子空间里更精细。

秩 怎么选 ​

  • 越大：拟合能力越强，可训练参数越多，越容易在小数据集上过拟合。
  • 越小：参数越少，越保守，可能欠拟合。
  • 常见区间： 取 4 到 64 这个量级，配合把 设为 的 1 至 2 倍。
  • 选择依据：数据量与任务难度。数据越多、任务与预训练分布差得越远，越需要更大的 。但不要报「最优 是多少」 —— 它依任务而定，说「用验证集扫一遍」才是正确的回答。

QLoRA：把基座量化到 4-bit ​

QLoRA 的三个技术点：

① 4-bit NormalFloat（NF4）量化。 一种为「近似正态分布」的权重设计的信息论最优的 4-bit 数据类型：把权重按分位数划分到 16 个桶，让每个桶被取到的概率相等。它的前提假设是「神经网络权重近似零均值正态分布」，这是长期的经验观察。

② 双重量化（double quantization）。 分块量化时每块要存一个量化常数（scale）。这些常数本身也占内存。双重量化把这些常数再量化一次，进一步压缩。

③ 分页优化器（paged optimizers）。 用统一内存（CPU/GPU 之间的分页机制）在显存尖峰时把优化器状态换出到内存，避免 OOM。本质是拿时间换显存。

关键的显存变化在哪里？

项目LoRA（fp16 基座）QLoRA（4-bit 基座）
冻结的基座权重 字节约 字节（4-bit = 半个字节/参数）
LoRA 适配器极小（千分位）极小
梯度只需适配器的只需适配器的
优化器状态只需适配器的只需适配器的

所以 QLoRA 省的是「冻结权重的存储」这一大块。 注意说法要精确：量化的是冻结的基座权重，可训练的 LoRA 适配器仍以较高精度（如 bf16）计算 —— 前向时反量化到计算精度。说「QLoRA 把整个模型都变成 4-bit 训练」是不准确的。

代价：反量化带来额外计算开销，训练更慢（不是更快）；4-bit 的表示精度有损，效果通常略低于同配置的 16-bit LoRA（但差距往往不大）。它的价值是「能不能在单卡上跑起来」，而不是「更快更好」。

一条必须建立的判断力：什么时候该微调，什么时候不该 ​

你的瓶颈正确手段
模型不知道某条事实RAG / 工具调用（微调不擅长注入可更新的事实）
输出格式不稳定prompt + 结构化输出约束（低成本）；若仍不稳才考虑 SFT
任务的风格 / 语气 / 领域表达需要统一SFT / LoRA（这正是它擅长的事）
领域词汇理解不到位（如医学、法律黑话）LoRA 或继续预训练（但需要足够语料）
需要多步推理换更强的模型或 CoT / 推理模型，微调不是首选
成本/延迟需要下降蒸馏或换小模型，微调解决的是质量不是成本

和你自己的项目对上号 ​

① 面试官问你「怎么不微调」，先定位瓶颈再谈手段。 你项目二的评测是分层的：检索层与生成层分开测。如果 badcase 分析显示错误集中在「召回失败」，微调生成模型对这个错误完全无效 —— 因为正确信息根本没进上下文。这是你最强的一条论证：不是「微调太贵所以不做」，而是「我定位过瓶颈，微调解决不了它」。 你 36 个消融脚本在证明的正是这个定位能力。

② 你的意图分流（9 类意图到 5 个出口）是最像微调任务的地方。 面试官很可能会说：「那你为什么不微调一个小模型来做意图分类？」这个问题要认真准备，答案是分层的：

  • 先看数据条件：你项目一的语料是合成的，评测集是本人标注的。合成数据训分类器容易学到模板噪声；评测集规模也撑不起一次可靠的微调评估。说出这一点是诚实，不是示弱。
  • 再看收益：意图分类是一个输出空间极小（9 类）的任务，用 LLM 直接在 prompt 里做，配上 few-shot 示例，通常已经足够。微调的真实收益是成本与延迟（用小模型替代大模型调用），而不是准确率 —— 所以它的正确动机是「降本」。
  • 如果要做，怎么做：LoRA 微调一个小规模的开源模型做分类头，用你的 9 类标注数据 + 合成数据混合；评估必须用你自己的分层评测集，并用配对检验对比「微调小模型」与「prompt + 大模型」的准确率与延迟/成本。注意：降本只有在准确率不退化到阈值以下时才成立。
  • 风险点：分类任务的类别分布会漂移（业务新增意图），微调后的模型需要重训才能认识新类别，而 prompt 方案改几个示例就能上线。这个「可更新性」的对比是这套系统里最实际的工程考量。

③ LoRA 的秩与你的「消融思维」天然契合。 你有 36 个消融脚本。如果做 LoRA，该扫的超参就是 与 、以及 LoRA 施加的层位置。特别注意那个可以照搬的规律：「加更多层」通常优于「加更大秩」 —— 这与你在检索侧做的「先动哪一个旋钮」的消融纪律一模一样。这是你已经有方法论的地方，只是换个应用对象。

④ 「不增加推理延迟」这条正好对上你的成本报告。 你的成本与延迟基准关心的是端到端延迟。LoRA 的合并特性意味着「微调后不会让推理变慢」，这在工程决策里是非常重要的一条 —— 很多方案（adapter、prompt tuning、更长的 few-shot）都会增加延迟或占用上下文预算，而 LoRA 合并后是零额外成本。能把这个取舍说清楚，说明你是在做系统优化而不是在堆技术名词。

⑤ 你的评测门禁同样适用于微调评估。 如果你的微调实验得出「准确率从 0.72 涨到 0.75」，这正是你项目二回归门禁要管的事：配对检验 + 效应量门槛 + 三态退出码。微调不是免于统计检验的特权路径 —— 把这句话说出来，你就把 L1 的训练议题和你已有的工程体系接上了。

可执行的小实验（做完就有实物证据）：用 LoRA 在你项目二的拒答二分类任务上做一次微调对照：

  • 任务定义：给定 (query, 检索到的片段)，判断是否应该拒答。
  • 数据来源：项目二天然拥有「不可回答」测试集（问你语料里不存在答案的问题），配合正常可回答问题，构成一个二分类数据集。
  • 对照组：① prompt + few-shot 直接用 LLM 判断；② LoRA 微调一个小规模开源模型。
  • 指标：准确率（配对检验）、延迟（p50 / p95）、单次调用的 token 成本。
  • 判据与预期：微调方案应在延迟与成本上有明显优势，而准确率是否持平取决于数据量 —— 如果准确率明显下降，那结论就是「这个任务的数据量还不够支撑微调」，这同样是一个有价值的结论，写进笔记就是一条真实的工程经验。

面试怎么问 ​

Q1：SFT 和继续预训练有什么区别？

A（要点）：目标函数完全相同（都是下一 token 预测的交叉熵）。区别在：数据形态（指令-回答配对 vs 连续文本）、损失范围（通常只在 assistant 回答段 vs 全序列）、数据规模（数万条 vs 万亿 token）、目的（对齐格式与行为 vs 获取能力）。

加分句：「因为目标函数一样，SFT 本质是一次分布切换而不是新算法 —— 这解释了为什么少量高质量数据就能明显改变行为，也解释了为什么它对注入新知识效率很低。」

别说：「SFT 用的是分类损失。」那把 SFT 与奖励模型训练搞混了。

Q2：SFT 训练时为什么只在回答上算损失？

A（要点）：因为对 prompt 也算损失会让模型学着生成用户的提问——label 就是右移一位，prompt 段的标签正好是用户的话。后果是模型输出里混入用户口吻、或者把格式说明当回答输出，明显损害对话质量。实现上就是把 system / user 段的标签设成忽略值。

加分句：「这条和我的工程实践是对应的：prompt 模板与 few-shot 示例是条件，不是要生成的内容。所以我在做输出解析时会把角色边界交给特殊 token 和模板管理，让模型只负责生成结构化结果。」

别说：「不知道，应该是 prompt 和回答都算吧。」这是能当场验证的设计细节，答含糊会被认为没读过训练代码。

Q3：LoRA 的原理是什么？为什么它不增加推理延迟？

A（要点）：低秩假设 —— 微调的增量 是低秩的，于是把它参数化 ， 冻结，只训 与 （ 高斯初始化、 初始化为零，保证起点等于原模型）。参数量从 降到 ，、 时约 0.4%。

不增加延迟的原因是它能合并： 就是一个普通的 矩阵，前向计算与原始模型逐算子一致。

加分句：「但合并的前提是只服务一个任务。多租户场景下要同时挂多个适配器，就不能合并，得在推理时动态切换 —— 那时会有额外调度成本。这是个真实的取舍，不是免费午餐。」

别说：「LoRA 就是在原模型上接一个小模块。」那是 adapter，不是 LoRA —— adapter 会串行增加延迟。

Q4：秩 该怎么选？加在哪些层？

A（要点）： 大拟合能力强、参数多、小数据上容易过拟合； 小更保守。常见区间是 4 到 64，配合 取 的 1 至 2 倍（关键是让 稳定）。通常不加在 embedding 与 LM Head（参数量大、低秩收益低）。

加分句：「有一条比调 更有效的规律：把 LoRA 施加到更多层（不止 ，还包括 FFN 的几个矩阵）通常优于单纯提高秩。直觉是适配需要在多个子空间里生效，而不是在一个子空间里更精细。另外 没有普适最优，正确做法是用验证集扫一遍。」

别说：「 越大效果越好」，或者报一个「最优 」。前者错，后者是编造。

Q5：QLoRA 省的是哪一部分显存？

A（要点）：省的是冻结基座权重的存储：从 fp16 的 字节压到 NF4 的约 字节（四分之一）。梯度与优化器状态本来就只覆盖 LoRA 适配器，LoRA 已经省掉了。另外两个辅助技术是双重量化（把分块的量化常数再压一次）与分页优化器（显存尖峰时把优化器状态换出到内存）。

注意说法要精确：量化的是冻结权重，可训练的 LoRA 适配器仍以较高精度计算，前向时反量化到计算精度。代价是反量化带来额外计算，训练更慢，且精度略低于 16-bit LoRA。

加分句：「所以 QLoRA 的价值是『能不能在单卡上跑起来』，不是『更快更好』。如果用 fp16 LoRA 就放得下，那没必要上 QLoRA。」

别说：「QLoRA 把整个模型变成 4-bit 训练。」这是不准确的，Adapter 与优化器状态不是 4-bit。

Q6：什么时候该微调，什么时候不该？

A（要点）：按瓶颈定位。事实更新/知识注入 → RAG 或工具调用（微调不擅长注入可更新事实，且难以审计）；格式不稳定 → 先 prompt 与结构化输出约束；风格、语气、领域表达需要统一 → SFT / LoRA（这是它最擅长的）；领域词汇理解 → LoRA 或继续预训练；要多步推理 → 更强模型或 CoT / 推理模型；要降成本或降延迟 → 蒸馏或换小模型。

加分句：「我的判断顺序是先看评测的分层结果：错误集中在检索就修检索，集中在格式就改 prompt，只有确认瓶颈在模型的行为方式时才考虑微调。这样微调是一个有依据的决定，而不是默认动作。」

别说：「看情况。」要说清看哪个指标、按什么顺序判断。

Q7：SFT 之后模型变差了（其他能力下降）怎么处理？

A（要点）：这是灾难性遗忘。缓解手段：混入通用指令数据或少量预训练数据做数据配比；降低学习率、减少训练轮数；用 LoRA 等参数高效方法（只动一小部分参数，对原能力的扰动更小）；也可以在多个任务的数据上混合训练而不是顺序训练。

加分句：「用 LoRA 本身就有抗遗忘的意味 —— 它冻结了原权重，改动被限制在一个低秩子空间里，所以对无关能力的扰动天然更小。这也是它在小数据微调场景受欢迎的原因之一。」

别说：「多训几轮就好了。」方向反了，往往越训越偏。
