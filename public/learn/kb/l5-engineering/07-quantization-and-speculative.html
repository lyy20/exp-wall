量化推理、投机解码与推理/业务服务耦合方式 ​

覆盖知识点：L5-13 量化推理 ｜ L5-14 投机解码 ｜ L5-15 推理服务与业务服务的耦合方式 面试频率：高 ｜ 建议学时：12h

一句话说清 ​

量化买的是显存与带宽（代价是精度），投机解码买的是延迟（代价是额外显存与算力）；而"把推理服务放在哪"是一个部署拓扑问题，它的答案取决于业务服务是同步调用还是异步任务。

为什么必须学（面试官视角） ​

这三个知识点覆盖了面试官的三种问法：

  1. "24G 卡能跑 32B 吗？"——考量化，而且是一个需要算账的问题，不是问你能不能背出 GPTQ 三个字母。
  2. "怎么让生成更快？"——考你能不能分清"总时长"和"每 token 时间"，投机解码只改后者。
  3. "你的推理服务跟业务服务是一个进程还是两个服务？"——考部署拓扑意识，这是应届生最容易答得含糊的一题。

⚠️ 本页纪律：量化方案的具体算法规格、各引擎支持的精度列表与参数名、投机解码的配置字段、K8s 相关字段，一律以官方文档为准。本页只讲机制、取舍与判据。

核心内容 ​

L5-13 量化推理 ​

1）量化到底在换什么 ​

定义：把权重（以及可选的激活值、KV Cache）从高精度（如 FP16/BF16，16 位）压到低精度（FP8 / INT8 / 4bit 等），从而减少显存占用与显存带宽需求。

为什么显存带宽这么关键：自回归解码每一步只生成一个 token，但要读一遍全部权重与整个 KV Cache。所以 decode 阶段是访存密集的——限制它的通常不是算力，而是"每秒能搬多少字节"。位宽减半，理论可搬的量翻倍，decode 速度随之上升。这解释了一个反直觉的现象：同样的模型和卡，量化后往往不只是"省显存"，还会"变快"——省的和快的来自同一个原因。

为什么显存占用也重要：权重省下来的显存可以划给 KV Cache 池，从而允许更多并发序列（见 06 页）。所以量化同时改善三个指标：单卡可装模型规模、decode 速度、并发容量。

2）四类方案的定位差异（只讲机制与取舍） ​

方案族主要对象机制要点典型定位代价
GPTQ 一类权重量化（训练后）逐层做量化并用校准数据补偿量化误差4bit 权重离线量化，追求"低比特可用"需要校准数据；离线性强，推理时按所选内核执行
AWQ 一类权重量化（训练后）基于"激活值分布中少数通道更重要"的观察，保护关键通道4bit 权重，通常精度更稳同上，且实现细节随内核不同
FP8权重（及部分激活）直接使用 8 位浮点，硬件原生支持时开销极低新一代 GPU 上的"无损优先"选择强依赖硬件是否原生支持该精度
GGUF 一类权重（多档位混合）分块/分档量化，允许不同层用不同位宽CPU / 混合推理、本地部署生态主要为本地运行服务，与高吞吐服务端的优化目标不同

必须主动说明的一句：这些方案在具体算法步骤、量化配置项名称、支持精度列表上差异很大且随版本变化，以官方文档为准；面试只要求讲清"为什么低比特还能保持效果"（校准/保护关键通道/分档）与"什么时候选哪一族"。

3）答案那个问题：24G 卡跑 32B ​

算账法（面试要展示的就是这个）：

text
权重显存 ≈ 参数量 × 每参数字节数
FP16/BF16（2 字节）：32B × 2 B ≈ 64 GB      ⇒ 单张 24G 卡装不下
INT8     （1 字节）：32B × 1 B ≈ 32 GB      ⇒ 仍装不下
4bit    （约 0.5 字节）：32B × 0.5 B ≈ 16 GB ⇒ 权重能装下

4bit 下权重约 16 GB，24 GB 卡剩下约 8 GB 要同时供给 KV Cache 池 + 激活/临时开销 + 框架开销。结论是："能装下"和"能跑得好"是两件事——能装下但 KV 池极小，并发上不去、长上下文直接爆；实际可行性与所支持的精度组合以官方文档与实测为准。

因此正确答案的结构是：

  1. 先算权重（上式）。
  2. 再看硬件是否支持想要的低精度（FP8 依赖硬件原生支持）。
  3. 再留 KV 池与激活余量，据此定 max_model_len 与并发上限。
  4. 最后必须用评测集验证效果损失——量化损失不是均匀的，长上下文、代码、数学类任务往往更敏感。

量化必须配的验证纪律：

  • 同一套评测集、同一批 prompt、同一解码参数，量化前后对照。
  • 报告要带样本量与口径；只报"感觉没变差"等于没验证。

误区更正
"量化只省显存，不影响速度"decode 是访存密集，位宽降低通常也提速——两个收益同源

L5-14 投机解码（Speculative Decoding） ​

定义：用一个更小更快的草稿模型先连续猜出若干 token，再让大模型一次前向并行验证这批 token，接受前缀匹配的部分、从第一个不匹配处继续。

机制与为什么有效：

  • 大模型 decode 的瓶颈是访存（每步读一遍权重与 KV，只换一个 token 的输出）。批量验证 k 个候选 token 的成本，与生成 1 个 token 的成本差别不大——因为读权重的量是一样的。这就是投机解码的立足点：用几乎相同的访存量，一次换来最多 k 个 token。
  • 数学上可证明：在理想接受率下，输出分布与直接用大模型解码是一致的（拒绝采样保证无偏）。这是它相对"用小模型直接回答"的根本区别——它不牺牲正确性，只压榨硬件利用率。
  • 收益取决于接受率：接受率高（草稿模型与大模型行为接近）时加速明显；接受率低时，验证的算力就白花了，甚至变慢。

关键设计取舍：

维度说明
草稿模型的来源独立的同族小模型 / 同模型的多头预测（如 Medusa 一类思路）/ 使用 n-gram 或检索结果做草稿
草稿长度 k越大潜在收益越高，但拒绝概率累积，实际接受长度有上界；k 需要调
采样一致性草稿采样与目标采样必须用同一套接受-拒绝规则，否则输出分布会被改变（这是最容易被忽略的正确性问题）
额外显存草稿模型本身要占显存，在"本来就显存紧张"的部署里可能是决定性代价
适用场景延迟敏感、并发低（如交互式单用户）。高并发批量场景下，直接把 batch 做大往往更划算

为什么高并发下不划算：投机解码提高的是单序列的每 token 速度，而高并发时 GPU 已经被批处理填满，吞吐瓶颈是总访存量；此时额外跑一个草稿模型反而抢走算力。

数量级与形状：收益上限由平均接受长度决定——若平均接受 m 个 token/次验证，理论加速比约为 m 倍，但实际要扣除草稿模型的开销与验证的额外计算，因此常显著低于 m。具体参数名、默认 k、支持情况以官方文档为准。

未执行验证：本页未跑过任何投机解码实验（无 GPU 环境）。验收方式：固定 prompt 集与解码参数，比较 P50/P99 TPOT 与输出 token/s，同时用同一脚本校验输出分布/质量未退化。

常见误区：

误区更正
"投机解码会降低质量"正确实现下不改变输出分布；质量退化通常说明接受-拒绝规则实现有问题
"加速比就是草稿长度"实际受接受率与额外开销限制，远低于 k
"所有场景都值得开"高并发吞吐场景通常不值；显存紧张时也不值
用不同采样参数对比采样参数一变，"是否无偏"就无法验证

L5-15 推理服务与业务服务的耦合方式 ​

三种拓扑，按耦合从紧到松：

拓扑形态优点代价 / 适用边界
同进程业务进程内直接加载模型或引擎零网络开销、无额外运维进程重、启动慢、无法独立扩缩容、故障域合并；只适合本地工具/单机 demo
独立推理服务推理以独立进程/容器/副本提供（通常暴露兼容 OpenAI 风格的 HTTP 接口）可独立扩缩容、独立升级模型、故障隔离；业务可无状态横向扩多一跳网络与序列化；需要处理超时、重试、限流、鉴权
网关/路由层业务不直连某个实例，而是经路由器决定"走哪个模型/哪个实例"可在网关做灰度、降级、成本归因、多供应商切换多一个组件要运维；路由策略本身成为故障点

判据（怎么选）：

  • 看调用是否在用户同步路径上：在 ⇒ 要低延迟、要超时与降级（独立服务 + 网关）；不在（离线批处理）⇒ 同进程批量跑更省事。
  • 看是否需要独立扩缩容：模型服务的资源曲线（GPU/内存）与业务服务（CPU/网络）完全不同，混在一起扩缩容一定浪费。
  • 看模型是否会独立迭代：模型/hosting 变化频繁 ⇒ 必须解耦，否则每次换模型都是一次全站发版。
  • 看是否有多个消费方：一旦有第二个消费方（另一个服务、离线任务、评测脚本），同进程方案立刻变成技术债。

为什么"网关/路由层"值得单独存在（这是最能体现工程判断的一档）：把"选哪个模型"从业务代码里抽出来，业务只说"我要一次生成"，路由层负责按复杂度、成本、可用性选目标。本项目正是这么做的：YYHelp 的 serve/routing.py（灰度打标 + 模型路由 + 成本记账）是库函数而非 HTTP 服务，decide_model(state) 按 plan 的 complexity 在 MODEL_SIMPLE_DEFAULT = "deepseek-flash" 与 MODEL_MULTI_DEFAULT = "deepseek-v4-pro" 之间选择，另有 MODEL_TIMEOUT_S = 30.0 与 BUDGET_WARN_RATIO = 0.90 两道闸门。

三种拓扑必须配套的工程能力（缺一项就会在生产上暴露）：

拓扑必须配套
同进程进程内并发上限、显存/内存熔断、优雅退出
独立服务鉴权（无鉴权 = 任何人都能让你花钱，见 service.py:60-68）、超时、重试（仅幂等）、限流、readiness 探针（验真实依赖）
网关/路由路由可观测（每次决策都要能被 trace 看到）、降级链、灰度开关、成本归因字段

面试怎么问 ​

Q1：24G 的卡能跑 32B 模型吗？

A（要点）：先算账。权重 ≈ 参数量 × 每参数字节数——FP16 约 64 GB（装不下）、INT8 约 32 GB（装不下）、4bit 约 16 GB（能装下，但只剩约 8 GB 给 KV 池 + 激活 + 框架开销）。

  • 加分句："我会把结论分成两句：'能装下'不等于'能跑好'；而且我会补一句验证纪律——量化前后必须用同一套评测集、同一批 prompt、同一解码参数对照，并写明样本量。只报'感觉没变差'等于没验证。"
  • 别说："4bit 量化就能跑。"（没有算账、没有 KV 余量、没有评测）
  • 追问 1：4bit 一定比 8bit 差吗？→ 不必然。取决于量化方案与任务类型；不能按位宽排序，必须实测。长上下文、代码、数学类任务通常更敏感。
  • 追问 2：为什么量化后还可能变快？→ decode 是访存密集的，每步要读一遍权重；位宽降低意味着同样带宽能搬更多参数。省显存和提速在这里是同源的。
  • 追问 3：FP8 有什么特别？→ 依赖硬件原生支持；原生支持时开销极低，是新一代 GPU 上"精度优先"的常见选择。支持列表以官方文档为准。

Q2：投机解码是什么？它会降低回答质量吗？

A（要点）：小模型当草稿连续猜 k 个 token，大模型一次前向并行验证，接受匹配前缀。正确实现下输出分布不变——这是它和"直接用小模型回答"的根本区别。加速来源是用几乎相同的访存量换多个 token。

  • 加分句："判断它值不值得开有两个条件：接受率够高，以及场景是低并发延迟敏感。高并发吞吐场景我一般不开——批处理已经把 GPU 填满了，再跑一个草稿模型是抢算力。"
  • 别说："小模型猜、大模型改，所以质量会差一点。"（把无偏性说反了，这是最危险的一处）
  • 追问 1：加速比是不是等于草稿长度？→ 不是。受平均接受长度与额外开销限制，实际远低于 k。
  • 追问 2：草稿从哪来？→ 同族小模型、同模型多头预测、或检索/ n-gram 类草稿。不同实现代价差别很大。
  • 追问 3：怎么验证"质量没退化"？→ 固定采样参数与 prompt 集，比较输出分布/评测分数，并比较 P50/P99 TPOT 与 token/s。只报速度不报质量，等于没验证。

Q3：你的推理服务跟业务服务是一个进程还是两个服务？怎么决定的？

A（要点）：判据看四件事——是否在用户同步路径上、是否需要独立扩缩容、模型是否独立迭代、是否会有第二个消费方。真实项目里我走的是独立服务 + 路由层：业务只发"我要一次生成"，路由层按复杂度选模型。

  • 加分句："我项目里的路由是一个库函数（serve/routing.py），不是 HTTP 服务。这个边界是刻意的：路由逻辑要被 Web 端点、离线评测、灰度脚本三处复用，做成 HTTP 服务反而增加三处调用成本。"
  • 别说："就写在一个 FastAPI 里。"（不区分资源曲线与故障域）
  • 追问 1：独立服务要多配套什么？→ 鉴权（没有鉴权，任何能访问端口的人都能让你花钱）、限流、超时、只重试幂等错误的策略、readiness 探针要验真实依赖。
  • 追问 2：--workers 1 还是多 worker？→ 多 worker 会让进程内状态（缓存、并发计数、限流窗口）各算一份，配额翻倍。要扩就得把状态外置或改扩副本。
  • 追问 3：网关层的路由怎么可观测？→ 每次决策都要能被 trace 看到。本项目用 stamp_route 打标 + object_versions 快照（prompt / 索引 / 路由三要素），所以能回答"这次为什么走了这个模型"。
