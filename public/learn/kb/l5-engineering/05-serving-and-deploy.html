服务化与容器化部署、配置与密钥注入 ​

覆盖知识点：L5-07 服务化与容器化部署 ｜ L5-08 配置与密钥的运行时注入 面试频率：高 ｜ 建议学时：7h

一句话说清 ​

服务化不是"把脚本包成 FastAPI"，而是三件可验证的事：探针要验业务最依赖的那次真实调用、错误码要能区分"谁的错"、密钥永不进镜像。

为什么必须学（面试官视角） ​

面试官问服务化，几乎必问的两个点都在这页：

  1. "liveness 和 readiness 有什么区别？"——能答出"一个决定要不要重启，一个决定要不要导流量"是及格；能给出"我的探针验的是哪次真实调用"才是过关。
  2. "密钥怎么管的？"——答"写在代码里/提交进 Git"直接淘汰；答"环境变量注入 + 不进镜像 + 日志脱敏"，再补一句"我做了启动时的配置校验，缺 key 就 fail fast"，是加分。

第三个高频点是错误码语义：504 vs 502 vs 503 vs 429 vs 401，能不能说清各自代表"谁的问题"，决定了你排障时能不能少打两小时电话。

核心内容 ​

L5-07 服务化与容器化部署 ​

1）服务化的最小完整形态 ​

一个 LLM 应用服务最少要有四部分：协议入口（路由 + 请求模型校验）、业务主干（被多个端点复用）、资源闸门（限流 + 并发上限 + 超时）、可观测出口（trace/日志/用量）。

端点设计的核心判据是"主干复用"。YYHelp 三个端点是：

端点行号作用
GET /health:696健康与就绪探测（def health(probe: str = "liveness")）
POST /ask:811非流式问答
POST /ask/stream:824流式问答

三者共用同一条主干 answer_question(question, *, trace_obj=None, ...)（:458），另有 programmatic_refusal(question) -> str|None（:401）与 pre_llm_gate(trace_obj, hits, threshold) -> str|None（:442）在主干之前做闸门判断。

为什么这样设计：如果 /ask 与 /ask/stream 各写一条链路，两条链路的行为一定会漂移（拒答条件不同、引用校验一个有 一个没有）。共用主干 + 流式只改"投递方式"，是让两条路保持一致性的唯一可靠办法。

应用对象与异常处理：app = FastAPI(title="YYHelp API", version="0.3.0")（:648），并显式注册 @app.exception_handler(RequestValidationError)（:659）与 @app.exception_handler(StarletteHTTPException)（:667）——让错误响应也是结构化的（统一字段、统一形状），而不是 FastAPI 默认的文本。中间件 @app.middleware("http")（:675）负责建立 trace_id 上下文。

2）健康检查：liveness vs readiness 的判据 ​

探针回答的问题失败时编排器的动作该验什么
liveness进程还活着吗重启容器进程/事件循环可响应即可
readiness现在能接真实流量吗从负载均衡摘除（不重启）业务最依赖的那一次真实调用

判据（本页最值钱的一句）：

探针要验业务最依赖的那一次真实调用，不是"对象能构造出来"。

反面案例（本项目真实记录）：RAG 服务写了后台线程预热（RAG_WARMUP=1 默认开），但 /health 秒回 200。后果是编排器在模型还没加载完时就把流量导进来，第一个请求照样等 48 秒。这条记录只有 rag-demo/service.py:73-78 的源码注释自述、没有原始日志留存，引用时应当如此标注。

正确的形态：让 readiness 反映真实依赖就绪状态。RAG 项目的做法可作参照：/health 的 detail 里带 llm / prompt_versions / limits / auth / ready / guard，并且

python
status = 503 if any(("缺索引" in p) or ("未就绪" in p) for p in problems) else 200
ready  = warm_state in ("done", "skipped") and not budget_out

2

配合 RAG_REQUIRE_WARM=1（未就绪则 503）。注意这里的语义分叉：缺索引或未就绪 ⇒ 503（readiness 失败，摘流量），而不是 500——500 会被当成 bug 触发告警风暴。

YYHelp 侧对应的是 /health?probe=readiness（14-serving.md docstring:133 记录"验真实依赖"）与模块级 self.llm_ready: bool = False（:138，:331 置 True / :334 置 False）。

为什么不能把 readiness 做成"重依赖全量自检"：readiness 可能被每几秒调一次。如果它每次都真调一次 LLM，探针本身就成了压测流量。取舍是：readiness 检查"依赖是否可用"（如一次轻量 ping / 缓存状态），而不是"每次跑一轮完整业务"。真实业务调用的验证（如 v1 api/app.py 的 selftest()）应该挂在显式的 /health?probe=... 或自检脚本上，不进编排器的探测路径。

依赖栈的真实形态（deploy/docker-compose.yml 行号）：mysql:83（mysql:8.4.11，容器名 yyhelp-mysql，宿主端口 3307）、etcd:145、minio:182、milvus:253、postgres:345、clickhouse:371、redis:424、langfuse-worker:455、langfuse-web:549、yyhelp-api:602；日志驱动 logging: {driver: json-file}（:72）。

4）错误码语义：让排障先于沟通 ​

码含义谁的问题该不该重试
401鉴权失败调用方否
402 / 429预算/配额超限、限流调用方（或容量规划）429 可退避重试；402 不重试
502上游返回了坏响应（LLMError，kind: upstream）上游/网关是（幂等时）
503本服务未就绪 / 并发满 / 配置缺（LLMConfigError，kind: config）本服务503 是"稍后可能好"，可重试
504超时（asyncio.TimeoutError）链路某一跳视幂等性

RAG 项目的映射就是一个标准答案：asyncio.TimeoutError→504、LLMConfigError→503（kind:config）、LLMError→502（kind:upstream）、熔断→402/429、限流→429（60 秒滑动窗口）、SSE 并发满→503、鉴权失败→401。

关键细节：错误响应要带 kind 这类机器可读字段，而不是只给人看的 message——否则前端/调用方只能靠字符串匹配判断该不该重试。

L5-08 配置与密钥的运行时注入 ​

定义：把随环境变化的东西（地址、端口、阈值、密钥）在运行时注入进程，而不是在构建时写进镜像。

机制——三条硬规则：

  1. 配置与代码分离：代码里只有"读配置 + 校验"的逻辑，没有具体值。
  2. 密钥不进镜像、不进 Git、不进日志：镜像层是可被任何有拉取权限的人反解的，一旦提交就等同于泄漏（要轮换，不是删掉提交）。
  3. 启动时校验（fail fast）：缺必需配置应当在启动时立刻失败，而不是等第一个请求才发现。

# 真实的读取形态（RAG guard.py / yyhelp api/app.py）

为什么用环境变量而不是配置文件：容器编排里环境变量是唯一在所有平台都一致的注入面（compose / K8s / 云函数都支持）。代价是：环境变量会出现在 docker inspect、崩溃转储和某些子进程的 /proc/<pid>/environ 里——所以敏感值应该走密管服务（如 Vault / 云 KMS / 编排平台自带的 Secret），由运行时以文件或内存形式注入，环境变量只放非敏感配置。具体密管服务的字段名与接入方式以官方文档为准。

多环境配置的落地方式（从低到高）：

方式适用风险
环境变量（.env 本地加载）本地开发、单机部署.env 容易误提交
编排平台 Secret生产容器需要平台权限治理
密管服务 + 短期凭据合规要求高的环境复杂度高，需处理续期

日志脱敏（最常被漏的一条）：RAG 项目的隐私纪律是默认不记 prompt 原文与用户问题原文，只记 question_len / top1 / chunk_ids / token 数；只有 RAG_LOG_PROMPTS=1 时才记（log_prompts_enabled():144-145）。同时 key 从日志里消失是必须的：日志系统是密钥最常见的泄漏路径（比镜像更容易被忽略，因为日志往往被集中收集且保留更久）。

鉴权的落地形态：RAG 侧同时支持 Authorization: Bearer <key> 与 X-API-Key；支持逗号分隔多 key 以便轮换；留空 = 关闭鉴权并在日志里明确警告。动机在 service.py:60-68 写得很直白：无鉴权时，任何能访问端口的人都能让部署者花钱。

容器化deploy/Dockerfile.api：python:3.12-slim:33、PYTHONUNBUFFERED=1:36、依赖层缓存 :56-57、uid 10001:74、EXPOSE 8080:80、HEALTHCHECK :89、uvicorn ... --workers 1:97索引/模型体积大 ⇒ 镜像分层与卷挂载更关键
配置注入YYHELP_RATE_LIMIT_PER_MIN 默认 60（app.py:120）RAG_MAX_CONCURRENCY 默认 2、RAG_WARMUP=1、RAG_REQUIRE_WARM、RAG_ALERT_COOLDOWN_S 默认 300
鉴权本层文档未逐行确认 header 名（待确认项）Authorization: Bearer <key> 与 X-API-Key 双支持、多 key 逗号分隔轮换、留空=关闭并告警
日志脱敏—默认不记 prompt/问题原文，只记 question_len/top1/chunk_ids/token；RAG_LOG_PROMPTS=1 才记

两个可以直接讲的真实缺陷（比完美答案更有说服力）：

  1. 限额块被复制粘贴定义两次（service.py:47-59）——配置的单一真源被破坏，两份值迟早漂移。
  2. from retrieve import retrieve 必须在模块顶层（service.py:38-43 注释）：函数内 import 会让模块级 monkeypatch 失效，导致离线测试偷偷加载 4.4 GB 模型，0.1 秒的测试变成 40 秒（实测输出里出现 Loading weights: 100%）。教训：可测性也是设计的一部分——import 位置这种小事会直接决定 CI 能不能跑。

面试怎么问 ​

Q1：liveness 和 readiness 有什么区别？你的探针验什么？

A（要点）：liveness 失败 ⇒ 重启容器；readiness 失败 ⇒ 从负载均衡摘除、不重启。判据是：探针要验业务最依赖的那一次真实调用，不是"对象能构造出来"。

  • 加分句："我这里踩过一个坑：我的服务写了后台线程预热，但 /health 秒回 200，编排器就在模型加载完之前把流量导进来了，第一个请求照样等 48 秒。这条在我项目里只有源码注释记录、没有原始日志，所以我现在会补的一件事是让 readiness 反映真实就绪状态，而不是反映进程能响应。"（引用时须注明只有 rag-demo/service.py:73-78 注释自述）
  • 别说："两个都是健康检查，都返回 200 就行。"（会被直接判定没做过部署）
  • 追问 1：readiness 里真调一次 LLM 会不会让探针变成压测？→ 会。所以取舍是readiness 检查依赖可用性（轻量），完整业务自检（如 selftest()）挂在显式路径或脚本上，不进编排器的高频探测路径。
  • 追问 2：未就绪该返回 503 还是 500？→ 503。500 会被当成代码 bug 触发告警风暴；503 语义是"我暂时不行"，编排器与调用方的动作都不同。
  • 追问 3：有没有持续健康度？→ 本项目没做（/health 只做一次性依赖探测），这是一个已知缺口：探针只能回答"此刻行不行"，回答不了"最近五分钟成功率是多少"。

Q2：你这个服务怎么部署的？镜像怎么写的？

A（要点）：python:3.12-slim 基础镜像，PYTHONUNBUFFERED=1，依赖清单先 COPY 再装依赖（利用层缓存），代码后 COPY，非 root 用户 uid 10001 运行，EXPOSE 8080，HEALTHCHECK 打 /health，CMD uvicorn ... --workers 1。

  • 加分句："我在项目里做过一次机械校验：compose 里 MinIO 的注释写着'用 digest 钉版本'，但 image: 行实际没带 digest、还是滚动 tag。我们写了 verify_compose_semantics.py 把它抓出来才补上。注释里的承诺不等于配置里的实现。"
  • 别说："就是 docker build 然后 docker run。"（没有任何纪律点）
  • 追问 1：--workers 1 为什么不加？→ 加多 worker 会让进程内状态（缓存、并发计数器、内存限流）各算一份，配额翻倍。要扩就要么改成共享存储，要么扩副本并让限流走外部存储。本项目选 --workers 1 是出于状态一致性的自觉。
  • 追问 2：为什么不 latest？→ 不可复现；昨天能跑今天不能跑时你无法确认是不是镜像换了。钉 digest 是唯一强保证。
  • 追问 3：日志怎么处理？→ json-file 驱动 + 结构化 JSONL；同时明确默认不记 prompt 与用户问题原文，避免把隐私写进日志，也避免日志体积失控。

Q3：密钥怎么管理的？

A（要点）：运行时注入 + 不进镜像 + 不进日志 + 启动时校验。环境变量适合非敏感配置；敏感值走密管服务并由运行时以文件/内存注入。

  • 加分句："我判断密钥是否泄漏的路径有三个：镜像层、日志、崩溃转储。最容易被忽略的是日志——因为日志会被集中收集且保留更久。所以我默认只记 question_len、top1、chunk_ids、token 数，不记 prompt 原文与用户问题原文。"
  • 别说："放在 .env 里，加进 .gitignore 了。"（只做了最小防护，且一旦误提交必须轮换而不是删除提交）
  • 追问 1：误提交了怎么办？→ 轮换密钥，而不是改写历史。泄漏面已经存在，删提交不改变事实。
  • 追问 2：配置缺失是启动失败还是用默认值？→ 分两类：有安全默认值的（限流阈值、并发上限）给默认值并在 /health 里暴露实际生效值；没有安全默认值的（密钥、上游地址）fail fast。RAG 的做法是 Authorization 留空 = 关闭鉴权，同时日志里明确警告——这是"允许但必须可见"的中间态。
  • 追问 3：多个实例怎么轮换 key？→ 支持多 key 并存（本项目逗号分隔），先加新 key、观察流量切完、再删旧 key。
