模型路由与降级、可观测三支柱与调用链追踪 ​

覆盖知识点：L5-16 模型路由与降级 ｜ L5-17 可观测性：日志/指标/Trace ｜ L5-18 LLM 调用链追踪 Tracing 面试频率：高 ｜ 建议学时：11h

一句话说清 ​

路由决定"这次让谁回答"，可观测决定"出事时你能不能知道是谁的锅"——而 LLM 应用的追踪必须贯穿多次模型调用才叫 Trace，只有一次调用的那种叫日志。

为什么必须学（面试官视角） ​

这三个知识点是"工程成熟度"的直接证据：

  1. 路由与降级：面试官会问"你的降级链是怎么判定的"。答"超时就降级"太粗；能说清"哪一层负责判定、降级后哪些行为必须保持一致（拒答语义、引用校验）、以及降级这件事本身必须被记录"才算过关。
  2. 可观测三支柱：会被追问"你埋在哪几个位置"。答"我打了日志"是零分；能说出"入口中间件建 trace_id、每次模型调用一个 span、每次工具调用一个 span、成本在响应返回后记一次、且所有埋点失败都不许影响主流程"才是满分。
  3. Tracing：最常见的坑是"接了 Langfuse 就算有 trace"。真实项目里的做法是双后端——自研 JSONL trace 作默认（零第三方依赖、离线可审计），Langfuse 作增强，两者用同一个 trace_id 缝合。

核心内容 ​

L5-16 模型路由与降级 ​

1）路由的三个决策维度 ​

维度决策依据项目里的形态
按复杂度对问题的难度做一次（便宜）判定，简单走小模型、复杂走大模型decide_model(state) 按 plan 的 complexity 选模型；MODEL_SIMPLE_DEFAULT = "deepseek-flash"、MODEL_MULTI_DEFAULT = "deepseek-v4-pro"
按流量比例灰度：把 x% 的流量导到新版本CANARY_ENV = "YYHELP_ROUTE_CANARY_PCT"，分流走 sticky_bucket(query)
按可用性/成本目标不可用或超出预算时切换MODEL_TIMEOUT_S = 30.0、BUDGET_WARN_RATIO = 0.90 两道闸门

粘性分桶（sticky bucketing）为什么是必须的：如果同一用户/同一问题在两次请求里被分到不同桶，A/B 对比就失效了——因为你无法区分"版本差异"和"分桶抖动"。sticky_bucket(query)（serve/routing.py:91）保证同一个 query 稳定落到同一个桶，这是回滚语义的前提：出问题时能说"这次流量里属于新版本的那部分"。

灰度的完整链路（可直接背）：

text
canary_pct（环境变量）
  → sticky_bucket(query)              # 稳定分桶
  → assign_route_version(query)       # 决定用哪个版本
  → object_versions 快照三要素        # prompt / 索引 / 路由，全部记进快照
  → stamp_route 打标                  # 给这次调用留下"走的哪条路"
  → plan 的 complexity
  → decide_model(state)
  → 模型

三个可灰度维度：prompt 版本、索引版本、路由策略。所以灰度对象不只是"模型"，还包括 prompt 与检索配置——这三者任何一个变了，行为都会变，必须都能被独立切换和回滚。

2）降级的四条纪律 ​

  1. 降级必须明确定义触发条件：超时（MODEL_TIMEOUT_S = 30.0）、上游错误、预算超限（BUDGET_WARN_RATIO = 0.90）。阈值的存在意义是让降级可判定，而不是"感觉慢就降"。
  2. 降级后行为必须保持一致：拒答语义、引用校验、错误码语义不能因为降级而改变。否则前端逻辑会被劈成两套。
  3. 降级必须被记录：每次降级都要留下"为什么降"的字段。没有记录的降级等于静默劣化——这是本项目明确踩过的坑：早期"循环擦着预算边过去"却被当成正常，日志里一切正常，恶化过程完全不可见。
  4. 降级要有界：降级链不能无限套娃（大模型 → 小模型 → 缓存 → 拒答）。每一跳都要有超时与预算约束，否则总时长不可控。

一个真实数量级的对照：YYHelp 实测 deepseek-v4-pro 单次 7.76 秒，MODEL_TIMEOUT_S = 30.0 按 P50 口径相对它留了约 4 倍余量（这个倍数是由 P50 相除得来的口径说明）。同一次批量调用里 deepseek-flash 挂起（不返回）、v4-pro 正常——记为台账 B18，属本机网关环境问题而非代码缺陷。关键结论：超时闸门必须存在，因为"不返回"比"变慢"严重得多；而没有超时，一次挂起就是整个请求永不返回。

L5-17 可观测性三支柱 ​

三支柱各回答一个问题：

支柱回答形态LLM 场景里的关键点
日志（Logs）这一件事发生了什么结构化事件（JSONL 一行一事件）默认不记 prompt 与用户问题原文；只记长度、命中项、token 数
指标（Metrics）系统整体在什么状态计数器/直方图LLM 的指标必须是 token 维度：输入/输出 token 数、缓存命中 token、成本；而非只有请求数
链路追踪（Traces）这一次请求经历了几跳、每跳多久span 树 + trace_idLLM 一次请求可能有多次模型调用 + 多次工具调用，这才是 Trace 的价值所在

中间件与响应头：tid = request.headers.get("x-trace-id") or obs.new_trace_id()，并把 tid 回写为响应头 X-Trace-Id（service.py:215-226）；响应体里也带 AskOut.trace_id（:246-261）。为什么要把 trace_id 回给调用方：用户报障时能直接给出一个 id，而不是"大概是下午三点那次"。

跨线程/跨进程传播是 Three Pillars 里最容易漏的一环：threading.local() 保证线程隔离，但线程池里的任务默认拿不到父线程的 trace；所以必须有 propagate(trace_id) 显式把 id 带进去（本项目 obs.py:99-116）。HTTP 中间件那条"复用客户端传入 x-trace-id"则解决了跨服务串联。

指标侧的真实阈值（本项目口径）：告警冷却 RAG_ALERT_COOLDOWN_S 默认 300 秒、错误率阈值 0.2、且要求最少样本 10 才评估。"最少样本"这一条最容易被忽略：没有它，凌晨两个请求里错一个就会触发 50% 错误率告警——告警本身就是一次事故。

告警的两条纪律：告警失败不能影响业务（本项目 webhook 在后台线程 threading.Thread(target=_post, daemon=True, name="alert")），但必须留痕（obs.log_event("alert.failed", ...)）；并且默认只落盘——RAG_ALERT_WEBHOOK 没配就绝不联网。另一个真实坑：钉钉关键词安全设置会导致静默拒收（errcode 310000），因此支持 RAG_ALERT_PREFIX 前缀兜底。

L5-18 LLM 调用链追踪 ​

定义：把一次用户请求内所有模型调用、工具调用、检索调用串成一棵树，每个节点有名称、起止时间、输入输出摘要与状态。

为什么 LLM 应用的 Trace 特别重要：传统微服务一个请求通常几次 RPC；而 Agent 场景一次请求可能有 十几次模型调用 + 数十次工具调用，还有循环与重试。没有 Trace，你只能看到"这次请求用了 12 秒"，看不到"12 秒花在第 7 次模型调用的工具参数上"。

双后端架构（本项目的核心设计，也是最值得讲的一处工程判断）：

后端定位理由
自研 JSONL trace默认路径零第三方依赖、离线可审计；Agent 场景离线评测管线依赖 trace 的文本形态
Langfuse v4增强路径可视化、跨服务聚合；但需要 5 个容器（langfuse-web / langfuse-worker / postgres / clickhouse / redis）

两者用同一个 trace_id 缝合：class Backend:122、class JSONLBackend(Backend):133、class LangfuseBackend(Backend):164、class _LFSpan:246、class Observability:315、init(name="yyhelp-ask", *, prefer="auto", **attrs):327、finish(obs, status="ok", output=None):359，另有 langfuse_installed():88 / langfuse_configured():94 判断可用性（v1 obs/langfuse_v4.py 474 行）。

为什么不能只有 Langfuse：需要 5 个容器 ⇒ 离线或资源受限环境整体失效。而离线评测管线正需要 trace：eval/run_ab.py 会把 trace_tail（最后 3 行、每行截 120 字符）与 trace_routing（[routing] 开头的行）抄进评测记录；serve/routing.py:290 的 parse_plan_complexity_from_trace(trace_tail) 用正则 \[plan\] complexity=(\w+)（:287）从 trace 文本里抠出真实复杂度。这说明：

trace 不只是给人看的可观测产物，它可以是下游程序的输入。一旦成为输入，它的格式就是接口——不能随手改。

降级纪律（v1 已定、v2 继承）：可观测降级不抛异常。写入失败时降级写 observability_degraded 事件。理由：观测是旁路，绝不能因为观测系统故障而让业务请求失败——观测系统最不该成为新的单点。

用 Trace 做延迟归因（本项目最强的一课）：

环节实测
首字延迟（TTFT）三次14.90 / 10.00 / 14.86 s
其中 CPU 精排 20 对约 8.5 s
LLM 生成 P501.26 s
检索 P5014.47 s
端到端 P5015.66 s

结论：TTFT ≈ 检索耗时，瓶颈在 CPU 精排，"优化 LLM"是错的方向。 这就是"为什么必须做延迟分解而不是凭直觉优化"的最直接证据。

另一条相关的实战细节：percentile(xs, q) 被用来找最长的 span——先按 span 名聚合耗时算 p95，再看哪一跳最长。这是 Trace 最实用的用法：把"慢"从形容词变成"某一跳的某一分位"。

隐私纪律—默认不记 prompt 与问题原文，只记 question_len/top1/chunk_ids/token；RAG_LOG_PROMPTS=1 才记（log_prompts_enabled():144-145）

一个真正的"可观测失败"案例（可以直接讲，非常有说服力）：YYHelp v1 的预算告警 budget_warnings（BUDGET_WARN_RATIO=0.90）加了但该缺陷未被测试发现；v2 用"总闸"保证它被执行。根因是告警没有被当成一个独立于终止原因的信号——所有 answered 都记成"正常"，其中一部分其实是擦着预算边过去的。教训："没有告警"不等于"没有异常"，也可能等于"这个异常不可见"。

面试怎么问 ​

Q1：你的模型路由怎么做的？降级链是怎样的？

A（要点）：路由有三个决策维度——复杂度（decide_model(state) 按 plan 的 complexity）、流量比例（CANARY_ENV + sticky_bucket(query) 稳定分桶）、可用性/成本（超时与预算闸门）。降级触发条件是超时/上游错误/预算超限，且降级必须被记录。

  • 加分句："我认为路由里最容易被忽略的是粘性：同一个 query 必须稳定落到同一个桶。否则 A/B 对比里你分不清'版本差异'和'分桶抖动'，而且回滚语义也建立不起来——你说不清哪些流量属于新版本。"
  • 别说："超时就切小模型。"（没触发条件、没记录、没行为一致性）
  • 追问 1：降级后哪些行为必须保持一致？→ 拒答语义、引用校验、错误码语义。不一致的话前端要写两套逻辑，而且用户会看到"同一个问题有时拒答有时不拒答"。
  • 追问 2：预算告警怎么设？→ 本项目 BUDGET_WARN_RATIO = 0.90，在 90% 处告警、留 10% 余量给收尾。关键教训是告警必须是一个独立于终止原因的信号——我们早期把"擦着预算边过去"的请求也记成正常，恶化完全不可见。
  • 追问 3：能不能一直降级？→ 不能。降级链要有界，每一跳都要有超时与预算约束，否则总时长不可控。降级到"拒答"也必须是明确终点。

Q2：可观测三支柱你埋在哪几个位置？

A（要点）：中间件建/复用 trace_id 并回写 X-Trace-Id；每次模型调用、工具调用、检索/精排各一个 span；响应返回后记一次成本；异常路径写 error 事件；所有埋点失败绝不影响主流程。

  • 加分句："我把'埋点失败'当硬约束：可观测系统最不该成为新的单点。所以我的 trace 写入失败时会降级写一个 observability_degraded 事件，而不是抛异常。"
  • 别说："我打了日志。"（没有位置、没有结构化、没有降级纪律）
  • 追问 1：LLM 的指标和普通 Web 服务有什么不同？→ 必须有 token 维度：输入/输出 token、缓存命中 token、成本。只有请求数的指标看不出成本与容量问题。
  • 追问 2：告警怎么设才不吵？→ 三条：冷却时间（本项目 300 秒）、错误率阈值（0.2）、最少样本数（10）。没有最小样本，凌晨两个请求错一个就会触发 50% 错误率告警——告警本身就是事故。
  • 追问 3：告警发不出去怎么办？→ 失败不能影响业务（后台线程发），但必须留痕（alert.failed）；默认只落盘，没配 webhook 就绝不联网。

Q3：Langfuse 和自研 trace 你怎么选的？

A（要点）：双后端。自研 JSONL 是默认路径（零第三方依赖、离线可审计），Langfuse 是增强路径，二者用同一个 trace_id 缝合。

  • 加分句："选 JSONL 作默认不是因为 Langfuse 不好，而是因为它的依赖面太重——5 个容器（web/worker/postgres/clickhouse/redis），离线或资源受限环境下整条可观测链会失效。而且我的离线评测管线要读 trace 文本：eval/run_ab.py 会把 trace 尾部几行抄进评测记录，routing.py 还会用正则从 trace 文本里抠出 plan 复杂度。trace 一旦成为下游程序的输入，它的格式就是接口。"
  • 别说："我接了 Langfuse 就有全链路追踪了。"（没讲成本、没讲离线失效、没讲 trace_id 缝合）
  • 追问 1：跨线程/跨进程怎么保证 trace 不串？→ 线程隔离（threading.local()）+ 显式 propagate(trace_id) 带进线程池任务 + HTTP 头 x-trace-id 串联跨服务。
  • 追问 2：怎么用它找性能问题？→ 按 span 名聚合耗时算分位数，找最长的那一跳。本项目就是这么发现"TTFT ≈ 检索耗时、瓶颈是 CPU 精排约 8.5 秒，而 LLM 生成 P50 只有 1.26 秒"的——结论直接否掉了"优化 LLM"这个方向。
  • 追问 3：trace 里存不存 prompt 原文？→ 默认不存。只记 question_len、top1、chunk_ids、token 数；需要时用 RAG_LOG_PROMPTS=1 显式打开。这是隐私与体积的双重考虑。
