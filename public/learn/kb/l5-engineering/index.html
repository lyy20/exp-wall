L5 · 工程化与服务部署 ​

本层知识点导览 ｜ 24 个知识点 / 10 页 / 84 学时 ｜ 面试频率：高 8 项、中 8 项、其余为高/中混合页 一句话：这一层决定你的项目是"能跑的 demo"还是"能上线的系统"。

这一层是什么 ​

L0–L4 讲的是"怎么把模型用对"：模型原理、prompt、检索、Agent。L5 讲的是另一件事：把上面那些东西送上线，并且让它可运维、可观测、可回滚、可算钱。

三句核心判断，请先建立：

  1. "本地能跑"和"能上线"之间隔着 8 个知识点。 流式要处理反代与缓冲、并发要处理 GIL 与显存、部署要处理探针与密钥、上线要处理灰度与成本、长期运行要处理 feedback 回流。这 8 个点里任何一个没做，面试官都会立刻判定"没上过线"。
  2. LLM 应用的工程质量集中体现在两个数字上：每问的成本、每个阶段的分位延迟。 说不出这两个数，前面 L1–L4 的所有优化都无法证明有价值。本层的 L5-17 到 L5-19 就是围绕这两个数字展开的。
  3. 先分解，再优化。 这是本层反复出现的方法论：延迟要分解到"哪一跳的哪一分位"（RAG 项目的首字延迟 = 检索耗时，LLM 生成只占 1.26s，于是"优化 LLM"是错方向）；成本要分解到"输入未命中 / 输入命中 / 输出"三段（命中与未命中的输入单价差 50 倍，于是缓存是价格结构决定的必然选择）；并发要分解到"这段代码到底释放不释放 GIL"（同一个函数两种写法给出 1.02× 和 6.41× 两个相反的结论）。

这一层的知识结构是一条流水线：先分层（谁负责什么）→ 再做对外接口（流式）→ 再做内部约束（并发与限流）→ 再省钱（缓存）→ 再上线（服务化与部署）→ 再深入推理引擎（vLLM 与量化）→ 再让运行态可见（路由与可观测）→ 再管成本与发布（成本、灰度、安全）→ 最后看长跑（GPU 调度与数据飞轮）。

这一层最容易挂在哪 ​

按"被问到的概率 × 答错的代价"排序，以下六条是真实高危项：

  1. SSE 的三个必需响应头说不出第三个。 Cache-Control: no-cache、Connection: keep-alive 大家都会，X-Accel-Buffering: no 是最常被漏的那个——少了它，Nginx 一类反向代理会把流式响应缓冲成一次性吐出，你在本机测一切正常，上线就"不流式"了。同类必答：FastAPI ≥0.135 已内置 fastapi.sse，不需要额外装 sse-starlette；以及拒答与正常回答共用同一个 token 事件（前端不需要为拒答写第二套渲染逻辑）。见 02、05。
  2. liveness 与 readiness 分不清。 判据只有一句：探针要验业务最依赖的那一次真实调用，不是"对象能构造出来"。 RAG 项目实测过这条的代价：后台线程预热做了、但 /health 秒回 200 ⇒ 编排器在模型加载前就把流量导进来 ⇒ 第一个请求照样等 48 秒（这条只有 rag-demo/service.py:73-78 的源码注释自述、无原始日志，引用时要说明）。见 05。
  3. 鉴权与限流的顺序反了。 鉴权必须在限流之前。 反了的话，未鉴权请求也会消耗限流额度，限流就从保护机制变成了拒绝服务放大器（攻击者用垃圾请求把正常用户的额度打满）。同类易错：限流用滑动窗口而不是取整分钟——取整分钟会在窗口边界放过两倍流量。见 03。
  4. 只会说"vLLM 快"，说不出为什么快。 要能讲清两个机制：PagedAttention 解决的是 KV Cache 的显存碎片（按页分配、不必预申请连续大块），连续批处理解决的是批次空转（不必等整批里最长的那条生成完才换下一批）。参数名、默认值与启动命令一律以官方文档为准，不要背具体数字。 见 06。
  5. 分不清 TP / PP / DP / EP 的适用边界。 一句话版本：TP 切同一层的权重（通信密、卡间带宽要求高、适合单机内）；PP 切层（流水线有空泡、适合跨机）；DP 复制整模型切数据（扩吞吐不扩单请求容量）；EP 切专家（MoE 场景）。 说错会显得只背过名词。见 06。
  6. 量化只答"省显存"，答不出代价。 必须同时说出：省了显存、降了带宽需求、通常也提速，代价是精度损失（通常不可逆）、部分算子对低精度的支持受限、以及校准数据带来的偏置风险。 「量化换来了什么又失去了什么」是这一层的标准必答题。见 07。

两条通用失分点，与具体知识点无关但会扣分：

  • 报数不带口径。 「延迟 200ms」没有分位数、没有样本量、没有环境。面试官会立刻追问"多少个请求测的"——本项目的压测每档只有 3–8 个请求，因此那些分位数不可写进 SLA，只能说结构性结论。主动说出这句话比被问出来强一百倍。
  • 把没做过的事说成做过。 GPU 并行、量化对比、跨进程缓存这些很可能你没条件做。正确答法是诚实分层："机制和取舍我清楚，但没有 GPU 环境，未做实测。"这不是减分项，"被追问三层后崩掉"才是。

和你自己的项目对上号 ​

本层每一页都有「和你自己的项目对上号」小节，逐条把概念映射到项目的真实符号与行号。三个最值得在面试里主动抛出的对照：

讲什么抛什么为什么有效
并发到底有没有收益serve/bottleneck.py 实测：计算块在函数内构造 → 加速比 1.02×（假结论）；块移到模块级预建 → 6.41×（真结论）。并发度 8、3 次取中位数（CONCURRENCY/TRIALS）、CPU_ITERATIONS = 3_000_000；zlib.decompress 同为释放 GIL 但要分配 52 MB → 只有 2.13×；判据阈值 < 1.2 无收益 / ≥ 1.2 且 < 并发度一半 部分收益 / ≥ 并发度一半 接近线性同一个函数两种写法给出相反结论，证明"性能实验必须先验证被测函数真的在跑"，展示实验素养而非背结论。见 03、YYHelp 踩坑
成本怎么算得过硬单次请求 1290 prompt + 36 completion token = $4.6e-05；价表带取数日期 PRICING_ASOF = "2026-09-28"；命中缓存的输入单价是未命中的 1/50（0.006 对 0.30，美元/百万 token）；外推 1 万次/天 ≈ $0.46/天 并主动标注这是量级估算、不含重试与评测流量报数带口径，并主动说明外推的边界——这是"诚实"的直接证据。见 09
数据飞轮怎么设计三入口（weak_evidence / self_eval_fail / user_downvote）汇入问题池并带检索快照；快照存 candidates 条而非 top_k 条，且把 retrieved_chunks（召回到的）与 final_context_chunk_ids（真正喂给模型的）分开存——差集 = "召回了但没喂给模型"；离线重放区分"真缺知识"（天级）与"没检索到"（分钟级）归因能力必须被设计进数据结构，这是一句技术判断，不是流程描述。见 10、YYHelp 数据飞轮
