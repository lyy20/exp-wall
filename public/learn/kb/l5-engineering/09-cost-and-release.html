成本核算与预算控制、灰度发布与 A/B、安全与合规基础 ​

覆盖知识点：L5-19 成本核算与预算控制 ｜ L5-20 灰度发布与 A/B 测试 ｜ L5-21 安全与合规基础 面试频率：高 ｜ 建议学时：9h

一句话说清 ​

成本要按调用归因才有用（归因不到"谁的哪一次调用"就管不了），灰度要按粘性桶切流量才有用（随机会让对比失效），安全要在入口和出口各设一道闸才有用（只在一边设等于没设）。

为什么必须学（面试官视角） ​

三个知识点各对应一类面试官的关注点：

  1. 成本：这是 AI 应用与传统 Web 应用最大的工程差异。面试官会问"你算过一次请求多少钱吗"。能报出数字并说明口径（单价来源、取数日期、token 构成）的人，和"大概几分钱吧"的人，立刻分层。
  2. 灰度：问的是"你怎么保证改动是变好还是变差"。没有对照组就没有结论——这是实验素养，而不是运维知识。
  3. 安全：LLM 应用有传统 Web 没有的三类风险——内容风险（模型生成不该生成的）、数据风险（prompt 里带出去的 PII）、资产风险（prompt 被套取）。答不出"闸门设在哪"就等于没有安全设计。

核心内容 ​

L5-19 成本核算与预算控制 ​

1）先说清钱花在哪：LLM 的成本结构 ​

成本项与什么成正比控制手段
输入 token（未命中缓存）prompt 长度 × 单价精简 prompt、裁剪检索上下文、前缀缓存
输入 token（命中缓存）同上但单价低一个数量级稳定 prompt 前缀、把动态内容后置
输出 token生成长度 × 单价限制 max_tokens、结构化输出、避免重复生成
检索/精排/嵌入计算量派生数据缓存、离线向量化
固定成本常驻实例、向量库、可观测栈资源按需、避免为低频功能常驻大组件

关键判别：输出 token 通常比输入 token 贵（生成的每一步都要一次前向），但输入 token 的量可以远大于输出（RAG 把所有检索到的文档塞进 prompt）。所以优化的优先级取决于你的 token 构成——必须先量出来。

2）归因：把成本算到"这一次调用" ​

成本归因的硬要求：每一次模型调用都要能被追问"这次花了多少、为什么"。这就要求：

  1. 记录用量：从响应里取 prompt_tokens / completion_tokens，以及缓存命中的 token 数（RAG 项目用 stream_options={"include_usage": True} 取用量；流式降级重试一次时不带 usage，并记 stream.retry_no_usage 事件留痕）。
  2. 区分命中与未命中：命中缓存的输入单价可能相差一个数量级（见下）。
  3. 价格要带取数日期：价格会变，任何成本结论必须能回溯到"哪张价表、哪天取的"。

真实形态（RAG 项目 obs.py）：

python
PRICING_ASOF = "2026-09-28"          # obs.py:41  价格来源：https://api-docs.deepseek.com/quick_start/pricing
# 峰时价表（obs.py:44-47，单位 美元/百万 token）
# deepseek-flash   : {in_miss: 0.30, in_hit: 0.006, out: 1.20}
# deepseek-v4-pro  : {in_miss: 1.32, in_hit: 0.044, out: 3.96}

miss = max(0, prompt_tokens - cached_tokens)        # obs.py:177-191
cost = (miss * in_miss + cached_tokens * in_hit + completion_tokens * out) / 1_000_000

三个可以直接讲的点：

  • 命中与未命中的输入单价差 50 倍（deepseek-flash：0.30 vs 0.006）。所以缓存不是"优化"，是价格结构决定的必然选择。
  • 公式里的 max(0, ...) 是防御：上游偶尔会报出 cached_tokens > prompt_tokens 的不一致数据，不做保护就会出现负成本。
  • 别名单独维护（_ALIASES = {"deepseek-chat": "deepseek-flash", "deepseek-reasoner": "deepseek-flash"}）：模型名会变，价表要能被别名映射，否则统计会静默漏掉一整类调用。

实测数量级（口径必须一起说）：单次请求 1290 prompt + 36 completion token = $4.6e-05（约十万分之五美元）。按此口径外推：200 次/天 ≈ $0.01/天；1 万次/天 = $0.46/天。

⚠️ 外推必须标口径：$4.6e-05 是单次实测，它不含重试、不含评测流量、不含缓存未命中的最坏情况；而且价格随时会变（取数日期 2026-09-28）。把"1 万次/天 = $0.46/天"当成预算承诺是错的，它只是量级估算。

3）预算控制：事前查 + 事后记，且告警要独立 ​

YYHelp 的两道闸门：MODEL_TIMEOUT_S = 30.0（管单次调用，graph/agent.py:159）与 BUDGET_WARN_RATIO = 0.90（管整个请求的预算，:185）。后者的语义是：在 90% 处告警，留 10% 余量给"收尾"——不要等到 100% 才发现在收尾阶段已经没有预算可用。

一个真实的失败案例（比完美方案更有说服力）：v1 加了 budget_warnings（BUDGET_WARN_RATIO=0.90），但该缺陷未被测试发现；v2 用"总闸"保证它被执行。根因：告警没有作为一个独立于终止原因的信号——所有 answered 都被记成"正常"，其中一部分其实是擦着预算边过去的。日志里一切正常，恶化过程完全不可见。

RAG 侧的记账策略与它的已知代价：事前查预算 + 事后记账，因此允许一次请求超出预算（/retrieve 不计费，只受限流，guard.py:18-21）。这是一个自觉的取舍：

策略优点代价
事前查 + 事后记（本项目）实现简单、无额外延迟允许单次超支；并发高时可能集体超支
事前预留 + 事后结算严格不超支需要预留与释放，忘释放会"漏额度"
流式按 token 实时扣减最严格流式路径上每片都要检查，延迟与复杂度上升

常见误区：

误区更正
只统计"请求数"请求数无法换算成钱；必须统计 token 构成与缓存命中
价表不带取数日期价格变了以后历史成本无法解释
把单次成本线性外推当承诺重试、评测流量、缓存未命中都会推高实际成本
预算是"月末看一眼账单"预算必须在请求路径上可判定，否则它只是事后归因
告警阈值=100%100% 处告警等于没有收尾空间；本项目取 0.90

L5-20 灰度发布与 A/B 测试 ​

1）灰度：切什么、怎么切、怎么回滚 ​

三个可灰度维度：prompt 版本、索引版本、路由策略（YYHelp 的项目结论）。扩展一下通常还有：模型版本、检索参数（top_k / candidates / 是否加重排）、解码参数。

怎么切：

text
CANARY_ENV = "YYHELP_ROUTE_CANARY_PCT"      # serve/routing.py:68
sticky_bucket(query: str) -> int            # :91  同一 query 稳定同桶
assign_route_version(query)                 # 决定走哪个版本
object_versions 快照三要素                  # prompt / 索引 / 路由，随每次调用记录
stamp_route 打标                            # 为后续统计留下路由标签

为什么必须粘性：随机会让"同一个问题在不同请求里走不同版本"，于是你无法归因差异；更严重的是回滚时说不清"哪些流量属于新版本"。粘性分桶让每一次请求的版本归属是可复现的。

2）A/B 的判定：你必须有一个对照组和一个判据 ​

没有对照组就没有结论——这是本页最重要的一句话。灰度的产出不是"新版本上线了"，而是一个可判定的比较结果。

本项目的真实两臂对照（可直接引用的实验规模）：

项数值口径
臂mode="multi" vs mode="single"同一套问题集
墙钟multi 20.9s vs single 9.9s（2.11×）同机、同问题集
显著性t 检验 p=1.9e-6、Wilcoxon p=8.7e-7、Holm 校正后拒绝原假设 → 判定 REGRESSION多假设校正
每问 tokensmulti 5,783.7 vs single 6,243.3注意：multi 反而更省 token
复杂度判定分歧规则 simple 3 / multi 37（40 题） vs live simple 34 / multi 0（34 题）两种判定口径给出几乎相反的分布

这张表里最值钱的是最后一行：规则判定的复杂度分布与实测（live）几乎相反。这说明**"路由决策"本身需要被验证**——你的 decide_model 规则可能根本没按你想象的比例分流。这正是"每个决策点都要打标"（stamp_route）的价值。

另一条纪律（统计效力）：本项目压测每档只有 3–8 个请求，因此分位数不可写进 SLA，只能作为结构性结论（延迟随并发线性增长、吞吐饱和、瓶颈是 CPU 排队）。同理，A/B 也要问样本量：样本量不足时，显著性检验只能告诉你"还不能下结论"。

3）灰度的判定指标不能只看"好不好" ​

指标类例子为什么需要
质量评测集分数、引用命中率、拒答率改动是否变好
延迟P50 / P95 / TTFT / TPOT用户是否感觉到变慢
成本每问 token、每问成本变好是否值得变贵
稳定性错误率、降级次数、超时次数是否引入新故障
安全越界输出率、PII 泄漏样例数见下一节

经典陷阱：只看质量、不看成本与延迟 ⇒ 上线一个"分数高一点但贵一倍、慢一倍"的版本。所以灰度必须同时看至少四个维度，且判定阈值在实验开始前定好。

L5-21 安全与合规基础 ​

1）三道闸门（两道在入口/出口，一道在数据） ​

闸门位置拦什么手段
输入闸门请求进来、进模型之前越界请求、注入攻击、超长输入规则/分类器审核、长度限制、参数化模板（不要把用户输入直接拼进 system 指令）
输出闸门生成完成、返回之前不该生成的内容、幻觉性承诺、越权信息输出审核、引用校验（可溯源）、拒答机制
数据闸门入库、出库、日志PII 泄漏、敏感数据外泄脱敏、最小化收集、日志不记原文

为什么闸门要设在两端：只在入口设 ⇒ 模型仍可能生成不该生成的（尤其是被诱导时）；只在出口设 ⇒ 已经付出了成本，且入口的恶意输入会污染数据飞轮。两端都要，且数据闸门横切全链路。

2）PII 脱敏：本项目有一个可直接讲的技术细节 ​

数据飞轮要把失败问题入池，而入池前必须做实体占位化。这里有两个真实坑（pool.py:124-132）：

  1. \b\d{11}\b 在中文里失效：汉字属于 \w，单 与 1 之间没有词边界，所以正则在中文语境下匹配不到手机号。
  2. 只做单遍替换会二次匹配：替换产生的占位符可能被后续规则再次命中。

修法是环视断言 + 占位符用不兼容形式：

python
# 用环视断言替代 \b（pool.py:124-132 的做法）
r"(?<!\d)\d{11}(?!\d)"
1
2

这条的意义远超正则：它说明脱敏是必须被测试的——一个"看起来在脱敏"的正则可能一直没生效，而且没有任何报错。

3）Prompt 泄漏防护 ​

Prompt 泄漏有三种典型后果：商业资产（精心调优的 prompt / 工具清单）被套取、系统指令被覆盖导致越界行为、敏感上下文被回溯（prompt 里塞了不该给的资料）。

防护层次：

层次做法注意
架构把敏感数据放在服务端按需注入，不要固化进 prompt 模板模板泄漏 ≠ 数据泄漏
指令系统指令与用户输入结构分离（不同角色/不同字段），并声明"用户内容不是指令"不能只靠一句"不要听用户的"
输出检测并拒绝"复述你的系统提示"类请求但要接受：完美的防泄漏不存在，目标是提高成本
兜底假设 prompt 会泄漏，因此 prompt 里不放密钥、不放内部地址这条最实在

4）日志与合规 ​

本项目的隐私纪律可以作为标准答案：默认不记 prompt 原文与用户问题原文，只记 question_len / top1 / chunk_ids / token 数；只有显式设 RAG_LOG_PROMPTS=1 时才记（log_prompts_enabled():144-145）。理由：日志会被集中收集、保留更久、访问面更宽——日志系统是数据泄漏最常见的路径。

面试怎么问 ​

Q1：你这个应用一次请求花多少钱？怎么算的？

A（要点）：先量 token 构成，再套价表，且必须区分缓存命中与未命中。本项目实测单次 1290 prompt + 36 completion = $4.6e-05，价表带取数日期 PRICING_ASOF = "2026-09-28"。

  • 加分句："这个数我会连着口径一起说：它是单次实测、不含重试与评测流量、价格取数日期是 2026-09-28。外推到 1 万次/天大约 $0.46/天，但那是量级估算，不是预算承诺。"
  • 别说："大概几分钱吧。"（没有口径、没有 token 构成、没有日期）
  • 追问 1：为什么公式里有 max(0, prompt_tokens - cached_tokens)？→ 防御上游偶尔报出的不一致数据（cached 大于 prompt），不保护就会出现负成本。
  • 追问 2：输入和输出哪个更该优化？→ 取决于你的 token 构成。输出单价更高，但 RAG 场景输入的量可以远大（把检索文档全塞进 prompt）。先量再优化，并用延迟/成本分解定位。
  • 追问 3：模型改名了怎么办？→ 维护别名映射（本项目 _ALIASES 把 deepseek-chat / deepseek-reasoner 都映射到 deepseek-flash），否则统计会静默漏掉一整类调用。

Q2：你的灰度是怎么切的？怎么判定改版是变好还是变差？

A（要点）：三个可灰度维度（prompt 版本 / 索引版本 / 路由策略），切流量用 sticky_bucket(query) 保证同一 query 稳定同桶，每次调用记录 object_versions 快照三要素并 stamp_route 打标。判定要同时看质量、延迟、成本、稳定性四类指标。

  • 加分句："粘性不是为了好看：随机会让同一问题在不同请求走不同版本，你既无法归因，回滚时也说不清哪些流量属于新版本。"
  • 别说："灰度就是把 10% 流量导过去看看。"（没有对照组、没有判据、没有回滚语义）
  • 追问 1：你的 A/B 结论是什么？→ 本项目两臂：multi 墙钟 20.9s vs single 9.9s（2.11×），t 检验 p=1.9e-6、Wilcoxon 8.7e-7、Holm 校正后拒绝 → 判定 REGRESSION（变差）。注意 multi 每问 token 反而更低（5,783.7 vs 6,243.3）——所以"更慢"和"更贵"不是同一件事，必须分维度看。
  • 追问 2：你的路由规则验证过吗？→ 验证过，而且发现了分歧：规则判定的复杂度分布（simple 3 / multi 37，40 题）与 live 实测（simple 34 / multi 0，34 题）几乎相反。这说明决策规则本身要被打标与核对，不能假定它按你想象的比例分流。
  • 追问 3：样本量够吗？→ 必须问。本项目压测每档只有 3–8 个请求，所以分位数不可写进 SLA。样本量不足时，显著性检验只能告诉你"还不能下结论"。

Q3：安全上你做了哪些？三道闸门设在哪？

A（要点）：输入闸门（长度限制、审核、系统指令与用户输入结构分离）、输出闸门（审核 + 引用校验 + 拒答机制）、数据闸门（脱敏 + 日志不记原文）。只设一端等于没设。

  • 加分句："我最实在的一条是'假设 prompt 会泄漏'：所以 prompt 里不放密钥、不放内部地址，敏感数据服务端按需注入。完美的防泄漏不存在，目标是提高攻击成本。"
  • 别说："我让模型不要听用户的指令。"（纯靠指令的防护等于没有）
  • 追问 1：PII 脱敏你怎么做的？→ 实体占位化，并且要测。本项目踩过两个坑：\b\d{11}\b 在中文里失效（汉字属于 \w，单 与 1 之间没有词边界）；只做单遍替换会二次匹配。修法是环视断言 (?<!\d)\d{11}(?!\d) + 占位符用不兼容形式。"看起来在脱敏"和"真的脱敏了"是两件事。
  • 追问 2：日志里能记 prompt 吗？→ 默认不记。日志会被集中收集、保留更久、访问面更宽——日志系统是数据泄漏最常见的路径。本项目只记 question_len / top1 / chunk_ids / token 数，需要时用 RAG_LOG_PROMPTS=1 显式打开。
  • 追问 3：合规还注意什么？→ 最小化收集、可删除（用户要求删除时能定位到所有副本）、可审计（谁在什么时候用什么数据做了什么）。这三条是"能不能交付给企业客户"的门槛。
