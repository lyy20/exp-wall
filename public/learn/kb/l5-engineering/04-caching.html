多级缓存策略 ​

覆盖知识点：L5-06 多级缓存策略（精确缓存、语义缓存、KV/Prompt 前缀缓存） 面试频率：高 ｜ 建议学时：4h

一句话说清 ​

LLM 应用的缓存有四层完全不同的东西可以缓存——最终答案、检索结果、prompt 前缀、向量与嵌入——它们的命中率、失效条件和风险各不相同；把"加个 Redis 缓存答案"当成全部，是这一页最常见的错。

为什么必须学（面试官视角） ​

缓存是面试官用来区分"会调 API"和"会做系统"的分水岭，因为缓存必然带出四个追问：

  1. 缓存键怎么设计？（用户维度、版本维度、模型维度）
  2. 怎么失效？（知识库更新了怎么办）
  3. 命中率是多少？（没有命中率的缓存等于没有缓存）
  4. 语义缓存会不会答错？（这是最危险的一层）

第 3 条是本项目里真实没做到的一条——RAG 项目的检索缓存是进程内的、未做跨进程持久化，且未找到命中率统计的实现。在面试里这件事有两种讲法：装作有（会被追问到崩），或者主动说"缓存的效果只能靠命中率证明，而我这条还没做"——后者是加分项。

核心内容 ​

L5-06 四层缓存与各自的取舍 ​

定义：按"缓存的是什么"分四层，从便宜到昂贵、从安全到危险：

层缓存对象命中条件典型收益主要风险
L1 精确缓存最终答案请求完全相同（含所有影响输出的参数）命中即 0 成本、0 延迟键设计漏维度 ⇒ 答错
L2 语义缓存最终答案问题语义相近（向量相似度 ≥ 阈值）覆盖面远大于精确缓存阈值太低 ⇒ 用错的答案回答对的问题
L3 前缀缓存（Prompt/KV Cache）模型侧 KVprompt 前缀完全相同省 prefill 计算、降 TTFT 与成本前缀里动态内容太多 ⇒ 前缀命中不了
L4 派生数据缓存嵌入、检索结果、重排结果输入 + 版本一致省最贵的那一跳（GPU/CPU 精排）版本混用 ⇒ 结果对不上

为什么这样设计：这四层的优化目标不同——L1/L2 优化"完全不用算"，L3/L4 优化"算得更少"。混着讲就说不清失效条件。

机制逐层拆解 ​

L1 精确缓存：键必须包含所有影响输出的维度。

一个可用的缓存键最少要含四类维度：

text
cache_key = hash(
    question_normalized,      # 归一化后的问题（去空白、统一标点、大小写）
    prompt_version,           # 提示词版本
    index_version,            # 索引版本（知识库更新必须变）
    model_id,                 # 模型版本（含路由档位）
    decode_params             # temperature / top_p / max_tokens 等
)

为什么必须带版本号：知识库更新后，同一条问题的正确答案会变。如果缓存键不含 index_version，你会用旧答案回答新问题，而且用户完全无法察觉。这是最隐蔽的一类正确性事故。

L2 语义缓存：收益与风险的交换比是"可调阈值"。

机制：问题先过 embedding，与已缓存问题的向量比相似度，超过阈值就复用答案。

  • 阈值高 ⇒ 近似精确匹配，安全但命中率低。
  • 阈值低 ⇒ 命中率高但可能"答非所问"，且错得很自然（答案本身语法完美、引用齐全，只是回答的是另一个问题）。

因此语义缓存必须配两样东西：阈值可配置 + 线上可观测（记录命中时的问题对与相似度，供人工抽检）。还有一条必须做：写操作/时效性问题禁止走语义缓存（如"我现在的订单状态"）。

L3 前缀缓存（Prompt / KV Cache）：改的是 prompt 的写法，不是加一层存储。

机制：模型对 prompt 前缀计算出的 KV 被复用，跳过重复的 prefill。它对应用侧的要求是"前缀要稳定"：把固定不变的部分（system prompt、工具清单、少样本示例、背景文档）放在前面，把随请求变化的部分（用户问题、时间戳、随机 id）放在后面。

写法后果
system prompt 固定在首位前缀可复用
把 当前时间 写在 system prompt 顶部前缀每次都不同，缓存永远不命中
把检索到的文档插在 system prompt 之前文档一变前缀就废，前缀缓存基本失效

这是与 [04 缓存] 无关但常被一起考的一条：它不占你的存储、没有失效逻辑，只要 prompt 布局对就行——性价比最高的一层。

L4 派生数据缓存：本项目最该做但没做透的一层。

RAG 项目的检索是 CPU 重活：检索 P50 14.47 秒、CPU 精排 20 对约 8.5 秒（30 题样本实测，bench_latency.py）。而 LLM 生成 P50 只有 1.26 秒。也就是说：这一层缓存能省掉 90% 以上的端到端耗时，它的价值远大于缓存最终答案。

现实状态（诚实口径）：检索缓存是进程内的、未做跨进程持久化，未找到命中率统计的实现。未做的验收方式：

常见误区 ​

误区后果
缓存键不含 index_version知识库更新后用旧答案回答新问题，且无告警
语义缓存阈值拍脑袋答非所问，且答案看起来完全正常
把动态内容放进 prompt 前部前缀缓存命中率归零，而你以为它在生效
缓存"未命中"路径不做记录命中率无法计算 ⇒ 缓存无法调优
只缓存最终答案省的是最便宜的那一跳（生成 1.26s），而不是最贵的那跳（检索 14.47s）
缓存无 TTL / 无容量上限内存被打满，或缓存永久陈旧

面试怎么问 ​

Q1：你的 LLM 应用加了缓存吗？缓存的键怎么设计？

A（要点）：按层设计。最终答案缓存（L1）的键必须含四类维度：归一化问题、prompt_version、index_version、model_id，外加解码参数。缺版本维度会导致"知识库更新后用旧答案回答新问题"。

  • 加分句："我认为缓存键里最不能省的是 index_version。少了它，缓存不会报错、不会告警，只会安安静静地用旧答案回答新问题——这是最难发现的一类正确性事故。"
  • 别说："我用 Redis 缓存了答案。"（没有键设计、没有失效、没有命中率）
  • 追问 1：知识库更新时怎么失效？→ 两种做法：版本号进键（旧键自然变冷，无需主动删，配合 TTL 回收）；或按 index_version 建命名空间整体作废。前者对写放大更友好。
  • 追问 2：TTL 设多长？→ 取决于问题时效性，没有通用答案。判断依据是"这条知识多久变一次"，而不是"缓存多大"。强时效问题（订单、库存）根本不该进缓存。
  • 追问 3：多实例部署时缓存放哪？→ 进程内缓存会在每个实例各自冷启动，命中率被摊薄；需要共享存储（如 Redis）或一致性哈希路由。本项目检索缓存只做到进程内，这是我已知的缺口。

Q2：语义缓存你知道它危险在哪吗？

A（要点）：危险在错得很自然——阈值太低时，缓存命中返回的是一个语法完美、引用齐全、但回答的是另一个问题的答案。用户和评测都不容易发现。

  • 加分句："所以语义缓存我一定会配两样东西：阈值可配置，以及线上记录'命中时的问题对与相似度'供人工抽检。没有抽检的语义缓存等于给自己埋雷。"
  • 别说："语义缓存能大幅提高命中率。"（只讲收益，不讲失败模式）
  • 追问 1：哪些请求绝不能走语义缓存？→ 时效性与个性化问题（订单状态、账户数据），以及任何带写副作用的请求。
  • 追问 2：阈值怎么定？→ 用一批人工标注的问题对（等价 / 不等价）扫阈值，看"误命中率"与"命中率"的交换曲线；不接受全凭经验的单一阈值。
  • 追问 3：那和精确缓存冲突吗？→ 不冲突，是流水线：先精确后语义，精确命中的零风险优先。

Q3：前缀缓存你用过吗？它和"加一层 Redis"有什么区别？

A（要点）：前缀缓存不占你的存储、没有失效逻辑，它要求的是prompt 布局：固定部分（system prompt、工具清单、少样本）在前，动态部分（用户问题、时间戳、随机 id）在后。命中时输入按 1/50 计价（本项目价格表，取数日期 2026-09-28）。

  • 加分句："我把它归为'性价比最高的一层'：代价只是 prompt 写法，收益是 prefill 计算与输入费用。反过来说，把 当前时间 放在 system prompt 顶部，就是把这层缓存主动关掉。"
  • 别说："前缀缓存就是 prompt 缓存。"（不说机制不说代价）
  • 追问 1：检索到的文档算前缀还是动态部分？→ 取决于它在 prompt 里的位置：放在前面且跨请求相同才可能命中；RAG 场景文档随问题变化，放前面基本命中不了。所以 RAG 里前缀缓存主要靠稳定的 system 部分。
  • 追问 2：本地推理服务的前缀缓存和云厂商的是一回事吗？→ 机制同类（复用 KV），实现与开关不同。具体参数名、默认值与开启方式以官方文档为准，各引擎差异很大。
  • 追问 3：怎么证明前缀缓存真的生效了？→ 看用量字段里的缓存命中 token 数与账单侧的单价，而不是看"感觉变快了"。没有可观测字段的优化等于没做。
