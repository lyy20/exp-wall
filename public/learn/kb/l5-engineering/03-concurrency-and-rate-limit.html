并发与批处理、限流重试与退避 ​

覆盖知识点：L5-04 并发与批处理 ｜ L5-05 限流、重试与退避 面试频率：高 ｜ 建议学时：7h

一句话说清 ​

并发能不能带来收益，取决于被并发的那段代码有没有真的把 GIL 释放掉；限流能不能保护系统，取决于它跑在鉴权之后还是之前——这两条都有可证伪的判据，不是经验之谈。

为什么必须学（面试官视角） ​

这一页藏着 L5 最好的一个面试素材：一个被测错的并发实验。面试官问"你做过并发优化吗"，最常见的两种回答都是失败的：

  • "我用了 asyncio，并发就上去了"——没有数字，没有判据。
  • "我测了一下，加速比 1.02 倍，说明并行没收益"——这是假结论，而且面试官很可能知道这个坑。

能答出"我第一版测出 1.02 倍，查出来是工作块在函数内构造、持有 GIL 盖住了可释放的部分，移到模块级预建后是 6.41 倍，口径是并发度 8、三次取中位数"的人，展示的不是知识，而是实验纪律。这是技术主管最想要的信号。

核心内容 ​

L5-04 并发与批处理 ​

定义：并发指"同时处理多个请求"，批处理指"把多个请求合成一批一起算"。对 LLM 系统两者都有：服务侧的 asyncio/线程池是并发，推理引擎的连续批处理（continuous batching）是批处理。

机制——先分清三类工作负载：

负载类型特征正确的并发手段加并发会怎样
I/O 密集等网络/磁盘，CPU 闲着asyncio 或线程池接近线性加速
CPU 密集且释放 GIL计算在 C 扩展里（压缩、向量运算、部分序列化）线程池/多进程按释放 GIL 的比例加速
CPU 密集且持有 GIL纯 Python 循环、大对象构造多进程，线程无收益几乎不加速，甚至变慢

为什么这样设计：CPython 的 GIL 意味着同一时刻只有一个线程执行 Python 字节码。所以"加线程"能不能提升吞吐，唯一取决于那段热点有没有在 C 扩展里长时间释放 GIL。这不是可以猜的，必须测。

数量级与形状——那个被测错的实验（本项目真实素材）：

场景：同一份工作负载（serve/bottleneck.py），并发度 CONCURRENCY = 8（bottleneck.py:92），每档 TRIALS = 3 次取中位数（:95），CPU_ITERATIONS = 3_000_000 / NATIVE_BYTES = 52_000_000 / IO_SLEEP_MS = 120.0（:100/102/104）。

档位第一版结论根因修法后
cpu_native（释放 GIL 的 C 扩展路径）1.02×（假结论）工作函数里每轮重建 52 MB bytes（blk * 大整数），那段构造本身持有 GIL，把可释放的部分盖住了块移到模块级预建 _NATIVE_BLOCK → 6.41×
zlib.decompress（同样释放 GIL，但要分配 52 MB）—分配阶段同样持有 GIL2.13×（对照档）
cpu_pure（纯 Python 计算）—按设计就不该加速应显著低于 CONCURRENCY/2

可迁移的判据（阈值口径来自 bottleneck.py:267）：

  • 加速比 < 1.2 ⇒ 这条负载上没有明显并发收益，别写"并发生效"。
  • ≥ 1.2 且 < CONCURRENCY/2 ⇒ 有部分收益，说明热点里混着持有 GIL 的部分。
  • ≥ CONCURRENCY/2 ⇒ 接近线性，热点确实释放了 GIL。

另一条同源教训：bottleneck.py 里 pypure 函数定义了但从没调用，那一行测出的 0.047 秒其实是空函数的耗时。教训：性能实验必须先验证"被测函数真的在跑"。这句话比 6.41× 更值钱。

背压（backpressure）：有并发上限就必须有"满了怎么办"。三种策略与适用场景：

策略行为适用
快速失败立即返回 503/429在线交互、用户可重试
排队限时入队但设等待上限，超时再失败期望抖动而非直接失败
降级走更便宜的模型/更少的检索有降级档位的系统

常见误区：

误区后果
认为"异步 = 并发加速"计算路径持有 GIL 时无收益，还引入调度开销
用信号量私有属性（如 _value）读剩余配额非公开 API，版本升级即碎；应自己维护计数器 + 锁
并发上限设成"机器核数"对 I/O 密集负载严重低估，对 CPU 密集负载严重高估
没有背压的并发请求堆积，延迟无限增长直到超时

代码（线程安全的并发计数，真实形态）：

# RAG service.py:136-150 —— /ask/stream 在线程池迭代生成器，所以不能用 asyncio.Semaphore
_inflight = {"n": 0}                 # :136
_inflight_lock = threading.Lock()    # :137

def _try_acquire() -> bool:          # :140-145
    with _inflight_lock:
        if _inflight["n"] >= MAX_CONCURRENCY:
            return False
        _inflight["n"] += 1
        return True

def _release() -> None:              # :148-150
    with _inflight_lock:
        _inflight["n"] = max(0, _inflight["n"] - 1)

L5-05 限流、重试与退避 ​

定义：限流是对入口流量的主动裁剪；重试是对可恢复失败的自动补偿；退避是重试之间的等待策略。

机制——限流的两个必答细节：

① 顺序：鉴权必须在限流之前。（本项目明确的设计判断）

如果限流跑在鉴权之前，任何未通过鉴权的请求也会消耗配额——攻击者可以用"无效 key"把配额打光，让合法用户全部被 429。限流会从保护机制变成拒绝服务放大器。

text
正确顺序：  TLS → 鉴权 → 限流 → 业务
错误顺序：  TLS → 限流 → 鉴权 → 业务   # 无效请求也能吃掉配额

2

② 窗口：滑动窗口 vs 取整分钟。

实现行为代价
取整分钟计数计数器在整分钟清零用户可以在 00:59 打满 + 01:00 再打满 ⇒ 瞬时 2 倍速率
滑动窗口只统计最近 60 秒内的请求精度高，需保存时间戳队列或做桶加权
令牌桶按固定速率补令牌，允许突发允许短时突发，参数需标定

RAG 项目用的是 60 秒滑动窗口（上限 60 次/分钟；/retrieve 只受限流、不计费，guard.py:18-21）；YYHelp 限流阈值是 60 次/分钟，由 YYHELP_RATE_LIMIT_PER_MIN 控制（api/app.py:120，class RateLimiter:345，实例 RATE = RateLimiter(RATE_LIMIT_PER_MIN):393）。RAG 侧另有更严的一档：30 次/分钟。

机制——重试的三条纪律：

  1. 只重试幂等且可恢复的错误：429（限流，值得等）、5xx（上游抖动）、超时。4xx 中的参数错误、鉴权失败绝不重试——重试只会放大伤害。
  2. 指数退避 + 抖动（jitter）：纯指数退避会让所有客户端在同一时刻重试，形成重试风暴（thundering herd）；抖动把重试时刻打散。
  3. 重试要有总预算：重试次数 × 单次超时不能超过上层超时，否则外层先超时、内层还在重试，配额白白烧掉。

幂等性提醒：写操作（下单、写库、发消息）默认不可重试。要重试必须带幂等键（idempotency key），由服务端去重。这一条在 Agent 场景尤其重要——工具调用可能是发邮件、写数据库。

数量级与形状（本项目实测口径）：

指标值口径
RAG 侧限流30 次/分钟60 秒滑动窗口
RAG 告警冷却300 秒（RAG_ALERT_COOLDOWN_S 默认值）冷却期内同类告警不重复发
RAG 错误率告警阈值0.2需 最少样本 10 才评估
并发档位实测（loadtest.py）并发 1 → RPS 0.15 / P50 7.5s；2 → 0.20 / 13.7s；4 → 0.25 / 25.7s；8 → 0.40 / 45.8s每档仅 3–8 个请求，分位数不可写进 SLA
并发上限默认值RAG_MAX_CONCURRENCY 默认 2上限设 2 时漏释放两次 = 服务不可用

口径声明：上表并发档位数据的结构性结论可用（延迟随并发线性增长、吞吐在并发 4 处饱和、瓶颈是 CPU 排队），但绝对分位数不可用——每档样本量只有 3–8 个。要写 SLA 必须重跑压测到每档样本 ≥ 数百请求。

告警的两条纪律（容易漏）：告警失败不能影响业务（webhook 在后台线程 threading.Thread(target=_post, daemon=True, name="alert")），但必须留痕（obs.log_event("alert.failed", ...)）；并且默认只落盘——RAG_ALERT_WEBHOOK 没配就绝不联网。另有真实坑：钉钉关键词安全设置会导致静默拒收（errcode 310000），因此支持 RAG_ALERT_PREFIX 兜底。

常见误区：

误区后果
限流放在鉴权前无效请求吃配额，限流变成 DoS 放大器

面试怎么问 ​

Q1：你做过并发优化吗？加速比多少？

A（要点）：做过一次并发实验（serve/bottleneck.py）。第一版结论是 1.02×，是假结论：工作函数里每轮重建 52 MB 的 bytes，那段构造持有 GIL，把可释放的部分盖住了。把块移到模块级预建后是 6.41×。口径：并发度 8、每档 3 次取中位数。

  • 加分句："这个坑教会我的是判据，不是数字：性能实验必须先验证被测函数真的在跑。同一次里还有一个函数定义了但从没被调用，那一行测出 0.047 秒，其实是空函数的耗时。"
  • 别说："并发度调到 8，速度提升 6 倍多。"（没有根因、没有口径，且会让人怀疑你是不是又测错了）
  • 追问 1：你怎么知道 6.41× 是真的，而不是又一次假结论？→ 换档位验证：同一个 bug 在 zlib.decompress 对照档上只出 2.13×，在 cpu_pure 档上按设计就该低于 CONCURRENCY/2。有一条不能解释的档位，结论就不成立。如果一个数字在所有档位上都一样好看，那它大概是假的。
  • 追问 2：那些阈值怎么定？→ < 1.2 无收益、≥ 1.2 且 < CONCURRENCY/2 部分收益、≥ CONCURRENCY/2 接近线性（bottleneck.py:267）。阈值的作用是让结论可失败，而不是让报告好看。
  • 追问 3：那什么负载该用多进程？→ 纯 Python 计算（持有 GIL）。判断依据是"热点是否在 C 扩展里释放 GIL"，而这条只能靠测，不能靠猜。

Q2：限流你怎么做的？为什么放在这个位置？

A（要点）：鉴权必须在限流之前。顺序反了，未通过鉴权的请求也会消耗配额，攻击者能用无效 key 把配额打光，让合法用户全部 429——限流就从保护机制变成拒绝服务放大器。

  • 加分句："顺序这件事我认为比阈值更重要。阈值调错了只是误伤，顺序错了是把自己的防线变成攻击面。"
  • 别说："限流就是个计数器，超过就 429。"（少了顺序与窗口两个考点）
  • 追问 1：窗口怎么选的？→ 取整分钟计数有"跨分钟双倍速率"的漏洞（00:59 打满 + 01:00 再打满）；所以用 60 秒滑动窗口（本项目 RAG 侧即如此）。令牌桶则能显式允许突发，但参数要标定。
  • 追问 2：限流按什么维度？→ 按 key 而不是按 IP。NAT 后大量用户共享 IP，按 IP 会误伤；按 key 才能对应到"谁在花钱"。
  • 追问 3：限流和并发上限是一回事吗？→ 不是。限流管入口速率（次/分钟），并发上限管同时在跑的数量。两者都要有：只有限流，慢请求仍会把并发占满；只有并发上限，请求会被堆积而不是被快速拒绝。

Q3：上游 429 了，你的重试策略是什么？

A（要点）：只重试幂等且可恢复的错误（429 / 5xx / 超时），用指数退避 + 抖动，并且受总重试预算约束。4xx 参数错误与鉴权失败绝不重试。

  • 加分句："抖动不是为了好看——没有抖动，所有客户端会在同一时刻重试，形成重试风暴，上游被打得更惨。"
  • 别说："失败了就重试三次。"（没说幂等性、抖动、预算）
  • 追问 1：哪些不能重试？→ 写操作（下单、写库、发消息）默认不可重试；要重试必须带幂等键由服务端去重。Agent 场景尤其危险，因为工具调用可能已经在外部产生了副作用。
  • 追问 2：重试预算怎么定？→ 重试次数 × 单次超时 ≤ 上层超时。否则外层先超时、内层还在重试，配额白烧。
  • 追问 3：那你这个项目里靠重试解决挂起吗？→ 不靠。挂起由 MODEL_TIMEOUT_S = 30.0 这道闸门兜住，而不是靠重试——重试一个"不返回"的调用只会把配额烧光。这属于"超时是断路器，重试是修复手段"，两者角色不同。
