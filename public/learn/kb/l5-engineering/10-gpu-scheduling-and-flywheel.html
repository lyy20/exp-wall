容器与 GPU 资源调度、数据飞轮与用户反馈回收 ​

覆盖知识点：L5-22 容器与 GPU 资源调度 ｜ L5-24 数据飞轮与用户反馈回收 面试频率：中 ｜ 建议学时：7h

一句话说清 ​

容器解决"跑起来一样"，GPU 调度解决"贵的东西别浪费"，而数据飞轮解决"线上出的错别白出"——飞轮的前提是归因，归因的前提是数据结构在设计时就留好了位置。

为什么必须学（面试官视角） ​

  1. 容器与 GPU 调度：L5 前九页讲的是单机上的软件工程，这一页是边界之外的约束。面试官问"你的镜像为什么这么大""GPU 怎么共享"时，考的是你有没有真正上过线。对没上过 GPU 的应届生，诚实分层（我做过 CPU 容器化，GPU 调度我了解机制但未实操）比硬答好得多。
  2. 数据飞轮：这是"这个项目有没有第二期"的判断依据。只会答"我们收集用户反馈"是弱回答；能答"我把失败样本结构化入池，离线重放来区分'知识库里没有'和'有但没检索到'，因为这两类的修复成本差一个数量级"——这是强回答。
  3. 两者的共同点：都在讲"系统长期运行"，而不是"这一次请求能不能通"。这正好是应届简历最能拉开差距的地方。

核心内容 ​

L5-22 容器与 GPU 资源调度 ​

1）镜像分层：为什么顺序决定构建速度 ​

Dockerfile 的每一层都会被缓存，只要该层及其所有前序层没变，就能复用缓存。所以顺序的唯一原则是：

变化频率从低到高排列 —— 基础镜像 → 系统依赖 → 语言依赖 → 应用代码。

真实形态（本项目 deploy/Dockerfile.api，5,749 B）：

dockerfile
FROM python:3.12-slim                  # :33   基础镜像（变化最低频）
ENV PYTHONUNBUFFERED=1                 # :36   日志不缓冲，容器日志才能实时
WORKDIR /app                           # :42
COPY deploy/requirements.api.txt .     # :56   先只拷依赖清单
RUN pip install --upgrade pip && pip install -r requirements.api.txt   # :57  依赖层
COPY code/ /app/code/                  # :64   再拷代码（变化最高频）
COPY deploy/ /app/deploy/              # :65
RUN useradd --create-home --uid 10001 yyhelp   # :74   非 root 运行用户
EXPOSE 8080                            # :80
CMD ["uvicorn", "yyhelp.api.app:app", "--host", "0.0.0.0", "--port", "8080", "--workers", "1"]  # :97

每一个设计点都能回答"为什么"：

写法为什么
先 COPY requirements 再 pip install，最后才 COPY code/改一行代码不会让几百 MB 的依赖层失效。反过来写，每次改代码都要重装依赖
python:3.12-slim 而非 python:3.12slim 去掉编译工具链与文档，体积小得多；代价是没有 gcc，需要编译的包得装构建依赖（或用 multi-stage）
PYTHONUNBUFFERED=1默认 Python 会缓冲 stdout，容器日志会延迟甚至丢失。容器里不设这个变量的日志基本不可用
--uid 10001 非 root容器逃逸后攻击面小；同时满足"以非 root 运行"这条常见合规要求
--workers 1单 worker 是有意的：多 worker 会各持一份模型/连接，内存与显存翻倍。要横向扩展应该在编排层加副本，不是在容器里加 worker

健康检查写在镜像里：

python
# Dockerfile.api:89 附近，用标准库 urlopen 探自己的 /health
urlopen('http://127.0.0.1:8080/health', timeout=5).status == 200

2）编排层：一个 compose 文件就是一次依赖审查 ​

本项目的 deploy/docker-compose.yml 是一份可以直接拿来当"依赖清单"讲的东西：

服务行号关键约束
yyhelp-api:602应用本体；logging: {driver: json-file}（:72）
mysql:83mysql:8.4.11，容器名 yyhelp-mysql，宿主端口 3307（避免与宿主 3306 冲突）
etcd:145Milvus 的元数据依赖（v3.5.25，配置 4 GiB 配额）
minio:182Milvus 的对象存储依赖；用 digest 钉版本
milvus:253向量库本体
postgres:345Langfuse 元数据
clickhouse:371Langfuse 的 trace 存储
redis:424Langfuse 队列/缓存
langfuse-worker / langfuse-web:455 / :549可观测增强路径

两个真实教训（都有据可查）：

  1. "注释里的承诺不等于配置里的实现"：compose 里 MinIO 的注释写着"用 digest 钉版本"，但 image: 行只写了滚动 tag、没带 digest。直到写了 deploy/verify_compose_semantics.py 做静态校验才被抓出来并补上（02-v1-to-v2.md:465/472、修正见 :196-203）。

    可迁移的判据：凡是"必须成立的约束"（钉版本、非 root、必需环境变量），都要有机器校验，不能只靠注释和记忆。这就是"策略即代码"的最小形态。

  2. 数据库初始化参数必须显式：MySQL 8.4.11 用 utf8mb4 + 0900 排序规则，并且显式固定时区——默认 SYSTEM 会在容器时区与宿主不一致时出问题（12-flywheel.md:410）。中文文本用错排序规则会导致排序与去重结果错误，这类问题不会报错，只会悄悄错。

为什么 Langfuse 一家要 5 个容器：langfuse-web + langfuse-worker + postgres + clickhouse + redis。这不是设计缺陷，而是 trace 存储的现实需求（写入量大、查询模式偏分析型）。但它也直接解释了 08 页 的架构选择：离线/资源受限环境下整条可观测链会失效，所以默认路径必须是零依赖的自研 JSONL trace。

3）GPU 调度：约束在哪一层 ​

核心事实：CPU 是"可超卖"的资源（1000m 可以给 20 个 Pod 各 50m），显存不是。所以 GPU 调度的第一原则是：

显存必须"独占式"分配 —— 谁占了多少 KV Cache、多少权重，是算得出的硬数字；超卖等于 OOM。

三种 GPU 共享方式与适用边界：

方式机制适用代价
整卡独占一个 Pod 拿一张整卡大模型推理（默认、最稳）贵；小模型浪费显存
MPS / 时间片共享多进程共享一张卡的算力多个小模型、或推理 + 离线任务混跑相互干扰；显存仍需事先划分
MIG（硬件分区）把一张卡切成多个独立实例需要强隔离的多租户只在新一代数据中心卡上支持；切分粒度固定，是否支持与切分规格以官方文档为准

K8s 上的 GPU 声明方式：以 NVIDIA 设备插件为例，Pod 通过资源名 nvidia.com/gpu 请求 GPU（具体资源名、device plugin 版本、以及 MIG / 时间片等高级能力对应的 CRD 或注解字段，以官方文档为准）。

编排层的 GPU 约束要写进调度：节点亲和/污点容忍（只有 GPU 节点能跑，别把 GPU Pod 排到 CPU 节点上等死）、节点标签选择（按卡型分池）、resources.limits 必须等于 requests（GPU 不可压缩）。"延迟启动"比"启动失败"更坑：Pod 会被调度到一个没有 GPU 的节点，然后在启动时报错——这类问题要在调度约束层面挡掉。

一个来自本项目的迁移判据：本项目的容器化全部在 CPU 上完成（python:3.12-slim、uid 10001、端口 8080），没有 GPU 节点，因此 GPU 调度部分只讲机制与取舍，未做任何 GPU 实操验证。

L5-24 数据飞轮与用户反馈回收 ​

1）飞轮的三入口 ​

线上有三种"不对劲"，它们必须汇入同一个池子，否则会散落在三份日志里，谁也看不到全貌：

入口判定来源含义
weak_evidence检索证据弱，被拒答闸门拦下可能是知识库没有，也可能是没检索到
self_eval_fail生成前自评没过模型自己认为答不好
user_downvote用户点踩（user_feedback = -1）最贵也最可信的信号

真实形态：TRIGGERS = ("weak_evidence", "self_eval_fail", "user_downvote")（pool.py:92）。

为什么三入口必须共用一张表：因为他们回答的是同一个问题——"用户想问什么，而我们答不了"。如果各自记各自的表，你就无法回答"这类问题一共被问了多少次、其中多少是知识缺失、多少是检索缺陷"。能聚合的前提是字段一致。

2）表设计：归因能力必须被设计进数据结构 ​

这是本页最重要的一句话。飞轮的产出质量在你建表那一刻就决定了。

双表分工（schema.sql:13-20）：

表是什么关键点
issue_pool去重后的问题（审核者的工作对象）trigger_flags 是 SET('weak_evidence','self_eval_fail','user_downvote')（schema.sql:37）——同一问题可以由多个入口共同触发；含 ask_count、max_confidence/min_confidence
issue_occurrence每一次发生（证据层）trigger 是 ENUM(...)（schema.sql:93）——单次只能由一个入口触发；含完整检索快照
issue_replay离线重放结论只增的批处理产物（schema.sql:155-156）

SET vs ENUM 的选择不是随意的：同一问题可能既是"证据弱"又被"点踩"，所以池子表的 trigger_flags 必须能装多个值（SET）；而单次发生必然由某一个入口触发（ENUM）。类型选择直接表达了业务语义。

检索快照的四处刻意设计（snapshot_from_trace(trace, *, final_context_chunk_ids=(), query_original="")，pool.py:189）：

  1. query_used 与 query_original 分开存：占位化/改写后的问题与原问题不是一回事。只存一个，重放时你无法区分"用户真这么问"和"我们改写成了这样"。
  2. retrieved_chunks（候选，含 rank/score）与 final_context_chunk_ids（真正拼进 prompt 的）分开存（schema.sql:141-144）。两者的差集 = "召回了但没喂给模型" ——这通常是上下文裁剪参数的问题，不是检索问题。只存后者，这个 bug 会被永久掩盖。
  3. 存 candidates 条而非 top_k 条：重放时要能回答"如果把 top_k 调大，正确答案会不会进来"。只存 top_k 条，答案是否在候选里这件事就永远查不到了。
  4. embedding_model + index_version 必须存：换了嵌入模型或重建了索引，旧快照的解释力就变了。没有版本号的快照是不可复现的。

入池时的四处非显然写法（Store.enqueue，pool.py:349-358）：

  • INSERT ... ON DUPLICATE KEY UPDATE（MySQL）/ ON CONFLICT ... DO UPDATE（SQLite）：把去重竞态交给唯一索引，而不是先查再插。先查再插在并发下必然重复。
  • max/min_confidence 用 GREATEST/LEAST 增量维护：在库里原地更新，不用"读出来—算—写回去"（那会丢更新）。
  • json.dumps(..., ensure_ascii=False)：保证中文在库里可读、可 grep；ensure_ascii=True 会让所有中文变成 \u 转义，排查时完全没法看。
  • 快照必须过校验才写：缺字段直接拒写。"宁可不入池，也不要空快照"——空快照在重放阶段是无用的噪声，而且会让人误以为"这条已经分析过了"。

指纹与去重的两个坑（pool.py:147 normalize_question；:167 fingerprint）：

指纹里绝不能放时间戳或会话 id，否则同一个问题每次都被算成新问题，ask_count 永远是 1——飞轮的核心指标直接失效。

这条之所以是"坑"，是因为加时间戳看起来很有用（"什么时候问的"），但它属于 occurrence 层的信息，不该进 pool 层的指纹。分层放错字段，指标就废了。

3）离线重放：区分"真缺知识"vs"没检索到" ​

这是飞轮的技术核心，也是最有面试价值的一段：

根因现象修复动作成本
知识库里真的没有候选里就没有正确片段（或片段不含答案）补知识：加文档、改切块、补同义词天级（要人写/审文档）
有但没检索到答案就在库里，候选里也没有 / 有但没进 final context调检索：top_k、candidates、加重排、改查询改写分钟级（改参数重跑）
召回到了但没喂给模型候选里有，final_context_chunk_ids 里没有调上下文装配：裁剪阈值、去重策略分钟级
喂了但答错答案在 final context 里，模型仍答错调 prompt / 换模型小时级

这张表就是"为什么必须做重放"的答案：这四类的修复成本相差数个数量级，而它们在表面上是同一个现象——"用户的问题我们答错了"。没有重放，你只能靠猜，于是大概率去修最贵的那一类（补知识）。

快照存 candidates 条而非 top_k 条的真正原因也在这里：要判定"是没检索到还是没喂进去"，你必须同时拥有候选集和最终上下文两份证据。

4）飞轮的闭环纪律 ​

  1. 入池不等于修复：池子是待办队列，不是成就。要有审核状态与优先级，否则池子会变成垃圾场。
  2. 样本要能被追踪到修复：某个问题修复后，要能验证"重放同样的问题，这次答对了"。
  3. 反馈采集不能影响主流程：点踩上报失败不能让对话失败（与 08 页 的"埋点降级不抛异常"同一条纪律）。
  4. 入池前必须脱敏：见 09 页 的实体占位化两坑。池子里的问题文本是用户输入，它是 PII 的高风险区。

一个真实的性能隐患（必须标注出处）：schema.sql:70-76 的设计注释指出——问题池达到 10 万行后，按原因统计会从 20ms 退化到约 4s。根因是 FIND_IN_SET(...) 是函数而不是列比较 ⇒ 全表扫描，而且 SET 类型无法直接走索引。修法是增一个 trigger_primary 列并建索引。

⚠️ 口径标注：这条"20ms → 4s"只有 schema.sql:70-76 的设计注释，没有实测记录，属设计预期而非实测数据，引用时必须说明。可执行的验收命令（未执行验证）：

这个坑的通用形态值得背下来："把枚举塞进一个字段"看起来省事，但它把你的统计查询从索引查询降级成全表扫描。 多值字段（SET、逗号分隔字符串、JSON 数组）在写入端很方便，在读端几乎总是性能陷阱。

一段可以直接背的飞轮答法：

"线上有三种'答不了'的信号——证据弱被拒答、生成前自评没过、用户点踩。我把三者汇进同一张问题池表，每种都带一份检索快照。快照里我存了两份证据：候选集（含 rank/score）和真正喂给模型的那几条。为什么存两份？因为它们的差集就是'召回到了但没喂给模型'，那是上下文裁剪的 bug，只存最终上下文就永远发现不了。然后离线重放，把失败分成四类：真缺知识（要补文档，天级）、没检索到（调 top_k 和重排，分钟级）、召回了没喂（调裁剪阈值，分钟级）、喂了还答错（调 prompt 或换模型）。这四类修复成本差好几个数量级，不重放就只能靠猜，而人总是倾向于去修最贵的那一类。"

面试怎么问 ​

Q1：你的镜像怎么构建的？为什么这么分层？

A（要点）：变化频率从低到高排列——基础镜像 → 系统依赖 → 语言依赖 → 应用代码。本项目 Dockerfile.api 先 COPY requirements.api.txt 再 pip install，最后才 COPY code/。

  • 加分句："分层不是为了好看：改一行代码不该让几百 MB 的依赖层失效。另外我用 python:3.12-slim 而不是完整镜像，健康检查也用标准库 urlopen 而不是 curl——镜像里的每一个依赖都要付体积税。"
  • 别说："我用 Docker 打包了。"（没有分层逻辑、没有体积意识）
  • 追问 1：为什么 --workers 1？→ 单 worker 是有意的：多 worker 会各持一份模型/连接，内存翻倍。要横向扩展在编排层加副本，不在容器里加 worker。
  • 追问 2：为什么要设 PYTHONUNBUFFERED=1？→ 不设的话 stdout 会被缓冲，容器日志延迟甚至丢失。容器里不设这个变量的日志基本不可用。
  • 追问 3：为什么 uid 10001？→ 非 root 运行，逃逸后攻击面小，也是常见合规要求。这条必须机器校验——我特意写了 deploy/verify_compose_semantics.py 做静态检查，因为本项目真抓出过"注释写着钉 digest、image: 行却没带"的错误：注释里的承诺不等于配置里的实现。

Q2：GPU 怎么调度？显存能共享吗？

A（要点）：先分清 CPU 可超卖、显存不可超卖。三种共享方式：整卡独占（最稳，大模型默认）、MPS/时间片共享（多小模型或推理+离线混跑）、MIG 硬件分区（强隔离多租户）。

  • 加分句："诚实分层：我做过的是 CPU 容器化（slim 镜像、uid 10001、端口 8080），GPU 调度我了解机制和取舍，但没有 GPU 节点、未做实操验证。"
  • 别说："GPU 用 K8s 调度就行了。"（没有共享方式、没有显存约束、没有调度约束）
  • 追问 1：K8s 上怎么请求 GPU？→ 以 NVIDIA 设备插件为例是声明资源名 nvidia.com/gpu，具体资源名、插件版本与 MIG/时间片相关字段以官方文档为准。要点是 limits 必须等于 requests（GPU 不可压缩）。
  • 追问 2：调度上有什么坑？→ 节点亲和/污点容忍要写对，否则 Pod 会被排到没有 GPU 的节点上"延迟启动失败"——比启动失败更坑的是启动成功但跑不起来。
  • 追问 3：什么时候该用 MIG？→ 需要强隔离的多租户场景（显存与故障域都切开）。代价是切分粒度固定、不是所有卡都支持，是否支持与规格以官方文档为准。

Q3：你的数据飞轮是怎么转的？

A（要点）：三入口（weak_evidence / self_eval_fail / user_downvote）汇入同一张问题池表并带检索快照；离线重放区分"真缺知识"与"没检索到"；修复结论写回 issue_replay。

  • 加分句："归因能力必须被设计进数据结构。 我在快照里存的是 candidates 条而不是 top_k 条，并且把'召回到的'和'真正喂给模型的'分开存——因为要判定'是没检索到还是没喂进去'，你必须同时有两份证据。只存最终上下文，那个 bug 会被永久掩盖。"
  • 别说："我们收集用户反馈来优化模型。"（没有结构、没有归因、没有修复闭环）
  • 追问 1：SET 还是 ENUM？→ 池子表的 trigger_flags 用 SET（同一问题可能被多个入口触发），occurrence 表的 trigger 用 ENUM（单次只由一个入口触发）。类型选择直接表达业务语义。
  • 追问 2：去重怎么做？→ 用 normalize_question 归一化后算指纹，指纹里绝不能放时间戳或会话 id——否则同一个问题每次都算新问题，ask_count 永远是 1，飞轮的核心指标直接失效。写库用 ON DUPLICATE KEY UPDATE 把竞态交给唯一索引，而不是先查再插。
  • 追问 3：数据量大了有什么问题？→ 有设计层面的坑：问题池 10 万行后按原因统计会退化（约 20ms → 4s），根因是 FIND_IN_SET(...) 是函数不是列比较 ⇒ 全表扫描，且 SET 无法走索引；修法是增一个 trigger_primary 列建索引。不过这条我只有 schema.sql 的设计注释，没有实测记录——所以我会用 EXPLAIN 去验收，而不是直接引用这个数字。
  • 追问 4：入池的数据安全吗？→ 入池前必须脱敏。本项目在实体占位化上踩过两个坑：\b\d{11}\b 在中文里失效（汉字属于 \w，没有词边界），以及单遍替换会二次匹配。池子里的问题文本是用户输入，是 PII 的高风险区。
