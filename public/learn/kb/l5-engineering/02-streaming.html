流式响应端到端与细粒度工具参数流 ​

覆盖知识点：L5-02 流式响应端到端实现 ｜ L5-03 细粒度流式（工具参数流） 面试频率：高 ｜ 建议学时：6h

一句话说清 ​

流式不是"把 stream=True 打开"，而是一条从模型 token 到浏览器像素的完整链路：模型侧增量 → 服务端分帧 → 反向代理不许缓冲 → 客户端增量渲染，任何一环把增量攒起来，用户看到的就是"转圈十秒然后一次性吐出"。

为什么必须学（面试官视角） ​

这是 L5 里最容易在面试现场被证伪的一页。面试官只需要问一个具体问题："你 SSE 响应加了哪几个头？"

  • 答"加了 Content-Type: text/event-stream"——及格。
  • 答"还有 Cache-Control: no-cache、X-Accel-Buffering: no、Connection: keep-alive"——过关，因为这说明你被反向代理坑过一次，或者认真读过别人的血泪史。
  • 答不出来——面试官会判定你的"流式"只是 demo 级别，从未经过 Nginx / 网关。

第二个必问点：流式与结构化输出、工具调用怎么共存。这直接引出 L5-03。

核心内容 ​

L5-02 流式响应端到端实现 ​

定义：服务端在生成过程中持续向客户端推送增量片段，使**首字节时间（TTFT）**远小于完整生成时间，客户端边收边渲染。

机制——四段链路，缺一不可：

  1. 模型侧：推理服务以增量方式产出 token / 片段（OpenAI 风格 stream=True 的 SSE 增量，或本地推理引擎的 token 回调）。
  2. 服务端分帧：把上游增量转成 SSE 帧。SSE 帧的硬格式是 event: <名>\ndata: <单行 JSON>\n\n——data 里不能有裸换行，因为换行是 SSE 的字段分隔符。中文不会被 SSE 破坏（SSE 是 UTF-8 文本），但 JSON 序列化时要保证不转义成不可读形式。
  3. 反向代理：必须显式关闭缓冲。Nginx 一类反代默认会对响应做缓冲聚合，一旦缓冲，流式就退化成"一次性吐出"。
  4. 客户端：解析 SSE、按事件类型分发、增量渲染（通常在 append 时保持滚动到底部），并处理"中途断开"。

为什么这样设计：LLM 的延迟结构是长尾的——总时长不可控，但首 token 是快的。流式把"用户等待感知"从 总时长 改成 TTFT，是唯一不需要改模型就能改善体感的工程手段。

数量级与形状（口径标注）：

  • RAG 项目实测（bench_latency.py，30 题样本，本机 CPU 环境）：TTFT 三次实测 14.90 / 10.00 / 14.86 秒，而 LLM 生成 P50 只有 1.26 秒（docs/projects/rag/11-serving.md）。
  • 这张数表的结论反直觉：TTFT ≈ 检索耗时，不是生成耗时。也就是说，"首字慢"的根因在检索与精排，不在模型。
  • 未执行验证：本页未在本机跑过"开/关 X-Accel-Buffering 的对照实验"。验收命令（判据：带该头时首字节到达时间显著早于响应结束时间）：

误区后果正解
只设 media_type="text/event-stream"经反代后退化成一次性吐出显式加 Cache-Control: no-cache、X-Accel-Buffering: no、Connection: keep-alive
data 里塞多行文本客户端解析错位（换行即分帧）data 只放单行 JSON；多行内容放进 JSON 字段里
用"拒答走 4xx"表达业务失败客户端流式解析器在拿到错误码前就断了，前端逻辑要写两套拒答与正常回答共用同一个 token 事件，用事件内容而非状态码区分
流式里做阻塞的同步检索事件循环被占住，多个流互相拖死同步检索/模型调用放线程池，或改异步客户端

三个必需的响应头（面试标准答案，逐条给理由）：

头不加会怎样
Cache-Control: no-cache中间缓存/CDN 可能缓存响应体，第二个用户拿到上一个人的答案

Connection: keep-alive连接被提前关闭，客户端只收到前半段

L5-03 细粒度流式（工具参数流） ​

定义：工具调用的参数也以增量分片的形式推送，让前端在工具真正执行前就能展示"模型正在生成什么参数"。

机制：模型输出的 tool call 参数本身是一段文本（JSON 字符串），天然可以分片。按分片粒度可分两档：

  • 粗粒度：只在参数完整时给出一次（大多数 API 的默认行为）。
  • 细粒度：按 token/小块持续推送 JSON 片段，客户端需要增量拼接 + 容错解析（未闭合的 JSON 是常态）。

为什么这样设计：工具参数可能很长（例如一份结构化的查询条件、一段 SQL、多轮检索计划）。粗粒度下，用户看到的是"模型卡住不动"，直到参数全部生成完毕才出现一次跳变。细粒度把这段等待也变成可见进度。

数量级与形状：参数流的总字节量与粗粒度相同，差别只在首片时间。因此它的收益完全体现在体感，不体现在总耗时——如果参数只有 20 个 token，细粒度没有意义；参数上千 token 时收益才明显。

常见误区：

误区说明
把增量片段拼成 JSON 后 json.loads未闭合的片段一定解析失败；要累积后解析，解析失败就继续累积，永不抛异常
前端等"参数完整"才渲染那等于没用细粒度
认为细粒度会减少总时长它只改首片时间，不改总时长与总 token
参数分片与工具执行混在一个流里客户端无法区分"参数还在生成"和"工具正在跑"，需要显式的阶段事件

代码（增量拼接，语法确定的最小实现）：

python
buf = ""
for piece in param_stream:          # piece 是 JSON 文本的一个片段
    buf += piece
    try:
        obj = json.loads(buf)
    except json.JSONDecodeError:
        continue                    # 未闭合是常态，继续累积，不报错
    yield ("tool_args_done", obj)

两条可直接讲的真实教训：

  1. 引用校验必须在流结束后做。RAG 项目在流结束后判断 answer.strip() == REFUSAL_TEXT ⇒ refused=True, note="模型自述资料不足"，否则用正则抽出引用编号再校验。流式让人误以为"边生成边校验"，实际上引用完整性只有拿到全文才能判断。
  2. 出错仍返回 200 是一个刻意的设计取舍。代价是客户端必须解析 error 事件；收益是"已经流出去的那半段答案"不会被 HTTP 错误码抹掉——前端可以把 partial_answer 留在屏幕上并标红。这个取舍适合"答案有部分价值"的场景（问答、摘要），不适合"全有或全无"的场景（写库、支付）。

面试怎么问 ​

Q1：你的流式是怎么实现的？加了哪些响应头？

A（要点）：模型侧增量 → 服务端按 event: ...\ndata: <单行 JSON>\n\n 分帧 → 反向代理关闭缓冲 → 客户端增量渲染。三个必需头：Cache-Control: no-cache、X-Accel-Buffering: no、Connection: keep-alive。

  • 加分句："X-Accel-Buffering: no 是最容易漏的一个——本地直连 uvicorn 时一切正常，一旦前面挂上 Nginx，流式就退化成一次性吐出。所以我在本地验证时会刻意让请求走一遍反代，而不是只打 127.0.0.1:8080。"
  • 别说："我用了 StreamingResponse，就流起来了。"（没说分帧与反代）
  • 追问 1：data 里能不能放多行 JSON？→ 不能裸放。换行是 SSE 字段分隔符，多行内容要放进 JSON 字符串里（要么转义、要么用 data: 多行续行规则——后者要求客户端支持拼接，复杂度更高，不推荐）。
  • 追问 2：落后端怎么保活？→ 长生成期间需要心跳（注释行或轻量事件）防止中间设备按空闲超时断连。心跳间隔取"小于链路上最短的空闲超时"为原则，具体阈值以各中间件配置为准。
  • 追问 3：客户端断开后服务端会怎样？→ 同步生成器在每次 yield 时才能感知断连；所以 finally 里的配额释放是必须的。漏两次在并发上限只有 2 的场景下等于服务直接不可用。

Q2：拒答怎么走流式？用 4xx 还是正常流？

A（要点）：走正常流，与正常回答共用同一个事件类型，用内容区分。理由是客户端解析器与渲染逻辑只需要一套。

  • 加分句："我在项目里统一了一个 token 事件承载两类内容，拒答就是一段特殊的文本。这样前端的流式解析器不需要为拒答写第二条分支，也不会出现'已经渲染了半句、后端再纠正是错误码'的撕裂状态。"
  • 别说："拒答我直接返回 400。"（会把流式链路劈成两套）
  • 追问 1：那前端怎么知道这是拒答？→ 用一个显式的结构化事件（如头部或结束事件里的 refused 标志位），而不是让前端做字符串匹配。
  • 追问 2：出错呢？→ 同理，RAG 项目的选择是出错仍返回 200，用 error 事件带 partial_answer；这是"部分价值 > 全有或全无"的场景取舍。
  • 追问 3：反过来什么场景必须用错误码？→"全有或全无"的写操作（写库、下单）。此时部分成功比失败更危险，应该一开始就走非流式 + 事务。

Q3：流式让 TTFT 变好，那 TTFT 的瓶颈在哪？

A（要点）：先测再优化。不能用"流式"这个手段去解首字延迟，因为首字延迟的瓶颈通常不在生成侧。

  • 加分句："我实测过：TTFT 三次是 14.90、10.00、14.86 秒（bench_latency.py，30 题样本，本机 CPU 环境），而 LLM 生成 P50 只有 1.26 秒。也就是说首字慢几乎全部来自检索与 CPU 精排——在这套系统上优化 LLM 生成是错的方向。"
  • 别说："流式能让首字更快。"（流式不改变上游 TTFT，只改变投递方式）
  • 追问 1：那怎么改？→ 按耗时排序定位：先解决最耗时的那一跳（本项目是 CPU 精排 20 对约 8.5 秒），流式只是把已发生的时间在感知上摊开。
  • 追问 2：怎么验证优化有效？→ 同一口径重跑 bench_latency.py，比对 TTFT 与端到端分位数；样本量与冷启动剔除规则必须一致。
  • 追问 3：分位数能写进 SLA 吗？→ 本项目的压测每档只有 3–8 个请求，分位数不可写进 SLA，只能作为结构性结论（延迟随并发线性增长、吞吐饱和）。
