推理服务：vLLM 架构、参数调优、并行策略与 KV Cache 优化 ​

覆盖知识点：L5-09 vLLM 架构总览与部署 ｜ L5-10 核心参数与吞吐调优 ｜ L5-11 并行策略 TP/PP/DP/EP ｜ L5-12 KV Cache 优化与卸载 面试频率：高 ｜ 建议学时：18h

一句话说清 ​

自建推理服务的全部收益与全部约束都来自同一件事：把显存切成"权重 + KV Cache"两块，然后用调度器让 GPU 永远有活干——PagedAttention 解决第一半，连续批处理解决第二半。

为什么必须学（面试官视角） ​

这是 L5 最容易被"读过博客的人"和"调过模型的人"区分开的一页。面试官的三连问通常是：

  1. PagedAttention 到底解决了什么？（答"省显存"会被追问到崩；正解是"解决 KV Cache 的碎片化，从而允许更高并发"）
  2. 显存不够怎么办？（正确顺序：先算清权重能装下几张卡、再定并行策略、再调 KV 预算——不是先加卡）
  3. TP 和 PP 什么时候用哪个？（判据是卡间带宽与是否同机，不是"哪个更先进"）

⚠️ 本页纪律：vLLM 的具体参数名、默认值、启动方式、量化与投机解码的字段名、K8s GPU 调度的 CRD 字段，各版本差异很大，一律以官方文档为准。本页只讲机制与取舍。

核心内容 ​

L5-09 vLLM 架构总览：两个机制，一个目标 ​

目标：在给定显存下尽可能提高吞吐，同时不让单请求延迟劣化到不可接受。

机制一：PagedAttention —— 把 KV Cache 变成"分页显存"

问题背景（先讲问题，再讲方案）：

  • 自回归生成要为每个序列保存历史 token 的 Key/Value 向量，这部分叫 KV Cache，随生成长度线性增长。
  • 朴素实现为每个序列预留一段连续显存（按最大可能长度预留），后果有两个：内部碎片（实际只用了预留的一小部分）和外部碎片（连续块凑不出来，明明总量够却分配失败）。
  • 于是显存利用率低 ⇒ 能并发的序列少 ⇒ GPU 空转。

PagedAttention 的思路直接借自操作系统的虚拟内存分页：把 KV Cache 切成固定大小的块（block），块可以不连续存放，用一张块表把"逻辑位置 → 物理块"映射起来。

由此获得三个能力：

能力机制收益
近乎零碎片块大小固定，分配以块为单位显存利用率高，同显存能装更多并发序列
块级共享多个序列的逻辑位置映射到同一物理块（写时复制）相同前缀只存一份，prompt 前缀缓存天然成立
按需增长生成到哪一步才分配下一块不需要按最大长度预留

面试关键话术：PagedAttention 的直接收益不是"推理更快"，而是**"同样显存能承载更多并发序列"；吞吐提升是并发放大的结果**，不是它自己变快了。把因果讲反了，后面所有调优推理都会错。

机制二：连续批处理（Continuous Batching）

传统静态批处理：一批请求凑齐 → 一起前向 → 等最慢的那个生成完 → 整批一起释放。后果是长尾阻塞：一个生成了 2000 token 的请求会把同批里已经生成完的 199 个请求一起拖住。

连续批处理（也叫 iteration-level scheduling）：调度粒度从"批"降到"每一步迭代"——每生成一步就重新组批，某序列结束就立刻释放其槽位并补进新请求。

维度静态批处理连续批处理
组批时机一次每一步迭代
短请求等待等最长的那个自己一结束就走
GPU 利用率尾部大量空转持续满负荷
延迟特征尾延迟差尾延迟显著改善

两者是互补的：PagedAttention 让"能同时装下多少序列"变大，连续批处理让"装下的槽位随时有人在用"。缺一个，另一个的收益都发挥不出来。

部署形态（机制层面，不含具体命令）：

  • 推理服务对外暴露兼容 OpenAI 风格的 HTTP 接口（这也是它能被上层业务当"本地 OpenAI"使用的根本原因）。
  • 启动时一次性加载权重并分配 KV 显存池；加载耗时是离线属性，不属于在线 SLA（本项目 RAG 侧冷启动 67.3 秒的实测就是这个性质，bench_latency.py --n 30，30 题样本，本机 CPU 环境）。
  • 具体 CLI 参数、Docker 镜像、K8s 部署方式：以官方文档为准。

L5-10 核心参数与吞吐调优 ​

参数优化的本质是三个量的三方拉扯：

text
显存总量 = 权重 + KV Cache 池 + 激活/临时开销
1
  • 权重由模型大小与精度决定（量化能显著压缩，见 07 页）。
  • KV Cache 池决定"能并发多少序列"。
  • 二者此消彼长：权重占得多，并发就少。

四个必须会讲的旋钮（机制描述，具体名称与默认值以官方文档为准）：

旋钮（示意名）控制什么调大的收益调大的代价
显存利用率上限（gpu_memory_utilization 一类）KV Cache 池占比并发序列更多、吞吐更高留给激活/临时显存变少，易 OOM；与同卡其他进程冲突
最大同时处理序列数（max_num_seqs 一类）批大小上限吞吐上升（GPU 更满）单请求延迟上升；注意它是"序列数"不是"token 数"
最大上下文长度（max_model_len 一类）单序列最长长度支持长文档直接压缩可用并发槽位；超过后必须拒绝而不是截断
前缀缓存开关（prefix caching 一类）是否复用相同前缀的 KV共享前缀场景省 prefill、降 TTFT需要块级共享与哈希命中判断；无共享前缀时无收益

核心取舍（面试最爱问的一条）：

吞吐与延迟是一根绳子的两端。 把 max_num_seqs / 批上限调大，吞吐上升但单请求延迟上升；调小则相反。定价方式决定了该往哪边调：按 token 计费的自营服务偏向吞吐；面向交互式场景的 API 偏向延迟。

本项目可以直接引用一个现实约束作为对照：YYHelp 实测 deepseek-v4-pro 单次调用 7.76 秒，而 MODEL_TIMEOUT_S = 30.0 是相对它按 P50 口径留了约 4 倍余量。这说明在"单次调用已经 7.76 秒"的前提下，用户可见的延迟瓶颈未必在推理引擎的批处理效率上——先做延迟分解，再决定调哪个旋钮。

调优的正确顺序（可背）：

  1. 量：先测当前 TTFT / TPOT / 吞吐基线，并记录并发档位。
  2. 算：把权重显存算清（参数量 × 每参数字节数），确认还剩多少给 KV。
  3. 定并发上限：由 KV 预算 ÷ 平均序列长度估算，再留安全余量。
  4. 调批上限：观察 GPU 利用率与尾延迟的交换曲线，取拐点而不是极值。
  5. 开前缀缓存：如果业务 prompt 有明显共享前缀。

常见误区：

误区更正
"显存不够就加卡"先看是否量化可行、max_model_len 是否设得过大、批是否过大
"把显存利用率调到最高就最快"上限过高会 OOM 或与同卡其他进程抢显存；吞吐拐点通常在 100% 之前
"max_model_len 加大只是慢一点"它直接减少可并发槽位，对吞吐是乘法级影响
"连续批处理能让单请求更快"它优化的是吞吐与尾延迟；单请求的 TPOT 基本不变
把"每秒请求数"当吞吐指标LLM 的正确吞吐单位是 token/s（输出 token 吞吐）与并发序列数，不是 RPS

L5-11 并行策略 TP / PP / DP / EP ​

判据先给结论：

策略切什么通信模式适用边界关键代价
TP（张量并行）切单层的矩阵计算每层都要 all-reduce，通信量极大且频繁同机多卡、NVLink 一类高带宽互连跨机做 TP 会被网络带宽拖死
PP（流水并行）按层切段只在段边界传激活值，通信量小跨机扩展、卡间带宽一般流水线气泡（填充/排空期间有空闲）
DP（数据并行）每卡一份完整模型，切数据几乎无通信（各算各的）权重装得下单卡时的吞吐扩展显存冗余：N 份权重
EP（专家并行）MoE 的专家分散到不同卡需要 token 路由/全对全通信MoE 架构模型路由不均衡 ⇒ 部分卡热点

为什么这样设计：并行的选择由硬件拓扑决定，而不是由"哪个更先进"决定。

  • 高带宽同机互连 ⇒ 敢做 TP，因为每层的 all-reduce 通信量能被打包进计算里。
  • 只有普通网络 ⇒ 只能做 PP，因为层边界通信量小得多。
  • 权重能装进单卡 ⇒ 优先 DP（最简单、无通信），只有在吞吐还不够时才考虑 TP/PP 把更大的模型塞进来。

组合使用的现实形态：大模型部署常见组合是"机器间 PP × 机器内 TP"（具体的并行度配置项名称与语义以官方文档为准）。此时还要注意：并行度会改变可用显存与批上限——TP 会把权重和 KV 都切成 N 份（单卡压力减小），PP 则会把不同层的显存压在不同卡上（可能出现"某些卡紧、某些卡松"的不均衡）。

数量级与形状：

  • TP 的每层通信是瓶颈所在，因此在多机场景下 TP 度一旦跨机，吞吐往往不升反降。
  • PP 的代价可量化为气泡比 ≈ (段数 - 1) / 总步数——步数越多（批越大、序列越长），气泡占比越小。这是"大 batch 才能掩盖 PP 气泡"的原因，也是 PP 与"低延迟小批"天然冲突的原因。
  • 未执行验证：本页没有跑过并行度对照实验（本环境无多卡）。验收方式（判据：固定输入与并发下比较输出 token/s）：

L5-12 KV Cache 优化与卸载 ​

四条路线，按"收益/成本比"排序：

路线机制收益代价 / 注意
前缀缓存复用PagedAttention 的块级共享 + 前缀哈希命中 ⇒ 相同前缀只算一次 prefill共享 system prompt/少样本时直接省 prefill，降 TTFT前缀必须真的相同；把动态内容放进前缀会使其失效
KV 量化把 KV 以更低精度存储KV 池容量成倍增长 ⇒ 并发提升精度损失（尤其长上下文）；具体支持精度以官方文档为准
KV 卸载（offload）把不活跃序列的 KV 换出到 CPU 内存 / NVMe，需要时换回显存池等价扩大PCIe/存储带宽成为新瓶颈；换回延迟会伤尾延迟
分离式部署（PD 分离）prefill 与 decode 拆到不同实例：prefill 是计算密集（大矩阵乘）、decode 是访存密集（每步只算一个 token 但要读整个 KV）各自用最合适的批与并行配置，互不干扰需要把 KV 在实例间搬运（网络开销与新的一致性面）

为什么"分离"有价值：prefill 与 decode 的资源特征几乎相反——

  • prefill：一次处理整段 prompt，计算密集、吞吐高、对大 batch 敏感度低。
  • decode：每步只生成一个 token 但要读全部 KV，访存密集、对 batch 敏感（批量越大越划算）。

把两者混在同一实例里，就必然要在"哪种配置更好"之间妥协。分离后 prefill 实例可以吃长 prompt 大 batch，decode 实例专注低延迟小步长。

KV Cache 与应用侧的直接关系（把推理和业务连起来）：KV 是按序列占显存的，序列越长、并发越多，KV 越大。这解释了一个业务侧常被忽略的事实：

你限制 max_model_len 或限制长文档输入，不是在"限制功能"，而是在保护并发容量**。**上下文长度与并发数是显存池里的零和关系。

常见误区：

误区更正
"KV 量化不会掉效果"会掉，尤其长上下文；必须用同一套评测集做前后对照
"卸载到 CPU 就没代价"换了资源瓶颈而已；换入换出会直接体现在尾延迟上
"PD 分离一定更好"只在有明确的 prefill/decode 混合干扰、且网络能把 KV 搬得动时才更好
把 KV Cache 当"普通缓存"它是显存里的活跃状态，不是可随时清空的只读缓存；没有它就等于从头重算

面试怎么问 ​

Q1：PagedAttention 解决了什么问题？为什么它能提升吞吐？

A（要点）：解决 KV Cache 的显存碎片化。朴素实现按最大长度预留连续显存，导致内部碎片（预留多、用少）与外部碎片（总量够但凑不出连续块），显存利用率低 ⇒ 并发序列少 ⇒ GPU 空转。PagedAttention 把 KV 切成固定大小的块、允许不连续存放，用块表映射逻辑位置到物理块。

  • 加分句："关键是把因果讲对：PagedAttention 的直接收益是'同显存能装下更多并发序列'，吞吐提升是并发放大的结果。如果以为它让单条推理变快，后面调优的方向就会全错。"
  • 别说："它省显存。"（不解释碎片与机制，会被追问"省显存为什么就能提吞吐"）
  • 追问 1：块的粒度是怎么定的？→ 块大小是引擎的实现选择，涉及"块表开销 vs 内部碎片"的权衡。具体默认值与可配置项以官方文档为准；面试只要讲清权衡方向即可。
  • 追问 2：块级共享是怎么实现的？→ 多个序列的逻辑位置映射到同一物理块；一旦某个序列要修改共享块，就做写时复制。这天然给出了 prompt 前缀缓存。
  • 追问 3：如果所有请求都没有共享前缀，PagedAttention 还有用吗？→ 有。碎片的减少与按需增长仍然成立，只是少了共享这一块收益。

Q2：显存不够跑大模型，你怎么办？

A（要点）：按收益/成本排序，不是先加卡。① 量化权重（FP8/INT8/4bit 一类，收益最大、掉精度需评测）；② 缩短 max_model_len 或限制输入长度（它是显存池里的零和项）；③ 降低批上限/并发上限；④ KV 量化或 KV 卸载；⑤ 才上 TP/PP 把压力摊到多卡。

  • 加分句："我会先算账：权重 = 参数量 × 每参数字节数，先确认它能不能装进一张卡；装不进才谈并行，装得进但并发不够才谈 KV 侧优化。并行不是第一选择，它是权重装不下时的被迫选择。"
  • 别说："加卡就行。"（没有顺序、没有算账）
  • 追问 1：24GB 卡跑 32B 模型可以吗？→ 取决于精度与量化方案：FP16 下 32B 权重约 64 GB，单卡装不下；4bit 量化后权重约 16 GB 量级，理论可装但KV 池与激活的余量会非常紧，实际可行性与支持情况以官方文档与实测为准。
  • 追问 2：KV 量化能省多少？→ 省的倍数等于精度压缩比（例如 16bit → 8bit 理论约 2 倍 KV 容量），但精度损失必须用评测集验证，尤其长上下文场景。
  • 追问 3：卸载到 CPU 什么时候值得？→ 当你能容忍尾延迟变差、且换出换入的频率不高时。它把瓶颈从显存换成 PCIe/存储带宽，不是消除瓶颈。

Q3：TP 和 PP 怎么选？

A（要点）：看硬件拓扑。TP 每层都要 all-reduce、通信量极大且频繁 ⇒ 只能同机高带宽互连；PP 只在层边界传激活、通信量小 ⇒ 适合跨机，代价是流水线气泡。

  • 加分句："我记这条的判据是'通信量与频率'：TP 是每层通信，PP 是每 N 层通信一次。所以哪怕跨机带宽不差，TP 跨机也会被 all-reduce 拖死。合并做法是机器间 PP、机器内 TP。"
  • 别说："TP 比 PP 快。"（两者解决的不是同一个问题）
  • 追问 1：PP 的气泡怎么缓解？→ 增大批/步数让填充排空占比下降；但这与低延迟目标冲突——气泡小的配置往往批大、延迟高。
  • 追问 2：DP 什么时候最划算？→ 权重能装进单卡时。DP 几乎无通信、实现最简单，代价是 N 份权重冗余。它扩的是吞吐不是模型规模。
  • 追问 3：EP 是给谁的？→ MoE 架构。专家分散到不同卡，token 路由需要全对全通信；风险是路由不均衡导致部分卡成为热点。具体并行度配置项以官方文档为准。

Q4：KV Cache 优化你了解哪些？PD 分离为什么有用？

A（要点）：四条路线——前缀缓存复用、KV 量化、KV 卸载、PD 分离。PD 分离的价值在于 prefill 与 decode 的资源特征相反：prefill 计算密集（一次算整段 prompt），decode 访存密集（每步只生成一个 token 却要读全部 KV）。混在同一实例里只能在配置上妥协。

  • 加分句："我理解 PD 分离的代价是 KV 要在实例间搬运——所以它只在对 prefill/decode 混合干扰敏感、且网络搬得动 KV 时才划算。它不是无条件的更好架构。"
  • 别说："PD 分离就是把 prefill 和 decode 分开，更快。"（不说为什么、不说代价）
  • 追问 1：这和业务侧有什么关系？→ 直接关系是上下文长度与并发数是零和。业务限制长输入不是在限制功能，而是在保护并发容量与尾延迟。
  • 追问 2：前缀缓存和 PagedAttention 是一回事吗？→ 不是。PagedAttention 是机制（分块 + 块表 + 写时复制），前缀缓存是利用这套机制的策略（识别相同前缀并复用其块）。
  • 追问 3：怎么验证 KV 优化真的有效？→ 固定输入与并发，比较 TTFT、TPOT、输出 token/s 三项；同时必须用同一评测集验证效果没有下降。只报速度不报效果，等于没验证。
