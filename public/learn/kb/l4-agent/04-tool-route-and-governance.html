工具选择与路由、工具结果治理 ​

覆盖知识点：L4-08 L4-09 ｜ 面试频率：高 ｜ 建议学时：6h

一句话说清 ​

工具治理有两端，方向正好相反：入口端要「收窄」——把全量工具筛成一小撮候选再交给模型，因为工具描述是每一轮都要重新付一遍的固定开销，而且候选越多选错概率越高；出口端要「压缩」——工具返回值必须治理后才能回填，因为一条没治理的日志工具能在一步之内把上下文推爆。入口收窄和出口压缩的区别在于：入口可以「不让它看见」，出口不行（结果是这次任务的信息，删掉就是永久丢失）。所以出口的正确做法是「保留可核对的信息 + 明确标注被省略了什么」，而不是随手截断。

为什么必须学（面试官视角） ​

这两条在频率上一次是「中」、一次是「高」，但它们回答的其实是面试官最爱问的两个工程成熟度问题：

  • 「你系统里有多少工具？模型怎么选？」——如果你的答案只有「把 schema 全给它，它自己会选」，面试官的下一个问题是「那 50 个工具呢」。这一问筛的是有没有做过规模化系统。真实业务系统里工具数轻松过 50，每轮固定开销会变成主要成本。
  • 「工具返回一大坨东西怎么办？」——这一问几乎必然出现，因为它是Agent 崩溃最直接的原因。答「我会截断」是及格线，答出「截断会丢信息，所以我要保留头尾 + 中间标注 + 完整结果落盘可按需分页取」才是加分。更重要的是：这一问会顺着引到 上下文工程 和 记忆系统，能不能把这三页串成一件事讲，是区分「背过知识点」和「真的设计过」的分水岭。
  • 一个反直觉的加分点：项目里工具可见性收窄的三条理由中，最值钱的不是上下文，是越权副作用。面试官问「你为什么要给不同专家不同工具」，大部分人会答「省 token」；答**「防越权写操作」**的人立刻高一个档次，因为他把工具可见性从「性能优化」重新定义成了「权限边界」——而权限边界是安全属性，不是性能属性。这一条是本页最值得带走的话术。

核心内容 ​

L4-08 工具选择与路由（含 Tool Search） ​

  • 定义：当工具数量超过模型能稳定选择的规模（经验上十几个就开始退化）时，先用一个筛选步骤把候选集缩到一个小组（常见 5–8 个），再把这一小组的 schema 交给模型做最终选择。这个筛选步骤可以是规则、可以是检索、也可以是分层菜单。

  • 机制（四种收窄手段，按成本从低到高）：

手段怎么做什么时候用代价
静态可见性（按角色切）每个 Agent / 专家 / 会话角色只挂自己那几个工具工具天然按业务域分组，且角色边界就是权限边界跨域请求需要显式转交机制
规则前置用意图分类 / 关键词 / 用户角色先定「可能的域」域划分清晰、误分类代价低分类器本身要评测；分错就再也选不到正确工具
检索式 Tool Search把工具描述向量化，用当前 query 检索 Top-k 个工具工具数大（50+）、描述文本丰富、域边界模糊多一次检索开销与一次召回率风险（漏召回 = 工具不可见）
分层菜单先让模型选「类别」，再返回该类下的工具清单工具可以自然分层（域 → 动作）多一轮模型调用，延迟上升

  • 为什么这样设计（三条理由，按重要性排）：

    1. 上下文膨胀：工具 schema 是每轮固定开销。15 个工具、平均 200 token 就是每次模型调用 3000 token 起步；6 步循环就是 18000 token——这笔钱和用户问什么无关。
    2. 选错工具：候选集合越大，语义重叠的工具越多，模型选错的概率越高。而且一次错调在 ReAct 循环里要花掉一步预算——如果步数上限只有 6，一次错调就是 1/6 的预算没了。
    3. 越权副作用（最值钱的一条）：工具可见性同时是一条权限边界。「不该看到某个工具的专家，在提示词层面根本看不到它的 schema」——这不是省 token，这是从结构上让某个角色不可能发起某个动作。它比「在 system prompt 里写『不要调用 create_ticket』」强得多，因为后者的防线是模型的服从性，前者的防线是信息不存在。

  • 数量级与形状：

    • 静态可见性的收窄幅度可以很大：项目的真实形状是「5 个专家 × 全量 5 个工具，每个专家只看得见 1–3 个」，覆盖单域请求与跨域请求的9 条可见性探针用来验证这个子集结构。
    • Tool Search 的候选集通常落在 5–10 个；太少会漏召回，太多等于没收窄。
    • 必须能回答「收窄的并集覆盖」：所有子集的并集必须等于全量工具集，否则存在永远不可达的工具。这是一条可以写成断言的不变量。

  • 常见误区：

    • 只收窄不检查并集：某个工具谁都不挂 → 它永远不会被调用，且没有任何报错。这正是「并集断言」要守的东西。
    • 把 Tool Search 当成纯性能优化：检索筛选会引入漏召回，一个本该被选中的工具因为描述和 query 不相似而没进候选——这种失败没有任何症状，只有当你发现「模型答不出某类问题」时才可能追溯到它。
    • 以为收窄是「少给提示」：收窄是结构性的（schema 根本不出现），不是提示性的（在 prompt 里说「尽量别用」）。两者可靠性差一个数量级。
    • 跨域请求没有转交机制：用户一句话里有「退款 + 改地址」，两个域，但当前专家只看得见一个域的工具——如果没有「交出控制权、转到另一个专家」的通道，跨域请求就必然答不全。这是静态可见性的固有代价，必须显式设计出口。
    • 工具描述不参与收窄决策却指望检索准：Tool Search 的效果直接取决于描述文本的质量——描述写得像 docstring，检索就召不回来。这一条把 L4-08 和 L4-05 绑在一起了。

  • 代码（收窄 + 并集不变量，后者是本页最该带走的一条）：

python
# 伪代码：静态可见性 + 并集断言
ALL_TOOLS = {"search_kb", "query_order", "query_refund_policy",
             "query_logistics", "create_ticket"}          # 全量真源，只维护一份

VISIBLE = {                                                # 每个角色的工具白名单
    "kb_faq":      ("search_kb",),                         # 1 个
    "order_ops":   ("query_order", "query_logistics"),     # 2 个
    "refund_flow": ("query_refund_policy", "query_order", "create_ticket"),
    "service_ops": ("query_logistics", "create_ticket"),
    "agent_free":  ("search_kb", "query_order"),           # 兜底角色
}

def visible_tools(role: str) -> tuple[str, ...]:
    """返回该角色可见的工具名。收窄失败时宁可少给，也不许静默给全量。"""
    return tuple(t for t in VISIBLE.get(role, ()) if t in ALL_TOOLS)

def assert_union_covers(visible: dict[str, tuple[str, ...]], all_tools: set[str]) -> None:
    """不变量：所有角色可见工具的并集必须覆盖全量工具。
    少了任何一个 → 存在永远不可达的工具，且不会有任何运行时报错。"""
    union = {t for tools in visible.values() for t in tools}
    missing = all_tools - union
    assert not missing, f"unreachable_tools: {sorted(missing)}"
    # 反向也值得断：可见集里出现了不在全量里的工具名 → 拼写错误
    assert not (union - all_tools), f"unknown_tools: {sorted(union - all_tools)}"

L4-09 工具结果治理与上下文管理 ​

  • 定义：工具返回的原始结果在回填进对话历史之前，必须经过一次面向模型的加工：截断、摘要、结构化压缩、分页引用。目标是让观测长度受控、信息密度高、且被省略的部分是可追溯的。

  • 机制（四类治理手段 + 一条兜底原则）：

手段做法适合的返回形状丢什么
截断（保留头尾）保留前 N 行 + 后 M 行 + 中间一行「已省略 K 行」标记日志、trace、长列表中间部分（但标注了）
摘要用一个小模型把结果压成几句话非结构化长文本、搜索结果细节与原文措辞
结构化压缩只保留字段名与值，去掉重复的 JSON 骨架 / 冗余键结构化 API 返回嵌套层级与调式信息
分页 / 引用只回填一个句柄（id 或路径），需要时再取大对象、文件、大结果集无（代价是多一次往返）

兜底原则：被省略的部分必须可追溯。 完整结果落盘（或留在 state 里），观测里带上「被截断」的标记与取回方式。「静默丢弃」和「显式截断」的区别是：前者让模型在缺少信息时自信地编，后者让模型知道自己缺什么。

  • 为什么这样设计：

    • 为什么必须治理而不是「等超了再说」：治理的成本是一段代码；不治理的成本是一次已经被付掉的 token 费 + 一次延迟 + 一个可能已经爆掉的上下文。上下文超限时的报错通常发生在一次请求里，而那次请求的花费已经产生了。
    • 为什么不能简单取前 N 个字符：工具返回的信息密度是不均匀的。日志的错误行常在尾部，结构化结果的关键字段常在头部，Excel 表格的合计行常在末尾——只留头部会把最需要的那一行丢掉。所以「保留头尾 + 中间标注」比「截断到 N 字符」划算得多。
    • 为什么治理要可观测：治理本身是「信息删减」动作。如果 trace 里看不出「这次回填了多少、被砍掉了多少、为什么砍」，事后归因时你无法区分「模型没答出来」是因为它真的不知道还是因为你把证据砍掉了。这和记忆召回留痕（见 记忆系统）是同一条纪律：能算/能记录的东西不要猜。
    • 为什么出口治理和入口收窄方向相反：入口的收窄是权限，可以硬性「不给看」；出口的压缩是信息损失，只能「少给但可追回」。把两者混为一谈会导致一个典型错误：为了让上下文变短而把工具结果永久丢掉。

  • 数量级与形状：

    • 单次工具返回超过几千字符就该走治理；日志类工具返回上万行是常态。
    • 一次 Agent 会话的总 token 里，工具结果往往是占比最大的一项——比 system prompt 和用户输入加起来都大。
    • 治理后的观测建议落在几百字符到一千字符这个量级：太短会丢关键信息，太长会挤掉后续轮次的预算。

  • 常见误区：

    • 只截断不标注：模型不知道信息被省略了，于是基于不完整的观测给出确定性的答案。
    • 对结构化结果做自然语言摘要：把「订单号 SO123，状态已发货」压成「订单状态良好」——关键字段无法再被核对。
    • 治理策略写死在代码里，不区分工具：不同工具的「关键信息在哪」完全不同，治理策略应当按工具类型配置，而不是全局一刀切。
    • 把治理当纯性能优化：它同时是正确性问题——被治理掉的信息如果必须用于回答，模型只能编。
    • 忘了并行调用会放大峰值：一次响应里 3 个工具结果同时回填，峰值是串行的 3 倍。治理阈值要按批次总长度算，不是按单个结果算。

  • 代码（按工具的治理策略 + 可追溯标记）：

python
# 伪代码：默认治理器。核心是「头尾保留 + 中间显式标注 + 完整结果可追回」。
HEAD_LINES, TAIL_LINES = 40, 20
CHAR_BUDGET = 4000

def govern(tool_name: str, raw: str, *, ref_id: str = "") -> str:
    """把工具原始返回加工成一段给模型看的观测。绝不静默丢弃。"""
    raw = raw or ""
    if tool_name.endswith("_log"):                 # 日志类：错误通常在尾部
        return _head_tail(raw, HEAD_LINES, TAIL_LINES, ref_id)
    if tool_name.startswith("query_"):             # 结构化查询：保留字段，去骨架
        return _compact_json(raw, CHAR_BUDGET, ref_id)
    return _head_tail(raw, HEAD_LINES, TAIL_LINES, ref_id)

def _head_tail(raw: str, head: int, tail: int, ref_id: str) -> str:
    lines = raw.splitlines()
    if len(lines) <= head + tail:
        return raw
    omitted = len(lines) - head - tail
    marker = f"... [已省略 {omitted} 行；完整结果 ref={ref_id or 'n/a'}，需要时用 read_ref 分页取回] ..."
    return "\n".join(lines[:head] + [marker] + lines[-tail:])

和你自己的项目对上号 ​

YYHelp v2（LangGraph 电商客服 Agent）：L4-08 在这个项目里有完整的实现 + 一条诚实的未实测声明，L4-09 有分散但齐全的落点。

  • L4-08 静态可见性（可直接引用的真实形状）：5 个专家 × 5 个工具（v1 全量），每个专家只看得见 1–3 个；VISIBILITY_CASES 是 9 条可见性探针，覆盖单域请求与跨域请求。控制点是 tools_for(spec.name)（experts.py:283），工具契约与专家定义分离在 graph/experts.py（592 行，只依赖工具定义、不依赖图）。

    三条收窄理由的原文口径就是「上下文膨胀 / 选错工具 / 越权副作用」，其中第三条最值钱——面试里要这样讲：「我本来以为收窄是为了省上下文，做完发现更关键的价值在越权写操作。」配套的做法是 MCP 侧刻意只暴露 2 个只读工具（search_kb、query_order），把 create_ticket、query_refund_policy、query_logistics 三个显式挡在协议层外面，并为这件事配了负向断言——即「断言这三个工具确实不在暴露清单里」。这是一个非常成熟的表达：权限边界的验证要用负向断言，不能只验证「我允许的那些能用」。

  • 可观测性（这条把可见性从设计变成了证据）：ExpertOutcome 里有 tools_visible 字段（expert_run.py:153），并跟着 trace 一起落盘。意思是「这个专家当时能用哪些工具」和它的回答被一起记录下来了——事后归因不用猜。这是本页「治理要可观测」那条纪律的实例。

  • 并集断言（本页最该背的不变量）：项目的自检里有「工具子集并集」这类断言，守的正是上一节说的那个静默失败——少了某个工具不会有任何运行时报错，只会有一类问题永远答不出。

  • ⚠️ 一条必须如实说的边界：专家菜单选择准确率尚未实测。VISIBILITY_CASES 的 9 条探针 + 跨域样例目前只跑到「结构上每个专家只看见 1–3 个工具」这一层，也就是隔离报告（isolation_report()）这一层；「用真模型跑这 9 条探针，看它是否选对工具」这件事还没做过。判据应当写成两条同时成立：选对率 ≥ 阈值 且 越界调用 = 0。主动说出这条未实测，比含糊地说「效果不错」可信得多——这也是本页最容易被追问的地方，提前准备好口径。

  • L4-09 结果治理：项目里对应的是 tool_calls 处理分支（graph/agent.py:604-610,625 处理未知工具与字段位置）与「校验失败不炸图，错误作为工具结果写回 state」这条纪律——后者正是「错误也是观测，要被治理后回填，而不是抛出去」的落地。写操作侧还有幂等键（_idem_key 由工具名 + 稳定序列化参数派生）与人工确认，它们与结果治理是同一层的东西：回填是模型看到的世界，治理决定这个世界的信息质量。

  • 一个可以直接讲的口径纪律：A/B 实测里 multi 臂每问 tokens 5,783.7 vs single 臂 6,243.3（40 题 × 2 臂，配对 t 检验 p=0.409，不显著）。但这个差值不能单独归因给工具可见性——它是「编排结构 + 工具可见性 + 专家 prompt」三件事合起来的净效果。报数时必须交代归因边界，这不是甩锅，这是口径。面试里主动补这一句，面试官会立刻知道你真的做过实验。

科研文献 RAG：这个项目没有工具层，也就没有工具结果治理——但它的检索结果是同一类问题，而且它有更成熟的对应做法：

  • 检索命中片段进入生成阶段之前已经被治理过了：重排后只保留 Top-k 个片段、每个片段有长度上限、并且带着引用编号。这几乎是本页「保留头尾 + 可追溯标记」的同构版本——编号就是 ref。面试里可以这样迁移：「我的 RAG 里每个片段都有编号，答案里的引用编号可以点回原文核对；Agent 的工具结果治理需要的正是同一件事——被省略的东西要能被追回，不然模型会在缺信息时编。」
  • 想补 L4-09 的话，最小做法是把一次「混合检索」的原始返回（各路的候选列表 + 分数）当成工具返回值，然后设计治理策略：只回填 Top-5 的 chunk_id + 分数 + 首 200 字，其余落盘。这样你能亲手验证一个判断——治理后的观测会不会让答案质量下降；判据是「faithfulness 不降 且 每问 token 下降」。这条实验同时覆盖 上下文工程 与 L3 的引用链路。

面试怎么问（≥3 组） ​

Q1：你系统里有多少工具？模型怎么知道该调哪个？

A（要点）：先说清数量级与形状——5 个专家 × 5 个工具（全量），每个专家只看见 1–3 个，收窄发生在提示词层面：不该看到某个工具的专家，schema 根本不出现。然后主动给出三条收窄理由，并把第三条摆在最后当重点：上下文膨胀（schema 是每轮固定开销）、选错工具（相似工具互相干扰，一次错调花掉一步预算）、越权副作用。

追问 1：为什么说第三条最值钱？

A：因为前两条是性能，第三条是安全。工具可见性本质上是一条权限边界——「不该看到某个工具的专家，在提示词层面根本看不到它的 schema」，它比在 system prompt 里写「不要调用 create_ticket」强得多，因为前者的防线是信息不存在，后者的防线是模型的服从性。我们在 MCP 侧只暴露 2 个只读工具，把另外 3 个显式挡在外面，并配了负向断言去验证它们确实不在暴露清单里。

追问 2：那跨域请求怎么办？某个专家看不见另一个域的工具。

A：这是静态可见性的固有代价，必须显式设计出口。我们的做法是给专家一个「交出控制权」的通道——专家输出里可以带一个合法的转交标记，supervisor 看到就再派一次给另一个域，派发次数受上限约束（DISPATCH_LIMIT = 2）。实测 40 题里转交 3 题（7.5%），全部 2 轮内收尾。要如实说的另一半是：「9 条可见性探针」目前只验证到「结构上每个专家只看见 1–3 个工具」这一层，用真模型跑探针看它是否选对工具这件事还没做——判据应该是「选对率 ≥ 阈值 且 越界调用 = 0」。

追问 3：如果工具数到 50 个呢？

A：静态分组就不够了，得加一道筛选：把工具描述向量化，用当前 query 检索 Top-k 个工具进候选，或者做分层菜单（先选类别再选工具）。但我会先说清 Tool Search 的风险：漏召回没有任何症状——一个本该被选中的工具因为描述和 query 不相似没进候选，表现为「模型某类问题永远答不好」。所以我会同时监控「候选召回率」，而且会补一条不变量：所有子集的并集必须等于全量工具集，否则存在永远不可达的工具。

Q2：工具返回几万行日志，你怎么处理？

A（要点）：分四类形状治，不是一刀切：日志类保留头尾各若干行、中间标注「已省略 K 行」；结构化 JSON 去掉冗余骨架只留字段名与值；长文本用一个小模型摘要；大对象只回填一个句柄，需要时分页取。无论哪种，完整结果落盘、观测里带可追回的标记。核心原则一句话：静默丢弃会让模型在缺信息时自信地编，显式截断会让它知道自己缺什么。

追问 1：为什么不能直接截断到 N 个字符？

A：因为信息密度不均匀。日志的错误行常在尾部，结构化结果的关键字段常在头部——只留头部会把最需要的那一行丢掉。而且截断之后模型不知道自己缺信息，会给一个确定性的错误答案。所以是「保留头尾 + 中间显式标注」，不是「切到 N 字符」。

追问 2：治理本身要不要留痕？

A：要。治理是「信息删减」动作，如果 trace 里看不出「回填了多少、砍掉多少、为什么砍」，事后归因时我无法区分「模型没答出来」是因为它真的不知道，还是因为我把证据砍掉了。这和记忆召回留痕是同一条纪律——能记录的东西不要猜。

追问 3：链式调用会不会让这个问题变得更严重？

A：会，而且是按轮数放大的。上下文每轮只增不减，工具结果通常是总 token 里占比最大的一项。所以治理必须在回填之前做，不能等「装不下再说」——那时候 token 费和延迟都已经付过了。另外并行调用会让峰值变成串行的几倍，所以阈值要按批次总长度算。

Q3：你怎么保证工具可见性收窄没有收过头？

A（要点）：写成不变量跑断言。有两条：第一条是并集覆盖——所有角色可见工具的并集必须等于全量工具集，少了任何一个就意味着存在一个永远不可达的工具，而且不会有任何运行时报错；第二条是反向检查——可见集里不能出现不在全量里的工具名，那是拼写错误。

追问：为什么「不可达的工具」这个问题值得单独写一个断言？

A：因为它是一个典型的静默失败。系统不会崩、日志里没有异常、测试也不会红，只是有一类问题永远答不出来，而且原因极难定位——你需要在脑子里把「用户问题 → 用户意图 → 哪个角色 → 那个角色挂了哪些工具」整条链推一遍。写一个三行的断言，成本几乎为零。

追问：你怎么证明这个断言真的在跑，而不是「写下了」？

A：这是一个我会主动提的问题。我们项目里清算过一次：v1 有 11 个 self-test 从未被 pytest 执行；v2 建了一个自检总闸，把 v1 14 条 + v2 16 条 = 30 条入口用 subprocess 真跑起来，超时从 180 秒收紧到 60 秒。判据是一条纪律：代码的防护力 = 被执行的断言数，不是写下的断言数——一个从不执行的断言，防护力与「没有断言」完全相同，但它会让你以为有防护。另外参数化测试是从清单读条目的，删掉一条只会「少跑一个用例」而不是变红，所以关键入口我额外写了点名断言。
