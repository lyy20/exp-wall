本页目录

多智能体协作模式、通信与共享状态 ​

覆盖知识点：L4-17 L4-18 ｜ 面试频率：高 ｜ 建议学时：8h

一句话说清 ​

多智能体不是「更聪明的架构」，它是一种用更多调用换取分工清晰的架构——收益不确定、代价确定。它真正解决的问题只有三个：工具太多（分工 = 收窄可见性）、提示词太长（每个专家的 system prompt 只服务一个域）、职责要审计（谁做了什么要能追溯）。如果你没有这三个问题，多智能体带来的就是「多一层路由、多一轮延迟、多一份失败归因难度」。所以这一页的核心不是拓扑图，而是一个判断标准 + 一套诚实的实验口径：怎么知道自己该不该上多智能体，以及怎么用「测不出差异」而不是「更好」来回答效果问题。

为什么必须学（面试官视角） ​

  • 这是简历上最容易被追问穿的架构。 「我做了多智能体系统」这句话会立刻引来四个问题：几个 Agent、怎么通信、为什么不用单 Agent、效果提升了多少。前三个能编，第四个编不了——因为「效果提升多少」是一个实验问题，而绝大多数人没做过实验。
  • ⭐ 本页最值钱的内容是一个「不证」的结论。你项目里做过一次 40 题 × 2 臂的配对盲测，结论是：完成率上 multi 40/40 vs single 39/40（t 检验 p=0.323、Wilcoxon p=1.0 → NSC，即无显著差异）；每问 tokens 5,783.7 vs 6,243.3（p=0.409 → NSC）；每问墙钟 20.9s vs 9.9s（2.11×，t p=1.9e-6、Holm 校正后拒绝 → REGRESSION）。这三个数一起讲，效果比「效果提升了 15%」强十倍——因为它证明你分得清「没测出差异」和「证明没有差异」，也说明你敢把不利结论写出来。
  • 它还附带一个能直接背的工程判断：两臂同对同错 39/40 ⇒ n_eff = 1。40 道题里几乎每道题两臂的表现都一样，这意味着每道题的语料是成对的，而这个任务集本身偏简单——所以任何差异都会被这个「同对同错」的底色盖住。能说出「我的评测集太简单，所以测不出差异」，是一个比任何指标都更能体现实验素养的表述。
  • L4-18 是「设计过状态」的考题。 面试官问「多个 Agent 之间怎么传数据」，答「共享一个 state」只是起点。他要听的是：什么该共享（会话事实、已完成步骤、预算计数）、什么必须隔离（每个 Agent 的完整工具结果、私有中间推理）、共享状态会不会成为竞态源、以及状态变大之后怎么治理。答出「共享什么 = 一次设计决策，而且共享越多失败归因越难」，这一题就过了。

核心内容 ​

L4-17 多智能体协作模式 ​

  • 定义：把任务分给多个各自拥有独立角色与工具集的 Agent，通过某种通信机制协同完成。与「一个 Agent 用很多工具」的本质区别是：每个 Agent 有自己的 system prompt 与可见工具集。

  • 机制（五种拓扑 + 每种的一个失效模式）：

拓扑形状适合典型失效
Supervisor（中心调度）一个调度者决定派给谁，专家做完交回域划分清晰、需要统一出口调度者选错域 → 整条链走错；调度者成为串行瓶颈
Handoff（平级转交）Agent 之间直接移交控制权流程型任务（先售后运维）转交成环；无人负责收敛
Hierarchical（多层）调度者本身还有上层调度者超大规模分工每一层都是一次额外调用；深度难以封顶
Debate / Voting（并行多意见）多个 Agent 同时给答案再聚合判断类任务（要不要批）成本 × N；聚合规则本身可能是错的
Pipeline（流水线）每个 Agent 处理一个固定阶段有明确阶段的任务（抽取→校验→写单）上游错误被下游放大；阶段间没有回退路径

四种通信形态（与拓扑正交）：

  1. 共享状态：所有 Agent 读写同一份状态（最常用，也最容易失控）。
  2. 消息传递：Agent 之间显式发消息（清晰，但消息会成为第二份真相）。
  3. 交接令牌：控制权与上下文一起移交（流程型任务常见）。
  4. 结构化产出：上游只交出一个结构化结果（推荐做法之一，因为产出的契约明确、可校验）。

  • 为什么这样设计（收益与代价必须成对说）：

    • 收益只有三个（这也是「该不该上多智能体」的判断标准）：① 工具太多 → 分工就是收窄可见性，每个专家只看见自己那 1–3 个工具；② 提示词太长 → 每个专家的 system prompt 只服务一个域，不会被其他域的规则干扰；③ 职责要审计 → 谁做了什么可以按 Agent 追溯。如果一个系统没有这三个问题中的任何一个，多智能体是纯开销。
    • 代价全是确定的：① 多一层路由 = 每次多一轮模型调用；② 多一轮延迟 = 串行调度下延迟接近叠加（项目的实测形状是 2.11×）；③ 失败归因难度上升 = 出错时要判断是「选错域」「专家做错」「交接丢了信息」还是「汇总丢了结果」，四种原因的修复动作完全不同；④ 上下文重复付费 = 每个 Agent 都带自己的 system prompt，同一个会话里这份开销要付多次。
    • 为什么「先问该不该」比「先选拓扑」重要：拓扑图很好背，但面试官真正筛的是你有没有能力不做。一个能说清「我评估过多智能体，最后因为任务结构太浅没上」的候选人，比一个上来就画五层架构的候选人可信得多。

  • 数量级与形状：

    • Agent 数量与每个 Agent 的可见工具数成反比：专家越多，每个专家越窄（项目真实形状：5 个专家 × 全量 5 个工具，每个专家只看见 1–3 个）。
    • 调度轮数分布是判断「多智能体是否必要」的第一个指标：如果绝大多数请求一轮就收尾（项目实测均值 1.075：37 题 1 轮、3 题 2 轮），说明任务结构是浅的，多智能体的分工收益很难体现。
    • 跨域请求占比是第二个指标：项目实测转交 3/40 = 7.5%（判据是 < 10%）。只有当跨域请求占比显著时，分工才有用武之地。

  • 常见误区：

    • 「多智能体 = 更强的 Agent」：它换的是分工清晰度，不是能力。没有证据时不要声称更强。
    • 每个 Agent 都给它全量工具：那就退化成了「一个 Agent 加一层路由」，多智能体唯一的硬收益（收窄可见性）被丢掉了。
    • 拓扑选得比问题复杂：任务只有两个域，却上三层层级调度。
    • 没有统一出口：多个 Agent 各自直接回用户，导致回答风格、格式、引用规范不一致，而且无从收敛。
    • 并行/多意见拓扑不设成本上限：成本 × N 且 N 是模型决定的。
    • 用「感觉更专业」当评估依据：这就是本页要重点解决的问题——见下一条。

L4-18 多智能体通信与共享状态 ​

  • 定义：多智能体之间传递信息与维持一致性的机制。核心问题是哪些信息是共享的、哪些是隔离的、以及共享之后谁来负责收敛。

  • 机制（三张表：共享 / 隔离 / 防环）：

    表一：什么该共享，什么必须隔离

类别共享还是隔离为什么
会话级事实（用户 id、商品、订单号、已确认的约束）共享每个专家都要用；不共享就会重复追问用户
已完成步骤与中间结论共享（结构化摘要形式）避免重复劳动；但要摘要后共享，不是原样搬
预算计数（步数、分派次数、重试次数）共享且单调递增它是闸的依据，必须是单一真相，不能每个 Agent 各自计数
每个 Agent 的完整工具结果隔离（或摘要后共享）原样搬会把上下文迅速撑爆，且引入无关噪声
私有推理 / 思考过程隔离既无必要，也扩大暴露面与 token
统一出口与最终回答由调度者独占否则无人负责风格与收敛

表二：共享状态的四个设计点

设计点要决定的事做错的后果
单一真相预算是共享的计数器，不是各 Agent 自己数的每个 Agent 都觉得自己还有额度 → 总步数失控
写入权限谁能写状态里的哪些字段两个 Agent 互相覆盖对方的结论
冲突处理两个专家给出矛盾结论时怎么办悄悄取最后一个（最常见也最糟），或明确交给调度者裁决
状态大小治理共享状态里放摘要还是原文共享状态本身就是上下文瓶颈

表三：防环的三道闸

闸作用缺了会怎样
分派次数上限封顶「调度者 → 专家」的次数A 派给 B、B 交回 A，无限循环
回环边各自的闸每一条回到起点的边都有自己的检查只在一侧检查，另一侧就是能绕过去的循环入口
单调递增计数器计数只能在收到结果后加一计数被重置或被各自维护 → 上限失效

  • 为什么这样设计：

    • 为什么预算必须是共享的单一真相：因为闸的依据只能有一个来源。如果每个 Agent 各自数自己的步数、各自判断「我还没超」，那么系统的总成本上限是「每个 Agent 的上限之和」——也就是上限失效。项目里的做法是把分派次数做成单调递增计数器，到上限强制收敛（source="quota"）。
    • 为什么「每一个回环边都要有自己的闸」：这是项目 ADR 里的原话。原因是检查的位置决定它能不能被绕过——如果只在「进入循环」的那条边上检查，那么「从循环里绕回来」的那条边就是绕过闸的入口。项目里的实例是两条回环边曾经错连（memory → __end__ 与 reflect → __end__），这正说明这类错误是结构性的，不是靠仔细就能避免的。
    • 为什么中间结论要摘要后共享，而不是原样共享：共享状态会被每个下游 Agent 读进自己的上下文，所以共享状态的总长度会被乘以参与 Agent 的数量。原样共享等于把一份工具结果复制 N 遍——这是多智能体系统上下文爆炸最常见的来源。
    • 为什么要有「统一出口」：收敛是一个责任，不是一个能力。多个 Agent 各自回用户，就没有人对「最终回答是否一致、是否合规、是否引用了正确的来源」负责。收敛点必须是唯一的。
    • 为什么冲突要显式处理：两个专家给出矛盾结论（一个说可以退款、一个说不行）在业务系统里是很常见的。默认行为（后写覆盖前写）会让结果依赖执行顺序——这类 bug 极难复现。正确做法是让调度者看到两个结论并显式裁决，或者定义清晰的优先级。

  • 数量级与形状：

    • 共享状态里应当只放摘要与结论，单条观测的长度受控；每个 Agent 的完整结果留在自己的执行上下文里。
    • 调度轮数与「跨域请求占比」是两个必须记录的指标，它们决定了分工是否值得。
    • 多智能体的成本形状是「轮数 × 单轮成本」：轮数增加是串行叠加的墙钟，而 tokens 未必同步增加（因为每个 Agent 的 prompt 更短，可能相互抵消）。这两个指标必须分开看——项目的实测正是这个形状：tokens 无显著差异（p=0.409），墙钟显著变差（2.11×，p=1.9e-6）。

  • 常见误区：

    • 共享状态当成「全局变量随便写」：没有写入权限划分、没有冲突处理。
    • 每个 Agent 各自计数：上限失效。
    • 原样共享工具结果：上下文 × N。
    • 只在一侧设闸：可绕过的循环入口。
    • 用「两边都一样」来推断「多智能体没用」：没测出差异 ≠ 证明没有差异。必须报功效分析（下面有）。
    • 拿单次 demo 的观感当结论：小样本、无配对、无盲测的对比不构成证据。

和你自己的项目对上号 ​

YYHelp v2（LangGraph 电商客服 Agent）：这一页是全层素材最硬的一页——你有一个完整的、有统计口径的多智能体实验，而且结论不是「更好」。

  • L4-17 拓扑与判断标准（真实形状）：项目的形态是手搓 Supervisor（中心调度）——supervisor 节点看请求后决定派给哪个专家或直接回答，专家执行完交回，最终回答由 supervisor 独占出口。它满足本页那条判断标准里的两条：① 工具太多（5 个工具要按域分配，每个专家只看见 1–3 个）；③ 职责要审计（ExpertOutcome 里有 tools_visible，跟着 trace 落盘，事后能回答「这个专家当时能用哪些工具」）。第二条（提示词太长）也部分成立——每个专家的 system prompt 只服务一个域。
    • 一个可以直接引用的架构决策：手搓 supervisor，不引入 langgraph_supervisor（supervisor.py:750）。三条理由：① 现成的 create_react_agent 是薄封装，套上去省不了多少；② 重装一套等于放弃已验收的可靠性资产（自检体系、幂等、可见性断言都得重来）；③ 多一个依赖 = 多一个版本风险面（环境事实：langgraph_supervisor 并未安装）。「不引入一个依赖」也是一个可辩护的决策，而且理由比『我自己写能学到东西』强得多。
    • 调度上限 DISPATCH_LIMIT = 2（supervisor.py:199），四条理由：① 1 是下限；② 2 够用（跨域例子「退款 + 改址」正好两个专家；9 条可见性探针全是单域；实测 40 题转交仅 3 题）；③ 2 封住无限循环（分派次数是单调递增计数器 budget.steps，到限强制 finalize，source="quota"）；④ 不选 3：每多一轮 = 多一次专家完整 ReAct 回合，专家 total_tokens 量级在千级，没有证据表明 3 轮更好之前选小值。
    • 串行而非并行：理由是形状不同——「串行是次数问题，上限可以直接封顶；并行是扇出问题，封顶需要『深度 × 宽度』两个预算，而且失败归因复杂化」。这条判断和本页 L4-18 的「共享状态与收敛」是同一套思路。
  • ⭐ L4-17 的实测结论（本页的核心素材，口径要一字不差）：Gate-1，40 题 × 2 臂 = 80 条记录（2026-10-02，模型 deepseek-v4-pro），配对盲测：
    • 完成率：multi 40/40 vs single 39/40；均值差 +0.025，CI [−0.024, +0.074]；t 检验 p=0.323、Wilcoxon p=1.0 → NSC（无显著差异）。
    • 每问 tokens：multi 5,783.7 vs single 6,243.3（差 +459.6，比值 0.93×）；t p=0.409 → NSC。
    • 每问墙钟：multi 20.9s vs single 9.9s（差 −10.95 s，CI [−14.79, −7.12]，2.11×）；t p=1.9e-6、Wilcoxon p=8.7e-7、效应量 dz −0.89、Holm 校正后拒绝 → REGRESSION。
    • 为什么不证（这条最关键）：两臂同对同错 39/40 ⇒ n_eff = 1。也就是说 40 道题里几乎每道题两臂表现一样，任务集本身偏简单，任何差异都会被这个「同对同错」的底色盖住。已经算出的功效阈值是：+5pp 需 76 题 / +10pp 需 17 题 / +20pp 数学无解（ψ=0.025、δ=0.025）。
    • 三态退出码：IMPROVEMENT 0 / REGRESSION 1 / NSC 0 / INCOMPARABLE 2；门槛 min_delta 为完成率 0.05、tokens 200.0、墙钟 2.0，alpha 0.05。注意 NSC 与 IMPROVEMENT 退出码都是 0——这是刻意的：「没测出差异」不是失败，硬说成成功才是。
    • 配套事实：Day1 live 全量 80/80 出答案、0 异常、481,078 token、1230.5 s；eval set 40 题（single_hop 12 / synonym 8 / unanswerable 8 / multi_hop 6 / exact_term 6）；KB 163 chunk / 9 doc；成本对比 multi 231,348 tokens vs single 249,730 tokens；裁判判 1 的比例 79/80。
    • 面试里怎么讲：先说结论是「不证」，再说为什么，最后说回归。 顺序很重要——如果你先说墙钟回归，听起来像在承认失败；如果你先说「40 题里两臂同对同错 39/40，n_eff=1，我的评测集测不出差异」，再说「但我确实测到一个显著的墙钟回归，2.11×」，那么整段话的落点是**「我知道我的实验能测出什么、不能测出什么」**。这比任何「提升 X%」都强。
  • L4-18 通信与共享状态（对应到真实字段）：
    • 共享：单一状态对象贯穿图（LangGraph 的 state 机制），预算相关字段是单一真相；budget.steps 是单调递增的分派计数器（到限强制 finalize source="quota"）。
    • 隔离：每个专家的执行上下文与完整工具结果不原样搬回，只回传结构化结果（ExpertOutcome 及其 tools_visible 等字段）。
    • 统一出口：supervisor 独占最终回答。
    • 四道闸里的一道特别值得背：「能被事前告知的约束，不要只做事后拦截」——supervisor_system_prompt(*, used=0, limit=2)（supervisor_core.py:205）会把当前已用次数与上限写进调度者的提示词，让它在决策时就考虑额度，而不是等超了再强行终止。这是「闸」的正确姿势：闸是硬约束（程序里的计数器），但能让模型提前知道约束，就让它提前知道。
  • 与记忆层的呼应（同一套「留痕」纪律）：RECALL_POLICY = "state_only"（longterm.py:810）意味着召回结果进 state 但不进 prompt，理由是可观测 / 可回滚 / 可对比。这在多智能体场景下价值更高——多个 Agent 共享同一份状态时，「写进去但没有被使用」和「用上了」必须可区分，否则你无法判断一个改动是哪个 Agent 起的作用。

科研文献 RAG：这个项目是单链路（检索 → 重排 → 生成，无多 Agent），但它在实验口径上有两处可以直接迁移到多智能体评测的成熟做法：

  • A/B 对照与配对设计：RAG 项目做过「策略 A vs 策略 B」的对照实验，用的是同一批查询、同一套指标、配对比较。这正是多智能体评测该有的设计——不配对、不盲测、不同批次的对比不构成证据。
  • 「没测出差异」要如实报：RAG 项目在处理「改了但指标没动」的情况时，口径是「在现有样本量下未观察到显著差异」，而不是「改动无效」。这个口径迁移到多智能体上就是本页的核心要求。
  • 可以补的实验：把 multi_hop 那 6 道题单独扩样（例如扩到 30 道跨域题），因为项目的功效分析已经告诉你「+10pp 需要 17 题」——在这个子集上做对照，是唯一有可能测出多智能体收益的地方。这条建议本身就是「用功效分析指导实验设计」的落地。

面试怎么问（≥3 组） ​

Q1：你做多智能体系统，效果比单 Agent 好吗？

A（要点）：我做过一次 40 题 × 2 臂的配对盲测，结论是「不证」，不是「更好」，而且我还测到一个显著的回归。完成率 multi 40/40 vs single 39/40（t p=0.323、Wilcoxon p=1.0 → 无显著差异）；每问 tokens 5,783.7 vs 6,243.3（p=0.409 → 无显著差异）；每问墙钟 20.9s vs 9.9s，2.11×，t p=1.9e-6，Holm 校正后仍拒绝 → 回归。

追问 1：「不证」是什么意思？你是说你不知道哪个更好？

A：是「没测出差异」，不是「证明没有差异」——这两件事完全不同。而且我知道为什么测不出来：两臂同对同错 39/40，n_eff = 1。40 道题里几乎每道两臂表现一样，说明任务集本身偏简单，任何差异都被这个底色盖住了。我还算了功效：在现有方差下，+5pp 需要 76 题、+10pp 需要 17 题、+20pp 数学无解。所以「测不出差异」是样本量与任务难度的结论，不是「多智能体没用」的结论。

追问 2：那你为什么还保留多智能体？

A：因为它的收益不在「答案质量」上，在我列的三条：工具太多（5 个工具按域分给 5 个专家，每个只看见 1–3 个）、提示词太长（每个专家只服务一个域）、职责要审计（ExpertOutcome 带 tools_visible 落进 trace，事后能回答「这个专家当时能用哪些工具」）。这三条是结构性收益，不需要统计显著性——而它换来的代价确实是真的：延迟 2.11×。

追问 3：那这个代价你接受吗？

A：接受，但要说清它在什么条件下可接受。这个系统的任务是客服问答，用户对秒级延迟不敏感，20 秒级可以忍；如果是交互式场景（比如代码补全或实时对话），2.11× 就不可接受了。而且我把代价封住了：DISPATCH_LIMIT = 2（串行 + 分派上限，依据是实测转交仅 3/40），不会因为多智能体结构就让最坏情况失控。代价可接受的前提是它被上限封住了。

Q2：多个 Agent 之间怎么传数据？

A（要点）：先分清什么该共享、什么必须隔离。共享的是会话级事实（用户、订单、已确认的约束）、已完成步骤的结构化摘要、以及预算计数——预算必须是共享的单一真相且单调递增，因为它是闸的依据。隔离的是每个 Agent 的完整工具结果和私有推理过程，只把摘要写回共享状态，否则共享状态会被下游 Agent 各读一遍，上下文乘以参与 Agent 的数量。最后，最终回答由调度者独占出口——收敛是一个责任，不是多个 Agent 各自具备的能力。

追问 1：为什么预算必须是共享的？

A：因为闸的依据只能有一个来源。如果每个 Agent 各自数自己的步数、各自判断「我还没超」，那系统的总成本上限就是「每个 Agent 的上限之和」——上限等于失效。我项目里的做法是把分派次数做成单调递增计数器（budget.steps），到上限强制收敛，并标注 source="quota"。

追问 2：两个专家给出矛盾结论怎么办？

A：必须显式处理。默认行为是「后写覆盖前写」，那会让结果依赖执行顺序——这类 bug 极难复现。正确做法是让调度者看到两个结论并显式裁决，或者定义清晰优先级。冲突处理是共享状态四个设计点之一（另外三个是单一真相、写入权限、状态大小治理）。

追问 3：循环怎么防？

A：三道闸，而且有个坑值得单独说：「每一个回环边都要有自己的闸。只在一侧检查，另一侧就是一个能绕过去的循环入口。」 这是我们的 ADR 原话，项目里 memory → __end__ 和 reflect → __end__ 两条回环边曾经错连。所以检查的位置决定它会不会被绕过——这类错误是结构性的，不是靠仔细就能避免的。配套还有一条：「能被事前告知的约束，不要只做事后拦截」——我们会把当前已用次数与上限写进调度者的提示词，让它在决策时就考虑额度，而不是等超了再强行终止。

Q3：你怎么知道多智能体在你的任务上是值得的？

A（要点）：三个可量化的信号 + 一条判断标准。信号一，调度轮数分布：均值 1.075（37 题 1 轮、3 题 2 轮）说明任务结构是浅的——多智能体的分工收益很难体现。信号二，跨域请求占比：实测转交 3/40 = 7.5%，判据是 < 10%；占比高才说明分工有用武之地。信号三，成本形状要拆开看：tokens 无显著差异（p=0.409），但墙钟显著变差（2.11×）——这两个指标必须分开报。判断标准则是那三条：工具太多 / 提示词太长 / 需要按 Agent 审计，一个都不占就是纯开销。

追问：如果占比很低，你会怎么做？

A：两条可选。要么去掉多智能体（既然跨域只有 7.5%，路由这一层的收益有限），要么保持结构但缩掉调度开销——后者更像我会走的路，因为结构收益（工具可见性、审计）是独立的，与跨域占比无关。但我会先说清哪一条收益是真的：质量收益未证、延迟代价已证、结构收益不需要统计。这三句话分开说，比一句「多智能体效果更好」诚实得多。

追问：那要测出质量收益需要什么？

A：功效分析已经给了答案：+10pp 需要 17 题。所以做法很清楚——把跨域/多跳那一类题单独扩样（项目里 multi_hop 只有 6 道），扩到 20–30 题，然后在这个子集上做对照。因为差异只可能出现在需要多域协同的题上，把整个 40 题的均值拿来做检验，会被大量单域题稀释掉。用功效分析指导实验设计，而不是加更多题重复同一个结论——这是我做完那次实验最大的收获。
