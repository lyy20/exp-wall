Agent 是什么：边界、谱系与运行循环 ​

覆盖知识点：L4-01 L4-02 L4-03 ｜ 面试频率：高 ｜ 建议学时：9h

一句话说清 ​

Agent 与 Workflow 的分界线只有一条：下一步做什么，是模型在运行时决定的，还是你在写代码时决定的。前者是 Agent，后者是 Workflow——哪怕 Workflow 里每一步都在调大模型。Agent 不是一个新技术，它是「感知—决策—行动」循环的第三代实现：符号 Agent 把决策写成规则，强化学习 Agent 把决策学成策略，LLM Agent 用语言模型的先验直接当决策器。不管哪一代，剥掉框架之后剩下的都是同一个东西：LLM + 工具 + 记忆 + 规划 四要素，跑在 Thought → Action → Observation 的循环上。

为什么必须学（面试官视角） ​

「什么是 Agent」是 AI Agent 岗位的第一问，也是淘汰率最高的一问，因为几乎所有人都能背出一个定义，而几乎没人能把边界说清。面试官在这一问上实际在测三件事：

  1. 你有没有真实的架构判断力。 如果你说「用了 LLM 多轮调用就是 Agent」，面试官会立刻追问「那你那个客服机器人，意图分类 → 查知识库 → 生成回答，是不是 Agent？」——这一段流程其实是你在代码里写死的。答不上来，后面所有项目描述的可信度一起归零。
  2. 你会不会为了用 Agent 而用 Agent。 把一个能用 Workflow 稳定解决的任务包装成 Agent，是应届简历里最常见的「技术选型错误」。面试官要听的不是「Agent 更先进」，而是「我知道 Agent 引入了不确定性，我为什么还愿意付这个代价」。
  3. 你能不能把框架归约到一个循环。 你写了 LangGraph、说了 StateGraph、画了一堆节点，面试官会问：「这些东西抽象掉之后，本质是什么？」。答出「一个带状态的四要素循环 + 终止条件」，说明你在用框架；答不出，说明框架在用你。

L4-02 的谱系在面试里频率是「中」，但它的价值不在背诵年份，而在技术判断力：能讲清「从符号主义到 RL 到 LLM，什么变了、什么没变」的人，在被问「你觉得 Agent 的瓶颈在哪」时不会只能答「幻觉」。L4-03 则是整层的地基——后面 30 个知识点（工具、记忆、规划、多智能体、MCP、LangGraph）全是它的展开。

核心内容 ​

L4-01 什么是 Agent（与 Workflow 的边界） ​

  • 定义：Agent 是一个由模型自主决定下一步动作的系统：它拿到当前状态，选择调用哪个工具（或直接给出答案），观察结果，再决定下一步，直到自己判断任务完成或撞上预算上限。

  • 机制（判断标准）：写代码的时候问自己一个问题——「如果我现在要写一个单元测试，断言第 3 步一定是「查订单」，这个断言写得出来吗？」 写得出来 = Workflow；写不出来（因为第 3 步取决于第 1、2 步拿到了什么）= Agent。

    这个判据可以从三个方向交叉验证：

维度WorkflowAgent
控制流在代码里（if / 边 / 状态机）在模型的输出里（结构化决策字段）
步骤数编译期确定运行期确定，有上限
成本可估性高（路径有限，可逐条算）低（要设预算闸才可估）
失败形态分支没覆盖漂移、绕圈、选错工具
调试方式打断点看分支看 trace 里的决策序列
适合的任务步骤可预知、有合规要求步骤必须看上一步结果才能定

  • 为什么这样设计（关键）：两者的取舍是**「确定性 ↔ 适应能力」**。Workflow 把决策固化下来，换来可测试、可估算、可审计；Agent 把决策交给模型，换来「遇到没见过的情况也能继续」。所以选型的正确问法不是「哪个更强」，而是「这个任务里，我需不需要在运行时应对计划外的情况」。

    一个常见的反例：LLM 调用次数多 ≠ Agent。RAG 问答链路是「查询改写 → 混合检索 → 重排 → 生成」，四步全在调模型，但它是彻头彻尾的 Workflow——因为每一步都是你写死的，模型只是每一步的执行器，不是决策器。反过来，一个只有两次模型调用的系统只要「调不调工具、调哪个」由模型定，它就是 Agent。

  • 数量级与形状：Agent 的成本形状是**「轮数 × 每轮上下文」，所以上下文随轮数近似线性甚至平方级增长**（每一轮都要把之前全部历史再发一次）。这意味着 3 轮的 Agent 往往比 1 轮的 Workflow 贵 3 倍以上，而不只是多花一点。

  • 常见误区：

    • 把「多轮调用」当成 Agent 的定义（多轮是形态，自主决策才是定义）。
    • 把「用了某个 Agent 框架」当成 Agent 的定义（框架只提供循环的脚手架，不提供自主性）。
    • 认为 Agent 是 Workflow 的升级版，所以新项目一律上 Agent。
    • 反过来把「有工具调用」当成 Agent 的门槛——工具调用是能力，但若「第几步调哪个工具」写死在代码里，它仍然只是 Workflow。

  • 代码（判据的程序化表达是伪代码）：真要说「我的系统是不是 Agent」，最小判据可以直接写成一段断言式的伪代码：

python
# 伪代码：用「决策是否可预知」来判定，而不是用「用没用 LLM」来判定
def is_agent(graph_spec) -> bool:
    """graph_spec 是你系统的拓扑描述。"""
    # 1) 有没有至少一条边的目标不是常量，而是由模型输出决定的？
    if not any(edge.target_from == "model_decision" for edge in graph_spec.edges):
        return False          # 全部目标写死 → Workflow
    # 2) 这条模型驱动的边，会不会构成回环（即模型可以连续做多次决策）？
    if not graph_spec.has_cycle_through("model_decision"):
        return False          # 模型只决定一次 → 更像「带路由的 Workflow」
    # 3) 循环有没有上限？（没有上限就不是 Agent，是定时炸弹）
    assert graph_spec.has_termination_guard(), "无上限循环不可交付"
    return True

L4-02 Agent 发展史与谱系 ​

  • 定义：Agent 概念经历了三代实现范式——符号 Agent（规则驱动）→ 强化学习 Agent（策略学习）→ LLM Agent（语言先验驱动）。三代共享同一个循环结构，变的是「决策器从哪来」。

  • 机制（三代各自的决策器）：

代际年代主线决策器是什么知识从哪来典型失败
符号 Agent1950s–1980s手写规则 / 逻辑推理引擎人工编码的符号知识库知识获取瓶颈：规则写不全、写不快
RL Agent1980s–2010s学出来的策略 与环境的交互试错样本效率极低、奖励设计难、难迁移
LLM Agent2022 至今语言模型本身预训练语料里的世界知识 + 少量示例幻觉、漂移、成本、不可形式化验证

  • 关键节点（面试提到就够，不用背年份到月份）：

    • 符号主义起点：Newell 与 Simon 的「物理符号系统假设」把智能定义为符号操作；STRIPS 一类的规划器把「目标 → 动作序列」做成了可搜索问题。
    • BDI 模型（Belief-Desire-Intention，1990 年代）：把 Agent 的内部状态显式拆成「我相信什么 / 我想要什么 / 我打算做什么」。这一条在面试里特别有用——今天 LLM Agent 的 state 字段（memories_recalled、plan、next_action）本质上是 BDI 的工程化版本。
    • RL 范式：MDP（状态、动作、转移、奖励）把 Agent 变成一个可优化的数学对象，Q-Learning / Policy Gradient 给出求解方法。
    • LLM Agent 的转折点：ReAct 把「推理」与「行动」交替放进同一个文本流，让语言模型直接充当策略——不再需要为每个任务训练一个策略网络。这是「为什么 LLM Agent 能一夜之间铺开」的真正原因。
    • 之后的工程化路线：工具调用标准化（Function Calling）、记忆与规划模块化、协议层（MCP 一类的工具接入协议）、多智能体编排。

  • 为什么这样设计（这条决定你能不能把谱系讲成判断力）：三代之间的变化不是「越来越聪明」，而是**「知识从哪里来」这件事换了答案**。符号 Agent 靠人写、RL Agent 靠试错、LLM Agent 靠预训练。而三代之间没变的是两件事：① 都是「感知—决策—行动」的循环；② 都需要一个「动作抽象层」（符号 Agent 是动作原语，RL 是动作空间，LLM 是工具 schema）。能同时说出「变了什么」和「没变什么」，才是这段历史在面试里的用法。

    顺带一个高价值判断：符号 Agent 的「知识获取瓶颈」，LLM Agent 用预训练绕过了，但没消除——它变成了「幻觉」和「工具选错」。认识到这一点，你在被问「Agent 最大的问题是什么」时就不会只说「模型不够强」。

  • 常见误区：

    • 把 Agent 当成 2023 年才出现的新概念（概念比 LLM 老至少半个世纪）。
    • 认为 LLM Agent 是「抛弃了前两代」——实际上它把符号 Agent 的结构（显式状态、显式循环）和 RL 的目标（在反馈中改进）都借回来了，只是把决策器换掉了。
    • 把「ReAct 论文」当成 Agent 的起点。

  • 代码：这段没有必须写的代码，但值得给一个「BDI ↔ 现代 state 字段」的对照，因为它让历史直接变成你项目里的东西：

python
# BDI 的三个成分 ↔ 一个 LLM Agent 的 state 字段（对照表，不是要运行的代码）
STATE_MAP = {
    "belief":  ["memories_recalled", "retrieved_hits", "tool_observations"],  # 我相信什么
    "desire":  ["user_goal", "intent", "expected_exit"],                       # 我想要什么
    "intent":  ["plan", "next_action", "dispatch_quota"],                      # 我打算做什么
}

L4-03 Agent 四要素与运行循环 ​

  • 定义：一切 LLM Agent 都可以归约成四个要素——LLM（决策器）+ 工具（作用于外部世界）+ 记忆（跨步骤与跨会话保存信息）+ 规划（把目标拆成有序动作），运行在 Thought → Action → Observation 的循环上。

  • 机制（一次循环的六步）：

    1. 装配上下文：system 规则 + 用户输入 + 历史消息 + 记忆召回 + 可用工具 schema。
    2. 模型决策：模型输出一段思考（Thought），以及一个结构化意图（Action）——调哪个工具、参数是什么，或者直接给出最终答案。注意：模型不执行任何东西，它只输出意图（见 工具调用生命周期）。
    3. 程序校验：工具名是否在允许清单里、参数是否过 schema 校验、这次调用是否越权或有副作用。
    4. 执行工具：真正跑起来的是你的代码。执行结果必须被规范成一段「模型能读、且不会炸掉上下文」的文本（见 工具结果治理）。
    5. 回填 Observation：把结果作为一条消息追加进历史，回到第 1 步。
    6. 终止判定：模型给出不带工具调用的答案、或撞上预算闸、或检测到绕圈 → 结束。

  • 为什么这样设计：

    • 为什么上下文必须重装而不是「记住」：LLM 是无状态的，所谓「记忆」只是你每次把历史重新拼进去。所以 Agent 的「记忆」问题本质是上下文预算问题——这解释了为什么 L4-12~L4-14 和 L4-09 是同一件事的三个侧面。
    • 为什么决策与执行必须分开：把执行权留在程序里，你才可能做参数校验、权限收窄、幂等、人工确认。一旦「模型直接执行」，这四件事全部无家可归。
    • 为什么一定要有显式终止条件：循环的默认行为是继续循环。没有闸门的 Agent 不是「能一直工作」，是「一定会一直烧钱」——详见 终止条件与预算控制。

  • 数量级与形状：

    • 一次循环 = 1 次模型调用 + N 次工具调用（N 在本层话题里可以是 0，也可以因为并行调用变成 3–5）。
    • 上下文每轮只增不减（除非你主动做压缩），所以第 轮的输入 token 约等于 ，累计成本按轮数近似平方增长。
    • 循环上限通常取 3–8 步量级，不是「越大越好」。步数上限越大，最坏情况成本越高，而收益集中在最前面几步。

  • 常见误区：

    • 只列四要素，不写循环：面试官问「四要素是什么」，很多人能答；接着问「它们在一次请求里什么时候出现」，就答不上来。四要素是静态结构，循环才是动态行为。
    • 把「规划」当成必须的独立模块：规划可以是显式的 plan 节点，也可以内嵌在 Thought 里。隐性规划不是「没有规划」。
    • 把「记忆」等同于向量库：短期会话记忆（滑动窗口、压缩摘要）和长期记忆（抽取、存储、召回）是两套机制，混着讲会被追问到崩。
    • 认为观测就是工具返回值：观测是经过治理的工具返回值。把工具原样输出（几万行日志）直接塞回上下文，是 Agent 崩溃的第一大工程原因。

  • 代码（最小循环骨架，可直接对照你项目的图）：

python
# 伪代码：ReAct 循环骨架。真实实现见 02-handwritten-react。
def run_agent(question: str, tools: dict, max_steps: int = 6) -> str:
    messages = [{"role": "system", "content": SYSTEM},
                {"role": "user", "content": question}]
    seen: set[tuple[str, str]] = set()          # 绕圈检测：相同 (工具, 参数)

    for step in range(max_steps):               # 闸门 1：步数
        reply = llm(messages, tools=[t.schema for t in tools.values()])

        if not reply.tool_calls:               # 终止条件：不给工具调用 = 最终答案
            return reply.content or ""         # 注意 content 可能是空串

        for call in reply.tool_calls:          # 可能是多个（并行调用，见 03 页）
            key = (call.name, stable_json(call.args))
            if key in seen:                    # 闸门 2：重复动作
                return f"loop_detected: {call.name}"
            seen.add(key)

            try:                               # 校验 + 执行；失败不炸图
                args = tools[call.name].validate(call.args)
                obs = tools[call.name].invoke(args)
            except Exception as exc:
                obs = f"ERROR: {type(exc).__name__}: {exc}"   # 错误也是一种观测

            messages.append({"role": "tool", "content": truncate(obs)})

    return "budget_exhausted:step_budget"

和你自己的项目对上号 ​

YYHelp v2（LangGraph 电商客服 Agent）：这一页的三个知识点在这里都能直接落地成话术。

  • L4-01 边界：这个项目做了一次刻意设计的 A/B——single 臂是「一个通用 Agent 拿全量 5 个工具」（v1 的做法），multi 臂是「triage → plan → supervisor → 专家 → reflect」的显式编排，5 个专家每人只看见 1–3 个工具。这个对照本身就是「Workflow 化的编排 + Agent 化的决策」的混合体：骨架是 Workflow（边是写死的），每次派给谁、调哪个工具是 Agent（模型决定）。被问「你这到底是 Agent 还是 Workflow」时，标准答案是「混合，而且我能指出哪一层是哪种」——这比二选一的回答高一个档次。

  • L4-02 谱系：项目里有一个可以直接当例子的设计——自己手搓 supervisor，不引入 langgraph_supervisor 预置组件（三条理由：预置组件本质是薄封装；重装一套等于放弃已经验收过的可靠性资产；多一个依赖多一个版本风险面）。这条判断的依据就是「四要素循环是可以自己实现的」，它把三代 Agent 的「循环结构没变、决策器换了」变成了一个真实的工程决策。

  • L4-03 四要素：supervisor（规划/决策）、5 个专家（工具执行）、memory 节点（长期记忆召回）、reflect 节点（反思）——四个要素在这个项目里都有独立节点，可以逐个指认。state 里的 memories_recalled、plan、next_action 三个字段恰好对应 BDI 的 belief / desire / intent。

  • ⚠️ 一个把「装配错误」钉在 L4 的实战素材（面试讲「你踩过什么坑」的首选）：v1 用 add_conditional_edges(source, path_fn, path_map) 建图时，第三参是「path_fn 的返回值 → 目标节点」的映射表。第一版让 route_by_exit 返回节点名（"retrieve"），却把 EXIT_TO_NODE 当 map 传了进去——两边各自都对，接起来就查不到。现象是 KeyError: 'agent_memory'，报错形态 During task with name 'triage' and id 'a06e0b0c-...'，代码位置 code/yyhelp/graph/build.py:149-176。

    这一条的价值在于它的性质：它能 import、能编译，纯函数单测天然测不出它——route_by_exit 作为纯函数完全正确，错的是它和 path_map 的契约，而契约只有 LangGraph 真正装配并运行图、在 triage 任务实际调度时去查 map 才会被检查。所以判据是：装配错误必须靠运行图来验，不能靠读代码；修法是「打印图的 edges 做断言」，不是「再读一遍代码」。这是本页对「Agent 运行循环」理解深度的最好证明——你能说出循环里哪一步由框架持有契约，说明你真的跑过它。反思/重试侧的同类教训见 规划与反思。

科研文献 RAG：这个项目是反面对照，而且这个「反面」本身就是加分项。

  • 它的链路是「查询改写 → 混合检索 → 重排 → 生成 → 引用校验 → 拒答」，步骤在编译期就写全了，所以它是 Workflow 而不是 Agent。用本页的判据回答「你为什么不用 Agent」：能提前把步骤写全的任务不该交给模型选下一步——那只会引入漂移和成本方差，而不新增任何能力。
  • 但它的拒答机制是一个 Agent 式的设计：模型自报 insufficient 是模型侧信号（花钱、不完全可靠），引用编号越界检查是程序侧校验（确定、免费）。这套「程序负责可判定的判断」的分工，正是 Agent 循环里第 3 步（程序校验）的独立版本。

面试怎么问（≥3 组） ​

Q1：你觉得什么样的系统算 Agent？

A（要点）：判据只有一条——下一步由谁决定。如果步骤在写代码时就固定了，哪怕每步都调大模型，那也是 Workflow；如果「调哪个工具、要不要继续」是模型在运行期根据当前状态决定的，那才是 Agent。我们项目是混合的：图的骨架（有哪些节点、哪些边）是写死的，但「这一次派给哪个专家、用哪个工具」是模型决定的——编排是 Workflow，决策是 Agent。

追问 1：那你说说 Workflow 和 Agent 各自的代价。

A：Workflow 换来确定性——可测试、可估算、可审计、可合规；代价是遇到没覆盖的情况就断。Agent 换来适应能力；代价是成本方差大、路径不可枚举、失败形态变成「漂移 / 绕圈 / 选错工具」。所以选型的问法不是「哪个强」，是「这个任务里我需不需要在运行期应对计划外情况」。

追问 2：那你为什么还选 Agent？举例说一个只有 Agent 才能覆盖的场景。

A：跨域请求。用户一句话里同时有「退款」和「改收货地址」，这两件事分别属于不同专家的工具集。Workflow 要覆盖它，就得为「退款+改址」「退款+改址+查物流」……枚举所有组合，组合数是乘积级；而 Agent 只需要在第一步看到意图后决定先派谁。我们实测 40 题里转交 3 题（7.5%），就是这一类。

追问 3：这 7.5% 值不值得让整体成本变这样？

A：这就是我要主动交代的地方。Gate-1 的 40 题 × 2 臂配对实测里，multi 臂的完成率 40/40 vs single 臂 39/40（t 检验 p=0.323，Wilcoxon p=1.0，不显著），每问 tokens 5,783.7 vs 6,243.3（p=0.409，不显著），但每问墙钟 20.9s vs 9.9s（2.11×，t p=1.9e-6，Holm 拒绝 → 判定为退化）。所以我的结论不是「多智能体更好」，而是**「在 40 题的样本上测不出完成率差异，但付出了 2.11 倍延迟」**——这个结构目前的净收益没有成立。详见 多智能体。

Q2：四要素是什么？它们在一次请求里分别在哪里出现？

A（要点）：LLM、工具、记忆、规划。关键是能说出它们在循环的哪一步出现：规划在第 1 步之前产出「剩余步骤」；记忆在装配上下文时被召回、在观测回填时被写入；工具在第 4 步被执行；LLM 主持第 2 步的决策。只背四个名词答不出这一问。

追问：你说的「记忆」是向量库吗？

A：不是，记忆至少分两层。短期是会话内的历史与压缩摘要，解决的是「上下文窗口放不下」；长期是跨会话抽取出来的事实与偏好，解决的是「上次说过的这次要记得」。两者的存储、生命周期、失效策略完全不同。我们项目里长期记忆单独一个 memory 节点，短期靠 state 里的消息列表和工具结果治理。

追问：那模型的「记忆」到底存在哪？

A：模型自己没有记忆，它是无状态的。所谓记忆全在你这一侧——每次请求都要把历史重新拼进去。所以「记忆系统」本质上是一个上下文预算分配问题，这也是为什么工具结果治理和记忆压缩是同一件事的两个侧面。

Q3：Agent 的发展谱系你了解吗？从符号 Agent 到 LLM Agent，变的是什么？

A（要点）：变的只有决策器从哪来：符号 Agent 的决策是人工编码的规则，RL Agent 的决策是从交互里学出来的策略 ，LLM Agent 的决策直接用语言模型的预训练先验。没变的是两件事：① 都是「感知—决策—行动」循环；② 都需要一个动作抽象层（符号 Agent 是动作原语，RL 是动作空间，LLM 是工具 schema）。

追问：那 LLM Agent 解决了前两代的什么问题？又留下了什么？

A：它绕过了符号 Agent 最致命的知识获取瓶颈——你不用再把世界知识写成规则；也绕过了 RL 的样本效率问题——不用为每个任务训练策略。但它没消除这个瓶颈，只是把它换了个形态：变成了幻觉和工具选错。这是我的判断：Agent 的核心矛盾一直是「知识从哪来、以及怎么保证它对」，只是每一代把它挪了个位置。

追问：那你觉得现在的瓶颈在哪？

A：不在模型能力，在验证。我们能把动作做出来，但很难低成本地判断「这一步做对了没」。所以工程上的对策是「把可判定的判断交给程序」——schema 校验、幂等键、引用越界检查这些确定性的闸门，比再让模型自评一次值钱得多。落到我做过的实验上：反思重试我设 REFLECT_MAX_RETRIES = 1，反思的触发条件是 pydantic 校验失败、工具错误码、空结果这类外部信号，不是「让模型再看看」。
