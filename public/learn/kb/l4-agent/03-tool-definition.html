工具定义、调用生命周期与并行调用 ​

覆盖知识点：L4-05 L4-06 L4-07 ｜ 面试频率：高 ｜ 建议学时：11h

一句话说清 ​

工具定义就是「给模型写一份 API 文档」——但和你给人写的文档不同，读它的是一个不会问你问题的概率模型，所以歧义不会被澄清，只会变成一次错误调用。工具调用的完整生命周期有六段，其中只有第二段发生在模型侧，其余五段都是你的代码，这个分工是整层最重要的一个事实。并行调用不是「一次调多个工具」这么简单：它把「一轮一次执行」变成「一轮一个批次」，于是超时、部分失败、速率限制、审批全部从「单个」变成「一组」，上下文增长和网络扇出都按并行宽度放大。

为什么必须学（面试官视角） ​

这三条是工具生态的主干，权重高于 MCP、高于框架、高于多智能体，原因很实在：

  • L4-05 决定你的调用成功率。 实际系统里「模型选错工具」和「参数填错」的根因，超过一半不在模型，在工具描述写得稀烂：描述里没写什么时候不该用、参数名有歧义、可选字段和必填字段混淆。面试官会拿你项目里的一个工具问你「这个工具的描述为什么这么写」，答不上来说明你从来没归因过失败调用。
  • L4-06 是面试必问的机制题。 「工具是谁执行的？」这个问题在 AI 岗位一面里出现的频率接近必考。答「模型执行的」直接结束。正确答案里还必须包含两个边界：tool_calls 字段会骗人（模型可能用自然语言说要调工具而字段是空的），以及工具结果必须被治理后才能回填（不然一步就能炸掉上下文）。
  • L4-07 是延迟优化的唯一抓手。 Agent 的延迟形状是「轮数 × 每轮耗时」，串行工具调用是每轮耗时的主要成分。把无依赖的工具并行化是唯一一个不牺牲正确性就能降延迟的手段——但它的代价（部分失败、审批语义、上下文放大）必须能说出来，否则会被判定为「只会看收益不会看风险」。
  • 权重上的一个对比：MCP 是 2026 年简历上的硬关键词，但它解决的是接入方式的问题；而工具 schema、生命周期、并行是接入之后你每天都要面对的东西。先有这三条，MCP 才有意义。

核心内容 ​

L4-05 Tool / Function 定义规范 ​

  • 定义：一个工具 = 一个确定性函数 + 一份给模型看的 JSON Schema 说明。说明包含工具名、用途描述、参数对象（类型、必填、每个参数的含义），有些实现还支持枚举、默认值、参数间约束。模型只看得到说明，看不到函数体。

  • 机制（一份好 schema 有七个必须写对的字段）：

位置写什么写错的后果
name动词 + 宾语，全局唯一，机器可读（query_order 而不是 订单查询）模型拼错名 → 未知工具；重名 → 随机命中
description什么时候用它 + 什么时候不要用它 + 返回什么该用的不用、不该用的乱用
parameters.type通常固定 "object"结构不对，部分实现直接报错
properties每个参数的类型 + 一句人话解释类型填错 → 校验失败；解释缺失 → 语义猜错
required只放真正必填的。可选参数一律不进这个数组把可选参数写成必填 → 模型被迫编一个值
enum取值可枚举的都列出来模型自由生成合法字符串 → 下游匹配不上
返回值描述说清返回是「结构化字段」还是「自然语言段落」模型对返回值做错误的解析假设

  • 为什么这样设计：

    • 为什么描述要写「什么时候不要用」：模型在多个相似工具之间做选择时，唯一的判据就是描述。如果你只写了「查询订单信息」，那么「查物流」和「查退款」这两个工具都会和它语义重叠。补一句「只在需要订单状态、金额、下单时间时使用；查物流轨迹请用 query_logistics」，调用错误率会明显下降。这条是工具设计里投入产出比最高的一句话。
    • 为什么可选参数不能进 required：JSON Schema 的 required 语义是「必须出现」。模型看到必填就会给值——它宁可编一个也不肯留空。所以把「筛选条件」这类可选字段写进必填，等于逼模型编造筛选条件。
    • 为什么参数名要有歧义预算：date 是可以同时被理解成「下单日期 / 查询日期 / 发货日期」的。歧义不会让模型问你，它会让模型按训练语料的多数分布猜一个，而那个猜测通常不是你想要的。
    • 为什么工具粒度要「一个工具一件事」：宽工具（一个 do_order_thing(action=...)）会让描述变复杂、参数互相污染；窄工具的问题是数量膨胀，进而引出 工具选择与路由。应届项目的正确起点是窄工具 + 少量（5–15 个）。

  • 数量级与形状：

    • 单个工具的 schema 通常在 100–400 token 量级（描述越长越贵）。工具数量 × 每个 schema 的 token = 每轮固定开销，这笔开销在每一次模型调用上都要付一遍，不只是一次。
    • 15 个工具、平均 200 token/schema ≈ 3000 token 的固定开销，在 6 步循环里就是 18000 token——比大多数用户的输入还大。这是「工具太多」最直接的代价。

  • 常见误区：

    • 描述写成函数 docstring：docstring 面向人，schema 描述面向模型。前者可以写「内部实现见 xxx」，后者必须自包含。
    • 参数描述省略单位与格式：「时间」不写是秒还是毫秒、是本地时间还是 UTC，「金额」不写是元还是分——下游一定出错。
    • 把内部实现细节写进描述：既浪费 token，也是提示词泄露面。
    • 工具名用中文或带空格：很多实现的工具名要能当标识符用，别赌。
    • 以为描述不重要，靠 prompt 里补：工具 schema 和 system 提示词是两个不同的位置，越靠近工具的信息越不容易在长上下文里被淹没。

  • 代码（schema 与函数体分开维护，是本页最该带走的一条工程纪律）：

python
# 伪代码风格：真实项目里 schema 由框架从函数签名生成，或手写维护。
# 关键纪律：schema 是「模型看到的契约」，函数体是「程序的行为」，两者的真源必须是同一个。
QUERY_ORDER_SCHEMA = {
    "name": "query_order",
    "description": (
        "查询订单的状态、金额与下单时间。"
        "只在需要订单状态/金额/下单时间时使用；"
        "查询物流轨迹请用 query_logistics，查询退款规则请用 query_refund_policy。"
        "返回结构化字段，不是自然语言段落。"
    ),
    "parameters": {
        "type": "object",
        "properties": {
            "order_id": {"type": "string", "description": "订单号，形如 SO 开头的字符串"},
            "status": {"type": "string", "enum": ["paid", "shipped", "delivered", "refunded"],
                       "description": "可选筛选项；不筛选时请不要传这个字段"},
        },
        "required": ["order_id"],          # 只放真正必填的
    },
}

L4-06 工具调用的完整生命周期 ​

  • 定义：从用户提问到拿到最终答案，工具调用经历 ① 契约注入 → ② 模型输出调用意图 → ③ 程序校验 → ④ 执行 → ⑤ 结果治理与回填 → ⑥ 再次生成 六段。其中只有第 ② 段发生在模型侧。

  • 机制（逐段，标出责任方）：

#段责任方这一段的产物出错的典型形态
①契约注入你的代码请求里带上工具 schema 清单清单太大 → 每轮固定开销高；清单有歧义 → 选错
②模型输出调用意图模型工具名 + 参数（通常是 JSON 字符串）+ 调用 id编造工具名；参数缺字段；嘴上说要调、字段却是空的
③程序校验你的代码通过 / 拒绝 + 拒绝原因不校验 → 越权、崩溃、参数注入
④执行你的代码原始返回值超时；抛异常炸掉整个会话；副作用重复发生
⑤结果治理与回填你的代码一段长度受控、模型可读的观测原样回填几万行日志 → 上下文被炸
⑥再次生成模型下一步意图或最终答案忽略错误观测继续往下答

  • 为什么这样设计（这四条是面试官在等的）：

    • 为什么要分成「模型侧」和「程序侧」两半：因为模型不执行任何东西，它输出的是意图。这个事实带来一个非常实用的推论：所有安全控制都必须落在第 ③ 段——工具白名单、参数 schema 校验、权限收窄、幂等键、人工确认。它们没有别的地方可放。
    • 为什么校验必须在执行之前：执行是不可逆的。「先执行、发现参数不对再补救」在只读工具上代价不大，在写操作上等于已经下过一次单了。
    • 为什么错误要走回填而不是抛异常：抛异常会打断会话，模型失去「看到错误、改参数、换工具」的机会。把错误当成一种观测回填，循环继续但信息变完整——这条纪律在项目里的写法是「校验失败不炸图，错误作为工具结果写回 state」。
    • 为什么结果治理不是可选项：模型返回的结果是给你看的，工具返回的结果是给模型看的，两者的形态要求完全不同。一条日志查询工具完全可能返回几万行，一步就能把上下文推到超限。治理放在第 ⑤ 段而不是「等到装不下再说」，是因为那时候你已经付过一次 token 钱和一次延迟了。

  • 数量级与形状：

    • 一次工具调用往返的网络延迟量级在几十毫秒到几秒；工具数量多时，第 ① 段的固定 token 开销乘以循环轮数就是总开销的大头。
    • 工具返回值的治理阈值通常按字符数或 token 数设（例如保留头部若干行 + 尾部若干行 + 中间省略标记），而不是按「看起来长不长」。
    • 一个容易漏的口径：tool_calls 里同一个工具可以在一次响应中被调用多次（不同参数）。所以「工具数」和「这一轮实际执行次数」不是一回事。

  • 常见误区：

    • tool_calls 会骗人：模型可能在 content 里写「我准备调用查询订单工具」，而结构化字段是空的。程序的判据必须只看结构化字段。反过来的情况也存在：字段里有调用而 content 是空串——很多实现里这是正常的，不要把它当异常。
    • 忘了把「模型这一轮的消息」放回历史：只追加工具结果，模型下一轮不知道自己上一步干了什么。
    • 解析 arguments 时假设它是 dict：多数实现里它是 JSON 字符串，需要自己解析，而且可能解析失败（模型偶尔会输出不合法 JSON）。解析失败要作为校验失败处理，不是崩溃。
    • 工具结果不带调用 id 回填：并行调用时结果与调用对不上号。
    • 把「模型说要调工具」当成「工具已经被调用」：于是日志里出现了「已调用」，实际什么都没有发生。

  • 代码（第 ③ 段的校验层，这是安全控制的唯一入口）：

python
# 伪代码：校验层。真实项目里入参校验用 pydantic 模型承载。
from pydantic import BaseModel, Field, ValidationError

class QueryOrderArgs(BaseModel):
    order_id: str = Field(min_length=1, max_length=64)
    status: str | None = None

ALLOWED = {"query_order": QueryOrderArgs}          # 白名单即权限：不在表里的工具一律拒绝

def gate(name: str, raw_args) -> tuple[BaseModel | None, str]:
    """返回 (校验后的参数, 错误说明)。错误不抛，交给上层回填成观测。"""
    model = ALLOWED.get(name)
    if model is None:
        return None, f"unknown_tool: {name}；可用工具 {sorted(ALLOWED)}"
    try:
        payload = raw_args if isinstance(raw_args, dict) else json.loads(raw_args)
    except (TypeError, ValueError) as exc:
        return None, f"bad_json: {exc}"
    try:
        return model.model_validate(payload), ""
    except ValidationError as exc:
        # 关键：把「缺了哪个字段」原样回灌，模型下一轮才知道怎么改
        return None, f"invalid_args: {exc.errors()}"

L4-07 并行工具调用 ​

  • 定义：模型在一次响应里发起多个工具调用（例如同时查订单状态和查物流轨迹），程序可以并发执行它们，再把多个结果一起回填，然后让模型做一次合成。它是延迟优化的主要手段，因为它把「多次串行的往返」压成「一次往返」。

  • 机制（三个前提 + 一个批次语义）：

    • 前提 1：模型侧支持。必须模型本身能在一次响应里输出多个调用意图（各家已普遍支持，具体字段形状以官方文档为准）。
    • 前提 2：调用之间无数据依赖。并行调用有数据依赖时是错的——后一个的参数需要前一个的返回值，那必须串行。
    • 前提 3:程序侧要能并发执行。伪并行的 for 循环（一次调一个）拿不到任何收益，反而多了一层复杂度。
    • 批次语义：一轮里的 N 个调用构成一个批次。批次是全成功 / 部分失败 / 全失败三态，不是一个布尔值。这决定了审批、重试、幂等的粒度都必须从「单个」升级到「一组」。

  • 为什么这样设计（收益与代价都要说）：

    • 收益：延迟上，N 个独立调用从 降到 。当每个调用耗时接近时，理论收益接近 N 倍——这是整个 Agent 延迟优化里唯一一个不牺牲正确性的手段。
    • 代价 1：部分失败。批次里 2 个成功 1 个失败时，不能把成功的两个丢掉重试整批（那会重复副作用），也不能假装整批失败。正确处理是把 batch 的三个结果逐个回填，失败的那个带 ERROR: 前缀，让模型看到「哪些成功了、哪个没成功」。
    • 代价 2：审批语义变复杂。人工确认面对的不再是「要不要执行这个动作」，而是「这三件事要不要一起做」；如果批次里有一个高风险写操作，整批要挂起等待，而只读的部分其实可以先执行——这需要你把批次按风险等级再切一刀。
    • 代价 3：速率限制与扇出。N 个并发请求可能同时触发下游的限流。并发宽度要有上限，不是「模型给多少就并发多少」。
    • 代价 4：上下文放大。N 个工具结果同时进上下文，峰值比串行高——串行时至少你有机会在中间做压缩。

  • 数量级与形状：

    • 常见并行宽度在个位数（一次响应里 2–5 个调用是常态）。这让「每轮执行次数」与「轮数」解耦：3 轮 × 每轮 3 个调用 = 9 次工具执行。
    • 因此闸门必须是两个：步数闸（管轮数）和调用次数闸（管实际执行次数）。这一点在 手写 ReAct 里给了代码，在 终止条件 里会展开。

  • 常见误区：

    • 把「模型输出了多个调用」当成「应该并行执行」：有依赖的调用并行化会拿到错误的参数。
    • 并行执行了但只回填一个结果：模型会以为其余的没执行，下一轮再调一遍——副作用就重复了。结果必须按调用 id 一一对应地回填。
    • 用一次大超时覆盖整批：正确做法是单次调用有超时，整批有上限，先返回的先用（哪个失败就在那个位置写错误）。
    • 在有副作用的工具上默认开并行：写操作并行前先过幂等键，否则重试路径会重复下单。
    • 以为并行能省 token：并行省的是延迟，token 通常还要多一点（多个结果的峰值同时在上下文里）。

和你自己的项目对上号 ​

YYHelp v2（LangGraph 电商客服 Agent）：这一页的三个知识点在这个项目里都有代码级的落点。

  • L4-05 工具定义：v1 的工具契约层是 graph/tools.py（1201 行），结构是「5 个 @tool + pydantic 入参校验」。5 个工具是 search_kb、query_order、query_refund_policy、query_logistics、create_ticket。这里最值得讲的不是数量，而是契约与行为分离：schema 面向模型，pydantic 模型面向程序，校验层是两者的接缝。

  • L4-06 生命周期：这个项目把第 ③ 段做得最细，而且有一条可以直接背的纪律——「校验失败不炸图，错误作为工具结果写回 state」。也就是说第 ③ 段拒绝之后的动作是生成一段观测，而不是 raise。这条纪律的效果是：模型下一轮能看到「order_id 少了」这类具体错误，从而改参数重试，而不是整个会话 500。

    另一个可以直接讲的细节：v1 在处理 未知工具 与 tool_calls 位置时写了专门分支（graph/agent.py:604-610,625）。这条代码存在的理由就是本页的核心警示：tool_calls 字段的形状会骗人，不能假设它一定在、也不能假设 content 一定是字符串。

  • L4-07 并行调用：这个项目的真实选择是「串行 + 分派上限」，而且理由是量化的、可以直接背。DISPATCH_LIMIT = 2（supervisor.py:199），决策依据里有一条正是并行与串行的形状差异：「串行是次数问题（上限直接封顶），并行是扇出问题（封顶需要『深度 × 宽度』两个预算，且失败归因复杂化）」。这是一个非常高级的取舍表达——你没有并行，但你能说清为什么不并行，比「我用了并行所以更快」强得多。

    上限为什么是 2 的四条理由也值得背：① 1 是下限；② 2 够用（需求书里的跨域例子「退款 + 改址」正好两个专家；9 条可见性探针全是单域；实测 40 题里转交仅 3 题：R11/R18 → agent_free，R24 → order_ops，全部 2 轮内收尾）；③ 2 封住无限循环（分派次数是单调递增计数器 budget.steps，到上限强制 finalize，source="quota"）；④ 不选 3（每多一轮 = 多一次专家完整 ReAct 回合，专家 total_tokens 量级在千级，没有证据表明 3 轮更好之前选小值）。

  • ⚠️ 一条工程纪律，比任何 API 都值钱：这个项目做过一次**「写下 ≠ 执行」的清算。v1 有 11 个 selftest 从未被 pytest 执行；v2 建了自检总闸，把 v1 14 条 + v2 16 条 = 30 条入口用 subprocess 真跑起来，并把超时从 180 秒收紧到 60 秒（依据：v1 最慢的自检 2.61s、v2 首个 mcp.selftest 2.84s，60 秒约为实测最慢者的 21 倍）。原话值得逐字背：「代码的防护力 = 被执行的断言数，不是写下的断言数。一个从不执行的断言，防护力与『没有断言』完全相同——但它会让你以为有防护。这比没有更危险。」** 追问「工具参数校验到底管不管用」时，这句话是最好的回答：校验函数的防护力同样等于它被执行到的次数。

科研文献 RAG：这个项目没有工具层——它的检索链路是写死的，模型不选择调用哪个工具。所以 L4-05 / L4-07 在这里没有落点，但 L4-06 有一条极接近的同构经验可以直接迁移：

  • 引用编号校验 = 工具参数校验的同一类问题。这个项目里引用编号的解析曾经出过一个真实缺陷：["1","2"] 这种形态被静默丢弃成 citations=[]，而校验函数返回了 True 报「校验通过」。这和「工具参数校验写成 except: pass」是同一个错误——一个总能通过的校验函数，等于没有校验。面试里可以把两件事并起来讲：「我的校验层的判据是能不能构造出一个让校验失败的用例；构造不出来的校验，我不会把它算进防护力。」这条比任何 API 名都有说服力。
  • 想给这个项目补 L4-05 / L4-07 的话，最小做法是把检索器工具化（入参 query / top_k），并把「多路查询改写」做成一次响应里的多个并行调用（各路互不依赖，天然适合并行），然后对照「串行多路检索」看延迟与召回的变化。这条实验同时覆盖 Agentic RAG 与并行调用两个知识点。

面试怎么问（≥3 组） ​

Q1：Function Calling 到底是谁在执行工具？

A（要点）：模型不执行任何东西，它只输出「要调哪个工具、参数是什么」的意图，执行的是我的代码。所以完整的生命周期有六段，只有第二段在模型侧：契约注入、模型输出意图、程序校验、执行、结果治理与回填、再次生成。这个分工不是实现选择，是机制的硬约束。

追问 1：那为什么说这个分工很重要？

A：因为它决定了所有安全控制只能落在第三段。工具白名单、参数 schema 校验、权限收窄、幂等键、人工确认，全都在模型输出之后、真正执行之前这一个窗口里。一旦你接受「模型直接执行」这个错误前提，这五件事就没有地方可放。

追问 2：tool_calls 会不会骗人？

A：会，有两种形态。第一种是模型在 content 里写「我准备调用查询订单工具」而结构化字段是空的——所以我的判据只认结构化字段，content 只用于展示。第二种反过来的：字段里有调用而 content 是空字符串，这在很多实现里是正常的，写成 if content: 之外对 content 做字符串操作会崩。我们项目里对未知工具与 tool_calls 位置写了专门分支，防的就是形状不对的输入。

追问 3：工具执行失败了怎么处理？

A：不抛异常，把错误包成观测回填。项目的纪律原话是「校验失败不炸图，错误作为工具结果写回 state」——这样循环继续，但模型能看到「order_id 少了」这类具体错误，下一轮能改参数。抛异常会让整个会话在第一次工具抖动时就断掉。

Q2：你怎么保证模型选对工具、填对参数？

A（要点）：三个层次。第一是描述层：工具的 description 必须写「什么时候用它」和「什么时候不要用它」，并显式点名应该改用的那个工具。模型在相似工具之间唯一的判据就是描述。第二是 schema 层：required 只放真正必填的（把可选字段写成必填，等于逼模型编值）、取值可枚举的一律上 enum、参数描述必须带单位与格式。第三是可见性层：不该看到某个工具的专家，在提示词层面根本看不到它的 schema——这一层同时也是一道权限闸。

追问：为什么说「什么时候不要用它」最值钱？

A：因为失败调用最常见的形态不是「模型完全不知道有这个工具」，而是「它在两个都能接受语义的工具之间选错了」。我项目里 5 个工具，query_order 和 query_logistics 就有语义重叠——订单状态里常常也带物流信息。所以描述里得写明「查物流轨迹请用 query_logistics」。这不是文案工作，这是把模型的选择空间收窄到唯一解。

追问：那工具太多了怎么办？

A：那时描述写不完，得靠筛选。但要说清一件事：工具描述占的是每轮固定开销，15 个工具平均 200 token 就是每次模型调用 3000 token，6 步循环就接近 18000——比用户输入还大。所以「工具太多」的第一代价不是选错，是每一轮都在付这笔钱。筛选机制见 工具选择与路由。

Q3：并行工具调用你怎么用？什么时候不该用？

A（要点）：只有当调用之间无数据依赖时才并行——后一个的参数需要前一个的返回值，那就必须串行。它的收益是延迟：N 个独立调用从 降到 ，这是 Agent 延迟优化里唯一不牺牲正确性的手段。代价有四条：部分失败（批次是全成功/部分失败/全失败三态，不是布尔值）、审批语义升级（从「要不要做这件事」变成「这一组要不要一起做」）、速率限制与扇出（并发宽度要有上限）、上下文放大（N 个结果同时进上下文，峰值比串行高）。

追问：批次里有一个失败了怎么办？

A：逐个回填，失败的那个带错误前缀，不许把整批合并成一条，也不许丢弃成功的结果重试整批——后者会重复副作用。这样模型看到的是「2 个成功、1 个超时」，它可以只重试失败那一个。

追问：那你怎么管并发宽度和总次数？

A：两个闸门，因为它们管的是两件事。步数闸管轮数（一轮可以有多个调用），调用次数闸管实际执行次数。3 轮 × 每轮 3 个调用 = 9 次真实执行，只限步数的话最坏情况是步数 × 并行宽度。我项目里选了另一个方向：串行 + 分派上限 2，理由是「串行是次数问题，上限可以直接封顶；并行是扇出问题，封顶需要深度 × 宽度两个预算，还要处理失败归因」——在没有证据表明并行收益值得这套复杂度之前，选小值。
