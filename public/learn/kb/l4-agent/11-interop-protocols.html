本页目录

A2A / ANP 等 Agent 间通信协议 ​

覆盖知识点：L4-25 ｜ 面试频率：低 ｜ 建议学时：3h

一句话说清 ​

MCP 解决的是「一个 Agent 怎么用别人的工具」，Agent 间通信协议解决的是「一个 Agent 怎么用别人的 Agent」。这两件事的抽象层次不同：工具是函数，Agent 是会自己决定下一步的实体。所以协议必须额外表达四样东西 —— 我是谁、我能干什么、这件事办到哪一步了、办完之后产出物在哪。这一页讲清 A2A、ANP 这类协议的设计动机与核心抽象，以及为什么它们在你现在的项目里用不上。

为什么必须学（面试官视角） ​

这一项在大纲里标的是低频，但低频率不等于可以空着 —— 它的价值在区分度上：

  • 它是「Agent 生态」这块拼图的最后一块。面试官问完 MCP（工具层）、再问「那多个 Agent 之间怎么协作」，如果你只有「我用 LangGraph 的多智能体节点」这一个答案，说明你的认知停在单进程内。能说出「进程内多智能体是编排问题，跨组织多智能体是协议问题」，这一步就把你和绝大多数候选人分开了。
  • 它是判断力的试金石。前沿协议的题，面试官真正想看的是你有没有能力识别「什么时候不该用它」。一个能说「A2A 解决的是跨组织信任与能力发现，我现在的系统没有这个前提」的应届生，比一个能把 A2A 讲得头头是道却什么都想往上套的应届生更可信。
  • 它是诚实度的考点。这一项你没做过就是没做过。正确答法是「我了解它的抽象层次与动机，但没有实际集成」；一旦你把「读过概念」包装成「做过」，而面试官恰好做过，追问两层就会把你按在地上（这是 AI 方向简历最典型的翻车方式，见 框架横向对比 里关于「别写不存在的落地经验」的讨论）。

核心内容 ​

L4-25 A2A / ANP 等 Agent 间通信协议 ​

  • 定义：Agent 间通信协议是一类应用层协议，规定了「一个 Agent（客户端侧）如何发现另一个 Agent（服务端侧）的能力、如何把任务托付给它、如何跟踪任务进展、如何取回结果」。A2A（Agent2Agent）、ANP（Agent Network Protocol）是这个方向上有代表性的两类公开努力。

    ⚠️ 本页不声称任何具体版本号、字段名、方法名、是否已标准化，也不声称谁支持谁。 这类协议还在快速演进，且不同项目的术语不统一。具体规范内容以各自的官方文档为准。 本页只讲为什么要这么设计，以及判据——这两样不会过期。面试里的正确表述也一样：讲抽象与动机，不背字段。

  • 机制：它必须表达的四个东西。抓住这四条，你就理解了这类协议的骨架，而不需要记忆任何 API：

要素解决什么问题类比
身份与能力声明「对方是谁、它能干什么」—— 没有这个就无法自动发现类似「名片 + 服务目录」
任务托付「把一件事交给它办」，并且这件事是长时运行的，不是一个函数调用类似「下单」而不是「调用方法」
状态与进展长任务会跑很久，需要查询进度、需要推送状态变化类似「物流跟踪」
产出物归集结果是文件 / 结构化数据 / 消息，不只是「一个字符串返回值」类似「交付物签收」

最容易讲错的一点：把 Agent 间的「任务」说成「一个更复杂的函数调用」。它们的根本差别在时长与不确定性 —— 一次 RPC 的语义是「很快返回」，一个任务是「可能几分钟到几天、可能中途需要向你追问、可能失败需要重试」。协议要表达的正是这些函数调用表达不了的东西。这就是为什么它们不可能退化成「MCP 加一个字段」。

  • 机制：为什么这个需求真实存在（两个驱动力）：

    1. 组织边界与信任边界重合。同一家公司内部，让两个 Agent 协作可以靠共享状态、共享数据库、共享代码 —— 进程内多智能体（见 多智能体协作与通信）就够了。但跨公司时这些手段全部失效：你不能读对方的数据库，不能假设对方和你用同一个框架，不能假设对方愿意把内部实现暴露给你。此时唯一能协商的就是协议。
    2. 能力发现的需求。MCP 的模型是「我预先知道要连哪个 server」，工具清单是配置出来的。而 Agent 生态的理想形态是「我需要一个会做 X 的 Agent，我不知道谁有，先去找」—— 这要求可发现的能力描述，是一个比「工具清单」更开放的问题。

  • 机制：分层关系 —— 这三个协议不是竞品。这是这一页最值钱的一段，因为它能一次性消除面试官的怀疑（怀疑你「看到新名词就往简历上贴」）：

三句话记住分层：

  1. LangGraph 那类框架解决「一个进程内的编排」 —— 强调可控、可观测、可持久化；
  2. MCP 解决「一个 Agent 用外部工具」 —— 抽象单元是函数契约；
  3. A2A / ANP 解决「一个 Agent 找另一个 Agent 办事」 —— 抽象单元是任务。

⚠️ 上图中「L2 的 Agent 内部可能再调 MCP」是架构上的合理嵌套，不是说某个协议规定必须这样。具体协议之间的关系以各自官方文档为准。

  • 数量级与形状：这类协议在企业落地时的典型形态是 —— 一侧是「Agent 网关 / 注册中心」，另一侧是各团队各自发布自己的 Agent。这带来两个你可能想不到的工程后果：

    • 延迟与超时的量级完全不同。MCP 的一次调用是秒级（项目实测口径：CALL_TIMEOUT_S = 20.0），而 Agent 间任务可能是分钟到小时级。同一套超时口径套不到两种场景上 —— 这是协议分层在代码里的具体体现（也解释了为什么 MCP 协议演进 里「长任务」会被单独列成一类能力）。
    • 费用与配额要按「任务」而不是按「调用」核算。一次任务托付背后可能是对方的 N 次模型调用，你看到的是一个任务，账单是一串消耗。

  • 为什么这样设计（三个反直觉取舍）：

    1. 为什么是「任务」而不是「远程调用一个 Agent 方法」？ 因为 Agent 的输出不确定：同样的问题，它可能直接回答、可能反问、可能拒绝。任务模型允许「不确定的时长 + 中途交互 + 最终产出物」这三种形态共存，而 RPC 模型只允许「立刻给出一个值」。
    2. 为什么需要「能力声明」而不是「我给你一份接口文档」？ 因为参与者是动态的：新 Agent 上线、旧 Agent 下线、能力升级。静态文档无法支撑自动发现，而这是生态的前提。
    3. 为什么这类协议强调「不暴露内部实现」？ 因为协作的前提是不要求对方和你同构。一个企业不会为了跟你协作就把自己的 Agent 框架换掉 —— 协议必须允许双方内部实现完全不同。

  • 常见误区：

    • 把 A2A 当成「MCP 的升级版」 —— 它们在同一系统里是并存的不同层，不是替代关系；
    • 以为「我先上 A2A 就是先进」 —— 这类协议的价值前提是跨组织/跨团队的多消费者，和 MCP 的判据同源：单消费者时上协议层是负收益（见 MCP 协议、传输与安全 的 ADR-2 讨论）；
    • 把「多智能体」等同于「需要 Agent 间协议」 —— 进程内用 LangGraph 的多节点拓扑就够了，只有跨进程/跨组织时才需要协议；
    • 背协议细节充当深度 —— 这类协议演进快，背的细节会过期；讲清「它为什么存在、什么时候不该用」才是不会过期的深度。

和你自己的项目对上号 ​

诚实结论：YYHelp v2 与科研文献 RAG 两个项目都没有使用 Agent 间通信协议，这一项你现在的状态是「只有概念，没有实操」。

不要为了填这个空去编造。这一项在面试里的正确打开方式是主动把它变成判断力的展示，三种场景三种说法：

  1. 面试官问「你了解 Agent 间通信协议吗」 —— 「了解它在生态里的位置：MCP 是工具协议、编排框架管进程内协作、A2A/ANP 那类管跨进程跨组织的任务托付，核心抽象是身份与能力声明、任务、进展、产出物四件事。我没有实际集成过，所以细节我不敢说。」
  2. 面试官追问「那你的多智能体为什么不用它」 —— 「因为我的多智能体全部在同一个进程、同一张图里（supervisor + 专家节点），共享 state 就够，用协议是凭空多一层序列化与生命周期管理。判据和我做 MCP 决策时是同一条：价值前提是跨消费者复用，不满足就是负收益。」（这条判据来自 12-ADR-2-MCP-vs-原生tool.md，是可以直接引用的真实结论。）
  3. 面试官问「如果要做跨组织的 Agent 协作你会怎么设计」 —— 这时才展开讲四要素，并主动指出你最担心的是前三件事：身份怎么被验证、任务失败与重试怎么界定（这直接接上 幂等与副作用防护）、以及产出物的格式协商。«不确定的地方说不确定» 在这里比编一段设计更能加分。

如果你想真正补上这一项（可执行、小而具体，不要做大）：

  • 第一步（约 2 小时）：挑其中一个协议的官方文档，只回答一个问题 —— 「它的能力声明里有哪些字段」。不用动手，把答案写成半页笔记。目的是能区分「我读过规范」和「我看过博客」。
  • 第二步（约 4 小时）：用你已有的 MCP server 做一次「假 Agent 服务」实验 —— 起一个进程，暴露两个 HTTP 端点：一个返回「我是谁、我能做什么」，一个接收任务、返回一个任务标识，再提供一个查询进展的端点。不引任何协议库，纯粹是为了亲手体会「任务」与「调用」在状态管理上的差别。
  • 第三步：把这次实验写成你项目页里的一段「未落地但验证过概念」的记录，必须显式标注「这是我为理解协议做的最小实验，不是生产集成」。

为什么值得做：面试里「我读过它」和「我为理解它写过一个 60 行的小实验」是两种分量。后者可以支撑追问三层；前者在第二层就会见底。

面试怎么问 ​

Q1：MCP 和 A2A 有什么区别？

A（要点）：抽象层次不同。MCP 的抽象单元是函数契约 —— 解决「一个 Agent 怎么用别人的工具」；A2A 这类协议的抽象单元是任务 —— 解决「一个 Agent 怎么找另一个 Agent 办事」。所以它们要表达的东西不同：MCP 要协商的是工具清单与参数 schema；Agent 间协议要额外表达身份与能力声明、任务托付、进展状态、产出物归集。它们在同一系统里是并存的不同层，不是替代关系。

追问：那为什么不能把 A2A 看成「MCP 加上长任务支持」？

A：因为根本差别是「不确定的时长 + 中途可能交互 + 结果是一组产出物」。一次 RPC 的语义是「很快返回一个值」；而一个任务可能几分钟到几天、可能中途反问你、可能失败需要重试、产出可能是文件或结构化数据。这些是 RPC 语义表达不了的，所以要另立一层。顺带说，这也解释了为什么超时口径套不到两种场景上 —— MCP 一次调用我按 20s 设超时，Agent 间的任务不可能用这个口径。

追问：那你举一个「差一点就设计错了」的例子。

A：我会拿自己项目里的一条决策类比：v1 曾经把 query_order(order_no, user_id="u_001") 内部函数原样搬上 MCP，结果 user_id 变成 client 可传的参数，把越权校验整个短路。它的教训和协议分层是同一条：每次把东西提升到协议边界，都要逐项重问「这个信息在新的信任模型下还成立吗」。 参数面如此，身份如此，Agent 间的「谁有权托付任务」也如此。所以设计 Agent 间协作时我最关心的不是消息格式，是身份与授权怎么跨组织成立。

再追问：那你会优先解决哪一个？

A：身份。因为「能力发现、任务托付、产出物归集」这三样在技术上都好解决 —— 本质是消息格式与状态机；而身份一旦错了，后面每一条都建在错的基础上。鉴权位置错了，你的能力发现就会把不该暴露的 Agent 暴露出去。这也是我在 MCP 那部分的结论：权限决策在 host 那一层，不在能力提供方那一层。

Q2：你了解 ANP 吗？A2A 和 ANP 有什么不同？

A（要点）：我了解它们都在 Agent 间互操作这个方向上，但具体规范内容、目标场景划分、字段与方法细节我不敢断言 —— 以各自官方文档为准。我可以说的是它们的共同抽象：身份与能力声明、任务托付、进展、产出物。至于差异，我更愿意讲判据而不是讲八卦：选哪一个，看的是你要解决的信任边界和参与者能不能同构，而不是哪一个名词更新。

追问：那你凭什么说自己懂这一块？

A：我不敢说自己懂规范。我懂的是它在生态里的位置，以及什么时候不该用它。前者是从协议分层的角度建立的：编排框架管进程内、MCP 管工具、Agent 间协议管跨组织的任务托付 —— 这三层的抽象单元分别是节点 / 函数 / 任务。后者是一条可复用的判据：协议层的价值前提是多消费者 + 动态变化。不满足这个前提，引入协议就是凭空多一层序列化、生命周期与版本兼容成本。

追问：这个判据你是怎么建立的？

A：从自己做 MCP 的经历迁移过来的。我在项目里做过一个 ADR：主链路的 Agent 循环继续用原生 @tool，只把跨进程/跨语言能力交给 MCP，因为单消费者场景下 MCP 的收益是零、成本是多一层边界与一个版本约束。同一条推理用在 Agent 间协议上结论一样 —— 不是「新协议更先进」，而是「跨边界协作才有收益」。

再追问：那你觉得这些协议最终会收敛吗？

A：我不预测。但我知道判断它们是否收敛的观察点：如果某一天「一个 Agent 的能力声明」变成了一个稳定、可校验、跨项目通用的东西，那收敛就发生了；在那之前，任何基于「某个协议的某个字段」做的深度集成都有被推翻的风险。这也是我暂时不在项目里引入它的理由之一 —— 不是不看好，是它的稳定收益还不确定。

Q3：多智能体协作到底要不要用协议？

A（要点）：先看边界。同一个进程内的多智能体不需要协议 —— 用编排框架的图、节点、共享 state 就够了，而且可控性和可观测性都好得多。只有跨进程、跨语言、尤其是跨团队/跨组织时，协议才开始有价值，因为此时共享状态、共享代码这些手段都不成立了。再一个判据是消费者的数量：只有一个消费者的一次性集成，引协议是过度设计。

追问：那「什么时候该从单智能体升级到多智能体」你怎么判断？

A：不是用「多智能体更好」来回答，而是用**「单智能体测不出差异」**来回答。我的实际做法是做一个 A/B：single 与 multi 两种模式跑同一批题，除被测变量外全部冻结（同一个 ReAct 内核、同一套工具、同样的闸），让自变量尽量少、且每一处差异都能被列出来 —— 差异只在前四行（有无 plan / supervisor / memory / reflect、决策者是谁、工具菜单、system prompt），第五六行完全同源。如果我测不出差异，那就是不该上多智能体。

追问：那这个 A/B 和「用不用 Agent 间协议」是同一个问题吗？

A：不是，但用同一种方法。前者是「架构形态要不要变」，后者是「通信边界要不要拉出去」。两者都应该用可测的证据回答，而不是用架构品味回答。区别在于 A/B 对「协议」这个变量不好做 —— 这是我没有做这个实验的原因，也是它还是未落地项的原因。

再追问：那如果真要做，你的最小验证是什么？

A：我会先做**「假 Agent 服务」的最小实验** —— 一个进程暴露两个端点：返回能力声明、接收任务并返回任务标识，再加一个查进展的端点。不引任何协议库。 目的是先把「任务」的状态管理（受理 / 进行中 / 需补充输入 / 完成 / 失败）在自己的代码里跑一遍。跑完之后我才能判断「协议帮我省了什么」，而不是在没跑过的情况下先引一个依赖。
