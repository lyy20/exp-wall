手写一个 ReAct Agent（不依赖框架） ​

覆盖知识点：L4-04 ｜ 面试频率：高 ｜ 建议学时：6h

一句话说清 ​

一个完整的 ReAct Agent 只要 80 行左右：拿一个消息列表，调模型，如果模型给了工具调用就校验并执行、把结果追加回消息列表、再调一次；如果没有工具调用就直接返回答案。它不需要任何框架。真正的工作量不在「循环」上，而在循环外面那三件容易出事的小事：提示词里怎么说清工具契约、怎么解析模型的输出（它可能说谎）、怎么终止且不让副作用重复发生。能在一张白纸上写出这 80 行，是「我真的写过 Agent」和「我调过某个框架的 API」之间最短的分界线。

为什么必须学（面试官视角） ​

面试官对这条知识点的考察方式非常固定，几乎一定会让你当场写：

  • 白板题：「不用任何框架，写一个能查天气的 Agent。」——这一问筛掉的是所有只会 create_react_agent() 的人。因为你一旦用了框架，就永远没机会面对「工具 schema 怎么拼进请求」「结果怎么回填」「模型输出怎么解析」这三个真问题。
  • 框架原理题：你简历上写了 LangGraph。面试官接着问「StateGraph 帮你做了什么？」如果你的回答是「它帮我管理状态」，那是背文档；如果你能说「它就是我这 80 行外面套了一层：把循环变成了显式的图、把 state 变成了带 reducer 的字段、把终止条件变成了条件边」，那叫你真的懂。
  • 工程细节题：这一条几乎必然引出一个高频追问——「模型会不会给了工具调用但你没执行到？」 或者反向的**「模型会不会嘴上说要调工具、结构化字段却是空的？」**。答不出这一问，说明你只跑过 demo，没在生产里被模型坑过。
  • 简历信号：一个几十行、能跑、你自己写的 Agent 小样，在简历上比「熟悉 LangChain / LangGraph」这句话强得多。因为前者可以现场打开代码看，后者只能靠你自己说。

核心内容 ​

L4-04 手写一个 ReAct Agent（不依赖框架） ​

  • 定义：不依赖 Agent 框架，用原始模型 API + 一个消息列表 + 一个 for 循环实现 Thought → Action → Observation 的执行闭环。框架能做的事，用几十行代码都能做；手写一遍的目的是搞清楚框架替你承担了哪些契约。

  • 机制（分四块，每一块都有它自己的坑）：

    ① 工具契约：每个工具要交给模型三样东西——名字、参数 schema、自然语言描述。名字和 schema 决定能不能调对，描述决定该不该调。这一段在 工具定义规范 会展开，这里只给最小形态。

    python
    import json, time, uuid

# 工具 = 一个确定性函数 + 一份给模型看的说明。注意：模型只看得到说明，看不到代码。
def get_weather(city: str) -> str:
    """查询指定城市的当前天气。city 用中文城市名，例如「杭州」。"""
    # 真实实现里这里是一次 HTTP 调用；此处用确定性桩函数，便于自检
    fake = {"杭州": "阴，18℃", "北京": "晴，12℃"}
    return fake.get(city, f"未收录城市：{city}")

def now_time(tz: str = "Asia/Shanghai") -> str:
    """返回指定时区的当前时间（本地实现，仅用于演示）。"""
    return time.strftime("%Y-%m-%d %H:%M:%S", time.localtime())

# 注册表：一个 dict 就够。value 同时携带「给模型的说明」与「给程序的可调用体」。
TOOLS = {

            "name": "now_time",

    ② 提示词与上下文装配：system 里要写清四件事——身份、可用的工具边界、怎么算结束、失败了怎么办。最后一条最常被漏，但它决定了 Agent 卡住时是「换个办法」还是「原地重试到预算耗尽」。

    python
    # 伪代码：system 的骨架。真实项目里这段应该是常量文件，并且带版本号。
SYSTEM = """你是一个可以使用工具来回答问题的助手。

规则：
1. 需要外部信息时调用工具；不需要时直接回答，不要为了显得勤快而调用工具。
2. 一次可以调用多个互不依赖的工具。
3. 同一个工具用同样的参数调用过一次就不要再调——如果失败了，改参数或换工具。
4. 工具返回 ERROR 开头的内容表示这次调用失败，错误信息要读，不要忽略。
5. 信息已经足够时立刻给出最终答案，不要继续调用工具。"""

    ③ 循环与解析（本页最核心的一段）：这里的关键不是循环，是解析。有两类模型行为必须防：

    • 「说了没做」：模型在自然语言里写「我准备调用查询天气工具」，但结构化字段是空的。所以程序的判据必须以结构化字段为准，content 只用来展示。
    • content 可能是空串：带工具调用的那一轮，content 经常为空。任何 if reply.content.strip() 之外对它的字符串操作（比如 reply.content[0]、直接做正则提取）都会崩。
    python
    # 伪代码：循环骨架。llm() 与 reply 的字段形状以你选用的模型官方文档为准。
def stable_json(obj) -> str:
    return json.dumps(obj, sort_keys=True, ensure_ascii=False, separators=(",", ":"))

def run_agent(question: str, *, max_steps: int = 6, max_calls: int = 12) -> dict:
    messages = [{"role": "system", "content": SYSTEM},
                {"role": "user", "content": question}]
    schemas = [t["schema"] for t in TOOLS.values()]
    seen: set[str] = set()          # 绕圈检测：相同 (工具名 + 稳定序列化的参数)
    calls = 0

    for step in range(max_steps):                                    # 闸门 1：步数
        reply = llm(messages, tools=schemas)                         # 一次模型调用 = 一步

        tool_calls = getattr(reply, "tool_calls", None) or []        # 以结构化字段为唯一判据
        if not tool_calls:
            return {"status": "answered", "answer": reply.content or "", "steps": step + 1}

        messages.append(reply.to_message())     # 必须把「模型这一轮的意图」原样放回历史
        for call in tool_calls:
            calls += 1
            if calls > max_calls:                                    # 闸门 2：调用次数（并行会放大）
                return {"status": "budget_exhausted:calls", "steps": step + 1}

            name = call.name
            raw_args = call.arguments          # 注意：多数实现这是「JSON 字符串」而非 dict
            key = name + "|" + str(raw_args)
            if key in seen:                                          # 闸门 3：重复动作
                obs = f"ERROR: duplicate_call: {name} 用同样参数已经调过一次，请换策略"
            else:
                seen.add(key)
                obs = execute(name, raw_args)                        # 见下一段

            messages.append({"role": "tool",
                             "tool_call_id": call.id,                # 必须回填，否则下一轮对不上
                             "content": obs})

    return {"status": "budget_exhausted:step_budget", "steps": max_steps}

    ④ 执行与错误处理：这一段是「工程感」最集中的地方。三个决定：

    python
    # 伪代码
def execute(name: str, raw_args) -> str:
    if name not in TOOLS:                                            # ① 工具名白名单
        # 模型会编工具名。校验不过时要「告诉它有哪些」，而不是只说错了。
        return f"ERROR: unknown_tool: {name}。可用工具：{sorted(TOOLS)}"
    try:
        args = raw_args if isinstance(raw_args, dict) else json.loads(raw_args)   # ② 参数是 JSON 字符串
    except (TypeError, ValueError) as exc:
        return f"ERROR: bad_json: {exc}。请输出合法 JSON"
    try:
        # ③ 参数校验 + 执行；任何异常都变成观测，绝不向上抛
        return str(TOOLS[name]["fn"](**args))
    except TypeError as exc:
        return f"ERROR: bad_args: {exc}. 期望参数：{sorted(TOOLS[name]['schema']['parameters'].get('properties', {}))}"
    except Exception as exc:                                          # noqa: BLE001 —— 这里就是要兜住一切
        return f"ERROR: {type(exc).__name__}: {exc}"

    ERROR: 前缀不是装饰，是协议：模型需要一条稳定的规则来区分「观测是内容」和「观测是失败」。纯自然语言的错误描述会和正常内容混在一起，模型很容易把「未找到订单」当成一条正常的业务信息继续往下答。

  • 为什么这样设计（逐条给动机，这几条是面试官真正在听的）：

    • 为什么执行放在你的代码里而不是「让模型自己跑」：模型只能输出意图，这一点是机制的硬约束，不是框架的选择。把执行权留在程序里，你才可能在执行前后加校验、幂等、权限、确认这四道东西。
    • 为什么工具错误要变成观测而不是抛异常：抛异常会把整个会话打断，模型再没有机会改参数或换工具。变成观测之后，循环继续，但模型看得到错误——这是「自愈」和「崩溃」的分界。项目里的对应做法是「校验失败不炸图，错误作为工具结果写回 state」。
    • 为什么要有独立的绕圈闸：模型的默认本能是「失败了再试一次」。步数闸也能拦住它，但拦住的时候剩下的预算已经白烧完了。绕圈检测必须是一道独立的、更早的闸。
    • 为什么要 tool_call_id 回填：并行调用时一轮会有多个工具结果，如果没有 id，模型无法把「哪个结果对应哪个调用」对上。这是并行调用（下一页）能成立的前提。
    • 为什么 max_calls 和 max_steps 是两个闸：一次响应里可能有 3–5 个并行调用，所以「步数」和「实际执行的工具次数」不是一回事。只限步数，最坏情况下实际动作次数是步数 × 并行宽度。

  • 数量级与形状：

    • 代码规模：80–120 行（含工具桩）能写出可跑的版本；框架版通常需要 150 行以上，但换来持久化、断点、人工介入。
    • 一次会话的模型调用次数 = 循环轮数（常见 1–5）；工具执行次数 = 各轮工具调用数之和（并行会放大）。
    • 上下文增长：每轮追加「模型意图消息 + 每个工具结果」。工具结果是最不可控的一项——一条没治理的日志工具能在一步之内把上下文推到几万 token。

  • 常见误区：

    • 把「模型说要调工具」当成「模型调了工具」：判据必须落在结构化字段上。这一坑在真实项目里出现过：v1 处理未知工具与 tool_calls 位置时专门写了分支（graph/agent.py:604-610,625），就是为了防这类形状不对的输入。
    • 解析自然语言里的 JSON 当正路：在没有 Function Calling 的模型上只能这么做，但那是降级方案，必须配「解析失败 → 重试 / 换个 prompt」。把它当主路，解析失败率会成为你线上最大的错误来源。
    • 忘了把模型的意图消息放回历史：只回填工具结果、不记录模型那一轮说了什么，模型下一轮就不知道自己上次做了什么，会重复调用。
    • 工具错误直接 raise：整个 Agent 在第一次工具抖动时死掉。
    • 没有上限的 while True：这是最贵的故障形态。
    • 手写一遍之后就说「框架没用」：错的结论。手写的价值是让你知道框架承担了哪些契约——持久化、断点续跑、人工介入点、状态 reducer，这些手写一遍都不划算。

和你自己的项目对上号 ​

YYHelp v2（LangGraph 电商客服 Agent）：这个项目没有手写这 80 行——它用的是 LangGraph，而且明确不引入 langgraph_supervisor 预置组件，自己手搓 supervisor。这个取舍恰好是本页最好的话术素材：

  • 「框架帮你承担了哪些契约」可以直接指着说：StateGraph + 条件边替你承担了循环的显式化（循环从 for 变成图上的回环边）；state 的 reducer 矩阵替你承担了多轮状态怎么合并（哪些字段覆盖、哪些追加）；interrupt 一类机制承担了断点与人工介入。手写的 messages 列表做不到这三件事里任何一件。
  • 自己手搓 supervisor 的三条理由（supervisor.py:750）正是「懂原理才敢不用框架」的证据：① 预置组件本质是薄封装，阅读成本不低于自己写；② 重装一套等于是放弃已经验收过的可靠性资产；③ 多一个依赖就多一个版本风险面。这三条每一条都建立在对「框架到底做了什么」的真实判断上。
  • tool_calls 会骗人这件事，项目里有真实代码位置：v1 在处理未知工具与 tool_calls 位置上写了专门分支（graph/agent.py:604-610,625）。可以在面试里这样讲：「我在自己的循环里不信任 content，只信结构化字段；框架封装了调用，但这个信任边界是我自己定的。」
  • 「写下 ≠ 执行」是本项目最硬的一条工程教训，它和本页的「手写才知道哪些契约被承担了」是同一枚硬币的两面。v1 有 11 个 selftest 从未被 pytest 执行；v2 建了一个自检总闸，把 v1 14 条 + v2 16 条 = 30 条入口全部用 subprocess 跑起来。原话是：「代码的防护力 = 被执行的断言数，不是写下的断言数。一个从不执行的断言，防护力与『没有断言』完全相同——但它会让你以为有防护。这比没有更危险。」 这句话回答的是「你的 Agent 怎么保证不出事」，含金量远高于任何框架名词。
  • 配套的一条：「装配错误必须靠运行图来验」——手写的 for 循环没有这个问题（代码顺序就是执行顺序），但一旦换成图，「能 import、能编译、一跑就崩」就成了一个真实类别。细节见 Agent 是什么 与 规划与反思。

科研文献 RAG：这个项目没有 Agent 循环，所以 L4-04 在这个项目上没有落点。正确的处理不是硬套，而是主动说明补法：

  • 想补这一课，最省的做法是给现有 RAG 加一个工具化的检索器，然后手写这 80 行：把「混合检索」包成一个工具（入参 query 与 top_k），让模型决定调几次、要不要换查询词。这就得到了一个最小的 Agentic RAG，而且对照实验天然存在：固定单次检索 vs 模型自决检索次数，指标用 recall 与答案 faithfulness，判据是「召回提升显著且 token 增幅可接受」。这条补法同时覆盖 L3-28（Agentic RAG），一箭双雕。
  • 另一个更小的练习：把「引用编号越界检查」包成一个工具，让模型在给出答案前自己调一次校验。这样你能亲手验证一个判断——程序侧校验比模型自评可靠得多。

面试怎么问（≥3 组） ​

Q1：不用框架，写一个能调工具的 Agent。

A（要点）：四块，逐块说清：① 工具契约（名字 + schema + 描述，注册成一张表）；② 上下文装配（system 里要写清「怎么算结束」和「失败怎么办」）；③ 循环（调模型 → 看 tool_calls → 执行 → 回填 → 再调）；④ 执行与错误处理（白名单、JSON 解析、参数校验，错误变成观测而不是异常）。然后主动说出三道闸：步数上限、调用次数上限、(工具, 参数) 重复检测。

追问 1：你怎么判断模型到底有没有想调工具？

A：只看结构化字段，不看自然语言。模型完全可能输出一段「我准备调用查询天气工具」而字段是空的。所以我的判据是「tool_calls 非空才算要调工具」，content 只用于展示和日志。另外带工具调用的那一轮 content 常常是空字符串，直接对它做字符串操作会崩。

追问 2：那工具执行失败了呢？

A：不抛异常，把错误包成一段带 ERROR: 前缀的观测写回历史。这样循环继续，但模型能看到错误原文、能改参数或换工具。抛异常会把整个会话打断，模型连改的机会都没有。我们项目里的对应纪律是「校验失败不炸图，错误作为工具结果写回 state」。

追问 3：那它反复调用同一个工具怎么办？

A：一道独立的重复检测闸——相同 (工具名, 稳定序列化的参数) 第 2 次出现就拦，并把「你已经用同样参数调过、请换策略」写进观测。不能用步数闸兜底，因为步数闸拦住的时候剩下的预算已经白烧掉了。

Q2：你用了 LangGraph，那 StateGraph 到底帮你做了什么？

A（要点）：三层。① 循环的显式化：手写是 for 循环，图把它变成节点和回环边，好处是循环结构可以被打印、被断言、被画出来——这也是为什么「装配错误」在图里能被发现。② 状态的合并规则：手写时多轮状态怎么合是你自己 append 的事，图用 reducer 把它变成了声明式的字段契约（哪些字段覆盖、哪些追加）。③ 持久化与中断：checkpointer 保存图状态，支持断点续跑和人工介入——这两件事手写一遍非常不划算。

追问：那你为什么不直接用 langgraph_supervisor？

A：三条理由。预置组件本质是薄封装，读它的成本不比写一遍低；重装一套等于放弃已经验收过的可靠性资产；多一个依赖就多一个版本风险面。但我要说清边界：不用预置组件不等于不用框架——我仍然用 LangGraph 的图和 state，只是 supervisor 的判断逻辑自己写。

追问：手写循环和图循环，失败形态有什么不同？

A：手写的核心风险在解析与终止（模型说谎、忘了回填、没有上限）；图的核心风险在装配——比如条件边第三参的语义。我们踩过一次：add_conditional_edges(source, path_fn, path_map) 的第三参是「path_fn 返回值 → 目标节点」的映射表，我第一版让路由函数返回节点名、却把出口名表当 map 传进去，结果 KeyError: 'agent_memory'。它能 import、能编译，纯函数单测测不出它，因为路由函数本身是对的，错的是它和 map 的契约。

Q3：你说你手写过，那手写的版本缺什么？

A（要点）：缺四样——① 持久化：进程一挂，整条会话的历史就没了；② 断点续跑：长任务中途要能停、能恢复，手写要自己存快照；③ 人工介入点：高风险动作要能挂起等人确认，这需要「暂停—序列化—恢复」的完整机制；④ 可观测：手写版通常只 print，没有 trace、没有 span，事后归因全靠猜。这四样正是框架值钱的地方。

追问：那你手写一遍图什么？

A：图的是知道哪些契约被框架承担了、哪些还在我手上。最典型的是「工具执行前必须校验、必须幂等」这条——框架可以帮你调用，但不能替你决定信任边界。第二是知道「写下 ≠ 执行」：我在 v1 里发现 11 个 self-test 从未被 pytest 执行，v2 补了一个总闸把 30 条入口全部真跑起来。代码的防护力等于被执行的断言数，不是写下的断言数。

追问：为什么「没被执行的断言」比「没有断言」更危险？

A：因为没有断言时你知道自己在裸奔，有未执行的断言时你以为自己有防护——它会让你跳过本该做的验证，也让 code review 的人放过这段代码。所以修法不只是补执行，还要防覆盖被静默删掉：参数化测试是从清单读条目的，把一条从清单里删掉，测试只会「少跑一个用例」而不是变红。所以我对关键的 MCP 自检入口额外写了一条点名断言，清单里少了它就直接失败。
