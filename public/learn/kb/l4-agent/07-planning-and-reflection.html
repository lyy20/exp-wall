规划与任务分解、反思与自我修正 ​

覆盖知识点：L4-15 L4-16 ｜ 面试频率：高 ｜ 建议学时：7h

一句话说清 ​

规划和反思是同一个循环的两半：规划决定「先做什么后做什么」，把一个大任务拆成可执行的步骤；反思检查「刚才做出来的东西够不够好」，不行就带着具体意见重来一次。两者的共同点是都会增加一次模型调用，所以它们的价值都必须用「多花的这一轮换来了什么」来证明，而不是用「听起来更聪明」来证明。还有一个更硬的共同点：规划和反思都是「回环」——只要有回环，就必须有闸；而闸写在图上的位置会决定它能不能被绕过去。装配错误是这一页最实战的部分：它在类型检查、导入、纯函数单测里全都隐形，只有在真正跑起来的那一刻才暴露。

为什么必须学（面试官视角） ​

  • L4-15 是「你会不会指挥模型」的考题。 面试官问「复杂任务怎么规划」，想听的不是「我用 CoT 让它分步」——那是 L2 的内容。他要听的是工程上的三个判断：规划粒度多大（太细上下文爆炸、太粗每步都在猜）、什么时候重规划（环境变了还是计划本身错了）、计划用什么形状承载（自然语言列表 / 结构化字段 / 图结构）。
  • L4-16 是「你知不知道反思的成本」的考题。 反思是简历上最常见的过度包装点：「我加了反思机制，效果提升了 X%」。面试官的下一个问题是「反思一次多少钱、几秒、最多反思几次、反思自己错了怎么办」。答不出上限和收敛性，就说明你没真的跑过。
  • ⭐ 本页最值钱的一条实战经验（也是最好用的面试素材）」：装配错误必须靠运行图来验。 这是一个只有实现过图编排的人才会踩的坑：add_conditional_edges(source, path_fn, path_map) 的第三个参数是**「path_fn 的返回值 → 目标节点」的映射表**，不是别的。第一版让 route_by_exit 返回节点名，却把 EXIT_TO_NODE 当成 map 传进去——于是 path_fn 返回 "agent_memory"，而 map 的键是别的字符串，KeyError: 'agent_memory'。这个东西能 import、能编译、纯函数单测测不出它，一跑就崩。这条经验把「测试策略」从「写单测」升级到「按故障类型选验证层级」，在面试里非常吃香。
  • 接上一条的纪律：每一个回环边都要有自己的闸。只在一侧检查，另一侧就是一个能绕过去的循环入口。 这句话的适用面远远超出 LangGraph——任何带回环的系统（重试、重规划、重试工具调用）都有同样的漏洞。能主动说出这句话的人，通常真的被它咬过。

核心内容 ​

L4-15 规划与任务分解（Planner） ​

  • 定义：把用户的一个复合目标拆成有序的子步骤，再逐步执行。规划器可以是一个独立的模型调用（先产出计划再执行），也可以是「边走边定」（每一步只决定下一步）——这两种是不同的架构，不是同一个东西的不同参数。

  • 机制（两条路线 + 一个重规划触发条件）：

路线形状优点缺点
先规划后执行（Plan-and-Execute）一次产出 N 步，逐条执行全局可见、可人工审阅、可预算（步数一开始就知道）计划一旦错了，整条路都错；环境变化后计划过期
边走边定（ReAct 式）每步只决定下一步对变化适应好、实现简单无全局视图、容易绕圈、步数预算只能在运行时封顶

现实中的成熟做法通常是混合：先出一个粗粒度计划（3–5 步），执行时允许局部重规划。触发重规划的典型条件：某一步连续失败、工具返回显示前提不成立（例如「订单不存在」意味着后续「查物流」没有意义）、上下文或预算接近上限。

  • 为什么这样设计：

    • 为什么规划粒度不能太细：每一步都要带上「任务 + 已完成步骤 + 当前状态」去请求模型，计划越细，每步的上下文越长、总轮数越多。一个 20 步的细计划，实际开销远大于「3 步粗计划 + 每步内部用代码/工具做细节」。判断标准很实际：如果一步可以被一个工具调用直接完成，它就不该是一个「计划步骤」，它就是那次调用。
    • 为什么规划粒度不能太粗：一步如果你说不清「这一步成功的样子是什么」，那它就不是一个可执行的步骤，而是一个愿望。可验证性是步骤定义的硬要求——「收集信息」不是步骤，「查到订单状态」是步骤。
    • 为什么计划要用结构化形状承载：自然语言列表可以被人读，但不能被程序用。结构化的计划（每个步骤有名称、状态、结果）才支持：按步骤记 trace、对某一步重试、跳过已完成的步骤、统计每一步的耗时与 token。这直接决定了你能不能回答「哪一步最贵」这个问题。
    • 为什么要有独立的重规划判断：「计划错了」和「执行失败」是两种不同的故障。执行失败重试一次就够；计划错了（前提不成立）重试只会继续错。把两者混成一个重试计数器，会出现「在一个错误前提上重试三次」的浪费。

  • 数量级与形状：

    • 计划的步骤数在上限约束下通常落在个位数（项目的真实取值是 PLAN_MIN_STEPS = 2 / PLAN_MAX_STEPS = 3，见下）。步数上限是预算的一部分，不是建议值。
    • 一次规划调用的额外成本 ≈ 一次完整模型调用（生成计划）+ 每个步骤上下文中多出的计划文本。所以规划在小任务上是纯亏——这也是要有一个「这个任务需不需要规划」的前置判断的原因。
    • 计划步骤的完成率与平均步数是两个必记的指标：步骤数分布是长尾时，说明任务复杂度差异大，固定步数上限可能过紧。

  • 常见误区：

    • 所有任务都先规划：给「查一下订单」这种单步任务套一个规划器，多花一轮模型调用，收益为零。
    • 计划生成后不校验：模型可能生成一个引用不存在工具的步骤，或者把同一个动作排两遍。计划本身也要过校验（工具名是否在白名单里、步数是否超上限）。
    • 重规划时不丢弃旧计划的结果：新计划应当继承已完成的观察，否则会重复执行已经有结果的步骤。
    • 没有「计划失败」的出口：规划器产不出合法计划时（步数超限、格式不合），必须有降级路径（例如退化成单步 ReAct），而不是直接报错。
    • 把计划写进 system prompt 期望模型自己守：计划是程序要读的数据，不是提示词。

L4-16 反思与自我修正循环 ​

  • 定义：在产出候选答案之后，增加一个评审步骤（可以是同一个模型换一个提示，也可以是一个独立的评审断言/检查器），根据评审意见决定「通过」还是「带着意见重做」。它是质量换成本的交易。

  • 机制（三个部分：何时触发、谁评审、怎么收敛）：

部分选项说明
触发条件每次必反思 / 按条件触发（结果为空、工具报错、置信度低）每次必反思 = 成本翻倍；按条件触发需要判据是显式规则
评审者同一模型换角色提示 / 独立模型 / 确定性检查器（断言、schema 校验、引用是否可核对）确定性检查器最便宜也最可靠，能用就该先用
收敛固定重试上限 / 改进停滞检测（分数不再提升就停）必须有上限，且上限是预算不是质量旋钮

  • 为什么这样设计：

    • 为什么必须有重试上限：反思循环是回环，而回环如果没有闸就是无限循环。更隐蔽的是：反思的每一步都比普通步骤贵（要带上已有答案和评审意见，上下文更长）。所以上限不是「防止极端情况」的保险，而是主路径上的成本控制。
    • 为什么上限设成 1 常常是对的：第 2 次反思的边际收益通常远低于第 1 次——第 1 次能修的是明确缺陷（漏了引用、格式不对、答非所问），第 2 次之后模型往往只是在换一种说法，而不是真的变好。所以「上限 1」不是偷懒，是**「在没有证据表明第 2 次有收益之前选小值」**这条通用纪律的应用。
    • 为什么优先用确定性检查器做评审：它有两个决定性优势——成本近乎零、判定可复现。能用断言表达的评审（引用编号是否都能在原文里找到、结构化字段是否齐全、数值是否在合理范围）不要交给模型。模型评审留给「语义质量」这一类无法用规则表达的问题。
    • 为什么反思意见必须结构化：只给模型一句「再改进一下」，它会重写一遍全文而不知道改哪；给出「缺了引用编号」「第 3 步的结果没有被用上」这类具体缺陷项，它才会做局部修复。局部修复的 token 成本和引入新错误的风险都远低于重写。
    • 为什么反思本身也可能错：模型可能提出错误或过度的修改意见（把对的改成错的）。所以上限不只是成本控制，也是错误抑制——上限越小，被错误意见带偏的机会越少。这也是「反思需要评测」的原因。

  • 数量级与形状：

    • 反思使单次任务成本大约乘以 (1 + 反思次数)（每次反思是一次完整生成）。所以「反思 1 次」= 大约翻倍，「反思 3 次」≈ 4 倍。
    • 合理的重试上限在个位数以内，且实践中 1 或 2 已经覆盖绝大多数可修缺陷。
    • 必记的两个指标：触发反思的比例（太高说明首次生成质量差，该修的是提示或工具，不是加反思）与反思后的改进率（反思了很多次但改进率低 = 纯浪费）。

  • 常见误区：

    • 反思没有上限，或者上限靠 prompt 里的「最多两次」——模型的服从性不是闸，程序里的计数器才是闸。
    • 把反思当质量旋钮：「效果不好就多反思几次」——它更常见的结果是更慢、更贵、更啰嗦。
    • 反思意见不落到 state：模型下一轮看不到自己上次的评审意见，于是重复同样的错。
    • 反思和主循环共用同一个上下文预算：反思会让上下文更长，如果总预算不变，反思反而会挤掉正常步骤的空间。
    • 用反思代替修根因：如果首次生成的失败集中在某一类（比如总是漏引用），正确动作是修提示或加确定性校验，不是让反思去救。反思救的是「长尾缺陷」，不是「系统性缺陷」。

和你自己的项目对上号 ​

YYHelp v2（LangGraph 电商客服 Agent）：这一页的两个知识点在你项目里的形态很特殊——规划在 v2 里被弱化了，而反思有真实的上限常量，另外还有一条全层最硬的实战经验。

  • L4-15 规划（真实口径要如实说）：v2 没有引入独立的 PlannerAgent。项目里确实存在规划相关的模块与常量——PLAN_MIN_STEPS = 2 / PLAN_MAX_STEPS = 3（plan.py:132/135）——但 v2 的主路径是「supervisor 路由 + 专家 ReAct」：supervisor 看用户请求后决定派给哪个专家（或直接回答），每个专家在自己的域内用 ReAct 逐步完成。也就是说，「规划」在这个系统里被落成了「路由决策 + 专家内的局部循环」，而不是「先生成一份 N 步计划再逐条执行」。
    • 为什么这是一个合法的设计：因为客服场景的任务结构是浅的——绝大多数请求一步就能完成（9 条可见性探针全是单域；实测 40 题里分派轮次均值 1.075，37 题 1 轮、3 题 2 轮）。给这种任务形状套一个通用 Planner，成本（每次多一轮模型调用）确定，收益是零。这正是「规划粒度不能太细 / 小任务上规划是纯亏」那两条判断的实例。
    • 面试里怎么讲：不要声称「我做了 Planner」。正确说法是：「我的任务是浅结构的，所以我用路由 + 局部 ReAct 代替了通用 Planner；我保留了 PLAN_MIN_STEPS=2 / PLAN_MAX_STEPS=3 这组上界作为计划长度约束，但主路径不走它。决定不上 Planner 的依据是分派轮次均值 1.075 这个数——95% 的请求一轮就收尾，规划器在这一层是纯开销。」用数据说明你不做什么，比声称你什么都做了更有说服力。
  • L4-16 反思（有真实上限，可直接引用）：REFLECT_MAX_RETRIES = 1（state_v2.py:593）。上限是 1 这件事本身就是话术：它的依据正是本页那条——「在没有证据表明第 2 次有收益之前选小值」，而且反思的每一步都要带上已有答案与评审意见，上下文更长、成本更高。同一个项目里 supervisory 层也有同构的纪律：DISPATCH_LIMIT = 2（supervisor.py:199），依据之一是「分派次数是单调递增计数器 budget.steps，到上限强制 finalize（source="quota"）」——闸是程序里的计数器，不是提示词里的请求。
  • ⭐ 全层最硬的一条实战经验：装配错误必须靠运行图来验。 项目里第一版 build.py 犯了 add_conditional_edges(source, path_fn, path_map) 的经典错误：
    • 第三参的语义是「path_fn 的返回值 → 目标节点」的映射表。
    • 第一版让 route_by_exit 返回节点名（例如 "retrieve"），却把 EXIT_TO_NODE 当成 map 传进去。于是 path_fn 返回 "agent_memory" 这个节点名，而表里的键是别的字符串（退出码一类），查不到 → KeyError: 'agent_memory'，报错形态是 During task with name 'triage' and id 'a06e0b0c-...'。代码位置：code/yyhelp/graph/build.py:149-176。
    • 它为什么难发现：能 import、能编译、一跑就崩，纯函数单测测不出它——因为 route_by_exit 自身是纯函数，单独调用它返回一个合法字符串，测试全绿；错的是它和图的连接方式，而图的连接在编译期不校验。
    • 结论与验收动作：装配错误必须靠「运行图」来验。 落地成两种可执行的验收：① 图结构断言——把决策表（path_fn 可能返回的所有值）与 add_conditional_edges 实际注册的键做集合比对，差集非空即失败；② 运行冒烟——编译后的图真跑一个跨域请求，覆盖至少一条非默认分支。
    • 配套纪律（ADR-1 原话）：「每一个回环边都要有自己的闸。只在一侧检查，另一侧就是一个能绕过去的循环入口。」 项目里落实为 protect 检查——memory → __end__ 与 reflect → __end__ 这两条边曾经错连，如果只在回环的一侧设闸，另一侧就是绕过闸的入口。
    • 面试里怎么讲这条：这是本页最值得讲的一个故事，因为它同时展示了三件事——你踩过真实的坑、你能把它抽象成「按故障类型选验证层级」的方法论、你把它变成了可执行的验收动作而不是一句经验。

科研文献 RAG：这个项目没有规划器与反思循环（它是固定的检索—重排—生成三段链路，没有回环），但有一条同构的、而且已经修好的教训：

  • 「编译通过 ≠ 装配正确」在 RAG 里同样是真命题。这个项目的引用编号链路上出过一个真实缺陷：["1","2"] 这种形态被静默丢弃成 citations=[]，而校验函数返回 True 说「校验通过」——链路的接线正确、每个环节单测全绿、只有端到端跑起来才看得到理由是空的。这和 add_conditional_edges 装配错误是同一个故障类型：每一个零件都对，组合起来错，而组合的错误不在任何单测的覆盖范围内。
  • 可直接迁移的方法论：按故障类型选验证层级——纯函数算错 → 单测；接线/装配错 → 端到端 smoke + 结构一致性断言；模型输出不稳定 → 评测集。面试里把两件事并起来讲：「我的判断是单测覆盖不了『组合错误』，所以我对装配类缺陷一律加一条端到端冒烟，并且会写结构断言（决策表 vs 注册表、引用编号 vs 原文）去把『静默通过』变成『显式失败』。」

面试怎么问（≥3 组） ​

Q1：复杂任务你怎么做规划？

A（要点）：先判断要不要规划，再决定路线。单步能完成的任务不规划——套一个规划器就是多花一轮模型调用、收益为零。复合任务上，先规划后执行和边走边定是两种架构：前者全局可见、可预算（步数一开始就知道），但计划错了整条路都错；后者适应变化好、实现简单，但没有全局视图、容易绕圈。成熟做法通常是混合：粗粒度计划 2–3 步 + 执行中允许局部重规划。步骤定义有一条硬要求：可验证性——「查到订单状态」是步骤，「收集信息」是愿望。

追问 1：计划做多细？

A：粒度太细，每一步都要带上「任务 + 已完成步骤 + 当前状态」去请求模型，上下文和轮数一起涨；太粗则每步都在猜。我的判断标准很实际：如果一步能被一个工具调用直接完成，它就不该是一个计划步骤，它就是那次调用。 另外计划要用结构化形状承载而不是自然语言列表——自然语言能被人读，不能被程序用；结构化的计划才能按步骤记 trace、对某一步重试、统计哪一步最贵。

追问 2：什么情况下重规划？

A：要让「计划错」和「执行失败」分开，否则会出现「在一个错误前提上重试三次」。触发重规划的典型信号是前提不成立——工具返回「订单不存在」，后续「查物流」就没有意义了，这不是重试能救的。还有连续失败、以及预算接近上限。

追问 3：你自己项目用了 Planner 吗？

A：没有，而且我有数据支撑这个决定。我的任务是浅结构的：实测 40 题里分派轮次均值 1.075（37 题 1 轮、3 题 2 轮），9 条可见性探针全是单域请求。所以我用路由决策 + 专家内局部 ReAct 代替通用 Planner。给这种任务形状套规划器，成本确定（每次多一轮模型调用）、收益是零。我是用数据说明不做什么，不是不会做。

Q2：你的反思机制怎么设计的？

A（要点）：三个部分。触发条件——不是每次必反思，而是按规则触发（结果为空、工具报错、确定性检查不过）。评审者——能用确定性检查器就绝不用模型：断言、schema 校验、引用是否可核对，这些成本近乎零且判定可复现；模型评审只留给无法用规则表达的语义质量问题。收敛——REFLECT_MAX_RETRIES = 1：闸是程序里的计数器，不是提示词里的「最多两次」，模型的服从性不构成闸。

追问：为什么上限是 1？

A：两个理由。① 边际收益：第 1 次反思能修的是明确缺陷（漏引用、格式不对、答非所问），第 2 次之后模型往往只是在换一种说法，不是真的变好。② 成本形状：反思是一次完整生成，而且上下文更长（要带上已有答案和评审意见），所以反思 1 次大约翻倍，反思 3 次接近 4 倍。这两条合起来就是那条通用纪律：在没有证据表明第 2 次有收益之前选小值。

追问：反思意见怎么写才有效？

A：必须结构化成具体缺陷项，不能给一句「再改进一下」——那样它会重写全文而不知道改哪。给出「缺了引用编号」「第 3 步的结果没有被用上」这类具体项，它才会做局部修复。局部修复的 token 成本和引入新错误的风险都远低于重写。而且反思意见必须落进 state，否则下一轮它看不到自己上次被批评了什么，会重复同样的错。

追问：反思会出错吗？

A：会，可能提出错误或过度的修改意见（把对的改成错的）。所以上限同时也是错误抑制——轮次越少，被错误意见带偏的机会越少。另外两个必看的指标是：触发反思的比例（太高说明首次生成质量差，该修的是提示或工具，不是加反思）和反思后的改进率（反思很多次但改进率低就是纯浪费）。反思救的是长尾缺陷，不是系统性缺陷。

Q3：你怎么验证一个 Agent 图编排是对的？

A（要点）：按故障类型选验证层级，不能一律写单测。我说一个真踩过的坑：add_conditional_edges(source, path_fn, path_map) 的第三参是「path_fn 的返回值 → 目标节点」的映射表。我第一版让 route_by_exit 返回节点名，却把另一张表当成 map 传进去，于是 KeyError: 'agent_memory'，报错形态是 During task with name 'triage' and id 'a06e0b0c-...'。

追问 1：为什么单测没发现？

A：因为能 import、能编译、纯函数单测全绿，一跑就崩。route_by_exit 自己是纯函数，单独调用它返回一个合法字符串，测试通过；错的是它和图的连接方式，而图的连接在编译期不校验。这是「组合错误」——每一个零件都对，接起来错，而任何单测的覆盖范围里都不包含『接线』。

追问 2：那怎么验？

A：两条，都可以写成自动化。① 图结构断言：把决策表（path_fn 可能返回的所有值）与 add_conditional_edges 实际注册的键做集合比对，差集非空即失败——这等于把「静默的 KeyError」提前成显式失败。② 运行冒烟：编译后的图真跑一个跨域请求，覆盖至少一条非默认分支。核心结论一句话：装配错误必须靠运行图来验。

追问 3：还有什么类似的坑？

A：回环边的闸。我们的 ADR 里有一条原话：「每一个回环边都要有自己的闸。只在一侧检查，另一侧就是一个能绕过去的循环入口。」 项目里 memory → __end__ 和 reflect → __end__ 这两条边曾经错连——如果只在回环的一侧设闸，另一侧就是绕过闸的入口。这条纪律的适用面超出 LangGraph：任何带重试、重规划、重调工具的系统都有同样的漏洞。 还有一个同构的例子在我的 RAG 项目里：引用编号的校验函数对 ["1","2"] 这种形态返回 True 说校验通过，实际引用被静默丢成空——一个总能通过的校验函数，等于没有校验；判据是「能不能构造出一个让校验失败的用例」。
