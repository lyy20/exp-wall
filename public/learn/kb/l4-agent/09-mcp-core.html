MCP 协议：架构、传输层、授权与安全 ​

覆盖知识点：L4-19 L4-20 L4-21 ｜ 面试频率：高 ｜ 建议学时：12h

一句话说清 ​

MCP（Model Context Protocol）要解决的是一件事：把「模型能用哪些工具、能读哪些数据」从「写死在某个 Agent 进程里的 Python 函数」，变成「一个跨进程、跨语言、可独立部署的服务」。它的架构是 host / client / server 三层，消息是 JSON-RPC，能力在握手阶段协商；传输层只有两大类（本地 stdio 与远程 HTTP）；授权与安全是它从「玩具」升级到「企业内可用」的门槛。这一页讲清架构、传输与安全三块，下一页（MCP 服务端与客户端实践）讲怎么把它写出来。

为什么必须学（面试官视角） ​

2026 年的 Agent 岗 JD 里，MCP 的关键词密度已经和 RAG、Function Calling 同级。面试官问 MCP 通常不是考你「知不知道有这个东西」，而是用三个层次筛人：

  1. 第一层（会背）：「MCP 是什么？」—— 只答「让模型连工具的协议」是及格线，答不出 host/client/server 三层与 tools/resources/prompts 三原语，基本就停在「看过二手博客」。
  2. 第二层（做过）：「你写过 MCP server 吗？跟直接写 @tool 有什么区别？」—— 这题在筛你有没有真的跨过一次进程边界。没跨过的人只会说「MCP 更通用」，跨过的人能说出反序列化边界、子进程环境、生命周期管理这些具体代价。
  3. 第三层（判断力）：「那你的项目为什么不把所有工具都上 MCP？」—— 这是分水岭。这题没有标准答案，但答「MCP 更先进所以都该上」的人会被判为只会跟风、不会做取舍；答出「MCP 的价值前提是跨消费者复用，单消费者上 MCP 是负收益」的人会被记为「有工程判断」。

所以这一页的学习目标不是「知道 MCP」，而是能在三层追问下讲清「我用它、也在它该停的地方停下来了」。

核心内容 ​

L4-19 MCP 协议：架构与核心概念 ​

  • 定义：MCP 是一个开放协议，规定「AI 应用」与「外部能力提供方」之间如何发现能力、调用能力、交换上下文。它不是模型的一部分，也不是某个框架的一部分 —— 它是进程之间的接口。

  • 机制：三层角色，各自职责不能混：

角色是什么关键职责常见误解
Host用户实际在用的那个应用（IDE 插件、桌面 Agent、你的客服 Agent 服务）拥有会话、拥有权限决策、拥有模型调用权以为 host 等于「服务器」—— 它是客户端侧的应用
ClientHost 内部为每一个 server 维护的连接器建立连接、握手协商、发请求、收响应、管生命周期以为是「多个 client 连一个 server」 —— 通常一个 client 对一个 server，一个 host 可以有多个 client
Server能力提供方（可以是本地子进程，也可以是远程服务）暴露 tools / resources / prompts，执行并返回结果以为 server 必须联网 —— stdio server 就是一个本地子进程

把这三层记牢的实用价值：面试官问「多接几个 MCP server 是什么形态」，你能立刻答出「host 里会有多个 client，每个 client 一条独立连接、独立握手、独立生命周期」，而不是含糊地说「就连过去」。

  • 机制：三类原语（primitives），谁调用谁决定：
原语语义由谁决定调用典型例子
Tools可执行的动作，可能有副作用模型决定调不调、传什么参search_kb(query, top_k)、create_ticket(...)
Resources可读取的数据/上下文应用决定什么时候读进来一份订单 JSON、一段知识库文本、一个文件
Prompts可复用的提示模板用户主动选择「用客服口径总结这段对话」这类预设模板

这个「谁调用谁」的分工是 MCP 最有设计感的地方，也是最常被答错的地方。 面试如果只允许你用一句话说清三者的区别，就说这句：「tools 是模型拉的、resources 是应用拉的、prompts 是用户点的。」很多人会把 resources 说成「模型读的数据」——那它就退化成另一种 tool 了，失去了「应用侧可控注入」的意义。

  • 机制：消息是 JSON-RPC，能力在握手阶段协商：MCP 的线上消息是 JSON-RPC 2.0 风格的请求 / 响应 / 通知三元组。连接建立后第一件事是初始化握手：双方各自声明自己支持哪些能力（capabilities），然后才进入正常调用。这意味着：

    • 一个只实现了 tools 的 server 是完全合法的 —— 它只要不声明 resources/prompts 能力即可；
    • 客户端也不能假设 server 有什么，必须先看声明再调用；
    • 能力协商是双侧的，client 也要声明自己能接受什么。

    ⚠️ 具体的方法名、字段名、能力字段的拼写以官方文档为准，本页不列。不同协议版本之间这些细节有变更，背一个错的字段名比不背更糟。

  • 为什么这样设计（三个反直觉的取舍）：

    1. 为什么不用 REST，要用 JSON-RPC？ 因为要支持双向通信：server 也能向 client 发请求（例如申请更多信息、请求用户确认）。REST 的请求-响应单向模型要表达这个得额外造机制。
    2. 为什么要有「能力协商」而不是「有个能力清单文档」？ 因为 server 是跨版本部署的，写死清单会在版本不匹配时静默失败；协商把不匹配变成握手期的显式失败，早失败好过晚出错。
    3. 为什么把 resources 和 tools 分开，而不是「读也是一种 tool」？ 因为读和写的权限模型不同。读取可以被应用侧预先决定并缓存、可以批量预取、可以由用户配置允许范围；而工具调用是运行时的、动态的、可能有副作用。分开之后，企业才能在策略层写「允许这个 Agent 读这些资源，但不允许它调用任何写工具」。

  • 数量级与形状：

    • 连接的建立是有状态的，不是每次调用重新握手（stdio 尤其明显 —— 握手 = 启动一个子进程，代价在百毫秒级）；
    • 一个 host 连接 N 个 server 时，工具清单是所有 server 声明工具的并集 —— 这就直接引出工具过多后的路由问题（见 工具选择与路由）；
    • server 返回的 content 是列表，不是单值 —— 这一条会在下一页用真实代码再讲一遍，因为它是新手实现里最常见的崩溃点。

  • 常见误区：

    • 把 MCP 说成「一个大模型工具标准」—— 它和模型无关，模型只看见工具定义，看不见协议；
    • 把 MCP 和 LangChain 的 Tool 抽象混为一谈（对比见 框架横向对比）；
    • 以为「用了 MCP 就不用写工具描述了」—— 工具描述质量仍然决定调用成功率（见 工具定义规范），MCP 只是换了传输方式。

L4-20 MCP：传输层（stdio / Streamable HTTP） ​

  • 定义：传输层规定 client 与 server 之间的字节怎么走。MCP 把传输抽象成接口，同一套协议消息可以跑在本地子进程上，也可以跑在 HTTP 上。

  • 机制：两类传输的形态差异：

stdioStreamable HTTP
连接对象本地子进程远程（或本机）HTTP 服务
谁启动谁client 负责拉起 server 进程server 自己跑着，client 连上去
生命周期与 client 进程绑定（子进程）独立，多个 client 可共连
适合场景本地工具、个人开发、隐私数据不出机平台化的工具服务、多消费者复用、容器化部署
主要代价子进程环境要手动传对；进程管理复杂需要 HTTP 基础设施；鉴权与多租户要自己做

⚠️ 历史上还存在过一种基于 SSE 的双端点形态（两个端点，一个长连接推送 + 一个接收）。哪种传输是当前推荐、哪些已被标记为不再推荐，以官方文档为准，本页不声称任何传输的引入或废弃版本。

  • 机制：stdio 的「子进程边界」才是真正的难点。很多人以为 stdio 比 HTTP 简单，实际相反 —— stdio 难在你同时管了三个资源：子进程、读流、写流。这三个必须同生共死。真实项目里踩过的四种错法，症状全部不指向根因：
写错的姿势症状会误导你往哪查
不显式关闭就退出Task was destroyed but it is pending、子进程残留以为是 async 代码写错
在 async with session 外访问 sessionClosedResourceError以为是 server 挂了
用 asyncio.run() 包了两层RuntimeError: Event loop is closed以为是 SDK 的 bug
自己写 try/finally 关三个资源漏关其一，且漏哪个不确定完全查不出来，只是偶发失败

正确写法是用 contextlib.AsyncExitStack 把三者压进同一个栈，退出时逆序统一释放。这是「同一个栈 = 同生共死」的工程化表达：

python
import contextlib, sys
from mcp import ClientSession, StdioServerParameters
from mcp.client.stdio import stdio_client

async def open_session():
    """返回 (stack, session)：调用方负责 await stack.aclose()。"""
    stack = contextlib.AsyncExitStack()
    params = StdioServerParameters(
        # 关键一：用 sys.executable，不要用裸 "python"
        command=sys.executable,
        args=["-m", "yourpkg.mcp.server"],
        env={
            # 关键二：子进程的编码必须显式指定（Windows 控制台是 GBK）
            "PYTHONIOENCODING": "utf-8",
            # 关键三：子进程要能 import 到你的包
            "PYTHONPATH": "D:/proj",
        },
    )
    read, write = await stack.enter_async_context(stdio_client(params))
    session = await stack.enter_async_context(ClientSession(read, write))
    await session.initialize()
    return stack, session

  • 为什么这样设计（三条判据，都能迁移到别的场景）：

    1. 「三个资源必须同生共死」 —— 任何一对多资源的管理，都应该问一句「它们是不是生命期绑定」。是，就用栈 / 上下文管理器，不要手写。
    2. 「宁可显式传环境，不要隐式继承环境」 —— stdio 子进程继承的环境是不确定的（不同 shell、不同 IDE、Windows 与 WSL 各不一样）。把 PYTHONIOENCODING、PYTHONPATH、command 显式写死，报错就从「server 崩了」变成「可复现的配置问题」。 真实症状举例：不设 PYTHONIOENCODING 时，子进程里打印一个中文或 ✓ 会 UnicodeEncodeError，而报错出现在子进程的 stderr，看起来完全像 server 自己崩了 —— 你会去查 server 代码，其实问题在 client 传的环境。
    3. 「能 import、能编译 ≠ 能跑」 —— 跨进程边界的装配错误只有真跑一次才会暴露（这条教训在 LangGraph 那页还会出现一次，见 LangGraph 状态图）。

  • 机制：远程 HTTP 路径上必须设的超时。stdio 的子进程如果挂住，你能 Ctrl+C；远程 HTTP 请求挂住，脚本会永不退出。所以远程验证脚本至少要两个超时：

    • 就绪超时（等服务起来）：项目实测取值 READY_TIMEOUT_S = 15.0（yyhelp_v2/mcp/transport_check.py:72）；
    • 调用超时（单次工具调用）：CALL_TIMEOUT_S = 20.0（yyhelp_v2/mcp/transport_check.py:73）。

    口径说明：这两个数是该项目的实测选择，依据是「本地起 uvicorn + 一次往返应该在秒级完成，15s/20s 已经是很宽的容错」，不是通用标准值。

  • 常见误区：

    • 以为 stdio 就是「本地所以更快更简单」—— 它只是省了网络，子进程管理的复杂度是净增的；
    • 远程传输写成「没有超时」，本地跑得通、CI 里偶发挂死；
    • 把传输层当成实现细节不写日志 —— 传输层的失败信息量最大，静音日志（见下一页）时要把开关留出来。

L4-21 MCP：授权与安全 ​

  • 定义：MCP 的授权讨论的是「远程 server 如何确认调用方有权限」，以及「跨进程边界后，原来在进程内的那些安全假设哪些失效了」。

  • 机制：远程场景的授权链路（概念层，不背字段名）：

mermaid
flowchart TD
  A["Host 应用"] -->|"① 尝试调用受保护的 server"| B["MCP Server"]
  B -->|"② 未授权：返回授权需求"| A
  A -->|"③ 走标准 OAuth 授权码流程"| C["授权服务器<br/>Authorization Server"]
  C -->|"④ 用户同意 / 拒绝"| A
  A -->|"⑤ 用拿到的令牌访问"| B
  B -->|"⑥ 校验令牌：签名、受众、有效期、scope"| D{"令牌是否<br/>为这个 server 签发"}
  D -->|"否"| E["拒绝：令牌受众不匹配"]
  D -->|"是"| F["执行并返回"]

概念解决的问题
OAuth 2.1 授权码流程用户不必把密码交给 Agent —— 授权与凭证分离

PKCE公共客户端（桌面 / CLI）不能安全保存密钥，用一次性挑战代替

⚠️ MCP 各版本在授权细节上有演进（谁做授权服务器、发现机制怎么走、是否支持某些扩展）。具体流程与参数名以官方文档为准，本页只讲「为什么需要这些概念」，不声称任何能力在哪个版本首次引入。

  • 为什么这样设计：因为 MCP 让工具从「同进程函数」变成「任何能连上来的进程都能调」。原来写在同一份代码里的信任关系消失了，必须以协议层的方式重建：谁能调、能调哪些、令牌给谁用 —— 全部要在协议里表达，而不是靠「反正只有我自己调」这个假设。

  • 机制：真正的高危点不是 OAuth，是参数面。这是一条比协议细节更值得背下来的判据，来自项目的真实演进：

    判据：协议边界上的参数面只收不扩。「谁能查谁的」是服务端会话事实，不是 client 可传的参数。

    具体事故形态：v1 里有一个函数签名 query_order(order_no, user_id="u_001")，其中 user_id 表示调用方的身份，函数内部用 _check_owner 做越权校验。当这个函数被原样搬上 MCP 时 —— 任何能连上 server 的 client 都可以自己指定 user_id，一句话把越权防御整个短路。

    修法不是「加个校验」，而是在协议边界上删掉这个参数：MCP 版不暴露 user_id，身份由 server 侧注入。判据可以推广成一类检查：每次把内部函数提升为对外接口，都要逐参数问「这个参数是不是调用方的权限凭据」；是，就必须从参数面移除。

  • 数量级与形状：

    • 暴露面要按风险等级画，不是按技术可行性画。真实项目的边界：MCP 只暴露 2 个只读工具（search_kb、query_order），明确禁止暴露 3 个（create_ticket / query_refund_policy / query_logistics），并且把「禁止暴露」写成负向断言进自检 —— 因为「只在注释和 ADR 里写清楚」的状态下，某天有人往注册函数里加一个工具，不会有任何测试变红。
    • 「禁止」要三条都禁，不能只禁最危险的那一个：写操作（create_ticket）是因为风险等级不匹配；另两个只读工具被禁，是因为它们对该项目的消费者没有价值增益，而每多暴露一个就多一份攻击面与维护面。这个取舍值得学 —— 「能暴露」不等于「该暴露」。

  • 常见误区：

    • 以为「用了 OAuth 就安全了」—— 授权解决「你是谁」，不解决「你不该拿到这个参数」；
    • 把写操作搬上 MCP 却没搬人工确认点与幂等保证（这两件事在跨进程后都要重新设计，见 幂等与副作用防护）；
    • 把「内网所以不用鉴权」当成策略 —— 内网里的任何一台机器都变成了有权退款的调用方。

和你自己的项目对上号 ​

YYHelp v2 的 MCP 部分（code/yyhelp_v2/mcp/）就是这一页的实证材料，面试时按下面四句讲：

  1. 「我实装了 MCP server 与 client。」 依赖约束 mcp>=1.28,<2，实装版本 1.30.0（口径：2026-10-02 实测）。mcp.selftest 四段自检（协议 / 往返 / 一致性 / 参数面）耗时 2.84s（口径：output/yyhelp-v2/00-v2现状审计与缺口清单.md 四-5）。
  2. 「传输我都跑通了，但我只用了它该用的地方。」 stdio、Streamable HTTP、SSE 三种传输都跑通（mcp/transport_check.py，退出码 0）；HTTP 路径的 READY_TIMEOUT_S = 15.0 / CALL_TIMEOUT_S = 20.0（transport_check.py:72-73）。跨语言 client 与多 client 并发未实测 —— 这句一定要主动说，它证明你分得清「我验证过的」和「我以为的」。
  3. 「我只暴露了 2 个只读工具，并禁止了 3 个。」 暴露 search_kb、query_order；明确禁止 create_ticket、query_refund_policy、query_logistics，且禁止是负向断言（mcp/client.py:145-263 的 A 段）。面试官追问「为什么禁 query_refund_policy 这种只读的」时，答「能暴露不等于该暴露，协议集成的边界按风险等级和消费者价值画，不按技术可行性画」。
  4. 「协议层不依赖编排层。」 mcp 与 anyio 是全部依赖，不依赖 langgraph —— 判据是「协议层不该依赖编排层」。这条能直接回答「你的分层是怎么画的」。

如果面试官继续问 user_id：讲 v1 的 query_order(order_no, user_id="u_001") 原样上 MCP 会短路 _check_owner、决策是 MCP 版不暴露 user_id、身份由 server 侧注入、以及这条决策的唯一执行保障是 D 段那条负向断言（断言 query_order 的 schema 里不含 user_id）。

面试怎么问 ​

Q1：MCP 是什么？它解决了什么问题？

A（要点）：它是一个让 AI 应用与外部能力提供方之间跨进程交换能力与上下文的开放协议；架构是 host / client / server 三层，消息是 JSON-RPC，三原语是 tools / resources / prompts。它解决的问题是：原来工具是写死在 Agent 进程里的函数，只有同语言同进程能复用；MCP 把这条边界推到进程/网络层，一套工具能被多个团队、多种语言、多个应用消费。

追问：那 tools、resources、prompts 有什么区别？

A：按「谁决定调用」区分 —— tools 是模型拉的，resources 是应用拉的，prompts 是用户点的。这个分工不是命名差异，是权限模型差异：resources 让应用能预先控制「读什么进来」，tools 则是运行时的、可能带副作用的动态调用。

追问：那这三层里，权限决策在哪一层？

A：在 host。server 只声明自己有什么能力，client 只是连接器，真正决定「这次要不要调、允不允许调」的是 host 应用。这一点决定了安全设计的落点：如果你把权限判断写在 server 里，就等于让「能力提供方」自己决定「调用方该不该有权」—— 位置错了。

Q2：stdio 和远程 HTTP，你怎么选？std​io 有什么坑？

A（要点）：按「这个工具服务的消费者形态」选。本地工具、隐私数据不出机 → stdio；平台化的工具服务、要跨语言跨团队复用、要独立部署 → 远程 HTTP。stdio 的真实难点是子进程管理：子进程、读流、写流三个资源必须同生共死，正确写法是 AsyncExitStack 统一进出栈；另外必须显式传环境（sys.executable 而不是裸 python、PYTHONIOENCODING=utf-8、PYTHONPATH），因为子进程继承的环境是不确定的，而配置错误的报错会长在子进程的 stderr 上，看起来完全像 server 崩了。

追问：远程 HTTP 有什么是 stdio 没有的问题？

A：至少三个。一是超时：stdio 挂住你能 Ctrl+C，HTTP 挂住脚本永不退出，所以必须有就绪超时与调用超时（我们取 15s / 20s）。二是鉴权与多租户：远程意味着不止你的进程能连上来，谁有权限要用协议层重建。三是服务生命周期：server 常驻意味着状态在实例上，重复启动、多次 run 这类问题会以「服务未就绪/超时」这种误导性症状出现。

追问：那你怎么验证远程传输真的在跑？

A：用可重复的验证脚本，不是手点。我的 MCP 自检分四段：A 段断言工具清单恰好是期望的两个、且不含刻意禁止的三个；B 段真发一次往返、断言返回的是我内部的 observation 格式；C 段把同一组参数同时打原生工具与 MCP 两条路，断言解析后的 JSON 信封逐字段相等；D 段断言 query_order 的 schema 里不含 user_id。四段加起来 2.84s，可以进 CI。

再追问：C 段比文本不行吗？

A：不行，而且这个坑很典型。返回里带 elapsed_ms 和 idempotency_key，后者包含与参数无关的会话域 —— 直接比文本必然不等。所以有一步 strip_volatile，在比较前先去掉「本来就该不同」的字段。否则你会为了让它相等而加一堆容差判断，把真正的差异一起容掉。

Q3：MCP 的授权是怎么回事？企业里落地 MCP 的硬门槛是什么？

A（要点）：授权解决的是远程 server 如何确认调用方有权限，走标准 OAuth 授权码流程做授权与凭证分离，核心概念包括资源指示器、令牌受众校验、scope、公共客户端的 PKCE。现实里 MCP 各版本在授权细节上有演进，具体流程与参数以官方文档为准。

追问：那还有比授权更容易出事的地方吗？

A：有，参数面。授权解决「你是谁」，不解决「你不该拿到这个参数」。我的项目里有一个真实例子：v1 的 query_order(order_no, user_id="u_001") 里 user_id 是调用方身份，同进程调用没问题；原样搬上 MCP 后，任何能连上 server 的 client 都能自己指定 user_id，把越权校验整个短路。修法是在协议边界上删掉这个参数、身份由 server 侧注入。

追问：那你怎么保证以后不会有人又把它加回去？

A：把它变成负向断言。自检里有一条断言 query_order 的参数 schema 不含 user_id。判据是：「刻意不做」如果只写在注释和文档里，某天有人改回去，不会有任何测试变红。 负向断言把「设计边界」变成「回归门禁」。同理，禁止暴露的三个工具也各有一条负向断言。

再追问：那你干脆把三个都禁了，为什么还留两个？

A：因为边界的画法是按风险等级与消费者价值，不是「越少越好」。我保留两个只读工具是为了验证「多工具不是特例」；止步于此是因为再往下暴露的边际收益已经低于维护成本。判据一句话：「能暴露」不等于「该暴露」。

再再追问：那如果要暴露写操作，你会先解决什么？

A：三件事，缺一不可。①人工确认点怎么跨进程传递 —— 确认必须在 host 侧发起，server 不能自己批准自己；②幂等键的会话域怎么对齐 —— 我的幂等实现是进程内的 IDEMPOTENCY_STORE，跨进程后天然失效，残余风险（并发下同键碰撞）到现在仍是未验证项；③攻击面收窄 —— 一个能被外部进程调用的写工具，等于把「谁可以退款」从「同进程代码」扩大到「任何能连上 server 的 client」。所以我当前的选择是不暴露，而不是「先暴露再补」。

Q4：你为什么不把所有工具都改成 MCP？

A（要点）：因为 MCP 的价值前提是跨消费者复用（跨团队、跨语言、跨应用）。我的主链路 Agent 只有一个消费者、同进程同语言，上 MCP 会凭空多出：一层序列化边界、一套进程/服务生命周期管理、一个协议版本约束。所以我的结论是并存：主链路继续用原生 @tool，只把跨进程/跨语言能力交给 MCP（ADR-2）。判据原话是「为了简历关键词上 MCP 是负收益」。

追问：那你怎么知道这个结论是对的，而不是你懒得做？

A：我在 v1 里也写过「不引入 MCP」，但那是一个判断，没有实测支撑 —— 依据是需求书的二手结论。v2 里我把它变成了证据：亲手把 search_kb 搬上 MCP，三种传输全部跑通，先 1 个只读工具跑通协议、再扩到 2 个验证「多工具不是特例」、然后停。

追问：实测之后结论变了吗？

A：部分变了，而且是向好的方向。原来担心的「版本风险」实测后结论反转 —— mcp>=1.28,<2 装到 1.30.0 可用，而且没有污染我原有的依赖基线（pydantic / fastapi / starlette 版本未变）。原来那个判断的问题在于把「有版本风险的依赖」等同于「不可做」；正确的表述是「必须先把版本钉死并跑通最小链路」。我保留了真实的版本风险证据：官方 SDK 的 2.x 有重命名，路径是「直接消失而不是先废弃」，所以钉 mcp<2 就是解法。

再追问：这条经历你自己总结成什么？

A：二手结论必须实测复核。 这条比 MCP 本身更有用 —— 它同时说明了为什么我在别的地方也坚持「先跑通最小链路」。
