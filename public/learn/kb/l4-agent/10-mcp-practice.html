MCP 服务端开发、客户端接入与协议演进 ​

覆盖知识点：L4-22 L4-23 L4-24 ｜ 面试频率：高 ｜ 建议学时：10h

一句话说清 ​

上一页（MCP 协议、传输与安全）讲的是「MCP 是什么、为什么这样设计」；这一页讲怎么把它写出来、怎么排错、怎么在版本变化里活下去。三件事按难度递增：写一个 server 暴露工具（半天能跑通）、把外部 server 接进自己的 Agent 并排掉那些「症状不指向根因」的故障（这才是真实工作量）、以及在大版本改名、能力不断加的协议上做版本兼容决策（这决定你是「用过 MCP」还是「能维护 MCP 集成」）。

为什么必须学（面试官视角） ​

「我给你写了个 MCP server」是简历上的强信号 —— 它同时证明三件事：你能读协议规范、能跨进程调试、能对自己写的东西做验收。面试官拿到这条信息后的追问链几乎是固定的：

  1. 「你暴露了哪些工具？」 —— 筛你有没有想过暴露面（答「全都暴露了」直接减分）；
  2. 「返回值的结构是什么？」 —— 筛你有没有真的处理过 MCP 的响应格式（content 是列表这一点能问出真做过和没做过）；
  3. 「你踩过什么坑？」 —— 这是 MCP 这一块最值钱的一问。踩过坑并能讲清「症状 → 根因 → 判据」的人，和只会复述教程的人，在这一问上会拉开明显差距；
  4. 「协议升级了怎么办？」 —— 筛你有没有把「依赖版本」当成一个需要主动管理的东西，而不是 pip install 之后就忘掉。

对应到这一页：L4-22 是「能写」，L4-23 是「能接能排错」，L4-24 是「能管版本」。三块都要有具体到文件与常量的证据，否则在追问两层之后就会垮。

核心内容 ​

L4-22 MCP：服务端开发实践 ​

  • 定义：用官方 SDK 起一个 server，把本地的函数、数据、模板声明成 MCP 的 tools / resources / prompts，让任何 MCP client 都能发现并调用。

  • 机制：一个 server 的骨架只有四件事：

  1. 创建 server 实例：给一个名字与一段 instructions（后者的作用是给模型看的使用说明，不是给人看的文档）。
  2. 注册工具：每个工具声明名字、参数 schema、描述、实现函数。
  3. 运行：按传输方式启动（stdio 启动即阻塞等待，HTTP 则起一个 ASGI app）。
  4. 可测性：把「注册」和「运行」拆成两个函数 —— 这是让 server 能被自检的关键，见下面的代码。
python
# 伪代码结构，示意分层；具体 API 名以官方文档为准
from mcp.server.fastmcp import FastMCP

_INSTRUCTIONS = "本 server 提供客服知识库检索与订单查询。仅只读。"

def register_tools(target):
    """把工具挂到一个已存在的 server 实例上；纯注册，不启动。"""
    @target.tool()
    def search_kb(query: str, top_k: int = 3) -> str:
        """在客服知识库中检索。只读。"""
        return run_search(query, top_k)          # 复用原生工具的实现

    @target.tool()
    def query_order(order_no: str) -> str:
        """按订单号查询订单状态。只读。
        注意：不接收 user_id —— 身份由 server 侧注入。
        """
        return run_query_order(order_no, user_id="u_001")
    return target

def build_server():
    return register_tools(FastMCP("yyhelp-tools", instructions=_INSTRUCTIONS))

def make_fresh_server():
    """每次要跑 HTTP 时都造一个新实例 —— 不要复用模块级实例。"""
    return build_server()

if __name__ == "__main__":
    build_server().run()          # stdio：安静地阻塞等待

  • 为什么「注册」和「实例创建」要拆开（项目真实做法）：mcp/server.py 里 register_tools(target)（:124）与模块级实例 mcp = register_tools(FastMCP("yyhelp-tools", instructions=_INSTRUCTIONS))（:181）分开，另外提供 make_fresh_server()（:184）。理由有二：

    • 可测性：自检可以「造一个 server → 检查工具清单」而不需要真的起进程；
    • HTTP 路径的实例约束：远程传输的 ASGI app 背后有每实例一次的会话管理器，第二次 run 同一个实例会抛错，而症状是「服务未就绪/超时」（完全不像「实例被复用」）。所以远程场景必须造新实例。判据：「一次性的资源（event loop、session manager、端口、子进程）都要有明确的归属实例，不要挂在模块级全局上。」

  • 机制：工具描述与 instructions 各管什么：

    位置谁看写什么
    每个工具的 docstring / 描述模型什么时候该用这个工具、参数含义、返回什么
    server 的 instructions模型这个 server 整体是什么、有什么边界、推荐的使用顺序
    server 的名字与人（工具清单里显示）简短标识

    常见错误是把「边界说明」写在 instructions 里却指望模型在单工具调用时遵守 —— 模型的决策发生在工具描述这一层，边界必须先写在那里（详见 工具定义规范）。

  • 机制：暴露面对齐。写 server 时最容易犯的错是「把内部工具清单原样搬出去」。正确做法是显式写三份清单：期望暴露的、明确禁止暴露的、以及一条负向断言。项目真实形态：

    • EXPECTED_TOOLS = ["search_kb", "query_order"]；
    • FORBIDDEN_TOOLS = ["create_ticket", "query_refund_policy", "query_logistics"]；
    • 自检 A 段（mcp/client.py:145-263）：缺工具或泄漏被禁工具都失败。

    ⭐ 这一条要背下来，因为它是「工程 vs 面试背诵」的分界线：「刻意不暴露 X」如果只写在注释和 ADR 里，某天有人往注册函数里加一个工具，不会有任何测试变红。 负向断言把「设计边界」变成「回归门禁」。

  • 机制：错误处理 —— server 侧不要抛栈给 client 看。MCP 的响应里有一个错误标志字段（拼写以官方文档为准）。语义是「工具执行失败」，它不等同于「协议出错」：

    情况应该怎么返回
    参数不合法 / 业务失败（订单不存在）返回内容，说明失败原因；让模型有机会纠正或转人工
    工具内部异常视策略而定：要么转成内容里的错误说明，要么让连接层处理

    项目上的判据（v1 工具层沿用过来）：「异常不炸图」—— 把失败变成 state 里的一条结果，而不是让整张图崩掉（graph/tools.py 的 ToolError / ToolResult / parse_observation）。到了 MCP 这一层，client 侧的处理是对称的：

    python
    # mcp/client.py 的核心处理（:113-131）—— 判据都在注释里
res = await session.call_tool(name, arguments=args)
items = res.content                                # ← 是列表，不是单值
if res.isError:
    raise RuntimeError(f"MCP 工具 {name} 返回 isError=true：{res.content!r}")
if len(items) != 1:
    raise RuntimeError(
        f"MCP 工具 {name} 返回了 {len(items)} 个 content 块；"
        "本模块只处理单文本块（多块要按类型分派，见 docstring）"
    )

  • 数量级与形状：

    • server 是长驻的（stdio 由 client 拉起、HTTP 自己跑），文档字符串与工具清单在启动时固定 —— 想动态改工具清单就得重启，这直接决定了「工具按需加载」这类需求不能只靠 MCP 解决；
    • 一个 server 暴露 2 个工具与暴露 50 个工具，对模型的难度完全不同：工具清单是并集、全部进上下文，所以 server 侧也应该控制暴露数量（路由与筛选见 工具选择与路由）；
    • 项目实测：MCP 自检四段 2.84s（口径：00-v2现状审计与缺口清单.md 四-5），所以它可以进 CI 而不拖慢流水线。

  • 常见误区：

    • 用模块级 server 实例跑 HTTP（第二次 run 必炸，症状是超时）；
    • 把 content 当字符串用（它是列表）；
    • 只写「期望暴露什么」，不写「禁止暴露什么」且不配断言；
    • 把内部函数的参数原样搬成工具参数（身份类参数必须删掉，见上一页）。

L4-23 MCP：客户端接入与 Inspector 调试 ​

  • 定义：把外部 MCP server 接进自己的 Agent（作为额外的工具来源），并在出问题时用官方调试工具定位到具体是哪一层坏了。

  • 机制：接入的四个接缝点：

mermaid

  C --> D["③ 并集：与原生工具合并成本次请求的 tools 定义"]

第 ② 步是「适配层」，也是所有诡异 bug 的老巢。第 ⑤ 步同样关键：两条路的返回必须归一，否则模型会看到两种不同形状的工具结果，行为会变得不可预测。

  • 机制：一致性自检 —— 怎么证明「适配层没改语义」。这是本项目最有迁移价值的一个设计：把同一组参数同时打两条路，断言结果一致。

    段内容关键断言
    A 协议工具清单恰好是期望的 2 个；且不含禁止的 3 个
    B 往返真发一次往返返回内容确实是内部 observation 格式（如 <untrusted_data> 开头）
    C 一致性同参数打原生与 MCP 两条路去掉时序字段后逐字段相等
    D 参数面工具 schema不含 user_id；必须含 order_no

    ⭐ C 段的比较口径值得单独背：比较的是解析后的 JSON 信封，不是整段文本。因为返回里带 elapsed_ms（每次都不同）与 idempotency_key（含与参数无关的会话域）—— 直接比文本必然不等。所以先做一步 strip_volatile，去掉这两类字段。判据：比较之前，先去掉「本来就该不同」的字段。 否则你会为了让它相等而写一堆容差判断，把真正的差异一起容掉。

  • 机制：Inspector 与「三段式排障顺序」。官方提供 Inspector 这类调试工具用于单独驱动 server、查看其工具与调用结果 —— 用途是把 server 从你的 Agent 里隔离出来测。但真正常用的是这条排障顺序（项目 _dump(fails) 的语义）：

⭐ 第 ③ 条最有价值：它把「协议层」和「语义层」分开了。A/B 通过意味着协议是通的 —— 此时再去怀疑 MCP 本身就是在浪费排查时间，差异只可能出在你自己的适配代码里。判据：排障的本质是把「可能出错的层」逐层排除，而不是从最可疑的地方开始猜。

  • 机制：日志治理 —— 一个「跑通之后才会遇到」的问题。真实形态：stdio 路径已经干净了，换成 HTTP 路径后又冒出一批 stderr 噪声。实测（2026-10-01）：

    • 跑一次 streamable-http 往返往 stderr 打 17 行：httpx ×11、mcp.client.streamable_http ×3、mcp.server.streamable_http_manager ×2、mcp.server.streamable_http ×1；
    • 第一版只压了 mcp.server.lowlevel.server 一个 logger，所以 HTTP 路径的噪声没被盖住 —— 根因是「HTTP 噪声来自 httpx 客户端与 session manager」，而 httpx 根本不是 mcp 的 logger；
    • 修法是抽出 mcp/logging_config.py，集中治理 12 个 logger（NOISY_LOGGERS，:88）：服务端 mcp.server.lowlevel.server / mcp.server.streamable_http_manager / mcp.server.streamable_http / mcp.server.sse；客户端 mcp.client.streamable_http / mcp.client.sse / mcp.client.session；第三方 httpx / httpcore / http.client；服务框架 uvicorn.error / uvicorn.access。

    ⭐ 静音级别是 logging.WARNING，不是 CRITICAL（QUIET_LEVEL = logging.WARNING，:110）。这个细节在面试里很值钱：CRITICAL 会把真正的错误也一起吃掉，而你要的是安静但不出错。判据：静音的级别要选在「噪音之上、错误之下」。

    ⭐ 而且必须有开关：LOG_ENV_VAR = "YYHELP_MCP_LOG"（:85），=1 → INFO、=debug → DEBUG。判据：能静音，也必须能再打开。 静音和不可观测是两回事 —— 只静音不给开关，等于把排障能力删掉。

  • 常见误区：

    • 把「我的代码跑通了」「Inspector 能列出工具了」当成「集成完成了」——缺一致性断言，适配层的语义漂移不会被任何测试发现；
    • 只手压一个 logger，以为治理完了；
    • 直接信「服务未就绪 / 超时」这个报错信息 —— 项目里这个症状的真实根因是「HTTP 客户端继承了环境代理配置」，url 与 port 实测完全正常（port = 60938 <class 'int'>、url = 'http://127.0.0.1:60938/mcp'），报错出现的位置和真正的问题毫无关系。判据：症状出现在「调用阶段」不代表根因在调用代码里。

L4-24 MCP：协议演进与版本兼容 ​

  • 定义：MCP 是一个在演进中的协议，能力集与推荐做法会随版本变化；使用方必须做版本决策，而不是「装上就不管」。

  • 机制：协议演进里会变的几类东西（这里只讲类别，不讲「哪个版本首次引入」）：

变更类别会变成什么样对你的影响
授权相关授权服务器角色、发现机制、客户端注册方式可能调整你的远程接入代码要跟着改；鉴权中间件要重测
人机交互类能力出现「server 可以向用户追问缺失信息」这类反向请求能力你的 host 需要能响应 server 发起的请求，不只是发请求
长任务类能力出现面向长时运行任务的机制（提交、查询状态、取结果）你的超时口径要重设 —— 不能用「一次调用 20s」套所有工具
往返模式出现「不结束当前调用就能追加输入」的往返模式client 的状态机要支持多轮交互
缓存与性能工具清单等可缓存、可变更通知你的缓存失效策略要写对，否则改了工具清单半天不生效

⚠️ 本页不声称任何能力在哪个具体版本首次引入，也不复述任何 SEP 编号。 上面的类别是按「会对集成代码产生什么影响」归纳的；具体能力名、版本号、是否已稳定，一律以官方文档为准。面试里正确的说法是「协议在授权、人机交互、长任务、往返模式这几类上都有演进，我关心的是它们对集成代码的影响」，而不是背一个可能记错的版本号 —— 背错版本号比不谈版本更减分。

  • 为什么协议要这样演进：因为 MCP 最初解决的是「一次请求、一次工具调用」的短交互，而真实 Agent 会遇到两类新需求：结果要等很久（长任务）、信息一开始就不全（需要向用户追问）。这两类需求单靠「发一个请求、等一个响应」表达不了，所以协议必须在交互模式这一层扩展，而不是靠让 server 自己 sleep。

    对应到工程上的判据：一旦协议支持了「一个调用可以有多轮往返」和「server 能反过来问 client」，你的 client 就不能再是「发出去 → 等一个响应 → 结束」的直线代码，得能处理中途的交互请求。这是升级协议时最容易漏的一处改造。

  • 机制：版本兼容的三种决策（这是本页真正要带走的东西）：

策略做法什么时候用代价
钉住上界约束成一个不跨大版本的区间（如 >=x.y,<z）生产依赖；大版本有破坏性改名时拿不到新能力，需要定期主动评估
跟随最新不设上界只做实验、无生产依赖上游一改名，你的代码第二天就红
同时兼容多版本在代码里做能力探测分支你要做通用的 client / 网关（同时服务多版本 server）复杂度最高，需要多版本测试矩阵

⭐ 项目的实际选择是钉住上界，而且这条决策有实测证据（口径：2026-10-02）：mcp>=1.28,<2 实测装到 1.30.0，FastMCP 可用；而 FastMCP 在 2.x 改名 MCPServer，官方路径是 「gone rather than deprecated」—— 直接消失，不是先废弃再移除。所以钉 mcp<2 就是解法。

这段经历在面试里要这样讲才对：

「我不是因为怕升级才钉版本的。我实测确认了两件事：一是当前区间装得上、且没有污染我原有的依赖基线（pydantic / fastapi / starlette 版本未变）；二是 SDK 大版本会做直接改名而不是先废弃，所以上界是必须的。钉上界之后我付出了主动评估的成本 —— 这是我接受的已知代价，不是没想过。」

  • 机制：版本一致性与「同版本即可协商」。server 与 client 同版本 → 自动协商一致。跨版本时行为取决于能力协商结果，凡是「我以为该有但没有」的能力，都要在握手结果里能看到，而不是靠 try/except 猜。判据：能协商的就不猜；协商不了的要显式失败。

  • 常见误区：

    • 把「实测装得上」等同于「可以放开上界」—— 两者是不同问题；
    • 只用 pip install 记录版本，CI 里不守约束 —— 真实做法是把版本约束写进依赖声明，让 CI 去守；
    • 背版本号充当「我很懂协议」—— 版本号会过期，判据不会；
    • 以为「钉版本 = 落后」—— 钉版本是把升级变成一次有意识的决策，而不是一次意外。

和你自己的项目对上号 ​

YYHelp v2 的 mcp/ 目录（服务端 + 客户端 + 日志治理 + 传输验证）是本页的完整实证。按面试叙事顺序：

  1. 「我写了 server，也写了 client。」 mcp/server.py（222 行）：register_tools(target)（:124）负责注册、FastMCP("yyhelp-tools", instructions=_INSTRUCTIONS)（:181）建模块级实例、make_fresh_server()（:184）供远程路径造新实例；mcp/client.py（294 行）：SERVER_MODULE（:68）、server_params()（:71）、list_remote_tools（:106）、call_tool_once()（:113）、parse_observation()（:134）。
  2. 「我把自检分成了四段，其中两段是负向断言。」 A 协议 / B 往返 / C 一致性 / D 参数面（client.py:145-263）。C 段去掉了 elapsed_ms 与 idempotency_key —— 因为后者含与参数无关的会话域，直接比文本必然不等。D 段是 user_id 那条决策的唯一执行保障，删掉它，「不暴露 user_id」就退化成一句注释。
  3. 「我踩的坑里最有价值的是日志那条。」 stdio 干净了但 HTTP 路径又冒 17 行；第一版只压了 mcp.server.lowlevel.server 一个 logger，根因是 httpx 根本不是 mcp 的 logger；修法是抽 logging_config.py 集中治理 12 个 logger、静音级别 logging.WARNING（不是 CRITICAL）、开关 YYHELP_MCP_LOG。
  4. 「我做了版本决策，并且有实测证据。」 mcp>=1.28,<2 → 实装 1.30.0；FastMCP 在 2.x 直接改名 MCPServer（gone rather than deprecated）→ 钉 mcp<2 是解法；server 与 client 同版本自动协商一致。
  5. 主动交代未验证项：跨语言 client（用 Node.js 写 client 调 search_kb）与多 client 并发均未实测（台账 B3 / B4）。说这句不会减分 —— 它证明你分得清「验证过的」和「以为的」。

这一页建议你补的执行动作：如果面试官问「你怎么证明适配层没改语义」，你现在的答案是 C 段。但 C 段只覆盖了 2 个工具。可以做的补强：把 C 段改成参数化跑全部工具 × 至少 2 组参数，并把断言从「逐字段相等」升级为「字段集相等 + 值域相等」，这样「新增工具时忘了配 C 段」也不会静默通过。

面试怎么问 ​

Q1：你写过 MCP server 吗？暴露了哪些工具？

A（要点）：写过。暴露 2 个只读工具：search_kb（知识库检索）、query_order（按订单号查状态）；明确禁止暴露 3 个：create_ticket / query_refund_policy / query_logistics，而且禁止是负向断言进自检，不是只写在文档里。依赖 mcp>=1.28,<2，实装 1.30.0，四段自检耗时 2.84s。

追问：为什么禁 query_refund_policy、query_logistics？它们只是只读啊。

A：因为我的判据是「能暴露不等于该暴露」—— 协议集成的边界按风险等级 + 消费者价值画，不按技术可行性画。只读不等于无风险：每多暴露一个就多一份攻击面、一份维护面、一份版本兼容面，而这两个工具对本系统的消费者没有价值增益。写操作 create_ticket 是另一类理由（风险等级不匹配，见下一问）。

追问：那你怎么防止别人以后偷偷加回去？

A：负向断言。A 段同时断言「期望的两个都在」和「被禁的三个都不在」。判据是：「刻意不做」只写在注释和 ADR 里的话，某天有人改回去，不会有任何测试变红。 所以必须把设计边界写成回归门禁。

再追问：这个断言有没有漏洞？

A：有，而且我知道它是什么 —— 它只覆盖「当前清单」。如果新增一个既不在期望里、也不在禁用列表里的工具，A 段不会红。更严的写法是把「工具清单的变更」本身当成需要 review 的事件（清单哈希入库 / 变更时强制更新期望常量），这是我现在没做的，属于已知缺口。

Q2：客户端接入最容易出什么问题？

A（要点）：三类。① 生命周期：stdio 要同时管子进程、读流、写流三个资源，必须同生共死，正确写法是 AsyncExitStack；② 返回值形态：content 是列表不是单值，多块时静默取第一个会丢数据且不留痕，我的做法是 len(items) != 1 直接报错；③ 适配层语义漂移：从 MCP 拿到的结果要转成和原生工具同一种格式，否则模型看到两种形状的工具结果，行为不可预测。

追问：你怎么知道适配层没改语义？

A：把同一组参数同时打原生与 MCP 两条路，断言解析后的 JSON 信封逐字段相等（C 段）。关键是比较口径：先 strip_volatile 去掉 elapsed_ms 和 idempotency_key —— 后者含与参数无关的会话域，不去掉的话直接比文本必然不等，然后你会为了让它相等而加一堆容差判断，把真正的差异一起容掉。

追问：那如果 C 段失败，你怎么知道问题在哪？

A：看 A、B 段。A/B 通过就说明协议是通的 —— 此时再怀疑 MCP 本身就是在浪费排查时间，差异只可能出在我的适配代码里。这就是我排障顺序的第三档。前两档是：先手动起 server（期望安静地阻塞，这是正常状态），再用 Inspector 单独连（能列工具、能调用）。三档下来，「协议层 / 资源管理 / 适配语义」三个可能出错的层就被逐个排除了。

再追问：你自己踩得最深的坑是哪个？

A：日志。我一开始以为跑通了就完成了，结果 stdio 干净、HTTP 路径又冒 17 行 stderr（httpx ×11、session manager 相关 ×5 等）。第一版我只压了一个 logger，没盖住是因为 httpx 根本不是 mcp 的 logger。修法是抽一个 logging_config.py 集中治理 12 个 logger。这里有两个我当时做错的判断：一是静音级别差点选 CRITICAL —— 那会把真错误一起吃掉，正确的是 WARNING（噪音之上、错误之下）；二是几乎忘了留开关 —— 只静音不给开关等于把排障能力删掉，所以加了 YYHELP_MCP_LOG 环境变量。

Q3：MCP 协议一直在变，你怎么管？

A（要点）：分三层。决策层：钉住上界（mcp>=1.28,<2），把升级变成一次有意识的决策而不是意外。证据层：上界的依据是实测 —— 大版本会直接改名（FastMCP → MCPServer，gone rather than deprecated），所以上界是必须的；同时实测确认当前区间没有污染既有依赖基线。执行层：约束写进依赖声明、让 CI 守。另外 server 与 client 同版本即自动协商一致，凡是「我以为该有但没有」的能力都必须在握手结果里看得到，而不是靠 try/except 猜。

追问：那协议演进里有哪些变更是会影响你集成代码的？

A：我不背版本号，我按影响类别记。有五大类：授权相关（授权服务器角色、发现机制、客户端注册方式）、反向交互（server 能向你追问缺失信息 —— 这要求 client 不只会发请求，还能响应 server 发起的请求）、长任务（提交 + 查询状态 + 取结果，会推翻「一次调用 20s 超时」这个口径）、多轮往返（一个调用可中途追加输入，client 不能是直线代码）、缓存与变更通知（工具清单可缓存后，失效策略写错会让改动半天不生效）。具体能力名、版本号与稳定性以官方文档为准。

追问：为什么不说具体版本？

A：因为背错版本号比不谈版本更减分，而版本号会过期。真正不会过期的是「这次变更会要求我改哪一部分代码」—— 比如反向交互会强制我改造 client 的状态机，这条判断在任何版本上都成立。

再追问：那你升级时会怎么验证？

A：用已有的四段自检当回归门禁跑一遍，加一条专门针对变更类别的用例。比如如果是反向交互类变更，就补一条「server 中途追问、client 能应答并完成调用」的用例 —— 而且这条用例必须是真的能跑的，不是写在文档里的验收标准。这里有个我自己的教训：代码的防护力等于「被执行的断言数」，不是「写下的断言数」。 一个从不执行的断言，防护力和「没有断言」完全相同 —— 但它会让你以为有防护。这比没有更危险。
