本页目录

记忆系统：短期会话、长期画像、写入与遗忘 ​

覆盖知识点：L4-12 L4-13 L4-14 ｜ 面试频率：高 ｜ 建议学时：10h

一句话说清 ​

记忆不是一个存储问题，是一个取舍问题。 短期记忆（会话内）的回答只有一句：上下文窗口不是记忆，它是工作台——工作台满了要收拾（截断 / 摘要 / 摘要再摘要），而不是加宽。长期记忆（跨会话）的真实难点也不在「怎么存」，而在三个每个都会做错的判断：① 什么值得写（写多了就是污染，写少了等于没有）；② 什么时候忘（永不遗忘的记忆库，召回质量随时间单调下降）；③ 召回了要不要给模型看（这条最反直觉：可以让召回结果进 state 而不进 prompt）。这三件事没有「正确答案」，只有「能被口径验证的取舍」——本页的所有数字都要当成一组具体的选择来读，不是一套普适参数。

为什么必须学（面试官视角） ​

记忆系统是应届简历上最容易吹、也最容易被戳破的一块，所以它的面试价值极高：

  • 它区分「调过 API」和「设计过系统」。 「我用了向量库做记忆」是零分答案；能说出写入门槛、衰减函数、召回打分三项权重的人，会立刻被当成做过设计的人。注意：不是数字越大越好，是有没有数字。
  • 「你怎么决定要不要记住这条」是必问的追问。 因为天真做法有两个方向都错的失败：全部记住 → 记忆库被一次性偏好和错误信息灌满，召回质量长期下降；从不记住 → 跨会话零收益，长期记忆等于没做。正确答案必须包含门槛（按种类分）+ 幂等（同内容不重复存）+ 上限（同类每会话最多几条）。
  • 「遗忘」是筛人题。 大部分候选人从没想过记忆要衰减；能说出「半衰期按记忆类型区分」「事实类不衰减、偏好类衰减」「衰减在召回时算而不是后台任务」的人很少。最后那条尤其值钱：能算出来的东西不要存——它同时是架构判断和工程纪律。
  • 本页最值钱的一条反直觉设计：可以让召回结果写进 state、但不拼进 prompt。这件事的好处是「可观测、可回滚、可对比」；代价是「模型其实看不到记忆」。能主动说出这条取舍和它的代价，比任何参数都更能证明你真做过实验——因为它意味着你愿意承认「用上了记忆」这件事本身还需要单独验证。

核心内容 ​

L4-12 记忆系统：短期会话记忆 ​

  • 定义：短期记忆 = 本次会话内的对话历史与中间结果，生命周期与 thread 绑定，会话结束即失去意义（或在结束时被提炼成长期记忆）。它的载体通常就是模型的上下文窗口 + 一份会话状态。

  • 机制（四种手段，按信息保真度从高到低）：

手段做法保真度什么时候用
全量保留原样保留所有轮次最高会话短（十几轮内）、成本可接受
滑动窗口只保留最近 N 轮低（早期信息永久丢失）早期信息确实不重要的闲聊类
摘要压缩把早期轮次总结成一段摘要，替换原文中（措辞丢失、事实可保留）默认选择：需要保留早期要点的多轮任务
分层摘要摘要的摘要（多级合并）中低超长会话（几十轮以上）

关键纪律：压缩要保留「可核对的事实」而不是「语感」。订单号、金额、日期、用户明确说过的约束必须原样保留；寒暄、重复确认、模型自己的思考过程可以丢。「有损压缩时优先保住什么」是一个显式决策，不该交给摘要模型随机决定。

  • 为什么这样设计：

    • 为什么不能靠「上下文窗口够大」解决：窗口变大改变的是上限，不是成本与注意力。① 每个 token 都要付钱，而历史 token 每轮都要重发一遍（这是上下文成本最容易被忽略的性质：第 10 轮的历史不是被读了一次，是被读了 10 次）；② 上下文越长，关键信息越容易被淹没，「中间遗忘」现象是公开已知的；③ 长上下文不给你跨会话记忆——那才是用户感知到的「它记得我」。
    • 为什么摘要要显式指定保留字段：摘要模型不知道自己下游要拿这段摘要做什么。如果你不告诉它「订单号必须原样保留」，它就会把 SO20261015008 改写成「订单」——这在人看来是合理的摘要，在系统里是信息毁灭。
    • 为什么短期记忆要和长期记忆分开设计：两者的失效条件完全不同。短期记忆的错误是「丢了本次会话的上下文」，长期记忆的错误是「把一个一次性的说法当成永久事实」。混在一起设计，一定会把后者当后者处理（比如把一次性的「我不着急」永久写进偏好）。

  • 数量级与形状：

    • 会话长度分布是长尾：大多数会话十几轮内结束，少数会到几十轮。压缩策略要对长尾设计，但不能为长尾牺牲前者的延迟。所以常见做法是设一个轮数阈值，超过才触发压缩。
    • 一次会话的总 token 里，工具结果通常占最大头，其次才是对话历史——这意味着压缩策略要先治工具结果（见 L4-09），再治对话历史。
    • 轮数阈值、保留轮数、摘要长度上限，这三个数都要显式写进配置，不能散落在代码里。

  • 常见误区：

    • 把上下文窗口当记忆：「我们有 128k 上下文所以不需要记忆」——混淆了容量与生命周期。
    • 用固定「保留最近 5 轮」而不做摘要：第 6 轮之前的用户约束（比如「别打电话给我」）就永久消失了。
    • 摘要时不做字段保护：编号、金额、日期被改写。
    • 压缩在「装不下」时才做：那时你已经付过一次超限的代价（报错或截断），而且没有机会优雅地选择保什么。
    • 会话状态里塞了不该塞的东西：原始工具结果、完整文档、明文凭据。state 会进 trace，trace 会进日志。

L4-13 长期记忆与用户画像 ​

  • 定义：跨会话保留、可在未来会话中被召回的持久化信息。典型种类：偏好（用户喜欢什么）、事实（关于用户或其环境的稳定信息）、解决方案（这类问题上次是怎么解决的）、纠正（用户明确指出你上次错了什么）。

  • 机制（一条完整链路：抽取 → 写入门槛 → 存储 → 召回打分 → 使用）：

阶段要决定的事做错的后果
抽取从这一轮对话里提取候选记忆，并给每条一个可信度把模型的猜测当成用户陈述
写入门槛按种类设不同的最低可信度门槛统一 → 敏感种类被灌满，稳定种类被漏掉
存储 + 幂等相同内容不能重复存（用内容指纹做 id）同一个偏好存 20 条 → 召回被单条记忆霸占
召回打分相似度 + 关键词重合 + 时间衰减，三项加权只按相似度 → 三年前的偏好盖过今天的
使用召回结果进不进 prompt（本页最重要的开关）不区分 → 无法归因、无法回滚

  • 为什么这样设计（逐条说「为什么」）：

    • 为什么写入门槛要按种类分而不是统一：不同种类的代价不对称。「偏好」写错只是推荐不准，代价低，所以门槛可以低一些（多记一点）；「纠正」写错意味着你把用户没有说过的话当成他纠正过你的证据，代价高，所以门槛必须最高。门槛的设计依据是「写错的代价」，不是「写对的收益」。
    • 为什么半衰期要按种类分，而且事实类可以不衰减**：偏好会变，事实不会。「我喜欢简洁回答」可能三个月后就不成立了；「我的订单号是 X」这类属于会话级事实，本来就不该长期存；而「我的账号是 Y」「我的时区是 UTC+8」这类稳定事实没有理由随时间失效——给它一个半衰期等于在制造错误。「什么该衰减」这个问题，答案藏在「什么东西会变」里。
    • 为什么衰减要在召回时算，而不是跑一个后台任务去改数据：因为能算出来的东西不要存。衰减值是 (种类, 创建时间, 当前时间) 的纯函数，把它算出来存下来意味着：① 要定时任务；② 存储里有一份可能过期的冗余真相；③ 想要「以某个历史时间点看记忆」时没有数据可回溯。存的是事实（创建时间），算的是视图（当前权重）——这是数据库设计里的老道理，在记忆系统里一样成立。
    • 为什么召回打分必须是三项加权而不是纯相似度：相似度只看「这条记忆和当前问题像不像」，完全不看「这条记忆还该不该被信」。一个三年前的偏好和一条昨天刚确认的事实，可能语义相似度一样高——时间衰减就是唯一能把它们分开的那一项。而关键词重合项补的是另一种失败：短查询（「地址」）在纯向量相似度下会飘，字符级重合能把它拉回正确的记忆。
    • 为什么记忆集合要和知识库物理隔离：这是两类完全不同的数据——知识库是共享的、相对静态的、可重建的；记忆是用户私有的、动态的、不可重建的。混在一起会导致：① 删用户的记忆时误删知识库；② 用户 A 的记忆可能被 B 召回（隔离边界失效）；③ 评测口径混在一起（检索质量 vs 记忆质量）。隔离不是洁癖，是权限与评测的双重需要。

  • 数量级与形状：

    • 召回条数通常落在 3–5 条（多了会挤掉上下文，少了覆盖不足）；置信度与分数都要有下限，否则会召回「勉强相关」的记忆。
    • 打分权重是归一化的（三项和为 1），这样每一项的可比性明确，调参时改一项不用重算其他项。
    • 记忆条数的增长是线性的（每次会话可能写入 0–几条），所以读路径（召回）必须保证不随总量爆炸：要么全量打分（量小时够用），要么上索引（量大时必要）。这条「什么时候必须换索引」的判断，是一个可以量化的口径问题，不要凭感觉。

  • 常见误区：

    • 把「记忆」和「知识库」混在一个集合（权限、删除、评测三重问题）。
    • 只按向量相似度召回：老记忆压过新事实。
    • 召回后无脑全拼进 prompt：上下文被塞满、无法归因、无法做 A/B。
    • 不设召回下限：把「勉强相关」的记忆也塞给模型，于是模型基于噪声做判断——这比不召回更糟。
    • 把用户的一次性表达当成长期偏好：「我今天不着急」被写成「用户不着急」。这类错误只能靠门槛 + 种类区分来防，靠模型判断是防不住的。
    • 从不清理：记忆库只增不减，几年后召回质量必然下降。

L4-14 记忆写入与遗忘策略 ​

  • 定义：写入策略 = 什么进、什么不进、以什么置信度进、同样的内容重复来怎么办；遗忘策略 = 什么会随时间变弱、什么永不衰减、什么时候真正删除。

  • 机制（四道闸，缺一道就会出现一种典型故障）：

#闸作用缺了会怎样
①种类识别把候选分成偏好 / 事实 / 解决方案 / 纠正所有记忆一视同仁，门槛与半衰期无从谈起
②置信度门槛（按种类）挡住「模型猜测」与「低可信陈述」记忆库被猜测灌满
③幂等（内容指纹做 id）同内容不重复写入同一个偏好存 N 条，召回被它霸占
④数量与长度上限同类每会话最多几条 + 单条字符上限一次长对话写进几十条垃圾

遗忘侧的三件事：时间衰减（按种类半衰期，且在召回时计算）、衰减下限（不能衰减到 0——否则等于删除，你就失去了「它曾经存在」这个信息）、真正的删除（用户要求删除 / 纠错后必须硬删，这是合规问题不是质量问题）。

  • 为什么这样设计：

    • 为什么置信度门槛要按种类分档：见 L4-13 —— 依据是「写错的代价」。代价高的种类（纠正）门槛最高，代价低的种类（偏好）门槛最低。
    • 为什么幂等要用「内容指纹」而不是「时间戳 + 计数器」：因为指纹表达的是语义身份——同一句话在不同时间说出来是同一条记忆，应该更新而不是新增。指纹还有一个附带好处：同内容天然得到同一个 id，于是幂等是「结构保证」而不是「查重逻辑」——不需要额外写一段「先查有没有」的代码。
    • 为什么要有「同类每会话上限」：置信度门槛挡的是质量，挡不住数量。一次两小时的深度对话完全可能产生 20 条高置信度偏好——它们全都「合格」，但全存下来会让召回被这次会话霸占。数量上限防的是「单次会话的过度影响」。
    • 为什么衰减要有下限：无下限的衰减等价于删除，但删除是不可逆的、且会丢失「这条记忆存在过」这个信息。留下一个很小的非零权重，召回排序里它几乎不出现，但审计和调试时还能看见它——这是可观测性与整洁性之间的取舍，选可观测性。
    • 为什么「真正删除」必须单独存在：衰减是我们对记忆做的判断，删除是用户对记忆做的决定。用户要求删除时不能只把权重降到很低——那只是「召不回来」，数据还在。这是合规问题（数据主体权利），不是排序问题。

  • 数量级与形状：

    • 一次会话写入个位数条是合理的（超过就该怀疑门槛太松）；每种记忆的半衰期量级从「月」到「永不」——量级差异本身就是设计意图的表达。
    • 打分三项权重归一化（和为 1）；衰减因子有下限（例如 0.30），所以总权重永远不会归零，这保证了「排序里几乎不出现」与「数据消失」是两件不同的事。
    • 抽取的可信度是按种类给初值：明确的用户陈述高于模型的归纳推断。这个初值差异是后续门槛能生效的前提。

  • 常见误区：

    • 同一句话说两遍存两条：没有内容指纹做 id。
    • 只增不删：以为「记忆越多越好」，实际上召回质量随噪声增加单调下降。
    • 用「权重降到 0」代替删除：数据仍在。
    • 在后台跑任务批量改权重：引入冗余真相与定时任务，且丢掉可回溯性。
    • 把置信度写成模型自报：模型对自己的把握程度估计不可靠；初值应由结构化抽取的结果种类决定，而不是由模型给的一个分数决定（要模型给分数，也必须经过校验与裁剪）。
    • 忘了「召回留痕」：召回结果如果不记录，事后无法回答「这次回答到底有没有用上记忆」。

  • L4-13 召回打分（真实三项权重）：W_SIM 0.55 + W_OVERLAP 0.25 + W_DECAY 0.20 = 1（longterm.py:169-171）。三项的含义与本页讲的一致：相似度、关键词重合（字符 2-gramchar_overlap，不按空格分词——中文没有空格，按空格分词会失效）、时间衰减。另外 HASH_DIM = 64（:174）、相似度走 _HashEmbedder（:303）。打分要能现场推导，不能只会背权重。
  • L4-14 写入门槛（按种类分档，门槛设计依据是「写错的代价」）：MIN_CONFIDENCE_BY_KIND（longterm.py:131-140）——

    • fact 0.75
    • solution 0.80
    • correction 0.85（把用户没说过的话当成他纠正过你，代价最高 → 门槛最高）

  • L4-14 衰减的实现在哪（「能算出来的东西不要存」）：decay(kind, created_at, *, now=None) -> float（longterm.py:367）：age_days = max(0, (now - created_at)/86400)；半衰期为 None 时直接返回 1.0；否则 max(DECAY_FLOOR, 0.5 ** (age_days / hl))，取值范围落在 [0.30, 1.0]。存的是创建时间，算的是当前权重——没有后台任务、没有冗余真相、可以拿任意历史时刻重算。这句「能算出来的东西不要存」是本页最该逐字背的一句。
  • L4-13 召回的下限三件套：RECALL_TOP_K = 3（:153）、RECALL_MIN_CONFIDENCE = 0.55（:158）、RECALL_MIN_SCORE = 0.25（:160）、衰减下限 DECAY_FLOOR = 0.30（:163）。「不设下限」是本页列的常见误区之一，这个项目三条都设了。
  • L4-14 幂等（内容指纹 → 结构保证）：content_fingerprint(content) -> str（:194）归一化后做 sha256；MemoryItem.id 默认 f"m_{fp[:16]}"——同内容同 id，所以幂等是结构保证，不需要额外写一段「先查有没有」的查重逻辑。这正是本页「为什么用内容指纹而不是时间戳」那一段的实例。
  • L4-14 数量与长度上限：同类抽取上限 2 条/会话（:906-915）；长度闸 correction ≤ 200 / preference ≤ 120 / solution ≤ 300 字符。门槛挡质量、上限挡数量——两件事都要有。
  • 抽取的置信度初值：correction 0.92 / preference 0.70 / solution 0.80，反思写入 0.90（reflect.py:92-94）。这些是由结构化抽取的种类决定的初值，不是模型自报的把握程度。
  • L4-13 物理隔离：记忆集合 yyhelp_memory_v1（longterm.py:187）与知识库 yyhelp_kb_v1（config.py:161）物理隔离。理由正是本页那三条：删除边界、用户隔离、评测口径。
  • ⭐ 最值钱的一条反直觉设计（必须能讲清取舍）：RECALL_POLICY = "state_only"（longterm.py:810）——召回结果写进 state["memories_recalled"]，但不拼进 prompt。三条理由：可观测性 / 可回滚 / 可对比。代价是模型其实看不到记忆，所以「用上了记忆」这件事本身尚未验证——判据要写成【待核对：记忆 hint 开与不开的偏好遵守率】。两个显式开关是 render_memory_hint(res, *, max_items=3)（:839）与 recall_for_state(state, *, store=None, top_k=3, with_hint=...)（:813）。
    • 面试里怎么讲：先说设计（写 state 不拼 prompt），再说三条好处，然后主动说代价——「所以我的 A/B 现在还测不出『记忆有没有被用上』，要测这个得单独做一个 hint 开 / 关的对照，判据是偏好遵守率」。主动暴露这一点，比声称「我的记忆系统效果很好」可信得多。

科研文献 RAG：这个项目没有用户记忆层（无用户概念、无跨会话状态），但有两处可迁移的同构经验：

  • 「能算出来的东西不要存」：这个项目的检索分数、MRR 之类的指标都是评测时现算的，不在库里存冗余分数。这与衰减在召回时计算是同一条纪律。
  • 摘要压缩的字段保护教训（这是最该迁移的一条）：RAG 里引用编号曾出过一个真实缺陷——["1","2"] 这种「编号做成了字符串」的形态被静默丢弃成 citations=[]，而校验函数返回了 True 说「校验通过」。这与「摘要时把订单号改写成『订单』」是同一类错误：压缩/解析环节静默丢弃了必须保住的结构化信息，而且没有任何报错。面试里可以合成一句话讲：「我的经验是有损环节必须显式标注丢了什么——摘要、截断、解析都算有损环节；静默丢弃是最危险的一种损失，因为它不报错。」

面试怎么问（≥3 组） ​

Q1：你的 Agent 有记忆吗？记忆和上下文窗口有什么区别？

A（要点）：先分清两层。上下文窗口不是记忆，它是工作台——容量可以很大，但生命周期只到本次会话，而且历史 token 每轮都要重发一遍（第 10 轮的历史不是被读了一次，是被读了 10 次）。长期记忆是跨会话持久化的用户私有信息，我的实现里分四类：偏好、事实、解决方案、纠正。两者的失效条件完全不同：短期记忆的错误是丢了本次会话上下文，长期记忆的错误是把一次性说法当成永久事实——所以必须分开设计。

追问 1：上下文窗口越来越大，还需要记忆吗？

A：需要，而且理由有三个，只有第一个和窗口大小有关。① 成本：历史 token 每轮重发，窗口大不代表便宜；② 注意力：上下文越长关键信息越容易被淹没，这是公开已知的现象；③ 跨会话：窗口再大也覆盖不了「上次那个用户说过什么」。第三条是记忆存在的根本理由，和窗口大小无关。

追问 2：短期记忆怎么压缩？

A：默认用摘要压缩（滑动窗口会永久丢掉早期约束）。关键纪律是显式指定必须原样保留的字段：订单号、金额、日期、用户明确说过的约束。因为摘要模型不知道下游要拿这段摘要做什么——不告诉它，它就会把 SO20261015008 改写成「订单」，在人看来是合理摘要，在系统里是信息毁灭。超长会话再上分层摘要。

追问 3：什么时候触发压缩？

A：设一个轮数阈值，超过才触发，而不是等「装不下」。因为装不下的时候你已经付过一次超限的代价（报错或硬截断），而且没有机会优雅地选保什么。另外压缩的顺序是先治工具结果、再治对话历史——一次会话里工具结果通常占大头。

Q2：什么信息值得写进长期记忆？

A（要点）：我的写入是四道闸，缺一道就会出现一种典型故障。① 种类识别：偏好 / 事实 / 解决方案 / 纠正；② 按种类的置信度门槛（我项目里 preference 0.60、fact 0.75、solution 0.80、correction 0.85，未知种类兜底 0.85——对未知从严）；③ 幂等：用内容指纹做 id，同内容同 id，所以幂等是结构保证，不需要写查重逻辑；④ 数量与长度上限：同类每会话最多 2 条，单条有字符上限。

追问：门槛为什么按种类分，还差这么多？

A：依据是「写错的代价」，不是「写对的收益」。偏好写错只是推荐不准，代价低，所以门槛低、可以多记；纠正写错意味着我把用户没说过的话当成他纠正过我的证据，代价最高，所以门槛最高。如果门槛统一，结果一定是敏感种类被灌满、稳定种类被漏掉。

追问：数量和门槛不是一回事吗？

A：不是。**门槛挡质量，上限挡数量。**一次两小时的深度对话完全可能产生 20 条高置信度偏好——它们全都「合格」，但全存下来会让召回被这次会话霸占。同类每会话上限防的是「单次会话的过度影响」。

追问：那同一个说法在不同时间说了两次呢？

A：那是同一条记忆，应该更新而不是新增——这就是用内容指纹（归一化后哈希）而不是时间戳做 id 的原因。指纹表达的是语义身份；用「时间戳 + 计数器」做 id 的话，同一句话存两遍就是两条，召回时被它霸占。

Q3：记忆会忘吗？你怎么设计遗忘？

A（要点）：会，而且遗忘是设计动作不是缺陷——永不遗忘的记忆库，召回质量随时间单调下降。三个部分：① 按种类的半衰期：偏好 90 天、解决方案 180 天、事实与纠正不衰减；② 衰减在召回时计算，不跑后台任务；③ 衰减有下限，且「用户要求删除」必须是硬删，那是合规问题不是排序问题。

追问：为什么事实类不衰减？

A：因为偏好会变，事实不会。「我喜欢简洁回答」三个月后可能就不成立了；而「我的时区是 UTC+8」没有理由随时间失效——给它一个半衰期等于在制造错误。「什么该衰减」的答案藏在「什么东西会变」里。

追问：为什么衰减要在召回时算，而不是定时任务改数据？

A：因为能算出来的东西不要存。衰减值是「种类 + 创建时间 + 当前时间」的纯函数。存下来意味着：要定时任务、存储里有一份可能过期的冗余真相、而且想做「以某个历史时刻看记忆」时没有数据可回溯。我的实现是 decay(kind, created_at, *, now=None)：半衰期为 None 直接返回 1.0，否则 max(0.30, 0.5 ** (age_days/hl))，范围落在 [0.30, 1.0]。存的是事实（创建时间），算的是视图（当前权重）。

追问：为什么衰减要有下限，而不是衰减到 0？

A：无下限的衰减等价于删除，但删除不可逆、而且丢掉了「这条记忆存在过」这个信息——审计和调试时你还想看见它。所以留一个很小的非零权重：召回排序里它几乎不出现，但数据还在。这是可观测性与整洁性之间的取舍，我选可观测性。

Q4（加分题）：召回到的记忆，你会拼进 prompt 吗？

A（要点）：我项目里默认不拼——RECALL_POLICY = "state_only"：召回结果写进 state["memories_recalled"]，但不进 prompt。三条理由：可观测性（事后能看见召回了什么）、可回滚（默认关掉就能对比）、可对比（A/B 时不会被记忆污染）。两个显式开关是 recall_for_state(state, *, with_hint=...) 与 render_memory_hint(res, *, max_items=3)。

追问：那模型不是看不到记忆吗？

A：对，这是这条设计的代价，而且必须主动说。所以「我的系统用上了记忆」这件事目前还没有被验证——要验证必须单独做一次「hint 开 / 关」的对照，判据是偏好遵守率。我不会把「召回功能跑通了」说成「记忆有效」。

追问：为什么不干脆默认拼上，效果不是更明显吗？

A：因为那样我就无法归因了。如果一个改动同时改了召回策略和拼接方式，指标变了我说不清是谁的贡献；更糟的是记忆会污染其他 A/B——两个臂如果都带着记忆，差异会被记忆造成的方差吃掉。先默认关、把召回这条路做扎实、单独验证它，比一开始就让它影响所有实验更省事。

追问：那你怎么知道记忆库里的数据是对的？

A：靠召回留痕：每次召回记下「召回了哪几条、各自三项分数是多少、为什么没过下限」。这样当模型答错时，我能区分「它没答出来是因为记忆里没有」还是「有但没被召回」还是「召回了但没进 prompt」。这条纪律和工具结果治理是同一条：能记录的东西不要猜。
