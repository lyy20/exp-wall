Agent 框架横向对比与低代码平台 ​

覆盖知识点：L4-30 L4-33 ｜ 面试频率：高 ｜ 建议学时：7h

一句话说清 ​

选型题在面试里的正确答法不是排行榜，而是三步：先问「要不要框架」，再问「要哪一种控制粒度」，最后问「这个成本我付得起吗」。这一页给出这两问的判据：L4-30 覆盖代码框架（LangGraph / AutoGen / AgentScope / CrewAI / smolagents / Dify 等）的设计哲学差异与适用边界；L4-33 覆盖低代码平台（Coze / Dify / n8n 等）的定位 —— 它的最大价值不是「快」，而是让你能用极低成本回答「这个需求值不值得写代码」。

为什么必须学（面试官视角） ​

框架选型是应届生面试里**最容易暴露「只会用、不会判断」**的一题。面试官问「你用过哪些 Agent 框架」时，他真正在测三件事：

  1. 你有没有一个统一的坐标系。只会说「LangGraph 好、AutoGen 也好」的人，等于没有坐标。正确的答法是先给出分类维度（控制粒度 / 多智能体的表达方式 / 部署形态 / 生态锁定），再把具体框架放进格子里。
  2. 你会不会算成本。这是最有区分度的一点：框架的收益是「省下的实现工作」，成本是「抽象税 + 依赖风险 + 迁移成本」。能说出自己为某个框架付了什么代价的人，比只讲收益的人可信得多。
  3. 你知不知道「什么时候不该用」。这一条同时适用于代码框架和低代码平台。答「低代码不够专业所以不用」是偏见；答「低代码能满足就先低代码，因为它能最快验证需求值不值得做」是判断。

⚠️ 本页的 API 纪律：框架的具体 API、版本、是否已更名、是否已停止维护，一律以各框架官方文档为准。本页只写「设计哲学与适用场景」这类不会过期的差异，并且不给任何框架排名 —— 排名会过期，判据不会。

核心内容 ​

L4-30 Agent 框架横向对比 ​

  • 定义：Agent 框架是一类「替你实现 Agent 运行循环、工具调用、状态管理、多智能体协作」的库或平台。它们之间的差异不在功能清单上（功能清单大同小异），而在三个设计维度上。

  • 机制：先建立坐标系 —— 三个真正有区分度的维度：

维度取值谱它决定了什么
① 控制粒度从「你画流程图，框架只负责执行」到「你给一个目标，框架自己决定循环」可控性 vs 上手速度。粒度越细，排查越容易、确定性越高；粒度越粗，代码越少、行为越不可预测
② 多智能体的表达方式图 / 角色对话 / 团队分工 / 流水线 / 层级协作形态能不能被表达。有些框架天然是「几个角色互相聊」，你很难表达「严格顺序 + 带闸的循环」
③ 部署与状态形态库（跑在你的进程里） / 服务（独立部署） / 平台（浏览器里画）能不能进生产链路。库最灵活但有状态与并发问题要你自己扛；平台最快但边界由平台定

⭐ 这三个维度就是选型的坐标系。面试里被问「你怎么选框架」，第一句话应该是「我先按控制粒度、多智能体表达方式、部署形态三个维度定需求，再看哪个框架落在我需要的那一格」。

  • 机制：按坐标系归位（讲哲学，不讲 API）：
框架控制粒度的落点多智能体的表达方式关键取舍（一句话）
LangGraph细：你显式建图（节点 + 边 + 条件边 + 状态）图上的节点与子图可控可持久化，代价是流程要你自己画对（见 LangGraph 状态图 的装配错误事故）
AutoGen中：核心抽象是「会互相发消息的智能体」角色对话（多智能体对话/群聊）天然表达「多个角色互相讨论」，代价是严格顺序与硬闸要额外约束
CrewAI中偏粗：核心抽象是「角色 + 任务 + 团队」团队分工（角色协作、任务委派）上手最快的多智能体心智模型，代价是细粒度控制流受限
AgentScope中：面向多智能体应用的开发框架消息传递 + 显式编排强调多智能体工程化与消息机制，国内生态文档友好
smolagents粗：强调代码即动作（让模型写代码来调工具）相对轻量，多智能体不是重点把「工具调用」升级成「写代码」，表达力强但沙箱与安全要求更高（见 代码执行与沙箱）
Dify（作为平台的代表）平台级：可视化工作流画布上的节点交付最快，代价是细粒度控制与版本管理由平台定义

⚠️ 上表是设计哲学归位，不是功能对比，也不是排名。每个框架的实际能力集与推荐用法以各自官方文档为准；同一框架的不同版本在抽象与命名上都可能变化。

  • 为什么这样设计（每个框架为什么长这样）：把框架的长相和它的目标场景对上，你就能理解它为什么做这个取舍，而不是死记功能表：

    • LangGraph 长成「图」，是因为它瞄准的是生产级、可中断、可持久化的长流程。要持久化和中断，就必须有显式状态；要有条件分支和循环，就必须有显式边。图不是它的风格选择，是它的目标场景逼出来的。
    • AutoGen 长成「对话」，是因为它的起点是「让多个模型互相讨论能提升质量」。对话是最自然的多智能体原型；而代价正是「对话」这种形态天生没有强制的执行顺序——严格流程要额外加约束。
    • CrewAI 长成「团队」，是因为它瞄准的是「用业务语言描述一组协作」。「角色 + 任务 + 团队」的心智模型几乎不需要学习成本；代价是细粒度控制。
    • smolagents 长成「代码 Agent」，是因为它认为自然语言表达动作有信息损失。让模型写 Python 而不是填 JSON 参数，能表达循环、条件、组合 —— 但这就把沙箱与安全变成了必答题。
    • Dify 这类平台长成「画布」，是因为它瞄准的是「从想法到可交付」的交付速度。它的用户不一定是后端工程师。

  • 机制：判断「要不要用框架」的四问（面试里会被直接问，背下来）：

⭐ 第一问「流程是确定的吗」是最该先问的。它直接对应 什么是 Agent（与 Workflow 的边界） 那一页的核心判断：如果流程完全确定，那就不是 Agent，是 Workflow —— Workflow 不需要 Agent 框架，几次函数调用加一个 if 就是最稳的实现。

  • 数量级与形状：选型的成本能被具体数出来，这也是面试里最有说服力的部分：
成本项形状怎么估
**抽象税（调试栈) **出错时定位要多跨几层数一下从「报错」到「根因」中间隔了几个框架层
依赖风险一个依赖 = 一个版本约束面项目的纪律是把约束写进依赖声明、让 CI 去守（例：mcp>=1.28,<2）
迁移成本从「能跑」到「可对比」的距离项目实测形态见下面那一段
学习成本不是学 API 的时间，是建立正确心智模型的时间分界线是「你知不知道自己什么时候不该用它」

  • 机制：一个真实且最有价值的案例 —— 手写 supervisor 还是用现成的。这是本页要给你的主证据，因为它是面试官最可能认同的那类判断。

    YYHelp v2 的选择：手写 supervisor，不引入 langgraph_supervisor。三条理由（原文口径）：

    1. 提供的那套 create_react_agent 是薄封装 —— 它省下的是写代码的时间，代价是放弃控制权与可观测性；
    2. 重装一套等于放弃已经验收过的可靠性资产 —— 自己的工具执行壳、四道闸、三态终止都是自检覆盖过的；
    3. 多一个依赖 = 多一个版本风险面。

    另外还有一条环境事实必须如实讲：langgraph_supervisor 在当时的开发环境里未安装（出处：00-现状审计 环境节）。也就是说「不引入」这个决策同时有设计理由和环境约束两者。面试时如果说成「我评估后主动不用」，那是拔高；正确说法是「设计上我不认为它划算，同时环境里它也没装 —— 这两件事我都告诉你。」

  • ⚠️ 反面样本：不要写自己没落地的框架经验。这是 AI 方向简历最典型的翻车点。面试官只要做过这个框架，追问两层就能问出来：

    • 「你说的 X 里那个能力，你实际是在哪个文件里用的？」→ 答不出文件名；
    • 「你用的时候踩过什么坑？」→ 答不出任何具体症状；
    • 「那它的状态存在哪？」→ 开始含糊。

    判据：写上去的每一个框架名，都要能回答「我在哪个模块用它解决了什么问题、它的边界在哪、我为它付了什么代价」。 答不出这三样的，从简历上删掉。想知道某个框架值不值得写进简历，先花两小时做最小实验 —— 这比多写一行关键词有用得多。

  • 常见误区：

    • 给框架排名（「X 比 Y 好」）—— 没有场景的优劣判断都是错的；
    • 因为 JD 写了自己的项目里就加（负收益，和「为了简历关键词上 MCP」同源）；
    • 把「框架能做的事」当成「框架会替你负责的事」 —— 框架给的是能力，正确性仍然是你的责任（图要你画对、闸要你加、字段要你不丢）；
    • 只对比功能清单（功能清单是最不重要的维度，因为都能做）；
    • 忘了问「这个需求的确定性有多高」 —— 确定的流程用 Workflow，别硬做成 Agent。

L4-33 低代码平台搭 Agent（Coze / Dify / n8n） ​

  • 定义：低代码 / 无代码平台（典型代表：Coze、Dify、n8n）提供可视化的方式搭建 LLM 应用与 Agent：拖节点、连线、在界面上配置模型与工具，平台负责运行、托管、发布，通常还带知识库、日志与评估等配套能力。

  • 机制：它到底省掉了什么、又拿走了什么：

平台替你做了平台从你手里拿走了
开发运行循环、工具接入、状态管理、前端（不少平台直接给可发布的对话界面）细粒度的控制流表达 —— 平台没提供的节点类型，你表达不了
运维部署、扩缩、密钥托管、调用日志基础设施的掌控 —— 出问题时你只能等平台或换方案
数据知识库 / 向量检索开箱可用数据的可迁移性 —— 换个平台，索引与配置往往要重建
实验改一个节点立刻能试可复现性 —— 版本对比、A/B、回归门禁通常比代码方案弱
协作产品 / 运营同学能直接改流程工程纪律 —— 很多时候没有 code review、没有回归测试

⭐ 这张表的意义不是「平台不好」，而是让你在面试里能给出一个专业判断：平台的取舍是用可控性换交付速度。这两样东西都值钱，问题只是当前阶段哪个更缺。

  • 为什么这样设计（平台的存在理由）：三个真实理由，缺一不可：

    1. 它把「验证需求」的成本压到了极低。写代码做一个能对话的原型要几天，平台上可能几十分钟。而在 AI 应用里，「这个需求值不值得做」往往比「怎么做」更难回答。
    2. 它让非工程师能参与。产品、运营、业务方能直接改 prompt 和流程，这在需求每天都在变的场景里是真实收益。
    3. 它把一堆基础设施问题一次性解决。知识库、向量检索、密钥、日志、发布 —— 自己搭一遍要花掉数周，而且每一块都有坑。

  • 机制：什么时候不该用平台（这一节比上一节更值钱）：

出现这些信号说明该怎么办
你需要终止条件 / 预算控制 / 幂等这类精细约束平台通常只给你「最大轮数」这类粗粒度开关（见 终止条件与预算控制）关键链路自己写；或用平台做外围、核心自研
你需要严格可复现的评测与回归平台侧的版本对比与门禁能力通常弱于代码方案评测放在自己的 harness 里（见 评测与可观测）
你需要跨进程/跨语言复用工具平台内的工具不天然是一个可被别的系统消费的服务这就是 MCP 的适用场景（见 MCP 协议、传输与安全）
你开始和平台打架用一堆绕行手段实现平台没提供的控制流信号很明确：该换代码方案了
你只有一个人、要投简历平台项目很难展示工程判断平台用来做原型，简历上要讲的是你自己写的核心链路

⭐ 「什么时候不该写代码」的镜像问题同样重要：面试官问「你为什么不直接用 Coze / Dify 做一个」时，不要答「平台不专业」。正确的答法是承认平台的优势，再说清自己的取舍： 「平台在交付速度上完胜 —— 如果我只是想验证一个想法，我会先用它。但要做我这套东西，我不行：我需要每一个回环边都有自己的闸、需要写操作有幂等键与人工确认、需要自检能被 CI 执行。这三样在平台里表达不了，所以我核心链路是自己写的。这不是平台的问题，是我这次的目标是工程可控性而不是交付速度。」

  • 数量级与形状：

    • 平台的收益是「天数级到小时级」的差距，在小需求上非常划算；
    • 平台的成本是「迁移时的重建」 —— 所以选平台时最该问的不是「它今天能做什么」，而是「我如果想搬走，能带走什么」（prompt 与工作流的导出形态、数据与索引能不能迁移、能不能通过 API 被我的代码调用）；
    • 一个务实的分层用法：平台做门户与原型，自研做核心链路。平台提供一个能被人点开的入口、快速验证交互；核心的编排、终止、幂等、评测留在自己的代码里。这个形态在面试里是加分答案，因为它同时展示了两边的价值。

  • 常见误区：

    • 把平台项目和手写项目混为一谈地写进简历（面试官会以为核心逻辑是你写的）；
    • 以为「低代码 = 简单需求专属」 —— 平台也能做挺复杂的流程，问题不在复杂度而在控制维度；
    • 忽略了「可迁移性」这个长期成本；
    • 反向偏见：因为「看起来不硬核」而拒绝平台，白白多花几周做原型。

和你自己的项目对上号 ​

先给结论：你的选型故事是完整的 —— 有三条可讲的证据。

① 手写 supervisor，而不是引入现成的 supervisor（最值钱的一段） 三条理由：提供的封装是薄封装（省实现时间，换掉控制权与可观测性）、重装一套等于放弃已验收的可靠性资产、多一个依赖多一个版本风险面。同时必须如实交代环境事实：langgraph_supervisor 在当时的开发环境里未安装（00-现状审计 环境节）。这个「设计理由 + 环境约束」的双重事实比单一理由更可信 —— 面试官对「我全都主动评估过」的说法是有戒心的。

② v1 → v2 的框架迁移成本，你有实测形态 v1 只有 LangGraph 主图（7 个节点，graph/build.py 850 行）；v2 加了专家与 MCP。这个迁移的代价不是 import 改动，而是重建 A/B 基线：除被测变量外全部冻结，甚至把 v1 代码目录冻结只读（唯一例外是修了一个 --selftest 红着的真实缺陷）—— 判据原文：「A/B 对比的前提是基线不变。」 面试里这段能直接回答「换框架要花多少钱」。

③ 你也实践过「不写代码」的一面：项目里有基于平台的评测与对比资产（eval/ 下的 A/B 与 judge 流程），以及自建的观测与追踪 —— 也就是说你没有把「平台 vs 代码」当成立场问题，而是按「哪一部分需要精细控制」分工。这个分层用法本身就是 L4-33 的加分答案。

⚠️ 你需要守住的一条：你对上面那张框架对比表里的框架，只对 LangGraph 有实操经验（外加 MCP 生态）。其余框架（AutoGen / AgentScope / CrewAI / smolagents / Coze / n8n）不要写进简历、不要在面试里说「我用过」。正确说法：「我了解它们在控制粒度与多智能体表达方式上的差异，但我没有实际集成过 —— 我的实操集中在 LangGraph 与 MCP。」这一句诚实的话，加上你能讲清 langgraph_supervisor 那个取舍，比列出六个框架名强得多。

建议的补强动作（约 3 小时，成本低、收益明确）：挑一个对话/团队式框架做最小实验 —— 目标不是学会它，而是亲手感受「同样一件事，在图里和在角色对话里分别怎么写」。实验完写半页笔记，只回答三个问题：① 这个框架里「严格顺序」怎么表达？② 它有没有「每个回环边自己的闸」这种概念？③ 如果我要表达我今天那个「分派上限 + 反思上限」的双闸，需要加多少额外约束？回答完这三问，你在选型题上就从「读过对比文章」升级成「有过手感」。

面试怎么问 ​

Q1：你了解哪些 Agent 框架？怎么选？

A（要点）：我不做排名，我用三个维度定需求再选：控制粒度（从「你画图、框架只执行」到「你给目标、框架自己循环」）、多智能体的表达方式（图 / 角色对话 / 团队分工 / 流水线）、部署与状态形态（库 / 服务 / 平台）。这三个维度决定了「可控性 vs 上手速度」「协作形态能不能被表达」「能不能进生产链路」。落到具体：需要显式流程与确定性的选图式框架；探索性的多角色协商场景用对话/团队式框架更自然。

追问：那你实际用了哪个？为什么？

A：LangGraph。因为我要四样东西：显式流程、可持久化状态、可中断等人、以及能对每一条回环边单独加闸。这四样都要求「状态与流程是我显式定义的」。而且我做了一个具体的取舍：手写 supervisor，没有引入 langgraph_supervisor —— 三条理由：那套 create_react_agent 是薄封装（省实现时间、换掉控制权与可观测性）、重装一套等于放弃我已经验收过的可靠性资产、多一个依赖多一个版本风险面。另外环境事实也要说清：当时那个包在环境里也没装。

追问：那别的框架你了解吗？

A：我了解它们的设计哲学与适用边界 —— 比如有框架的核心抽象是「角色对话」，天然适合多角色讨论，代价是严格顺序与硬闸要额外约束；有框架的核心抽象是「角色 + 任务 + 团队」，上手最快但细粒度控制受限；还有框架主张「让模型写代码而不是填参数」，表达力强但把沙箱与安全变成必答题。但我没有实际集成过这些，所以细节我不敢说。 我的实操集中在 LangGraph 与 MCP，这一点我不想含糊。

再追问：那你凭什么能判断它们的边界？

A：因为我能把「框架的长相」和「它的目标场景」对上。一个框架长成图，是因为它瞄准可持久化、可中断的长流程 —— 要持久化就必须有显式状态，要分支循环就必须有显式边；图不是风格选择，是目标场景逼出来的。 长成对话，是因为它的起点是「多个模型互相讨论能提升质量」；而对话这种形态天生没有强制执行顺序。长成画布，是因为它瞄准交付速度。能解释「为什么它长这样」，就能判断「它到哪一格为止」。

Q2：你为什么不用 Coze / Dify 这类平台做？

A（要点）：平台在交付速度上是完胜的 —— 如果我只是想验证一个想法，我会先用它。但我这次要的四样东西它表达不了：每一个回环边都有自己的闸、写操作的幂等键与人工确认、自检能被 CI 执行、以及可复现的 A/B 对比。这不是平台的问题，是我这次的目标是工程可控性而不是交付速度。

追问：那平台有没有比自研更好的地方？

A：有，而且是结构性的。它把「运行循环、工具接入、知识库、部署、密钥、日志」一次性解决了 —— 这些自己搭要花数周，而且每块都有坑。更重要的是它把**「验证需求值不值做」的成本压到极低**，而在 AI 应用里「值不值得做」往往比「怎么做」更难回答。所以我不会反对用平台，我会反对只有平台。

追问：那如果需求变了，你会怎么调？

A：分层。平台做门户与原型，自研做核心链路。 平台负责一个能被人点开的入口、快速试交互；核心的编排、终止、幂等、评测留在自己代码里。这样我既拿到了交付速度，也没有把可控性交出去。选平台的时候我最关心的其实不是「它今天能做什么」，而是「我如果想搬走，能带走什么」—— prompt 与工作流的导出、数据和索引能不能迁移、能不能通过 API 被我的代码调用。

再追问：那你怎么说服一个坚持用平台的人？

A：不做立场之争，把取舍翻译成他关心的东西：平台用可控性换交付速度，两样都值钱，问题只是当前阶段哪个更缺。如果他的目标是两周内上线验证，平台就是对的选择；如果他的目标是一个要跑一年、要审计、要回归的东西，那可控性早晚会成为瓶颈 —— 而且那一天到来时，迁移成本会比分阶段做更贵。我能给的只是一个判断信号：当你开始用一堆绕行手段实现平台没提供的能力时，就该换方案了。

Q3：手写还是用框架？你的判断依据是什么？

A（要点）：四问。① 流程确定吗 —— 完全确定就不是 Agent 是 Workflow，几次函数调用就够，别引框架；② 需要分支/循环/状态吗，我自己能不能几十行写清楚 —— 能，就先手写；③ 需要持久化、中断、人工确认吗 —— 需要，图式框架的收益才真正出现；④ 框架的成本我付得起吗 —— 抽象税、依赖版本风险、迁移成本，三样都要算。

追问：框架的成本具体是什么？

A：三样，都能具体数出来。抽象税：出错时从「报错」到「根因」中间隔了几个框架层 —— 隔得越多，排查越贵。依赖风险：一个依赖就是一个版本约束面，我的做法是把约束写进依赖声明、让 CI 去守（例：mcp>=1.28,<2，因为大版本会直接改名）。迁移成本：这个我有实测感受 —— v1 只有一张 LangGraph 主图，v2 加了专家和 MCP，代价不是 import 改动，是重建 A/B 基线：除被测变量外全部冻结，甚至把 v1 目录冻结只读，唯一的例外是修一个 --selftest 红着的真实缺陷。

追问：为什么冻结这么较真？

A：因为判据是「A/B 对比的前提是基线不变」。如果基线被我顺手改了，我测出来的差异就不知道来自哪了。这条和「让自变量尽量少、且每一处差异都能被列出来」是同一件事 —— 我的两种模式（single / multi）差异只在四行（有无 plan/supervisor/memory/reflect、决策者、工具菜单、system prompt），第五六行（ReAct 内核、四道闸与三态终止）完全同源。

再追问：那你怎么知道「手写」没有变成「重复造轮子」？

A：看框架替我承担的部分，是不是我正在自己承担的责任。我的自检已经覆盖了「每个回环边都有自己的闸」「每个新字段都有断言」这些 —— 那框架能替代我的部分就很少，手写是划算的。反过来，如果我在某一块反复出问题（比如时间旅行的一致性），而那正好是框架的强项，那就说明我在重复造轮子，该换。判据是差距出现在哪里，不是框架的新旧，也不是「自己写显得硬核」。

Q4：低代码平台搭的 Agent 能不能写进简历？

A（要点）：能写，但必须写清哪些是你做的。平台项目的真实形态是「你配置出来的交付物」，面试官会默认你以为核心逻辑是你写的 —— 一旦他问「终止条件怎么控制的」「怎么保证不重复下单」而你答「平台里设的」，落差会很大。正确写法是区分「我用平台交付了什么」和「这条链路哪一部分是我实现的」，如果核心逻辑是平台给的，就别把它当成技术深度写。

追问：那平台经验就完全没用吗？

A：有用，但用的地方不同。它的价值在判断力展示：能说清「我为什么不自己做」「平台替我解决了哪些基础设施问题」「什么时候我会从平台迁到自研」。这属于架构判断，不是实现深度。我会把它写在项目背景或取舍讨论里，不写在技术栈那一行。

追问：那怎么让平台项目变得有说服力？

A：在平台之外补一层属于自己的东西。比如同样的需求，用代码实现其中最关键的那一段（编排、终止、幂等任选一个），然后说清「平台负责了什么、我负责了什么、为什么这样分工」。这样你既拿到了交付速度，又有了可被追问三层的实现细节 —— 面试官问的是你的判断与你的代码，不是你有没有用过某个平台。
