评测框架、CI 门禁与线上监控 ​

覆盖知识点：L6-11 L6-12 L6-13 L6-14 ｜ 面试频率：高 ｜ 建议学时：8h

一句话说清 ​

前三页讲的是「怎么算分」，这一页讲的是「让算分这件事自动发生，而且不让它说谎」。四件事串成一条链：框架（L6-11）解决「评测怎么组织成可重复的流程」；CI 门禁（L6-12）解决「改动什么时候允许合并」；线上监控（L6-13）解决「上线之后怎么发现真效果和评测集不一致」；人工评估（L6-14）解决「裁判拿什么当锚点」。贯穿这四件事的只有三条口径纪律：不假装跑过 / 报数必带口径 / 配置类开关必须配一个能失败的断言。这一页也是整层里最能体现工程成熟度的一页——因为它评的不是模型，是你的流程本身。

为什么必须学（面试官视角） ​

简历上「接入 CI 与回归门禁」这句话，在面试官眼里是一个高风险承诺。因为它可以被三层追问拆穿，而且三层都很难糊弄：

  1. 第一层——「你的门禁挡过谁？」 如果你的门禁从来没失败过，说明它没有门槛，只是在跑；能说出「挡过哪一次、因为哪个指标、当时怎么办的」才算数。
  2. 第二层——「你的检查项跑全了吗？」 这是最隐蔽的一层。本项目 run_all_checks.py 的 CHECKS 登记 19 项，实测 PASS 17 / FAIL 0 ——差额来自 SKIP 态。如果你只报「17 项全过」，面试官会算成「漏跑 2 项」（19 − 17 = 2），你瞬间从「有门禁」变成「连自己跑了多少项都说不清」。主动说出「19 项登记、17 项 PASS、2 项 SKIP，SKIP 的原因分别是什么」，是这一整层性价比最高的一句话。
  3. 第三层——「不可比怎么办？」 如果你的报告换过标尺（ground truth 版本、块数、题数变过），历史数字就不能沿着列连读。本项目 16 份历史报告跨越 ≥4 把尺子。报数字不带标尺，等于报了一个自己都不知道含义的数。

第三层还带着一条工程态度的加分项：机器 ground truth 的报告顶部自己写着「🚫 不可作为结论」。让报告自己声明它的边界——这个习惯比任何指标名都更能说明你懂评测。

核心内容 ​

L6-11 评测框架：把指标、数据集、报告串成可重复流程 ​

  • 定义：评测框架负责四件事——数据集加载与版本化、指标计算与并发调度、结果落盘与报告生成、与 CI/追踪平台的集成。它本身不产生任何结论，只保证「同一条命令、同一份数据、同一份判据，得到同一份报告」。

  • 机制与选型维度（各框架的具体 API 名、指标字段名与其版本差异以各框架官方文档为准）：

    维度取舍方向
    指标覆盖面内置多 = 上手快；自研判据多 = 内置库反而要绕开
    判据可替换性不允许换裁判模型 / 自有 rubric 的框架，会把你的口径绑死在它的实现上
    数据格式耦合强 schema 换来少写胶水代码，代价是迁移成本
    依赖量级重依赖会污染生产环境；评测依赖建议单独一组
    报告与基线没有基线机制 = 每次都要人肉看数字
    编排集成现成 CI 入口能省一天胶水，但退出码语义要自己确认

  • 为什么这样设计：因为评测的价值不在一次的结果，而在可重复性。跑不出第二次的评测，第一次多漂亮都没用——你无法判断第二次的差异来自代码还是环境。所以第一判据不是「指标多不多」，而是「它能不能被固定住」：数据集版本、裁判配置、并发与重试、输出格式全部固定。

  • 数量级 / 形状——隐形成本在「调用次数」：一次全量评测的调用次数大致是 样本数 × 指标数，裁判型指标再加一次。这笔账直接决定你能不能在每次 PR 上跑全量。常见做法是分层：PR 上跑小切片（快、稳、确定性断言为主），合并到主干后跑全量（含裁判型指标）。

  • 常见误区：

    1. 把框架当评测。装了框架不等于有评测——没有基线、没有门槛、没有退出码，它只是个报告生成器。
    2. 评测依赖混进生产依赖。体量大、版本要求松，容易在部署时撞依赖。
    3. 迷信内置指标名。不同框架对同一个名字的定义可能不同（分母是什么、要不要用 ground truth），换框架就等于换口径，历史数字不可直接连读。
    4. 没有 baseline 快照。没有基线，一次评测的绝对数字无法解读。

L6-12 接入 CI 与回归门禁 ​

  • 定义：把评测做成流水线的一个阶段，用退出码决定这次改动能不能合并。核心不是「跑评测」，而是「把评测变成一个会失败的检查」。

  • 机制——三态退出码（本页最重要的一个设计）：

    退出码语义工程含义
    0IMPROVEMENT / NSC（测不出差异）放行
    1REGRESSION（确认变差）阻断
    2INCOMPARABLE（标尺变了，不可比）不是「失败」，是「先对齐再跑」

    这个设计里最值得讲的一句是：「通过」和「测不出来」都是 0。因为**「测不出来」不等于「变差了」**——把 NSC 也判成失败，门禁会在小样本评测集上疯狂误报，最后所有人学会的只有绕过门禁。

    这是本项目真实落地的（task_metrics.py:231-234）。要特别说清一个容易搞错的地方：另一条链路上的 eval_regression.py:113-115 实际是二态的（return 1 if n_fail else 0）——只有「过 / 不过」，没有「不可比」。类似地，qa.py:10-14 另有一组三态语义（0 = 正常含拒答 / 1 = 未预期错误 / 2 = 配置错误），被 generate.py:479-481 复述。同一个「三态」思想在三个模块里各管一段——能分清哪套是二态、哪套是三态，本身就在展示你读过自己的代码。

  • 为什么这样设计（为什么门禁只测确定性断言）：因为回归门禁要求判据本身是稳定的。裁判模型有位置偏差与宽大偏差（见 LLM-as-a-Judge），temperature = 0.0 也不保证跨批次完全一致。把裁判型指标接成阻断项，结果就是同一份代码昨天过、今天挂——工程师的应对不会是修模型，而是关掉门禁。所以正确的分层是：

    层判据类型在门禁里的角色
    阻断层确定性断言（格式、字段、拒答行为、超时、健康检查、限流行为）失败即阻断
    观察层裁判型指标、统计检验（Completion / tokens / 墙钟）记录趋势，人工复核，不默认阻断

  • 「配置类开关必须配一个能失败的断言」——这条纪律值得单独记住。任何一个配置开关（"开启精排"、"开启多跳"、"切换到新裁判"）如果只有开的功能、没有「开启后如果不对就会报警」的断言，那这个开关就是不能验证的功能。写法上很简单：开关打开时同时断言一个可观测的副作用（比如开启精排后 R@5 必须不低于某个下限、或工具调用次数必须落在某个区间）。没有断言的开关，等于没有关闭能力。

  • 数量级 / 形状——一个真实可引用的 CI 结构：

    事实数值 / 落点
    检查项登记总数19 项（run_all_checks.py 的 CHECKS）
    实测结果PASS 17 / FAIL 0，差额来自 SKIP 态（run_all_checks.py:22-23）
    被收编的检查模块ci_checks.py（7.7KB）由 run_all_checks.py:50 调用
    集成层检查service_tests.py 是 run_all_checks.py:51 的 C 层检查：健康 / 限流 / 超时 / SSE
    与已知问题分离known_issues 与真实失败分开统计
    统计门禁退出码task_metrics.py:231-234：IMPROVEMENT 0 / REGRESSION 1 / NSC 0 / INCOMPARABLE 2
    门槛参数min_delta：完成率 0.05 / tokens 200.0 / 墙钟 2.0；alpha 0.05（task_metrics.py:392-396）

    两个设计要点：

    1. known_issues 与真实失败分开统计。已知问题如果混进失败计数，门禁会被长期噪音淹没，最后没人看红色。分开之后，失败列表里的每一条都是新的信息。
    2. min_delta 是门槛，不是精度。完成率门槛 0.05 意味着「差异小于 5 个百分点不值得阻断」，tokens 200.0 意味着「每次问答差 200 个 token 以内属于噪声」。门槛必须显式写进代码，不能靠人眼看数字决定。

  • run_all_checks.py 的分层结构（该文件的具体实现细节以其源码为准，这里是结构示意）：

    python

    # A 层：静态与单元级
    ("lint_and_imports",       run_lint_and_imports,       "A"),
    ("unit_tests",             run_unit_tests,             "A"),
    # B 层：组件级（被收编进来的检查模块）

    for name, layer, (status, detail) in results:
        if status != "PASS":
            print(f"  [{layer}] {name}: {status} — {detail}")

    return 1 if n_fail else 0                   # 注意：这里也是二态

    最后一行值得停一下：这一层检查只要「没有真实失败」就返回 0，是一个二态判断。三态是统计门禁那一层的事——两个模块的职责不同，混淆它们就会写出「跳过也当成失败」的门禁，然后所有 SKIP 都会变成红色噪音。能说清「我项目里有两个不同的门禁语义，各管一段」是非常强的一句回答。

  • 报告必须带标尺：16 份历史报告跨越 ≥4 把尺子（ground truth 版本不同、gt 块数不同、题数不同），因此不可沿列连读。工程做法是让报告自描述：报告头部写死「本报告使用的 gt 版本 / gt 块数 / 题数 / 日期 / 是否可用作结论」。本项目机器 gt 的报告顶部直接写着 「🚫 不可作为结论」——让报告自己声明它的边界，比事后让人记住边界可靠得多。

  • 常见误区：

    1. 报「17 项全过」而不报登记总数与 SKIP 数。会直接被算成漏跑。
    2. 把裁判型指标接成阻断项。抖动 → 误报 → 全员绕过门禁。
    3. 门禁从不失败。从没失败过的门禁等于没有门禁。
    4. 不区分「未预期错误」与「配置错误」。配置错误（缺 API key、路径写错）混进失败统计，会把真正的回归信号埋掉。
    5. 报告不带标尺。跨标尺连读历史数字是评测里最贵的错误，因为它看起来完全正常。

L6-13 线上监控与质量告警 ​

  • 定义：上线之后，用线上信号（真实流量、用户反馈、抽样评测）持续观察质量，发现漂移就告警，并把 bad case 自动采样回填到评测集。

  • 机制——三条线并行：技术指标（延迟分位 / 错误率 / 限流命中 / 超时，用途是可用性）、质量指标（抽样跑裁判或规则、拒答率、格式非法率，用途是效果漂移）、反馈指标（点赞点踩 / 转人工率 / 重复提问率，最贵也最真）。

  • 为什么这样设计（与评测的关系）：因为评测集是有偏的采样——它是你在过去某个时刻想到的失败类型，而线上会遇到你没想到的输入分布。所以监控不是「评测的重复」，而是评测集的供给管道：线上 bad case 采样 → 人工确认 → 进评测集 → 下一轮 CI 就会覆盖它。没有这条回流，评测集会在几个月内彻底老化。

  • 本项目真实素材（YYHelp 侧的可观测设计）：自研 JSONL trace 为默认路径 + Langfuse 为增强路径（具体 SDK 的 API 名、span 字段名、版本以 Langfuse 官方文档为准），同一 trace_id 把两条路径缝合起来。最值得讲的一条设计是：写入失败绝不抛异常，而是降级写一条 observability_degraded 记录。

    理由必须能说出来：可观测性系统本身不能成为单点故障。如果 trace 写入失败会抛异常，日志后端抖一下就把客服 Agent 打挂了——观测手段把生产过程打死，是最典型的自伤。降级标记的价值在于：trace 缺了，但你知道它缺了，不会把这批请求误读成「没异常」。

  • 数量级 / 形状：质量抽样率是成本 vs 灵敏度的取舍，没有普适值，按「每分钟请求数 × 抽样率 × 裁判单价」算预算。它必须是一个配置项，并且配一个能失败的断言——例如抽样率被配成 0 且不在白名单里时启动即报错：一个「静默地完全不抽样」的监控，看起来和「一切正常」一模一样。

  • 常见误区：

    1. 只有技术指标，没有质量指标。P99 好看、答案全错，仪表盘一片绿。
    2. 监控写入失败就抛异常，反过来把主流程打挂。
    3. 不回填评测集。监控只用来「看」，不用来「长出新的评测题」，评测集就永远停在第一天。
    4. 把 drift 当 bug 立刻回滚。漂移可能来自上游模型版本更新、数据分布变化或采样偏差——先定位漂移源再决定动作，与 可观测三支柱与调用链追踪 是同一套方法。

L6-14 人工评估与标注流程 ​

  • 定义：用有明确量表的人来打分，作为裁判的校准基线，并处理标注者之间的不一致。

  • 机制——三件必须做的事：

    1. 量表先行。写清每个等级「满足什么条件」才给这个分，并给出边界样例（最容易分歧的两个例子）。没有边界样例的量表一定会产生系统性的等级偏移。
    2. 双人标注 + 一致性校验。同一批样本至少两人标，算一致性系数（Cohen's kappa 适用于两名标注者与离散标签；Krippendorff's alpha 适用于多名标注者且允许缺测；有序分数可用 Spearman / Kendall 秩相关——各系数的实现与临界值以所用统计库和官方文档为准）。不要只报一致率：类别不平衡时一致率虚高得离谱。
    3. 分歧样本单独审理。不一致的样本不是「取平均」，而是量表定义不清的定位器——它们的分布告诉你量表哪一档写得含糊。

  • 为什么这样设计：因为裁判需要一个锚点，而锚点只能是人。这是 L6-08「Judge 对齐」在流程上的落地：没有人工校准，你报出来的裁判分数只是一个未经检验的测量仪器读数。

  • 数量级 / 形状——一个真实的反面教材：本项目 RAG 侧报告的答案准确率 65.2% / 91.3%，是旧 30 题口径、且 LLM 裁判未人工校准，与当前 130 题报告不是同一批次。同一个项目、同一个指标名，换题数与判据之后数值差了 26 个百分点——它们不能支撑任何结论，只能用来解释「为什么必须带口径」；具体哪条数字对应哪一版，以该报告自身标注的版本与日期为准。

  • 数量级 / 形状——人工标注的预算：按「样本数 × 每条标注耗时 × 标注人数」估工时。策略是分层抽样：不要在 79 个「1」和 1 个「0」里按 50% 比例抽（你永远抽不到那个 0），而要按判据维度分层（有依据 / 无依据、可回答 / 不可回答、单跳 / 多跳）各抽几条。

  • 常见误区：

    1. 量表只有等级名，没有判定条件。两个标注者用两套隐含标准。
    2. 自己标自己评（同一人既写规则又打分又不复核）。至少要有一个不一致检查环节。
    3. 只报一致率不报 kappa。
    4. 标注结果不做版本管理。标注集改了但没记版本，历史报告立刻失去可比性。

三条口径纪律（这一层所有页共用） ​

纪律违反时会怎样落地做法
不假装跑过被追问口径时答不出，整段经历的可信度归零没跑就说没跑；跑的是小切片就写小切片
报数必带口径两个不可比的数字被当成趋势解读每个数字附：样本量、gt 版本与块数、密度、比较对象、日期
配置类开关必须配「能失败的断言」开关是真是假无法验证，功能退化成不可测开关打开时同时断言一个可观测副作用

  • 报告带标尺：16 份历史报告跨越 ≥4 把尺子（gt 版本 / gt 块数 / 题数不同），不可沿列连读；机器 gt 的报告顶部自己写着「🚫 不可作为结论」。
  • 可以连读的正面对照（评测集 124 题 / gt 206 块 / 密度 1.66 块每题，三档同一把尺子）：① 纯向量 R@5 64.4% / R@10 73.7% / MRR 0.577；② 混合无精排 59.1% / 69.2% / 0.502；③ 混合 + 精排 71.8% / 77.4% / 0.714。

  • 三态落地：task_metrics.py:231-234（IMPROVEMENT 0 / REGRESSION 1 / NSC 0 / INCOMPARABLE 2）；门槛 min_delta 完成率 0.05 / tokens 200.0 / 墙钟 2.0，alpha 0.05（task_metrics.py:392-396）。

面试怎么问（5 组） ​

Q1：你的 CI 门禁跑了多少项检查？全过了吗？

A（要点）：登记 19 项，实测 PASS 17、FAIL 0，差额 2 项是 SKIP，SKIP 各自有明确原因。检查分三层：A 层静态与单元、B 层组件（ci_checks.py，由 run_all_checks.py:50 收编）、C 层集成（service_tests.py：健康 / 限流 / 超时 / SSE）。

追问一：为什么会有 SKIP？SKIP 算不算没跑？

SKIP 是显式状态，不是异常吞掉。它出现在前置条件不满足时（比如需要外部服务的检查在当前环境不可用）。关键是报告必须同时打印登记总数与四种状态，否则「17 项全过」会被读成「漏跑 2 项」——我自己就差点这么读。

再追问：如果 SKIP 变多了，怎么发现？ 把 SKIP 数当成一个独立的被观察量：它的趋势比 FAIL 更危险，因为 FAIL 是红的、SKIP 是灰的。灰的东西增加时没人会注意，直到某天门禁里只剩 3 项真的在跑。

Q2：回归门禁为什么只测确定性断言？

A（要点）：因为门禁要求判据本身稳定。裁判型指标有位置偏差与宽大偏差，temperature = 0.0 也不保证跨批次完全一致。把裁判接成阻断项，同一份代码昨天过、今天挂，工程师的正确应对不会是修模型，而是关掉门禁。

追问一：那裁判型指标不就白测了？

不白测，它进观察层：记录趋势、留报告、人工复核，但不默认阻断。分层是：阻断层放确定性断言（格式 / 字段 / 拒答行为 / 超时 / 健康 / 限流行为），观察层放裁判与统计检验。

再追问：那统计门禁（tokens / 墙钟 / 完成率）算什么层？ 中间层——可以阻断，但必须预先注册门槛，并且只在样本量够的时候解读。我的完成率 只有 1，那种情况它就是观察项，不能拿它挡人。门槛本身是显式的：min_delta 完成率 0.05、tokens 200.0、墙钟 2.0，alpha 0.05。

Q3：为什么「测不出来」也返回 0（放行）？

A（要点）：因为「没有显著差异」和「变差了」是两件事。把 NSC 判成失败，门禁会在小样本评测集上疯狂误报，最后所有人学会绕过它。「通过」和「测不出来」都是 0，只有确认回归是 1。 这不是放松：NSC 会单独打印进报告，避免被读成「通过了」。

追问一：那还有一种情况是「不可比」，怎么处理？

那是第三态，退出码 2，语义是「先对齐标尺再跑」。典型触发是 gt 版本变了、题数变了、gt 块数变了——我的 16 份历史报告跨 ≥4 把尺子，直接比就是拿两把尺子量同一段距离。

再追问：门禁在这时候应该做什么？既不能说通过也不能说回归，只能要求先对齐标尺再重跑。这也是为什么退出码要有三个值——二态门禁会把「标尺换了」误报成「模型变差了」，然后你花两天查一个不存在的问题。

Q4：线上监控你做了什么？

A（要点）：自研 JSONL trace 是默认路径，Langfuse 是增强路径，同一 trace_id 缝合两条路径。最关键的一条设计是写入失败绝不抛异常，降级写一条 observability_degraded。

追问一：为什么不抛？

因为可观测系统不能成为单点故障。日志后端抖一下就把客服 Agent 打挂，是典型的自伤。降级的价值在于——trace 缺了，但你知道它缺了，不会把它误读成「这次没异常」。

再追问：线上质量问题你怎么发现？ 三条线：技术指标（延迟 / 错误 / 限流）、质量抽样（规则 + 裁判，采样率是配置项）、用户反馈。三条线的 bad case 自动采样回填评测集——没有这条回流，评测集会在几个月内老化。这一点我必须如实说边界：项目是合成语料、没有真实用户，所以第三条线现在只有设计、没有真实数据。

Q5：你怎么保证报出去的数字是可信的？

A（要点）：三条纪律。不假装跑过——没跑就写没跑；报数必带口径——样本量、gt 版本与块数、密度、比较对象、日期；配置类开关必须配一个能失败的断言——没有断言的开关就是不可验证的功能。

追问一：举一个「没带口径」的反例。

我自己的：答案准确率 65.2% / 91.3%，那是旧 30 题口径、裁判未人工校准的数字，和当前 130 题报告不是同一批次。同一个指标名差 26 个百分点——不是效果变了，是尺子换了。所以这两个数字现在的唯一用途是当反面教材。

再追问：还有一个 100% 的指标呢？ 拒答准确率 100.0%——分母只有 6 道题。我一定会把「分母 6」和「100%」放在同一句话里说出来。不说分母的百分比，在面试里等于没说。
