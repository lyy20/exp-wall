本页目录

为什么必须评测、评测集构建与合成测试集 ​

覆盖知识点：L6-01 L6-02 L6-03 ｜ 面试频率：高 ｜ 建议学时：6h

一句话说清 ​

LLM 应用是概率系统：同一个 prompt 跑两遍能得到两个答案，所以「变好了」在这个系统里没有默认含义，必须先有一把尺子才谈得上「变好」。这把尺子由三件事组成——一批固定的题（评测集）、一套写清了分母的口径（指标）、一个独立于被测系统的标准答案（gt）。三者里任何一环出问题，指标都是在自己给自己打分。

本页讲清三件事：为什么没有评测就没有迭代（L6-01）；评测集怎么造，以及造法如何决定指标能说明什么（L6-02）；用 LLM 批量合成题目能省什么、又必然引入什么偏差（L6-03）。这三个知识点是后面 5 页的地基——02/03 讲指标怎么算，04 讲裁判怎么信，05/06 讲怎么接进流水线，但它们全部建立在「你手上有怎样一批题」之上。

为什么必须学（面试官视角） ​

面试官问「你的系统效果怎么样」，你答「挺准的」，这轮就结束了。分水岭在于：你会不会主动说出自己这次测量的适用边界。

  • HR / 简历侧：一份写了「RAG 问答准确率 91.3%」的简历，如果面试时被追问「严格口径呢」答不出来，会被直接判定为数字是抄的或编的。带口径的数字（「旧 30 题口径、LLM 裁判判定、未人工校准的严格 65.2% / 宽松 91.3%」）反而比一个大数字更有说服力，因为它证明你知道自己数字的产地。
  • 技术主管侧：这一层考的不是你会不会调 sklearn，而是你有没有能力怀疑自己的测量工具。真实面试里最高频的一击是「你怎么知道是它变好了，而不是题目变简单了」——答不上来，前面所有指标都会被重新打折。
  • 简历里有两个项目都写了评测，面试官必然顺着追。追的第一层是「多少题」，第二层是「gt 谁标的」，第三层是「这批题能检出多大的差异」。这三层正好对应本页三个知识点。

核心内容 ​

L6-01 为什么 LLM 应用必须评测 ​

  • 定义：评测不是「打个分」，而是给「变好」这个词下一个可复算的定义。它的产物是一组 (题集版本, gt 版本, 指标口径, 比较对象) 四元组齐全的数字。

  • 机制：评测要按顺序回答三个层次的问题，跳过任何一层，后面的数字都无意义。

    层次问题不解决的后果
    第一层：有没有尺子有没有一个固定题集，每次改动都跑一遍只能靠手感判断，改动不可比、不可回退
    第二层：尺子准不准gt 是怎么来的指标自己给自己打分：拿检索结果当 gt，检出率必然虚高
    第三层：尺子量的是什么口径有没有写清（分母、样本量、运行模式）「分数涨了」但不知道是系统变好，还是题目变友好

    第三层是最容易栽的一层。一个真实的例子：项目里有 16 份历史报告跨越至少 4 把尺子（gt 版本、gt 块数、题数各不相同），所以不可沿列连读——同一列里上下两行的分母可能不是同一个东西。

  • 为什么这样设计：概率系统没有「编译通过」这个信号。传统软件的「跑一遍测试」在这里必须升级成**「跑一批题 + 做统计检验」，因为单次运行的结果里混着随机性。这也是为什么评测成本要可控到能进 CI**——不能每次都跑的尺子，等于没有尺子。

  • 数量级与形状：一个可用的离线评测集，量级在几十到几百题。

    • YYHelp 侧：40 题（data/yyhelp/eval/questions.jsonl），题类分布 single_hop 12 / synonym 8 / unanswerable 8 / multi_hop 6 / exact_term 6，answerable 真 32 / 假 8。
    • RAG 侧：130 题（可回答 124 + 不可回答 6），填了 gt 的 124 题，gt 块总数 206，密度 1.66 块/题。
    • 报告的第一节必须是标尺，形如：可回答题 124｜填了 gt 的 124｜gt 块总数 206｜平均 1.66 块/题｜运行模式 --llm-final-only。没有这一节，任何数字都不许被引用。

  • 常见误区：

    1. 把「分数下降」当成「系统变差」——先要排除题目变了、分母变了、运行模式变了。
    2. 报一个不带样本量的百分比。100.0% 分母只有 6 道题时几乎不含信息（见 03-generation-metrics）。
    3. 一次改动只跑一题两道「看着对」就算通过——那两道题往往是改动之前就对的。
    4. 用被测系统产出的结果造 gt（见下节）。

  • 代码：最小可跑的评测骨架。注意两处「必须炸」的设计——缺失文件炸、空题集炸，因为「静默空跑并通过」是评测里最贵的一类 bug。

python
import json
import pathlib

def load_eval_set(path: str) -> list[dict]:
    p = pathlib.Path(path)
    if not p.exists():
        raise FileNotFoundError(path)        # 缺文件必须炸，不能静默空跑
    rows = [json.loads(ln) for ln in p.read_text("utf-8").splitlines() if ln.strip()]
    if not rows:
        raise ValueError(f"评测集为空：{path}")  # 空集不算"跑过了"
    return rows

def run_eval(eval_set, answer_fn, metric_fns) -> dict:
    """answer_fn(question) -> dict；metric_fns: {名称: fn(records, eval_set)}"""
    records = []
    for item in eval_set:
        out = answer_fn(item["question"])
        records.append({"qid": item["qid"], "question": item["question"], **out})
    return {name: fn(records, eval_set) for name, fn in metric_fns.items()}

L6-02 评测集构建方法 ​

  • 定义：评测集 = 题 + 标准答案（gt） + 元数据（题类、可否回答） 三件套。构建路径有三条，实际项目里通常是混合使用。

    路径做法优点固有偏差
    ① 真实问题从线上日志 / 用户提问里抽样最贴近真实分布早期产品没有真实流量时就造不出来；且真实问题里大量重复与噪声
    ② 文档反推读语料块，人工或半自动出题覆盖可控，能定向补冷门主题出题时已经看到答案在哪一块 → gt 天然在库里，绝对分数虚高
    ③ 人工标注先有题，再由人读原文标 gt最可信贵，而且标注者会被检索结果锚定

  • 机制（gt 纪律）：gt 必须是你真的去看过、确认答案在那里的 chunk，不许猜。项目的做法是把这条纪律写死在工具 docstring 里，并用两个互补工具分工：一个从答案出发（抽关键串 → 在前 N 个候选块里搜，带检索偏置）、一个从语料出发（关键词/数值直接定位切片，完全独立于检索）。两者交叉才能判断某题该标哪一块。

    为什么必须交叉：只用「从答案出发」的那个工具，标注者看到的候选本身就是检索器的输出，于是 gt 会系统性偏向检索器已经召回的块——这不是标注，这是给检索器抄答案。

  • 数量级与形状：

    • gt 密度决定 Recall 的难度。Recall@k 的分母是 gt 块数，不是题数，所以gt 越稀疏越容易拿高分：一道题只有 1 块 gt，命中 1 块就是 100%；另一道题有 3 块 gt，命中 2 块只有 66.7%。项目实测密度 1.66 块/题（multi_hop 2.56 块/题 vs single_hop 1.30 块/题）。
    • 题集规模与来源要一起报。RAG 侧 130 题 = 旧 30 题 + 新增 N001–N100；新 100 题是读语料块出题，旧 30 题是先有语料后出题，两者的 gt 密度不同（新 1.63 vs 旧 1.79 块/题）。按来源分解之后才能判断「是系统变好了还是题目变友好了」：新 100 题 74.2% vs 旧 30 题 61.8%，只有旧题那一行的变化才是系统侧的真实变化。
    • 负样本不是永久属性。项目扩库后，7 道「不可回答」题里 1 道（U07）其实已经可回答（论文的 future work 提到了关键词，检索必然命中，但正文没答案）；盲标复核转题后，拒答准确率从 85.7% → 100.0%。负样本是语料的函数，扩库就要重审。

  • ⭐ 一个必须讲得出来的真实病例：Recall@10 == Recall@5

    报告里两列完全相等，第一反应是「排序已经完美了」。错。 正确性断了两次：

    1. 第一段（死参数）：top_k 参数从未被使用，只在函数签名里出现过 1 次 → retrieved[:10] == retrieved[:5] 恒成立。
    2. 第二段（修好后仍然相等）：生成 gt 候选的脚本只取 retrieve()[:5]，标注的人只看了前 5 个候选。凡是答案落在第 6–20 位的题，gt 块根本不可能被标出来。

    于是有数学后果：

    用 top-10 真实名次审计后的分布：名次落在 1–5 位的 21 道、6–10 位的 0 道——这正好是「gt 必然是 top-5 子集」的签名。

    修好之后暴露的信息才有价值：不做精排时，R@10 比 R@5 高 11–14 个百分点。含义是答案其实已经召回了，只是没排进前 5——「检索不到」要改召回，「排不上来」要改排序。那个 bug 把这个事实从报告里彻底抹掉了，让排序问题一直进不了待办清单。

  • 为什么这样设计：把「评测集」和「被测系统」在流程上隔开（换会话、不看分数、独立工具），是因为人会被锚定。项目做过一次独立盲标：换会话、不看检索分数、直接读原文复核，结果 Recall 从 87% 掉到 71%，并推翻了两条已有结论。掉下来的 16 个百分点不是退步，是原来的 87% 里有 16 个点是标注者被检索结果锚定出来的。

  • 常见误区：

    1. 用被测系统的输出造 gt。RAG 侧的机器 gt 取自 ③ 组的 top-5 ⇒ ③ 组 R@5 必然是 100.0%（实测 ③ 组 100.0%/100.0%/0.906）——这个数字是构造出来的，不是测出来的。正确做法不是删报告，而是让报告自己声明无效：那份报告顶部写着「🚫 本报告不可作为结论」。
    2. 换切片配置后继续沿用旧 gt：切片配置一换，chunk_id 全变，旧 gt 全部悬空 → 跨配置只能比趋势并注明限制。
    3. 让脚本自动修复 gt。项目踩过：自动修复「无引文支撑的 gt 块」时删掉了含答案的块 ⇒ 改为只允许「补」不允许「删」（多部件答案里引文只覆盖一半是正常的）。
    4. 自检里的分母硬编码：gt_chunks 已回填 124/23 里的 124/23 是旧题集时代的常数，换题集后既不是 124 也不是 23，自检却仍然「通过」。自检脚本里的常数，就是下一次的假通过。

  • 代码：题目集体检脚本。分母动态计算，且把「没有 gt 的题」单独报出来而不是当成 0 分。

python
from collections import Counter

def describe_eval_set(rows: list[dict]) -> dict:
    n = len(rows)
    n_gt = sum(1 for r in rows if r.get("gt_chunk_ids"))
    gt_blocks = sum(len(r.get("gt_chunk_ids") or []) for r in rows)
    return {
        "n_total": n,
        "n_with_gt": n_gt,
        "gt_blocks": gt_blocks,
        # 1.66 就是这一行的值；分母用 n_gt 而不是 n，否则密度会被空 gt 的题稀释
        "gt_density": round(gt_blocks / n_gt, 2) if n_gt else None,
        "type_dist": dict(Counter(r.get("type", "unknown") for r in rows)),
        "answerable": dict(Counter(bool(r.get("answerable")) for r in rows)),
    }

L6-03 合成测试集生成（Testset Generation） ​

  • 定义：用 LLM 从语料批量生成问题—答案对，把「造题」这个人力瓶颈换成算力。产物是一份带来源溯源的合成题集。

  • 机制（标准四步）：

    1. 取块：从语料里挑出「有可出题事实点」的块（有明确数值、定义、条件分支的块优先）；
    2. 出题：让模型只根据这一段写一个有唯一答案的问题，同时给出答案；
    3. 回填 gt：gt_chunk_ids = [该块 id]——这一步是构造出来的，不是标出来的；
    4. 去重与配比：同块多题要去重（否则同一事实点会被计多次）；简单题 / 多跳 / 不可回答问题要按目标比例配。

  • 为什么这样设计，以及代价在哪：合成题解决的是覆盖度问题——人工出 100 题要几天，合成 100 题要几十分钟，而且能定向补冷门主题（项目里新增 100 题覆盖 9 类主题，其中 6 类是旧 30 题完全没碰过的方向）。但它带来一条不可消除的偏差：

    合成题的 gt 必然存在于库里，且必然是出题时读到的那一块。 所以合成题的绝对分数天然偏高，而且它们的分数与手写题的分数不可互相比较。

    这条偏差在数据里看得见：新 100 题 gt 密度 1.63 块/题，旧 30 题 1.79 块/题——同一份报告里的两组题，尺子不是同一把。所以合成题集的正确用法是**「自己和自己比」**：固定这批题，比较两次改动的分数差；不要拿合成题的绝对分去对外宣称系统能力。

  • 数量级与形状：

    • 合成题集也必须报来源占比。130 = 30 手写 + 100 合成 意味着77% 的题是合成题——这个比例本身就是一条必须写进报告的口径。
    • 不可回答的合成题要单独设计：项目的原则是「库里有这个词，但没有答案」。例如 U07「多智能体 RL 中如何处理环境的非平稳性？」——论文的 future work 提到多 USV 协同，检索一定命中，但正文没给答案。这类题的构造逻辑与「随便编一个库里没有的问题」完全不同，后者测的是「检索器认不认得这个词」，不是「模型会不会硬答」。

  • 常见误区：

    1. 把合成题当成真实分布。合成题从语料出题，天然没有真实用户的问法（错别字、指代、省略、多意图），所以用合成题测不出「听不懂人话」这类失败。
    2. 不去重：同一块生成 5 道几乎同义的问题，等于把这一道题的权重放大 5 倍，指标会被少数块主导。
    3. 把合成题的绝对分写进简历而不注明来源——这正是「分数涨了但系统没变好」的典型来源。
    4. 忘记录日期与生成参数：合成题集是一个产物，产物没有版本号就无法回溯。
    5. Ragas 等框架的 testset generation 具体 API、参数名与产物字段以官方文档为准——本页只讲机制，不写具体方法名。

  • 代码：合成骨架。关键不是调用方式，而是每一条题都必须带溯源字段（source + gt_chunk_ids + source_chunk），否则这批题将来无法审计。

python
def synthesize(chunks, llm, *, per_chunk: int = 1) -> list[dict]:
    """chunks: [{"chunk_id": str, "text": str}]；llm(prompt) -> {"question","answer"}"""
    out = []
    for ck in chunks:
        for i in range(per_chunk):
            qa = llm(
                "仅根据下面的片段出一道有唯一答案的问题，并给出答案。"
                "问题里不要出现「根据上文」这类指代。\n"
                f"片段：{ck['text']}"
            )
            out.append({
                "qid": f"{ck['chunk_id']}#{i}",
                "question": qa["question"],
                "answer": qa["answer"],
                "gt_chunk_ids": [ck["chunk_id"]],  # ⚠️ 构造性 gt，必然在库里
                "source_chunk": ck["chunk_id"],
                "source": "synthetic",             # 必须能一眼区分合成题与手写题
            })
    return out

面试怎么问（4 组） ​

Q1：你的评测集多大？

A（要点）：分开报两套。YYHelp 40 题、五类题型配比 + answerable 32/8；RAG 130 题（可回答 124 + 不可回答 6）、填了 gt 的 124 题、gt 块总数 206、密度 1.66 块/题。然后主动补一句：「但题目数量本身不说明任何事——关键看其中有多少题能区分我要比较的两条臂。」

追问（中层）：那 RAG 那边的 130 题是怎么来的？

A：两条来源，必须分开报：旧 30 题是先有语料后出题；新增 N001–N100 是读着语料块出题——出题时已经看到某一块包含答案。所以它们的 gt 密度不同（新 1.63 vs 旧 1.79 块/题），绝对分数不可互相比较。我按来源分解过：新 100 题 74.2%、旧 30 题 61.8%，只有旧题那一行的变化才是系统侧的真实变化。

追问（深层）：那你怎么保证后来标 gt 的时候没被自己的系统带偏？

A：有一次真实打脸——我做了一次独立盲标：换会话、不看任何检索分数、直接读原文复核。结果 Recall 从 87% 掉到 71%，并且推翻了两条我已经写下来的结论。掉下来的 16 个百分点不是系统退步，是原来那 87% 里有 16 个点是我自己被检索结果锚定出来的。所以我现在的防线有三条：① 纪律写死在工具的 docstring 里——gt 必须是真的去看过、确认答案在那里的 chunk，不许猜；② 两个互补工具交叉，一个从答案出发（带检索偏置）、一个从语料出发（完全独立于检索）；③ LLM 裁判看不到任何检索排名和分数，只看到【问题 + 期望答案 + 某一块原文】，所以它是内容判断，跟「检索器认为哪块相关」是两条独立路径。指标的可信度不取决于数字多高，取决于标注流程是否独立于被测系统。

Q2：你的 Recall@10 和 Recall@5 为什么早期完全相等？

A：不是排序完美，是标注窗口造成的构造结果。 断了两处：第一次是 top_k 参数从来没被使用过，只出现在函数签名里一次，所以 retrieved[:10] 就是 retrieved[:5]；我修好之后发现两列还是相等，才回头查到真正的原因——生成 gt 候选的脚本只取 retrieve()[:5]，标注的人只看了前 5 个候选，所以凡答案落在第 6–20 位的题，gt 块根本不可能被标出来。gt 是 top-5 的子集，R@10 在数学上就不可能高于 R@5。

追问（中层）：修好之后你看到了什么？

A：不做精排时，R@10 比 R@5 高 11–14 个百分点。 意思是答案其实已经召回了，只是没排进前 5。它把两类问题分开：「检索不到」要改召回（换 embedding、扩 top_k、加术语表），「排不上来」要改排序（加精排、调融合）。那个 bug 的危害是把这个事实从报告里彻底抹掉了，让我一直以为排序没问题。

追问（深层）：你怎么确定这次不是又一次构造性假象？

A：我用 top-10 真实名次审计去验证：修好之后看每道题 gt 的真实名次分布，落在 1–5 位的 21 道、6–10 位的 0 道——这个分布本身就是「gt 是 top-5 子集」的签名。所以我现在有一条通用判据：「两列数字相同」要先排除构造性解释，再怀疑模型。 这条已经成了我项目里的一条坑记录。

Q3：你用 LLM 合成过题吗？合成题能不能用？

A：用过——新增的 100 题是读着语料块出的题，合成题占了我 130 题里的 77%。能用，但只能用来自己比。因为合成题有一条不可消除的偏差：gt 必然存在于库里，而且必然是出题时读到的那一块，所以它的绝对分数天然偏高，跟手写题的分数不是同一把尺子。我留了溯源字段（source / source_chunk / gt_chunk_ids），随时能区分哪些是合成的。

追问（中层）：合成题测不出什么？

A：测不出「听不懂人话」。合成题从语料出题，天然没有真实用户的问法——错别字、指代、省略主语、多意图混在一句里。而我的 YYHelp 里 synonym 8 题、multi_hop 6 题是专门为这类问法设计的，还标了跨域题占比 3/40 = 7.5%，判据是 < 10%。这部分只能手写，合成不出来。

追问（深层）：那你怎么控制合成题的质量和配比？

A：三件事。① 去重——同一块生成多道近义题会把这一道题的权重放大几倍，指标会被少数块主导；② 配比——简单题 / 多跳 / 不可回答按目标比例配，而不是让模型自由发挥；③ 不可回答题单独设计。我的原则是「库里有这个词，但没有答案」：比如 U07「多智能体 RL 中如何处理环境的非平稳性？」——论文的 future work 提到多 USV 协同，检索一定命中，但正文没给答案。这跟「随便编一个库里没有的问题」完全不同，后者测的是检索器认不认得这个词，不是模型会不会硬答。另外还有一条现实修正：扩库之后我发现 7 道负样本里有 1 道（U07）其实已经可回答了——负样本是语料的函数，扩库就要重审。转题之后拒答准确率反而从 85.7% → 100.0%。

Q4：如果让你从零给一个新的 RAG 项目建评测集，你怎么做？

A：按顺序四步，每一步都有交付物。① 先有语料再出题错的顺序要反过来——先定题型配比与目标规模，再出题：单跳 / 同义改写 / 多跳 / 精确术语 / 不可回答各占多少，写死成目标。② 标注必须盲：换会话、不看检索分数、直接读原文；工具准备两个，一个从答案出发（知道它有偏置）、一个从语料出发（无偏置），交叉判断。③ 报告第一节写标尺，包括题数、填了 gt 的题数、gt 块总数与密度、运行模式、日期；gt 版本 这一行如果真是空的，就如实留空并注明「跨版本比较一律无效」，而不是填一个看起来完整的版本号。④ 【待确认：新项目的具体题型配比与规模】 这一步我给不出数字，因为它取决于你的语料规模和真实问题分布——我会先跑一次现状统计（describe_eval_set）再定目标。
