LLM-as-a-Judge：用法、偏差与对齐 ​

覆盖知识点：L6-07 L6-08 ｜ 面试频率：高 ｜ 建议学时：4h

一句话说清 ​

开放式生成（客服回复、报告摘要、多轮对话）没有唯一正确答案，无法用精确匹配或 F1 打分，于是用「一个模型 + 一份评分规则」去给输出打分，这就是 LLM-as-a-Judge。它解决的是可扩展性问题：人工评估准确但成本随样本量线性上涨，裁判模型一次调用就是一份标注。代价是——你换了一个尺子，而尺子本身有系统性偏差：偏好靠前的位置、偏好更长的回答、偏好自己家族的输出、以及最普遍的一条「不爱给差评」。所以这一页的后半部分讲的是怎么把裁判校准回人类口径：固定量表、控制位置、用一小批人工标注当锚点算一致性、把一致性数字连同评测结论一起报出来。

为什么必须学（面试官视角） ​

面试官问「你的 RAG 项目效果怎么评的」，如果你只答「用 LLM 打的分」，这个回答会被立刻钉住三层：

  1. 第一层——你没意识到裁判是变量：「你换一个裁判模型，结论还成立吗？」答不上来，说明你的「效果提升」可能是裁判换了个口味。
  2. 第二层——你没看分布：「你的裁判给过几次不及格？」如果你的裁判在 80 条样本里给了 79 次「通过」（这是本项目真实发生的事），那它测的不是质量，是你自己的期望。一个不会说「差」的裁判，对回归门禁毫无价值——因为回归门禁恰恰要靠它发现变差。
  3. 第三层——你的门禁是个摆设：「如果裁判有位置偏差，你把它接进门禁会怎样？」答案是门禁会随样本顺序抖动，同一份代码昨天过、今天挂。

反过来，这一页是性价比最高的加分位。绝大多数应届简历写到「用 LLM 评估」就停了；能说出「我用 40 题双盲做位置对照、裁判的通过率 79/80 说明它没有区分度、所以我把它降级成辅助信号，主判据换成确定性断言」的人，直接跨到「做过系统」那一档。

核心内容 ​

L6-07 LLM-as-a-Judge：什么时候用、怎么用 ​

  • 定义：用一个（通常更强的）LLM 作为评分器，输入是「待评输出 + 评分规则 +（可选的）参考答案 / 检索上下文 / 用户问题」，输出是一个分数或一个等级，以及一段理由。

  • 机制——四种基本形态，先确定你在用哪一种，否则后面的偏差讨论全是空谈：

    形态裁判看到什么适用主要风险
    Reference-free 打分只有问题 + 回答风格、有用性、安全性无客观锚点，最容易被冗长与语气带跑
    Reference-based 打分外加参考答案有标准答案的任务参考答案本身的质量成了上限
    Grounded / Faithfulness 打分外加检索到的上下文RAG 的「答案有没有依据」上下文里没有的信息被判为幻觉（假阳性）
    Pairwise 偏好两个回答 + 位置A/B 对照、模型选型位置偏差直接污染结论

    Pairwise 的分数本身没有绝对含义：它只回答「在这对样本里哪个更好」。把它当成一个 的连续分去算「提升了 0.03」是常见的越界用法。要做强度判断，得让很多对样本胜率构成一个分布，再对分布做检验（见 多轮与轨迹评测）。

  • 为什么这样设计：因为人写不出「什么是好回答」的完整规则。传统 NLP 用 BLEU / ROUGE 这类 n-gram 重叠度指标，它隐含假设「好答案 = 和参考答案字面接近」——这个假设在开放生成上直接失效：一个用词完全不同但完全正确的回答会被判低分。裁判模型的价值就在于把「语义等价」这件事交给一个能理解语义的东西来判断。

  • 数量级 / 形状：裁判是一次额外的模型调用，所以成本与延迟按「评测样本数 × 每题判据数」放大。这带来两条工程约束：

    • 裁判调用也要并发与限流，否则一次全量评测会把配额打满、触发上游 429（错误处理见 并发、限流与退避）。
    • 评测集的规模要先做功效分析再定，不然你会花几千次裁判调用得出一个「测不出来」的结论。

  • 常见误区：

    1. 以为 temperature = 0.0 就等于完全确定。它只保证贪心解码，在多机、多批次、MoE 路由或后端换版本的情况下仍可能有微小差异。所以「同一份评测跑两次结果完全一致」这个假设不能当基线用——门禁不能依赖它。
    2. 把裁判理由当证据。理由是一段生成文本，它可能事后合理化一个随手给出的分数。理由只用来帮你抽查，不用来做统计。
    3. 用同一批数据既调规则又报分数。这是评测里最经典的数据泄漏：你把评分规则改到在这批样本上好看，报出来的就不是泛化性能。
    4. 只报一个平均分。分布形状（多少条满分、多少条零分、有没有中间地带）比均值信息量大得多。

  • 代码（可运行的最小裁判，要点在参数与截断，不在框架）：

    python
    import json, hashlib
from openai import OpenAI

client = OpenAI()

JUDGE_RUBRIC = (
    "你是严格的评测员。根据【问题】与【检索上下文】判断【回答】是否满足：\n"
    "1) 断言都能在上下文中找到依据；2) 直接回应问题；3) 不编造引用。\n"
    "score=1 表示全部满足，score=0 表示存在任一条不满足。\n"
    "只输出 JSON：{\"score\": 0|1, \"reason\": \"不超过 60 字\"}"
)

# 截断长度必须是常量：它会改变裁判看到的信息量，也就改变了分数口径
MAX_ANSWER_CHARS = 1500

def judge(question: str, context: str, answer: str, model: str = "your-judge-model") -> dict:
    payload = (
        f"【问题】{question}\n【检索上下文】{context}\n"
        f"【回答】{answer[:MAX_ANSWER_CHARS]}"
    )
    key = hashlib.sha256(f"{model}|{JUDGE_RUBRIC}|{payload}".encode()).hexdigest()
    cached = JUDGE_CACHE.get(key)          # 评测必须可重放：同一输入不重复付费
    if cached is not None:
        return cached

    resp = client.chat.completions.create(
        model=model,
        temperature=0.0,                    # 贪心，降低抖动；但不等于确定性
        response_format={"type": "json_object"},
        messages=[
            {"role": "system", "content": JUDGE_RUBRIC},
            {"role": "user", "content": payload},
        ],
    )
    raw = resp.choices[0].message.content
    try:
        out = json.loads(raw)
        score = int(out["score"])
    except (json.JSONDecodeError, KeyError, TypeError, ValueError):
        # 解析失败必须留痕，不能静默当成 0 分——否则「分数下降」其实是「格式坏了」
        return {"score": None, "reason": f"PARSE_ERROR: {raw[:200]}"}
    if score not in (0, 1):
        return {"score": None, "reason": f"OUT_OF_RANGE: {score}"}
    result = {"score": score, "reason": str(out.get("reason", ""))[:200]}
    JUDGE_CACHE[key] = result
    return result

L6-08 Judge 对齐与偏差治理 ​

  • 定义：偏差治理 = 先用实验证明存在哪种偏差，再用结构性手段把它从结论里剔掉，最后用一小批人工标注量化「裁判与人还剩多少差距」。

  • 机制——四类偏差与对应的抵消手段：

    偏差表现抵消手段
    位置偏差把两个回答对调后，裁判偏好翻转每对样本跑正反两遍，只统计结论一致的样本
    冗长偏差更长、更分点的回答拿高分等长截断、或先归一化再判
    自我偏袒裁判对自家家族模型输出给高分裁判模型与候选模型来自不同家族
    宽大 / 中心趋势几乎不给差评，或全给中间分强制二选一（无「差不多」选项）、或按分布做阈值化

  • 为什么这样设计：因为这四类偏差都不是随机噪声，而是有方向的系统误差。随机噪声可以用更多样本平均掉，系统误差不会——你采一万条，它仍然整体偏移一个常数。位置偏差的正解只有「对称化」（A/B 两次）这一种，加样本量没有用。

  • 数量级 / 形状——用真实数据看清「宽大偏差」长什么样：本项目的 YYHelp 侧用 deepseek-v4-pro 作裁判，temperature = 0.0、response_format = {"type": "json_object"}、回答截断 1500 字符，对 80 条回答（40 题 × 2 臂）做 grounded 判定。结果是判「1」79 条 / 判「0」1 条，通过率 79/80。

    这个数字要分两面读：好消息是裁判口径确实对齐了「答案有依据」这件事；坏消息是它几乎没有区分度——一个 98.75% 输出同一个值的评分器，信息熵极低，它无法支撑「这一版比上一版好」的判断，更不适合接进回归门禁。正确的处理不是删掉它，而是降级：把它当「粗筛」，主判据换成确定性断言（这部分设计见 评测框架、CI 门禁与线上监控）。

  • 校准流程：一致性度量可选 Cohen's kappa（两标注者、离散标签）、Krippendorff's alpha（多标注者、可缺测）或 Spearman / Kendall 秩相关（有序分数）。别只报一个「一致率」——一致率不扣除随机一致，类别极不平衡时（例如 79/80 这种分布）一致率会虚高得离谱。具体系数与其临界值以所用统计库和官方文档为准。

  • 代码思路（对称化位置的最小实现，与语言/框架无关）：

    python
    def pairwise_debiased(judge_fn, q, ans_a, ans_b):
    """跑两次对调位置，只保留结论一致的样本。"""
    first  = judge_fn(q, ans_a, ans_b)   # A 在前
    second = judge_fn(q, ans_b, ans_a)   # B 在前
    if first is None or second is None:
        return {"winner": None, "reason": "judge_failed"}   # 失败不投票
    flip = {"A": "B", "B": "A"}
    if flip[first["winner"]] == second["winner"]:
        return {"winner": first["winner"], "consistent": True}
    # 不一致 = 位置偏差生效。它是"不可比"，不是"平局"，两者不能混为一类
    return {"winner": None, "consistent": False, "reason": "position_flip"}

    关键在最后一行：位置翻转导致的「无结论」必须与「真的打平」分开统计。如果把它们合并进「平局」，你的胜率会被系统性稀释，A/B 之间再大的差异也可能被抹平成「没有显著差别」。

  • 常见误区：

    1. 只报一个裁判分数，不报人工一致性。没有一致性数字的裁判分数，在面试里等于没有证据——面试官无法判断这个分数可信到什么程度。
    2. 拿裁判当唯一裁判。任何由裁判得出的「提升 X%」都应附带：裁判模型、判据版本、样本量、以及与人（或与另一裁判）的一致性。
    3. 用裁判去判它判不了的事。裁判可以判「有没有依据」「切不切题」，判不了「这个回答是否让用户满意」——后者需要真实用户信号，而合成语料项目根本没有（见下文）。

科研文献 RAG 侧：报告里的答案准确率 65.2% / 91.3% 是旧 30 题口径、且 LLM 裁判未经人工校准，与当前 130 题报告不是同一批次。这两条历史数字就是「Judge 对齐」这一节的现成反面教材——同一个项目、同一个指标名，换了题数和判据之后数值差 26 个百分点。引用它们时必须带口径（题数、批次、裁判是否校准），否则就是在用一个自己都不知道含义的数字。

缺口与补法：本项目没有做过真正的 Judge–人工一致性度量。要补的话，最小可执行版本是：从 80 条里分层抽 20 条（不要把 79 个「1」和 1 个「0」按比例抽——按比例只会抽到 1），自己标一遍，算一次 kappa，把数字写进报告。这 20 条同时为 人工评估流程 一节提供了素材。

面试怎么问（≥3 组） ​

Q1：你为什么用 LLM 当裁判？为什么不直接人工评？

A（要点）：两类任务分开答。有唯一答案的（引用了不存在的文献、字段格式对不对）我用确定性断言，人工和裁判都不需要。开放式的（回答有没有依据、切不切题）人工评准确但成本随样本量线性涨，评测集又必须能反复跑，所以用裁判做可扩展的那一层，人工只在校准环节花一次。

追问一：那你怎么知道裁判是准的？

我报的不只是分数，还有口径：裁判模型、判据文本、样本量、截断长度。而且我知道自己这条链现在是断的——我做过裁判，但没做过与人工的一致性度量，所以我不会说「准确率 X%」这种话。

再追问：那你现在凭什么相信 79/80 这个结果？ 我不把 79/80 当质量证明，我把它当偏差证据。40 题 × 2 臂共 80 条判定里只有 1 条判 0，说明这个裁判几乎不给差评、区分度接近零。所以我把它降到辅助信号（粗筛明显离谱的回答），门禁的阻断权交给确定性断言。

Q2：LLM 裁判有哪些已知偏差？你怎么测？

A（要点）：位置偏差、冗长偏差、自我偏袒、宽大/中心趋势。测位置偏差的办法是构造性的：同一对回答正反各跑一遍，看结论翻转率；翻转率本身就排除了「裁判口味」的解释，因为回答内容没变、只变了顺序。

追问一：那你怎么处理翻转的样本？

记为「不可比」，不记为平局。混进平局会把胜率系统性稀释。

再追问：如果翻转率很高，比如 40%，说明什么？ 说明这个判据在这个任务上没有分辨力，不是「差异小」。这时候加样本量没用——位置偏差是系统误差，采样平均不掉。要么把量表收紧到二选一且强制选一个，要么放弃 pairwise 改用确定性判据。

Q3：temperature = 0.0 是不是就能保证评测可复现？

A（要点）：不能。它只让采样变成贪心，但工程上仍可能因为服务端批次、模型版本更新、MoE 路由等产生差异；而且我实际遇到的可复现性问题更多来自非模型因素：截断长度改了、检索上下文顺序变了、上游限流导致部分样本失败被当成低分。

追问一：那你靠什么保证同一份评测跑两遍结果一致？

三件事：固定输入（截断长度是常量、上下文顺序稳定）、缓存（同输入不重复调用，哈希里包含判据全文，规则一改缓存自动失效）、失败留痕（解析失败记 PARSE_ERROR，不回落到 0 分）。

再追问：如果某次评测大批量出现了 PARSE_ERROR，你的门禁会怎么表现？ 这正是我在门禁里用三态退出码的原因：这类情况的正确输出是「不可比」（退出码 2），而不是「回归」（1）。二态门禁会把「基础设施坏了」误报成「模型变差了」，然后你花两天去查一个不存在的性能问题。
