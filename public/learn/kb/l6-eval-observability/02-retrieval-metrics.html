检索端指标：Recall@k、MRR、nDCG 与 Hit Rate ​

覆盖知识点：L6-04 ｜ 面试频率：高 ｜ 建议学时：2h

一句话说清 ​

检索端指标回答的是一句话：该召回的证据，有没有进入前 个候选，以及排在第几位。它和生成端指标的最大区别是——它的分子分母都由 ground truth 定义，而不是由模型输出定义，所以它是整条链路上唯一能给出「确定答案」的一段。四个指标分工明确：Hit Rate 答「有没有」、Recall@k 答「召回全不全」、MRR 答「第一块相关排第几」、nDCG 答「整张排序表好不好」。

这一页的核心不是背公式，而是认出指标被构造出来的假象。下面会用一个真实病例讲透：Recall@10 == Recall@5 不是排序完美，而是标注窗口造成的数学必然——这个病例是本层价值最高的一段素材，也是面试官最容易被点燃的追问点。

为什么必须学（面试官视角） ​

一个 RAG 系统答错了，有且只有三种归因：没检索到（召回问题）、检索到了但没排进上下文（排序问题）、上下文里有但生成没用好（生成问题）。检索端指标就是做这个归因的唯一工具。

  • HR / 简历侧：简历里写「RAG 问答准确率 91.3%」这类生成端数字，面试官无从验证；但如果写「Recall@5 71.8%、MRR 0.714」，懂行的面试官立刻知道你分开测过检索与生成。这是「做过系统」与「做过 demo」的分水岭。
  • 技术主管侧：这一层考三个层次，一层比一层深。第一层「你会不会算 Recall@k」；第二层「你知道分母是 gt 块数不是题数吗」；第三层「你怎么保证你的 gt 不是检索结果的子集」——第三层能答出来的人极少，答出来就是强信号。
  • 你的两个项目都写了评测，所以这题必被追。追到底的形态通常是：「你说你 Recall 71.8%，那 28.2% 是没召回还是没排上来？」——答不出这个，指标就只是装饰。

核心内容 ​

L6-04 检索端指标：Recall@k / MRR / nDCG / Hit Rate ​

  • 定义：四个指标的输入都是同一组东西——每题一个 gt 集合（哪些 chunk 是标准答案）与一个有序的检索结果列表（模型给出的 top- 候选）。指标就是在这两者之间做集合运算与位置加权。

    设某题 gt 集合为 （大小 ），检索返回的有序列表为 ，取前 个记作 ：

    其中 表示第 位候选是否是 gt 块；IDCG 是理想排序（所有 gt 块排最前）下的 DCG，做分母是为了把分数压到 。

  • 机制（每个指标怎么读）：

    指标它精确回答的问题分母是什么分母变化时分数怎么动
    Hit Rate@k前 个里至少有一个 gt 吗题数与 gt 块数无关；gt 越多的题越容易拿分
    Recall@k该召回的 gt 块，召回了百分之几gt 块数（不是题数）gt 越稀疏越容易拿高分：1 块 gt 命中即 100%
    MRR第一块 gt 排在第几位（只在乎第一块）题数有多块 gt 时只看最好的那块，会掩盖第二、三块很差
    nDCG@k整张 top- 排序表离理想排序有多远每题独立归一化位置越靠后权重越低（），对排序质量最敏感

  • 为什么这样设计：四个指标并存不是因为标准多，而是因为它们分离了三种不同的失败模式。

    • 想要「检索器认不认得这段材料」→ 用 Hit Rate，最宽松。
    • 想要「证据齐不齐」→ 用 Recall@k，因为多跳题往往需要 2–3 块证据，缺一块就答不全。
    • 想要「用户看到的第一条对不对」→ 用 MRR，因为很多产品只把第一条给用户看。
    • 想要「排序整体质量」→ 用 nDCG，因为它同时惩罚「相关项排太后」和「不相关项排太前」。

    面试里最值得说的一句：Recall@k 和 MRR 必须成对报。只看 Recall 看不出排序差，只看 MRR 看不出召回缺——一个说「有没有」，一个说「排哪儿」。

  • 数量级与形状（真实对照）：项目里三档检索配置在同一套题上跑出来的结果（题集 130 题，可回答 124，填 gt 的 124 题，gt 块总数 206，密度 1.66 块/题）：

    配置R@5R@10MRR
    ① 纯向量64.4%73.7%0.577
    ② 混合检索（无精排）59.1%69.2%0.502
    ③ 混合检索 + 精排71.8%77.4%0.714

    这组数字值得逐列读，因为它推翻了一个常见直觉：

    1. 「混合检索一定比纯向量好」是错的。② 比 ① 全面更差（R@5 59.1% vs 64.4%，MRR 0.502 vs 0.577）。原因是融合引入了 BM25 路的噪声候选，把原本排得不错的向量结果挤下去了——召回变宽不等于排序变好。
    2. 加了精排之后 ③ 才反超。③ 比 ① 高 7.4pp（R@5）/ 3.7pp（R@10）/ 0.137（MRR）。所以正确的表述是「混合检索负责把候选捞进池子，Rerank 负责把对的捞上来」，两者缺一不可，单加混合不加精排会掉分。
    3. MRR 的变化幅度比 Recall 大。① → ③ 的 R@5 涨 7.4pp，而 MRR 涨 0.137（相对提升约 24%）。因为 Rerank 天生就是改位置的，它对 MRR 的贡献比它对 Recall 的贡献更能说明它在干活。

  • ⭐ 必须讲透的坑：Recall@10 == Recall@5 是构造结果，不是排序完美

    报告里两列数字完全相等，第一反应是「排序已经到顶了」。这个解释是错的，而且错得很贵——因为它会让排序问题从待办清单里消失。

    根因断了两段（第一段修好了才会暴露第二段）：

    段现象根因修好后的表现
    第一段两列恒等top_k 参数从未被使用，只在函数签名里出现过 1 次 → retrieved[:10] == retrieved[:5] 恒成立改成真取 10 条
    第二段两列仍然恒等生成 gt 候选的脚本只取 retrieve()[:5]，而人也只看了这前 5 个候选 —— 答案落在第 6–20 位的题，gt 块根本不可能被标出来改用 top-10 名次审计，立刻暴露差异

    第二段的数学后果是必然的，不是巧合：

    也就是说：只要 gt 是 top-5 的子集，R@10 在数学上就不可能高于 R@5。 这不是模型好，这是尺子自己弯了。

    审计手段：改用 top-10 的真实名次去查 gt 块的位置。实测名次分布是 1–5 位：21 道、6–10 位：0 道。这个「6–10 位恰好一道都没有」的分布，就是 gt ⊆ top-5 的签名——零命中不是巧合，是构造的指纹。

    修好之后才拿到的真信息：不做精排时，R@10 比 R@5 高 11–14 个百分点。含义是：

    答案其实早就召回了，只是没排进前 5。

    这一句话直接把两类问题分开了——「检索不到」要改召回（换 embedding、扩 top_k、加术语表）；「排不上来」要改排序（加精排、调融合权重）。那个 bug 的危害不是让分数错了，而是让排序问题一直进不了待办清单：报告说 R@10 = R@5，看上去排序完美，没人会去查排序。

  • ⭐ 第二个坑：gt 循环依赖——拿被测系统给自己出题

    机器 gt 的候选块由检索结果生成，然后再拿同一个检索器去评它。这是典型的自证：③ 组的 R@5 = 100.0%（实测 100.0% / 100.0% / MRR 0.906）就是这么来的。R@5 满分不是因为系统完美，而是因为gt 的定义就是「③ 组检索出来的 top-5」。

    正确处置不是删报告（删了就查不到这段教训），而是让报告自己声明无效：那份报告顶部写着「🚫 本报告不可作为结论」。这是工程上很成熟的一种做法——保留证据，撤销结论。

  • ⭐ 第三个坑：换尺子——不同报告的数字不能沿列连读

    项目里 16 份历史报告跨越 ≥4 把尺子（gt 版本 / gt 块数 / 题数各不相同）。同一列里上下两行的分母不是同一个东西，所以明确不可沿列连读。

    最硬的一次证据是独立盲标：换会话、不看任何检索分数、直接读原文复核，结果 Recall 从 87.0% 掉到 71.0%。掉下来的 16 个百分点不是系统退步，而是原来的 87.0% 里有 16 个点是标注者被检索结果锚定出来的。换尺子会让分数掉，掉的是虚高部分。

  • ⭐ 第四个坑：粗切会改变分母，分数变化里混着「换尺子」

    切片配置从细档换到 1024 档时，相邻两个 gt 块会被并成一块，于是 gt 从 36 块掉到 30 块。分母从 36 变成 30，得分从 68.8% 升到 76.8%——这 8 个点里有一部分是「换尺子」换来的，不能直接读成「1024 档更好」。

    这条坑的通用形式值得背下来：

    凡是改变了 gt 集合的操作（换切片、换解析器、并块、扩库），都会同时改变分子和分母。分数变化里必须把「换尺子」这一项单独剥出来，剩下的才是系统侧的真实变化。

  • 常见误区：

    1. 把 Recall@10 == Recall@5 读成「排序完美」。先排除构造性解释，再怀疑模型。
    2. 报 Recall 不报分母。Recall@5 71.8% 后面必须跟 （124 题 / gt 206 块 / 密度 1.66），否则这个数字不可复算。
    3. 用同一批题横向比较不同切片配置。换切片后 chunk_id 全变，旧 gt 全部悬空——跨配置只能比趋势并注明限制。
    4. 只算平均不打分层的。multi_hop 题的 gt 密度（2.56 块/题）远高于 single_hop（1.30 块/题），所以多跳题的 Recall 天然更低。不分层报，就看不出是「系统整体差」还是「多跳这一类差」。
    5. 把 Hit Rate 当主指标。它太宽松——gt 块多的题几乎必然命中，会把「答不全」的失败全部隐藏掉。
    6. 指标算完不看候选块本身。看「第 3 位是哪个块、它和 gt 差在哪」往往比看分数有用十倍。

  • 代码：四个指标一起算，分母动态、gt 为空单独报告而不是当 0 分。

python
import math

def retrieval_metrics(records: list[dict], k_values=(5, 10)) -> dict:
    """
    records: [{"gt_chunk_ids": [...], "retrieved_chunk_ids": [...]}]  retrieved 必须是有序的
    返回每个 k 的 HitRate / Recall，外加 MRR 与 nDCG@max(k)。
    """
    n = len(records)
    out = {}
    for k in k_values:
        hits = rec = 0
        for r in records:
            gt = set(r["gt_chunk_ids"])
            topk = r["retrieved_chunk_ids"][:k]
            inter = gt & set(topk)
            if inter:
                hits += 1
            rec += len(inter) / len(gt) if gt else 0      # gt 为空的题贡献 0，但下面单独报数量
        out[f"hit_rate@{k}"] = round(hits / n, 4)
        out[f"recall@{k}"] = round(rec / n, 4)            # Recall 先按题求比值再对题取平均

    rr = ndcg = 0.0
    for r in records:
        gt = set(r["gt_chunk_ids"])
        order = r["retrieved_chunk_ids"]
        first = next((i for i, c in enumerate(order, 1) if c in gt), None)
        rr += 1.0 / first if first else 0.0
        dcg = sum((1.0 if c in gt else 0.0) / math.log2(i + 1) for i, c in enumerate(order, 1))
        idcg = sum(1.0 / math.log2(i + 1) for i in range(1, min(len(gt), len(order)) + 1))
        ndcg += dcg / idcg if idcg else 0.0
    out["mrr"] = round(rr / n, 4)
    out["ndcg"] = round(ndcg / n, 4)
    out["n_with_gt"] = sum(1 for r in records if r["gt_chunk_ids"])   # 报数必带的样本量
    out["gt_blocks"] = sum(len(r["gt_chunk_ids"]) for r in records)   # 报数必带的分母
    return out

注意 Recall 的两种算法：上面是「先按题算比值，再对题取平均」（macro，每道题权重相同）；另一种是「总命中数 / 总 gt 块数」（micro，gt 块多的题权重大）。两者在 gt 密度不均衡时会给出不同答案，所以报数时必须写清用的是哪一种。项目里的 71.8% 是 macro 口径。

python
def assert_gt_not_subset_of_top5(records: list[dict], k: int = 5) -> None:
    """gt 若是 retrieve()[:5] 生成的，就会全部落在 top-5 内 → 必须炸出来。"""
    n_gt_total = sum(len(r["gt_chunk_ids"]) for r in records)
    n_in_top5 = sum(len(set(r["gt_chunk_ids"]) & set(r["retrieved_chunk_ids"][:k]))
                    for r in records)
    if n_gt_total and n_in_top5 == n_gt_total:
        raise AssertionError(
            f"全部 {n_gt_total} 个 gt 块都落在 top-{k} 内 —— 疑似 gt 由检索结果生成（循环依赖）；"
            "请先用 top-10 名次审计确认 gt 集合是否被标注窗口截断。"
        )

  • multi_hop 严格准确率只有 27.8%——它是检索与生成共同的短板，只能说成线索，不能说成结论（题量太小）。

面试怎么问（3 组） ​

Q1：你的检索效果怎么衡量？

A（要点）：四个指标分开报，因为它们分离不同失败模式——Hit Rate 答「有没有」、Recall@k 答「召回全不全」、MRR 答「第一块相关排第几」、nDCG 答「整张排序表好不好」。我的主指标是 Recall@5 与 MRR 成对报，因为只看 Recall 看不出排序差，只看 MRR 看不出召回缺。三档配置的实测：① 纯向量 64.4% / 73.7% / MRR 0.577；② 混合无精排 59.1% / 69.2% / 0.502；③ 混合+精排 71.8% / 77.4% / 0.714。而且我必须补一句口径：这是 124 题、gt 206 块、密度 1.66 块/题的 macro 口径。

追问（中层）：② 比 ① 全面更差，你的混合检索是不是做错了？

A：不是做错了，是**「召回变宽不等于排序变好」。BM25 路捞进来的候选里有一部分和向量路重合度低、但相关度也不高，RRF 融合后它们把原本排在向量路前几位的正确块挤下去了**。数据上就是 ② 的 MRR 从 0.577 掉到 0.502——排序变差，召回优势没体现出来。真正的结论是：混合检索和精排是一对，③ 才反超 ①（R@5 +7.4pp、MRR +0.137）。所以我的说法是「混合负责把候选捞进池子，Rerank 负责把对的捞上来」，单加混合不加精排会掉分。

追问（深层）：那你怎么知道 ③ 的提升不是 Rerank 把 gt 块硬推上去的过拟合？

A：三点。① Rerank 只看过问题和候选文本，没见过 gt 集合，它的训练数据与我的评测集无交集；② MRR 的涨幅（相对约 24%）明显大于 R@5 的涨幅（7.4pp），符合「精排是改位置的」这个机制预期——如果它是靠某种泄漏拿分，涨幅分布不会正好落在位置上；③ 我保留了 ② → ③ 单步消融，知道每一步各自的贡献，而不是只报一个总提升。

追问（再深一层）：那你现在还有 28.2% 没进 top-5，是没召回还是没排上来？

A：这正是我踩过的坑。 我早期的报告里 R@10 和 R@5 完全相等，我一度以为是排序已经完美。后来查出来是构造结果：gt 候选生成脚本只取 retrieve()[:5]，标注的人也只看这 5 个，所以 gt 必然是 top-5 的子集，R@10 在数学上不可能更高。修好之后看到——不做精排时 R@10 比 R@5 高 11–14 个百分点，说明那部分题答案已经召回了，只是没排进前 5。所以现在我能把两类问题分开：「检索不到」改召回，「排不上来」改排序。那个 bug 最大的危害不是分数错，而是让排序问题从我的待办清单里消失了。

Q2：Recall@k 的 k 你怎么定的？

A（要点）：k 不是拍脑袋，由上下文预算反推：能塞进 prompt 的块数上限决定 ，而检索阶段会取更大的 给精排用。我报数时报两个：R@5 对应「最终进上下文的量级」，R@10 对应「候选池的量级」。k 本身不是结论，k 之间的差才是结论—— 就是「有证据但没排上来」的比例。我实测这个差在不精排时是 11–14pp、精排后会收窄。

追问（中层）：分母是什么？

A：分母是 gt 块数，不是题数。 所以有个反直觉推论：gt 越稀疏越容易拿高分。一道题只有 1 块 gt，命中 1 块就是 100%；另一道题有 3 块 gt，命中 2 块只有 66.7%。我的数据里这个差异很实在——multi_hop 密度 2.56 块/题、single_hop 1.30 块/题，所以不分层报就误判。另外要注意 macro 和 micro 两种算法在 gt 密度不均衡时会给不同答案，我报的是 macro（先按题算比值再平均）。

追问（深层）：换切片配置之后你还能比吗？

A：不能直接比。 我的 1024 档把相邻两个 gt 块并成了一块，gt 从 36 块掉到 30 块，得分从 68.8% 升到 76.8%。分母变了，这 8 个点里有一部分是「换尺子」换来的，不能读成「1024 档更好」。我现在的做法是：凡改变 gt 集合的改动（换切片、换解析器、并块、扩库），变化里必须把「换尺子」这一项单独剥出来，剩下的才是系统侧变化；跨配置只比趋势并注明限制。

追问（再深一层）：那你怎么保证下一次不会再被尺子骗？

A：我把它做成了能失败的断言，而不是靠我记得去查。比如一条自检：如果全部 gt 块都落在 retrieve()[:5] 内，就抛异常判定为疑似循环依赖——这个恒等关系成立时脚本是「跑得好好的」，只验「没报错」等于没验。另外我做过一次独立盲标（换会话、不看任何检索分数、直接读原文复核），Recall 从 87.0% 掉到 71.0%，还推翻了两条已有结论。掉下来的 16 个点不是系统退步，是原来那 87.0% 里有 16 个点是标注者被检索结果锚定出来的。所以我现在的立场是：指标的可信度不取决于数字多高，取决于标注与评测流程是否独立于被测系统。

Q3：如果两个指标互相矛盾（比如 Recall 涨了但 MRR 掉了），你怎么办？

A（要点）：那不是矛盾，是信息。Recall 涨、MRR 掉意味着召回池变宽了但排序变差了——典型的「加了混合检索没加精排」。我的决策规则：先看 MRR，因为用户看到的是前几条；MRR 掉了就先别上这个改动，或者补上精排再评。反过来 Recall 掉、MRR 涨，说明候选池变窄了，长尾题会开始答不上来，要去看是不是 top_k 被调小了。

追问（中层）：你会看平均分还是看分布？

A：都看，但决策看分布。 平均分只能告诉你「整体动了」，分布才能告诉你「谁在动」。我会按题类分层报（single_hop / synonym / multi_hop / exact_term / unanswerable），因为分母结构不同的题不能混在一起看。我的多跳题 gt 密度是高密度组的两倍左右，混起来算平均，多跳的差就被单跳的高分稀释掉了。

追问（深层）：题量小的时候，涨 2 个点算数吗？

A：不算，不能只报点估计。 我的经验是：题量小的时候（比如拒答这一类），宁可把分子分母一起报也不要说百分比。一个真实例子：我的拒答准确率是 100.0%，但分母只有 6 道题——这个数字几乎不含信息，我必须在面试里主动说出分母，否则它就是一个误导性的满分。更稳的做法是配对比对（同一批题、两条臂跑两遍）看差分，而不是看两个绝对值的差。
