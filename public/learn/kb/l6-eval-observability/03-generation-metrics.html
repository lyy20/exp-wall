生成端指标与通用 NLP 指标：faithfulness、answer relevancy、BLEU/ROUGE/BERTScore ​

覆盖知识点：L6-05 L6-06 ｜ 面试频率：高 ｜ 建议学时：4h

一句话说清 ​

检索端指标问「该找的东西找到了吗」，生成端指标问「模型拿这些材料说出来的话能不能立住」——两套尺子测的不是同一个对象，数字不能互相替代。生成端在 RAG 里要拆成三问：答案是不是完全由上下文支持（faithfulness）、答案是不是真在回答这个问题（answer relevancy）、给进去的上下文有没有冗余（context precision）。经典 NLP 指标（P/R/F1、BLEU、ROUGE、BERTScore）是另一套工具：完全确定、可复算、便宜、能进 CI，但用在开放式生成上会系统性失效。

为什么必须学（面试官视角） ​

L6-05 是本层关键词密度最高的一页——faithfulness、answer relevancy、context precision 这三个英文词就是技术面试官判断「你测过还是没测过」的检索词。报不出这三个名字，基本被判定为没做过评测；报得出名字却说不出分母，会被判定为只是抄了框架的默认指标列表。

  • HR / 简历侧：写「RAG 系统」的人一抓一把，写「faithfulness / answer relevancy 分层评测」的少很多。关键词是初筛检索项，写不出来就等于这段经历在初筛里不存在。
  • 技术主管侧：他真正要确认的是——你知不知道生成端分数是「有条件的」。换个裁判、换个样本量、换个批次，分数都会变。能主动交代裁判有没有人工校准的人，比报高分的人可信一个量级。
  • 你的情况特殊：两个项目都写了评测，而且你手上有一组典型的反面教材（口径不一的历史数字 + 未校准的裁判）。这一段要主动讲——主动交代口径是加分项，被追问出来是减分项。

核心内容 ​

L6-05 生成端指标：faithfulness / answer relevancy / context precision ​

  • 定义：三个指标回答三个独立的问题。它们不是同一个能力的不同侧面，而是三道不同的关卡——答案可以「有依据但没回答问题」，也可以「切题但凭空编」。

    指标精确回答的问题谁的输出被评归属
    faithfulness（忠实度）答案里的每一句话，能否被检索到的上下文支持答案 vs 上下文RAG 专属（没有外部上下文就没有这个概念）
    answer relevancy（答案相关性）答案切不切题——是不是在回答被问的那个问题答案 vs 问题通用（RAG、纯 LLM、Agent 都能用）
    context precision（上下文精确率）塞进 prompt 的上下文里，有用比例有多高上下文 vs 问题检索侧与生成侧的交界指标

  • 机制：把「答案是否有依据」和「答案是否切题」当成两条独立的轴，四个象限就是四种典型故障：

    切题不切题
    有依据理想答非所问：复述了正确材料，但没回答问题 → answer relevancy 掉
    无依据幻觉：回答切题、语气自信，但上下文里没有这句 → faithfulness 掉双重失败

    三个指标本质上是同一个模板「分句 → 逐句判定 → 求比例」的不同实例。以 faithfulness 为例：

    分母是「答案里的断言条数」，不是题数、也不是引用条数。副作用很关键：又长又碎的答案天然更难拿高分，只答一句话的答案天然容易拿高分——所以跨系统比较 faithfulness 时，答案长度必须一起报。

    实现细节统一标注：这三个名字是 RAG 评测领域的通用叫法；它们在 Ragas、DeepEval、TruLens、LangSmith、Langfuse 等框架里的字段名、参数名、返回结构与调用方式各不相同，以官方文档为准。 本页只讲机制与分母，不写任何具体 API。

  • 为什么这样设计：RAG 的产品承诺是「有据可查」，所以 faithfulness 是一级指标，它直接对应「引用可溯源」这个卖点。而 answer relevancy 存在的原因是faithfulness 可以被作弊——模型把检索到的原文整段抄回来就是满分，但可能一个字都没回答你的问题。两个一起看才堵得住这个洞。 同理 context precision 存在的理由是上下文不是免费资源：塞进去的每一块都占 token、都可能分散注意力，它是唯一能直接换算成成本和延迟的生成端指标。

  • 数量级与形状（真实口径）：

    指标实测值必须一起报的分母
    拒答准确率100.0%分母只有 6 道题——几乎不含信息
    误拒率（该答却拒答）7.3%全部可回答题
    漏拒（该拒却答了）0不可回答题
    两层误拒率分开测1.6% vs 6.5%客服域层 vs 其它层，不能合并报

    「100.0%（6 题）」这个组合能一句话证明你懂口径：拒答准确率 100.0%，但分母只有 6 道题，所以它不能当作系统能力的结论，只能说「当前这批负样本上没出错」。两层误拒率差的 4 倍同样重要：合并报一个平均值，这个差异就被平均掉了，而工程上真正的结论恰恰是「某一层明显更容易误拒」。

  • ⭐ 反面教材：答案准确率 65.2% / 91.3% 为什么不能直接用

    属性具体内容后果
    旧口径出自旧的 30 题口径与当前 130 题报告不是同一批次，不可混引
    裁判未校准由 LLM 裁判判定，该裁判未做人工校准严格/宽松差 26.1pp，本身就是裁判口径未定的症状

    正确用法只有三种：① 引用时带全口径（旧 30 题、LLM 裁判判定、未人工校准，严格 65.2% / 宽松 91.3%）；② 只在旧题集内部纵向比较；③ 不引用。这就是本层生命线纪律的落地：报数必带口径——样本量、gt 版本与块数、密度、比较对象、是否含精排、日期。

  • ⭐ 引用校验的边界：验编号 ≠ 验事实

    引用校验只验「编号合法性」（编号是否指向真实存在的块），验不了「事实是否真在该片段里」——那需要 NLI（自然语言推理）级别的判断，项目里没有。

    这条边界的面试价值极高：它划清了「我做了什么」与「我没做什么」。主动划边界的人不会被追问打穿，模糊表述的人会被一路追到底。

  • 常见误区：

    1. 只报 faithfulness 不报 answer relevancy（或反过来）。两者正交，只报一个等于留了一个盲区。
    2. 报 faithfulness 不报答案长度。分母是断言条数，长答案天然吃亏。
    3. 把裁判分数当客观真值。未经人工校准的 LLM 裁判只是一个待验证的测量工具。
    4. 严格分与宽松分都报，却不解释为什么差 26 个点。分差大说明评分规则没定死。
    5. 把不同批次的数字放进同一张表。旧 30 题与新 130 题不是同一把尺子。
    6. 报没有分母的百分比（尤其 100.0% 这类）。
    7. 用引用编号合法率冒充「无幻觉率」。编号合法只说明引用格式对，不说明内容对。

  • 代码：P/R/F1，分母显式、零分母不炸成 0

python
def prf1(preds: list[bool], labels: list[bool]) -> dict:
    """拒答判定 / 引用合法性 / 路由决策都走这一条。"""
    if len(preds) != len(labels):
        raise ValueError(f"长度不匹配：preds={len(preds)} labels={len(labels)}")
    tp = sum(p and l for p, l in zip(preds, labels))
    fp = sum(p and not l for p, l in zip(preds, labels))
    fn = sum((not p) and l for p, l in zip(preds, labels))
    p = tp / (tp + fp) if (tp + fp) else None      # 分母为 0 → None，不是 0.0
    r = tp / (tp + fn) if (tp + fn) else None
    f1 = (2 * p * r / (p + r)) if (p and r and p + r) else None
    return {
        "precision": p, "recall": r, "f1": f1,
        "n": len(labels),                          # 报数必带分母
        "tp": tp, "fp": fp, "fn": fn,              # 只报 F1 会掩盖 P/R 的失衡
    }

L6-06 通用指标与经典 NLP 指标 ​

  • 定义：这一组是不需要大模型当裁判的确定性指标——输入输出都是字符串或集合，同一输入永远得到同一分数。它们便宜、可复算、可进 CI，是唯一能当回归门禁用的那一类。

    家族指标输入形态确定性
    分类级精确率 Precision / 召回率 Recall / F1预测标签 vs 真标签完全确定
    重叠级BLEU / ROUGE / METEOR生成文本 vs 参考文本（n-gram 重叠）完全确定
    语义级BERTScore生成文本 vs 参考文本（embedding 相似度）确定（同模型同版本下）
    可读性级困惑度 PPL文本 + 语言模型确定（同模型下）

  • 机制（逐个说清「它在数什么」）：

    • 精确率 / 召回率 / F1：在 LLM 应用里的主战场不是文本生成，而是分类与抽取——意图识别、路由决策、拒答判定、字段抽取、引用编号合法性。

      为什么 F1 用调和平均而不是算术平均：调和平均对小值敏感。 时算术平均是 0.55（看着还行，其实没用），调和平均是 0.18（如实反映它没用）。这就是 F1 的意义：惩罚偏科。

      一个把所有题都拒答的拒答器，召回率可以是 100%——所以只看召回率的拒答评测是无效的。

    • BLEU：数生成文本与参考文本的 n-gram 重合度，通常取 1–4 gram 的几何平均，并带长度惩罚（生成太短就扣分）。

      为什么用几何平均：只要有一项是 0，整体就是 0——这逼迫生成在每一个 n 上都有重叠，只对上一元组（单词对了顺序错）拿不到高分。

    • ROUGE：与 BLEU 同族但方向相反——BLEU 偏精确率（生成的 n-gram 有多少在参考里），ROUGE 偏召回率（参考的 n-gram 有多少被生成覆盖）。常用 ROUGE-N 与 ROUGE-L（最长公共子序列）。

      为什么摘要任务用 ROUGE：摘要的失败模式是「漏」（该说的没说），不是「编」。偏召回的指标更贴合这个失败模式。

    • BERTScore：把生成与参考都编码成 embedding，逐 token 找最相似的参考 token，算 P/R/F1。它解决的是「意思对了但用词不同」；代价是不再是纯字符串运算（依赖一个具体 embedding 模型，换模型或换版本分数会变），且比 BLEU 慢几个量级。

  • 为什么这样设计，以及失效场景（本知识点真正的考点）：

    BLEU / ROUGE 的根本假设是「好答案和参考答案是同一句话」。 这在翻译、摘要、模板化生成里大致成立，在开放式问答里完全不成立——同一个问题的正确答案有无数种写法。

    场景会发生什么该怎么测
    开放式 RAG 问答「42 度」与「温度阈值设定为 42 摄氏度」，BLEU 接近 0，但都对faithfulness + answer relevancy，或 LLM 裁判 + 人工校准
    参考答案只有一条模型答得更全反而扣分准备多条参考答案，取最大重叠
    答案含数值/单位/编号「一半」vs「50%」算错抽数值后单独精确比对
    拒答/不可回答类拒答话术五花八门，BLEU 全低；拒答恰恰是分类问题用 P/R/F1
    引用编号校验这是格式合法性判定，不是文本相似度用精确率/召回率
    多跳推理答案推理链表述自由度最大，BLEU 最不适用拆成「结论正确 + 证据充分」两步

    一句话判据（建议背下来）：

    BLEU / ROUGE 用来做「同一件事的两种说法」之间的比较（回归、模板、翻译、摘要）；不要用来判「答案对不对」。 开放式问答里它们只能当回归门禁（同一份 prompt 改了参数输出不该大变），不能当质量分。

  • 数量级与形状：

    • BLEU 不是「百分比正确率」：它衡量字面重合。可用系统的 BLEU 常在几十这个量级，而完全不同的两段文本通常是个位数甚至 0——看到 0.05 不要读成「准确率 5%」。
    • 分类问题的样本量代价：拒答准确率分母只有 6 道题，用 P/R/F1 报且必须写分母；6 道题的 F1 没有统计意义，只能当「当前没出错」的现状描述。
    • 引用编号校验按「条」算，一条长答案里的 10 个引用贡献 10 个判定点——分母形状与按题算的指标完全不同，不能混在一起平均。

  • 常见误区：

    1. 把 BLEU 当准确率报（「BLEU 0.65，所以准确率 65%」）。它的对齐单位是 n-gram，不是题。
    2. 在开放式问答上主用 ROUGE，再用「分数低」得出「系统差」的结论——其实是尺子选错了。
    3. BERTScore 跨模型/跨版本比较。
    4. 只看 F1 不看 P 和 R。P=1.0, R=0.1 与 P=0.5, R=0.5 的 F1 可能接近，但故障模式完全不同。
    5. 把不同分母的指标平均。「按题」与「按引用条」平均出来的数字没有任何含义。
    6. 回归门禁用 BLEU 阈值卡死。同一份 prompt 在不同温度下输出本来就会变，BLEU 抖动会误报回归。

  • 代码：BLEU 的 n-gram 精确率骨架（说明「为什么只在同一种说法之间比才有意义」）

python
from collections import Counter

def ngram_precision(hyp: str, ref: str, n: int) -> float:
    """clip：一个 n-gram 在参考里出现几次，最多只认几次，防止重复刷分。"""
    h = Counter(tuple(hyp.split()[i:i + n]) for i in range(len(hyp.split()) - n + 1))
    r = Counter(tuple(ref.split()[i:i + n]) for i in range(len(ref.split()) - n + 1))
    if not h:
        return 0.0
    clipped = sum(min(c, r[g]) for g, c in h.items())
    return clipped / sum(h.values())

面试怎么问（3 组） ​

Q1：RAG 的生成效果你怎么测？

A（要点）：拆成三问，因为它们正交、不能互相替代：faithfulness（答案每句话能否被检索到的上下文支持——RAG 专属，没有外部上下文就没这个概念）、answer relevancy（答案切不切题）、context precision（塞进去的上下文里有用比例多高，这个能直接换算成成本和延迟）。我另外测了拒答这一类分类指标：准确率、误拒率、漏拒。报数每一条都带分母——比如拒答准确率 100.0%，但分母只有 6 道题。

追问（中层）：为什么 faithfulness 和 answer relevancy 不能只报一个？

A：它们正交，四种组合里两种是典型失败模式：「有依据但不切题」——复述了正确材料却没回答问题；「切题但无依据」——就是幻觉。而且 faithfulness 可以被作弊：把检索到的原文整段抄回来就是满分，但可能一个字都没回答你的问题。两个一起看才堵得住。

追问（深层）：faithfulness 的分母是什么？

A：是答案里的断言条数，不是题数、也不是引用条数。副作用是——长答案天然更难拿高分（断言多，任何一句出戏就扣分），短答案天然占便宜。所以跨系统比 faithfulness 时必须一起报答案长度，否则可以靠「答得越来越短」把它刷上去。

追问（再深一层）：你的引用校验能证明没有幻觉吗？

A：不能，我把边界说清楚。我做的引用校验只验编号合法性——编号是否指向真实存在的块。它验不了「事实是否真的在那个片段里」，那需要 NLI 级别的判断，我项目里没有。所以我的引用合法率不能被当成「无幻觉率」讲。要补的话，最小做法是把答案拆成断言，逐条判「这段上下文支持这句话吗」。

注意：如果报告里有一组旧数字（严格 65.2% / 宽松 91.3%），一定要主动说明它是旧 30 题口径、且 LLM 裁判未人工校准。主动说出来，面试官对你的信任度是上升的——它证明你知道自己每个数字的产地；等被追问才答，同一个数字就变成扣分项。

Q2：你用过 BLEU / ROUGE 吗？为什么 RAG 的答案不用它们评？

A（要点）：用过，但用在不同的地方。它们是字面重叠指标——BLEU 偏精确率，ROUGE 偏召回率（所以摘要常用它，摘要的失败模式是「漏」）。它们完全确定、可复算、便宜，是唯一适合做回归门禁的一类。但它们的根本假设是「好答案和参考答案是同一句话」——这在翻译摘要里大致成立，在开放式问答里完全不成立。

追问（中层）：具体怎么不成立？

A：举我项目里就有的例子：答案「42 度」与「温度阈值设定为 42 摄氏度」，意思完全一样，BLEU 接近 0；同理「一半」对「50%」，以及拒答话术的无数种写法。开放式问答里同一问题有无穷多种正确写法，字面重叠测的是「说得像不像」，不是「对不对」。所以 RAG 的答案质量我用 faithfulness + answer relevancy，或 LLM 裁判，从不用 BLEU 当质量分。

追问（深层）：那 BLEU / ROUGE 在 RAG 里还有什么用？

A：当回归门禁，不是当质量分。用途是：「改了 prompt 措辞 / 换了参数，在同一批题上输出不该大变」——这是同一份答案与自己比，字面重叠是合理的。但这里也有坑：同一份 prompt 在不同温度、不同批次下输出本来就会变，BLEU 抖动会误报回归。所以我的门禁更倾向卡确定性断言：字段存在、格式合法、引用编号合法、不可回答问题必须拒答——这些非黑即白。

追问（再深一层）：BERTScore 能解决同义改写吧？

A：能缓解，但代价变了。它是把生成与参考都编码成 embedding、逐 token 找最相似的参考 token，所以能识别「意思对了但用词不同」。两个后果：① 不再是纯字符串运算，依赖具体 embedding 模型，换模型或换版本分数就变，不能跨版本比；② 比 BLEU 慢几个量级，而且仍然是和参考答案比，参考答案本身写得不全时一样会低估。我的判断是：要判「答案对不对」，最终还是要裁判 + 人工校准；BERTScore 只适合当比 BLEU 宽容一点的回归指标。

Q3：100.0% 的拒答准确率，含金量多少？

A（要点）：含金量取决于分母，我的分母只有 6 道题——所以它几乎不含信息。 我必须同时说清它是「当前这批负样本上没出错」，而不是「系统能力达标」。另外我报三项：准确率、误拒率 7.3%、漏拒 0。漏拒为 0 比准确率 100% 更值得说，因为漏拒才是 RAG 里更危险的一侧——那就是硬答。

追问（中层）：误拒率你怎么测？

A：分层测，不合并报。 我的两层误拒率是 1.6% 与 6.5%，差了 4 倍。合并成一个平均值，这个差异就被平均掉了，而工程上真正的结论恰恰是「某一层明显更容易误拒」——那正是我要去修的地方。平均分只告诉你整体动了，分布才告诉你谁在动。

追问（深层）：负样本怎么造的？会不会本身有问题？

A：这是我踩过的真实坑。我的原则是「库里有这个词，但没有答案」——比如 U07「多智能体 RL 中如何处理环境的非平稳性？」，论文的 future work 提到了关键词，检索必然命中，但正文没给答案。这跟「随便编一个库里没有的问题」完全不同，后者测的是「检索器认不认得这个词」，不是「模型会不会硬答」。但扩库后我发现 7 道负样本里有 1 道其实已经可回答了；盲标复核转题后，拒答准确率从 85.7% 变成 100.0%。

追问（再深一层）：那这个 100.0% 是系统变好了还是尺子改了？

A：是尺子改了。 这正是我这一层最想强调的事：负样本是语料的函数，扩库就要重审。所以我把这条做成了能失败的断言——如果有题目被标为「不可回答」却已经填了 gt 块，脚本直接抛异常，而不是静默算出一个漂亮分数。只验「脚本没报错」等于没验：一个恒等关系成立时，脚本是跑得好好的。
