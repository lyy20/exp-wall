asyncio、并发控制与超时重试 ​

覆盖知识点：L0-02 L0-11 ｜ 面试频率：高 ｜ 建议学时：9h

一句话说清 ​

LLM 应用的时间几乎全花在等上：等 embedding、等向量检索、等 rerank、等 LLM 出第一个 token。这些等待彼此独立，串行做就是把最慢的那个乘以次数。这一页讲两件事：用 async/await + Task + Semaphore 让 I/O 密集调用真正并行（L0-02）；以及这些能力最后要交付成什么形状——把生成结果逐 token 推给用户的流式传输（L0-11），它的分帧规则、被缓冲就失效的坑、以及「流式改善的是首字延迟、不是总时长」这条最容易说错的判据。两条判据贯穿全页：一次请求里能并发的 I/O 必须并发，但并发度必须被显式限制；每一个外部调用都必须有超时和失败路径，没有失败路径的调用等于没有上线资格。

为什么必须学 ​

这是「应届生项目」和「能上线的服务」之间的分水岭。面试官问「P99 延迟多少」之后，紧接着的一句一定是「你怎么降下来的」。如果你的答案是「换了更快的模型」，说明你没做过延迟工程；如果答案是「检索、rerank、缓存查询三种 I/O 并发发出，用信号量限制在 N 路，超时预算单独配」，面试官会认为你懂服务。

频率上，L0-02 和 L0-11 都是高频。原因是它们同时被三种岗位考：大模型开发问推理并发与批处理，Agent 开发问工具调用的并发与超时，AI 应用开发问接口的限流、降级与流式交付。答不上来的判定很直接——「这个人没写过多线程/异步的生产代码」，或者「他说的流式只是前端在转圈」。

核心内容 ​

L0-02 asyncio 与并发基础 ​

  • 定义：asyncio 是单线程事件循环上的协作式并发：协程在 await 处主动让出控制权，事件循环去跑别的就绪任务。它解决的是 I/O 等待，不是 CPU 计算。
  • 为什么 I/O 密集场景够用（也是必须澄清的 GIL 问题）：GIL 限制的是同一时刻只有一条线程执行 Python 字节码，但网络 I/O 在等待期间会释放 GIL。所以「单线程 + 事件循环」可以同时挂起成百上千个网络请求，而不会被 GIL 拖住。反过来说，CPU 密集任务（本地 embedding、大规模 rerank、图像处理）放在 asyncio 里只会让整个循环卡住——那要用多进程，或者干脆接受它慢。
  • 最小可运行形态：
python
import asyncio
import time


async def fake_io(name: str, cost: float) -> str:
    await asyncio.sleep(cost)  # 真实场景换成 await client.get(...)
    return f"{name} done in {cost}s"


async def main() -> None:
    t0 = time.perf_counter()
    # 串行：总耗时 = 各任务之和
    serial = [await fake_io(f"s{i}", 0.3) for i in range(3)]
    t1 = time.perf_counter()
    # 并发：总耗时 ≈ 最慢的那个
    concurrent = await asyncio.gather(*(fake_io(f"c{i}", 0.3) for i in range(3)))
    t2 = time.perf_counter()
    print(f"serial={t1 - t0:.2f}s concurrent={t2 - t1:.2f}s")
    assert len(serial) == len(concurrent) == 3


asyncio.run(main())

  • 必须记住的原语（面试问「你用过哪些」时按这张表答）：
    原语用途关键点
    asyncio.gather并发收集多个结果默认任一异常会向上抛，其余任务不会被取消；要 return_exceptions=True 才能拿到全部结果
    asyncio.Semaphore(n)限制同时进行的路数必须在协程内部 async with 获取，不要用全局计数器自己数
    asyncio.wait_for给单个协程设超时超时会取消该任务并抛 TimeoutError，要接住并降级
    asyncio.Queue生产者消费者常见的用途是「边生成边发送」的流式管道
    asyncio.to_thread把阻塞调用丢到线程池参数是「同步函数」，这是唯一的逃生通道
  • 并发度不是越大越好：本地模型推理是 CPU 密集，不限制并发会让所有请求一起变慢（每个都从 20 秒变成全部超时）；远程 API 侧通常有 RPM/TPM 限制，超了直接 429。所以并发度是一个要配置、要压测、要写进文档的参数，不是一个随手写的数字。
  • 最常见的事故：在 async def 里直接调用阻塞函数（同步的 requests.get、model.encode、faiss.search、time.sleep）。症状是整个进程卡死——连 /health 都响应不了，健康检查失败，编排系统把本来健康的实例摘掉。判据：async def 函数体里不允许出现任何同步 I/O。 已有的同步库就用 await asyncio.to_thread(...) 包一层，或者把 FastAPI 的路由写成普通的 def（FastAPI 会把它放进线程池执行）。
python
import asyncio
from collections import defaultdict, deque

_sem = asyncio.Semaphore(4)  # 全局并发闸门，值来自配置与压测


async def limited_call(client, payload: dict, timeout_s: float = 20.0) -> dict:
    async with _sem:
        return await asyncio.wait_for(client.post(payload), timeout=timeout_s)

L0-24 异常处理与降级（本页只讲与并发有关的部分） ​

完整的四件套（超时 / 重试 / 熔断 / fallback）与降级要留证据、降级要能被评测区分出来这些内容，在 健壮性、成本与工具链（L0-24）里讲。

本页只保留并发视角下必须成立的三条约束，它们是你写 gather 和重试循环时的判据：

  • 可重试的是「瞬时错误」：连接超时、429 Too Many Requests、500/502/503/504。不可重试的是 400/401/403/422 与内容审核拒绝——对 400 系列重试只是浪费时间和配额，还会掩盖真正的 bug。另有一条：写操作默认不可重试，除非它被设计成幂等的（见 HTTP 语义与 FastAPI 服务骨架 里的 L0-09）。
  • 退避必须带抖动：delay = min(base * 2**attempt, max_s)，再加 random.uniform(0, delay * 0.3) 的抖动。并发场景下这不是优化——没有抖动，多个协程会在同一时刻一起重试，把上游再打崩一次。
  • 重试和超时都要算进总延迟预算：一次最多 3 次重试的调用，最坏耗时接近 4 × timeout。所以超时预算要从最外层（客户端等多久）往回分配，而不是给每个内部调用随便设一个数。

L0-11 SSE 与 WebSocket 流式传输 ​

  • 定义：SSE（Server-Sent Events）是服务器到客户端的单向文本流，基于普通 HTTP，媒体类型 text/event-stream；WebSocket 是双向全双工，需要协议升级（101 Switching Protocols）。LLM 场景 90% 用 SSE——因为需求只是「把生成的 token 单向推下去」。

  • SSE 的线上格式（要能默写）：一个事件由若干 字段: 值 行组成，空行结束。

    event: delta
data: {"text": "你好"}

event: done
data: {"citations": ["[1]", "[3]"], "trace_id": "abc123"}
    1
    2
    3
    4
    5

    两条硬约束：data 里不能出现裸换行（会破坏分帧），所以结构化数据要先用 json.dumps 压成一行；字段名大小写敏感，data: 后面那个空格是格式的一部分。

  • 代码（真实项目的流式路径）：

python
def _sse(event: str, data: dict) -> str:
    # ensure_ascii=False 保留中文；json.dumps 保证内部不会出现裸换行
    return f"event: {event}\ndata: {json.dumps(data, ensure_ascii=False)}\n\n"

async def stream_answer(q: str):
    async for piece in llm_stream(q):      # 逐 token
        yield _sse("delta", {"text": piece})
    yield _sse("done", {"citations": citations, "trace_id": trace_id})

  • 流式与「结构化输出」在原理上冲突（本项目最重要的一个设计判断）：JSON mode 要求整个 JSON 生成完才能解析，而流式要逐 token 吐出去——增量文本永远不是合法 JSON，这两件事不能同时满足。只有两条路：
    • a) 流式走纯文本 prompt，引用由程序在流结束后从完整答案里抽取并校验。代价是失去 JSON 的语法保证：格式更依赖 prompt 约束、抽取靠正则（有失败率）。收益是首字延迟从「整段生成完」降到「第一个 token」。
    • b) 假流式：先拿完整答案，再切块吐给前端。看起来在打字，但首字延迟一点没降，纯粹是表演。 本项目选 a，并把这条流式 prompt 单独标了版本号（与非流式那条不是同一条 prompt）——因为 prompt 变了评测结论就会变，版本号是唯一能追溯的方式。
  • \n\n 这个分帧符也决定了前端怎么写：浏览器用 EventSource 消费，或前端自己解析——必须按「空行」切分帧，不能按单个换行切。这是 SSE 解析最常见的 bug。
  • 常见误区：
    • 流式路由里用了带缓冲的中间件或反向代理，把整段响应缓存到结束才发。流式被缓冲 = 流式失效，症状是「本地好好的，上网关就不流了」。
    • 客户端断开后服务端继续生成。要在生成循环里检查连接状态并提前退出，否则白花钱。
    • 首字延迟和总时长混为一谈。流式改善的是首字延迟，不改善总时长——总时长取决于生成 token 数和模型速度。

和你自己的项目对上号 ​

  • 科研文献 RAG 的 /ask 与 /ask/stream：service.py 里有一个真实的设计决策——检索与 LLM 调用都是同步实现（sentence-transformers、faiss、openai 同步客户端），所以它们在 async def 路由里被放进线程池执行，而不是直接在事件循环里跑。原因写在模块头部注释里：同步调用直接在事件循环里跑会阻塞整个进程，「连 /health 都响应不了」。这正是本页那条判据的正例，面试时可以直接讲：我先判断这个调用是同步还是异步，再决定它能不能待在 async def 里。
  • 并发上限不是优化而是必需：同一个服务里还有限流与并发上限，注释里给的理由很值得复述——LLM 调用是花钱的，没有限流一次刷接口就能把预算打光；而本地模型推理是 CPU 密集，不限制并发会让所有请求一起变慢（每个都 20 秒，最后全部超时）。这与本页「并发度是要配置与压测的参数」完全对应。
  • 重试参数在配置里：generate.py 从 config.py 读取 LLM_TIMEOUT_S、LLM_MAX_RETRIES、LLM_RETRY_BASE_S、LLM_RETRY_MAX_S。把重试策略外置成配置，好处是压测时可以只调这一组参数对比，不需要改代码——这和 L0-18 的配置分层是同一件事。
  • YYHelp v2 的一处真实缺陷：v1 的字段清单与自检期望集合是三处真源，加字段时漏改一处，导致 --selftest 红着而 pytest 全绿。修法是用「故意配错 reducer」的测试证明断言真的会红。这条经验可以直接迁移到本页：降级路径和重试路径也必须被测到，否则它们只是写在代码里的装饰——测试里用一个必然返回 429 的假客户端，就能验证退避次数与最终降级行为。
  • 还没做到的：目前没有熔断器（连续失败后短时间内直接走 fallback，不再打上游），也没有对 finish_reason 异常的专门处理。面试被问到「上游连续挂了 10 分钟你的系统会怎样」时，诚实回答：现在会每次都完整重试，浪费配额；下一步加一个基于滑动窗口失败率的熔断。

面试怎么问（≥3 组） ​

Q1：你的服务并发怎么做？为什么用 asyncio 而不是多线程/多进程？ A（要点）：工作负载是 I/O 密集型（HTTP 调用模型服务、检索、rerank），asyncio 在单线程事件循环上挂起大量等待中的请求，开销远低于线程；GIL 只限制字节码执行，不限制等待 I/O 的线程，所以 I/O 场景下事件循环足够。CPU 密集部分（本地模型推理）不能放进事件循环——要么放线程池，要么接受并发受限。加分句：「我判断的标准是同步还是异步，而不是哪个『更快』：同步库要么包 to_thread，要么路由写成普通 def 让 FastAPI 丢线程池，绝不让它阻塞事件循环。」别说：「asyncio 比多线程快」——这是没有判据的说法。

Q2：并发度设多少？依据是什么？ A（要点）：两个约束共同决定——上游的速率限制（RPM/TPM，超了 429）和本地的资源上限（CPU 密集推理会把所有请求拖慢）。所以并发度是配置项，先按上游配额估算初值，再压测确认延迟与错误率曲线的拐点。加分句：「我还会区分检索并发和生成并发：检索是本地 CPU，压得太狠 P99 直接崩；生成是远程 API，主要受配额限制。」别说：「越多越好，反正有 await 不会卡。」

Q3：模型接口返回 429，你怎么处理？ A（要点）：分类——429/5xx/连接超时算可重试，4xx（含 422 校验失败）不重试；重试用指数退避 + 随机抖动，设 max_retry 与 max_delay 双上限；重试耗尽后走 fallback 并打降级标记。加分句：「重试的总时长也要算进延迟预算——max_retry+1 次乘以 timeout 是最坏情况，不能让它超过上游给我的超时。」别说：「while True 重试到成功为止。」

Q4：怎么保证降级路径本身是可靠的？ A（要点）：降级路径必须有测试——用假客户端构造 429/超时/空结果，断言最终行为是「返回兜底答案 + 打上降级标记 + 写 trace」，而不是断言「不抛异常」。加分句：「降级最怕静默：能力下降了但没人知道，评测时会把降级当成模型变差。所以降级一定要进日志和 trace 的字段。」别说：「加 try/except 包一下就好了。」

Q5：流式输出是怎么实现的？为什么不用 WebSocket？ A（要点）：LLM 场景只需要「服务器单向把 token 推下来」，HTTP 上就能做，不需要协议升级——所以用 SSE，媒体类型 text/event-stream，帧格式是 event: / data: 行加一个空行结束。WebSocket 留给真正需要双向、低延迟小消息的场景（协同编辑、语音双工）。加分句：「我在注释里写过『假流式（拿完整答案再切块吐）不改善首字延迟』——所以我把它排除掉了，剩下要接受的真实代价是失去 JSON mode 的语法保证，引用改成流结束后用程序抽取并校验。」别说：「流式让回答更快了。」（快的是首字延迟，总时长一点没变。）
