Python 类型与数据校验 ​

覆盖知识点：L0-01 L0-26 ｜ 面试频率：高 ｜ 建议学时：7h

一句话说清 ​

LLM 应用里最容易出错的不是模型，是数据在边界处的形状：用户传来的 JSON、模型吐出的结构化输出、工具调用的入参、写进数据库的那些字段。这一页把两件事绑成一条线：用 type hints / dataclass / pydantic 把「靠约定的字典」变成「有校验的对象」（L0-01）；再把校验后的对象与 JSON Schema 对齐，并规定校验失败时怎么办（L0-26）。核心判据只有一条：任何一条跨越边界的数据，都必须在一个明确的地方被校验过，且失败时系统给出可定位的错误，而不是在十层调用之后崩掉。

为什么必须学 ​

面试官在两种场合一定会碰这块。第一种是编码环节：让你写一个函数，你给 def parse(data): 而不是 def parse(data: dict) -> Chunk:，第一印象就掉一档——应届生里能自然写出类型的人不多。第二种是项目深挖：「你的工具调用参数怎么校验的」「模型返回的 JSON 少了一个字段你怎么办」「同一份代码怎么跑两套评测配置」。这三个问题的答案，决定了面试官把你归到「会调 API 的人」还是「做过系统的人」。

HR 端也看这里：技能栏出现 pydantic / JSON Schema / type hints，与 LangGraph RAG 出现在同一行的简历，给人的信号是「这人的代码是能维护的」。反过来，「熟练 Python」但不带任何工程关键词，会被归到只会写脚本的一类。

核心内容 ​

L0-01 Python 类型与工程规范 ​

  • 定义：类型标注是写给人看、给工具查的接口契约；运行时是否真的拦截，取决于你用哪种载体。三种载体的分工要背熟：
    • typing.Annotation / typing.TypedDict：静态可查（mypy / pyright），运行时完全不校验，一个字段缺失也不会报错。
    • @dataclass：运行时给你 __init__ / __repr__ / __eq__，但不做类型校验，Chunk(text=123) 照样跑。
    • pydantic.BaseModel：运行时真校验，失败抛 ValidationError，并且能按字段打印错在哪一条。
  • 机制：LLM 项目里的高频数据形态只有四类——请求体、工具入参、模型结构化输出、检索命中的 chunk。这四类全在边界上，全该用 pydantic；而系统内部流转的中间对象（例如检索命中的 Hit）用 @dataclass 就够，不必每层重新校验。边界严、内部松，是性能与安全之间最省事的折中。
  • 为什么这样设计：LLM 的输出是概率性的，你无法保证它一定给出合法 JSON。把校验放在边界，等于把「模型可能不听话」这件事收敛到一个可处理的点上；散落在业务代码里做 if "key" not in d，则会让错误延迟到很远的地方爆发，排查时你只知道「线上某处报 KeyError」。
  • 代码（以下为示意写法，field_validator 属 pydantic v2 接口）：
python
from __future__ import annotations

from pydantic import BaseModel, Field, ValidationError, field_validator


class RefundRequest(BaseModel):
    order_id: str = Field(min_length=6, max_length=32, description="订单号")
    reason: str = Field(default="", max_length=200)
    amount_yuan: float = Field(gt=0, description="退款金额，单位元")

    @field_validator("order_id")
    @classmethod
    def strip_and_upper(cls, v: str) -> str:
        return v.strip().upper()


try:
    req = RefundRequest.model_validate({"order_id": " ab1234 ", "amount_yuan": -1})
except ValidationError as e:
    # e.errors() 给出 [{loc: ('amount_yuan',), msg: 'Input should be greater than 0', ...}]
    for err in e.errors():
        print(err["loc"], err["msg"])

  • 常见误区：
    • 用 model.dict() / model.json()——这是 v1 的写法，v2 里是 model_dump() / model_dump_json()。写错版本是最容易被面试官抓的细节。
    • 用 model_construct() 绕开校验，然后在业务代码里默认它一定合法。model_construct 存在的意义是反序列化已信任的数据，不是给你偷懒。
    • 可变默认值：tags: list[str] = []。pydantic 内部对可变默认值做了拷贝，但如果你用 @dataclass 就会踩经典的共享默认值坑，跨实例串数据。
    • except ValidationError: return None。丢掉 errors() 的字段信息，等于把最有价值的排查线索扔了。

L0-26 数据序列化与校验（JSON Schema） ​

  • 定义：JSON Schema 是跨语言的数据契约，pydantic 模型可以通过 Model.model_json_schema() 直接导出它。同一个 Schema 有三个用途：给前端对齐字段、给 LLM 当结构化输出的约束、给工具定义当 parameters。
  • 机制：JSON 只有五种基础类型，所以 Python 侧的对象必须被降维——datetime → ISO 8601 字符串，Decimal → 字符串（避免二进制浮点误差），set → 数组，Path → 字符串，bytes → base64 字符串。向量本身不要塞进 JSON 再传，那是几十 KB 的无用负载；传 chunk_id，让下游自己去索引里取。
  • 量化边界：一个工具 schema 的字段数控制在 8 个以内、每个字段都给 description。字段太多会让模型的参数错误率上升，也会让 prompt 里的工具定义挤占上下文预算。
  • 校验失败的三条路（这一段是面试里最值钱的部分，因为它体现你「设计过失败路径」而不是「祈祷模型听话」）：
    1. 回灌重试：把 e.errors() 压缩成「字段 + 约束 + 你给的值」三列，连同原始输出一起回给模型，让它只做修正。重试次数上限设 1–2 次，超过就降级。
    2. 宽松降级：只对关键字段强校验（例如 order_id、amount_yuan），其余字段允许缺失并填默认值。适用于「少一个可选字段也能给出有用答案」的场景。
    3. 快速失败：离线评测、批处理场景直接判这条样本失败并计入指标。在评测里悄悄放过一条失败样本，比直接报错危害大得多——它会让你的分数虚高。
  • 代码（回灌重试的最小骨架）：
python
def parse_with_repair(raw_text: str, model_cls, call_llm, max_retry: int = 2):
    last_err = None
    for _ in range(max_retry + 1):
        try:
            return model_cls.model_validate_json(raw_text)
        except ValidationError as e:
            last_err = e
            raw_text = call_llm(
                fix_prompt(raw_text, e.errors())  # 只把字段/约束/实际值回给模型
            )
    raise last_err  # 交给上层做降级，不要在这里静默返回 None

和你自己的项目对上号 ​

  • YYHelp v2 的工具层：@tool 装饰器 + pydantic 入参模型，是本页知识的直接落地。写操作（查订单、建工单）如果入参校验失败就继续往下走，会引发最糟糕的后果——拿错误的订单号去写库。正确做法是校验失败立刻返回一个结构化的失败对象（指出哪个字段不合法），让 ReAct 循环里的模型自己决定是重问用户还是重新调用。这正是「校验失败三条路」中的第 1 条。
  • YYHelp v2 的状态图：graph/state_v2.py 里每个字段都要回答「它的 reducer 是什么、为什么」。这背后是一个真实的坑——字段清单、new_state() 的构造字典、自检脚本的期望集合是三处真源，加字段时改一处就会漂移；实测出现过 state_v2.py --selftest 红着而 pytest 全绿的情况（因为那个自检从未被 pytest 收集）。修法就是本页的思路：能推导的清单不要手写第二遍，字段清单从 schema 推导，并用一条「故意配错 reducer」的测试来证明断言真的会红。这条经验在面试里答「你怎么保证 schema 演进不出错」时非常有力。
  • 科研文献 RAG 的检索命中对象：retrieve.py 里用 @dataclass class Hit 描述检索结果，而请求体与工具入参用 pydantic 模型——这正是「边界严、内部松」的分工。Hit 在内部流转时不做重复校验，但它的字段名会被写进 trace 与评测快照，所以字段一旦改名，评测脚本与 badcase 分析都要跟着改：内部对象的字段名也是契约，只是它的破坏方式不是报错，而是分析脚本静默失效。
  • 还没做到的：模型输出的结构校验目前是「prompt 约束 + 生成后校验」，没有用厂商的 response_format 强约束字段级 schema（JSON mode 只保证整体是 JSON）。面试被问到「怎么降低解析失败率」时，诚实的答法是：现在靠一次回灌重试把失败率压住，并在 trace 里记录失败字段；下一步是把工具 schema 直接作为结构化输出约束传给模型，减少「格式对但字段错」这一类失败。

面试怎么问（≥3 组） ​

Q1：你的工具调用参数是怎么校验的？模型给错参数会怎样？ A（要点）：工具入参用 pydantic 模型定义，@tool 把它转成 JSON Schema 交给模型；调用时先 model_validate，失败不抛给业务层，而是返回结构化错误（哪个字段、违反什么约束、实际值是什么），让 ReAct 循环里的模型有机会自我修正；重试有上限，超限就返回「无法完成」并把这次失败写入 trace。加分句：「我这套设计的前提是不信任模型输出——校验点是唯一的，错误信息是字段级的，所以我能从日志里直接看出是模型给错了参数还是我没把约束写清楚。」别说：「pydantic 会自动校验的，不会出错。」

Q2：模型返回的 JSON 解析失败，线上怎么处理？ A（要点）：分三步——① response_format 只保证是 JSON，字段级校验必须自己做；② 把 e.errors() 压成字段/约束/实际值三列回灌给模型做一次修正（上限 1–2 次）；③ 仍失败则降级：关键字段缺失就拒答或走兜底话术，非关键字段缺失就填默认值继续。离线评测场景选择直接判失败并计入指标，避免分数虚高。加分句：「我会统计解析失败率并按失败字段聚类，如果某个字段反复失败，通常是 schema 描述写得不够清楚，而不是模型不行。」别说：「加个 try/except 返回默认值」——那会把错误藏起来。

Q3：JSON Schema 和 pydantic 是什么关系？ A（要点）：model_json_schema() 从模型导出标准 JSON Schema，一份 Schema 三处用：结构化输出约束、工具定义、前后端字段对齐。加分句：「要注意 JSON 只有基础类型，datetime/Decimal/向量都得先降维——向量我只传 chunk_id，不把几十 KB 的浮点数组塞进 JSON。」别说：「就是一个校验库。」（只答工具名不答契约价值，会被判定为背书型答案。）

Q4：你怎么保证数据结构的演进不出错（今天加一个字段，明天改一个名字）？ A（要点）：三件事——① 字段清单只保留一处真源，能从 schema 推导的就不要在手写的地方再抄一遍（构造字典、自检期望集合都是典型的手抄点，它们漂移时不会报错，只会让某个字段悄悄丢）；② 每条字段配一条「能失败的断言」，并用一条故意配错的用例证明断言真的会红；③ 跨进程的契约（工具 schema、模型输出）改动时带版本号并写进 trace。加分句：「我踩过一次三处真源漂移的坑——自检脚本红着而单元测试全绿，因为那个自检从来没被测试框架收集到；从那以后我会先问『这条断言有没有可能红』，再问『它现在绿不绿』。」别说：「加字段嘛，加就行了，不会有问题。」
