测试、mock 与可测性 ​

覆盖知识点：L0-04 ｜ 面试频率：中 ｜ 建议学时：5h

一句话说清 ​

模型是随机的、外部 API 是要钱的、下载模型是要几个 GB 的——这三件事加起来，意味着你不能用「跑一遍看看」来验证 LLM 应用。这一页讲怎么把系统改造成可测的：用 pytest 的 fixture 固定外部世界的状态，用假实现（stub / mock）把模型调用换成确定的返回，用 parametrize 把评测集和单元测试接起来。核心判据只有一条：一个「不联网、不花钱、秒级返回」的测试套件，能否覆盖检索、生成、拒答、降级四条链路。 能，你的项目就是工程；不能，它就是一个 demo。

为什么必须学 ​

面试官问「你怎么保证改了 prompt 没把别的东西弄坏」时，答案是评测与回归门禁——但门禁能不能进 CI，取决于测试是否确定。一个需要下载 4.4 GB 模型、调真实 LLM、单次跑十几分钟的检查，放进 CI 的结果不是「更安全」，而是「跑一次十几分钟、要配 API Key、外部服务抖动就会变红，最后团队把门禁关掉」——等于没有门禁。

这块的面试频率是「中」，但它对你的项目可信度是决定性的。同样两个 RAG 项目，一个有测试与 CI、一个没有，面试官对前者「评测集是怎么标的」的追问会温和得多。另外注意这一页的次级收益：把代码改成可测的，顺带就把「换模型要改几处」这个问题解决了——可测性和可替换性是同一件事的两面（依赖注入与分层的完整讲法在设计模式与依赖注入）。

核心内容 ​

L0-04 测试与 mock ​

  • 定义：测试的本质是把外部世界固定住，只让被测逻辑变化。LLM 应用里需要被固定的外部世界有四类：模型服务（随机 + 花钱）、检索索引（几 GB 的产物）、文件系统（PDF 原文）、时钟与随机数（影响幂等与退避）。
  • pytest 的三件必会：
    • fixture：准备与清理测试资源，靠 scope 控制粒度——session 级放「只读、构造昂贵」的产物（切好块的语料、小规模索引），function 级放「会被修改」的状态。
    • parametrize：同一段断言跑多组输入，这是把评测集和单元测试连起来的桥梁。
    • -k / -m 选择性执行：把「离线秒级」与「需要模型」的测试分开，前者进 CI，后者留在本地。
  • 代码：
python
import pytest

pytestmark = pytest.mark.offline  # 离线测试标记，CI 只跑这一类


@pytest.fixture(scope="session")
def fake_llm():
    """假模型：把 (prompt 关键字 -> 固定回答) 做成表，测试不联网、不花钱。"""

    class FakeLLM:
        def __init__(self, table: dict[str, str]) -> None:
            self.table = table
            self.calls: list[str] = []

        def complete(self, prompt: str) -> str:
            self.calls.append(prompt)
            for key, answer in self.table.items():
                if key in prompt:
                    return answer
            return "根据提供的资料无法回答该问题"

    return FakeLLM({"安全距离区间": "根据资料，安全距离区间为 [1]。"})


def test_refusal_when_no_evidence(fake_llm):
    """检索为空时必须走拒答，而不是硬编一个答案。"""
    from generate import answer_question

    out = answer_question("Transformer 的 KV Cache 显存怎么估算？", retriever=lambda q: [])
    assert out.refused is True
    assert fake_llm.calls == []  # 拒答路径不应产生 LLM 调用（省一次配额）

  • mock 的粒度与代价：mock 掉外部调用，不要 mock 掉被测逻辑。把 retrieve 换成一个返回固定 chunk 列表的假函数是合理的；把「切块函数」也 mock 掉，你的测试就只剩下断言自己写的假数据。
  • 断言要断在契约上，不要断在文案上：
    • 该断的：返回对象是否有引用编号、引用编号是否都能在上下文里找到、拒答标志、调用次数、是否落盘 trace。
    • 不该断的：LLM 回答的具体措辞。措辞会随模型和 prompt 变化，断言辞的测试会让门禁天天红，最后被人加 skip。
  • 一个必须写的测试：失败敏感性测试。 做法是「故意做出一个错误实现，断言测试会红」。例如给状态字段配一个错误的 reducer，如果测试仍然全绿，说明那条断言从来没生效过——这比没有测试更危险，因为它给了你虚假的安全感。
  • 常见误区：
    • 用 sleep 等异步结果（flaky 的根源），应该用事件或 await。
    • 测试之间共享可变状态（模块级 list 累积），导致「单独跑绿、全跑红」。
    • 只在本地跑过就认为 CI 会过（依赖没写进依赖文件、路径写死成 D:\...）。

可测性的唯一前提：依赖是「传进来的」 ​

L0-04 的测试能写成离线秒级，前提是代码里没有在函数内部 new 出它需要的外部对象。测试改造的第一步不是学 pytest，而是给三个依赖各开一个「可替换的入口」：

python
class StubRetriever:
    """把「检索」换成确定输入：测试不再依赖索引产物，也不需要模型。"""

    def __init__(self, hits: list[Hit]) -> None:
        self._hits = hits
        self.queries: list[str] = []

    def search(self, query: str, top_k: int) -> list[Hit]:
        self.queries.append(query)
        return self._hits[:top_k]


def test_answer_uses_retrieved_context():
    from generate import answer_question

    stub = StubRetriever([Hit(text="安全距离区间为 [1]。", score=0.9, source="p1", doc="spec")])
    out = answer_question("安全距离是多少？", retriever=stub, generator=FakeLLM({}))
    assert stub.queries == ["安全距离是多少？"]   # 断言「检索被调用了」，不是断言措辞
    assert out.citations == ["p1"]

真正的框架级替换发生在服务层——FastAPI 的 dependency_overrides 让你在一次测试里把整条路由的真实模型客户端换掉，业务代码一行不改：

python
from fastapi import Depends, FastAPI

app = FastAPI()


def get_generator():
    return RealLLMClient()          # 生产实现


@app.post("/ask")
async def ask(q: str, gen=Depends(get_generator)):
    return {"answer": gen.complete(build_prompt(q, []))}


# 测试文件里：整体替换，不改任何业务代码
app.dependency_overrides[get_generator] = lambda: FakeLLM({})

这条路径本身属于 L0-23（依赖注入与分层架构，见设计模式与依赖注入）；本页只取它对测试的意义：可测性是「依赖从外部传入」的直接结果，不是靠更努力地写断言换来的。 反过来，如果为了测一个函数不得不去 monkeypatch 模块级单例，那就是设计信号——该把依赖提到参数上了。

  • 常见误区：
    • 用「全局单例 + 猴子补丁」做测试替换。补丁漏了一处，测试就变成真实调用（CI 变红或直接烧钱），而代码本身完全看不出来。
    • 只在代码里加 if os.getenv("TESTING") 分支。这等于把测试逻辑混进生产路径，两者互相污染。
    • 把「能 mock」当成设计目标。能 mock 只是副产品，真正的目标是换实现不改业务代码。

和你自己的项目对上号 ​

  • CI 只跑离线检查：rag-demo/.github/workflows/ci.yml 里写明了一个刻意的工程决策——完整链路要下载 4.4 GB 模型（bge-m3 + bge-reranker）并调真实 LLM，放进 CI 会导致「跑一次十几分钟、要配 API Key、外部服务抖动就让 CI 变红」，最后团队会把门禁关掉。所以 workflow 只做三件事：装轻量依赖（numpy / rank-bm25 / fastapi / uvicorn[standard] / httpx / pydantic，不装 torch、不下模型）、跑 python ci_checks.py（语法 + 单元 + 服务层 + obs 自检）、timeout-minutes: 10。需要模型的检索质量、三组消融、答案准确率留在本地 run_all_checks.py，并在 README 里写明「手动跑 + 记录结果」。这段话本身就是面试答案：它体现你理解「门禁的价值在于可持续执行，而不是覆盖面最大」。
  • 假模型 + 结果表：test_generate_mock.py 用假模型验证生成链路（引用抽取、拒答分支），不联网、不花钱；test_metrics.py 对指标计算做纯函数单测；test_heading_regex.py 对标题正则做参数化测试。这三个文件正好对应本页的三种测试层级：纯函数 / 契约 / 端到端骨架。
  • 依赖注入的现状与缺口：service.py 使用 FastAPI + pydantic 请求模型，service_tests.py 依赖 httpx（TestClient 的传输层）做离线服务测试——这已经具备「注入假实现」的结构。但检索与生成目前仍以模块级函数形式被路由直接调用，没有走 Depends，所以替换粒度是进程级的（改配置重启），不是请求级的。面试被问到「你怎么支持换模型做 A/B」时，诚实的答法是：现在靠配置 + 重新启动，PROMPT_VERSION / LLM_MODEL 都写进了 trace，可以用同一套评测脚本对比两次运行；要做请求级灰度，下一步是把生成器换成 Depends 注入的接口，按请求头或流量比例选实现。
  • YYHelp v2 状态图的经验：v1 出现过「字段清单 / new_state() 构造字典 / 自检期望集合三处真源漂移，导致 --selftest 红而 pytest 全绿」的缺陷——因为那个自检从未被 pytest 收集。修法是让字段清单从 schema 推导，并用「故意配错 reducer」的测试证明断言真的会红。这两条（能推导的不要手写第二遍、证明你的测试失败敏感）在面试里是比「我写了 125 个测试」强得多的表述。

面试怎么问（≥3 组） ​

Q1：你的项目有测试吗？LLM 是随机的，怎么测？ A（要点）：分三层——纯函数单测（切块、RRF 融合、指标计算，全部确定）；服务层测试（用假客户端与假 retriever 覆盖路由、重试、降级、拒答，离线秒级）；质量评测（需要真实模型，走评测集与回归门禁，不进 CI）。随机性用「固定 seed + 断言契约不断言辞」处理：断引用编号是否可核对、断拒答标志、断调用次数，不断具体句子。加分句：「我的 CI 刻意只跑前两层，因为把需要 4.4 GB 模型和外部 API 的检查放进 CI，两周内它就会被人关掉——门禁的价值在于能被持续执行。」别说：「模型有随机性所以没法测。」

Q2：怎么保证改了 prompt 不会把别的功能弄坏？ A（要点）：三层防线——单元/服务层测试保证「结构不坏」（引用可核对、拒答分支仍在）；评测集 + 回归门禁保证「质量不降」（配对比较 + 多重比较校正 + 效应量门槛，输出三态退出码）；prompt 版本号进日志与 trace，让分数变化能被归因到具体改动。加分句：「prompt 改动必须有版本号，否则三周后你分不清分数下降是 prompt 造成的还是检索造成的。」别说：「我改完自己点几个问题看看。」

Q3：你的测试怎么做到不联网、不加载模型？ A（要点）：把外部依赖变成「传进来的参数或框架依赖」，而不是函数内部创建的对象。测试时传假 retriever / 假模型；服务层用 FastAPI 的 Depends + app.dependency_overrides 整体替换真实客户端，业务代码一行不改。加分句：「我不会 monkeypatch 模块级单例——那种测试的通过与否取决于『有没有人忘了打补丁』，而补丁漏一处就会变成真实调用，在 CI 里直接烧钱。」别说：「跑测试前先把模型下载好就行了。」

Q4：mock 掉模型调用，测试不就没有意义了吗？ A（要点）：mock 的目的是把「外部世界的不确定」与「我的逻辑」分开，断言点在后者：检索为空必须拒答、引用编号必须可核对、重试耗尽必须走降级并打标记。真实模型的质量由评测集负责，两者职责不重叠。加分句：「我还会写失败敏感性测试——故意做一个错误实现，断言测试会红；如果还绿，说明那条断言从来没生效。」别说：「mock 之后只能测流程，测不了质量」（对，但没说出分工）。
