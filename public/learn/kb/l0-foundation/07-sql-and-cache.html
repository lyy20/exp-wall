数据层：SQL、缓存与读写路径 ​

覆盖知识点：L0-12 L0-13 ｜ 面试频率：高 ｜ 建议学时：9h

一句话说清 ​

这两项回答同一个问题的两个面：数据放在哪里、怎么读得快。L0-12（关系型数据库与 SQL）负责「不能丢、要能查、要能对账」的部分——用户、会话、工单、问题池；L0-13（Redis 与缓存）负责「读得多、变得快、丢了也还能重建」的部分——限流计数、热数据缓存、任务队列。判据：问自己「这份数据丢了会怎样」——会丢客户的钱和你的结论的，进数据库；丢了只是慢一点的，可以进缓存。

为什么必须学 ​

面试官问「你的问题池表怎么设计的」时，他在看三件事：你有没有真建过表（字段、类型、时间、唯一键），你有没有被烂查询教育过（索引、慢查询、EXPLAIN），你有没有想过并发（事务、锁、幂等）。只会写 SELECT * 的候选人，在「数据飞轮要按 trace_id 关联检索快照」这种需求上会立刻暴露出设计能力的缺口。

缓存那一半考的是判断力：什么时候该加缓存、加完怎么保证不一致窗口可控、哪些数据绝对不能缓。能说清「我用缓存换到了什么、付出了什么代价」的人，和「听说 Redis 快所以就加一个」的人，在面试官眼里是两个量级。数据在进程之间传递时的形状与校验（L0-26）属于Python 类型与数据校验，这里只讲它落到表结构与缓存键上的后果。

核心内容 ​

L0-12 关系型数据库与 SQL ​

  • 定义：关系库 = 表（行 + 列 + 约束）+ 事务 + 查询优化器。它对你的承诺是 ACID：原子性（要么全成要么全不成）、一致性（约束不被破坏）、隔离性（并发事务互不干扰到约定的程度）、持久性（提交了就不丢）。
  • 表设计的三条实用规则：
    1. 每张表都要有主键，业务表另加一个唯一键表达业务不变式。例如问题池需要「同一条问题只登记一次」，那就让 (question_hash) 唯一——约束写在数据库里，比写在代码的 if 里可靠，因为并发下代码判断会漏。
    2. 时间字段用带时区的类型，并统一时区。同一条记录的时间要与 trace 时间戳对齐，否则「先看 trace 再查表」时两边差几小时，排查时你会怀疑人生。
    3. 状态用可枚举的短字符串或小整数，不用中文长句。长度稳定、能建索引、改文案不用改数据。
  • 索引：唯一值得背下来的性能知识。没有索引时，WHERE 条件只能全表扫描——数据量从 1 万涨到 100 万，查询时间线性上涨。索引把「找行」变成「在有序结构里定位」，代价是写入变慢、占空间。所以：给「经常出现在 WHERE / JOIN / ORDER BY 里的列」建索引，不是给所有列建索引。
    • 复合索引遵循最左前缀：(a, b) 上的索引能服务 WHERE a=? 和 WHERE a=? AND b=?，但不能服务 WHERE b=?。
    • 对列做函数运算会让索引失效：WHERE DATE(created_at) = '2026-10-01' 用不上 created_at 上的索引，改成范围查询 created_at >= ... AND created_at < ...。
    • 用 EXPLAIN 验收，而不是靠感觉。看 type 列（ALL = 全表扫描，是要修的信号）、key（实际用了哪个索引）、rows（预估扫描行数）。
  • 事务与隔离级别：默认的可重复读已经能挡住大部分并发异常，但要记住两个真实风险：丢失更新（两个请求读同一个值、各自加一再写回，结果只加了一次）和写偏斜（两次读的范围结果不自洽）。前者靠 SELECT ... FOR UPDATE（悲观锁）或版本号乐观锁解决——幂等键 + 唯一索引是比锁更简单的一种写法。
  • 慢查询：把 long_query_time 设为 3 秒在客服这类在线业务里已经算故障级——不是「有点慢」，是「用户已经在抱怨了」。慢查询日志的价值在于它告诉你哪条语句该加索引或改写法，而不是让你事后猜。
  • 常见误区：
    • N+1 查询：查 100 条订单，再循环里为每条查一次用户 → 101 次往返。改用一次 JOIN 或一次 IN 批量查。
    • 用 SELECT * 然后在应用层丢掉大部分字段。宽表 + 大字段（文本、JSON）会显著放大 IO。
    • 把大段文本、向量、二进制塞进主业务表。该拆表拆表，该进对象存储进对象存储。
    • 把 TEXT 之类大字段塞进经常扫描的表，让每页能装的行数骤降。

L0-13 Redis 与缓存基础 ​

  • 定义：Redis 是内存里的数据结构服务器——KV、哈希、列表、集合、有序集合，都支持过期。它快的原因是「数据在内存 + 单线程避免锁竞争」，代价是内存有限、持久化不是默认强一致。
  • 缓存最常用的形态是 Cache-Aside：读时先查缓存、未命中就查库并回填；写时更新数据库 + 删除缓存（而不是更新缓存）。为什么删除而不是更新：先写库再写缓存的两步之间必然存在窗口，删缓存把「不一致窗口」压缩到「下一次读回填」这一刻，而更新缓存会把这个窗口放大到「两次写的间隔」。
  • 三个必须认识的失效模式：
    名称症状做法
    缓存穿透查询不存在的数据，每次都打到库缓存空值并设短 TTL；入口做参数校验
    缓存击穿某个热点 key 恰好过期，瞬间大量请求同时回源单飞（single-flight）：只让一个请求去回源，其余等结果
    缓存雪崩大批 key 同时过期，或缓存整体不可用TTL 加随机抖动；缓存故障时降级为直接查库并限流
    TTL 加抖动是本页最便宜的一条经验：ttl = 300 + random.randint(0, 60)，避免同一批写入的数据在同一秒集体过期。
  • 淘汰策略（maxmemory-policy）要按用途选，不能一把梭：
    • 纯缓存：allkeys-lru——内存满了淘汰最久未用的，重建成本可接受。
    • 当队列用（例如任务上报先入队再批量落库）：必须 noeviction。用 LRU 会在内存压力下淘汰掉队列里的任务，症状是「数据少了几条」，而日志里什么都没有——这是最贵的一类 bug，因为它在数据层静默发生。
  • 分布式锁的最小正确写法（三个要点缺一不可）：
    SET lock_key <唯一token> NX PX 30000     # 原子加锁 + 过期兜底，防止持有者崩了锁不释放
业务处理…
if token 匹配: DEL lock_key              # 只删自己的锁
    1
    2
    3
    ① NX 保证「只有一个人拿到」；② PX 过期时间防止死锁；③ token 必须是唯一值并且删除前比对——否则你会在自己超时后，把别人的锁删掉。更重的场景（多 key、需要原子性）才需要 Lua 脚本或现成的锁库。
  • 常见误区：
    • 把 Redis 当唯一存储用。它是缓存/队列，默认配置下重启可能丢数据；真数据必须在数据库或对象存储里有原件。
    • 缓存没设 TTL，指望手动清理。
    • 用缓存来「修」慢查询。缓存只是把慢查询变成偶尔的慢查询，根因还在。

落库前后的三个形状问题 ​

数据结构与校验的完整讲法在 Python 类型与数据校验（L0-26）；本页只取和存储相关的三条：

  • 进入数据库的那一份必须是「已校验」的。 业务表一旦写进脏数据，后面所有的查询、报表、缓存都会继承这个错误。所以约定是：校验发生在写库之前的那一层（FastAPI 的 Pydantic 模型或仓储层的入参校验），数据库拿到的永远是通过校验的对象。FastAPI 把校验失败自动变成 422 + 结构化错误体，坏数据根本进不到业务代码里。
  • 格式选择：JSON vs protobuf。 JSON 人可读、跨语言、无 schema 也能读，是 HTTP 接口与 LLM 结构化输出的默认选择；protobuf 体积小、schema 强约束、但需要编译，适合服务间高频调用。混合用法很常见：对外接口用 JSON，内部的写操作事件与消息用 protobuf。
  • 加字段与改字段的兼容性不同。 加字段通常兼容（老读者忽略新字段），改字段类型或删字段不兼容——这是要版本化的原因（L0-19）。最常见的翻车方式是「我把接口字段名改了，忘记改缓存里的 key 与 trace 里的字段」，于是缓存全部 miss、分析脚本静默数不到数据。字段名也是契约，改它要按改接口对待。

和你自己的项目对上号 ​

  • 数据库层是「双实现」而不是单一实现：科研文献 RAG 提供 MySQL 与 SQLite 两套后端，能在没有 MySQL 的机器上降级运行。这件事在面试里的说法是：降级不是妥协，而是让「第一天上手」和「生产运行」用同一份代码——代价是要保证两侧 SQL 语义一致（例如时间函数、自增、UPSERT 写法都有差异）。
  • 慢查询与索引验收有真实配置：YYHelp 的 MySQL 容器参数里显式设了 --slow-query-log=1 --long-query-time=3（理由：3 秒在 OLTP 客服场景已是故障级），并统一 --default-time-zone=+00:00——因为数据飞轮的 first_seen_at / last_seen_at 要和 trace 时间戳对齐。同时字符集用 utf8mb4：用旧的 utf8（实为 utf8mb3）插入 emoji 会直接报 Incorrect string value: '\xF0\x9F...'。这三行参数每一个都对应本页的一条论点。
  • Redis 的 noeviction 不是随手写的：容器栈里给 Redis 显式设了 --maxmemory-policy noeviction，理由是队列任务（trace 上报先入队再批量落库）不能因为内存压力被淘汰——用 LRU 会导致 trace 静默丢失，而 UI 上只看到「少了几条」。这正是 L0-13 里「淘汰策略要按用途选」的实例，也是「静默失败最贵」的又一次印证。
  • 数据形状的纪律在项目里到处可见：retrieve.py 用 @dataclass class Hit 统一检索结果的形状；config.py 用 @dataclass 把环境变量收敛成有类型的配置对象（asdict() 还能直接打日志，且不打密钥）。检索快照要整段写进问题池表，所以它的字段名一旦改动，历史快照的可解读性就断了——这也是「字段名是契约」的实例。

面试怎么问（≥3 组） ​

Q1：你的问题池表怎么设计？为什么要加唯一键？ A（要点）：字段上——问题哈希（唯一）、原始问题、检索快照、来源入口（弱证据被拒答 / 生成前自评未过 / 用户点踩）、首次与最近出现时间、处理状态；时间统一时区以便和 trace 对齐。唯一键的作用是「同一条问题只登记一次」这个不变式由数据库来保证，而不是靠应用层先查后写——并发下先查后写会漏。加分句：「入口来源单独存字段，是为了后面能回答『哪一类失败贡献最多』。」别说：「用 INSERT IGNORE 就行，重复了也无所谓。」（那你就没法统计频次了。）

Q2：数据量大了查询变慢，你怎么定位？ A（要点）：先看慢查询日志找具体语句，再用 EXPLAIN 看 type 是不是 ALL（全表扫描）、key 有没有用上索引、rows 预估扫多少行；然后按最左前缀的原则调整索引，或者改写让列上不做函数运算。加分句：「我会先确认瓶颈是查询还是数据量——有时候真正的修法是分页、只取需要的列，或者把大字段拆表。」别说：「加个缓存吧。」（缓存是推迟问题，不是解决问题。）

Q3：缓存和数据库怎么保证一致？ A（要点）：Cache-Aside——读未命中回填，写时更新库 + 删除缓存而不是更新缓存，把不一致窗口压到最小；再配 TTL 抖动、空值缓存、单飞回源。加分句：「我会明确说清代价：这是最终一致，不是强一致；对账类逻辑必须直接读库，不能读缓存。」别说：「双写就一致了。」（双写的窗口更大。）

Q4：你为什么要维护 MySQL 与 SQLite 两套数据层实现？怎么保证它们行为一致？ A（要点）：SQLite 让「第一天上手」不需要装任何数据库就能跑通全链路，MySQL 是生产形态；同一份代码用配置切换后端。代价是两侧 SQL 方言有差异（时间函数、自增、UPSERT 写法），所以要把差异收敛在一个仓储层里，而不是散落在业务代码中。加分句：「我没有做接口契约测试来保证两套实现行为一致——这是明确的缺口；下一步是给仓储接口写一套共享的行为测试，两套实现都跑同一套用例，把『换实现』从手工验证变成自动验证。」别说：「两个都一样，只是换个连接字符串。」（方言差异会以静默错误的形式出现。）
