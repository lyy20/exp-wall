环境、依赖与交付形态 ​

覆盖知识点：L0-03 L0-08 L0-07 ｜ 面试频率：中 ｜ 建议学时：10h

一句话说清 ​

面试官问「你的项目别人 clone 下来能跑吗」时，考的是三件事：依赖是不是钉住的（L0-03）、运行环境是不是可重建的（L0-08）、你能不能在没有图形界面的机器上把它起来并排障（L0-07）。顺序是：本地用虚拟环境 + 锁文件把依赖钉住；容器把「操作系统 + Python + 依赖」一起固化成镜像；最后在 Linux 上用 ssh / 进程 / 端口 / 日志这套工具把它跑起来。判据：给另一个人一台干净机器和一条命令，他能不能在 20 分钟内看到同样的结果。 能，你的项目才是「交付物」；不能，它只是「你机器上的东西」。

为什么必须学 ​

三个高频追问都落在这里。第一「你项目怎么部署的」——回答「我本地能跑」直接结束这一轮。第二「你装的 torch 是 GPU 版还是 CPU 版，为什么」——这个问题看似细节，实际在测你有没有真的配过环境。第三「模型文件多大，打进镜像了吗」——把 4.4 GB 模型打进镜像的人，会立刻被判定为没做过交付。

还有一个更现实的动机：你的简历要贴 GitHub 链接。面试官 clone 下来跑不通，比没有仓库更糟——它证明你写的东西不可复现。

核心内容 ​

L0-03 包管理与虚拟环境 ​

  • 定义：虚拟环境解决「多个项目依赖同一个包的不同版本」；包管理器解决「怎么装、怎么记、怎么复现」。两条轴分开看：
    工具定位什么时候用
    venvPython 标准库自带的虚拟环境只想隔离环境，依赖清单自己维护
    pip标准安装器装包；配 requirements.txt 用
    uv用 Rust 写的极快安装器与解析器，兼容 pyproject.toml想快速重建环境、要锁文件
    conda连非 Python 依赖（CUDA 库等）一起管需要它管的二进制依赖时才用，否则是负担
    poetry / pdm以 pyproject.toml 为中心的依赖与打包要发 SDK 或包时
  • pyproject.toml 与 requirements.txt 不是一回事：前者是项目元数据 + 依赖声明（包名、版本范围、构建后端、工具配置），是 PEP 621 定义的标准；后者是一份可被任意工具读取的清单，历史更久、语义更弱。小项目用哪个都行，但要知道差别——面试问「你的依赖声明放哪」时，答 pyproject.toml 说明你按现代标准做事。
  • 可复现性的关键不是「列了依赖」，而是「钉到什么粒度」。numpy>=2.0 这样的范围声明在三个月后可能装到不同的版本。两种钉法：
    • 直接依赖钉精确版本：faiss-cpu==1.15.1、rank-bm25==0.2.2。好处是清单短、一眼看得懂。
    • 生成完整锁文件：把传递依赖也冻住。只锁直接依赖时，传递依赖仍可能在别人机器上装出不同版本——症状就是「昨天还能跑，今天跑不了」。
  • 落地形态（本项目真实做法）：requirements.txt 是人读的，声明「我需要什么、为什么」，每个包后面写一行用途注释；requirements.lock.txt 是机器读的，冻结当时实际装到的版本。两者分工写进文件头注释，避免后来人困惑为什么有两份。
  • 常见误区：
    • 用 pip install -r requirements.txt 时不带虚拟环境，把包装进系统 Python。换机器就冲突。
    • 只钉直接依赖却不生成锁文件（见上）。
    • 把 .venv/ 提交进 Git。它包含几万个文件、几百 MB，而且路径是绝对路径，换机器基本没用。
    • 依赖清单里写 torch 不写变体。PyPI 上的 Windows 轮子通常是 CPU 版，要 GPU 得指定 --index-url 与 --gpus all——这行注释值得写进依赖文件里，因为下一个人一定会踩。

L0-08 Docker 镜像与容器 ​

  • 定义：镜像 = 只读的分层文件系统 + 启动配置；容器 = 镜像的一个运行实例 + 一层可写层。Docker 的一切都建立在「分层」上。
  • 分层与缓存（这是 Dockerfile 唯一必须理解的东西）：每条 COPY / RUN 产生一层，某层的内容变了，它和它之后的层全部失效、需要重建。所以顺序是——先拷依赖清单、装依赖，再拷源码。这样你改一行业务代码时，依赖层命中缓存，构建只需几秒；反过来（先拷代码再装依赖）则每改一行都要重装一遍所有依赖。
  • 代码：一个针对本项目形态的 Dockerfile（节选，逐行都有理由）：
dockerfile
FROM python:3.12-slim

ENV PYTHONUNBUFFERED=1 \
    PIP_NO_CACHE_DIR=1 \
    HF_HOME=/root/.cache/huggingface

WORKDIR /app

# 先装依赖再拷代码 —— 代码改动不会让依赖层缓存失效
COPY requirements.txt .
RUN pip install -U pip && pip install -r requirements.txt

COPY . .

# 健康检查查的是 /health 端点（它真的去验索引产物与配置），
# 而不是"进程还在不在" —— 假健康检查会让编排系统继续把流量导进不可用的实例
HEALTHCHECK --interval=30s --timeout=5s --start-period=120s --retries=3 \
    CMD python -c "import urllib.request,sys; \
sys.exit(0 if urllib.request.urlopen('http://127.0.0.1:8000/health', timeout=4).status==200 else 1)"

EXPOSE 8000
CMD ["python", "-m", "uvicorn", "service:app", "--host", "0.0.0.0", "--port", "8000"]

  • 四条必须记住的规则：
    1. 模型不进镜像。bge-m3 + bge-reranker-v2-m3 合起来约 4.4 GB，打进镜像会让镜像巨大、构建极慢，而且每次改代码都要重传。正确做法是运行时下载到挂载卷（例如 -v hf_cache:/root/.cache/huggingface），首次启动慢，之后复用。
    2. 数据用卷，不用容器可写层。容器删了可写层就没了；-v 或 compose 的 volumes 才让数据活过容器生命周期。
    3. 别用 latest 标签。latest 是滚动的，昨天和今天的同一个 latest 可能是两个版本。能钉版本号就钉版本号，只发滚动 tag 的镜像就钉 digest（image@sha256:...）。
    4. 区分「容器起来了」和「容器能服务了」。healthcheck 必须真查依赖：查端口开没开是不够的——MySQL 大库重启后端口已开但还在 crash recovery，此时连上去只会报错。
  • 常见误区：
    • 把密码写进 Dockerfile（ENV API_KEY=...）。镜像的每一层都可以被导出查看，这等于把 Key 公开。
    • 用 docker compose down -v 做日常重启。-v 会删数据卷。
    • 日志不设上限。不给限制的 json-file 日志会无声把磁盘写满，症状是某天报 no space left on device，而数据卷其实只有几个 GB——剩下全是日志。容器日志配 max-size + max-file 是标配。
    • 忘了宿主内核参数。Milvus 这类依赖 mmap 的服务要求宿主 vm.max_map_count >= 262144，不设的症状是 Milvus 起不来或跑几分钟后崩，报错里通常没有这个参数名——这是「排查方向全错」的典型。

L0-07 Linux 命令行与服务器基础 ​

  • 定义：把你从「会写 Python」变成「能把 Python 跑在别人机器上」。最小技能集只有五类：
    类别命令你要能回答的问题
    连接与传输ssh、scp / rsync怎么把代码送上去、怎么传一个文件
    进程与服务ps、top、systemctl status/restart、journalctl -u服务挂了怎么重启、日志在哪
    端口与网络ss -ltnp、curl -v、nc -z端口有没有被占、接口通不通
    文件与权限chmod、chown、df -h、du -sh为什么写不进去、磁盘满在哪
    资源与排障nvidia-smi（GPU）、free -h、tail -f显存被谁占了、内存够不够
  • 排障的固定顺序（面试爱问「线上服务 502 你怎么查」）：① 进程在不在（ps / systemctl status）→ ② 端口在不在听（ss -ltnp）→ ③ 本机 curl 通不通 → ④ 日志报什么（journalctl / 应用日志 / trace）→ ⑤ 依赖服务通不通（DB、向量库、模型服务）→ ⑥ 资源够不够（内存、磁盘、GPU 显存）。不要一上来就改代码。
  • 容器 vs 宿主的一个经典混淆：容器里的 127.0.0.1 是容器自己，不是宿主。所以服务之间用服务名互连（http://milvus:19530），而不是本机地址。这个坑的症状是 Connection refused，而你在宿主上明明连得上——面试提到这一条，等于证明你真配过多容器网络。
  • docker stats --no-stream 比「我觉得够用」可靠：多服务容器栈的内存预算是算出来的。Milvus standalone 官方下限 8 GB、推荐 16 GB，加上 ClickHouse、MySQL、MinIO、etcd、Langfuse web/worker，一套教学栈合计可能是 11–20 GB。在 32 GB 的笔记本上不设上限地全开，最先 OOM 的往往是 Milvus——容器 exit code 137 就是 128+9（SIGKILL），看到 137 先查内存，别查代码。

和你自己的项目对上号 ​

  • 科研文献 RAG 的镜像取舍：Dockerfile 与它的注释就是本页的实战版——基础镜像 python:3.12-slim；先 COPY requirements.txt 再 RUN pip install、最后 COPY . .（作者把「代码改动不会让依赖层缓存失效」写进了注释）；模型不打进镜像，改为运行时下载到挂载卷 -v hf_cache:/root/.cache/huggingface，并在注释里写明 bge-m3 + bge-reranker-v2-m3 约 4.4 GB；HEALTHCHECK 查的是 /health 端点而不是进程存活，理由是「假健康检查会让编排系统继续把流量导进一个已经不可用的实例」；torch 是 CPU 轮子，注释里给出要 GPU 时的两种改法（--index-url 与 --gpus all）。把这段注释背下来，就是一段完整的面试答话。
  • 依赖的两份清单：requirements.txt（人读：只列真正 import 的包，每行附用途与实测版本）与 requirements.lock.txt（机器读：完整依赖树）。文件头写明分工与「只锁直接依赖 → 传递依赖漂移仍可能让昨天能跑的今天跑不了」——这正好是本页 L0-03 的核心论点。
  • YYHelp v2 的容器栈：deploy/docker-compose.yml 把 MySQL 8.4、etcd、MinIO、Milvus standalone、Langfuse（postgres + clickhouse + redis）与可选的项目 API 编成一套栈。里面有几处可以直接作为面试素材：
    • 版本必须是「取回来」而不是「凭印象」：Milvus 与 etcd 的版本注明取自 Milvus 官方 compose；MinIO 因为 Docker Hub 撤下社区镜像而改用 Chainguard 镜像，并且用 digest 钉住——文件里还记录了一次自我纠正：注释写着「用 digest 钉」，但 image: 那一行最初没带 digest，实际仍是滚动 tag。这条「注释与实现不一致」的例子，比任何理论都更能说明为什么要写校验脚本。
    • 健康检查要跟着镜像换：Chainguard 镜像里没有 mc、没有 curl，所以探针改用 busybox 发 HTTP 请求；否则会得到「每天报 unhealthy 但服务其实是好的」的假告警——假告警会让人忽略真故障。
    • 内存预算与快速失败：Milvus 设 16 GB 上限并设 mem_swappiness: 0，理由是向量检索一旦换页，延迟会从几十毫秒变成秒级，不如干脆被 OOMKill（失败得更快、更好观测）。exit code 137 的含义写进了注释。
    • 端口冲突要靠改端口解决而不是排查：MySQL 映射到宿主 3307 而不是 3306，因为本机可能已有原生 MySQL；撞端口的症状是 bind: address already in use 而 Docker 会直接启动失败（好过静默连错库）。
  • 你还没做但面试会问的：镜像没有推到任何 registry，也没有 CI 构建镜像的步骤；没有用 systemd 管理任何服务（都是 docker compose 或前台 uvicorn）。被问到「怎么部署到服务器」时，诚实答法是：目前是单机 compose 形态，上服务器要补三件事——镜像推送与版本标签、外部化的 .env 与密钥、以及一条可回滚的发布流程。

面试怎么问（≥3 组） ​

Q1：你的项目别人 clone 下来能跑吗？ A（要点）：三步——① 依赖声明与锁文件都在仓库里，直接依赖钉精确版本，锁文件冻住传递依赖；② .env.example 给出所有必需变量，.env 在 .gitignore 里；③ Dockerfile 与一条 compose/README 命令能把服务起来，模型走运行时下载进挂载卷。加分句：「我专门区分了『人读的 requirements』和『机器读的 lock』——只锁直接依赖时传递依赖仍会漂移，症状就是昨天能跑今天不能跑。」别说：「能跑，我把环境发给他就行。」

Q2：镜像多大？为什么不把模型打进去？ A（要点）：模型约 4.4 GB，打进镜像会让镜像巨大、构建极慢、每次改代码都要重新分发那一层；正确做法是运行时下载到挂载卷并复用缓存。加分句：「我还把依赖安装放在 COPY 源码之前，这样改业务代码时依赖层命中缓存，构建只要几秒。」别说：「打进去方便，反正是离线环境。」

Q3：容器起来了但接口 502，你怎么查？ A（要点）：按固定顺序——进程在不在 → 端口有没有在听 → 容器内 curl 本机 → 健康检查查的是「进程活」还是「依赖可用」→ 日志 → 依赖服务（DB/向量库/模型服务）→ 资源（内存、磁盘、显存）。容器化的经典坑是连接串写成 127.0.0.1：容器里的回环地址是它自己，必须用服务名。加分句：「我会先看 exit code——137 是 SIGKILL，先查内存，别查代码。」别说：「重启一下试试。」

Q4：为什么用 Docker，不用 conda 直接跑？ A（要点）：Docker 交付的是「操作系统 + Python + 依赖 + 启动配置」的完整快照，能消除宿主差异；conda 只解决 Python 包（和部分二进制）层面。加分句：「代价也要说清：容器增加了卷与网络这一层复杂度，数据必须落卷，日志必须设上限，版本必须钉住；教学/单机场景我用 compose，生产要额外考虑镜像仓库与发布回滚。」别说：「Docker 更先进。」
