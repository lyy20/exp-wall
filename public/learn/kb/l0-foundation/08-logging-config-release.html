日志、配置开关与版本发布 ​

覆盖知识点：L0-17 L0-18 L0-19 ｜ 面试频率：中 ｜ 建议学时：6h

一句话说清 ​

这三项共同回答一个面试问题：「线上出问题，你怎么知道、怎么止血、怎么回退。」 L0-17（日志与结构化日志）解决「知道」——让每个请求有一条可被检索、可被串联的记录；L0-18（配置与开关）解决「止血」——不改代码、不重新发版就能关掉出问题的分支；L0-19（版本与发布）解决「回退」——你改了什么、影响谁、怎么退回去。一句话记法：没有日志你只能猜，没有开关你只能停服，没有版本你只能靠记忆。

为什么必须学 ​

AI 应用的失败大多是概率性、非致命的——同一个问题昨天答对了今天答错了，服务不报错，指标不掉，只有用户说「它刚才胡说」。这类问题的唯一抓手是可追溯的记录：这次请求检索到了什么、走了哪条路径、用了哪个 prompt 版本、哪一步拒答了。没有这些，"排查"就退化成"再试一次看看"。

面试里这条线也很明显：候选人在讲项目时如果只会说「实现了 RAG」，追问「线上答错了你怎么查」就会卡住；而能说出「我给每个请求一个 trace_id，从入口贯穿到检索、生成、引用校验，日志和 trace 用同一个 id 缝合，可观测平台的写入失败也不会影响主流程」的人，直接进入「做过线上系统」的档位。

核心内容 ​

L0-17 日志与结构化日志 ​

  • 定义：日志是给你自己看的事件流。三个层次要分清：
    层次形态回答什么问题
    print无结构、无级别、无时间「我调试时看到的」——生产代码里不该有
    文本日志2026-10-01 12:00:00 INFO xxx「大概发生了什么」
    结构化日志一行一条 JSON，字段固定「具体哪个请求、哪一步、耗时多少、结果如何」——可被机器检索与聚合
  • 为什么结构化是必须的：文本日志的字段位置不固定，只能靠正则抠；一旦日志平台（或你自己的 grep）要按 trace_id 聚合、按 step 分组算耗时，文本格式就撑不住了。结构化日志把「字段」变成一等公民：
    json
    {"ts":"2026-10-01T12:00:03.412Z","level":"INFO","event":"retrieve_done",
 "trace_id":"a1b2c3","step":"hybrid_search","recall_n":12,"fused_n":8,
 "rerank_n":5,"latency_ms":183,"refused":false}
    1
    2
    3
  • request_id / trace_id 必须贯穿全链路（本页最核心的一条）：在请求入口生成（或沿用调用方传入的），然后——① 写进所有日志；② 传给下游调用（HTTP 头或函数参数）；③ 回给调用方（响应头）。只有第 ③ 步做了，用户报障时你才能用他给的那一串字符直接筛出这一次请求的全部记录。缺任何一步，trace 就断了。
  • Python 的最小正确用法：
    python
    import logging, json, time

logger = logging.getLogger(__name__)   # 模块级 logger，不要 logger = logging.getLogger()

def log_event(event: str, **fields) -> None:
    """结构化日志：字段进 JSON，不用 f-string 拼字符串。
    拼字符串的坏处是字段位置不固定，检索只能靠正则。"""
    logger.info(json.dumps({"event": event, **fields}, ensure_ascii=False))

start = time.perf_counter()
log_event("ask_start", trace_id=trace_id, question_len=len(q))
...
log_event("ask_done", trace_id=trace_id, latency_ms=int((time.perf_counter()-start)*1000))

  • 该记什么、不该记什么（写错方向会被面试官抓住）：
    • 该记：trace_id、外键 id、步骤名、耗时、数量级（召回 k 条、截断到 n 字）、结果状态（成功/拒答/降级）、版本号（prompt 版本、模型名）。
    • 不该记：密钥与 token（哪怕前缀）、完整对话原文与整段上下文（体积大且是用户数据）、无界长度字段。
    • trace_id 不要只用自增数字或时间戳——多实例下会撞。用随机十六进制串或 UUID。
  • 常见误区：
    • 用 print 代替 logger。没有级别、没有统一格式、无法按模块过滤，而且和库自己的日志混在一起输出顺序混乱。
    • 日志级别乱用：正常业务事件用 ERROR，导致真正的问题淹没在噪声里。
    • 只在 except 里 logger.error("出错了") 而不带异常栈与上下文。用 logger.exception(...) 才会带 traceback。
    • 日志没有轮转或上限。日志会把磁盘写满——容器里要给 json-file 驱动设 max-size / max-file。

L0-18 配置文件与实验开关 ​

  • 定义：配置 = 不改变代码逻辑、但需要随环境或实验变化的值；feature flag = 一个能被远程/配置关掉的代码分支。配置的优先级承继 L0-06：真实环境变量 > 配置文件/.env > 代码默认值，越靠环境侧的越优先，方便临时覆盖。
  • 格式选择：YAML 人类友好、支持嵌套与注释，适合多层配置；JSON 严格、无注释、适合机器交换；TOML 介于两者之间（pyproject.toml 就是它）。规则只有一条：配置文件里不放密钥，密钥走环境变量（见 Git 与密钥管理）。
  • feature flag 的最小形态与它的两个坑：
    python
    # 开关读一次存进配置对象，不要在请求里反复读环境变量
ENABLE_RERANK = os.getenv("YYHELP_ENABLE_RERANK", "1") == "1"
    1
    2
    • 坑一：「临时开关」会变成永久开关。上线前随手加的 if FLAG: 半年后没人敢删——给开关写清楚「什么时候可以删」（代码注释 + 任务清单），否则它会和主逻辑永久分叉。
    • 坑二：实验开关必须被记录。如果一次实验改了开关，而 trace 里没记开关状态，你就无法归因「这次变好是因为开关，还是因为换了个模型」。结论的可追溯性取决于配置的可追溯性。
  • 实验标签（tag）是配置的一种：把「这次跑用了哪套参数、哪个模型、哪个 prompt 版本」合成一个标签写进产物路径与 trace 里。事后复盘时，标签是唯一能还原实验条件的线索。
  • 常见误区：
    • 把配置读进一个全局可变对象，测试时改它、测试完忘记改回，导致测试之间互相污染。
    • 用「配置」表达真正的逻辑分支（例如「如果配置里是这个字符串就走完全不同的流程」）。那是代码，该写进代码。
    • 开关默认值选错方向：新功能默认开启，出问题时不改配置就直接影响全量用户。风险性开关默认关闭。

L0-19 版本与发布（语义化版本） ​

  • 定义：语义化版本（semver）是 MAJOR.MINOR.PATCH 三段：
    • MAJOR：不兼容的改动（删字段、改字段含义、改接口语义）
    • MINOR：向后兼容的新增（加字段、加接口、加可选参数）
    • PATCH：向后兼容的修复（改 bug、改文案、调性能） 判据是对调用方的影响，不是改动大小。改 prompt 也属于影响输出的改动，所以你的 prompt 版本号要跟着升——本项目里 prompt 版本是字符串（v2-...、v2-stream-...），因为它不是发布给外部消费者的 API，而是内部实验的可追溯标识。
  • CHANGELOG 写什么：写「别人能感知到的变化」——新增/修改/删除的能力、行为变化、以及那些没变但需要知道的事（超时、限流阈值、模型版本）。不要贴 commit 列表，那等于没写。
  • 灰度发布：把新版本先给一小部分流量，观察关键指标（错误率、延迟分位、质量指标），再逐步放量。它的前提是指标可用（L0-17）与新旧版本能同时运行（L0-18 的开关或路由）。
  • 回退（rollback）必须事先准备，而且要能在不重新构建的情况下完成：
    • 镜像或产物按版本/digest 保留，不是只有 latest。
    • 数据兼容：新版本写了新字段、旧版本读得懂吗？不可逆的数据迁移是发布事故的常见根因。
    • 依赖侧回退：模型、向量库、外部 API 都有旧版本可切。
  • 常见误区：
    • 版本号随手改，导致「哪个版本修了这个问题」说不清。
    • 发布没有清单：改了配置、迁移了表、重启了服务各做了一半。
    • 只测「新版本对不对」，不测「回退能不能成功」。回退路径没演练过，出事时大概率失败。

和你自己的项目对上号 ​

  • 可观测是 YYHelp v2 的强项，而且形态很特别：两条通道 + 同一 trace_id 缝合。默认路径是自研的 JSONL trace（一行一条 JSON，落到文件，不依赖任何外部服务），增强路径是 Langfuse v4。两条路用同一个 trace_id 关联，所以「有平台时看平台，没平台时看文件」都能还原同一次请求。
  • 最值得在面试里讲的一条细节：trace 写入失败不抛异常，而是降级写一条 observability_degraded 事件。这条设计的推理是——可观测性是辅助设施，它不能成为业务链路的单点故障：可观测平台挂了，答问服务不该跟着挂。同时「降级事件」本身又被记下来了，所以你能知道「这段时间的 trace 是残缺的」，而不是误以为数据完整。这是本页「知道」这一项最成熟的落地样本。
  • trace_id 的三处使用做全了：入口生成 → 日志全带 → 响应头回给调用方。第三处最容易漏，但它恰恰是「用户报障→你在日志里定位」的钥匙。科研文献 RAG 的 service.py 里把这条写成了设计理由：trace_id 从入口就定下来、响应头回给调用方、日志里全带它。
  • 配置与标签也真在用：RAG_OUT_TAG 环境变量给每次实验的产物打标签，prompt 有独立版本号（v2-分级不足-... 与非流式的 v2-stream-... 是两条不同的字符串）——因为 prompt 变了，评测结论就不能跨版本比较。容器栈里所有敏感与开关类取值都走 .env + compose 环境变量，不写进镜像。
  • 踩坑记录也在印证本页：项目里那份 NOTES-踩坑记录.md 的存在本身就是「日志与可追溯」的动机——能被写进踩坑记录的问题，都是当时没有足够观测手段、只能靠摸索定位的问题。
  • 诚实缺口（面试会被问）：目前没有一个正式的发布流程——没有 CHANGELOG、没有镜像推送与版本标签、没有灰度。被问到「怎么发布」时，答法是：现在是「本地 compose + 手动重启」形态，要产品化必须补三件事——镜像按版本/digest 保留、CHANGELOG、以及一条演练过的回退路径；另外「临时开关」目前没有过期机制，属于知道但还没做的技术债。

面试怎么问（≥3 组） ​

Q1：线上用户说「刚才答错了」，你怎么定位？ A（要点）：要 trace_id。它从请求入口生成、写进这条链路的每条日志、并在响应头回给调用方；拿到它就能筛出这次请求的检索结果、走了哪条分支、用了哪个 prompt 版本、有没有触发拒答。加分句：「我的可观测是双通道：自研 JSONL trace 是默认路径，不依赖外部服务；可观测平台是增强路径，两条用同一个 trace_id 缝合——而且平台写入失败只降级记一条事件，不会让答问跟着失败。」别说：「让用户再问一遍，我盯着看。」（不可复现的问题这么处理等于放弃。）

Q2：为什么用结构化日志而不是文本日志？ A（要点）：字段位置固定才能被机器检索与聚合——按 trace_id 聚合、按 step 分组算耗时，文本格式只能靠正则抠。加分句：「我还会控制记什么：记 trace_id、步骤、耗时、数量级、版本号；不记密钥、不记完整对话原文。」别说：「结构化日志更好看。」（不是排版问题，是可查询性问题。）

Q3：你想改一个参数（比如 top_k）需要重新发版吗？ A（要点）：不需要——配置有多层来源，环境变量优先于文件与默认值，改环境变量重启即可；风险性改动配 feature flag，能在不改代码的前提下关掉。加分句：「但我会给开关写清楚『什么时候可以删』，否则它半年后会变成没人敢动的永久分叉；另外实验开关的状态必须写进 trace，不然事后无法归因。」别说：「直接用开关，永远留着，方便。」（这是技术债的生产方式。）

Q4：一个新版本上线后效果变差，你怎么处理？ A（要点）：先看指标确认是「质量回归」还是「延迟/错误率恶化」，然后回退——回退的前提是旧版本镜像与旧配置都还在、且数据迁移是可逆的。回退之后再拿 trace 与评测集定位原因。加分句：「版本号我按 semver 看影响面：加字段是 MINOR、改字段含义是 MAJOR；prompt 改动我也当版本处理，因为评测结论不能跨 prompt 版本比较。」别说：「先关掉所有新功能再慢慢查。」（那等于把灰度变成了停服。）
