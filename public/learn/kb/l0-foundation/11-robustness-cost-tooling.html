健壮性、成本与工具链 ​

覆盖知识点：L0-24 L0-25 L0-29 L0-30 ｜ 面试频率：高 ｜ 建议学时：13h

一句话说清 ​

这四项是一组「项目能不能给人用」的工程能力：L0-24（异常处理与降级）让它在依赖出故障时还能给用户一个结果，L0-25（成本与配额意识）让它不会因为一次跑飞就把额度刷光，L0-29（调试器）让你能在五分钟内定位一个 bug 而不是两小时，L0-30（代码阅读）让你能读懂别人的框架和源码——后者是前者的前提，因为你不可能调试一个你没读懂的调用链。

为什么必须学 ​

第一，AI 应用的依赖链天生脆弱：LLM 厂商会 429 会超时，embedding 服务会挂，向量库会 OOM，网络会抖。没有降级设计的项目，在这些事发生时表现为「整个服务不可用」——而用户其实完全可以接受「这次用备用模型回答，质量略降」。

第二，成本是真实约束。大模型调用按量计费，一次失控的循环或一次全量重放可能顶掉一个月的预算。面试官问「你这个项目一天花多少钱」时，能给出量级与算式的候选人和答「不花钱，用的免费额度」的候选人，是两种完全不同的工程意识。

第三，代码阅读是学习速度的天花板。AI 领域一年一换栈，你不可能靠教程跟进；能直接读源码、issue、PR 的人，卡住的时间以小时计，不能读的人以周计。

核心内容 ​

L0-24 异常处理与降级 ​

  • 定义：健壮性 = 在依赖部分失效时，系统仍能给出一个「明确好于崩溃」的结果。四种手段按投入排序：

    手段作用判据
    超时不让一个慢依赖拖死整条链路每个外部调用都必须有超时时间
    重试（指数退避 + 抖动）遮住偶发抖动只对幂等操作重试；次数有上限
    熔断下游持续失败时快速失败，不再打它连续失败 N 次后进入打开状态，定时半开探测
    fallback换一条路给结果备用模型 / 返回缓存 / 降级为检索片段直出 / 明确拒答

  • 降级的层次要写清楚：降级不是「静默用差方案」，而是「换一个有明确边界的方案」。一个成熟的降级表长这样：

    失效点降级动作用户看到什么记什么
    生成模型超时重试一次 → 切备用模型答案正常，可能质量略降llm_fallback + 原模型/备用模型
    生成模型完全不可用返回检索到的原文片段「以下是相关资料」（无生成）degraded_no_llm
    精排不可用跳过精排，用融合结果相关性可能略降rerank_skipped
    可观测写入失败不影响主流程，只记录降级事件无感知observability_degraded
    依赖全挂明确报错（503）「服务暂不可用，请稍后再试」错误码与原因

    最后一行很重要：有边界的失败比假装成功好。硬凑一个答案比说「暂时不行」更糟——尤其在有拒答机制的系统里。

  • 超时的数量级要和自己链路的预算对齐：一次问答的总预算如果是几十秒，那么单次 LLM 调用的超时不该超过这个预算，重试次数也要在预算内算得过来（两次 30 秒超时 = 60 秒，用户早走了）。这就是「预算」概念：超时、重试、重排候选数、Agent 最大步数，本质都是预算分配。

  • 兜底信息要比异常本身更有用：给用户看的是「服务暂时不可用」，给日志的是「timeout after 30s calling llm provider=X model=Y trace_id=Z」。不要把技术堆栈暴露给用户，也不要把异常信息丢掉不记。

  • 常见误区：

    • except Exception: pass——问题被吞掉，日志里什么都没有。
    • 对写操作盲目重试（下单、建工单）。要么配幂等键，要么不重试。
    • 无限重试。那是在给已经过载的下游加压。
    • 用降级掩盖真故障：降级事件没有指标、没有告警，于是「一直降级运行」变成常态，而没人知道质量已经掉了一档。

L0-25 成本与配额意识 ​

  • 定义：知道钱花在哪里、花多少、怎么让它降下来。LLM 应用的计费模型是「按量」——不像服务器那样按小时包月，而是每个请求都在实时花钱，并且几乎无法事后追回。
  • 成本的第一性拆解：总成本 = Σ(调用次数 × (输入 token × 输入单价 + 输出 token × 输出单价))。这张式子里三个乘数都有可操作空间，按性价比排序：
    1. 调用次数降下来：缓存重复问答、避免无效重试、给 Agent 的循环设最大步数、别在离线重放里跑全量。这是最有效的一刀。
    2. 输入 token降下来：RAG 的输入常是成本大头（拼进去的上下文）；做法是减少拼入的片段数、切块更精准、先精排再截断——这正是混合检索 + 重排的直接经济收益。
    3. 输出 token降下来：限制最大输出长度、提示「简洁作答」、别让模型复述资料。
    4. 换更便宜的模型：分级路由——简单问题走小模型，复杂问题走大模型。代价是要有质量评测兜住。
  • 必须掌握的三个数量级（面试常问）：
    • 输出通常比输入贵（同一模型上常见数倍差距），所以「限制输出长度」往往比「压缩输入」更直接。
    • 上下文长度直接决定单次成本，所以 RAG 的「召回多了」与「花钱多了」经常是同一件事。
    • 一次问答的 token 量级在「千」这个级别（问题 + 若干片段 + 回答），所以「一万次问答」是几千万 token 的量级——用这个换算估算你的项目花多少钱，比记住具体价格有用（价格会变，量级换算不会）。
  • 配额与防跑飞（这一节是重点，因为跑飞是真实事故）：
    • 单请求 token 上限、单日预算上限、并发上限、Agent 最大步数、重试次数上限——这五个数字是必备的刹车。
    • 离线重放/批量评测必须先估成本再跑：样本数 × 单样本预期 token × 单价，跑之前心里有数。
    • 成本归因：按「入口 / 功能 / 用户 / 模型」分组记录 token 用量。没有归因就只能看到一个总数，而总数不能告诉你该优化哪里。
  • 别忘掉隐性成本：本地模型推理吃 CPU/GPU 时间（等于机器成本）、embedding 全量重算要几十分钟、向量库的内存占用是硬成本。「不花钱」的路径往往花的是别的东西。
  • 常见误区：
    • 只在脑子里记「应该不贵」，不做实际核算。
    • 缓存命中率不做统计，于是不知道缓存有没有省到钱。
    • 用「免费额度」做假设，一上量就撞配额。
    • 把「质量」和「成本」当成对立项——实际上减少无效召回同时降低成本又提升质量是常见的双赢。

L0-29 VS Code / Cursor 与调试器 ​

    justMyCode: false 能让你单步进入库的源码——这也正是「调试器」与「代码阅读」的连接点：想搞清楚框架到底怎么处理你的请求，单步进去看比自己读一遍快。
  • 条件断点：只在 trace_id == "abc123" 或循环第 500 次时停下。在循环里打断点是新手最容易耗掉半天的地方——你会在同一个位置上按几百次「继续」。
  • 异步代码的调试有个真陷阱：事件循环是单线程的，你在 await 附近停下时，整个进程的其他协程都停住了。所以调试一个带超时的 LLM 调用时，断点停留时间会直接把超时触发——现象是「一加断点就报超时，去掉断点就正常」。正确做法是：把网络调用换成假实现再调（这会用到 L0-23 的依赖注入）、或者只把断点打在纯逻辑层。
  • 远程与容器内的调试：附加到运行中的进程（debugpy 监听端口 + "request": "attach"），容器里需要把调试端口映射出来。这一步目前你的项目没做，被问到「怎么调试生产环境的问题」时，诚实答法是：靠结构化 trace 与日志还原，本地再复现；远程调试可以作为下一步。
  • 常见误区：
    • 用 print 替代调试器：改一次代码跑一次，一个 bug 耗掉一小时。
    • 在循环里打无条件断点。
    • 调试时忘了自己改过代码（临时加的 print / 注释掉的校验没删回去）。
    • 只在「出错的地方」下断点，不看调用栈——根因通常在上一层。

L0-30 代码阅读能力（读框架源码、issue、PR） ​

  • 定义：在别人的代码库里快速建立可用的心智模型，并把它用在「解决问题」上。核心态度：读代码是有目的的，不是从第一行开始读整篇。
  • 五步法（按顺序）：
    1. 定目标：我想知道什么？例如「@tool 装饰器到底给函数加了什么」「LangGraph 的 reducer 在哪一步被调用」。没有目标就不要打开源码。
    2. 找入口：__init__.py 的导出、README 的示例、main 或路由注册处。先跑通一个最小示例，再读它背后走的路径。
    3. 沿调用链走通一条路：用「转到定义」逐层深入，只跟着一个具体场景走，不横向展开。
    4. 验证理解：加一行日志、改一个参数、写个十行的小脚本调用它，看行为是否与你的理解一致。能被验证的理解才是理解。
    5. 沉淀：把结论写成注释或文档（说清「为什么我的代码要这么写」，而不只是「它是什么」）。
  • issue 与 PR 是最高效的入口，且常被忽略：
    • 遇到报错先搜「错误原文 + 库名」：如果这个坑很常见，issue 里通常已经有人贴了完整复现和原因。
    • 想确认「这个行为是有意的还是 bug」：看 issue 里维护者的回答。
    • 想知道「某个功能从哪个版本开始有」：看 CHANGELOG 与相关 PR 的 merged 时间。
    • 想理解设计意图：读引入该功能的那个 PR 描述——PR 描述里通常写着「为什么不那样做」，这是文档里不会有的信息。
  • 常见误区：
    • 试图先通读整个仓库建立全局地图。大型框架几万行，读三天也读不完，而且读完就忘。
    • 只看函数名猜行为，不进去看实现（这是幻觉与 bug 的共同来源：以为它会排序，其实它不保证顺序）。
    • 一次读三层以上再往回返，回来时忘记自己从哪来。用「查找引用」而不是靠记忆往回走。
    • 找到一个能跑的写法就停止理解。能跑不等于对——它可能依赖了未定义的行为。

和你自己的项目对上号 ​

  • 降级在项目里有真实案例，而且是最成熟的那一类：YYHelp 的可观测双通道里，Langfuse 写入失败不抛异常，而是降级写一条 observability_degraded 事件——理由是可观测是辅助设施，不能变成业务链路的单点故障；同时降级事件本身被记下来，于是你知道「这段时间的 trace 是残缺的」，而不会误以为数据完整。这一条同时回答了 L0-24 和「静默失败最可怕」这两个话题。
  • 成本与配额：科研文献 RAG 有独立的成本报告脚本（cost_report.py）、压测与延迟基准（loadtest.py / bench_latency.py）。这组工具的意义在于把「贵不贵、快不快」变成可测量的数，而不是感觉。面试时的诚实说法是：这些数字都是本地小规模实测，不能直接外推到线上量级。
  • 限流与并发上限被明确写成「必需品而非优化」：service.py 的 docstring 给出推理——LLM 调用花钱、本地模型推理是 CPU 密集，不限制并发会让所有请求一起变慢（每个都 20 秒然后全部超时）。这是 L0-24 与 L0-25 的交汇点：并发控制同时是稳定性和成本控制手段。
  • 代码阅读在项目里是真实生产力：项目里修掉的那个「Milvus 默认 analyzer 导致中文 BM25 静默返回空」的问题，就是读文档 + 读行为 + 验证假设的产物（换成 jieba 分词并补一条「检索结果必须非空」的断言）；graph/state_v2.py 那份「把每个字段的 reducer 与选择理由写在文件里」的清单，本质上是把读出来的理解沉淀成可执行的断言——文件里记录了判据：能推导的清单不要手写第二遍，并且用一条「故意配错 reducer」的测试来证明断言真的能红。
  • 调试方法的现实版本：项目里的自测入口都刻意设计成离线可跑（不需要网络、不需要模型）——例如服务层的自测脚本与状态图 schema 的 --selftest。这条设计与 L0-29 直接相关：能被离线复现的问题，才谈得上在调试器里单步；依赖真实外部服务的 bug，只能靠 trace 还原。
  • 诚实缺口：没有配置远程/容器内调试（只做本地调试 + trace 还原）；成本报告是本地实测，没有按功能/用户维度的线上归因；也没有把降级事件接入告警（目前只是记录）。被问到「你的降级策略怎么验证有效」时，正确答法是：用故障注入的方式验证——把某个依赖的地址改成不存在的端口，看服务是否按预期给出降级结果而不是 500。

面试怎么问（≥3 组） ​

Q1：你的服务依赖的模型服务挂了，会怎样？ A（要点）：有预算的超时 + 一次退避重试 → 切备用模型 → 备用也不可用时降级为「返回检索片段、明确告知无生成」→ 全部失败才返回 503。每一层都记降级事件与 trace_id，所以事后能统计「这个月降级了多少次」。加分句：「我特意避免了『硬凑一个答案』——在没有依据的情况下生成比明确说不可用更糟，这点和我项目里的拒答机制是同一个原则。」别说：「那就报 500 吧。」（其实用户完全可以接受一个降级结果。）

Q2：你这个项目一天要花多少钱？ A（要点）：给出算式而不是数字——每个请求的输入 token（问题 + 拼入的片段）+ 输出 token，乘以模型单价，再乘以日请求量；并且指出最有效的三个降本点：减少无效调用（缓存、限步数）、压缩输入（减少拼入片段数，靠精排而不是靠多召回）、限制输出长度。加分句：「我做混合检索 + 重排的收益不只是质量——减少拼入的片段数直接降成本，这是同一个优化的两面。」别说：「用的免费额度，没花过钱。」（暴露没有成本意识，而且会引出「那上量以后呢」。）

Q3：你的 Agent 会不会死循环烧钱？ A（要点）：会，如果没有刹车。所以我设了四个上限：单请求 token 上限、Agent 最大步数、单次调用超时与重试次数上限、日预算上限；超限时明确失败并记账，而不是静默继续。加分句：「离线批量重放我也会先估成本（样本数 × 单样本预期 token × 单价）再跑。」别说：「ReAct 一般三五步就结束了。」（这是期望，不是约束。）

Q4：怎么读一个陌生框架的源码？ A（要点）：先定目标（我要回答哪个具体问题）→ 找入口（跑通最小示例、看 __init__ 导出）→ 只跟一条调用链走到底 → 用小实验验证理解 → 把结论沉淀成注释或断言。加分句：「遇报错我第一件事是搜『错误原文 + 库名』找 issue；想搞清某个行为是不是 bug，看维护者在 issue 里的回答比读源码快；想知道某功能从哪个版本开始有，看 CHANGELOG 和对应 PR。」别说：「我会把源码从头到脚读一遍。」（面试官会立刻怀疑你没真读过大型框架。）

自检清单 ​

  • [ ] 我能给出一条链路的完整降级表（失效点 → 降级动作 → 用户可见行为 → 记录什么）
  • [ ] 我能说出「哪些操作可以重试、哪些必须先有幂等键」
  • [ ] 我能估出自己项目的单次请求 token 量级与日成本量级
  • [ ] 我能说出四个防跑飞的上限，并解释超限时应该失败而不是继续
  • [ ] 我能用调试器在离线用例上定位一个 bug，并知道异步代码下断点的陷阱
  • [ ] 我能按「定目标 → 找入口 → 跟一条链 → 验证 → 沉淀」读一个陌生库
