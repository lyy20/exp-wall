设计模式与依赖注入 ​

覆盖知识点：L0-16 L0-23 ｜ 面试频率：中 ｜ 建议学时：6h

一句话说清 ​

这两项解决同一个问题：怎么让代码里那些「一定会变的东西」变得可以替换——换 embedding 模型、换向量库、换大模型厂商、换缓存后端、换可观测平台。L0-16 给的是局部手法（策略、工厂、适配器、责任链），L0-23 给的是整体结构（把模型 / 检索 / 存储抽成可替换接口 + 依赖注入）。判据只有一条：改一处实现，要动几个文件？ 答案是「一个文件、不动调用方」就说明分层的接缝在正确的位置；答案是一串 if provider == "..." 散落在五个文件里，就说明接缝没切。

为什么必须学 ​

AI 领域的技术栈变化速度决定了可替换性是刚需：embedding 模型半年换一代，向量库在 Milvus / Qdrant / FAISS 之间选型，大模型厂商在 DeepSeek / 通义 / 智谱之间切换——如果你的代码把某一家 SDK 的调用写死在业务逻辑里，上面任何一件小事都会变成一次重写。

面试里的问法很直接：「如果换一个向量数据库，你要改多少代码？」「你的测试怎么在不联网的情况下跑？」第二个问题的潜台词是：如果你的代码只能连真实服务才能测，那你就没法做回归测试——而这与 L0-04（测试与 mock）、L0-24（降级）是同一条链条上的事。

核心内容 ​

L0-16 设计模式在 LLM 工程中的应用 ​

  • 先记住反对意见：模式是「被重复发现的解法」，不是「写得高级的写法」。 一个只有一种实现、永远不会有第二种的类，套上工厂 + 抽象基类是纯粹的复杂度负债。判断标准是「变化轴」：这里将来会不会变？会怎么变？

  • 四个真正用得上的模式（都能在 LLM 工程里指出具体位置）：

    模式一句话在 LLM 工程里的位置不用它会怎样
    策略（Strategy）同一接口的多种算法，运行时选一个embedding / rerank / LLM provider、切块策略、检索模式满屏 if provider ==，新增一家要改所有调用点
    工厂（Factory）按名字/配置创建具体实现build_embedder(name)、工具注册表创建逻辑散布在业务代码里
    适配器（Adapter）把第三方接口转成自己的接口把不同厂商的 SDK 差异抹平成同一个 chat()业务代码里出现三家 SDK 的字段风格
    责任链（Chain of Responsibility）一串可组合的处理环节中间件：限流 → 鉴权 → 日志 → 脱敏 → 缓存这些逻辑堆进每个处理函数

  • 适配器在 LLM 工程里几乎是一个范式：厂商的 HTTP 接口在「字段名、消息结构、错误码、是否支持结构化输出」上各不相同。有两种做法：① 每家写一个适配器类，统一成 chat(messages, **opts) -> str；② 直接使用「OpenAI 兼容协议」这个事实标准——现在多数厂商都提供兼容端点，于是「换厂商 = 换 base_url + model + key」。本项目选的是第二种，并且这正是「适配器思想」的极致形态：让别人的接口来适配你的代码，比你自己写三个适配器便宜得多。 但要记住它的边界：兼容协议只覆盖 OpenAI 那套子集，厂商私有能力（例如某些推理参数）走兼容端点就用不上。

  • 责任链的判据：「这些环节是不是都围着同一个请求，且能独立开关」。是，就用一条链（或 FastAPI 的中间件/依赖注入）串起来——这样新增一个「脱敏」环节不用改任何已有环节；不是，就别硬套，那会变成「为模式而模式」。

  • 常见误区：

    • 抽象基类建了一堆、实现只有一个。等到真要换实现时，你会发现当初的抽象接口切错了地方（漏了关键方法），照样要重写。
    • 把「模式」用在数据上：比如给一个纯数据结构（如检索结果）套工厂。数据用 dataclass，行为用对象。
    • 用模式掩盖了本该写清楚的 if。三个分支的分支逻辑写成责任链，读代码的人要多跳三层才能看懂——可读性优先于形式。

L0-23 依赖注入与分层架构 ​

  • 定义：依赖注入（DI）= 对象不自己创建依赖，而是从外部接收。它带来的三个收益按重要性排序：

    1. 可替换：上层逻辑不关心下层是谁（本地模型 or API、Milvus or FAISS）。
    2. 可测试：测试时传入假实现——这是「离线测试」的唯一可行路径（不联网、不加载模型、不下索引）。
    3. 依赖可见：看函数签名就知道它用了什么，而不是读完全文找隐藏的全局单例。

  • 分层的最小正确切法（按「变化频率」分层，而不是按「文件类型」分层）：

    关键在中间那层：能力层用「协议 + 实现」表达，编排层只依赖协议。于是三件事同时成立：换实现只改装配处、测试可以注入假实现、真实现返回的结构由协议固定。

  • Python 里怎么做 DI（三种粒度，按需选）：

    ① 构造器注入（最常用，测试时直接传假对象）；② 配置驱动装配（在启动处按配置挑实现，业务代码里没有 if）；③ 框架级 DI（FastAPI 的 Depends，用 app.dependency_overrides 在测试里一键替换）。不要引入容器——你的项目规模不需要它，多一个间接层就少一分可读性。

  • 和「配置」的分工：L0-18 的配置决定选哪个实现（YYHELP_EMBED_PROVIDER=local|api），DI 决定怎么把选好的实现传进去。两者配合起来，「换 embedding 提供方」才真能做到只改一行环境变量。

  • 常见误区：

    • 注入「容器」而不是注入「依赖」：函数收到一个 ctx 大对象，里面什么都有——这等于没有解耦，只是把全局变量换了个名字。
    • 接口切在「实体」上而不是「能力」上：class MilvusClient 作为协议，等于把实现细节钉死在接口名里。协议该叫 Retriever、VectorStore。
    • 抽象层次过多：接口 → 抽象实现 → 具体实现 → 包装器。每加一层都要能说出它挡掉了什么变化。
    • 把 DI 当目的：项目的入口只有一处装配代码，别为了「对称」给每层都造工厂。

和你自己的项目对上号 ​

  • provider 可替换在项目里是「配置 + 装配」而不是「一堆 if」：YYHelp 的容器配置里有 YYHELP_EMBED_PROVIDER 与 YYHELP_RERANK_PROVIDER（默认是一个不依赖模型下载的轻量实现）——换 embedding / 精排提供方 = 改一个环境变量，业务代码一行不动。这是 L0-16 的策略 + 工厂与 L0-23 的配置驱动装配合起来的落地形态。
  • OpenAI 兼容协议就是适配器的「零成本」版本：科研文献 RAG 的 .env.example 给出三套方案——DeepSeek（默认）、通义 DashScope 兼容模式、智谱 GLM，切换只改 BASE_URL + MODEL + KEY 三行。面试时的加分说法：「我没有为每家厂商写适配器，而是选了一个事实标准的协议边界，让厂商来适配我；代价是厂商私有能力用不上，所以遇到必须用私有能力的场景我会在适配层单独开一个方法。」
  • 可观测的两条通道也是同一套思路：自研 JSONL trace（默认路径，零依赖）与 Langfuse（增强路径）——同一个 trace_id 缝合，写入失败降级记事件而不抛异常。这正是「能力层可替换 + 主流程不依赖辅助设施」的组合：可观测平台是一个可替换的能力，不是一个必须存在的前提。
  • 离线自测=可注入的证明：科研文献 RAG 有 service_tests.py，能在不联网、不加载模型的前提下测服务层（用 FastAPI 的 TestClient，依赖 httpx 作为传输层）；YYHelp 侧也有多个 --selftest 入口（例如状态图 schema 的自检）与 test_* 脚本，明确标注「离线，不需要 LLM」。能做到离线测试，说明这些依赖是被注入的、不是被写死的——这是「你的测试怎么跑」这个问题最好的答法。
  • 一个真实的接缝错位（值得当反面素材讲）：graph/supervisor_core.py 里为什么单 Agent 模式不直接复用专家执行器？文件里写得很清楚——单模式的三个自变量（全量工具清单、v1 通用人设、不解析跨域标记）与专家模式不同；如果让单模式也去走专家执行器，A/B 实验的自变量就从「工具菜单从 5 个降到 1–2 个」变成了「有没有经过 supervisor」，真正的变量被抹掉了。这说明「复用」不是无条件的：当复用会污染实验的自变量时，重复实现反而是正确选择——这是依赖注入与分层里最容易被忽略的一条判断。
  • 诚实缺口：目前没有正式的「接口契约测试」来保证两套实现行为一致（例如 MySQL 与 SQLite 双实现只在部分路径上被覆盖）；也没有把 provider 切换纳入 CI 的矩阵测试。被问到「你怎么保证换实现不出错」时，正确答法是承认这条缺口，并说出下一步：给协议写一套共享的行为测试，两套实现都跑同一套用例。

面试怎么问（≥3 组） ​

Q1：如果要把向量库从 A 换成 B，你要改多少代码？ A（要点）：理想是「只改装配处」——业务层依赖的是 VectorStore 协议（upsert / search / delete），实现是独立的类，由配置驱动在启动时装配。加分句：「判断接缝切得对不对，我会数一下『改一处实现要动几个文件』；如果发现调用方要跟着改，说明接口里漏了能力，或者根本切错了地方。」别说：「我全局搜索替换一下就能改。」（说明实现细节已经渗进业务层。）

Q2：你怎么在不联网的情况下测试整个问答链路？ A（要点）：依赖注入 + 假实现——检索返回固定的 Hit 列表，LLM 返回固定的 JSON，服务层用 FastAPI 的 TestClient 打请求，断言状态码、响应结构与引用校验结果。加分句：「我的离线测试能在不下载模型、不联网的前提下跑完服务层，而真实链路的检索质量与答案准确率留在本地手动跑——这样 CI 只测确定性部分，不会因为外部服务抖动变红。」别说：「只能连上真实环境测。」（那就没有回归测试可言。）

Q3：你的项目里用了哪些设计模式？ A（要点）：只讲用得上的——策略（多 provider、多切块策略）、工厂（按配置构建实现、工具注册表）、适配器（OpenAI 兼容协议抹平厂商差异）、责任链（限流/鉴权/日志/脱敏/缓存这类可独立开关的横切环节）。加分句：「我会同时说清代价——抽象只有一种实现时就是纯负债，所以我只在确实有第二、第三个实现（本地/API/假实现）的地方切接口。」别说：一口气报十个模式名。（面试官会逐个追问「这里有几种实现」，答不上来就是背的。）

Q4：为什么单模式不直接复用专家模式的执行逻辑？ A（要点）：因为复用会改变实验的自变量——单模式的特征是全量工具菜单 + 通用人设 + 不解析跨域标记，专家模式是裁剪后的 1–2 个工具 + 专家人设 + 解析跨域标记；若强制复用，被比较的就变成了「有没有经过 supervisor」，而工具菜单这个关键变量被抹掉，A/B 结论就失去意义。加分句：「我在代码里把两者的差异逐条列出来，就是为了让半年后的自己能对上当时的实验结论。」别说：「代码重复是不好的，我尽量复用。」（DRY 不是最高原则，可解释的实验对比在这里更重要。）
