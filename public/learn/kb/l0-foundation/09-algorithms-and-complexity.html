算法与复杂度 ​

覆盖知识点：L0-14 L0-15 ｜ 面试频率：高 ｜ 建议学时：43h

一句话说清 ​

这是整层里学时最长、唯一有独立笔试环节的一项：L0-14 是刷题面（数组/哈希/栈队列/树/堆/图 + 排序/二分/双指针/滑窗），L0-15 是口述面（说清时间空间复杂度、均摊分析）。两者必须一起练——只写出能跑的解法不够，面试官要的是「为什么这个解法在这个数据规模下能过」。工程视角的版本是：复杂度不是学术指标，它是你选型时唯一能提前算出来的东西——FAISS 用精确检索还是近似索引、RRF 融合排序会不会成为瓶颈、滑动窗口的窗口开多大，答案都从量级估算来。

为什么必须学 ​

第一，它是硬门槛。 大厂笔试与一面基本都有编码环节，且是淘汰制：做不出来，后面聊得再好也没有机会。第二，它考的是「转化」而不是「背诵」——题目不会写「请用滑动窗口」，要你自己从「连续子数组」「最长满足条件」这些特征里认出来它属于哪一类。第三，复杂度问答是唯一能当场检验的概念题：问「你的方案时间复杂度是多少」时，答「O(n log n)，因为做了一次排序」和答「应该挺快的」是两个档位。

  • 算法套路：认特征的清单（面试时按特征匹配，而不是按题目记忆）：

    • 二分：有序 + 「找边界/最小值」。写的时候把「区间开闭」定死，最容易错的是边界与死循环。
    • 双指针：有序数组的两数问题、原地删除/去重。
    • 滑动窗口：连续子数组/子串 + 「最长/最短满足某条件」。模板固定，值得背下来：

    • 哈希：把「查找」从 变成 ，是拿空间换时间最常用的一招。
    • 排序：比较排序的下界是 ；计数/桶排序在值域小时能到 。需要计算前先想「排序会不会改变题目的不变量」（要保序就别排）。

  • 图的两个基础与一个陷阱：BFS 求无权最短路，DFS 做连通/拓扑；图的题先问清「有向无向、有没有环、节点数多少」。节点数大时邻接矩阵会爆内存，要用邻接表。

  • 递归与栈的等价性：所有递归都能写成显式栈。面试里被要求「改成非递归」时，这是出路；工程里它对应「深递归会爆栈」这个真实限制。

  • 常见误区：

    • 只写出来不讲复杂度。面试官常常更在意你能不能分析，而不是能不能秒杀。
    • 用哈希表解决「需要有序」的问题，然后被迫再排序一遍。选错结构会让复杂度多一个 。
    • 边界条件不检查：空输入、单元素、全相同元素、越界。这些用例自己先跑一遍。
    • 一题只写一种解法。面试官问「还有更优的吗」时要能接上。

L0-15 复杂度分析 ​

  • 定义：用输入规模的函数描述「增长趋势」，忽略常数与低阶项。 是上界， 是同阶，。
  • 三条工程上真正用得到的判断（比背表重要）：
    1. 量级换算：一个 的循环， 在 Python 里大约是零点几秒量级； 的 是上万亿次操作，直接不可行。面试时用这个换算说明你的方案能不能过。
    2. 空间与 IO 也算：本地模型推理、embedding 计算、向量检索里，内存占用与磁盘 IO 常常是真正的瓶颈，不是 CPU 循环次数。
    3. 常数因子的现实权重：Python 层的循环比 numpy/FAISS 内部的循环慢两三个数量级。所以「同样是 」的两种实现，实测可能差 50 倍——这也解释了为什么要用库而不是手写。
  • 均摊分析（摊还分析）：单个操作偶尔很贵，但均摊到每次操作上成本是低的。两个必会的例子：
    • 动态数组扩容：list.append 偶尔要扩容复制（），但因为容量翻倍增长， 次 append 的总成本是 ，均摊 。
    • 哈希表扩容：负载因子超阈值时整体 rehash，均摊仍是 ——但单次请求可能变慢，这就是尾延迟毛刺的来源之一。 均摊 ≠ 每次 ：讨论 P99 延迟时不能拿均摊值说事。
  • 常见误区：
    • 把常数当无关： 的两次遍历 vs 一次遍历，在大 下就是两倍时间。
    • 用最坏情况吓自己、或只用平均情况骗自己。面试答法：说清「平均/最坏各是什么」。
    • 忽略 Python 层面的开销：for 循环里做字符串拼接可能是 （应改用 list + join）。

和你自己的项目对上号 ​

  • 哈希表在项目里是隐形的常客：引用校验要把模型输出的来源编号（[1]、[3]）映射回上下文里的具体片段，靠的就是「编号 → 片段」的字典；检索结果的去重（同一片段被 dense 和 sparse 两路同时召回）也是一次哈希查重。面试问「你项目里用过什么数据结构」，答数组和字典不算亮点，答「融合阶段用字典做去重、用堆做归并取 top-k」才算。
  • 堆与排序在融合阶段：RRF 融合要把两路排名合成一个分数再取前 N，本质是「归并 + 取 top-k」——不需要全排序，维护一个大小为 k 的堆即可把这一步从 降到 。这个优化在候选集小时无所谓，但它是「知道自己在算什么」的证据。
  • 复杂度决定选型，这是项目里最真实的例子：科研文献 RAG 用的是 FAISS IndexFlatIP（精确检索，逐条算内积）而不是近似索引（如 IVF/HNSW）。理由不是「精确更好」，而是量级：60 多篇论文切出来的片段在数千到数万级，精确扫描在这个规模下延迟完全可接受，而换成近似索引就引入了「召回率损失」这个新的不可控变量——在评测还没做扎实之前，多一个变量是负债。这就是「复杂度分析服务于选型」的最好答法。
  • 复杂度的另一半是延迟分布：项目里有压测与延迟基准脚本（loadtest.py / bench_latency.py），验收看的是延迟分位数而不是平均值——因为检索与生成链路里既有哈希扩容、模型冷启动这类「偶发很贵」的环节，也有外部 API 的抖动。平均值会把 P95 的灾难抹掉，这正好是 L0-15 里「均摊不等于每次都便宜」的工程版本。
  • 一个必须诚实说的边界：项目里没有做过大规模数据集上的复杂度对比实验（没有 10 万 / 100 万片段的规模测试），所以「精确检索在这个规模下够用」这句话的可信范围就是当前数据规模。被问到「数据涨十倍怎么办」时，正确答法是给出会变的部分（内存、单次检索耗时线性增长）和下一步动作（先测，再决定是否换近似索引 + 用召回率指标兜住损失），而不是拍一个结论。

面试怎么问（≥3 组） ​

Q1：给你一个「最长无重复字符子串」，你怎么想？ A（要点）：特征匹配——连续子串 + 最长，指向滑动窗口。用左闭右开窗口 + 哈希记录字符最后出现位置，右指针扩张、遇到重复就跳到重复位置之后， 时间 空间。加分句：「我先说清窗口的定义和收缩条件，再写代码——滑窗的 bug 基本都出在边界定义含糊上。」别说：「我先写个双重循环，能过就行。」（可以提暴力解法作为起点，但必须紧接着说出优化方向。）

Q2：你说这个方案是 ，为什么？ A（要点）：指出哪一步产生 （排序、堆操作、二分），哪一步是主项，以及空间用量。加分句：「我会顺带说清常数在工程里的权重——同样是 ，用 numpy 向量化算和用 Python 循环算可能差两个数量级，所以真实延迟要靠实测而不是靠量级下结论。」别说：「大概是 n 乘 log n 吧，反正够快。」

Q3：为什么用 Python 列表的 append 不担心性能？ A（要点）：动态数组容量翻倍增长，扩容虽然单次 ，但 次 append 的总成本是 ，均摊 ；哈希表 rehash 同理。加分句：「但均摊不等于每次都便宜——单次扩容会造成延迟毛刺，所以讨论 P99 时不能拿均摊值当保证。」别说：「列表就是快。」（没有解释，等于没答。）

Q4：你的向量检索为什么不用近似索引？ A（要点）：先算规模——当前片段数是千到万级，精确检索的单次耗时线性增长且这个规模下可接受；再算代价——换近似索引会引入召回率损失这个新变量，而评测还没稳定到能监控它。加分句：「如果数据涨到十倍以上，我会先做规模测试，再用 recall@k 兜住近似索引带来的损失，而不是直接换。」别说：「精确的肯定比近似的好。」（近似索引存在的理由就是规模，忽略规模等于没做选型。）
