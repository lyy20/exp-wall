HTTP 语义与 FastAPI 服务骨架 ​

覆盖知识点：L0-09 L0-10 ｜ 面试频率：高 ｜ 建议学时：9h

一句话说清 ​

你的模型要变成「服务」，中间隔着的就是这两件事：L0-09 决定接口的语义是否正确（方法、状态码、幂等、超时重试），L0-10 决定服务骨架是否规范（Pydantic 模型 + 路由 + 依赖注入）。两者是同一件事的两个层次：语义错了服务就是错的；骨架不规范，业务逻辑就会和框架粘死，换一个框架就得重写。至于「用户能不能在 1 秒内看到第一个字」——那是流式传输要解决的问题，它在 asyncio、并发控制与超时重试（L0-11）里讲；但流式端点怎么设计（独立路由、超时预算、可取消性）仍然是本页的话题。

为什么必须学 ​

AI 应用岗的日常交付物就是一个 HTTP 服务。面试问「你的服务怎么设计」时，能区分候选人水平的不是「用了 FastAPI」，而是这几句：/ask 是 POST 不是 GET（有请求体、可能产生副作用、不该被缓存）；/health 查的是依赖而不是进程；写操作要幂等（重试不重复下单）；流式和非流式是两条路，不是同一个函数的两种返回。这些不是框架知识，是语义知识——换任何语言、任何框架都成立，所以面试官爱问。

核心内容 ​

L0-09 HTTP 与 REST 语义 ​

  • 定义：HTTP 是「请求-响应」的应用层协议——一个方法、一个路径、一些头、一个可选的体。REST 是建立在它之上的一组约束，其中最实用的一条是：用资源 + 方法表达意图，而不是用动词堆路径。

  • 方法与语义（这张表要能背下来）：

    方法语义幂等安全（不改状态）典型用途
    GET读取是是查订单、读健康状态
    POST创建 / 触发否否提问、建工单
    PUT整体替换是否覆盖一份配置
    PATCH局部修改否（约定上可做成幂等）否改单据状态
    DELETE删除是否删会话

    幂等的意思是「执行一次和执行 N 次，服务端最终状态相同」，不是「返回一样的结果」。GET 天然幂等所以浏览器会缓存、代理会重试；POST 不幂等所以超时后客户端不敢随便重试——这直接引出下面两条。

  • 状态码分五类，最常用的是这几个：200 成功、201 已创建、400 请求格式错、401 未认证、403 已认证但无权限、404 资源不存在、409 冲突（例如幂等键重复）、422 参数校验失败（FastAPI 的默认行为）、429 被限流、500 服务端出错、503 依赖不可用。别用 200 包一个 {"code": 500}——那等于告诉所有中间设施（网关、监控、重试库）「这次是成功的」。

  • 超时与重试的三条铁律：

    1. 必须设超时。任何对外的 HTTP 调用（LLM、embedding 服务、向量库）都要有超时，否则一个卡住的依赖会拖着你的线程/协程一起卡死。
    2. 只重试幂等的操作，或者给写操作配幂等键（客户端生成一个 request_id，服务端遇到重复键直接返回上次结果）。
    3. 重试要退避，指数退避 + 随机抖动，并设次数上限。立刻重试等于对已过载的下游再打一拳。

  • 常见误区：

    • 用 GET 传敏感参数。URL 会进日志、进浏览器历史、进 Referer。
    • 状态码一律 200，错误信息塞在 body 里。限流中间件、重试库、监控全都会失效。
    • 不设超时，靠「它一般很快」。
    • 把长任务同步做完再返回。正确做法是先返回任务 id（202），再提供查询接口——你的 LLM 调用动辄十几秒，属于典型长任务。

L0-10 FastAPI 服务骨架 ​

  • 定义：FastAPI = 路由声明 + Pydantic 请求/响应模型 + 依赖注入 + 自动 OpenAPI 文档，跑在 ASGI 服务器（uvicorn）上。它的价值集中在一点：把「输入校验」和「业务逻辑」分开，并让校验错误自动变成 422 而不是 500。
  • 骨架的最小正确形态（含真实项目里的关键注释）：

    answer: str
    citations: list[str]
    trace_id: str

@app.post("/ask", response_model=AskResponse)
async def ask(req: AskRequest) -> AskResponse:

    #    连 /health 都响应不了。一律丢进线程池。

  • async def 与 def 的选择（必考）：FastAPI 对同步路由会自动放进线程池，对 async def 路由则直接在事件循环里跑。所以：路由是 async def 时，里面绝不能出现同步阻塞调用（requests、本地模型推理、同步 DB 驱动）；要用就把它们 await asyncio.to_thread(...) 丢出去。反过来，纯同步实现写成 def 反而更安全。这条规则是「本地模型 + Web 服务」组合最常见的性能杀手。
  • 依赖注入的作用不是「为了解耦」这么虚，而是三个具体收益：① 把「取数据库连接 / 校验 API Key / 记录 request_id」这类横切逻辑从业务函数签名里移出去；② 测试时用 app.dependency_overrides 一键替换成假实现，不用打桩网络；③ 让「这个路由依赖什么」在签名上可见。
  • 启动与关闭钩子：模型加载、索引加载这类「贵且只做一次」的事放 lifespan（旧写法是 @app.on_event("startup")），不要放在路由里——每个请求加载一次模型，服务在两三个并发下就崩了。
  • 健康检查必须分两个：/health（liveness：进程活着）与 /health?probe=readiness（readiness：依赖真的可用）。readiness 要真去读索引产物、真查依赖——「进程活着但索引文件缺失/Key 没配」对调用方就是不可用。
  • 常见误区：
    • 在路由里 try/except 把一切异常吞掉返回 200。监控上看到 100% 成功率，用户那边全是「系统繁忙」。
    • 限流和并发上限当成「优化」往后放。LLM 调用花钱、本地模型推理吃 CPU，不限制并发的结果是所有请求一起变慢：每个都 20 秒，然后全部超时。
    • 把 trace_id 只在内部生成不出现在响应里。调用方报障时你无法把它的请求和你的日志对上。

流式为什么属于这一页 ​

SSE 的完整讲法在 asyncio、并发控制与超时重试（L0-11）：它讲清了「逐 token 推流」背后的 async for、分帧规则、以及流式与 JSON mode 的原理冲突。从服务设计角度只需要记住一条：流式端点是长连接，它的超时预算、连接数上限、可取消性都和普通请求不同——所以它通常独立成一个路由（/ask/stream），而不是给 /ask 加一个布尔参数。反问一句就能自检：你这个端点被中断时，已经在跑的模型调用会被取消吗？ 如果答不上来，说明你还没把长连接当成一类独立资源来设计。

和你自己的项目对上号 ​

  • /health 的判据是实做出来的，不是抄的：科研文献 RAG 的 service.py 里，/health 会真去读索引产物与配置——理由写在 docstring 里：「进程活着但索引文件缺失、或没配 Key，对调用方就是不可用」。这正好是 L0-10 里「liveness 与 readiness 判据不同」的落地版。
  • 限流与并发上限是必需品，不是优化项：同一份 docstring 给出了推理——LLM 调用花钱，本地模型推理是 CPU 密集，不限制并发会让所有请求一起变慢（每个都 20 秒，然后全部超时）。这段话直接对应 L0-09 里的 429 与 L0-10 的横切关注点。
  • 「同步调用绝不能跑在事件循环里」是踩出来的：service.py 明确写着同步的检索与 LLM 调用一律丢进线程池，理由是会阻塞整个进程，连 /health 都响应不了。这是 L0-10 那个必考点的真实版本——不是理论推演，是「健康检查也跟着挂」这个具体症状逼出来的。
  • 流式与非流式是两条 prompt：streaming.py 的模块 docstring 完整记录了本页第三条的推理链——为什么不能复用 generate.answer_question（它用 response_format={"type":"json_object"}，必须等整个 JSON 生成完），以及两条路各自的代价；STREAM_PROMPT_VERSION 与非流式的 PROMPT_VERSION 是两个不同的字符串，就是为了让评测能分开归因。
  • SSE 的 _sse 与 trace_id：_sse(event, data) 返回 f"event: {event}\ndata: {json.dumps(data, ensure_ascii=False)}\n\n"，注释写明「data 里不能出现裸换行（会破坏 SSE 分帧）」；trace_id 在入口就定下来，同时回给调用方（响应头）和日志——这就是 L0-17 里 request_id 贯穿链路的具体实现。
  • YYHelp v2 的挂载点不同：它是多轮对话 Agent，所以有会话状态持久化与中断恢复的需求（缺关键信息不猜、停下来问，重启后能续跑）；它的服务入口在 serve/ 下，而容器编排把 API 端口与健康探针分开配置（/health?probe=readiness 查真依赖）。多轮场景下 /ask 的语义要复杂一层：同一个 session_id 的连续请求可能改变服务端状态，所以更不能当幂等接口处理。

面试怎么问（≥3 组） ​

Q1：你的 /ask 为什么是 POST 而不是 GET？ A（要点）：有请求体（问题可能很长）、可能产生副作用（记录 trace、写数据飞轮的问题池）、且不该被缓存或预取——这三条都指向 POST。同时我给它配了幂等键与限流，因为 POST 不幂等，超时后客户端重试会重复计费。加分句：「我把『是否幂等』当成接口契约的一部分写进文档，因为写操作要不要重试完全取决于它。」别说：「习惯用 POST。」

Q2：怎么保证用户不会等太久？ A（要点）：先分清两个指标——首字延迟和总时长。首字延迟靠流式解决（SSE 逐 token 推，机制细节见 /kb/l0-foundation/02-async-concurrency）；总时长只能靠模型和输出长度解决，流式一点没改善它。从服务设计角度我还要回答三件事：流式是长连接，所以它独立成一个路由 /ask/stream 而不是给 /ask 加布尔参数；这个路由的连接数要单独限额，否则几个慢客户端就把并发槽占满；并且超时预算也完全不同——普通请求 30 秒应该报错，流式请求可能合理地跑几分钟。加分句：「我在 docstring 里明确写了『假流式（拿完整答案再切块）不改善首字延迟』——所以我没走那条路。」别说：「我加了 loading 动画。」（改善的是感知，不是延迟，而且会被继续追问。）

Q3：FastAPI 里哪些代码不能放在 async def 路由里？ A（要点）：所有同步阻塞调用——requests、同步 DB 驱动、本地模型推理、time.sleep。它们会占住事件循环，导致所有请求（包括 /health）一起卡住。正确做法是 await asyncio.to_thread(...) 丢进线程池，或者对纯同步实现直接用 def 路由让 FastAPI 自己放进线程池。加分句：「我的服务里检索和 LLM 调用一律走线程池，就是因为踩过『连健康检查都超时』这个症状。」别说：「async 更快，所以都写 async。」

Q4：服务健康检查你查什么？ A（要点）：两个层次——liveness 只查进程（挂了就重启），readiness 真查依赖（索引产物在不在、配置齐不齐、下游通不通），不健康就把流量摘掉而不是重启。加分句：「假健康检查比没有健康检查更糟：它会让编排系统持续把流量导进一个已经不可用的实例。」别说：「返回一个 200 就行。」（被追问「那索引文件被删了呢」就崩了。）
