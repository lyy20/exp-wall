演示层：三个前端最小可用 ​

覆盖知识点：L0-20 L0-21 L0-22 ｜ 面试频率：中 ｜ 建议学时：13h

一句话说清 ​

你的模型再好，面试官第一次接触它的时候，是通过一个界面。这一页讲三件事：用 Streamlit 在半小时内把一条链路变成可点的工具（L0-20）、用 Gradio 把接口变成可分享的 demo 页（L0-21）、以及用 React 说清「浏览器怎么消费流式响应」（L0-22）。判据只有一条：演示层只负责「把用户的操作翻译成一次 API 调用，把结果稳定地画出来」——任何业务判断、检索参数、prompt 拼装都不该长在这一层。它既是工程边界，也是面试官盘你项目结构时最常下手的接缝。

为什么必须学 ​

  • 它是「能不能被体验」的分水岭。 两个候选人写同样的 RAG：一个只有命令行，面试官只能听你描述；一个有一条链接，面试官随手点两下就看到了引用和拒答。同一份工作，可信度完全不同。这是投入产出比最高的一层——Streamlit 版通常一个下午就能跑起来。
  • 前端三件套全部考「契约」，不考样式。 面试官不会问你 CSS，但会问：/ask/stream 的每帧长什么样、前端怎么切帧、上传文件走哪个字段、多轮会话的 session_id 谁生成。这些问题的答案都在服务端那一侧定好了，前端只是它的消费者——答不上来说明接口设计没想清楚。
  • 它是最容易暴露「胶水层」思维的地方。 把检索逻辑写进 UI 回调里，等于把业务逻辑焊死在界面上：换前端要重写、写测试得启动界面、连并发问题都复现不了。演示层薄不薄，是判断一个人有没有分层意识的又快又准的探针（这条接缝的完整讲法在 设计模式与依赖注入 的 L0-23）。
  • session_state 与「流式渲染」这两个概念，是 LLM 应用独有的坑。 普通 CRUD 页面没有「生成到一半的文本」这个状态；能把这几个状态（流式中 / 完成 / 失败 / 已取消）说清楚的人，明显是真做过。

核心内容 ​

L0-20 Streamlit：半小时把链路变成工具 ​

  • 它的模型是「脚本重跑」，不是传统前端的事件回调。每次交互（点按钮、输入文字）都会从头到尾重新执行整个脚本。这一条推导出它的全部特性与全部坑：普通 Python 变量在下一次重跑时就没了，所以状态必须放进 st.session_state。
  • 两个状态容器要分清：
    • 控件的值：st.text_input、st.file_uploader 这些控件的当前值，由 Streamlit 按控件的 key 保存。你不给 key，它按代码位置生成一个——代码一改位置，值就串了，这是最经典的幻觉 bug。
    • 你自己的状态：聊天历史、session_id、上一次的引用来源，必须显式放进 st.session_state。
python
import uuid
import streamlit as st

if "messages" not in st.session_state:
    st.session_state.messages = []          # 只初始化一次
if "session_id" not in st.session_state:
    st.session_state.session_id = str(uuid.uuid4())   # 多轮会话的标识

for m in st.session_state.messages:
    st.chat_message(m["role"]).write(m["content"])

if prompt := st.chat_input("问点什么"):
    st.session_state.messages.append({"role": "user", "content": prompt})
    st.chat_message("user").write(prompt)
    with st.chat_message("assistant"):
        # 流式：把后端逐块吐出的文本交给 st.write_stream
        answer = st.write_stream(call_ask_stream(prompt, st.session_state.session_id))
    st.session_state.messages.append({"role": "assistant", "content": answer})

关键的一行是 st.write_stream(...)：它把「流式生成器」当成一等输入。后端是 SSE 也没关系——你只要在客户端把帧拆开、yield 出纯文本即可。

  • 缓存是 Streamlit 的性能命门，也是它唯一强制的性能纪律：
装饰器缓存什么典型用途失效条件
@st.cache_resource全局单例对象模型、向量索引、数据库连接池进程重启、参数变化
@st.cache_data可序列化的返回值一次检索的结果、一份统计表参数变化、手动 clear()

这条区分很值得在面试里讲：模型和连接池必须是 cache_resource（每次重跑都重新加载 4.4 GB 的模型，页面等于不可用）；而检索结果适合 cache_data（同样的 query 直接命中缓存，省一次调用）。

  • 常见误区：
    • 把检索、拼 prompt、调模型全写在 st.button 的回调里。判据很简单：把这些代码抽进 service.py 之后，你的页面还能不能用一行 call_ask(...) 顶替？ 不能，就说明业务逻辑长在了 UI 上。
    • 在重跑模型里以为变量会保留。只有 session_state 会保留，其余每次都是新的。
    • 忘了 key。给每个有状态的控件显式 key（如 key="uploader"），别依赖自动生成的 key。

L0-21 Gradio：把接口变成可分享的页面 ​

  • 它的模型是「函数 + 输入输出组件」：你声明 fn 与 inputs / outputs，框架负责搭页面、排队、处理并发。它不重跑脚本，所以状态靠 gr.State 与闭包传递。
python
import gradio as gr

def respond(message: str, history: list):
    history = history + [{"role": "user", "content": message}]
    # 生成器 = 流式：yield 出去的每个中间值都会被前端渲染
    partial = ""
    for piece in ask_stream(message):
        partial += piece
        yield "", history + [{"role": "assistant", "content": partial}]

gr.ChatInterface(fn=respond).launch()

注意 respond 是生成器：在 Gradio 里，yield 中间结果就等于流式渲染，不需要你手写 SSE 解析。

  • 什么时候选它、什么时候选 Streamlit（面试很爱问这个，要有判据而不是偏好）：
维度StreamlitGradio
数据探索与多图表仪表盘更合适（布局自由、st.dataframe 强）偏弱
单函数模型演示、快速分享链接偏弱更合适（share=True 一条链接）

判据一句话：要「像产品一样组织信息」用 Streamlit；要「让人快速试用一个函数」用 Gradio。

  • 常见误区：把大模型或索引当成函数内局部变量加载（每次请求重新加载一次，比慢更糟的是内存直接爆）；把 share=True 生成的公网链接当成可以随便发的地址（它默认没有鉴权，会连你的 Key 一起暴露给任何拿到链接的人）。

L0-22 React 基础：浏览器怎么消费流式响应 ​

  • 只需要四个概念就能读懂并改一个 LLM 前端：组件（返回 UI 的函数）、props（父传子的只读数据）、state（useState，变了就重渲染）、副作用（useEffect，同步外部世界）。判断一个值该不该是 state 的判据：它变了之后界面需要跟着变吗？不需要就别放 state。
  • 消费 SSE 有两条路，选哪条由「用 GET 还是 POST」决定，这是本页最实用的一条：
EventSourcefetch + ReadableStream
请求方法只能 GET（无法带请求体）任意方法，可带 JSON body 与自定义头
头部不能自定义 Authorization完全可控
自动重连有（内建）要自己实现
适合查询式、参数在 URL 里的推送问答类请求（问题在 body 里）

LLM 问答的问题在请求体里，所以大多数项目走的是 fetch + 手动切帧：

tsx
async function askStream(q: string, onDelta: (s: string) => void) {
  const res = await fetch("/api/ask/stream", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ question: q }),
  });
  const reader = res.body!.getReader();
  const decoder = new TextDecoder();
  let buf = "";
  for (;;) {
    const { value, done } = await reader.read();
    if (done) break;
    buf += decoder.decode(value, { stream: true });   // 中文被切断时靠 stream:true 兜住
    const frames = buf.split("\n\n");                  // 按空行切帧
    buf = frames.pop() ?? "";                          // 最后一段可能是不完整帧，留到下次
    for (const frame of frames) {
      for (const line of frame.split("\n")) {
        if (line.startsWith("data:")) {
          const payload = JSON.parse(line.slice(5).trim());
          if (payload.text) onDelta(payload.text);
        }
      }
    }
  }
}

三个细节都有理由：必须按空行切帧（服务端的事件以空行结束）；最后一段要留着（网络分片可能把一个帧切成两半，这是流式解析最经典的 bug）；TextDecoder 要带 stream: true（否则一个中文字符被切成 3 个字节跨两次分片时，就会解出乱码）。

  • 在 React 组件里渲染流式文本：
tsx
function Chat() {
  const [text, setText] = useState("");
  const [busy, setBusy] = useState(false);
  const send = async (q: string) => {
    setBusy(true);
    setText("");
    try {
      await askStream(q, (d) => setText((prev) => prev + d));  // 函数式更新，避免闭包拿到旧值
    } finally {
      setBusy(false);            // 中断/报错也要复位，否则按钮永远禁用
    }
  };
  return <button onClick={() => send("你好")} disabled={busy}>{text || "发送"}</button>;
}

  • useEffect 的两个硬约束（这是应届生写 React 最常见的两处失分）：
    • 清理函数必须写。开了 EventSource、setInterval、订阅，就要在 return () => ... 里关掉；否则组件卸载后回调仍在跑，轻则重复渲染，重则内存泄漏。
    • 依赖数组要真。useEffect(fn, []) 只在挂载时跑一次，闭包会永远捕获第一次渲染时的变量。想在闭包里读最新值，要么用函数式更新，要么把它写进依赖数组。
  • 常见误区：把「一个字一个字追加」做成 state 的 N 次更新还担心性能——React 会批量处理，真正的问题不是性能而是中断：用户点「停止」时你必须能 abort 掉那个 fetch，否则服务端还在生成（这一点直接连着 asyncio、并发控制与超时重试 里那条「客户端断开后服务端继续生成就是白花钱」）。

和你自己的项目对上号 ​

  • 科研文献 RAG 的演示层用的是 Streamlit：requirements.txt 里明确列了 streamlit，服务侧同时提供 /ask（一次返回）与 /ask/stream（流式）两条路，.streamlit/config.toml 负责界面配置。这正好是本页讲的「一条链路两个出口」：非流式用于自测与脚本调用，流式用于人看。面试时可以这样讲：我先把服务端契约定死（每帧长什么样、结束帧带什么），再让前端去消费——而不是先写界面再倒推接口。
  • st.write_stream 与后端的 _sse 是一对：后端把每个 token 包成 event: delta + data: {...} 的帧，前端只需要拆帧取 text 字段然后 yield 出去。这解释了为什么要在这个项目里把帧格式写进 docstring——它是一份跨进程的接口文档（分帧规则与「data 里不能有裸换行」的原因见 asyncio、并发控制与超时重试）。
  • @st.cache_resource 这个知识点在你项目里是刚需：检索侧要加载 bge-m3 与 bge-reranker-v2-m3（合计约 4.4 GB），如果不用 cache_resource 缓存，每次交互都重新加载模型，页面等于不可用。这也解释了为什么 Dockerfile 里选择把模型放在挂载卷而不是打进镜像——同一件事在两个层面：模型是「进程级资源」，不是「每次请求的输入」。
  • YYHelp v2 的演示层要额外处理会话：它是多轮对话 Agent，界面必须持有并传递 session_id，而且刷新页面后应当能续上同一段会话（服务端有会话状态持久化与中断恢复）。对应到前端的职责就是两条：session_id 只生成一次并存进 session_state；中断恢复的状态由服务端说了算，前端不要自己猜进行到哪一步——前端一旦试图推断「Agent 现在问到第几个槽位」，就会和服务端的中断恢复逻辑打架。
  • 两个项目共同的边界经验：演示层里唯一允许存在的逻辑是「拆帧 + 渲染 + 维护流式中的显示状态」。检索参数、拒答阈值、prompt 版本一律不进前端——否则改一个参数要重发前端，评测配置与部署配置被绑在了一起。

面试怎么问（≥3 组） ​

Q1：你的 demo 用什么做的？为什么选它？ A（要点）：给出判据而不是偏好。Streamlit 适合「像产品一样组织信息」：数据表、多图、多轮对话的会话历史，用 session_state 管理；Gradio 适合「让人快速试用一个函数」，ChatInterface 加生成器就能流式，还能给一条可分享链接；React 只在需要自己做交互细节（停止生成、多标签、嵌入已有网站）时才值得上。加分句：「我用 Streamlit，因为我的核心是对话加引用展示，而它的 write_stream 直接把生成器接到界面上；如果只是展示一个摘要函数，我会用 Gradio，一条 launch() 就能发链接给人试。」别说：「哪个好看用哪个。」（没有判据。）

Q2：Streamlit 里界面的状态为什么老是丢？ A（要点）：因为它的执行模型是脚本重跑——每次交互从第一行重跑整个脚本，普通变量全部重建。要跨重跑保留的东西必须放进 st.session_state；控件的值由 Streamlit 按 key 保存，不给显式 key 就会按代码位置生成，代码一改动值就串。此外大对象（模型、索引）要用 @st.cache_resource 做成进程级单例，否则每次重跑都重新加载。加分句：「我把『界面状态』和『业务状态』分开：界面状态放 session_state，业务状态（会话、进行到哪一步）放在服务端——因为界面刷新不该影响业务。」别说：「加个缓存装饰器就好了。」（把两件事混成一件。）

Q3：浏览器怎么消费你的流式接口？踩过什么坑？ A（要点）：先讲选路——EventSource 方便但只能 GET、不能自定义头，而我的问题在请求体里，所以用 fetch + ReadableStream 手动拆帧。再讲三个必踩的坑：按空行而不是按单换行切帧；保留最后一段不完整帧（网络会把一个帧切成两半）；TextDecoder 带 stream: true（否则多字节的中文字符跨分片时会解出乱码）。加分句：「我还处理了中断：用户点停止时 abort 掉 fetch——不然服务端会把整段生成完，那部分 token 是白花的钱。」别说：「用 axios 一次性拿完整响应再显示。」（那是假流式。）

Q4：为什么你的前端里没有检索逻辑？ A（要点）：因为演示层只做「翻译与渲染」：把用户操作翻译成一次 API 调用，把返回的结果画出来。业务逻辑放在前端会带来三个具体代价——换前端要重写、写测试必须启动界面、并发与状态问题无法在服务层复现。判据是可以自检的：把 UI 换成命令行脚本，业务逻辑能不能一行不改地复用？ 能，说明分层是对的。加分句：「我的项目里界面只依赖一个函数 ask(question, session_id)；这个函数在页面上、在评测脚本里、在压测脚本里是同一个。」别说：「前端里也存了一份阈值配置。」（配置分叉是评测与线上不一致的经典原因。）
