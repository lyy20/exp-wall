Git 协作、多版本与密钥管理 ​

覆盖知识点：L0-05 L0-06 ｜ 面试频率：高 ｜ 建议学时：4h

一句话说清 ​

Git 在两个地方会被面试官看到：你的 commit 历史（他点开你的仓库，看的是「你怎么走的」，不是「你最后站在哪」），和你的第一条历史里有没有 API Key（这一条是淘汰项，不是扣分项）。L0-05 的目标是让历史读起来像一份过程记录：一次提交只做一件事、message 说清「为什么」、分支和 PR 体现协作方式。L0-06 的目标是让密钥在物理上不可能进仓库——.env 在 .gitignore 里、仓库里只有 .env.example、运行时环境变量优先于文件。

为什么必须学 ​

第一，密钥泄漏是硬门槛。 仓库一旦公开，扫描机器人会在几分钟内爬到 sk- 开头的字符串，然后你的额度被刷光。更糟的是「删了文件就好了」这个误解——Git 保存的是历史，不是当前状态。你 git rm .env 再提交，前一个 commit 里那份 Key 仍然完整可读。面试官问「Key 泄漏了怎么办」，第一句答「先轮换密钥」的人，和第一句答「先删 commit」的人，不在同一个水平线上。

第二，commit 历史是免费的「过程证据」。 面试聊到技术选型时，你说「我先用了方案 A，跑出问题后换成方案 B」——如果历史里有对应的提交和提交信息，这句话是可信的；如果没有，它只是一句话。

第三，多版本并存是 AI 应用工程的常态。 Prompt 版本、索引版本、模型版本、实验标签，这些都要能被同时运行、被对比。你不可能只留一份「最新最好的」，因为「最好」是要靠对比证明的。

核心内容 ​

L0-05 Git 与协作流 ​

  • 定义：Git 是内容寻址的版本库——每个 commit 是整棵树的快照，配上父指针构成 DAG。快照语义决定了两件事：切分支很便宜；历史是追加的、几乎不可抹去。
  • commit 粒度：一个 commit 只做一件可以独立描述的事。「加个功能顺便修三个 bug 再格式化整个文件」会被追问「那你到底改了什么」。反过来说，把一次改动拆成 20 个「wip」提交也是噪声。
  • message 写「为什么」而不是「改了什么」：git diff 已经告诉你改了什么，历史需要的是当时的判断。

  • rebase 和 merge 的区别与选择：merge 保留真实的分叉历史（多一个 merge commit），rebase 把你的提交重新接到目标分支顶端（历史是线性的）。已经推送到共享分支的提交不要 rebase——它会重写提交哈希，别人的本地历史会分叉。个人分支上想整理历史时 rebase 是合适的。
  • .gitignore 必须在第一次提交之前就位。事后补救的成本与「这个仓库是否被克隆过」成正比。

  • 密钥泄漏处理（顺序不能错）：
    1. 立刻轮换密钥——去控制台废弃旧的、生成新的。这一步必须在清理仓库之前，因为清理期间旧 Key 依然有效。
    2. 用 git filter-repo（或 BFG）重写历史，把该文件从所有提交里抹掉。
    3. 强制推送，并通知所有协作者重新克隆（他们的本地仍留着旧历史）。
    4. 复盘：为什么会进来、哪一道防线失效。
  • 常见误区：
    • 把 .env 提交进去，注释写「反正是测试 Key」。测试 Key 也能刷出真金白银。
    • 把密钥写进 Dockerfile 的 ENV、写进 notebook 输出、写进截图。镜像层可被导出查看。
    • 在 issue / PR 描述里贴报错日志，而日志里带着 Key。这是最隐蔽的一种。

L0-06 环境变量与密钥管理 ​

  • 定义：把「随部署环境变化的东西」（密钥、接口地址、模型名、库存路径、日志级别）从代码里提到外部，通过环境变量注入。核心判据只有一句：同一份代码，不改一行，能跑在开发和线上。

  • 配置分层与优先级（这是本节最该记住的一张表）：

    优先级来源用途
    1（最高）真实环境变量（shell / 容器 / CI）临时覆盖、CI 注入、生产密钥
    2.env 文件本地开发的默认值，被 gitignore
    3代码里的默认值非敏感项（超时秒数、top_k）的兜底

    实现要点是用「不存在才写入」的语义加载 .env，让已存在的真实环境变量赢：

    python
    import os
from pathlib import Path

def load_dotenv(path: Path) -> None:
    """极简 .env 读取：KEY=VALUE，# 为注释。
    用 setdefault 而不是 os.environ[key] = val —— 已存在的真实环境变量优先，
    这样 `set RAG_LLM_MODEL=glm-4-flash && python app.py` 能临时覆盖 .env，
    不需要为了测一次就改文件。"""
    if not path.exists():
        return
    for raw in path.read_text(encoding="utf-8").splitlines():
        line = raw.strip()
        if not line or line.startswith("#") or "=" not in line:
            continue
        key, _, val = line.partition("=")
        os.environ.setdefault(key.strip(), val.strip())

  • 凭据必须固定、必须纳入备份：有一类变量不是「密钥」但同样不能随机生成——比如自托管可观测平台用来加密已存数据的那几个 secret。每次部署随机生成它们，症状是「数据都还在，但一个都读不出来」。这类变量要写进 .env、进备份清单，并且不要在 CI 里临时生成。

  • .env 之外的密钥来源：本地开发用 .env；CI 用平台提供的 secret 变量（例如 GitHub Actions 的 repository secrets），绝不在 workflow 文件里明文写 Key；生产用容器编排的 secret 或云厂商的凭据服务。三处的形态不同，但「代码里永远没有 Key」这条不变。

  • 常见误区：

    • 用 .env 存非敏感配置，导致「想改个 top_k 要重启并改文件」。量级类参数给代码默认值 + 环境变量覆盖更合适。
    • 把 .env 和 .env.example 搞混，后者被 gitignore 了——那样新同学只剩一个 README 里的模糊描述。
    • 打印配置做「自检」时不脱敏，把 Key 打进日志。日志会进 trace、进可观测平台、进工单截图。

和你自己的项目对上号 ​

  • 两个版本用目录并存，而不是用分支：YYHelp 从 v1 演进到 v2 时，v1 与 v2 的代码是同一仓库里并存的两套，而不是「v2 覆盖 v1」。这个选择带来一个直接好处：A/B 对比有真实的对照组——graph/supervisor_core.py 里为此专门写了 run_single，让单 Agent 模式走全量工具清单 + v1 通用人设，多 Agent 模式走专家裁剪后的 1–2 个工具。文件里明确写出理由：如果让单模式也去走 run_expert，A/B 的自变量就会变成「有没有经过 supervisor」，而「工具菜单从 5 个降到 1–2 个」这个真正的自变量反而被抹掉了。这段注释本身就是「为什么保留两套代码」的最好答案——保留旧版本不是懒得删，是为了保住对照组。
  • 实验与产物也要版本化：科研文献 RAG 的 Dockerfile 里设了 RAG_OUT_TAG 环境变量，requirements.txt 里每个包的版本号都注明是「本机 .venv 中实测安装成功的版本，非推测」。这两件事是同一个思维：任何影响实验结论的东西都要能被标签化、被追溯——否则两个月后你无法回答「那次涨点是换了检索参数，还是换了模型版本」。
  • 密钥与配置的真实形态：.env.example 给出三套 OpenAI 兼容方案的切换方式（DeepSeek / 通义 DashScope 兼容模式 / 智谱 GLM），切换只改 BASE_URL + MODEL + KEY 三行——这正是「同一份代码跑不同 provider」的本页论点；config.py 的 _load_dotenv 是上面那段代码的原型（setdefault 让真实环境变量优先，注释里写了为什么不用 python-dotenv）；.env 在 .gitignore 里，HF_HOME 被注释要求指向 D 盘（C 盘只剩约 13 GB）——这是「配置里有平台约束」的真实例子。
  • 你还没做但面试会问的：这套栈里有几个必须固定、必须进备份的凭据（可观测平台用于加密已存数据的 salt / encryption key 一类），目前只在 compose 的 .env 里，没有进任何备份清单；仓库也没有配置 pre-commit 的 secret 扫描。被问到「怎么保证团队里别人不会把 Key 提交上去」时，诚实答法是：目前靠 .gitignore + .env.example 约定，工程上还缺自动化拦截（pre-commit + CI 扫描）。

面试怎么问（≥3 组） ​

Q1：你的 API Key 是怎么管理的？ A（要点）：三层——.env 只存在于本地且被 gitignore；仓库里只有 .env.example 列出全部必需变量名与占位值；读取时真实环境变量优先于 .env，所以 CI 与生产直接用平台注入的 secret，代码一行不改。加分句：「我用 os.environ.setdefault 加载 .env 而不是直接赋值，这样命令行可以临时覆盖配置而不必改文件——顺带我也没引入 python-dotenv，十行代码换掉一个依赖。」别说：「我写在一个 config.py 里。」（这意味着它进了仓库。）

Q2：如果 Key 已经提交上去了，你怎么处理？ A（要点）：顺序是先轮换密钥，再清理历史——因为清理期间旧 Key 仍然有效。清理用 git filter-repo（或 BFG）重写历史后强制推送，并通知协作者重新克隆；然后复盘是哪一道防线失效。加分句：「关键是理解 git rm 只是删掉当前状态，历史里的那个 commit 依然完整可读——所以『删掉就好了』是错的。」别说：「把仓库删了重建。」（这丢了全部历史，而且没有解决已泄漏的 Key。）

Q3：为什么你的仓库里有两套版本的代码？ A（要点）：为了保住对照组——A/B 对比要的是只改一个自变量，而两套实现并存让「单 Agent 用全量工具」和「多 Agent 用裁剪工具」能被同时跑起来比较；如果直接覆盖掉旧版本，这个对比就再也没有基线了。加分句：「我在代码注释里写清了两个模式在哪三个点上不同（system prompt、工具菜单、是否解析跨域标记），就是为了让半年后的自己能对上实验结论。」别说：「旧的是遗留代码，还没来得及删。」（同一件事，两种表述，一个是工程决策，一个是拖延。）

Q4：你的 commit 历史为什么这么碎 / 这么少？ A（要点）：碎是因为按「一个可独立描述的改动」提交，附带说明为什么；少说明在本地攒了很久才提交一次，代价是出问题无法二分定位，也让别人无法从历史里理解你怎么推进的。加分句：「我的原则是提交信息写『为什么』——git diff 已经能看出改了什么，历史的价值在于当时的判断。」别说：「我习惯写完一次性提交。」
