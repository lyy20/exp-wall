本页目录

ReAct、Plan-and-Solve、Reflection 与 Meta-Prompting ​

覆盖知识点：L2-09 L2-10 L2-11 L2-12 ｜ 面试频率：高 ｜ 建议学时：12h

一句话说清 ​

这一页是 Agent 面试的入口。四个知识点其实是同一件事的四种「谁来驱动循环」的答案：ReAct 让模型每步自己想下一步（思考-行动-观察循环）；Plan-and-Solve 先把计划定下来再执行（降低长任务漂移）；Reflection 用外部信号把错误喂回去重试（纠错回环）；Meta-Prompting 把「写 prompt」这件事也交给模型。最重要的是那条贯穿全页的红线：模型只输出意图，执行的是你的代码。 谁没记住这条，谁的 Agent 就会变成一个可以被提示词操纵的、有副作用的程序。

为什么必须学 ​

  • ReAct 是「Agent 的第一性原理」。几乎所有 Agent 岗位的面试都从「你画一下你的 Agent 循环」开始，答不出 Thought / Action / Observation 三元结构就直接掉档。
  • 面试官最想确认的一点是：你知不知道 tool_calls 字段会骗人。 模型可能输出一段自然语言「我准备调用查询订单工具」而没有真正进入结构化字段；如果你的代码只看 content 就去执行，就等着线上出事。
  • Reflection 是最容易讲成空话的知识点（「我让模型反思一下」）。会答的人能说清「反思必须有外部信号」；不会答的人会在追问「那它反思了还是错怎么办」时暴露没有闭环。
  • Plan-and-Solve 与 ReAct 的对比是标准高频题，正确的答法不是「哪个更好」，而是「长任务、步骤可预知 → 先规划；下一步依赖上一步结果 → ReAct」。

核心内容 ​

L2-09 ReAct 提示范式 ​

  • 定义：Reasoning + Acting。模型在每一步交替产出 Thought（思考：我现在知道什么、还缺什么）、Action（行动：调用哪个工具、参数是什么）、Observation（观察：工具返回的结果），如此循环直到它能给出最终答案。
  • 机制：三元结构的分工非常明确，这是必须背下来的：
    • Thought 是给模型自己看自然语言，内容自由、不可靠、不能当执行依据；
    • Action 必须是可解析的意图（工具名 + 参数），最终形态就是 Function Calling 的结构化字段（见 结构化输出）；
    • Observation 是外部世界的事实回执，由你的代码写回上下文，且必须当不可信内容处理（工具返回的文本里可能含着注入指令，见 Prompt 注入与缓存）。
  • 为什么这样设计：把「想」和「做」拆开，是为了让「做」这一步可以被程序拦截。如果模型直接生成最终动作的文本，你就没有插入点去校验权限、去查幂等键、去要求人工确认。拆开的价值不在推理质量，而在于执行前有了一个可拦截的边界。
  • 数量级与形状：
    • 每轮循环至少一次模型调用 + 一次工具调用；一个典型的多步任务在 3–8 轮收敛，没有终止条件时会一直循环（这是最贵的故障形态，必须设最大轮数与预算）。
    • 上下文随轮数线性增长：每轮的 Thought + Action + Observation 都要回填。工具返回很长时（例如检索出 4000 字符的原文），必须截断并在 Observation 里声明被截断，否则几轮就撑爆窗口。
    • 失败模式的空间：工具不存在、参数类型错、工具抛异常、工具返回空、模型重复调同一个工具——这五类都要有明确分支。
  • 常见误区：
    • 让模型自己执行工具：模型从来不执行任何东西。它只能输出「我要调用 X，参数是 Y」。执行、鉴权、幂等、审计全在你的代码里。
    • 只看 content：带工具调用时 content 可能是空串而结构化字段非空。这个坑在 消息角色与系统提示 里已经出现过一次，这里是它的主战场。
    • 无限循环：没有轮数上限、没有重复动作检测。检测方式很直接：把「同一工具 + 同一参数」的调用记为一次重复，连续重复就中断。
    • Observation 直接信任：把工具返回的原文拼进 prompt 时，必须包裹成「这是数据」并转义可能的闭合标签，否则检索到的文档可以直接指挥你的 Agent。
    • 把写操作交给循环重试：循环里失败 → 重试 → 重复下单。所有有副作用的动作必须幂等键 + 人工确认，且在校验通过之后才执行。
  • 代码（纯 Python 标准库 + 伪代码风格的模型接口，可运行）：一个带终止条件的 ReAct 骨架。
python
"""ReAct 循环骨架：不含任何 SDK，模型接口用可替换的 callable 注入。"""
from dataclasses import dataclass, field


@dataclass
class Step:
    thought: str
    tool: str | None          # None 表示模型要直接给最终答案
    args: dict = field(default_factory=dict)
    observation: str | None = None


class MaxTurnsExceeded(RuntimeError):
    pass


def react_loop(
    llm_step,                 # (history) -> Step ：由你的代码把 prompt 拼好再调模型
    run_tool,                 # (name, args) -> str ：执行 + 校验 + 幂等都在这里
    question: str,
    max_turns: int = 8,
) -> tuple[str, list[Step]]:
    history: list[Step] = []
    seen_calls: set[tuple] = set()      # 重复动作检测
    for _ in range(max_turns):
        step = llm_step(history)
        history.append(step)
        if step.tool is None:                       # 模型给了最终答案
            return step.thought, history
        key = (step.tool, tuple(sorted(step.args.items())))
        if key in seen_calls:
            raise RuntimeError(f"重复调用同一动作，中断：{step.tool}{step.args}")
        seen_calls.add(key)
        try:
            step.observation = run_tool(step.tool, step.args)
        except Exception as e:                       # 工具错误作为观察写回，不炸循环
            step.observation = f"TOOL_ERROR: {type(e).__name__}: {e}"
    raise MaxTurnsExceeded(f"{max_turns} 轮未收敛，问题：{question}")


if __name__ == "__main__":
    plan = [Step("先查订单状态", "get_order", {"order_id": "A1"}),
            Step("订单已发货，查物流", "get_logistics", {"order_id": "A1"}),
            Step("信息齐了，给出结论", None)]
    it = iter(plan)
    def fake_llm(history):
        return next(it)
    def fake_tool(name, args):
        return {"get_order": "状态=已发货", "get_logistics": "预计明天送达"}[name]
    answer, history = react_loop(fake_llm, fake_tool, "我的订单到哪了")
    print(answer)
    for s in history:
        print(" -", s.tool, "→", s.observation)

L2-10 Plan-and-Solve / 先规划后执行 ​

  • 定义：两次调用分工。第一次让模型先输出完整计划（步骤列表，最好结构化）；第二次起按计划逐步执行，每步只关注当前子任务，最后合成结果。
  • 机制：与 ReAct 的差别在于规划与执行的耦合度。ReAct 每步都重新规划（隐式、机会主义、灵活）；Plan-and-Solve 一次规划、多次执行（显式、可审计、但计划可能过期）。
  • 为什么这样设计：长任务上 ReAct 的典型故障是目标漂移——走到第五步时已经没有全局视图了。把计划显式化之后，计划本身就是「当前进度与剩余目标」的锚点；同时计划是可读的，可以被检查、被修改、被展示给用户确认（这一点在需要人工确认的业务里非常值钱）。
  • 数量级与形状：
    • 调用次数：1 次规划 + 次执行 + 1 次合成。相较 ReAct，总轮数通常更少、更可预测。
    • 计划本身要占 token（通常几百），且一旦偏离现实就需要重规划——生产里一般是「执行失败或收到意外观察时触发一次重规划」，而不是无条件重规划，否则成本翻倍。
    • 计划必须能被结构化解析才有价值（步骤列表），否则它只是段散文，程序无法做进度管理。
  • 常见误区：
    • 计划不可执行：让模型输出一段「首先我要理解用户意图……」的计划，等于没规划。计划必须是带工具名与参数的操作序列。
    • 执行阶段仍然自由发挥：如果执行时又把全部工具交给模型，它照样会漂移。正确的做法是按当前步骤收窄可见工具。
    • 计划泄露给用户：内部计划（尤其是包含工具名、检索策略的）不该直接回显给终端用户——那是实现细节，也是提示词泄露面。要展示给用户时必须先改写成人话。
    • 不设重规划预算：重规划循环同样会无限。设上限，并把「计划被推翻几次」当成质量指标记下来。
  • 对比表（面试可直接背）：
维度ReActPlan-and-Solve
规划时机每一步隐式重规划一次显式规划
可预测性低（轮数与成本不定）较高（计划定后成本可估）
长任务表现容易目标漂移更稳，但计划过期会整体跑偏
适应突发变化强需要触发重规划
可审计性需从轨迹里还原意图计划本身就是待审计对象
适配合适场景下一步依赖上一步结果的探索型任务步骤可预知、需要进度的业务流

L2-11 Reflection / 自我反思与重试 ​

  • 定义：让模型对自己的输出做批判，并据此修正或重试。生产中它通常不是独立技巧，而是流程里的一环：校验失败 → 把失败原因回灌 → 重试。
  • 机制（这条是本页最容易被追问的一点）：Reflection 要生效，必须有一个外部信号（external signal）。可靠的外部信号有：schema 校验失败的报错、pydantic 的 ValidationError、单元测试结果、工具返回的错误码、检索证据不足以支撑答案。没有外部信号时，「让模型自己再看看」只是又一次采样——它会给出另一个看起来同样合理的答案，成本翻倍而正确率无保证，还带着自我偏袒（模型倾向于认可自己刚写的东西）。
  • 为什么这样设计：把「判断对错」的责任从模型转移到程序，是工程上最划算的分工。程序能确定性地回答「字段少了没」「编号是否越界」「测试过没过」；模型只需要负责在已知错误信息下改。这就是为什么最好的 reflection prompt 里，最重要的一句话是那句原样回灌的错误信息。
  • 数量级与形状：
    • 一次反射 = 额外一次调用，成本翻倍。因此必须设重试上限（常见是 1–2 次），并把「重试后仍失败」当成降级路径而不是继续重试。
    • 收益主要集中在可判定的错误（格式、字段缺失、编号越界、引用缺失），对知识性错误几乎无效。
    • 副作用风险：重试会重复执行有副作用的动作。写操作必须幂等（同一请求 ID 只生效一次），或者把「校验」放在执行之前。
  • 常见误区：
    • 把反思当成「再问一次」：没有错误信息的重试与第一次采样同分布。
    • 不把错误信息带回去：只说「格式错了」，模型只能猜哪里错。必须回灌具体报错。
    • 不设上限：反思循环会一直烧钱，且收敛不了会同时拖垮延迟。
    • 对写操作反射重试：第一次可能已经成功了，只是回执丢失。必须有幂等键。
    • 只做「自我批评」不做「闭环」：批评完要真的改并重跑校验，否则反思只是把一段自我批评文本加进上下文。
  • 代码（纯标准库，可运行）：带错误回灌的重试管线。
python
"""校验失败 → 把具体错误回灌 → 重试（有上限）。纯标准库可运行。"""
from dataclasses import dataclass


@dataclass
class Attempt:
    n: int
    raw: str
    error: str | None


class RetryExhausted(RuntimeError):
    pass


def produce_with_retry(generate, validate, max_attempts: int = 3):
    """generate(hint: str | None) -> str ；validate(raw) -> None 或抛异常。"""
    hint, attempts = None, []
    for n in range(1, max_attempts + 1):
        raw = generate(hint)
        try:
            validate(raw)
            attempts.append(Attempt(n, raw, None))
            return raw, attempts
        except Exception as e:
            # 关键：把**具体报错原文**回灌，而不是"格式不对请重试"
            hint = f"上一次输出未通过校验，错误为：{type(e).__name__}: {e}。请修正后只输出修正结果。"
            attempts.append(Attempt(n, raw, repr(e)))
    raise RetryExhausted(f"{max_attempts} 次仍未通过；最后一次错误：{attempts[-1].error}")


if __name__ == "__main__":
    import json

    def validate(raw):
        obj = json.loads(raw)
        if not isinstance(obj, dict):
            raise TypeError("顶层必须是对象")
        if "citations" not in obj:
            raise KeyError("缺少字段 citations")
        if not obj["citations"]:
            raise ValueError("citations 不得为空：有引用的答案必须给出引用编号")

    outs = iter(['{"answer":"A"}',
                 '{"answer":"A","citations":[]}',
                 '{"answer":"A","citations":[1]}'])
    raw, tries = produce_with_retry(lambda hint: next(outs), validate)
    print(raw)
    for a in tries:
        print(a.n, a.error)

L2-12 Meta-Prompting ​

  • 定义：让模型生成或改写 prompt：把任务描述、若干输入输出样例、约束条件交给模型，让它产出一版更优的 prompt（或直接产出候选 prompt 让另一模型执行）。
  • 机制：它把 prompt 工程变成一次优化循环：生成候选 → 在评测集上打分 → 保留更好的 → 再生成。注意它本身不提供任何保证，它只是把搜索过程自动化了，选择那一步仍然靠你的评测集。
  • 为什么这样设计：人工调 prompt 的问题是变量太多且无法穷举（措辞、示例、顺序、格式描述）。让模型做大规模候选生成、让评测集做筛选，是典型的「生成便宜、验证贵」的分工。它的产出物仍然是一个可版本化的字符串，所以它必须和 Prompt 版本化与评测闭环 绑在一起用，否则生成的 prompt 无人能回滚。
  • 数量级与形状：每次迭代至少 1 次生成调用 + 评测集大小的执行次数。评测集 50 条、候选 5 个，就是 250 次执行——评测成本通常是这条路的真实瓶颈，而不是生成成本。
  • 常见误区：
    • 没有评测集就用它：没有打分函数，Meta-Prompting 就退化为「随机换一版提示词」。
    • 把优化后的 prompt 当黑盒：自动产出的 prompt 往往冗长且含隐含假设，必须人工读一遍再入库，否则会出现「能过评测集但依赖某种偶然措辞」的情况。
    • 让同一模型既生成又评判：自我偏袒会让搜索偏掉。至少要换一个视角，或掺入确定性断言。
    • 在生产链路里在线优化：它属于离线流程。在线只读版本号。
    • 平台特性：部分模型厂商在 API 侧提供了 prompt 的托管与版本管理能力（把 prompt 作为服务端资源引用）。具体端点、字段与限制以所用供应商的官方文档为准，本页不写具体字段名。

和你自己的项目对上号 ​

YYHelp v2（LangGraph 电商客服 Agent）：这一页的四个知识点在这个项目里几乎全部有对应实现，可以直接照着讲：

  • ReAct 是骨架：supervisor 决定派给哪个专家、专家调用工具、结果作为观察写回 state，这是标准的三元循环。项目里有一条特别值得讲的设计：校验失败不炸图，错误作为工具结果写回 state。这正是把「工具错误」当成一种 Observation 处理——循环继续，但模型能看到错误、能改参数、能换工具。相比之下，直接抛异常会把整个会话打断。
  • 工具可见性收窄：5 个专家 × 5 个工具，每个专家只看到与自己相关的 1–3 个。这是 Plan-and-Solve 执行阶段的正确做法——执行时不要把全部工具都摊给模型，否则它会漂移回「随便挑一个」。
  • 写操作的三道锁：幂等键（同一业务动作只生效一次）+ 人工确认（不可逆动作前必须过确认）+ 「校验通过之后才执行」。这直接对应 ReAct 的两个坑：循环重试导致重复副作用，以及在参数没校验前就动了外部系统。
  • Reflection 有外部信号：这里的反思不是「让模型自我批评」，而是pydantic 校验失败 + 工具返回的错误码/空结果作为信号回灌。所以能回答「你的反思靠什么触发」。
  • 版本号：plan-v2 与 supervisor-core-v2 说明这一页的提示词是当代码管的。plan-v2 的改动方向就是把「先列步骤再执行」显式写进计划提示词——从「边执行边想」迁到「先规划后执行」，是一次可讲的架构决策。
  • 诚实边界：这个项目不适合 Self-Consistency（写操作不可逆、且温度低），也不适合在线做 Meta-Prompting。面试时主动说出「哪些我没做、为什么」比强行罗列更可信。

科研文献 RAG：这个项目没有 ReAct 循环，而这一点本身是可讲的取舍——

  • 检索链路是固定的（查询改写 → 混合检索 → 重排 → 生成），步骤事先列得全，所以它是 workflow 而不是 Agent。用 L2-10 的判断依据回答「你为什么不用 Agent」：能提前把步骤写全的任务不该交给模型选下一步，因为那只会引入不确定性而没有新增能力。
  • 它是反思闭环的典型：拒答要模型自报 insufficient（模型侧信号，要花钱、不完全可靠），引用编号要过程序侧校验（确定、免费）。这个双层结构就是 L2-11 的核心：把可判定的判断交给程序，把语义判断留给模型。
  • 引用编号的解析鲁棒处理（["1","2"] 曾被静默丢弃成 citations=[] 却报「校验通过」，见 NOTES-踩坑记录.md 坑 21）正是「反思不能靠自我批评、必须靠可证伪的校验函数」的反面教材：check_citations([]) 返回 True 的校验函数，等于没有校验。
  • Meta-Prompting 在这个项目里没做过——这一点应当诚实说明，并给出可执行补法：拿现有评测集当打分函数，让模型生成 3 版生成阶段提示词、离线跑分、保留最好的一版并按 Prompt 版本化 的规则入库。

面试怎么问（≥3 组） ​

Q1：画一下你的 Agent 循环，ReAct 里到底谁在调用工具？

A：循环是 Thought → Action → Observation。但要说清一件事：模型从不执行工具，它只输出「要调用哪个工具、参数是什么」的意图，真正执行的是我的代码。所以工具名要校验、参数要过 pydantic、有副作用的动作要查幂等键并走人工确认，执行完把结果作为 Observation 写回上下文再发下一次请求。

追问：那你靠什么拿到这个意图？

A：靠结构化字段（Function Calling），不是靠解析自然语言。这里有个必须防的坑：模型可能输出一段自然语言说「我准备调用查询订单工具」而结构化字段是空的，所以我的代码以结构化字段为准，content 只用来做展示。另外带工具调用时 content 常是空字符串，直接对它做字符串操作会崩。

追问：循环怎么终止？

A：三条闸门：模型给出不带工具调用的最终答案、达到最大轮数、达到预算。另外还有一个重复检测——同一工具 + 同一参数连续出现就中断，因为那是模型卡住的典型信号。终止不是小事：没有上限的循环是最贵的故障形态。

Q2：长任务你会用 ReAct 还是先规划？

A：看「下一步是否依赖上一步的结果」。步骤能事先列全、且有进度需要展示或人工确认的，用先规划后执行——计划是显式的，可以被检查、被重规划，成本也更好估。下一步必须看前一步拿到什么才能决定的（探索型），用 ReAct。我们项目里是混合的：计划由 plan 节点显式产出，执行阶段才是循环，也就是先规划、后逐步执行，执行时只给当前专家看它相关的 1–3 个工具。

追问：计划本身出错了怎么办？

A：两种处理。一是执行阶段收到的观察与计划矛盾时触发一次重规划，但重规划要有预算上限，否则成本翻倍；二是把计划当结构化的步骤列表而不是散文——程序能检查步骤数量上限、能判断当前进度，人也能读。如果计划是一段「首先我要理解用户意图……」，那它根本不能被程序消费。

追问：ReAct 在长任务上的典型故障是什么？

A：目标漂移。走到第五步时模型已经没有全局视图，开始做局部看起来合理、但和原始目标无关的动作。显式计划就是对它的解药——计划成了「剩余目标」的锚点。

Q3：Reflection 你怎么做的？

A：关键是有没有外部信号。我们的反思触发条件是确定的：pydantic 入参校验失败、工具返回错误码、引用编号越界、检索证据不足以支撑答案。触发之后把报错原文回灌给模型让它改，限定重试 1–2 次，仍然失败就降级——而不是继续重试。

追问：如果只是让模型「自己再看看」，会怎样？

A：那只是再采一次样，成本翻倍、正确率没有保证，而且模型倾向于认可自己刚写的东西，自我偏袒会让它改坏。所以没有外部信号时，我宁可不做反思——先去做那个能让判断变得确定的东西（校验函数、单元测试、评测集）。

追问：反思重试会不会造成重复副作用？

A：会，而且这是生产事故的常见来源——第一次其实成功了，只是回执丢了，重试又执行一次。所以两道防护：写操作必须幂等（同一业务动作只生效一次，靠幂等键），以及校验必须在执行之前，格式没过就不该动外部系统。
