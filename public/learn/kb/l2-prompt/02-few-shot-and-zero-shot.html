Few-shot 示例选择与 Zero-shot 边界 ​

覆盖知识点：L2-04 L2-05 ｜ 面试频率：高 ｜ 建议学时：5h

一句话说清 ​

Few-shot（少样本示例）是不改权重地把「任务定义 + 输出契约」塞给模型的手段：它不给模型新知识，只给它一个可模仿的形态样本。Zero-shot（零样本）则是基线——先证明零样本不够，再决定加示例。这一页要建立三个判断：（1）什么时候必须给示例；（2）示例怎么选、给几个、按什么顺序放；（3）给示例的代价是什么（token 成本、格式被示例绑架、示例本身可能被当成待处理数据）。

为什么必须学 ​

面试官问这个问题时，要的不是「Few-shot 能提升效果」这句结论，而是判断你有没有做过对照实验。三个真实场景：

  • 「你这个抽取任务为什么不做微调？」——正确回答的起点是「我先跑了 zero-shot 基线，错在哪几类上，few-shot 补掉了哪几类，剩下哪几类只能靠微调」。
  • 「示例你怎么选的？」——如果你的答案是「随手挑了三个」，面试官会判定你没做过评测，接下来所有数字都不再可信。
  • 「给几个示例最好？」——答「越多越好」直接暴露你没有成本意识；答「三五条最好」也是背的。正确答案是「在留出集上测边际收益，通常在个位数条就饱和」。

HR 侧不太会检索 few-shot 这个词，但会检索「评测」「A/B」；而「示例选择」恰好是你唯一可以在简历上写成「用留出集做示例选择，把某类错误率从 X 降到 Y」的地方（数字必须来自你的真实记录）。

核心内容 ​

L2-04 Few-shot 与示例选择策略 ​

  • 定义：在 prompt 里放入 个「输入 → 输出」示范对（ 通常是 1–5），让模型从示范中推断任务形态与输出格式。这一行为依赖模型的 in-context learning（上下文学习） 能力——能力来自预训练，示例只负责定位它。
  • 机制：示例对模型的三个作用，按可靠性从高到低排列：
    1. 输出契约：给字段名、嵌套结构、单位、语言、标点风格（这一条最可靠，也最常用）；
    2. 任务边界：用反例或边界例说明「什么情况该走另一路」（比如「无信息时应返回拒答」）；
    3. 任务定义：当标签体系不是常识（你自己的四分类）时，示例是唯一能让模型知道标签有哪些的方式。注意这一条替代不了指令——示例没写清的分类标准，模型只能猜。
  • 为什么这样设计：模型是无状态的，它的「行为规格」只能来自上下文。指令是声明式的规格（模型要靠指令遵循能力去执行），示例是演示式的规格（模型靠模式匹配去模仿）。当任务形态难以用语言精确描述（比如「按这种口径抽取日期并统一成 YYYY-MM-DD」），演示比声明便宜得多。
  • 数量级与形状：
    • 示例对 token 的占用必须单独算：一段「输入 + JSON 输出」的示范对，简单分类约 50–100 token，抽取/结构化任务约 150–300 token。3 个示例 ≈ 450–900 token 的每条请求固定开销。
    • 边际收益递减很快：从 0→1 个示例的收益最大，1→3 常有小幅收益，再往上通常不再涨、甚至下降（模型开始照抄示例的表面形式）。
    • 成本公式：额外日成本 ≈ 示例 token 数 × 日请求数 × 输入单价。1000 次/日、多 800 token 示例，就是每天多 80 万输入 token——加示例前先算这笔账。
  • 常见误区：
    • 示例顺序无关：不是。模型对最后几个示例的模仿更强（与上下文末端权重更高有关）。把最典型、最规范的示例放在最后，是零成本的排序收益。但顺序敏感这件事本身要在你的评测里验证，不要当定律背。
    • 示例越多越好：见上，超过个位数条通常饱和；同时示例会占上下文，把真正的新信息挤到更靠后的位置。
    • 只有正例：类别不平衡的任务里，全正例会推高模型的误报率。要么给边界负例，要么在指令里显式写「没有匹配项时输出空数组」。
    • 示例里放脏数据：示例是模型模仿的对象，示例里字段名不一致（一条用 source、一条用 citations），它会直接学到漂移——这正是 结构化输出与解析鲁棒性 里要治的病。
    • 示例里的文本被当成待处理数据：示例天然包含输入文本，若分隔符不明确，模型可能把示例的输入一起「处理」进答案，或把示例里的指令当成真指令——这就是 注入与缓存 的注入面之一。
  • 代码（纯标准库，可运行）：按「最容易混淆的类别对」挑示例，比随机挑更有针对性。
python
"""按混淆矩阵挑 few-shot 示例：把最容易被搞混的两类的代表样本放进 prompt。"""
from collections import Counter


def pick_demonstrations(samples, y_pred, n=3):
    """samples: [(text, label)]；y_pred: 同长度预测列表。返回挑选出的示例。"""
    # 1. 统计混淆：{(金标, 预测): 计数}
    conf = Counter(
        (gold, pred) for (_, gold), pred in zip(samples, y_pred) if gold != pred
    )
    # 2. 最易混类别对 —— 每一对贡献一个"处于该边界上"的真实样本
    picked, seen_texts = [], set()
    for (gold, pred), _ in conf.most_common():
        for text, label in samples:
            if label == gold and text not in seen_texts:
                picked.append((text, label))
                seen_texts.add(text)
                break
        if len(picked) >= n:
            break
    # 3. 不足时用「类分布均衡」补齐（避免全是一个类的正例）
    if len(picked) < n:
        by_label = {}
        for text, label in samples:
            by_label.setdefault(label, []).append(text)
        for label in sorted(by_label):
            for text in by_label[label]:
                if len(picked) >= n:
                    break
                if text not in seen_texts:
                    picked.append((text, label))
                    seen_texts.add(text)
    return picked[:n]


# —— 自测（可直接运行）——
if __name__ == "__main__":
    samples = [("运费怎么算", "logistics"), ("多久到", "logistics"),
               ("怎么退款", "refund"), ("退款要几天", "refund"),
               ("多少钱", "price")]
    y_pred = ["refund", "logistics", "refund", "logistics", "price"]
    for t, lb in pick_demonstrations(samples, y_pred, n=3):
        print(f"[{lb}] {t}")
    # 期望：先给出被搞混的两个类的代表样本，再补齐

L2-05 Zero-shot / Instruction 遵循 ​

  • 定义：不给任何示例，仅靠指令完成任务的调用方式。它是基线（baseline），不是「低配版」。
  • 机制：近几年的模型在「指令微调 + 偏好对齐」阶段被大量训练过「按格式回答」这件事，所以对明确、可验证的指令，zero-shot 的遵守率已经很高。示例的收益主要体现在「指令难以描述」的地方，而不是「模型不听话」的地方。判断顺序因此固定为：先写清楚指令 → 测 zero-shot → 看错误类型 → 若错误集中在格式/口径上，再加示例；若错误集中在知识上，加示例没用（那是 RAG 或微调的事）。
  • 为什么这样设计：把 zero-shot 当基线是一种成本纪律。示例是纯成本（token、维护、缓存失效风险），只有换来可测量的准确率提升才值得。很多团队一开始就堆五条示例，最后没人知道这五条到底贡献了多少。
  • 数量级与形状：一次 zero-shot 请求的固定开销只有 system prompt。同理，instruction 的写法对结果的影响通常大于示例数量——「只输出 JSON，键为 answer/citations」和「请以 JSON 格式回答，包含答案和来源」是两条命中率完全不同的指令（后者实测会导致字段名漂移，见 结构化输出）。
  • 常见误区：
    • 把 zero-shot 当「没做优化」：它应该是你唯一有基线数字的那一档。没有基线的优化等于没有优化。
    • 用示例掩盖指令缺陷：如果一条规则必须靠示例才能被理解，说明指令写得不清楚——这种情况先改指令，因为指令能被 A/B、能进版本库，示例还会随数据漂移。
    • 忽略「指令遵循有上限」：模型对否定式约束（「不要编造」）的遵守率普遍低于正向替代（「只能引用上下文中的句子」）。Zero-shot 下这条差异更明显。
    • 跨模型迁移时不重测：不同模型的指令遵循强度差异很大，zero-shot 表现尤其敏感——旧模型上加示例才勉强跑通的任务，新模型可能完全不需要示例。换模型必须重跑基线。

判断表（可直接背下来用到面试里）：

情形选择理由
任务与常见任务同形（分类、抽取、改写），且输出格式由 结构化输出 约束Zero-shot格式已由 Schema 保证，示例只剩边际收益
输出有自定义口径（单位、枚举、命名规范），指令描述成本高Few-shot（1–3 条）演示比声明便宜，且示例即测试用例

错误集中在「不知道的事实」都不选 → RAG / 微调示例不提供新知识
模式复杂、样本成千上万、延迟与成本敏感都不选 → 微调（见 L7）用权重换掉上下文里的示例开销

和你自己的项目对上号 ​

YYHelp v2（LangGraph 电商客服 Agent）：这个项目故意没用 few-shot，这个决定本身就是可讲的：

  • 路由层（supervisor 选专家）靠的是明确的专家名 + 工具可见性收窄（5 个专家 × 5 个工具，每个专家只看到 1–3 个），不是一个需要示例来教的模糊分类任务。工具列表本身就是「选项的显式枚举」，把示例塞进去只会占 token、还会让每轮请求的缓存前缀变长。
  • 工具入参用 @tool + pydantic 校验，格式契约由 Schema 保证，不靠示例保证。这正是判断表的第一行：格式已由结构化输出兜住，示例只剩边际收益。
  • 唯一想过加示例的地方是「回复语气」——这类需求最后是靠 system prompt 里的口径描述 + 版本号（plan-v2 / supervisor-core-v2）管理的，因为它需要 A/B，而示例很难做 A/B（换一条示例就是换了一个变量，对照不干净）。
  • 长期记忆的 RECALL_POLICY="state_only"（写 state 但不拼进 prompt）也是一致的成本纪律：进 prompt 的东西必须有理由。

科研文献 RAG：这里的 few-shot 需求更弱，但有一处必须做的是「输出契约的演示」而不是「任务的演示」：answer / citations / insufficient 三个字段的语义（尤其拒答时 insufficient 与 citations 的组合）用指令描述时实测会出现字段名漂移与类型漂移。当时的选择是不靠示例，靠 JSON mode + 生产侧归一化（normalize_citations 处理 7 种形态），因为示例会随检索上下文变化而失效。这条经历可以直接回答「你为什么不用 few-shot 修格式问题」——因为示例治的是「模型没看懂」，而这里的问题是「模型看懂了但输出了合法 JSON 的另一种形状」，属于校验层的问题。

面试怎么问（≥3 组） ​

Q1：Few-shot 为什么有效？

A：因为它依赖 in-context learning——能力来自预训练，示例的作用是定位模型已经具备的能力，而不是教它新知识。具体它提供三样东西：输出契约（字段名、结构、单位）、任务边界（什么情况该拒答/走另一条路）、以及当标签体系是自定义时的任务定义。

追问：那它和微调的关系是什么？

A：示例是用上下文换行为，微调是用权重换行为。示例的代价是每次请求都付 token 费、且占用上下文；微调的代价是数据、训练、以及迭代慢。判断顺序是：先 zero-shot 基线，再加示例看边际收益，只有当示例已经堆到个位数条以上还在涨、且模式足够稳定时才考虑微调。

追问：那你怎么知道该给几个示例？

A：在留出集上做 0 / 1 / 2 / 3 的扫描，看准确率的边际曲线在哪饱和。经验上饱和点通常在个位数条，但我不会把这个数字当结论讲——它是我们那个任务饱和了，换任务要重测。同时我会把示例带来的输入 token 增量算进成本：示例 token × 日请求数 × 单价。

Q2：你的示例是怎么选出来的？

A：先用零样本跑一遍固定评测集，拿混淆矩阵看错误集中在哪两个类别之间，然后从真实数据里挑处于这些边界上的样本当示例，而不是随机挑或手工编造。示例本身必须是生产分布里的真样本，否则你以为在教边界，实际在教一个不存在的分布。

追问：为什么不能随机挑？

A：因为随机挑的期望是「覆盖最常见的类别」，而模型本来就会做最常见的类别。示例的价值在于修正它做错的那部分。随机挑在类别不平衡的数据上还会给出一个几乎全是多数类的示例集合，等于告诉模型「答案几乎总是这个」。

追问：示例顺序有影响吗？

A：有，模型对靠后的示例模仿更强，所以我会把最规范、最典型的那条放在最后。但这条我会实测验证——不同模型对位置的敏感度不一样，我不会当定律用。另外顺序一改，前缀就变了，对 Prompt 缓存 是有影响的，所以顺序一旦定下来就不要随机化。

Q3：什么情况下你会放弃 few-shot？

A：三种。第一，错误是知识性的（模型不知道某个事实），示例不提供新知识，该做 RAG 或微调；第二，格式错误可以被 Schema 消灭，那就不该用示例治，示例只能降低概率、不能给保证，而 strict 模式与校验重试 给的是保证；第三，加了示例但留出集上看不出提升——这时候示例就是纯成本，我会删掉，并把这次实验记进评测报告。

追问：你说「看不出提升」，多少算看得出？

A：看评测集大小和噪声。我会先确认评测是确定性的（同一输入同一输出，温度设到最低），再看差异是否稳定复现。如果两次重跑的结果自己都不一致，那这个差异不能算提升——先修评测的不确定性，再谈优化。

追问：那如果提升了但成本也涨了很多呢？

A：看这个任务的失败代价。客服场景答错一次可能产生真实工单，那 800 token 的示例费是便宜的；但如果只是格式好看，我会优先选「协议侧约束 + 校验重试」而不是「多给示例」，因为前者在成本上是一次性的（代码），后者是每次请求都付的。
