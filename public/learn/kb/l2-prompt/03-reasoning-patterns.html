CoT、Self-Consistency 与任务分解 ​

覆盖知识点：L2-06 L2-07 L2-08 ｜ 面试频率：高 ｜ 建议学时：9h

一句话说清 ​

这一页讲的是同一件事的三个层次：让模型多花算力去算，而不是直接猜。CoT（Chain-of-Thought，思维链）说的是「把中间步骤写出来」；Self-Consistency 说的是「写多遍再投票」；任务分解与 Least-to-Most 说的是「把题目拆小，一步步喂回去」。它们共同的机制是：自回归模型每生成一个 token 只做一次固定深度的前向计算，中间过程 token 越多，等效计算量越大。所以 CoT 不是「让模型更聪明」，而是「给模型更多计算预算」。理解了这一点，你就能回答面试官真正想确认的那件事：什么时候该用、什么时候纯属浪费钱。

为什么必须学 ​

  • 这是 L2 里唯一一个能讲出原理的提示技巧。Few-shot 讲的是经验，CoT 讲的是机制——面试官很容易用「为什么写中间步骤就有用」把只会背结论的人筛掉。
  • Self-Consistency 是必须和成本一起答的题：「你采样几次？」答不上 n 与收益的关系，等于没做过。
  • 任务分解是通往 ReAct 与 Agent 的桥。面试官问「为什么需要 Agent 而不是一个大 prompt」，最有力的回答就是「长任务必须拆步，拆步之后每一步的结果要能被工具验证」。
  • 这三条在简历里都能写成可验证的句子（「在 X 类多步问题上把准确率从 A 提到 B，代价是采样 n 次」），而且不需要编数字也能讲得诚实：只要你说清「我测了 n=1/3/5 的扫描，饱和点在哪」。

核心内容 ​

L2-06 Chain-of-Thought（CoT） ​

  • 定义：在提示中要求模型先输出推理步骤、再输出最终答案。两种常见形态：Zero-shot CoT（只加一句「先一步步推理，再给答案」）与 Few-shot CoT（示例里带着推理步骤，见 Few-shot 示例选择）。
  • 机制：自回归解码是「每个位置一次前向」。生成 个中间 token 相当于把计算分摊到 步、每步都能看到前面的中间结果。直接猜答案时，所有推理负担都压在那一个 token 上；写中间步骤时，后续 token 可以在已经写下来的中间结论条件下继续算。这就是为什么它对手工多步计算（算术、逻辑、单位换算、多跳问答）提升明显，而对「模型知道就知道」的事实题几乎没用。
  • 为什么这样设计：CoT 是把「隐式计算」显式化成 token。显式化的副产品同样重要：中间步骤是可读、可审计、可校验的——这正是后面 Reflection 与结构化输出能接上的原因。
  • 数量级与形状：
    • 输出 token 数通常增加到原来的数倍（一条 100 token 的直答可能变成 300–600 token 的推理 + 答案）。费用按输出 token 计，这是实打实的倍数成本。
    • 收益与任务步数正相关，与模型能力反相关：弱模型上 CoT 收益大，强推理模型上收益小（它已经内化了推理）。2025 年之后的推理模型（reasoning model）本身就是「先想再答」，你再叠加一句「think step by step」通常没有增量收益。
  • 常见误区：
    • 对简单任务也开 CoT：抽取、分类、格式转换这类单跳任务上，CoT 只增加延迟和成本，有时还会因为它「想多了」引入原文没有的信息。
    • 零样本 CoT 与推理模型混为一谈：这两件事不同。一个是提示技巧，一个是模型能力/训练目标。面试里能分清这一点是加分项。
    • CoT 和结构化输出硬碰硬：如果输出必须是严格 JSON，让模型「在 JSON 里思考」很容易崩——要么把思考放进一个独立字段（如 reasoning），要么分成两次调用。这是本页最常踩的工程坑。
    • 把 CoT 的中间结论当事实：中间步骤是生成物，不是推理过程的记录。它可能自洽地错，所以不能只靠它做审计。
  • 代码（纯标准库，可运行）：从「先推理再作答」的输出里稳健地取最终答案。
python
"""从 CoT 输出中提取最终答案：只认显式标记，不做语义猜测。"""

FINAL_MARKERS = ("最终答案：", "最终答案:", "答案：", "答案:")


def extract_final_answer(text: str) -> str:
    """取最后一个标记之后的内容；没有标记就返回空串（由调用方决定怎么兜底）。"""
    best = -1
    for m in FINAL_MARKERS:
        i = text.rfind(m)
        if i > best:
            best, cut = i, i + len(m)
    if best < 0:
        return ""
    return text[cut:].strip().splitlines()[0].strip() if text[cut:].strip() else ""


if __name__ == "__main__":
    raw = ("用户问的是安全距离。规范里写 15 m，操作规程写 30 m，"
           "以更严的 15 m 为准。\n最终答案：15 m\n依据：[1]")
    print(extract_final_answer(raw))   # 15 m
    print(repr(extract_final_answer("我觉得是 15 米。")))  # '' → 触发兜底

L2-07 Self-Consistency ​

  • 定义：同一问题用较高温度采样 次，得到 条推理链和 个答案，对最终答案做多数投票。
  • 机制：单次采样是「模型分布中的一个样本」。正确的解法通常有多条不同的推理路径都能走到同一个答案，而错误的解法往往各自发散——所以答案空间的一致性会放大正确答案的概率。注意它投票的是答案，不是推理过程；中间步骤不一致完全可以接受。
  • 为什么这样设计：它是「用推理时的算力换准确率」最直接的实现：不改权、不改 prompt、不用标注数据，只改采样次数。代价可预测（成本随 线性增长），非常适合在离线批处理里用，不适合在同步在线路径上用。
  • 数量级与形状：
    • 成本：输入 token （若开了 Prompt 缓存，前缀部分可复用，实际增量小很多）+ 输出 token 。
    • 的常见起点是个位数（3–5），收益通常在 从 1 增到几的时候最明显，再往上饱和。饱和点是任务相关的，必须自己扫。
    • 只有在「答案可枚举、可比较」时才成立。开放式生成（写一段文章）没有投票对象。
  • 常见误区：
    • 温度太低： 接近 0 时 次采样几乎同分布退化成一次，投票毫无意义。Self-Consistency 的前提是采样有多样性。
    • 投票前不做归一化："15 m" / "15米" / "15" 会被当成三个不同答案，多数投票因此退化。归一化是必须写的一步。
    • 在 JSON 结构化输出场景硬上：严格模式下多样性被压缩，投票收益下降；而且 份 JSON 的比对成本不低。此时更划算的是「一次生成 + 校验重试」。
    • 用 CoT 的成功案例证明 Self-Consistency 有效：两者要分开测。收益要单独归因，否则面试官一问「你怎么知道是投票起的作用」就答不上来。
    • 忽略「都不对」的情形：如果 次答案各不相同，说明模型在这个问题上没有共识，此时投票结果等价于随机挑一个。正确做法是把这种情况判为「不确定」并降级（拒答或转人工），而不是硬取第一个。
  • 代码（纯标准库，可运行）：含归一化与「无共识」判定。
python
"""Self-Consistency 的投票环节：归一化 + 多数票 + 无共识检测。"""
import re
from collections import Counter


def normalize(ans: str) -> str:
    """把同一答案的不同写法折叠成同一个 key。"""
    s = ans.strip().lower()
    s = re.sub(r"\s+", "", s)
    s = s.replace("米", "m").replace("meters", "m").replace("meter", "m")
    s = re.sub(r"(?<=\d)m$", "m", s)
    return s


def majority_vote(answers: list[str]) -> tuple[str, int, bool]:
    """返回 (胜出答案的原写法, 票数, 是否有共识)。

    共识判据：最高票必须严格多于第二名，且票数 >= 2。
    全不相同 → 无共识，调用方应降级而不是硬选。
    """
    counts = Counter(normalize(a) for a in answers)
    if not counts:
        return "", 0, False
    ranked = counts.most_common()
    top_key, top_n = ranked[0]
    second_n = ranked[1][1] if len(ranked) > 1 else 0
    consensus = top_n >= 2 and top_n > second_n
    original = next(a for a in answers if normalize(a) == top_key)
    return original, top_n, consensus


if __name__ == "__main__":
    print(majority_vote(["15 m", "15米", "30 m", "15", "12 m"]))  # ('15 m', 3, True)
    print(majority_vote(["15 m", "30 m", "12 m"]))               # ('15 m', 1, False) → 降级

L2-08 任务分解与 Least-to-Most ​

  • 定义：把复杂问题拆成一组有序子问题，逐个求解，每次把前面已解出的子答案带入下一次调用，最后合成总答案。Least-to-Most 是其中一种具体做法：先让模型列出子问题（分解），再逐个求解（顺序求解），每个子问题都比原问题更简单。
  • 机制：它同时解决三个问题：（1）单次调用里的推理深度被压缩到「一跳」，降低单步漂移；（2）每个子答案可以被独立验证（有依据、有引用、有工具回执）；（3）失败可以局部重试，不必整题重来。
  • 为什么这样设计：这是 workflow 与 Agent 的分界线。把步骤写死在编排里就是 workflow（可预测、可测、便宜）；让模型自己决定下一步调什么就是 Agent（灵活、但不可预测、贵）。面试里被问「你为什么不用 Agent 直接用一个大 prompt」，正确答案就是：长任务单次调用会漂移，拆开后每一步可验证；而拆法是否固定，决定了用 workflow 还是 Agent。
  • 数量级与形状：
    • 调用次数：（分解）+ （子问题数）+ （合成）。 通常是 2–5；再高说明子问题粒度太细，编排开销会超过收益。
    • token 成本随 线性增长，且每个子问题都要重复带上已解出的前文——累计输入 token 是 ，随 近似二次增长。这是「拆得越细越贵」的量化原因。
    • 误差同样会累积：单个子答案错了，后面全歪。所以每一步都要有校验或证据，而不是无条件相信上一步的输出。
  • 常见误区：
    • 只拆不验：分解的价值有一半来自「每一步可以被验证」。如果子答案没人检查，分解只剩下「把一次错变成多次错」。
    • 子问题之间互相依赖却没排序：Least-to-Most 的关键是有序——先解的子问题必须是后解子问题的输入。顺序错了两步都要返工。
    • 把自然语言分解结果直接当可执行计划：拆出来的是一段文本，不是数据结构。要做流程控制就得让它输出结构化的步骤列表（配合 结构化输出）。
    • 在已经能一次答对的问题上用分解：和 CoT 一样，单跳任务上加分解只有成本。
    • 忽略「分解本身可能错」：模型可能漏掉一个必要子问题，或把无关步骤塞进来。分解结果要过一遍合理性检查（子问题数上限、是否覆盖问题关键词、是否都是可回答的）。

和你自己的项目对上号 ​

YYHelp v2（LangGraph 电商客服 Agent）：这个项目里 CoT 与分解不是「提示技巧」而是架构的一部分：

  • 分解被固化进了图结构：plan 节点先产出计划、再分派给专家、最后由汇总节点合成回复。这就是 L2-08 的形态，只不过「子问题」变成了「专家任务」。它的成本特性也完全一致：每多派一个专家，前面已产出的观察结果要再带一遍，所以计划不是越细越好，而是要用工具可见性收窄（每个专家只看到自己那 1–3 个工具）来避免「拆了但没拆开」。
  • 每一步都可验证：写操作要过 pydantic 入参校验 + 幂等键 + 人工确认；校验失败不炸图，错误作为工具结果写回 state。这正好补上了分解法最大的漏洞——子答案错误会污染后续步骤，而这里每一步的错误都会被记录下来、可以被后续节点看见。
  • 反射不等于重复推理：plan-v2 这一版计划提示词的核心改动就是把「先列步骤再执行」明确写进提示，而不是让模型边执行边想。这就是 Plan-and-Solve 与 ReAct 的取舍（下一节展开）。
  • 值得说的诚实结论：客服场景里最终答案不靠多数投票。因为写操作（下单、退款）是不可逆的，Self-Consistency 只能用在只读问答上，且我们走的是「温度低 + 校验重试」而不是 次采样——这解释了为什么项目里没有 Self-Consistency 的痕迹，而不是「忘了用」。

科研文献 RAG：这里能对上号的是两点，而且都能用实测数字讲：

  • LLM_TEMPERATURE = 0.1 这个值决定了Self-Consistency 在这个项目里不可用：温度低到接近贪心时， 次采样几乎退化成一次，投票没有多样性。所以「想提升准确率」的路径被限定为「改检索 + 改 prompt + 校验重试」，而不是「多采样投票」。这是「选了一个参数就关掉了一条优化路径」的真实例子，面试时讲它比讲「我知道 Self-Consistency」有说服力得多。
  • 拒答要模型自报 insufficient 这一设计，本质是「把不确定显式化」——和 Self-Consistency 里「票数没有共识就判为不确定」是同一条产品逻辑的两处实现：不确定就说不确定，不要硬给一个看起来像答案的东西。注意两者的实现层级不同：前者靠模型自报（要花钱、不完全可靠），后者靠程序统计（免费且确定），所以生产上更信程序侧那一层。
  • CoT 与结构化输出的冲突在这里是真实存在的：输出必须是 JSON，就没法让模型「在正文里长篇推理」。当时的处理是不要在拒答路径上开 CoT，因为拒答判定依赖的是检索证据是否充足，不是推理步数。

面试怎么问（≥3 组） ​

Q1：CoT 为什么能提升准确率？

A：因为自回归解码每生成一个 token 只做一次固定深度的前向计算。直接把答案压在一个 token 上，等于让所有推理挤在一步完成；写出中间步骤，模型就能把计算分摊到多个位置，后面的 token 在前面的中间结论条件下继续算。所以 CoT 提升的是可用计算量，不是模型知识。

追问：那它对什么任务没用？

A：两类。一类是单跳的事实抽取或格式转换，答案本来就在输入里，多写步骤只增加输出 token；另一类是模型已经内化了推理的场景——2025 年之后的推理模型本身就是先想再答，再叠一句「一步步想」通常没有增量。

追问：那你怎么判断该不该开？

A：分成两类错误来看。如果错误是「解法对了但算错了 / 漏了一步」，CoT 有戏；如果错误是「原文里就没有这个信息」或「字段名不对」，那 CoT 无效——前者要做 RAG，后者要做结构化输出。我会在固定评测集上跑开 / 关两档对比，而不是凭感觉开。

Q2：Self-Consistency 的代价和收益怎么算？

A：收益侧是在留出集上扫 的准确率曲线，通常在个位数处饱和——饱和点在哪儿是任务相关的，我不会背数字。代价侧是输入和输出 token 都按 倍计，所以只有离线批处理或对准确率极敏感的场景才划算；同步在线请求上它会直接把首字延迟和账单都乘 。

追问：那 份答案不一致的时候怎么办？

A：这本身就是信号。我会在投票前做归一化（15 m / 15米 / 15 是同一个答案），然后要求最高票严格多于第二名且票数 ≥ 2；如果 份答案两两不同，说明模型在这题上没有共识，我会判为「不确定」并降级——拒答或转人工，而不是硬取一个。

追问：温度对它有影响吗？

A：决定性影响。温度接近 0 时 次采样几乎退化成一次，投票没有多样性可言，收益接近 0 而成本是 倍。所以我们项目里生成温度是 0.1，等于放弃了 Self-Consistency 这条路，提升准确率只能靠改检索和改 prompt。这个取舍我会在面试里主动说，因为它同时解释了「为什么我没用」和「我知道它什么时候才有用」。

Q3：什么情况下你会把一个任务拆成多步？

A：三个信号：一是单次调用的推理链太长，中间容易漂移；二是每一步需要外部信息或工具，不拆就没法拿到；三是每一步需要被验证或留证据（写操作、引用、金额），拆开才可能逐步校验与局部重试。反过来的信号也很明确：如果任务是一跳的、或者拆开之后每步都不能独立验证，那分解只是把一次错误变成一串错误。

追问：拆成 workflow 还是交给 Agent 自己决定？

A：看拆法是否固定。固定拆法就写进编排里——可预测、可测、每次成本一样，还能把每步的超时和重试单独配；只有当下一步依赖上一步的内容、事先列不出完整步骤时才交给模型选。判断依据是「我能不能在写代码的时候把步骤列全」，而不是「Agent 听起来更先进」。

追问：分解的调用成本怎么估？

A：不是线性的。 个子问题里，第 个都要重复带上前面所有子答案，累计输入 token 大约按 增长。所以 一般控制在 2–5，再细就要问「多出来的这几步换到了什么」。这个估算我在 YYHelp 里是能对上号的：多派一个专家，就要多带一遍前面的观察结果。
