Prompt 版本化、A/B 与评测闭环 ​

覆盖知识点：L2-17 L2-18 ｜ 面试频率：高 ｜ 建议学时：7h

一句话说清 ​

这两节回答面试官唯一真正关心的问题：「你怎么知道这次改动让效果变好了？」 答案必须是一整套东西，而不是一句「我觉得更好了」：prompt 要可寻址（有版本号、能回滚），改动要可对照（一次只动一个变量、分流要粘性），结论要由评测集而不是手感给出（先确定性断言，再引入模型评判），而且prompt 版本号必须和模型版本号一起记录——否则模型升级和 prompt 改动混在一起，你的所有结论都是猜的。

为什么必须学 ​

  • 这是所有 prompt 技巧的前置条件。如果 prompt 不是「一个可寻址的字符串」，那么 Few-shot 示例选择、CoT、结构化输出 的所有优化都不可比较、不可回滚、也无法写进简历。
  • 面试官问「你怎么做 A/B」时，真正在测三件事：你有没有评测集、你知不知道混淆变量是什么、你有没有回滚预案。
  • 这是 L2 里最容易做过头的一节。真正的门槛不是统计学，而是纪律：一次只改一个变量、分流要粘性、先把评测集做小再做准。
  • 简历上能写的最强条目往往来自这里：「把 prompt 变更纳入固定评测集回归，某类错误从 X 降到 Y」——但只有你真有记录才敢写。

核心内容 ​

L2-17 Prompt 版本化与 A/B 管理 ​

  • 定义：把 prompt 当成有版本号的代码资产管理：入库、命名、记录变更原因、与评测报告关联、可单步回滚。A/B 则是把两个版本同时放给不同流量，用同一套指标比较。
  • 机制：最小可用的版本化方案不需要任何平台，只需要四条纪律：
    1. prompt 与代码分离：从代码里抽出来成独立资源（文件/表/配置），有稳定 ID（如 plan-v2）；
    2. 版本号单调递增，语义变更必须升版本：改一个词也算——因为改一个词就可能让结构化输出的字段名漂移；
    3. 请求日志里记录版本号（以及模型名/版本、温度等采样参数）：线上出问题时第一个要回答的就是「这是哪个版本、和昨天有什么不同」；
    4. 回滚是单步操作：把指针指回上一个版本，而不是「把代码改回去再发一次」。
  • 为什么这样设计：因为 prompt 的效果没有类型系统。它不会编译失败，只会静默地变差。唯一能替代编译器的东西就是「版本 + 评测 + 日志」这三件套。而 A/B 的存在是为了把「我觉得」换成「在固定评测集上通过了」——注意离线评测通常是第一道闸门，线上 A/B 是第二道，两者不要混。
  • 数量级与形状：
    • 一次 prompt 变更（文本改动，不含模型调用）的成本 ≈ 0；真正的成本在评测：评测集 条 × 每个候选版本一次执行 = 次调用。 时不明显， 时就要考虑只跑变化相关的子集。
    • 灰度比例通常从很小的流量起步（如几个百分点）再逐步放量。分流必须是粘性的（sticky）——同一个用户/会话必须落进同一组，否则用户体验会抖、指标也会被冲淡。常用做法是对稳定的业务键（会话 ID / 用户 ID）做哈希取模，不要用随机数。
    • 每个版本的观测样本次数决定结论可信度：两组差异越小时，需要的样本越多。样本不够时正确的结论是「不可比」，不是「B 更好」。
  • 常见误区：
    • 一次改多个变量：同时换 prompt、换模型、换温度，然后说「提升了」——这个结论无法归因，等于没做实验。这是最常见的错误。
    • 不粘性分流：同一用户在 A/B 之间跳来跳去。对多轮对话系统是灾难（上下文不一致），对指标是噪声。
    • prompt 里塞动态内容：把时间戳、随机 ID、未固定的检索结果顺序（字典序不定的工具列表、set 迭代顺序）写进 prompt，会让每次请求的前缀都不同——A/B 对照失效，而且直接破坏 Prompt 缓存。
    • 用线上指标证明一个离线就该证明的事：能从评测集回答的问题（字段是否齐全、引用是否越界）不该拿到线上烧流量。
    • 没有回滚演练：回滚路径从没跑过，等于没有回滚路径。
    • 不记录模型版本：只记 prompt 版本是不够的。模型侧也可能静默更新；prompt 版本 + 模型标识 + 采样参数才算一条完整的实验记录。
    • 把标注与口径当小事：评测集里的「标准答案」如果本身有争议，所有对比都在噪声上跑。口径必须先审后冻结，改动要留痕。
  • 代码（纯标准库，可运行）：提示词注册表 + 粘性分流 + 对照报告。
python
"""Prompt 注册表 + 粘性分流 + A/B 对照报告。纯标准库，可直接运行。"""
import hashlib
from dataclasses import dataclass, field


@dataclass(frozen=True)
class PromptVersion:
    pid: str                # 稳定 ID，如 "plan"
    version: str            # 语义变更必须递增
    text: str
    note: str = ""          # 改了什么、为什么改
    model: str = ""         # 必须与 prompt 版本一起记录
    temperature: float = 0.0


@dataclass
class Registry:
    versions: dict[str, PromptVersion] = field(default_factory=dict)
    active: dict[str, str] = field(default_factory=dict)   # pid -> version 指针

    def register(self, p: PromptVersion) -> None:
        key = f"{p.pid}@{p.version}"
        if key in self.versions:
            raise ValueError(f"版本已存在，语义变更请递增版本号：{key}")
        self.versions[key] = p

    def get(self, pid: str) -> PromptVersion:
        return self.versions[f"{pid}@{self.active[pid]}"]

    def rollback(self, pid: str, to_version: str) -> None:
        key = f"{pid}@{to_version}"
        if key not in self.versions:
            raise KeyError(f"无法回滚：{key} 未注册")
        self.active[pid] = to_version          # 单步回滚：只动指针


def sticky_bucket(business_key: str, salt: str, buckets: int = 100) -> int:
    """粘性分流：同一 business_key 永远落进同一桶。不要用随机数。"""
    h = hashlib.sha256(f"{salt}:{business_key}".encode()).hexdigest()
    return int(h[:8], 16) % buckets


def assign(group_ratio: float, business_key: str, salt: str) -> str:
    """group_ratio = 新版本拿到的流量比例（0~1）。"""
    cut = int(round(group_ratio * 100))
    return "B" if sticky_bucket(business_key, salt) < cut else "A"


def ab_report(rows: list[tuple[str, bool]], *, min_n: int = 30) -> str:
    """rows: [(组名, 该次请求是否通过)]。给"不可比"一个明确出口。"""
    stats = {}
    for g, ok in rows:
        n, k = stats.get(g, (0, 0))
        stats[g] = (n + 1, k + int(ok))
    lines = []
    for g in sorted(stats):
        n, k = stats[g]
        rate = k / n if n else 0.0
        lines.append(f"{g}: n={n:4d} 通过={k:4d} 通过率={rate:.1%}")
    small = [g for g in stats if stats[g][0] < min_n]
    if small:
        lines.append(f"⚠ 样本不足，结论不可比：{', '.join(small)}")
    return "\n".join(lines)


if __name__ == "__main__":
    reg = Registry()
    reg.register(PromptVersion("plan", "v1", "……先回答再列依据……", "初版", "demo-model"))
    reg.register(PromptVersion("plan", "v2", "……先列步骤再执行……", "改为先规划后执行",
                               "demo-model"))
    reg.active["plan"] = "v2"
    print(reg.get("plan").version, "→", reg.get("plan").note)
    print("sticky:", [assign(0.1, f"sess-{i}", "exp-1") for i in range(10)])
    print(ab_report([("A", True)] * 9 + [("A", False)] + [("B", True)] * 3))
    reg.rollback("plan", "v1")
    print("回滚后:", reg.get("plan").version)

L2-18 Prompt 评测与优化闭环 ​

  • 定义：用固定评测集驱动 prompt 迭代：假设 → 改一个变量 → 跑集 → 比对 → 入库或丢弃 → 记录。这是把「调 prompt」从手感变成工程流程的那一步。
  • 机制：闭环的四个组件缺一不可：
    • 评测集：从真实使用里收集，先做小而准再做多。起点可以很小（几十条），但必须包含回归样本（曾经出错、已修好的那几条）。合成测试集可以补覆盖，但要标注来源，不能拿它当真实分布。
    • 判分规则：优先确定性断言（字段齐全、编号在范围内、必须包含某段话、必须拒答的必须拒答），其次才是用模型当评判者。模型评判有已知偏差（偏爱冗长、偏爱先出现的答案），需要对齐与人工抽查校准。
    • 基线：每个指标都要有一个「上次定稿版本」的数字。没有基线的通过率只是一个不知道好坏的百分比。
    • 回归门禁：把可确定性断言的部分接进 CI，改动后自动跑，失败就挡在合并前。注意门禁只能测确定性断言——语义质量不适合做硬门禁。
  • 为什么这样设计：LLM 应用没有类型检查，评测集就是它的编译器。而且要接受一个现实：如果你的评测集噪声大于你要测的效果，你就测不出来——这时正确做法是增大样本或收紧判分规则，而不是宣布「效果有提升」。
  • 数量级与形状：
    • 迭代一轮的成本 ≈ 评测集条数 × 每个候选一次调用。把评测集控制在几百条以内，才能做到「改一次跑一次」。
    • 判分规则的确定性比例越高，回归越可靠。经验判据：能被程序判定的断言，不要交给模型判——又贵又不稳。
    • 一轮典型节奏：定义假设 → 改一处 → 跑集 → 看差异是否落在预期的那类错误上 → 记录数字 → 决定入库/丢弃。记录这一步不能省，它是下次判断的基线。
  • 常见误区：
    • 没有评测集就开始调：结果是「改了三版，不知道哪版好，只能凭感觉选一版」。
    • 只测规范路径：见 结构化输出 的退化式实验——只测最规范的输入，等于只测了不会出问题的路径。回归样本必须包含脏输出与边界输入。
    • 评测集与线上分布脱节：手工编的题偏简单、偏干净，结论不能外推。要让评测集有来源标注，并定期用线上抽样更新。
    • 一次改多处再跑一遍：无法归因，白跑。
    • 用模型评判者却不校准：判分者本身的偏差不会自己消失，需要人工抽查一批对齐，并固定判分用的版本与提示词。
    • 不区分「测不出」和「没提升」：这是最专业的一条。样本量和效应量的关系决定了结论的可比性；说不清就诚实说「这轮不可比」。
    • 忽略失败样本的价值：评测集里最有价值的是你曾经答错的那几条。要把它们钉进去当回归，而不是修完就删。
  • 可复用的迭代模板（面试可以直接讲）：
步骤动作产出
1写假设：我怀疑 X 类错误来自 Y 原因一句话假设
2改一个变量（只改一处 prompt 或只加一个示例）新版本号
3跑固定评测集，与基线对比指标差异
4看差异是否集中在预期的那类错误上归因判断
5入库（升版本 + 记变更原因 + 关联报告）或丢弃决定 + 记录
6若入库，接回归门禁；线上灰度按粘性分流门禁 + 灰度

  • 版本号已经在用：plan-v2、supervisor-core-v2 就是「prompt 当代码管」的直接证据。回答「你的 prompt 怎么管版本」时，直接说这两个名字 + 「语义变更递增、请求日志带版本号」即可，不需要编造平台。
  • 一次只改一个变量：plan-v2 这一版的改动方向是单一的——把「先列步骤再执行」显式写进计划提示词。这就是一次合格的对照实验设计：改动意图可以被一句话说清，跑评测时能直接看「长任务的目标漂移是否减少」。
  • A/B 与灰度的口径：分流基于会话/业务键做粘性划分，保证同一会话不会在两个版本间跳（多轮对话系统如果粘不住，用户会看到前后不一致的行为）。报告要处理「两组都对/都错」的情形——这类样本本身不携带区分信息，硬算进通过率只会稀释差异。相关记录见 /diagrams/yyhelp-ab-statistics。
  • 回归样本：把线上真实坏例钉回评测集，是「先做小而准」的具体执行。评测集设计有单独文档（项目里那份「评测集设计说明」），面试时可以说明出处。
  • 回滚纪律：prompt 版本是配置指针，回滚不需要重新发版——这是「可回滚」这条要求在工程上的落点。
  • 顺带说一条相关纪律：项目里存在「未声明模式」「范围与目录不一致」「无证据字段」这类合规检查项，它们本质上是同一件事的另一种表述——每一次改动都要能被追溯、能说清依据。

科研文献 RAG：这个项目的评测痕迹比较完整，是这一页最好的素材：

  • 固定评测集 + 机器报告：跑固定题集、产出机器可比的报告，并且会主动修正口径问题（例如召回指标的口径纠正），而不是把跑出来的数字直接当结论。这正是「口径必须先审后冻结」的执行。
  • 对照实验：项目里留下了大量的消融实验记录（切块参数、是否开某一路检索/语义处理等对照），命名上一眼能看出「一次只动一个变量」的对照结构。这是把 prompt/参数调优做成实验的标准形态。
  • 温度参数是全局常量：LLM_TEMPERATURE = 0.1 作为常量存在，意味着所有对照实验之间温度是固定的——排除了一个混淆变量。这一步很便宜，但很多人的实验没有做到。
  • prompt 版本号：生成阶段的提示词是用版本化的模板标识标识的，所以「这次下降是不是因为我改了提示词」这个问题在本项目里是可回答的；如果没有版本号，两次报告之间的差异将无法归因。
  • 还没做但可以补的：把「prompt 版本 → 评测报告」显式关联成一张表（现在更多是隐含在实验脚本命名里），以及把可确定性断言（字段齐全、引用编号范围、必须拒答的必须拒答）抽出来接进 CI 门禁。这两件事都是低成本、高说服力的补法，面试时可以作为「下一步计划」讲，但要明确说这是还没做的。

面试怎么问（≥3 组） ​

Q1：你怎么知道这次 prompt 改动让效果变好了？

A：三步。第一，改之前先写假设：哪类错误、来自什么原因；第二，一次只改这一个变量，跑固定评测集和上一版基线比；第三，看差异是否落在预期的那类错误上。如果落在，就升版本号入库并把变更原因和评测报告关联；如果不落在，我会把它当负结果记录下来，而不是留着碰运气。

追问：如果两组数字差了两个点，但样本只有二十条呢？

A：那我会明确说「不可比」，然后增大样本或收紧判分规则，而不是宣布提升。样本量不够时两个点的差异完全可能是噪声；把噪声当结论，后面所有基于它的决策都会歪。

追问：那如果评测集本身就不准呢？

A：所以评测集的口径要先审后冻结，改动留痕。我们项目里就遇到过口径本身有争议的情况（标注的标准答案需要复核），当时的处理是先把口径问题修正掉、把受影响的指标单独标注，再谈优化——不能在一个自己都不相信的标尺上做对比。

Q2：你怎么做 prompt 的 A/B？

A：先分清两件事：能离线回答的问题（字段是否齐全、引用是否越界、该拒答的有没有拒答）用固定评测集回答，不该烧线上流量；只有真正依赖用户行为的（语气接受度、任务完成率）才做线上 A/B。线上部分要求三点：粘性分流（按会话/用户键做哈希取模，绝不用随机数——多轮对话里跳组会让上下文不一致）、只动一个变量（prompt 版本 + 模型标识 + 采样参数一起记录）、有回滚预案。

追问：为什么强调粘性？

A：两个原因。用户体验上，同一会话在两版提示词之间跳会出现前后不一致的行为；统计上，不粘性会把对照组污染——同一用户同时贡献两组样本，差异被冲淡。实现上就是对稳定的业务键做哈希，而不是每次请求抽随机数。

追问：prompt 里有什么东西会破坏 A/B？

A：任何让请求前缀不稳定的东西：时间戳、随机 ID、未固定顺序的检索结果、用集合迭代顺序拼出来的工具列表。它就同时破坏两件事——A/B 对照和 Prompt 缓存。工具列表一旦定下来，顺序就该冻结。

Q3：你的评测集怎么建的？

A：从真实使用里收，先做小而准再做多。每一轮线上发现的坏例都钉回评测集当回归样本——最有价值的样本是你曾经答错的那几条。合成数据可以用来补覆盖，但要标注来源，不能当真实分布用。判分规则优先确定性断言，模型评判只用于无法程序化的部分，而且要先用人工抽查校准。

追问：为什么优先确定性断言？

A：三个原因：便宜、稳定、可做 CI 门禁。模型评判有已知偏差（偏爱冗长、偏爱靠前出现的答案），而且判分者自己也需要版本管理。所以我的顺序是：能用程序判的绝不交给模型；确实要模型判的，固定判分版本并定期和人工抽查对齐。

追问：门禁挡不住的那些问题怎么办？

A：门禁只放确定性断言，语义质量靠离线评测报告 + 灰度观测 + 人工抽查三件套，而不是硬塞进 CI。硬塞进去的结果是门禁变脆、大家开始习惯性跳过它——那比没有门禁更糟。
