向量索引、库选型与 Top-k ​

覆盖知识点：L3-12 L3-13 L3-14 L3-15 ｜ 面试频率：高 ｜ 建议学时：14h

一句话说清 ​

向量检索之所以快，是因为它主动放弃了「一定找到最近邻」这个保证，用近似（ANN）换速度；而选型的判据不是「哪个库更流行」，是「你的瓶颈在不在这一环」。

为什么必须学 ​

「向量检索为什么快、牺牲了什么」是这一层最高频的题，答不好会直接影响「你懂不懂自己在用什么」的判断。这一层的典型送分/送命题有四个：

  1. HNSW 是什么结构：答「一种图索引」是及格；能说出分层 + 贪心搜索 + M 与 ef 各控制什么才是过关。
  2. M 和 efConstruction 取多少：这一题故意不给标准答案——面试官想听的是「参数与召回率/内存/构建时间的关系，以及必须在自己数据上扫参」，而不是背一个数字。
  3. 向量库怎么选：从 Chroma 到 Milvus，答「Milvus 性能最好」会被追问到「你的数据量多大、要不要分布式」。
  4. top_k 取多少、要不要设阈值：这是成本与噪声的直接开关，也是与拒答机制耦合的地方。

核心内容 ​

L3-12 向量数据库与索引基础 ​

定义：ANN（Approximate Nearest Neighbor，近似最近邻）索引是一类用一点召回损失换几个数量级速度的数据结构。

机制：三类主流算法，各自用不同的方式压缩搜索空间。

索引结构搜索方式主要代价什么时候用它
Flat（暴力）不做索引，全量算距离精确复杂度 ，与 线性数据量小（十万级以内）或召回不能丢时
HNSW（Hierarchical Navigable Small World）多层近邻图，上层稀疏、下层稠密从顶层入口贪心向下，逐层逼近内存占用最高（要存图）、构建慢要求低延迟 + 高召回，且内存够
IVF（Inverted File）先聚类成若干桶（），查询只扫一部分桶只搜最近的 个桶边界样本可能永远搜不到（漏召回）数据量大、内存受限、可接受少量漏召回
PQ / SQ（Product / Scalar Quantization）把向量压缩成更短的编码在压缩空间算距离（常用作 IVF 的搭档）精度损失内存/存储是硬约束时

为什么这样设计：所有 ANN 都建立在同一个交易上——「可能不是最近邻」换「快很多」。所以每个 ANN 参数（nprobe、ef）本质上都是召回-延迟旋钮：拧大一点更准更慢，拧小一点更快更漏。

数量级与形状：Flat 的代价与 成正比——在十万块量级上它可能仍是毫秒级，这正是「不要无脑换 ANN」的依据。HNSW 的内存除向量本体外还要存图结构（每个节点存约 条邻居，多层叠加），所以内存开销通常显著高于向量本体。

常见误区：

  • 「向量检索是精确的」——默认不是。用 ANN 就有近似误差，而且要主动测它（用 Flat 的结果当参照）。
  • 「HNSW 一定比 IVF 好」——HNSW 召回与延迟通常更优，代价是内存与构建时间；内存紧张时 IVF + 量化更现实。
  • 「索引建好了就不用管」——增量写入、删除、segment 合并都会影响索引形态与延迟表现。

L3-13 向量库选型与工程落地 ​

定义：向量数据库 = ANN 索引 + 元数据过滤 + 持久化 + 并发与一致性管理。

机制：按「部署形态」分三档，选型先看这一条轴。

档代表特点适合
内嵌 / 单机轻量FAISS（库，非服务）、Chroma零运维、进程内、随应用部署单机 demo、离线实验、语料在十万块以内
单机服务化Qdrant、Milvus 单机/轻量部署有 HTTP/gRPC 接口、过滤、持久化单机生产、需要并发与运维接口
分布式Milvus 集群分片、副本、水平扩展亿级向量、多租户、高可用要求

为什么这样设计：库与服务的分界在「谁负责并发、持久化、过滤下推」。FAISS 是一个索引库：它给你最快的最近邻，但不管持久化、不管并发、不管元数据过滤——过滤要你自己在候选上做。而 Milvus/Qdrant 这类服务把「元数据过滤 + 向量检索」放进同一个查询计划，这是能不能做权限隔离（L3-26）的关键差别。

数量级与形状：一个朴素但有用的判据——先算你的向量占多少内存/磁盘： 每维字节数。5325 块 × 1024 维 × 4 字节 ≈ 22 MB，这种规模下任何库都快，选型应该按「运维成本、过滤能力、生态」来定，而不是按性能。

常见误区：

  • 「直接上分布式」——在十万块量级上上集群，是给自己加运维工作量，而且不会让端到端变快（瓶颈通常不在这）。
  • 「过滤就是检索完再筛」——过滤放在检索之后有两个问题：过滤后可能不足 条（要迭代补偿），以及无法在检索期做权限隔离（未被授权的数据仍然被算进候选）。
  • 参数与 API 名必须查官方文档：各家对「集合/表」「分区」「度量类型」「索引参数」的命名都不同，本页一律不写具体参数名，请以你所选库的官方文档为准。

L3-14 向量索引优化 ​

定义：在既定索引上，通过参数、量化、分片、副本把「召回-延迟-内存」调到可接受。

机制：nprobe / ef 是查询期参数（在线可调、随请求变化），nlist / M / efConstruction 是构建期参数（改了要重建）。这个区分很重要：查询期参数可以用来做延迟兜底，构建期参数只能离线调。

想要手段副作用
召回更高调大查询期参数（nprobe / ef）延迟上升
延迟更低调小查询期参数；加副本分摊召回下降 / 成本上升
内存更省量化（PQ / SQ）、降维精度损失
吞吐更高分片 + 副本运维复杂度、跨分片结果要合并

为什么这样设计：因为这三个指标是三角关系，不可能同时最优。所谓「索引优化」不是找一组神奇参数，而是先确定哪个指标是硬约束（通常是 P95 延迟），再在这个约束下把召回做到最好。

数量级与形状：调参必须有基线。做法是：拿一批真实查询，用 Flat（精确）结果当参考，量 ANN 的 Recall@k；然后扫参数画「召回-延迟」曲线，选曲线拐点。没有基线就没法说「我的召回是 95%」——你不知道 100% 长什么样。

常见误区：

  • 「照抄别人的参数」——参数与数据分布、维度、 强耦合，抄来的数字只是别人的解。
  • 「只测延迟不测召回」——加速一个漏召回的索引等于把效果换成了速度，而这笔交易你没记在账上。
  • 「不改动就无法优化」——很多时候真正的优化是减少检索量：缩小候选集（更好的切块）、减少路数、把精排候选从 20 降到 10。先看总量，再看单次成本。

L3-15 相似度检索 Top-k 与阈值 ​

定义：top_k 决定「取回多少条候选」；阈值决定「低于某个分数就丢掉（或直接拒答）」。

机制：top_k 影响链条上的三个位置，必须分开设：

位置作用设太小设太大
召回深度（每路 top-k）给融合/精排的原料精排无米可炊（好块没被召回）融合与精排成本上升
融合后保留数融合结果的截断融合的优势没体现噪声进入精排
最终进上下文数直接决定 prompt 的 token 数与信噪比证据不足噪声挤占预算、模型更容易看错

为什么这样设计：召回深度和进上下文条数是两个不同的参数，很多实现把它们混成一个。正确做法是让召回宽、进上下文窄——宽度是精排的输入，窄度是生成的质量。典型形态是「每路召回几十条 → 精排 → 只留个位数进 prompt」。

数量级与形状：进上下文的条数受上下文预算约束：块长 × 条数要留出空间给系统提示词与历史对话。先算预算，再定条数，不要反过来。

常见误区：

  • 「取越多越好」——上下文里塞入不相关块会降低答案质量（噪声干扰），而且成本线性上升。
  • 「阈值可以直接跨实现复用」——绝对不能。分数的可比范围完全取决于返回路径：Cross-Encoder 精排分数（0–1）、余弦相似度、内积、RRF 融合分是四种不可比的量纲。拿 A 的阈值去比 B 的分数是常见事故。
  • 「把 Recall@10 == Recall@5 当排序质量好的证据」——这可能是构造性结果：如果候选窗口本身只到 5，那两个指标当然相等。要检查 gt 的构造方式。

和你自己的项目对上号 ​

这一页你的项目有一个反直觉但极其有说服力的结论：你主动选择了不上 ANN。

  • 当前索引：FAISS 的 IndexFlatIP（精确内积搜索），向量是 1024 维、已归一化，所以内积等价余弦（docs/projects/rag/04-retrieval.md:32-37）。
  • 判据是延迟实测，不是分数（_research/RAG-事实清单.md:319、exp31_index_scaling.py）：CPU 精排 20 对约 8.5 秒，而 Flat 搜索在 52 万块量级上仍是毫秒级。结论是「在本项目链路上向量搜索根本不是瓶颈，换 ANN 只会白丢召回」。这句话可以直接背下来——它把「为什么不用 HNSW」这个问题从「我不懂」翻转成「我量过」。
  • 一次问答的延迟分解：首字延迟 ≈ 检索耗时（14.90 / 10.00 / 14.86 s），LLM 生成 P50 只有 1.26 s。也就是说整个系统的瓶颈在检索侧，而检索侧里最贵的是精排，不是向量搜索。真正的优化方向是精排侧（缩小候选、换硬件、批量化），不是换索引。
  • 三段 top-k 确实是分开设的（config.py:163-167）：DENSE_TOP_K = 20（:163）、SPARSE_TOP_K = 20（:164）、FUSED_TOP_K = 20（:166）、RERANK_TOP_N = 5（:167）——召回宽（20+20）、进上下文窄（5），正是本页讲的形态。
  • Recall@10 == Recall@5 的构造性陷阱（一定要讲，这是最容易露怯也最容易加分的一题）：主报告里 ①②③ 三组的 Recall@10 与 Recall@5 都成对相等，看起来「排序质量极好」。根因是标注窗口：机器 gt 的候选只取了 retrieve()[:5]、人工标注也只看前 5 个，所以 gt 只可能落在前 5 里——Recall@10 的上限被构造方式锁死在 Recall@5 上。按项目页的记录，修正标注窗口后暴露出现象：不做精排时 R@10 比 R@5 高 11–14 个百分点（具体数值以项目页为准）。正确说法是：「这两个指标相等不是我的排序好，是我的评测只看了前 5 个。」
  • 阈值这件事在本项目有明确前提：REFUSE_THRESHOLD = 0.30（config.py:170）只对精排分数成立；无精排时返回的是 RRF 融合分，实测区间约 0.016–0.033，拿它比 0.30 会让每一道题都被拒答。所以代码里的判据是 use_rerank and t1 < threshold（docs/projects/rag/07-guardrails.md:59-74）。

面试怎么问 ​

Q1：向量检索为什么快？牺牲了什么？

A（要点）：因为它用近似换速度——ANN 索引主动放弃「保证找到最近邻」，只保证「大概率找到」。不同索引换法不同：HNSW 用多层图把搜索空间逐层收窄；IVF 用聚类只扫最近的几个桶；量化把向量压短。加分句：所以我从不声称「召回率 100%」——ANN 的召回必须以 Flat 精确结果当参照量出来，而且要用自己的数据扫参数。别说：「向量检索是精确的，只是做了优化」——这句话等于承认你没读过索引原理。

  • 追问 1：那你怎么知道我的 ANN 召回够不够？→ 拿一批真实查询，用 Flat 的结果当基线，量 ANN 的 Recall@k；再扫查询期参数（ef / nprobe）画「召回-延迟」曲线，取拐点。没有基线就没法谈召回率。
  • 追问 2：M 和 efConstruction 你取多少？→ 我不会给一个数字，因为这两个参数与数据分布、维度、 强耦合；它们都是构建期参数，改了要重建索引。我的做法是固定其他变量扫参，看在给定内存与构建时间约束下的召回曲线。给数字的人往往没扫过参。

Q2：为什么用（或不用）某个向量库？

A（要点）：先给选型轴——部署形态（内嵌 / 单机服务 / 分布式）、过滤能力（能否把元数据过滤下推到检索期）、生态与运维成本；再给自己的答案，并说清针对的量级。加分句：我的语料是 55 篇 / 5325 块、1024 维，向量本体只有约 22 MB——这个规模下任何库都快，所以我的选型理由是「离线实验要零运维 + 检索期能按元数据过滤」，而不是性能。别说：「Milvus 是工业级所以选它」——数据量撑不起这个选择时，这句话会暴露你在照抄别人的架构。

  • 追问 1：如果用分布式集群，你会怎么切？→ 按「数据规模 × 增长速率」定分片，按 QPS 与延迟目标定副本；但我会先算是否真的需要，因为分布式带来的运维成本可能远大于它省下的延迟。
  • 追问 2：元数据过滤你放在哪一步？→ 我要求下推到检索期。放在检索之后筛选有两个问题：一是过滤后可能不足 条、要迭代补偿；二是未被授权的数据仍然进了候选集，这在多租户场景里是不可接受的。

Q3：top_k 取多少？要不要设相似度阈值？

A（要点）：分开说三个位置——每路召回深度、融合后保留数、最终进上下文数；给形态（召回宽、进上下文窄），再给自己的值（20 / 20 / 20 → 精排 5）。加分句：我从不跨路径复用阈值，因为分数的量纲取决于返回路径——精排分数可以做阈值，RRF 融合分不行（区间差一个数量级）。别说：「阈值 0.7 比较通用」——这句话会被立刻追问「哪个分数？什么量纲？」。

  • 追问 1：你的 Recall@10 和 Recall@5 一样，这说明什么？→ 说明我的评测窗口只到 5，不说明排序好。机器 gt 的候选只取了 retrieve()[:5]，人工标注也只看前 5 个，所以 gt 不可能落在第 6–10 位，两个指标被构造方式锁死成相等。修正标注窗口后，不做精排时 R@10 比 R@5 高出 11–14 个百分点。这是一个我自己抓出来的评测缺陷，不是效果数据。
  • 追问 2：那你怎么防止这类缺陷？→ 两条纪律：① 指标的口径必须和 gt 的构造方式一起报（gt 版本 + 密度「块/题」）；② 报告里「不适用」和「0」必须区分——把不适用渲染成 0.0% 会让读者以为「测过了，是 0」。
