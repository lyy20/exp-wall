Rerank、查询改写与多跳检索 ​

覆盖知识点：L3-18 L3-19 L3-20 L3-21 ｜ 面试频率：高 ｜ 建议学时：14h

一句话说清 ​

Rerank 是用延迟换排序质量（拿 Cross-Encoder 精算候选），查询改写是把用户的说法改成文档的说法（拿一次 LLM 调用换召回），多跳是承认一次检索不够（拿多轮往返换复杂问题的可答性）。三件事都在做同一件事：缩小「用户问法」与「文档写法」之间的距离。

为什么必须学 ​

「Rerank」是 AI 岗位 JD 里出现频率最高的检索类关键词之一，也是面试里最容易分辨「真做过」与「见过」的一题：

  • 问 「双塔和交叉编码器有什么区别」，答不出「一个不交互可预计算、一个交互不可预计算」，说明你只知道有这个东西。
  • 问 「精排为什么比向量检索准」，能答出「查询与文档拼接后做注意力交互」才是过关。
  • 问 「你精排一次要多久」，能给出真实数字并说清瓶颈在哪的人，通常真的跑过；而答「很快」的人会在这里露怯——精排往往是整条链路里最贵的一步。

查询改写这一组则是区分「会用框架」和「会做产品」的分水岭：HyDE、多查询、路由都是以额外 LLM 调用为代价换召回的，能不能说清「什么时候值得付这个代价」才是重点。

核心内容 ​

L3-18 Rerank 与 Cross-Encoder 重排 ​

定义：Rerank（重排）是对粗召回的候选集做一次更精确的相关性排序，核心实现是 Cross-Encoder（交叉编码器）。

机制：三种编码器范式的关键差别在查询与文档在什么时候交互：

范式结构查询-文档交互能否预计算文档向量成本
双塔 / Bi-Encoder查询与文档各自编码无（只在最后算相似度）能极低（一次向量检索）
Cross-Encoder查询与文档拼接成一个输入过模型每一层都有注意力交互不能高：每个（查询，文档）对都要前向一次
Late Interaction（如 ColBERT 思路）两塔分别编码，但保留 token 级向量再做细粒度匹配延迟到检索时做 token 级 max-sim能（但要存 token 级向量，空间大）中

为什么这样设计：因为交互与可预计算是互斥的——一旦让查询参与文档的编码，文档向量就不能提前算好。所以工程上的分工是两级漏斗：双塔从百万级捞几十条（召回），Cross-Encoder 从几十条里排前几条（精度）。Cross-Encoder 不可能用于全库检索，这一点必须能一口说清。

数量级与形状：Cross-Encoder 的调用次数 = 候选数。这是它成本的本质：候选从 20 提到 100，精排耗时大致线性涨 5 倍。所以精排前的候选数与精排后的条数是两个必须分开的旋钮。

常见误区：

  • 「用 Cross-Encoder 直接检索」——不可能，除非库只有几百条。
  • 「精排分数可以直接和向量分数比」——量纲不同。精排分数是模型在「查询+文档」拼接输入上输出的相关性分，可能是概率也可能是 logits（必须先判定：出现明显负数或 > 1 说明是 logits，需要先做 sigmoid 之类的换算才能当概率用），绝不等同于余弦相似度。
  • 「精排一定能提升」——它提升的是排序，不是召回。答案压根没被召回时，精排无能为力。

L3-19 查询改写与扩展（Query Rewriting / HyDE） ​

定义：在检索前用 LLM 改造查询，让它更接近文档的写法。三种典型做法：

做法做什么适合解决
改写（Rewrite）去掉口语化与寒暄、补全指代（把「它」补成上一轮提到的实体）、扩写缩写多轮对话里指代不清的查询
扩展（Expansion）加同义词、领域术语、上下位词用户用词与文档用词不一致
HyDE（Hypothetical Document Embeddings）先让 LLM 编一段假设性答案，用这段假设答案去检索，而不是用原问题检索问题很短、文档很长时的语义鸿沟

HyDE 的机制要说清：它的假设是「答案的措辞比问题的措辞更接近文档」。原问题「怎么处理非平稳性」和论文里的「non-stationary environment 的处理方式」共享词很少；而一段由模型生成的假设答案会自动带上「non-stationary」「训练分布漂移」这类更接近论文用语的词，于是检索更准。代价是多一次 LLM 调用，而且假设答案是可能错的——它只是用作查询的语义代理，不能当成事实。

为什么这样设计：因为检索的失败模式里有一大类叫「词汇鸿沟」（vocabulary mismatch）——用户说的是 A，文档写的是 B，语义相同但字面不同。这类问题靠更好的 Embedding 只能缓解一部分，靠在检索前把 A 翻译成 B 的措辞才更直接。

数量级与形状：每次改写 = 一次额外的 LLM 调用（延迟典型在秒级，与生成同类）。所以改写的开关必须能按场景关掉：简单直白的查询改写只会增加延迟。

常见误区：

  • 「改写一定要开」——它是一笔交易：多一次调用换召回。简单查询上纯亏。
  • 「HyDE 的假设答案要保存起来给用户看」——它在链路里的定位只是检索用的代理，不是答案。
  • 「改写会把查询变精确」——改写也可能引入偏移（把用户的意图改错）。所以要求：改写后的查询要能回到原文验证（日志里留原始查询与改写后查询，便于归因）。

L3-20 查询重构与分发（多查询 / 路由） ​

定义：

  • 多查询（Multi-Query）：把一个问题拆成多个子查询并行检索，再把结果合并去重。适合复合问题（问句里包含两个独立子问题）。
  • 路由（Routing）：先判断问题该去哪个数据源/哪条链路（如「结构化数据问答」vs「文档问答」vs「闲聊」），再执行对应路径。

机制：两者都建立在「一次查询不可能对所有问题都合适」这个判断上。多查询用召回并集提高覆盖；路由用分类降低无效检索与成本。

为什么这样设计：因为真实系统往往有多个知识源（文档库、数据库、FAQ、API），把所有问题都往向量库里塞是最贵的做法——有些问题该走 SQL（L3-22），有些根本不该检索。

数量级与形状：多查询的检索次数 = 子查询数，延迟和成本按倍数上涨（并行的前提下延迟增幅较小、成本照涨）。路由的收益是省掉不该走的路径，代价是路由错了就全错——所以路由必须可观测、可回退（记录路由决策与置信度）。

常见误区：

  • 「多查询就是多写几个 prompt」——还要处理去重与融合：同一块可能被多个子查询命中，必须按 ID 去重并决定合并后的排序（通常仍用 RRF，见 ⑥ 稀疏检索与混合融合）。
  • 「路由可以用小模型省钱」——可以，但要测量路由准确率并设兜底（不确定时走默认路径），否则一次误路由会让整个回答错。
  • 「拆得越细越好」——子查询过多会带来大量低质量候选，反而稀释上下文。

L3-21 多跳检索与迭代检索 ​

定义：一次检索不足以回答问题，需要用中间结果驱动下一轮检索。

形态机制典型场景
多跳（multi-hop）第一跳找到实体 A，第二跳用 A 去找与 A 有关的信息「X 这篇论文的方法被谁改进过」
迭代检索（iterative）每轮判断「当前证据够不够」，不够就生成新的子查询继续检索需要逐步收敛的问题
IRCoT 式（检索与推理交替）检索一段 → 推理一步 → 再检索，交替进行需要链式推理的问题

为什么这样设计：有些问题的答案不在任何单个块里——它需要把 A 块的实体拿去 B 块里找。这类问题靠「扩大 top_k」解决不了（因为第二跳的查询词在第一跳里根本不存在），只能靠多轮。

数量级与形状：轮数 × 每轮检索成本 = 总成本，而且是指数级的风险（每轮都可能引入错误，错误会传播）。所以必须设停止条件：最大轮数、证据是否已充分、以及预算上限（见 L4 · Agent 的终止条件设计）。

常见误区：

  • 「多跳就是多检索几次」——关键是中间结果的表述：把上一步的答案原文喂给下一轮，还是提炼成查询词，效果差别很大。
  • 「轮数越多越好」——轮数增加会带来错误传播与延迟叠加，必须有停止条件与预算。
  • 「多跳只影响效果，不影响体验」——每轮都是一次完整检索（可能含精排），在精排昂贵的系统里（比如本项目单次约 8.5 秒），多跳会直接把延迟推高一个量级。

和你自己的项目对上号 ​

1）精排是本项目「最贵也最值」的一步（docs/projects/rag/05-rerank.md:29-40）：

  • 模型 RERANK_MODEL = "BAAI/bge-reranker-v2-m3"（Cross-Encoder，config.py:153），CrossEncoder(RERANK_MODEL, max_length=512) 懒加载（retrieve.py:112-118）。
  • 调用形态：pairs = [(query, h.chunk.text)] → reranker.predict(pairs) → 按分数倒序取 top_n（retrieve.py:242-249）。
  • 耗时：单次约 8.5 秒（20 对，CPU）。这个数字的来历很朴素：30 道题的评测多花了 4 分钟，折算每题约 8 秒。它直接催生了一个接口设计——answer_question(..., hits=...) 允许把已精排好的结果传进来，避免对同一批 hits 重复精排。
  • 它值不值：加精排前后 ③ 组 R@5 71.8% vs ② 组 59.1%（差 12.7 个百分点），MRR 从 0.502 提到 0.714；而 LLM 生成只要 1.26 秒（P50）。用 8.5 秒换 12.7 个点的召回，在离线评测口径下划算，在交互口径下不划算——这个冲突本身就是很好的面试素材。

2）延迟账要把瓶颈指准（docs/projects/rag/05-rerank.md:89-108）：

阶段P50P90P99
检索（dense + BM25 + RRF + 精排）14.47 s18.44 s30.74 s
LLM 生成1.26 s1.87 s2.82 s
端到端15.66 s19.58 s32.26 s
冷启动67.3 s——

检索占端到端约 92%，LLM 只占约 8%。流式首字延迟 ≈ 检索耗时（TTFT 14.90 / 10.00 / 14.86 s）——用户在流式界面前十几秒什么都看不到，因为此时还没调用 LLM，还在精排。所以「优化 LLM」是错误方向；正确方向按收益排序是：① 让精排快起来（GPU / ONNX 量化 / 批处理 / 更小的 reranker）；② 让用户更早看到东西（先返回来源列表再流式出答案）；③ 才轮到 LLM。但要诚实：这两条优化本项目都没有做——事实清单里没有对应的实测数字。「我知道瓶颈在哪、该往哪修，但没修」，比编一个优化后的数字安全得多。

3）精排分数的两个语义陷阱（docs/projects/rag/05-rerank.md:67-87）：① 先用判据确定分数性质——出现明显负数或 > 1 说明是 logits，阈值必须重新换算（exp06 里给了 sigmoid 换算）；全部落在 [0,1] 且分布分散才是概率，0.30 的语义才成立。② 只有 Cross-Encoder 的分数能做拒答阈值——use_rerank=False 时返回的是 RRF 融合分（约 0.016–0.033），拿它比 0.30 会让每道题都被拒答。

4）上下文组装的两个设计点也是被实测逼出来的（generate.py:84-119 build_context()）：① 来源必须用论文标题，不能用文件名——早期写「来源：SCIS 第 15 页」，模型无从知道 SCIS 就是那篇论文，在「不得猜测」的约束下倾向拒答（这属于上下文写法问题，不是模型能力问题）；② 标题只声明一次，不要每块重复——标题约 140 字符 × 5 块 = 700 字符，约占上下文 17%，且同一长串重复 5 遍会稀释注意力。最终形态是「开头一次文献图例 [A] {title}，每块头部 [序号] 文献[A]｜第 N 页[｜章节]」。

5）本项目的诚实边界：查询改写（含 HyDE）、多查询、路由、多跳这几件事，项目里都没有做——你不会在事实清单里找到它们的实测数字。面试时不要声称做过。可以这么讲：我的查询侧目前只有 glossary.py 的 57 条术语表扩展（只作用于稀疏路，不加延迟）；改写与多跳是下一步要按收益排期的方向，而它们的共同代价是额外 LLM 调用，在检索已经占 92% 延迟的现状下，我会先把精排变快再谈改写。这个答复比编一个 HyDE 实验更有说服力。

面试怎么问 ​

Q1：Rerank 为什么有效？和向量检索有什么区别？

A（要点）：因为交互时机不同。双塔的查询与文档互不交互，相似度只在最后算一次，所以文档向量能离线预计算——这是它能扫百万级的根本原因；Cross-Encoder 把查询与文档拼成一个输入过模型，每一层都在做注意力交互，判断准得多，但每个（查询，文档）对都要前向一次，无法预计算。加分句：所以工程上是两级漏斗——双塔从百万级捞几十条，Cross-Encoder 从几十条里排前几条；Cross-Encoder 不可能用于全库检索。 别说：「精排就是再算一遍相似度」——它不是算相似度，是让两个序列互相看。

  • 追问 1：精排的代价你测过吗？→ 测过。单次约 8.5 秒（20 对，CPU），这个数来自「30 道题评测多花 4 分钟」的折算。它值不值要分口径看：离线评测口径下，它把 R@5 从 59.1% 提到 71.8%、MRR 从 0.502 提到 0.714，很值；交互口径下不划算——因为检索占了端到端延迟的约 92%，而 LLM 生成只有 1.26 秒。
  • 追问 2：那你怎么优化它？→ 方向按收益排：上 GPU 或做 ONNX/量化、批处理、换更小的 reranker；产品层可以让用户先看到来源列表再流式出答案（把等待变可见）。但我必须诚实说：这两条我都还没做，我没有优化后的数字。

Q2：你的精排分数能当拒答阈值用吗？

A（要点）：先判定分数性质，再决定阈值。两条判据：出现明显负数或 > 1 就是 logits，阈值必须重新换算（sigmoid 之类）；全部落在 [0,1] 且分布分散才是概率，概率上谈阈值才有意义。加分句：而且只有 Cross-Encoder 的分数能做阈值——无精排时返回的是 RRF 融合分（实测区间约 0.016–0.033），拿它比 0.30 会让每一道题都被拒答。所以我的评测脚本判据是 use_rerank and t1 < threshold，那两组的拒答列渲染成「不适用」，不是 0。别说：「分数当然是概率」——这句话就是「全部拒答」或「全部通过」的来源。

  • 追问 1：那你怎么标定 0.30？→ 阈值扫描（区间 [0.05, 0.6]）+ 看两类分数的分布重叠程度。精排组上可回答题 top1 中位数 0.9617 vs 不可回答 0.0127，差近 76 倍；但要知道两类区间仍有重叠（可回答最小值 0.0411 落在不可回答最大值 0.2502 之下），所以准确说法是「可分的是分布，不是每一个样本」。
  • 追问 2：不可回答的样本有多少？→ 只有 6 道。所以基于它算的比率分母很小，说 100% 的时候必须带上这个前提。这一点我会主动说，因为不说就会被问到。

Q3：用户的口语化问题和文档写法不一致，你怎么解决？

A（要点）：分三层——改查询（改写/扩展/HyDE）、多路召回（稠密 + 稀疏互补）、改排序（精排）。然后指出三者代价不同：改查询要一次额外 LLM 调用，多路召回要维护两套索引，精排要付延迟。加分句：HyDE 的机制是「答案的措辞比问题的措辞更接近文档」——先让模型写一段假设答案，用假设答案去检索，它自动带上更接近文档的用词；但假设答案可能错，它只是查询的语义代理，不能当事实。别说：「我用了 HyDE 和 multi-query」（项目里没有），这是在给自己埋雷。

  • 追问 1：那你项目里是怎么处理词汇鸿沟的？→ 我目前只有一层：glossary.py 的 57 条中文→英文术语表，把中文查询里的领域词映射成英文词，只作用于 BM25 路、不增加精排候选所以不加延迟。它的增益是 ② 组 R@5 62.3% → 64.5%、R@10 66.7% → 73.2%。我把它明确标成领域补丁：换语料就失效、要人工维护、映射错了会引入噪声。
  • 追问 2：那更通用的做法是什么？→ 我的 exp35 五路对照给了最干净的答案：原始 BM25 的 R@5 只有 8.3%，加术语表到 29.2%，而先把查询翻译成英文再检索能到 70.8%。结论是：不要用 BM25 做跨语种召回，跨语种需要语义桥——要么翻译查询，要么训一个跨语言稀疏模型。我会把「查询翻译」排在术语表之后做，因为它比维护一张人工术语表更通用。

Q4：什么情况下需要多跳检索？

A（要点）：当答案不在任何单个块里，需要「先找到实体 A，再用 A 去查」时。这类问题扩大 top_k 解决不了——因为第二跳的查询词在第一跳里压根不存在。加分句：多跳的代价是轮数 × 每轮检索成本，而且有错误传播风险，所以必须有停止条件（最大轮数、证据是否充分、预算上限）。在精排昂贵的系统里（我这边单次约 8.5 秒），多跳会把延迟直接推高一个量级。别说：「多跳检索就是多查几次」——关键是中间结果的表述方式（原文 vs 提炼成查询词），效果差别很大。

  • 追问 1：那你项目里有多跳吗？→ 没有。我有一道题（U07）因为语料变化从「不可回答」变成了「多跳题」，并据此调整了负样本集（7 道 → 6 道），但链路本身没有多跳能力。这是我知道的缺口，不是完成的功能。
  • 追问 2：如果要做，你会怎么开始？→ 先补评测：把标注集里需要多跳的题单独标出来（现在没有这一列），否则做完无法判断有没有变好；然后做最简的一版——用第一跳 top-1 的实体名重新组织查询，设最大 2 跳与超时上限；最后看它在这组题上的 Recall 与整体延迟的代价。
