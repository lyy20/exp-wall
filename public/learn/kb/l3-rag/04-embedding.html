Embedding 原理、选型与微调 ​

覆盖知识点：L3-08 L3-09 L3-10 L3-11 ｜ 面试频率：高 ｜ 建议学时：14h

一句话说清 ​

Embedding 把文本映射到语义向量空间，让「找相关内容」变成「找最近邻」；选型与归一化决定这个空间的几何形状，而没有在你自己语料上量过的模型都是赌。

为什么必须学 ​

这一层是检索质量的地基，也是技术面最容易挖穿的浅坑：

  • 问「为什么选 bge-m3」，只想听「中文效果好」的人，会被追问到「你的语料里英文占多少、你比过哪个模型、用什么指标比的」。
  • 问「余弦和内积有什么区别」，答「差不多」的人会被接着问「那为什么要归一化」「归一化之后欧氏距离和余弦是什么关系」——这是公式级的送分题，答不出来会被判成「只会调库」。
  • 问「Embedding 能不能微调」，答「能，用对比学习」是及格线；能说出正负样本怎么来、hard negative 从哪挖、用什么指标判定微调有效才是加分项。

核心内容 ​

L3-08 Embedding 模型原理与选型 ​

定义：Embedding 模型是一个把变长文本映射成定长向量的编码器 ，训练目标是让语义相近的文本向量在空间中距离近、不相近的远。

机制：主流是双塔（bi-encoder / dual-encoder） + 对比学习（contrastive learning）。关键点是查询与文档各走一个编码器（实践中常共享参数、分开编码），二者互不交互，因此文档向量可以离线预计算并在库里存好——这是它能支撑百万级检索的根本原因。

训练信号是（查询，正例文档，负例文档）三元组，损失函数（InfoNCE 形式的对比损失）大致是：

其中 是温度系数。注意这个式子的形状：分子是正例相似度，分母是「正例 + 所有负例」。所以负例的数量与质量直接决定模型学到多细的区分度——这也是后面 L3-11 微调时最费工的部分。

为什么这样设计：不做交互是为了可缓存。如果让查询与文档做交叉注意力（cross-encoder），精度更高但每个文档都要和查询重算一遍，无法预计算，只能用于对少量候选做精排（见 ⑦ Rerank 与查询改写）。这就是「双塔 / 交叉编码器」的分工：双塔负责从百万级里捞出几十条，交叉编码器负责从几十条里排出前几条。

数量级与形状：文本（ 个 token）→ 向量（ 维，常见 384 / 768 / 1024 / 1536）。工程上通常做池化（取 [CLS] 位或对 token 向量做平均）再归一化。一个 5325 块的库在 1024 维 float32 下，向量本体约 字节 ≈ 22 MB——这个量级下「换更省空间的模型」不是优先事项，效果和延迟才是。

常见误区：

  • 「Embedding 是通用的，换哪个都差不多」——不同模型在同一语料上的排序差异可以很大，领域与语言是两个主要变量。
  • 「维度越高越好」——维度高通常表达能力更强，但存储与检索开销同步上升；而且高维在小语料上不一定带来收益。
  • 「选了模型就不用管了」——同一个模型对查询侧与文档侧的用法可能不同（有的模型要求给查询加特定前缀指令），用错了会静默掉点。

L3-09 Embedding 维度、距离度量与归一化 ​

定义：三个常用度量——余弦相似度（看夹角）、内积（夹角 + 模长）、欧氏距离（看位置差）。

机制：对归一化向量（）三者等价（欧氏距离是余弦的单调函数）：

为什么这样设计：归一化的目的是消掉模长这个与语义无关的干扰项。很多 Embedding 模型的向量模长会随文本长度、词频变化，如果不归一化，内积会偏向「长向量」而不是「语义接近」——排序会被文本长度污染。归一化之后你可以放心用内积索引（因为内积此时等于余弦），而内积索引是唯一被大多数向量库一等公民支持、且能被 ANN 算法高效加速的形式。

数量级与形状：向量形状 (d,) 或批量下的 (N, d)，float32 时每维 4 字节；若做量化（见 L3-14）可降到 1 字节/维，代价是精度损失。

常见误区：

  • 「归一化了就万事大吉」——归一化只保证度量一致，不保证同一维度上查询侧与文档侧的编码方式一致（比如某些模型要求查询加指令前缀）。
  • 「欧氏距离和余弦完全不同」——在归一化下它们给出相同的排序；差别在于未归一化时欧氏距离仍然看位置。
  • 「浮点精度无所谓」——归一化时用 float32 计算、存储时降到 float16 会引入微小误差。在近似的 ANN 索引里，这类误差一般被索引本身的近似误差盖住，但在把分数当阈值用时必须知道它存在（见 L3-15 与两层拒答）。

L3-10 中文与多语言 Embedding 选型 ​

定义：面向中文与多语言检索的 Embedding 模型选型。

机制：中文的难点有三个——

  1. 无空格分词：词语边界不显式，模型要学会从连续汉字里切出语义单位；
  2. 近义改写密集：「安全距离」/「避碰距离」/a safe distance 在中文语料里经常混着出现；
  3. 中英混排：科研语料尤其明显（正文英文、提问中文）。这时跨语言对齐能力比单语能力更关键。

公开的常见选择方向（具体版本、维度、最大长度、是否需要查询指令前缀一律以模型官方文档为准）：BGE 系列（含面向多语言的版本与 M3 系列）、M3E、GTE、以及各家多语言通用模型。不要背维度数字，要背判定流程：

判定步骤具体做法
1 据语言构成选候选语料以中文为主 → 中文优化模型；中英混排 → 多语言 / 跨语言对齐模型
2 看是否要长文本块长设得大（比如 2048 字符）就要看模型的最大输入长度是否够
3 在同一批硬样本上对比用自己的语料构造对比：近义缩写（CTRIP-SAC vs PER-SAC）、跨语言同义句、专有名词
4 看推理成本本地 CPU 推理的编码耗时与显存占用，直接决定索引构建与查询延迟

为什么这样设计：选型的判据不是「别人的排行榜」，而是「在你的语料上，它把该近的拉近了吗」。排行榜用的是通用语料，你的语料可能恰好是分布外。

常见误区：

  • 「中文模型处理中文、英文模型处理英文就够了」——中英混排场景下，用中文提问去检索英文文档是常态，需要的是跨语言对齐，不是两个单语模型。
  • 「模型能处理 8192 长度，所以块可以开很大」——能处理不等于表征好，长输入下向量容易「变糊」（变成段落摘要，失去区分度）。
  • 「换模型是免费的」——换 Embedding 模型意味着全库重新编码 + 全部历史指标作废，成本和换切法是同一量级。

L3-11 微调 Embedding 模型 ​

定义：用领域（查询，正例文档）样本对，把通用 Embedding 对齐到你的语料与问题分布。

机制：与 L3-08 的对比学习同一套损失，差别在数据从哪来。三类正例来源：① 真实日志里的「点击/采纳」行为；② 语料里天然的强结构对（论文标题 ↔ 摘要、章节标题 ↔ 正文、问答对）；③ 用 LLM 从块里反向生成问题。负例质量是决定成败的部分：随机负例太容易，模型学不到细粒度区分；必须挖 hard negative——检索器当前排在前列、但标注上不相关的那些块。

为什么这样设计：通用模型的语义空间是按通用语料训练的，而你的业务里「相关」有一个具体定义（比如「同一个指标定义体系下的块」才算相关）。微调做的事就是把这个业务定义写进向量空间。

数量级与形状：样本对通常在「几千到几万」量级起步；hard negative 每对挖 3–10 个。评估必须用检索指标（Recall@k / MRR）而不是分类指标——因为下游要的是排序。

常见误区：

  • 「微调 Embedding 是第一步」——错。先修解析、切块、混合检索、精排，因为那些的收益更确定、成本更低、可回退。微调的代价是：全库重新编码 + 历史指标全部作废。
  • 「正样本越多越好」——正样本质量差的微调会让模型学到错误的相关性定义。
  • 「用训练损失下降判断微调成功」——训练损失下降只说明模型拟合了训练集；必须回到检索指标上看 Recall@k / MRR，并且要在没参与训练的题上测（否则你测的是记忆）。

代码（伪代码，训练框架 API 以官方文档为准）：

python
# 1. 构造样本对：正例 + hard negative（hard negative 来自当前检索器的高排位错例）
pairs = [(q, d_pos) for q, d_pos in positives]

# 2. 用对比损失微调（双塔、共享或分开编码器，按所选模型的官方训练脚本为准）

# 3. 指标必须回到检索任务上：同一批题、同一份 gt，比微调前后的 Recall@k / MRR

和你自己的项目对上号 ​

  • 模型与维度：EMBED_MODEL = "BAAI/bge-m3"（config.py:152），1024 维（docs/projects/rag/04-retrieval.md:32-37）。它是多语言模型，这正好对上你的语料构成：正文以英文论文为主，提问以中文为主。
  • 归一化是显式做的：_S.embedder.encode([query], normalize_embeddings=True)；因为归一化了，内积等于余弦，所以索引用 IndexFlatIP 是语义正确的——这是可以在面试里一句话讲清的因果链，而不是「反正大家都这么写」。
  • 一行危险代码，值得单独讲：稠密检索拿到的是「距离 + 行号」，必须做一次 行号 → chunk_id 的映射（cid = _S.chunk_list[int(i)].chunk_id，retrieve.py:162-172）。这一行错了不会报错，只会返回另一个块的正文——这是索引与元数据不同步时的典型静默故障。
  • 中文适配的真实代价长什么样：exp02_embedding_fail.py 给了一个极端例子——CTRIP-SAC 与 PER-SAC 只差两个字母、语义相反，余弦相似度高达 0.881，反而超过真正同义改写的 0.599。这直接说明了两件事：① 稠密检索不认识「近义缩写」；② 光看相似度分数不能判断相关性，必须有字面匹配一路补（见 ⑥ 稀疏检索与混合融合）。
  • 微调这一格你目前是空的：项目里没有做 Embedding 微调。这不是缺陷，但面试时不要说「做了微调」。正确的说法是：我现在的语料规模（55 篇 / 5325 块）下，先把解析、混合检索、精排的收益拿完了；微调的代价是全库重新编码 + 全部历史指标作废，我会把它排在「确认真瓶颈在语义表征」之后，并用同一批题比 Recall@k / MRR 判定收益。

面试怎么问 ​

Q1：你为什么选这个 Embedding 模型？

A（要点）：给判定流程而不是「它效果好」——先按语料语言构成筛候选（中英混排 → 需要跨语言对齐的多语言模型），再看最大输入长度是否覆盖我的块长，再在同一批硬样本上对比（近义缩写、跨语言同义句），最后看本地推理成本。加分句：我用 BAAI/bge-m3，1024 维；它是否最优我没法声称，因为在 55 篇 / 5325 块这个规模上我没有跑过全模型横评——我只跑过它的失效案例。 别说：「因为它是榜单第一」——榜单语料不是你的语料。

  • 追问 1：你的语料里英文占绝大多数，提问却是中文，这会不会有问题？→ 会有，而且我实测过它的失效形态：CTRIP-SAC 与 PER-SAC 余弦相似度 0.881，比真正的同义改写 0.599 还高——近义缩写是稠密检索的原理性盲区，我用稀疏路和精排来补。
  • 追问 2：那你怎么知道换一个模型会更好？→ 我不会凭感觉换。要换就固定其他变量（同一份 gt、同一套切块、同一套检索参数），只换 Embedding 重跑 Recall@k / MRR；换模型的成本是全库重新编码 + 历史指标作废，所以这个决定必须带数据。

Q2：余弦相似度和内积有什么区别？为什么归一化？

A（要点）：内积 = 余弦 × 两个模长。归一化把模长消成 1，于是内积等于余弦；此时欧氏距离也变成余弦的单调函数（）。加分句：归一化的真正理由是消掉与语义无关的长度干扰——向量模长常随文本长度变化，不归一化的话排序会被「文本长度」污染，而且内积是 ANN 索引支持最好的形式。别说：「差不多，随便用一个」——这句话会把面试官直接引到这三个公式上。

  • 追问 1：那归一化之后用欧氏距离索引行不行？→ 排序等价，但工程上没理由这么做：内积（余弦）索引支持最广、也最容易被量化与近似算法优化。能等价的时候选支持最好的那个。
  • 追问 2：那我把分数当阈值用，要注意什么？→ 要注意分数的可比范围取决于返回路径。我项目里有个具体教训：精排分数（Cross-Encoder 分数，0–1 区间）可以做阈值；而融合分数是 RRF 分（区间约 0.016–0.033），拿它比 0.30 会让每一道题都被拒答。所以代码里判据写成 use_rerank and t1 < threshold，报告里那两列的拒答指标渲染成 —（不适用），而不是 0。

Q3：Embedding 要不要微调？你怎么做？

A（要点）：先给顺序——解析、切块、混合检索、精排的收益更确定、可回退，微调排在这些之后；再给方法——对比学习 + hard negative，正例可以来自业务日志或语料天然结构。加分句：微调真正的成本不是训练，而是全库重新编码 + 历史指标作废；判定是否值得的唯一标准是同一批题上的检索指标（Recall@k / MRR）有没有变好。别说：「微调一下效果就好了」——说不出 hard negative 怎么挖，会被认为没做过。

  • 追问 1：负例怎么选？→ 随机负例太容易，模型学不到细粒度区分；必须挖 hard negative，也就是当前检索器排在前列但标注上不相关的块。这类样本才是模型的边界。
  • 追问 2：怎么判断微调有效？→ 训练损失下降不算证据。要回到检索任务：同一份 gt、同一批题，比微调前后的 Recall@k / MRR，而且测试题不能进训练集。我项目里没做微调，我会如实说，并说明我把它排在什么位置、用什么判据来决定要不要做。
