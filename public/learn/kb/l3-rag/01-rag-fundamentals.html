RAG 是什么、最小闭环与选型 ​

覆盖知识点：L3-01 L3-02 L3-03 ｜ 面试频率：高 ｜ 建议学时：9h

一句话说清 ​

RAG（Retrieval-Augmented Generation，检索增强生成）是把「知识」从模型参数里搬出来、放进一个可增删改查的外部存储，在生成前把相关片段拼进上下文——模型负责理解与组织，知识库负责事实。

为什么必须学 ​

这一层是 AI 应用岗面试的开场题，也是筛人最快的一题。面试官问「讲讲你的 RAG 项目」时，实际在听三件事：

  1. 你知不知道知识从哪来。答「我把文档喂给大模型」= 不知道 RAG 是什么，直接出局。
  2. 你会不会做选型。只会 RAG 一种方案、说不出它什么时候不该用，会被归到「只会照着教程搭」。
  3. 你闭环了没有。有没有「切块 → 向量化 → 检索 → 生成」之外的那一圈——评测与拒答。只有四步没有评测的，面试官会追问到「你怎么知道它变好了」，答不上来就很难进二面。

核心内容 ​

L3-01 RAG 是什么、解决什么问题 ​

定义：RAG 是一种把「检索器」与「生成器」解耦的架构。检索器（Retriever，通常是 Embedding 模型 + 向量索引 + 关键词索引）负责从外部语料中找到与问题相关的片段；生成器（Generator，一个 LLM）只负责把这些片段组织成答案。

机制：拆成两条链路。

链路什么时候跑做什么
离线索引（Offline Indexing）语料更新时跑一次加载 → 解析 → 切块 → 向量化 → 写索引
在线问答（Online Serving）每次提问都跑查询改写 → 检索 → 融合 → 精排 → 拼上下文 → 生成 → 引用校验

为什么这样设计：把「知识」与「推理」分开，换来三件事——知识更新不需要重新训练模型（改索引即可）；答案可以带出处（因为片段是字面量，能定位回原文）；错误可以归因（答错是「没检索到」还是「检索到了但没用好」，这是两个完全不同的修法，见 L6 · 评测与可观测）。

数量级与形状：检索侧一次请求的典型形状是「一条 query 向量（ 维，常见 768 / 1024 / 1536）→ 命中 top-k 条片段（ 通常 10–50）→ 精排后取 top-n（ 通常 3–8）→ 拼成上下文（几千 token）」。

常见误区：

  • 「RAG 是给模型补充知识」——只说对了结果，没说对机制。机制是补充上下文，模型参数一点没变。
  • 「RAG 能消除幻觉」——RAG 把「没有知识」这一半幻觉压下去了，但引入了一条新的失败模式：检索回来的片段本身不相关或相互矛盾时，模型照样能编出一段通顺的错误答案。
  • 「向量检索 = RAG」——向量检索只是检索器的一种实现，RAG 还包含生成阶段的约束与拒答。

代码：最小 RAG 的核心只有三步，先看清它有多短（伪代码，接口以各家官方文档为准）：

python
def answer(question: str) -> str:
    q_vec = embed(question)                    # 1. 问题向量化
    hits = index.search(q_vec, top_k=10)       # 2. 向量检索
    context = "\n\n".join(f"[{i+1}] {h.text}" for i, h in enumerate(hits[:5]))
    prompt = f"只依据下列资料回答，资料不足就直说不知道。\n\n{context}\n\n问题：{question}"
    return llm(prompt)                         # 3. 带上下文生成

L3-02 RAG 与微调、长上下文的取舍 ​

定义：往模型里注入知识有三条路——RAG（检索进上下文）、微调（Fine-tuning，改参数）、长上下文（Long Context，把更多原文塞进窗口）。它们不是替代关系，是成本、时效、可控性三个维度上的不同取值。

机制：

维度RAG微调（SFT / LoRA）长上下文
知识更新成本改索引，分钟级重新造数据 + 训练，天级无需更新，但每次都要重新喂
单次推理成本中（检索 + 几千 token 上下文）低（无检索开销）高（token 数随文档线性增长）
时效性实时（索引即真相）有滞后（训练数据的截止时间）实时
出处可溯源性强（片段是字面量）弱（知识融进参数，说不清来自哪）中（原文在上下文里，但要自己定位）
适合注入的内容事实、条款、文档、会变的业务知识风格、格式、行为模式、判断能力短而集中的一次性文档

为什么这样设计：判断标准不是「哪个更强」，而是你要注入的是「事实」还是「行为」。

  • 注入事实（产品条款、API 文档、论文库）→ 用 RAG。理由是事实会变，而参数不会自己变。
  • 注入行为（固定输出格式、领域术语的正确用法、某类判断）→ 用微调。理由是这类东西不依赖具体某段文本，无法靠检索「捞」出来。
  • 两者可以叠加：先微调对齐行为（比如让模型严格输出带引用的结构），再用 RAG 供事实。这是工业界的常见组合。

数量级与形状：长上下文的坑在于成本与注意力都不线性。上下文从 8k 涨到 128k，token 成本涨 16 倍，而「中间部分被忽略」（lost in the middle）是普遍现象——把 55 篇论文全文塞进窗口，不仅贵，有效利用率也低。检索的作用就是在预算内把信噪比拉高。

常见误区：

  • 「有长上下文就不需要 RAG 了」——长上下文解决的是「窗口装不装得下」，RAG 解决的是「在装得下的前提下，放进去的是不是该放的东西」。语料到了几千块、几百万 token 的规模，纯靠长上下文成本不可控。
  • 「RAG 检索不准就微调 Embedding、再不行就微调 LLM」——顺序错了。先定位是检索没召回、还是召回后被噪声挤掉、还是生成没用好，再决定改哪一环。
  • 「微调可以注入新知识，而且比 RAG 便宜」——训练成本一次性看着低，但知识一更新就要重训，而且微调注入事实会带来更难排查的幻觉：模型会用训练时的语气自信地说出过期内容。

L3-03 四步构建最小 RAG ​

定义：最小闭环 = 加载（Load）→ 切块（Chunk）→ 向量化（Embed）→ 检索生成（Retrieve & Generate），对应 L3-04 到 L3-07 与 L3-08 到 L3-15。

机制：每一步的输入输出与它自己会引入的失败模式必须一起记。

步输入 → 输出这一步独有的失败模式
加载解析文件 → 纯文本 + 页码/版面信息双栏串行、页眉页脚混入正文、表格被线性化、公式符号被误识别（见 ② 文档加载与多格式解析）
切块长文本 → 若干块 + 元数据答案被切在两块之间；块太大导致向量失去区分度（见 ③ 切块策略）
向量化块 → 归一化向量中英混排下同一模型表现差异大；领域术语被映射到通用语义空间（见 ④ Embedding）
检索生成问题 → 答案 + 引用只召回字面相似但答非所问的块；上下文超预算（见 ⑤ 向量索引）

为什么这样设计：这四步的顺序不是随意的——后一步的能力被前一步的上限锁死。解析丢掉的字符，切块和向量化再怎么调也找不回来。所以调优的顺序必须是从上游到下游，而定位问题的顺序必须从下游到上游（先看生成有没有用好，再回溯到检索、切块、解析）。这个「调优顺着走、排查倒着走」的纪律是应届生在面试里最容易显得专业的一句话。

数量级与形状：一个 1000 页 PDF 的知识库，走完四步的典型产物量级是「几千到几万块」——所以第一个必须做的自检是：块数对不对、平均块长是多少、有没有明显异常的块（比如只有标题的块）。数量级要拿自己的语料实测，不要照抄别人的数字。

常见误区：

  • 「四步都跑通了 = 项目做完了」。真实项目的 80% 工作量在之后的评测、拒答、引用核对与延迟优化。
  • 先调 Embedding 模型、再调切块。顺序反了：切块的影响通常比换模型更大，而且换切块会作废全部历史指标（见本项目 ④ 切块策略 里 exp30 抓到的「换尺子」）。
  • 没有留出评测位。从第一天起就要留一列「这道题的正确答案应该落在哪个块」，否则后面想评测时连分母都没有。

和你自己的项目对上号 ​

你的科研文献 RAG 项目就是这份最小闭环的完整实例，而且每个数字都是自己测出来的，不是抄的：

  • 语料规模：55 篇（USV 无人水面艇 + 多智能体强化学习方向的论文）、5325 块（eval/report.md:129）——这是「离线索引」的产物量级，也是「第一个自检」要看的那个数。
  • 在线链路：问题 → 双路召回（稠密 20 + 稀疏 20）→ RRF 融合 20 → Cross-Encoder 精排取 5 → 拼上下文生成。参数定义在 rag-demo/config.py：DENSE_TOP_K/SPARSE_TOP_K/FUSED_TOP_K 均为 20（:163-166）、RERANK_TOP_N = 5（:167）、RRF_K = 60（:165）。
  • 三档实测对照（124 题 / gt 206 块 / 密度 1.66 块每题，eval/report.md:41-43）：① 纯向量 R@5 64.4% / MRR 0.577 ｜ ② 混合无精排 59.1% / 0.502 ｜ ③ 混合 + 精排 71.8% / MRR 0.714。注意 ② 比 ① 更差——这是这个项目最有价值的反常识结论，机制见 ⑥ 稀疏检索与混合融合。
  • 选型的证据是延迟不是分数：首字延迟 ≈ 检索耗时（14.90 / 10.00 / 14.86 s），而 LLM 生成 P50 只有 1.26 s。也就是说这个项目的时间几乎全花在检索侧，其中 CPU 精排 20 对约 8.5 s。当你被问「为什么不换更快的向量库」，正确回答是「瓶颈不在这」：exp31_index_scaling.py 实测 Flat 索引在 52 万块量级仍是毫秒级，换 ANN 只会白丢召回。
  • 四步之后的那一圈：双层拒答（程序层阈值 + 模型层自述）与分层评测，见 ⑩ 生成约束与 Agentic RAG 与 ⑨ 引用与权限。

面试怎么问 ​

Q1：你这个项目为什么用 RAG，不直接微调一个模型？

A（要点）：要注入的是会变的事实（论文库、术语、指标定义），不是行为模式。RAG 的更新成本是一句 reindex，微调的更新成本是一次重新造数据 + 训练，而且训练完说不出「这句话出自哪一篇第几页」。加分句：我没有把两者对立，真要叠加的话顺序是「微调对齐输出行为（严格带引用的结构），RAG 供事实」。别说：「RAG 比微调便宜」——只谈钱不谈时效和可溯源性，会被认为没做过选型。

  • 追问 1：如果知识是每天更新的业务文档，你还选 RAG 吗？→ 更选 RAG，而且要把「文档版本 + 生效时间」写进元数据，让检索能按时间过滤；微调在这里不是「慢」，是错，因为它会自信地输出过期内容。
  • 追问 2：什么情况下你会反过来选微调？→ 要注入的是说话方式或固定格式（比如必须输出某种 JSON 结构、必须用某套领域术语）、或者要做一类不依赖具体文本的判断时，微调更合适，因为这类能力没法靠检索「捞」出来。

Q2：现在模型上下文都 128k 了，还需要 RAG 吗？

A（要点）：需要，而且理由变了。长上下文解决的是「装不装得下」，RAG 解决的是「该装什么」。成本上，上下文长度与 token 成本近似线性，语料规模一大就不成立；效果上，「中间被忽略」是普遍现象，把整库塞进去也不会带来与 token 数成正比的收益。加分句：这两个方案不互斥——RAG 负责把候选压到能进窗口的规模，长上下文负责让单次请求容纳更多证据。别说：「长上下文很强所以 RAG 要淘汰了」——这句话在 2026 年会被追问到语料规模的具体数字上。

  • 追问 1：那你凭什么说「检索能把该装的装进去」？→ 我不凭感觉说，我有一列 gt（每道题的正确答案落在哪些块），能用 Recall@k 量出「该装的有没有装进去」；没有这一列，这句话就只是声称。
  • 追问 2：如果语料只有 20 页、问题也很集中呢？→ 那我会先测纯长上下文，很可能它更简单也更准，RAG 的复杂度在这个规模下不划算。选型要跟着规模走。

Q3：现场画一下最小的 RAG 闭环，并说说它最常见的失败点。

A（要点）：画出「离线四步 + 在线五步 + 那两条链路之间的索引」；然后主动指出最容易被忽略的是从第一步就丢掉的东西——解析丢掉的公式符号、切块切碎的答案。加分句：调优从上游往下走（先修解析与切块），但排查从下游往上走（先确认生成有没有用好，再回溯检索）。别说：「RAG 的难点是选向量库」——向量库是最不难点的那一环。

  • 追问 1：这四步里，哪一步的收益最大？→ 切开看的话，把「检索到了但排序不对」和「压根没检索到」分开统计（前者用 MRR 看，后者用 Recall@k 看），哪个缺口大改哪个。凡是没有实测的「收益最大」都是猜。
  • 追问 2：那你怎么保证换了切法之后，指标变好不是尺子变了？→ 用与切片无关的口径去比，比如「答案的关键串是否完整落在同一块内」；Recall@k 的分母是 gt 块数，粗切会合并相邻 gt 块、把分母改小，分数自然好看。这是我在自己项目里踩过的坑（exp30_slice_compare.py）。
