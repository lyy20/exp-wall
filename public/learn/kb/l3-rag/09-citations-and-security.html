本页目录

引用可溯源、权限与多租户隔离 ​

覆盖知识点：L3-25 L3-26 ｜ 面试频率：高 ｜ 建议学时：6h

一句话说清 ​

引用是让用户能核实答案（把信任从「模型说」转移到「原文写着」），权限隔离是让用户只能看到他有权限看的内容（把「检索到」这件事从「技术问题」变成「安全问题」）。前者决定答案能不能被相信，后者决定系统能不能上线。

为什么必须学 ​

这一页的两个知识点，一个决定信任，一个决定能不能过合规。面试里的问法很直白：

  • 「你怎么保证答案不是编的？」——这是每个 AI 应用岗位都会问的问题。答「我限制模型只能基于检索内容回答」是只说了一半；能说清「引用编号要程序化校验、校验不过怎么办」才是完整答案。
  • 「多个部门共用一个知识库，B 部门的人会不会搜到 A 部门的资料？」——这是企业落地访谈里的必答题，而且它有一个反直觉的技术要点：过滤必须下推到检索层，不能检索完再删。答错这一点通常意味着你没真正做过企业项目。

这两点都不需要复杂技术，但都需要想过一遍。它们也是「企业级 RAG」与「个人 demo」最明显的分界线。

核心内容 ​

L3-25 引用与可溯源性（Citations） ​

定义：在答案里标注证据出处（哪块、哪篇文档、第几页、哪一节），并保证这个出处可以被点击打开核对。

机制：引用不是「让模型在回答末尾写几个来源」这么简单，它是一条完整链路：

  1. 给上下文里的每块编号：模型只被告知「这里有几块编号材料」，输出时按编号引用。
  2. 要求引用格式统一：例如「答案里的关键论断后面标 [3]」，格式必须在 prompt 里明确、且用户可见的展示层也按同一编号渲染。
  3. 程序化校验引用（关键一步）：拿到模型输出后，用代码检查它引用的编号是否真的存在于本次上下文。这是唯一能自动发现「凭空引用不存在的编号」的手段——字符串层面的编号检查是机械可判定的，不依赖模型自觉。
  4. 校验失败的处置要有策略：重试一次、降级为「无引用回答 + 提示证据不足」、或者直接拒答。策略必须提前定，不能在校验失败时才想。

为什么这样设计：因为 LLM 的幻觉有一条最隐蔽的分支——内容可能是真的，但出处是假的（引用了不存在的一篇文献）。这类错误比整段编造更难被发现，因为读者看到「有引用」就放松了警惕。引用校验把「信任模型」变成「验证编号」，这是可以用几行代码换来的可靠性。

数量级与形状：引用校验的代价极低（一次字符串/编号集合比对，微秒到毫秒级），但它只能证伪「编号不合法」，不能证明「内容确实出自该块」。也就是说：

  • ✅ 能自动发现：引用了不存在的编号（[7] 但上下文只有 5 块）。
  • ❌ 不能自动发现：引用了合法的 [2]，但 [2] 里的内容其实不支持这句话。

后者要靠人工抽检或更强的校验模型，成本高得多。把这条边界说清楚，是回答「引用校验有多可靠」的正确答案。

常见误区：

  • 「让模型自己保证引用正确」——模型没有「记得自己看过哪几块」的强约束，必须程序校验。
  • 「引用越多越好」——把每句话都标上来源会稀释信号，用户反而看不出哪句是关键论断。引用应该标在关键论断上。
  • 「引用只是 UI 功能」——引用同时是评测基础设施：有了「答案必须带出处」，你才能自动检查「引用块是否真的包含答案」，这也是 faithfulness（忠实性）类指标的基础（见 L6 · 评测与可观测）。
  • 「页码不重要」——必须讲清：在扫描件/PDF 场景，「哪一页」是权重的——用户点开直接跳过去，比对。所以解析阶段要把页码与章节当作元数据保留（L3-07）。

L3-26 权限与多租户检索隔离 ​

定义：让每个用户/组织只能检索到他有权限的内容，同一套索引服务多租户共用。

机制：四种粒度，成本递增：

粒度做法隔离强度成本
应用层过滤（先检索后删）检索 top_k，再按权限表剔除无权限的弱：不推荐低
元数据过滤下推把权限标签作为向量库的前置过滤条件，检索时只在不越权集合内搜中中
物理分区按租户分 collection / partition / 索引强高
独立实例每租户独立部署最强最高

为什么「先检索后删」是错的——这是本页最该记住的一句话：

  1. 上下文被稀释：取 top-k 时如果其中一部分被剔除，实际有效条数就少于 k，答案可用性直接依赖越权内容在库里的占比。
  2. 信息已经泄漏：检索结果本身可能包含敏感片段；它进了日志、进了调试视图、进了模型上下文，泄漏已经发生了。
  3. side-channel：即使不展示内容，「命中/未命中」「分数高低」本身也是泄漏——用户能据此推断出某份文档存不存在、标题是什么。

所以正确顺序永远是：权限条件进入检索（filter pushdown），而不是结果后处理（post-filter）。

数量级与形状：过滤条件会影响向量索引的召回——ANN 索引（尤其 IVF 类）是先在向量空间里找近邻再过滤，如果某个租户的数据只占 1%，在固定 nprobe/ef 下可搜到的近邻本来就少，再叠加上权限过滤就容易空手而归。这是「过滤下推」的工程代价，也是分区的理由（见 ⑤ 向量索引与 Top-k）。具体某个向量库支持哪些过滤语法与算子、是否有独立 partition/租户概念，以该库官方文档为准。

常见误区：

  • 「检索层不管权限，API 层管就行」——API 层管的是返回，泄漏发生在检索。
  • 「标签加上就行」——标签必须在写入时就打好（L3-07 的元数据），事后补标要大重建索引；而且标签的来源必须可信（不能靠模型自动打标签来决定权限）。
  • 「权限=文档级就够」——真实企业里常有「同一文档内某几段是敏感的」，那就需要块级/行级权限，成本又上一个层次。
  • 「多租户就是多个 collection」——还要考虑共享缓存、日志、评测集是否串租户，那些地方同样会泄漏。

和你自己的项目对上号 ​

这两项在本项目里都有真实实现，而且比大多数个人项目做得细——这是你面试时的强项，值得主动讲。

1）引用链路的真实做法：上下文组装时给每块加上「文献图例 + 页码 + 章节」的头（generate.py:84-119 build_context()）。这里有两个被实测逼出来的设计点：① 来源必须写论文标题，不能写文件名——早期用 SCIS 这类文件名当来源，模型无从知道它指哪篇论文，在「不得猜测」的约束下倾向拒答；② 标题只在开头声明一次——一篇论文标题约 140 字符，5 块就是 700 字符，约占上下文 17%，且同一长串重复 5 遍会稀释注意力（docs/projects/rag/05-rerank.md:114-123）。

2）生成阶段的约束与拒答（generate.py:350-449、streaming.py:65-190）：系统提示里的 REFUSAL_TEXT = "根据提供的资料无法回答该问题。"（generate.py:59）是固定的拒答话术——这样做的好处是拒答可以被程序识别（评测时能自动判定「是否拒答」），而不是靠人读。这是「拒答也要有协议」的一个具体例子。

3）已经实现的护栏（这是企业级意识的证据）（docs/projects/rag/07-guardrails.md，guard.py:100-158/248-251/254-297/315-333）：

4）必须诚实说的边界：本项目没有多租户隔离。 它只有单层 API Key 鉴权，没有「用户 A 只能看文献集合 A」这类能力；语料是一个全局索引（55 篇 / 5325 块）。所以面试时：

  • ❌ 不要说「我做了权限隔离」。被追问「那你说说过滤是下推还是后置」时会立刻暴露。
  • ✅ 可以说：「我做了鉴权与资源护栏（401/429/503/504/402 六种状态码都有明确语义），但没有做租户级的检索隔离。我知道正确的做法是权限条件随检索一起下推、而不是检索完再删——后者会把越权内容读进日志和上下文，泄漏已经发生。我的语料是公开论文，没有这个需求，所以我没做；如果换成企业文档，这会是我第一个补的能力，因为它决定能不能上线。」

5）一个数据层已有的「可信度分级」素材：data/doc_sources.json 顶层记录了 n_docs: 55、n_direct: 52、n_search: 3、n_verified: 47（_research/RAG-事实清单.md:87）——55 篇里 47 篇经过核验、3 篇是通过检索获得的。这不是权限，但它是同一类思想的雏形：不同来源的证据不该被同等对待。在答案里标注「这条来自已核验的原文，那条来自二手检索结果」，就是引用分级的最小实现。

面试怎么问 ​

Q1：你怎么保证模型的答案不是编的？

A（要点）：三层——检索层给证据（有页码有章节）、生成层约束（只允许基于材料回答，无证据就拒答，拒答用固定话术以便程序识别）、输出层校验（程序检查引用编号是否真的存在于本次上下文）。加分句：要讲清引用的可达边界——编号校验能自动发现「引用了不存在的编号」，但不能证明「内容确实出自该块」；后者要靠人工抽检或更强的校验模型。把边界说清楚，比声称「引用一定准确」可信得多。别说：「我在 prompt 里让它不要编」——那只是三层里最弱的一层。

  • 追问 1：那引用编号不在上下文里，你会怎么处理？→ 要提前定策略，我倾向重试一次，然后降级为「证据不足」并明说，而不是把带错引用的答案放出去。降级也要有可见的出口——不能让用户觉得系统卡住了。
  • 追问 2：怎么自动衡量「答案有没有被证据支持」？→ 用引用做基础：把答案里的关键论断与它引用的块做比对（规则或模型判定），再聚合成 faithfulness 类指标。做这件事的前提是答案里必须有可解析的引用结构——所以我一开始就让引用格式固定下来，而不是让模型自由发挥。这也和 L6 的评测体系 是同一套基础设施。

Q2：同一个知识库服务多个部门，你怎么做数据隔离？

A（要点）：权限条件必须随检索一起下推，绝不先检索后过滤。 理由三条：① 后过滤会让有效条数少于 k，可用性依赖越权内容的占比；② 检索结果会进日志、调试视图、模型上下文，泄漏已经发生；③ 「命中与否、分数高低」本身就是 side-channel 信息。加分句：还要注意过滤对 ANN 召回的影响——数据占比小的租户在固定 nprobe/ef 下容易空手而归，所以规模到了一定程度要走到物理分区或独立实例。别说：「检索回来再按权限删掉」——这一句基本就被判定没做过企业项目。

  • 追问 1：权限标签什么时候打？→ 写入时（L3-07 的元数据），而且标签的来源必须可信——不能用模型自动打标签来决定权限，那等于把安全交给模型。事后补标要全量重建索引，成本高一个量级。
  • 追问 2：你项目里做了吗？→ 没有。我只有单层 API Key 鉴权、限流、并发与超时护栏，语料是公开论文、单一全局索引，没有租户概念。我不会把它说成做了。 我知道要做的话第一步是给每块补 tenant_id 与权限标签，然后改检索接口让过滤条件进查询，最后补一条**「越权内容不得进入任何日志与上下文」**的测试。

Q3：如果用户问的问题确实没有答案，你的系统怎么表现？

A（要点）：两层拒答——程序层用精排 top1 分数低于阈值直接零成本拒答（不调 LLM），模型层在提示约束下自报证据不足兜底。加分句：两层要分开测误拒率，否则说不清是拦太狠还是模型太保守。更重要的是随机性签名：阈值层的误拒是「同一个率、不同的集合」——同样 23 道可回答题、每轮固定 3 道被误拒，但中招的题每轮都不一样（S01/S15/M08 → S15/M05/M08）。这说明盯单道题的失败是找不到根因的，必须看分布。别说：「拒答很准，100%」——那个 100% 是 6 道不可回答题的小分母口径，必须带上前提。

  • 追问 1：拒答准确率和漏拒怎么衡量？→ 分开算：不可回答题里被拒的比例（拒答准确率）、可回答题里被误拒的比例（误拒率）。两类的分母不同，不能合成一个「准确率」，而且必须注明评测批次——我不同批次的数字（1.6% / 6.5% / 7.3%）来自不同口径，不能混用。
  • 追问 2：拒答的代价是什么？→ 对用户是「明明有答案却被告知没有」，这比答错更让人恼火，因为用户无法自己补救。所以拒答话术要给下一步（比如提示换个问法、或说明当前语料范围），而不是只有一句「无法回答」。
