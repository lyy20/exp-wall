切块策略、参数与元数据 ​

覆盖知识点：L3-05 L3-06 L3-07 ｜ 面试频率：高 ｜ 建议学时：11h

一句话说清 ​

切块是整条链路里**参数最敏感、也最容易「换把尺子把指标换好看」**的一步；chunk size 没有普适最优值，只有在你自己语料上做消融才能定的值。

为什么必须学 ​

「chunk size 你取多少？为什么？」是 RAG 岗位出现频率最高的实操题，它一次性筛掉三类人：

  1. 背了个数字的人：答「512」或「1000」，追问「为什么」就没了。
  2. 只知道一种切法的人：只会 RecursiveCharacterTextSplitter，说不出结构感知、语义切分、父子块各自解决什么问题。
  3. 没做过消融的人：说不出「换切法之后指标为什么会变」，也识别不出指标变好可能只是尺子变了。

第 3 类是最可惜的——他其实做了实验，但没意识到 Recall@k 的分母会被切法改变，于是得出了错误结论。这一页的核心目标就是让你能识别这件事。

核心内容 ​

L3-05 文本切块（Chunking）策略 ​

定义：把长文档切成检索单元（retrieval unit）——每一块是「一次向量化 + 一次召回」的最小粒度，也是「一次送进上下文」的最小单位。

机制：五种主流策略，按「结构信息的利用程度」递增。

策略怎么切优点代价 / 失效场景
固定长度每 个字符（或 token）切一刀实现最简、块长可控会把句子、定义、公式切两半
递归分隔按分隔符优先级依次尝试（段落 → 换行 → 句号 → 逗号…），直到块长合规尽量落在自然边界，工程最常用对没有标点的语料（表格、代码）退化成固定长度
结构感知 / 层级先按文档结构（标题层级、章节号）划边界，再在边界内按长度切边界语义正确，且天然产出 section 元数据依赖解析质量；结构识别失败就退化成固定长度
语义切分计算相邻句子的 Embedding 相似度，在相似度「突降点」断开边界与语义变化对齐，不依赖标点成本高（要先编码）；阈值难定；对本就同质的语料没有收益
父子块 / 句子窗口小块用于检索（child），命中后返回它所属的大块或前后邻句用于生成（parent / window）同时拿到「小块的检索精度」与「大块的上下文完整性」要维护两层映射；上下文预算变大

为什么这样设计：切块要同时满足两个方向相反的约束——

  • 块要够大：一个定义、一段推导、一张表必须落在同一块里，否则召回的东西答不了任何问题；
  • 块要够小：块长决定了送进 prompt 的 token 数，也决定了向量能表达多少语义——块越长，向量越像「整章的摘要」，区分度越低。

这两个约束的最优解只能靠实验定。所以正确的回答不是给数字，而是给判据：① 语义完整性（答案的关键串是否完整落在同一块内）；② 检索单元粒度（块与块之间的向量是否还能区分开）；③ 上下文预算（ 块拼起来会不会超窗）。

数量级与形状：块的形状是「文本 + 元数据」。以一个正常段落为单位思考：一段 300–800 字符的正文，在一篇 16 页论文里可能落在第 3–8 块的位置。你至少要能说出自己语料的三个数：总块数、平均块长、最长块长。

常见误区：

  • 「有个业界最优 chunk size」——没有。它取决于语料语言、平均段落长度、问题类型（事实型问题偏好小块，总结型问题偏好大块）、以及 Embedding 模型对长文本的表征能力。
  • 「切块只是切文本」——元数据是切块的同级产物，见 L3-07。
  • 「块越小召回越准」——小块确实让向量更聚焦，但会切碎语义、增加块数（索引成本与上下文碎片化都上升）。两头都是坑，中间那段要自己量。

L3-06 切块参数与重叠窗口 ​

定义：chunk_size（块长上限）、overlap（相邻块的重叠长度）、以及最小块保护（min chunk length）。

机制：重叠的作用只有一个——防止答案正好被切在边界上（前半句在块 A、后半句在块 B，两块单独看都不完整）。重叠长度的常见做法是块长的 10%–20%，但这是一个经验区间，不是定值。

数量级与形状：

  • 单位陷阱：chunk_size 到底按字符还是 token 计，不同工具、不同配置层可能不同。配置里的数字不等于产物里的数字——你必须去量产物。
  • 一条更隐蔽的换算：字符/token 比在不同语言下不一样。中文约 1.2–1.3 字符/token，纯英文可达 3 字符/token 以上。所以「同一个长度档位」在中英混排语料里，中文块的 token 数会比英文块多出接近一倍。上下文会不会超窗，取决于真实 token 数，不取决于配置里的数字。

为什么这样设计：重叠是用存储和检索冗余换边界安全。它不需要很聪明，但要有意识地选：语料是「一条条独立短条款」（FAQ、术语表），重叠基本无收益；语料是「长段落连续论证」（论文、合同），重叠明显有用。

常见误区：

  • 配置写了上限，产物就满足上限——不一定。硬切兜底路径与长度约束之间如果有缝，产物会超过上限。
  • 换档位可以直接比指标——不能。换切法会改变gt（标准答案块）的数量，从而改变指标的分母，详见下面的项目实例。
  • 「overlap 越大越安全」——重叠太大等于把同一段内容索引多遍，检索结果里会出现多个几乎相同的块，挤掉真正不同的证据。

代码（伪代码，工具 API 以官方文档为准）：

python
def chunk(text: str, max_chars: int, overlap_chars: int, min_chars: int = 60) -> list[str]:
    """结构边界优先，长度约束兜底；不足 min_chars 不单独成块。"""
    out, buf = [], ""
    for unit in split_by_structure(text):          # 章节 / 段落级切分（结构感知）
        if len(buf) + len(unit) <= max_chars:
            buf += unit
            continue
        if len(buf) >= min_chars:                  # 最短块保护：防「光标题」噪声块
            out.append(buf)
            buf = buf[-overlap_chars:] + unit      # 保留重叠，防答案被切断
        else:
            buf += unit                            # 缓冲太小就继续累积，跨页也继续
    if len(buf) >= min_chars:
        out.append(buf)
    return [hard_split(c, max_chars, overlap_chars) for c in out]   # 硬切兜底

L3-07 元数据与结构化清洗 ​

定义：给每一块打上「它是谁、从哪来、什么时候生效、谁能看」的标签。

字段示例用途
chunk_idSCIS:p2:c010全链路唯一稳定标识（向量下标、BM25 行号、gt 都回到它）
docSCIS文献/文档标识
page15引用溯源
section3.4.3 Reward function引用溯源 + 将来的章节过滤接口
seq全库顺序号稳定排序
时间 / 版本 / 权限effective_from、version、acl时效过滤、多租户隔离（见 ⑨ 引用与权限）

为什么这样设计：元数据是功能接口，不是装饰。没有 page/section 就没有可信的引用；没有「时间/版本」就无法回答「以哪一版为准」；没有权限标签就无法做检索期的隔离（把过滤放在检索之后等于没隔离）。

常见误区：

  • 元数据事后补：事后补的元数据往往对不上块的真实边界（块可能跨越章节，此时该标哪一节？）。
  • 清洗规则不版本化：清洗规则一变，所有块的文本都会变、所有历史指标作废。规则要有版本号并写进配置。
  • 「清洗就是删噪声」：删错比不删更糟——被误删的内容不会再出现在任何地方，而噪声至少还会被检索到、有机会被人看见。

和你自己的项目对上号 ​

这一页你的项目弹药最多，而且包含一个可以当场把面试官说服的「换尺子」案例。

1）三层切块结构（docs/projects/rag/03-chunking.md:29-36）：结构感知（按章节标题切，chunk_pages() @ingest.py:123）→ 长度约束（在结构边界内按 max_chars 切 + 重叠）→ 硬切兜底（_hard_split() @ingest.py:234）+ 最短块保护（MIN_CHUNK_CHARS = 60 @config.py:386）。

2）配置键名 ≠ 实际生效值（config.py:156-159）：

档位键名含义实际 max_chars实际 overlap_chars
"512"token 名义值1024 字符153 字符（15%）
"1024"token 名义值2048 字符307 字符（15%）

那个 ×2 的换算依据是注释里「中文约 1 字 ≈ 1 token」的经验值，而它被自己的实测推翻了：exp01_token.py 量出中文约 1.2–1.3 字符/token、纯英文可达 3+。也就是说「512 档切出 1024 字符」既不是 512 token，也不是中英一致的 token 数——中英混排语料下，同一档位里中文块的 token 数明显多于英文块。不改线上参数的理由是：改了 chunk_id 全变、gt 全部对不上、16 份历史消融报告一起作废；处理方式是把真实字符数写进文档，另写 exp18b_token_budget.py 测真实切片 token 分布。

3）「换尺子」案例（本页最该背下来的一段）：512 档 ③ 组 R@5 = 68.8%（gt 36 块 / 1.57 块每题），1024 档 ③ 组 R@5 = 76.8%（gt 30 块 / 1.30 块每题）。看起来 1024 更好——但这两行不可比：Recall@5 = |gt ∩ top5| / |gt|，分母是 gt 块数；粗切把相邻两个 gt 块合并成一块，分母从 36 掉到 30，分数自然变高。正确做法是用与切片无关的口径去比：exp30_slice_compare.py 的「覆盖率@k + probe 级 MRR」。最终保持 512 档作为线上默认，理由不是「它更好」，而是①它是全部现有指标与 gt 对应的那一档；②切块档位在这个项目里不是最大瓶颈——真瓶颈是 CPU 精排 20 对约 8.5 s 与中文查询的稀疏路失效。

4）产物与配置的偏差：全库平均块长 763 字符、最长 1132 字符，而 512 档的配置上限是 1024——配置写了上限，不等于产物满足上限（坑 10）。

5）元数据实测字段：chunk_id（SCIS:p2:c010、SCIS:p11:c052）、doc、page、section、seq、text（docs/projects/rag/03-chunking.md:104-114）。

面试怎么问 ​

Q1：你的 chunk size 怎么定的？

A（要点）：先给判据（语义完整性 / 检索单元粒度 / 上下文预算），再给自己的值，并说清这个值是在自己语料上做消融定的，没有普适最优。加分句：我配置里的键名是 token 名义值，实际生效的是1024 字符上限、153 字符重叠，这个换算的原始依据是错的，我用 tokenizer 实测推翻并写进了文档。别说：「大家都用 512」——这是最典型的减分句。

  • 追问 1：那你怎么知道 1024 字符就是好的？→ 我不知道它「最优」，我只知道它是当前所有指标与 gt 所对应的那一档，换档会让全部历史结论作废。要不要换是个要单独排期的决定，不是顺手改一行配置。
  • 追问 2：换更大的块会不会更好？→ 我试过 1024 档，原始指标看起来更好，但那是尺子变了：粗切合并了相邻 gt 块，分母从 36 降到 30。我用与切片无关的口径重测后，结论是「不可直接比较」。

Q2：overlap 取多少？为什么？

A（要点）：重叠只解决一件事——答案被切在边界上。常用区间是块长的 10%–20%，我取 15%（153 字符）。加分句：重叠是用冗余换边界安全，它不聪明但有效；语料是独立短条款时收益基本为零，是长段落连续论证时收益明显。别说：「越大越好」——重叠过大会让同一段内容被索引多遍，挤掉真正不同的证据。

  • 追问 1：怎么验证重叠有效？→ 用「事实完整性」口径：已知答案的关键串是否完整落在同一块内。这是唯一与检索器无关的口径，测的是切法本身有没有把答案切碎。
  • 追问 2：那你的块还有别的问题吗？→ 有：全库平均块长 763 字符、最长 1132 字符，而配置上限是 1024——硬切兜底与上限约束之间有缝，我把它记录为已知问题而不是假装没有。

Q3：为什么要给每块打元数据？

A（要点）：三类用途——引用溯源（page + section，让「第 15 页 4.3 节」这种说法成立）、过滤（时间/版本/权限，见 L3-26）、稳定标识（chunk_id 是向量下标、BM25 行号与 gt 的共同锚点）。加分句：元数据是接口不是装饰，事后补的元数据对不上块的真实边界——块可能跨越章节边界，那时该标哪一节本身就是个设计决策。别说：「元数据到时候再加」——权限过滤、时间过滤都依赖它，加晚了要重建整个索引。

  • 追问 1：你清洗过文本吗？怎么保证没删错？→ 清洗规则我做了版本化（v2-page-number-by-proximity）。踩过的坑是：按「孤立数字 = 页码」删，把表格里的整数单元格一起删了，结果表格类问题全部答不对——「看起来像页码」和「是页码」是两件事。
  • 追问 2：那怎么防止这类错误？→ 规则要带版本号、要能回滚、并且要有一条「用产物反查」的自检（对全库块长/块数做分布统计）。配置改了必须重新 ingest，并核对产物是否与配置一致。
