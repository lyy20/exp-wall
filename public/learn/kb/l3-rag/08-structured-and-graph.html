本页目录

结构化数据、图谱与多模态检索 ​

覆盖知识点：L3-22 L3-23 L3-24 ｜ 面试频率：中 ｜ 建议学时：17h

一句话说清 ​

向量检索只是「从一堆文本里找相似的段落」这一种取数方式；当数据是表格、是实体关系、是图片时，同一条链路要换三种完全不同的检索范式——Text2SQL 换成「精确计算」，GraphRAG 换成「图上的多跳与聚合」，多模态换成「跨模态对齐」。

为什么必须学 ​

这三项频率是「中」而不是「高」，但它们的作用是区分度：

  • 面试官问「你的系统只能答文档里写着的答案吧」，是在试探你知不知道结构化数据问答这条完全不同的路。
  • 问「总结一下你这 55 篇论文的共同趋势」，是在试探你知不知道向量检索对全局性问题（global question）天然无力——而 GraphRAG 正是为此而生。
  • 问「你的语料里有图表怎么办」，是在试探你有没有意识到多模态信息在文本抽取阶段就已经丢了。

这三题都不需要你「做过」，但需要你能说清它们各自解决什么、代价是什么、什么时候才值得上。答得出来是加分项，答不出来也不会致命——但把没做过的说成做过，会致命。

核心内容 ​

L3-22 Text2SQL 与结构化数据问答 ​

定义：把自然语言问题翻译成 SQL（或等价的查询 DSL），在数据库/表格上执行，再用执行结果组织答案。

机制：与文档 RAG 的分工是范式的差别，不是实现细节的差别：

文档 RAGText2SQL
检索对象文本块（语义相似）表与行（精确匹配与聚合）
关键动作相似度排序模式链接（schema linking）：把「上个月的销量」映射到 sales 表的 amount 列与时间条件
正确性判据证据是否支持答案SQL 执行结果是否等于预期（可精确判定）
主要失败模式召回不到 / 排序不对列名猜错、聚合函数用错、连接条件漏掉——而且语法正确、结果错得很自然
典型防护引用与拒答执行前校验 + 只读权限 + 行数上限 + 结果自检

为什么这样设计：因为有一类问题语义检索原理上答不了——「今年销售额同比是多少」「有多少条记录满足条件」。这不是「相关段落」能回答的，必须算。反过来，Text2SQL 也答不了开放式问题（「客户为什么抱怨」）。

数量级与形状：进入 LLM 上下文的不是数据行，而是表结构（表名、列名、类型、注释、示例值）。表结构越大，prompt 越长，而且列越多越容易选错列——这是 schema 检索（只放相关表/列进 prompt）存在的理由。

常见误区：

  • 「让模型直接读表就行」——小表可以；表一多列一多，模型会选错列，而且不会报错。
  • 「SQL 生成对了就万事大吉」——要防的不止是语法，还有语义错误：WHERE 条件漏了、JOIN 多对多导致行数膨胀、时间边界（含不含当天）搞错。所以必须有执行前校验（权限、只读、LIMIT）与执行后自检（行数异常、空结果、结果与问题是否对应）。
  • 「Text2SQL 是 RAG 的特例」——它是另一条取数路径，正确的架构是路由（L3-20）：结构化问题走 SQL，文档问题走向量，两边都用同一套生成与引用规范。

L3-23 GraphRAG 与知识图谱增强检索 ​

定义：从语料里抽出实体与关系构建图（或补充图的摘要层），检索时利用图上的多跳遍历与社区聚合。

机制：两步——

  1. 索引阶段：切块 → 用 LLM 做实体/关系抽取（谁和谁有什么关系）→ 建图 → 社区检测（把关系稠密的节点聚成社区）→ 为每个社区生成摘要（community summary）。
  2. 查询阶段：
    • 局部问题（local）：从问题里的实体出发，沿图做多跳邻域检索，拿到相关实体、关系与原文块；
    • 全局问题（global）：「这批文档的主题趋势是什么」这类问题，向量检索根本无力（它只能返回若干相似块，没有任何一块承载「全局」），而社区摘要可以直接作为分层聚合的原料。

为什么这样设计：因为向量检索的结构性盲区有两条——① 无法跨块推理（A 块与 B 块之间的关系，除非写在文本里，否则检索看不见）；② 无法回答全局性问题（top-k 块永远只是局部证据）。GraphRAG 用显式的图结构补第一点，用社区摘要的分层补第二点。

数量级与形状：图的构建成本主要由 LLM 抽取决定——每块都要跑一次抽取（可能还要多轮），所以它比切块 + 向量化贵一个量级，而且抽取质量决定了图的上限。检索时，局部查询的成本与邻域大小相关，全局查询的成本与社区数量相关。

常见误区：

  • 「GraphRAG 一定比向量检索好」——它换的是能力，不是普适的分数。对「找一段描述」这类问题，图上遍历不如向量相似度直接；而图上多一跳就多一分错误传播。
  • 「实体抽取可以随便抽」——抽取错的关系会让图给出看起来很结构化但事实错误的答案，比文本里的模糊表述更危险。
  • 「有了图就不需要原文」——最终答案仍要回到原文块做引用溯源，图是索引结构，不是答案来源。

L3-24 多模态 RAG（图文检索） ​

定义：把图片、图表、扫描件、版面信息也纳入检索与生成。

机制：三条路线，按「信息在哪一步保留」划分：

路线做法优点代价
OCR / 文本化把图里的文字识别成文本，走原链路复用现有链路图形、布局、颜色、趋势全丢
图注 + 上下文拼接文本块与它所在的图表一起编码（如「图 3 + 图注 + 引用该图的段落」）成本低，能回答「图 3 说明了什么」图与正文的对应关系要靠解析正确
多模态 Embedding用跨模态编码器把图与文映射到同一向量空间，直接做图文互相检索支持「以图搜文」「以文搜图」需要多模态模型；向量空间对齐质量是新的不确定源

为什么这样设计：因为科研/业务文档里大量结论就在图里（曲线趋势、对比条形、系统框图）。文本抽取阶段丢掉的这些信息，后面任何一步都补不回来——这和多模态的关系，和 L3-04 解析与切块的关系是同一件事。

数量级与形状：多模态检索的难点在粒度：一张图可能承载一整节的结论，按「一张图一块」切会让向量变成「整节的摘要」（区分度下降）；按「图 + 图注 + 正文引用段」打包更合理，但要保证这三者在解析阶段就被正确关联。

常见误区：

  • 「有 OCR 就够了」——OCR 只解决「图里的字」，不解决图表表达的数值关系（趋势、极值、对比）。
  • 「多模态 Embedding 可以直接替换文本 Embedding」——它引入了一个新的对齐质量维度，而且检索指标要重新建（题集里要有图文跨模态的题）。
  • 「先做文本，多模态以后再说」——合理，但要在评测集里留位：如果题集里一条图文题都没有，将来做完也没有判据。

和你自己的项目对上号 ​

先把边界说清楚：这三项在你的 RAG 项目里都没有实现。 面试时不能说「我做过 GraphRAG」。但有三条真实材料可以用，而且用好了效果不差：

1）你已经踩到了「表格是另一种模态」的坑。你的语料是科研论文，表格与公式在解析阶段就被有损线性化——∉ 被识别成 <（语义反转）、下标丢失、分情形结构被压成一行（docs/projects/rag/03-chunking.md:85-93）。这正好是 L3-24 那条线的最朴素版本：结论就在图表里，而文本化会把它丢掉。你的应对是把限制写进策略：「表格类事实优先引用正文」。如果面试官问「多模态你怎么看」，这个例子比任何教科书说法都有说服力：你的多模态缺口是你自己量出来的，不是猜的。

2）你的数据层已经区分了「直接来源」与「检索获得」：data/doc_sources.json 顶层记录 n_docs: 55、n_chunks: 5325、n_direct: 52、n_search: 3、n_verified: 47（_research/RAG-事实清单.md:87）。这是什么意思？——55 篇里有 3 篇不是直接获得的（通过检索获得），47 篇经过核验。这是一个「数据来源可信度」的元数据雏形，而来源可信度分级正是企业 RAG 与 GraphRAG 里「证据权重」的同一件事：不同的证据不该被同等对待。你可以在面试里把它讲成「我已经在数据层开始做来源分级」，而不要讲成「我做了知识图谱」。

3）你有一个现成的「映射表」思路可以类比：glossary.py 的 TERM_MAP 是 57 条中文→英文的映射，用来把中文查询里的领域词翻译成英文检索词。这本质上是一张人工维护的小型术语图——它和知识图谱的差别在规模、关系类型与自动抽取，不在思想。你可以这样表述：「我的术语表是实体对齐的雏形：它证明了『把查询侧的表述映射到语料侧的表述』这件事有明确收益（② 组 R@5 62.3% → 64.5%），代价是要人工维护、换语料就失效。要做成图谱就得换成自动抽取 + 关系建模，成本高一个量级，我的语料规模还撑不起这个投入。」 ——这段话既诚实又展示了判断力。

4）如果面试官追问「那你会怎么补」，给排期而不给口号：① 先在评测集里补全局性问题的一整类题（现在没有），因为向量检索对这类问题的无能为力是可测的；② 再补图文题（现在也没有），否则多模态做完无法判断有没有变好；③ Text2SQL 与你的语料无关（论文里没有可查询的结构化库），但对 YYHelp 那类有订单/工单数据的系统是刚需——这也是两个项目的能力边界差异（见 前作与 YYHelp 的能力边界）。

面试怎么问 ​

Q1：用户问「今年订单量同比多少」，你的 RAG 能答吗？

A（要点）：不能，而且这不是调参能解决的——这类问题的答案不在任何文本块里，必须算。正确做法是路由到 Text2SQL：先把「订单量」「今年」「同比」映射到表结构（模式链接），生成 SQL，执行前做只读与 LIMIT 校验，执行后做结果自检（行数异常、空结果、与问题是否对应），最后用执行结果组织答案。加分句：Text2SQL 的正确性判据比文档 RAG 更硬——SQL 的执行结果可以和预期精确比对，所以它的评测比「答案像不像」干净得多。别说：「我让模型读全部数据自己算」——数据量稍大就不可行，而且会算错还不报错。

  • 追问 1：那 SQL 生成错了怎么办？→ 分两类防：执行前（权限、只读连接、强制 LIMIT、语法校验）与执行后（空结果、行数异常膨胀、结果与问题不匹配）。还要有回退：不确定时说明「我理解的是这个口径」，把生成的 SQL 展示给用户确认。在结构化数据上，把 SQL 摊开给用户看，比在文档问答里给引用更有效，因为 SQL 是可复核的。
  • 追问 2：表很多、列很多怎么办？→ 不能把整库表结构塞进 prompt。要么做 schema 检索（按问题先选出相关表/列），要么维护视图或语义层。核心矛盾是「选错列不会报错」——所以列名与注释的质量、以及示例值，比 prompt 措辞更重要。

Q2：GraphRAG 解决什么问题？什么时候值得上？

A（要点）：解决向量检索的两条结构性盲区——① 跨块关系（A 块与 B 块的关系不写在任何单块里，检索看不见）；② 全局性问题（「这批文档的主题趋势」这类问题，top-k 块永远只是局部证据）。GraphRAG 用显式图补第一点、用社区摘要的分层聚合补第二点。加分句：它的成本主要在 LLM 抽取——每块都要抽实体关系，比切块 + 向量化贵一个量级，而且抽取质量决定图的上限；一跳就多一分错误传播。别说：「GraphRAG 比向量检索更先进」——它换的是能力，不是普适分数。

  • 追问 1：什么问题上 GraphRAG 反而更差？→ 「找一段具体描述」这类局部问题。向量相似度直接命中，图上遍历要多跳、每跳都可能偏。判断标准是问题类型分布：如果全局性问题占比很低，图上投入很难回本。
  • 追问 2：你怎么判断该不该上？→ 先看评测集里有没有全局性问题（没有就先补题，否则做完无法判断），再算构建成本（抽取调用次数 × 单次成本）与它替代掉的人工总结成本。能说清「不上」的理由，比说清「上」更能证明判断力。

Q3：你的语料里全是图表和公式，怎么处理？

A（要点）：先承认文本抽取阶段就丢了：表格被线性化、∉ 变成 <（语义反转）、下标丢失。然后给三条路线的取舍（OCR 文本化 / 图注与上下文拼接 / 多模态 Embedding），并说清各自保留了什么、丢了什么。加分句：我目前的取舍是把限制写进策略——表格类事实优先引用正文，而不是引入会「给出看起来很整齐但数字错了」的版面识别。如果我换成财报类语料，这个取舍要反过来。 别说：「我用 OCR 处理了表格」——除非真的做了，这类声称会被要求现场给一段输出。

  • 追问 1：为什么不直接上图注拼接？→ 可以，而且成本最低；但要保证图与正文的对应关系在解析阶段就是对的——我的语料里已经出现过「一节里的 6 个块全被标成 References」这类标签错乱，图注关联比 section 标签更脆弱，所以要先解决解析的可靠性再谈多模态。
  • 追问 2：那你现在最该补的是什么？→ 补评测集的题类：全局性问题、图文题、多跳题现在都是空的。没有这些题，任何新能力做完都无法判断有没有变好——这是要先做的事，不是先做功能。
