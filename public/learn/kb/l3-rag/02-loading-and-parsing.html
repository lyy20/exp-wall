文档加载与多格式解析 ​

覆盖知识点：L3-04 ｜ 面试频率：高 ｜ 建议学时：5h

一句话说清 ​

解析是整条 RAG 链路里唯一一步「损失不可逆」的工作——正文抽取错了，后面切块、向量化、检索、生成无论怎么调都救不回来，而且它不报错。

为什么必须学 ​

面试官问「你的文档怎么处理的」，通常在筛两种候选人：

  1. 只跑过教程的人。教程里语料是干净的 Markdown，一句 loader.load() 就完事；一问到 PDF 双栏、表格、公式、扫描件就答不上来。
  2. 做过真实语料的人。这类人有一个共同特征：他能举出自己语料里具体的解析损失，并说清这个损失让哪一类问题永远答不对。

这一层还决定了一个更硬的东西：你项目效果的上限。检索不到的东西一定答不出来，而解析丢掉的字符就等于没进过索引。面试里「你这套系统准确率多少」的追问，一半答案在这一页。

核心内容 ​

L3-04 文档加载与多格式解析 ​

定义：把异构文件（PDF / DOCX / HTML / Markdown / CSV / 图片扫描件）转换成带结构信息的纯文本。关键词是「带结构信息」——只吐一坨纯文本是降级做法，页码、标题层级、表格边界、段落顺序都是后面引用溯源与过滤的原料。

机制：分两层。

层做什么常见实现
格式适配层按扩展名选解析器，统一成中间结构文本类（Markdown / TXT）直接读；结构化文档（DOCX）按 XML 抽段落与样式；HTML 先去脚本样式再按语义标签抽正文；PDF 走 PDF 解析库
版面还原层把「一堆带坐标的文本块」还原成阅读顺序按坐标聚类成行 → 行成段 → 判断分栏（单栏/双栏）→ 表头页脚识别并剔除 → 标题层级识别

为什么这样设计：PDF 的底层是排版指令流，不是文档结构。它只知道「在 (x, y) 处画这串字符」，不知道什么叫段落、什么是标题。所以「读 PDF」本质上是一次版面重建，而重建规则必须跟语料长什么样绑定——换个出版社的模板，规则就可能全废。

数量级与形状：一页 A4 论文的典型形态是「几百到两千个字符、几十到上百个文本块（text block）」。分栏判断的难点在双栏：如果不做分栏检测，按 y 坐标逐行读会把左右两栏交替串成一句话，而这种串行在文本里看不出任何异常——它是通顺的乱码。

常见误区：

  • 「PDF 抽出来就是文本」：抽出来的是「文本块的集合」，顺序要靠重建。
  • 「页眉页脚只是噪声，删了没影响」：删得对是收益，删错是灾难。一个真实教训：用「孤立数字 = 页码」这条规则清理时，表格里的整数单元格也被删了，导致所有表格类问题都答不对。
  • 「复杂 PDF 上 OCR 就完了」：OCR 只解决「图画里的字」，不解决阅读顺序、表格结构、公式语义；而且 OCR 自身有错字率，会给下游引入看不见的错字。
  • 「解析是一次性的，做完就不用管了」：语料一变（换期刊模板、加中文文献），正则与规则就可能全废。

代码（伪代码，具体 API 以各家官方文档为准）：一个最小但保留了元数据的加载器长这样——

python
def load_pages(path: str) -> list[Page]:
    """返回按页组织的文本块，保留坐标与页码——后面切块与引用都要用。"""
    ext = path.rsplit(".", 1)[-1].lower()
    if ext == "md":
        return [Page(text=open(path, encoding="utf-8").read(), page=1, blocks=[])]
    if ext == "pdf":
        blocks = pdf_extract_blocks(path)         # 每个 block 带 x0, y0, x1, y1, text
        pages = []
        for pno, blocks_on_page in group_by_page(blocks):
            ordered = reconstruct_reading_order(blocks_on_page)   # 分栏 + 行聚类 + 成段
            ordered = drop_header_footer(ordered)                 # 页眉页脚：按邻近性判，不按「是不是数字」
            pages.append(Page(text="\n".join(b.text for b in ordered), page=pno, blocks=ordered))
        return pages
    raise ValueError(f"unsupported: {ext}")

和你自己的项目对上号 ​

你的科研文献 RAG 项目的解析损失是实测记录下来的，不是笼统的「可能有损失」：

  • 公式的语义反转（最值得讲的一条）：原文的分情形公式被抽成线性串——∉（不属于）被识别成 <（小于）、下标 aₙ 丢成 an、分情形结构被线性化（eval/report.md:132）。这不是格式难看，而是语义反转：任何依赖这个公式作答的问题都会得到错误答案，而链路不会报错。
  • 表格被线性化，且设计稿里说的「表格单独成块」并未实现（docs/projects/rag/03-chunking.md:38）。你的文档里写的是「未实现」，而不是照抄设计稿——这一点在面试里是加分项，因为它证明你敢区分「设计」与「产物」。
  • section 标签的两类真实故障：正则里 $ 写在了 (?:A|B) 内部、只锚定了一个分支，造出 235 个假章节标签；早期章节正则只认阿拉伯数字编号，不认 IEEE 的 II. SYSTEM MODEL / A. State Space 形式，导致 5 篇语料里有 2 篇的 section 覆盖率是 0%（126 块与 117 块两篇全丢）。
  • 一条硬纪律：表格类事实优先引用正文。这条规则本身就是对「解析有损」的工程回应——不是假装解析没问题，而是把限制写进检索与引用策略里。
  • 清洗规则的版本化：页码清理规则从「孤立数字 = 页码」改成 v2-page-number-by-proximity（按邻近性判定，config.py:307），版本号写进配置——因为清洗规则一变，所有切块都会变。

面试怎么问 ​

Q1：你的 PDF 是怎么解析的？

A（要点）：分两层说——抽取（拿到带坐标的文本块）与还原（按坐标聚类成行、成段，再做分栏判断与页眉页脚剔除），产出的中间结构保留页码与坐标，因为后面引用溯源要用。加分句：我不会说「抽出来就是文本」，PDF 的底层是排版指令流，阅读顺序是我重建出来的。别说：「我用 XX 库一句话就搞定了」——这句话会把面试官引向「那遇到双栏和表格怎么办」。

  • 追问 1：双栏排版你怎么处理？→ 先做分栏检测，再按「先左栏后右栏」排序。不做的后果是把左右两栏交替串行，而且串出来的文本是通顺的，肉眼看不出来。
  • 追问 2：那你怎么知道分栏检测对了？→ 拿几页人工核对，并做一条可自查的断言：同一段的字符宽度分布应当在分栏前后保持一致。任何解析规则都要有验证手段，不能只靠肉眼抽查。

Q2：为什么要保留页码和坐标？只留纯文本不行吗？

A（要点）：因为下游有三处要用——引用溯源（「第 15 页 4.3 节」）、章节过滤（将来按章节缩小检索范围）、排序稳定（全库顺序号）。丢掉坐标等于把这三件事的原料丢了，而且在后面任何一步都补不回来。加分句：这也是我把 page / section 写进块元数据的原因，元数据不是装饰，是功能接口。

  • 追问 1：那 section 标签准吗？→ 不完全准，而且我踩过两个具体的坑：正则的 $ 锚定写错造出 235 个假标签；只认阿拉伯数字编号导致 2 篇论文的 section 覆盖率是 0%。修正后仍有一条已知现象：块跨越章节边界时标签会「看起来偏移一格」。
  • 追问 2：那你后来怎么确认那不是偏移？→ 用一个具体块的实测证据推翻了原判断——根因是块本身就跨越了章节边界，一个块同时含上一节末尾与下一节开头是合法形态。这条结论是我自己更正自己得到的。

Q3：你的语料里有表格和公式，怎么处理的？

A（要点）：先明确说是有损的，再给具体的损失形态与影响面，最后说策略（表格类事实优先引用正文）。加分句：我算过引入版面分析工具的成本收益——识别错的表格比线性化的表格更危险，因为线性化的至少看得出是乱码，识别错的会给你一个看起来整齐但数字错了的结果。别说：「公式我做了 LaTeX 还原」——除非真的做了，这类声称会被要求现场给一段输出。

  • 追问 1：那你的引用还有什么意义？引用了也可能是错的内容。→ 我的引用校验只能验编号合法性（模型引用的 [n] 是否落在上下文范围内），不能验「引用的内容是否真的支持这个结论」，后者需要 NLI 或人工复核。这两件事我在文档里是分开写的，不会含糊成「引用已校验」。
  • 追问 2：如果语料换成财报呢？→ 那取舍要反过来：表格是主体内容、且数字错误代价极高，这时候必须上专业的版面分析，宁可多一道人工抽检。取舍跟着语料的性质走，不跟着工具的新旧走。
