生成阶段约束与 Agentic RAG ​

覆盖知识点：L3-27 L3-28 ｜ 面试频率：高 ｜ 建议学时：8h

一句话说清 ​

生成阶段决定「检索回来的东西怎么变成一句可信的话」——约束不是让模型更聪明，而是给它划出可回答的边界，越界就拒答；Agentic RAG 则把这个边界交给模型自己判断：什么时候检索、检索几次、检索不到怎么办，由模型在与工具的往复里决定。

为什么必须学 ​

  • L3-27 是幻觉治理的最后一环，也是全链路唯一能直接向用户交付价值的一环。「我限制模型只基于检索内容回答」这句话人人会说，但面试官接着会问：「那它还是编了怎么办」「没有证据时它会不会硬答」「你怎么测出它没编」——三层追问下来就能分出谁真调过、谁只是读过。
  • L3-28 是 2026 年 JD 里的热词，也是「RAG 会不会被 Agent 取代」这类开放性问题的标准入口。它考的不是你用过哪个框架，而是你能不能判断什么时候值得把控制权交给模型——这需要你对成本、延迟、可调试性有真实的体感。

核心内容 ​

L3-27 RAG 生成阶段的提示与约束 ​

定义：在生成阶段用系统提示 + 上下文格式 + 参数共同约束模型行为，核心目标有三条：

  1. 只允许基于检索内容回答——不能引入外部知识；
  2. 无证据则拒答——宁可说不知道，不可硬答；
  3. 答案必须可溯源——关键论断带引用（与 L3-25 是同一条链路的两端）。

机制：约束落在四个地方，缺一条就漏一种失败模式。

约束位置做什么防的是
系统提示明确「只用下列材料」「材料不足就按固定话术拒答」模型用参数记忆里的知识补充
上下文格式每块带可核对的身份（来源标题、页码、章节、编号）答案里的引用无法核对；以及格式错误反而诱发拒答
生成参数低 temperature、设超时与重试上限输出的随机性与不可控延迟
输出协议拒答用固定话术；引用用固定编号格式拒答与引用无法被程序识别

为什么「输出协议」这一条最容易被忽略却最关键：因为下游的评测、埋点、前端渲染都依赖它是机器可解析的。

  • 拒答用固定话术 → 评测脚本能自动判定「这题是不是拒答」，否则只能人工读；
  • 引用用固定格式 → 程序能自动校验编号合法性（L3-25 的前提）；
  • 答案结构固定 → 前端能把「出处」渲染成可点击的卡片。

数量级与形状：

  • temperature 要在 0.1 这个量级（本项目的 LLM_TEMPERATURE = 0.1，config.py:203）——事实性问答不需要多样性，热采样只会让同一个问题两次答案不同，凭空增加复现成本。
  • 超时要设，而且要短于用户的容忍上限（本项目 LLM_TIMEOUT_S = 60 s，config.py:190）；重试要有上限与指数退避（LLM_MAX_RETRIES = 3、LLM_RETRY_BASE_S = 0.8、LLM_RETRY_MAX_S = 8.0，config.py:209-211）。理由：无界重试会把一次失败放大成资源雪崩。
  • 上下文预算是硬约束：进 prompt 的块数 × 每块长度必须留在预算内侧。本项目精排后进 prompt 的是 5 条（RERANK_TOP_N = 5）；如果来源标题每块都重复一遍，光标题就占掉可观比例（见下文项目事实）。

常见误区：

  • 「提示写得越长越严越好」——约束越多，模型越容易过度保守（该答的也拒答）。提示强度与误拒率是一对需要实测调平的量，不是单方向优化的。
  • 「拒答就是失败」——在有风险的知识库场景，拒答是正确行为；要衡量的是误拒（有答案却拒）与漏拒（无答案却编）各自的代价，而不是让拒答率越低越好。
  • 「约束只在 prompt 里」——prompt 是最弱的一层。程序层能零成本拦掉的（比如精排分数明显过低）就不该交给模型去判断，那是白花一次 LLM 调用（见 ⑦ 精排与拒答阈值）。
  • 「上下文给得越多越保险」——无关块会稀释注意力并引入矛盾信源，反而降低忠实度。所以「精排后取几条」这个数是要按评测定的。

L3-28 Agentic RAG ​

定义：把检索封装成一个工具，交给 Agent（能自主决定下一步动作的循环）调用：由模型判断要不要检索、检索什么、结果够不够、要不要再检索、什么时候停。

机制：与「固定链路 RAG」的差别不在用什么模型，而在控制流的位置：

固定链路 RAGAgentic RAG
谁决定检索代码（每次必检索）模型（可能检索 0 次、1 次或多次）
轮数固定（1 轮）动态（受预算约束）
可预测性高（延迟方差小）低（轮数不定，延迟长尾）
可调试性高（链路固定，瓶颈好定位）低（每题的路径不同）
成本固定随轮数增长（检索 + 每轮一次决策调用）
适合高频、简单、要求稳定的场景复杂、多变、允许慢一点的场景

典型形态有四类，复杂度递增：

  1. 自适应检索（adaptive）：先判断问题是否需要检索（简单问题直接答，省一次检索）；
  2. 迭代检索（iterative）：检索 → 判断证据是否充分 → 不够就再检索（即 L3-21 的多跳）；
  3. 多源路由（routing）：在多个工具/数据源之间选择（向量库、SQL、API、内部工具），与 L3-20 的路由是同一件事，只是决策者从代码变成了模型；
  4. 自反思（self-reflective）：对生成的答案做一次「有没有被证据支持」的自检，不过就重检索或改答案。

为什么这样设计：因为固定链路 RAG 的结构性局限是「它必须假设每次检索都必要且够用」。真实问题分布里既有「根本不需要检索的寒暄与常识问题」，也有「一次检索明显不够的复杂问题」——固定链路在前者上多花了一次完整检索，在后者上注定答不好。Agentic RAG 用动态轮数同时换到了这两头。

数量级与形状（这是面试里最该给分寸的地方）：

  • 收益：在「检索并非总有必要」的题分布上，省掉的检索次数就是省掉的成本与延迟；在多跳题上，它把「答不了」变成「答得了」。
  • 代价：① 轮数不定 → 延迟长尾，P99 是最危险的指标；② 每轮都要一次 LLM 决策调用，所以调用次数是普通 RAG 的数倍；③ 可调试性下降——同一个问题在不同时刻可能走不同路径，出问题难复现；④ 错误传播——上一轮的错误判断会成为下一轮的前提。所以 Agentic RAG 的必备件是：最大轮数、总 token/调用预算、每步超时、以及完整的轨迹日志。（这套终止条件的通用设计见 L4 · Agent）

常见误区：

  • 「Agentic RAG 是 RAG 的升级版，应该默认用」——它换的是能力上限，代价是稳定性与可预测性。高频简单问答用它，只会把 P50 和成本一起抬高。
  • 「有了 Agent 就不需要精排/混合检索了」——恰恰相反。模型决定的是「检索几次」，不是「检索得准不准」。检索质量差时，Agent 只会多检索几次，但每次都召回同一批错的块——把钱包烧掉而不改善结果。这是最能体现判断力的一句话。
  • 「Agent 会自己找到正确数据源」——它只能在你给它的工具集合里选；工具描述写得含糊，它就会选错或不用。工具设计（名称、描述、参数、返回格式）是收益的前提而不是细节。
  • 「不需要人工确认」——只读检索可以做自动循环，但一旦 Agent 能执行有副作用的动作（写库、下单、发消息），就必须加确认与幂等（见 L4 · Agent）。这条边界与 RAG 的「只读」性质正好相反，必须分清。

和你自己的项目对上号 ​

1）生成阶段的约束，本项目有一整套真实参数（_research/RAG-事实清单.md:198 的 config.py 真源）：

参数值位置

这些数字可以直接背出来，因为它们每一个都有理由：低温度保可复现；超时防单个请求挂死；重试上限加退避防雪崩（无界重试把一次失败放大成资源雪崩）。

2）拒答是「两层」而不是「一句提示」：

  • 程序层：use_rerank and t1 < REFUSE_THRESHOLD 时直接返回固定话术，零 LLM 成本（generate.py:350-449、streaming.py:65-190）。
  • 模型层：提示约束下模型自报证据不足，作为兜底。

所以「我们拒答做得准」这个说法要拆成两层来谈，而且必须分开测误拒率：仅阈值层 1.6%，阈值层 + 提示层自述 6.5%（另一次 5.6%），③ 组 124 题口径下双层 7.3% / 拒答准确率 100.0% / 漏拒 0。这三行来自不同批次，不能混着用——面试时主动说明「这些数字口径不同、我不把它们混起来讲」，比报一个更漂亮的数更有分量。

3）最能证明你「真做过」的一个细节：拒答的随机性签名。 config.py:195-199 记录的现象是：23 道可回答题里每轮固定有 3 道被误拒，但每轮中招的题不一样（S01/S15/M08 → S15/M05/M08）。这说明误拒率是一个统计量，不是一组固定的坏样本——盯单题找根因是找不到的，必须看分布。这条认识只有真的反复跑过评测的人才有。

4）上下文格式直接影响了拒答率——这是「生成约束」最反直觉的真实案例：早期上下文里用文件名当来源（例如写「来源：SCIS 第 15 页」），模型无从知道 SCIS 指哪篇论文，在「不得猜测」的约束下倾向拒答。改成论文标题、并且标题只在开头声明一次之后，既解决了拒答，又省了开销（标题约 140 字符 × 5 块 = 700 字符，约占上下文 17%）。教训：上下文写得让模型「无法核对」，会把它的保守行为放大成误拒——这不是模型能力问题。

5）Agentic RAG：本项目没有做，而且不该硬讲做了。 现状是固定单轮链路：retrieve(query, use_sparse=True, use_rerank=True, verbose=False, final_k=None)（retrieve.py:255-336）里检索路径由参数决定，不由模型决定。

但这里有一个你必须想清楚的分寸，因为很多人会答错：「项目延迟高」不能用来反对 Agentic RAG。 本项目的延迟账是——检索 P50 14.47 s（含 CPU 精排约 8.5 s），而 LLM 生成 P50 只有 1.26 s（docs/projects/rag/05-rerank.md:89-108）。瓶颈在检索的 CPU 精排，不在 LLM。所以正确的说法是：

Agentic RAG 的成本主要是多轮检索 + 每轮一次决策调用。我现在的延迟瓶颈本来就压在检索侧（单次检索 14.47 s，其中精排 8.5 s），在把精排优化掉之前引入多轮检索，会把最贵的那一步乘上轮数——这是我不做的第一个理由。第二个理由是可调试性：我现在的链路固定，失败可以归因到具体一步；换成动态轮数后，同一个问题两次路径可能不同，我现有的评测（124 题、固定口径）没法直接比较。第三个理由是评测缺口：我的题集里没有多跳题、也没有「不需要检索」的题，做完无法判断有没有变好。

先补评测、再补能力——这是判断力，不是保守。如果面试官追问「那什么时候你会上」，答案是：① 精排先降到秒级以内；② 题集里补上多跳与免检索两类题；③ 用最大轮数 + 总预算 + 每步超时 + 轨迹日志四条约束把不确定性关起来。这样它就从一个「炫技」，变成一个可测、可控、可回退的能力。

另外可以提一句已有雏形：glossary.py 的查询扩展、retrieve() 的开关参数（use_sparse / use_rerank）、以及 verbose=True 打印重排名次变化——这些都是「让链路可观察、可开关」的准备。Agentic 化的第一步不是接框架，而是把每个决策点暴露出来。

面试怎么问 ​

Q1：你说只让模型基于检索内容回答，那它还是编了怎么办？

A（要点）：prompt 是最弱的一层，所以要有程序层兜底：① 明显没有证据时（精排 top1 分数过低）程序直接拒答，不调模型——零成本；② 有证据时让模型回答，然后程序校验它引用的编号是否真的在本次上下文里；③ 校验不过就重试或降级为「证据不足」。加分句：还要能区分两种失败——「编造内容」和「引用了不存在的编号」是两件事，后者可以用代码自动发现，前者只能靠人工抽检或更强的校验。别说：「我在 prompt 里强调了不要编」——这只说了一层，而且是最弱的一层。

  • 追问 1：上下文里没有答案时它会硬答吗？→ 会，所以约束必须显式给「拒答的出口」：提示里给出固定的拒答话术，并且程序能识别这句话。让拒答有协议，才能测它。
  • 追问 2：你怎么衡量约束有没有效果？→ 分两层测误拒率（仅阈值层 1.6% vs 加上提示层自述 6.5%）——如果混在一起测，就永远说不清是拦太狠还是模型太保守。另外要接受一个事实：误拒是统计量不是固定样本，我这边 23 道可回答题每轮固定 3 道被误拒，但中招的题每轮不同。

Q2：什么时候该用 Agentic RAG，什么时候不该用？

A（要点）：判断依据是问题分布与控制流需求。如果问题里既有「不需要检索」的，也有「一次检索明显不够」的，Agentic 换来的是两头收益；如果绝大多数问题都是「一问一查一答」，它就是纯成本。加分句：还要看可调试性预算——动态轮数意味着同一问题两次路径可能不同，你的评测口径和日志必须能承受这一点。别说：「Agentic RAG 更先进所以要用」——它是能力上限的交换，不是免费升级。

  • 追问 1：Agentic RAG 能解决召回不准吗？→ 不能，这是最容易被搞混的一点。模型决定的是「检索几次」，不是「检索得准不准」。检索层差的时候，Agent 只是多检索几次、每次召回同一批错的块——白花预算。所以要先修检索（混合检索 + 精排），再谈 Agentic。
  • 追问 2：那它的必备件是什么？→ 四条：最大轮数、总调用/成本预算、每步超时、完整轨迹日志。缺任何一条，出问题都无法定位；再加上一条边界：只读检索可以自动循环，有副作用的动作必须人工确认与幂等（这与 RAG 的只读性质正好相反）。

Q3：你的项目为什么不做 Agentic RAG？

A（要点）：用真实数字回答，不用感觉回答。我的检索 P50 14.47 s（其中 CPU 精排约 8.5 s），而 LLM 生成 P50 只有 1.26 s——瓶颈在最贵的那一步，多轮检索等于把最贵的乘上轮数。另外我现有评测是固定口径（124 题），题集里没有多跳题与免检索题，做完无法判断有没有变好。加分句：所以我的顺序是「先补评测题类 → 再优化精排 → 最后才引入动态轮数」，并且引入时要带最大轮数、预算、超时、轨迹日志四条约束。别说：「Agentic RAG 我打算以后做」——只给愿望不给判据，等于没回答。

  • 追问 1：你有没有已经有雏形的地方？→ 有：查询扩展、检索开关参数（use_sparse / use_rerank）、以及打印重排名次变化的调试开关——Agentic 化的第一步不是接框架，而是把每个决策点暴露成可观察、可开关的接口。
  • 追问 2：如果现在让你上线 Agentic RAG 你会先做什么？→ 先做评测集：加多跳题和免检索题，并给每条题标上「最少需要几次检索」——这个标注本身就是路由器的训练/评测依据。没有它，任何路由实现都无法验收。
