LoRA / QLoRA 实操与全参微调、分布式训练 ​

覆盖知识点：L7-03、L7-04 ｜ 面试频率：高 ｜ 建议学时：12h

一句话说清 ​

L7-03 讲的是"用最少的显存换来可控的行为改变"：LoRA 靠一个低秩增量 把可训练参数量压到基座的零头，QLoRA 再把冻结的基座量化到 4-bit，于是单卡也能跑领域微调。L7-04 讲的是"当 LoRA 不够用或者要动全参时，显存账单怎么算、算不过来怎么摊"：全参微调的显存不主要由参数量决定，而是由优化器状态（Adam 一动一静两份状态）决定；摊的办法是 ZeRO 的三级分片，再加上混合精度、梯度累积、梯度检查点这几样"用计算与通信换显存"的手段。这两节连起来的核心能力是：给定模型规模与显卡，判断"能不能训、用什么配置训"。

为什么必须学（面试官视角） ​

这是 L7 层里最容易被问出真实水平的一节，因为它的答案全都是数字与取舍，编不出来。面试官通常从一条开放问题切入：

「给你一张 24G 卡，要微调一个 7B 模型，怎么做？」

这一问能同时考出四件事：

  1. 你会不会先算显存——还是直接说"跑 LoRA 就行"。先估算再选方案，是工程能力与背诵的分水岭。
  2. 你知不知道 LoRA 的参数量在哪儿——target_modules 选哪些层、rank 调大调小分别影响什么。
  3. 你知不知道 QLoRA 省的是显存、付出的是什么（不是免费的）。
  4. 你能不能把"全参微调"讲成一个显存分配问题——而不是"要用 DeepSpeed"。

⚠️ 本节最大的坑是"数字背得很熟但没验证过"。所以下面所有具体数值要么标口径、要么标「以官方文档为准」、要么写"常见区间、无普适最优"。面试里最有说服力的不是"我记得 r=8"，而是"我会怎么扫这个参数"。

LoRA 冻结原权重 ，只训练一对低秩矩阵 、，前向变成：

这一页只讲三件 L1 没讲的事：① 参数怎么选（不是选"最优值"，是选"扫的策略"）；② QLoRA 的真实代价；③ 显存账单怎么算、算不过来怎么摊。

四个参数各自的含义与取舍方向 ​

用 PEFT 的接口写出来大概是这个形状（具体参数名、默认值、以及不同版本的行为差异，请以 PEFT 官方文档为准）：

python
from peft import LoraConfig, get_peft_model
# 具体导入路径与参数名以 PEFT 官方文档为准

lora_cfg = LoraConfig(
    r=16,                                   # 低秩维度：唯一的"容量"旋钮
    lora_alpha=32,                          # 缩放系数，实际步长与 alpha 成正比
    lora_dropout=0.05,                      # 只作用于 LoRA 分支，不是全模型 dropout
    target_modules=["q_proj", "v_proj"],    # 注入哪些层：决定"改哪里"
    bias="none",                            # 是否连 bias 一起训
    task_type="CAUSAL_LM",                  # 任务类型，影响哪些模块可被注入
)
model = get_peft_model(base_model, lora_cfg)
model.print_trainable_parameters()          # 必须打印：确认可训练参数量符合预期

① r：容量旋钮，不是"越大越好" ​

  • 作用是限制增量的秩。 越大，能表达的改动越复杂，可训练参数量与优化器显存也线性上升。
  • 不存在普适最优值。 常见做法是从一个较小的值起步（个位数到几十这个区间在小数据集上很常见），在你自己的验证集上对比效果，再决定是否加大。
  • 判断依据是任务类型：风格与格式对齐（改"怎么说"）通常需要小 rank；注入新知识、新语言、新模态（改"知道什么"）往往需要更大容量——但这条也只能作为方向，不是数值依据。
  • 绝对不能说的：「LoRA 的最佳 rank 是 8」。任何没有在验证集上扫过的具体数字，都会被追问"你怎么知道的"。

② alpha：与 r 绑在一起看 ​

因为步长里有 这个缩放，只改 r 不改 alpha，等于同时改了容量和学习到的更新幅度——两个变量纠缠在一起，实验就没法归因。

工程上常见的处理是把两者的比例当成一个整体来调（例如让 alpha 与 r 成固定倍数），这样单独扫 r 时缩放是稳定的。具体比例没有普适最优，要在验证集上扫。

③ target_modules：这一项的影响常常比 r 更大 ​

它决定把 LoRA 注入到哪些线性层。三种常见策略：

策略含义影响
只注入注意力投影只改 attention 的若干投影层参数量最小，通常够改"风格与格式"
注意力 + MLP覆盖更完整的 Transformer block容量显著变大，能承载更强的行为改变
全部线性层把所有线性层都注入参数量最大，显存与训练时间都上升

为什么这一项常比 r 更关键：r 只是限制每个注入点的容量上限，而 target_modules 决定有多少个注入点。在"注入点很少"的前提下把 r 调大，收益远小于把注入点铺开。

⚠️ 具体该写哪些模块名，取决于基座模型的实现（不同模型的注意力层命名不同，有的还有 GQA / MQA 带来的形状差异）。不要凭记忆写模块名清单——去官方文档或直接 print(model) 看实际层名。

④ lora_dropout 与 bias ​

  • lora_dropout 只作用在 LoRA 分支上，不改变基座的前向。小数据集上它是常用的防过拟合手段。
  • bias 通常设为不训练（"none"）。改 bias 会动基座参数，与你选 LoRA 的初衷（只加增量、可卸载）相冲突。

QLoRA 省的是显存，付出的是什么 ​

QLoRA 的思路是：冻结的基座权重用 4-bit 存（常见是 NF4 这类为近似正态分布权重设计的数据类型），前向时按需反量化成计算精度；同时用分页优化器缓解显存尖峰、用梯度检查点换激活显存。

必须讲清的三件事：

  1. 省下来的是"权重常驻显存"。 7B 的 fp16 权重与 4-bit 权重的差距是数倍量级——这正是单卡能跑的来源。
  2. 付出的是吞吐。 反量化是有成本的，同样的训练步数，QLoRA 通常比 fp16 的 LoRA 慢。所以只有"显存不够"时才用它，不是"更快的方法"。
  3. 基座被量化了，精度有损。 影响程度与数据类型、分组大小、以及你是否把某些层排除在量化之外有关。这些选项的具体名称与默认值以官方文档为准。
python
# 加载顺序很重要：先按量化配置加载模型，再套 LoRA
# 具体类名、参数名与各字段默认值以 transformers / bitsandbytes / PEFT 官方文档为准
from transformers import AutoModelForCausalLM, BitsAndBytesConfig

bnb = BitsAndBytesConfig(load_in_4bit=True)   # 其余量化细节参数以官方文档为准
base = AutoModelForCausalLM.from_pretrained("your-base-model", quantization_config=bnb)
# 再套 PEFT 配置；训练前通常还需要一步"为 k-bit 训练做准备"的处理

QLoRA 里一个高频陷阱：4-bit 加载的模型不能直接 merge_and_unload 出可用的 fp16 权重——量化的基座合并后精度仍然受损。要得到干净的合并权重，得在非量化的基座上加载 adapter 再合并。

训练中必须盯的几件事 ​

指标为什么盯它异常信号
可训练参数量 / 总参数量确认 target_modules 真的命中了预期层比例异常小或等于全参 → 配置没生效
单步显存峰值决定能不能加 batch / 加长度峰值贴满显存 → 先降序列长度再降 batch
loss 曲线（含验证集）过拟合与欠拟合的分界训练集降、验证集升 → 该用更大 dropout、更小 rank、或更早停
梯度范数 / 是否出现 NaN混合精度下的数值稳定性出现 NaN → 优先查学习率与是否开了 fp16 而非 bf16
吞吐（tokens/s）决定实验迭代速度突然掉一半 → 常见原因是数据侧长度分布变了

「先跑通再调参」这条纪律在这里的具体形式是：先用极小数据量（几十条）跑几十步，确认 ✅ 可训练参数量对、✅ 显存不炸、✅ loss 在下降、✅ checkpoint 能存能load，然后再上全量数据。把"管线通了"和"数据够了"分开验证——这两个结论经常被混为一谈。

L7-04 全参微调的显存账单 ​

先算账：训练显存花在哪四块 ​

显存项fp16 混合精度下的粗算说明
模型权重2 字节/参数推理也要花
梯度2 字节/参数只有可训练参数才有
优化器状态最大的一块Adam 每个参数要存一动一静两份状态，fp32 下可达 8 字节/参数
激活值与 batch × 序列长度 × 层数 强相关随序列长度近似线性上涨，常常是长上下文训练的真正瓶颈

关键结论（也是面试答案的骨架）：LoRA 省的不是权重显存，是"梯度 + 优化器状态"这两块——因为可训练参数只剩零头，Adam 的状态也就只剩零头。所以 7B 全参微调在一张 24G 卡上装不下，而 LoRA 可以，差距主要不在权重，在优化器状态。

⚠️ 上面是量级估算，不是精确公式。 实际占用还受框架实现、并行策略、算子融合、是否开梯度检查点等因素影响。答辩时给"哪一块最大、大致几倍关系"，比背一个精确 GB 数更安全——后者一被追问细节就崩。

ZeRO：把"重复存"变成"分开存" ​

数据并行（DP）下，每张卡都持有一份完整的权重 + 梯度 + 优化器状态——这部分是纯冗余。ZeRO 的思路是把这些状态沿数据并行维度切分，按切分范围分三级：

级别切分对象省下的大头代价
ZeRO-1优化器状态最大（优化器状态本来就最大）通信开销小，性价比最高
ZeRO-2+ 梯度梯度那块通信增加
ZeRO-3+ 模型权重三者全切通信最重；每层前向都要临时聚合权重
ZeRO-Infinity / offload把状态放到 CPU 内存或 NVMe显存不够时的兜底带宽成为瓶颈，速度显著下降

"为什么这样设计"：切得越多，单卡显存占用越低，但通信与聚合的代价越高。所以选级别的原则不是"越高越好"，而是**"够装下"就行**——能跑 ZeRO-1 就别上 ZeRO-3。

三种并行不是为了省显存 ​

除了 ZeRO，还有两种切模型本身的并行方式，它们解决的是"单层都放不下"或"层数太多"的问题：

  • 张量并行（TP）：把单个层内的矩阵按维度切开（例如把 Linear 的输出维切开、在远端做归约）。通信在每层内都发生，所以对带宽要求最高，通常只在单机内做。
  • 流水线并行（PP）：把不同的层分到不同设备上，前向像流水线一样依次经过。代价是气泡（bubble）——靠 micro-batch 填充来缓解，但填充不满就有空转。
  • 专家并行（EP）：MoE 模型按专家切分。这是 MoE 的特有维度，与 TP/PP 正交。

ms-swift 的文档明确列出了对 Megatron 的 TP / PP / CP / EP 并行组合的支持（见下页的项目事实），具体并行组合与参数名以各框架官方文档为准。

混合精度、梯度累积、梯度检查点、checkpoint 管理 ​

这四样是**"用计算换显存"与"用小卡模拟大 batch"**的标准工具：

手段做法换来什么 / 代价
混合精度权重与计算用低精度，累加与优化器状态用高精度显存与速度双收益。bf16 的数值范围与 fp16 相同但精度更低，却不需要 loss scaling——所以稳定性通常更好
梯度累积累积 N 个 micro-batch 的梯度再更新一次用时间换来等效大 batch。注意与学习率调度、warmup 步数的口径要一起改（否则等于偷偷改了训练配方）
梯度检查点前向不存全部激活，反向时重算激活显存大幅下降，代价是额外一次前向（时间换显存）
checkpoint 管理定期存 + 保留最优 + 能从任意点续跑这不是优化项，是必需品：长任务中途崩了不能续跑，等于把前面几小时白跑

checkpoint 管理的三条硬要求（这条在面试里几乎没人讲，讲了就区分度极高）：

  1. 可续跑：存的不只是权重，还要有优化器状态与步数，否则续跑等于重新开始。
  2. 存得下：LoRA 的 adapter 通常只有几十 MB 量级，全参微调则不然（7B 的 fp16 权重本身就有十几 GB 量级），要考虑存盘空间与频率。
  3. 能验真：存完必须至少 load 一次跑一步前向。"脚本报成功"不等于"文件可用"——这条纪律与项目里"设了 env 却不生效"是同一类：契约不一致、而且不报错。

LoRA 与全参微调：什么时候选哪个 ​

维度LoRA / QLoRA全参微调
可训练参数基座的零头全部
优化器状态显存极小最大项，随参数量线性涨
单卡可行性单卡 24G 级别可以尝试小模型通常需要多卡 + ZeRO
表达能力上限受低秩限制，改风格/格式通常够，注入大量新知识可能不够上限最高
部署adapter 可单独加载 / 切换 / 卸载，多任务可共用一份基座改了就改了，多任务要各存一份完整权重
推理延迟合并后不增加不增加
迭代成本低（checkpoint 小、可快速回滚）高
遗忘风险相对更可控（基座被冻结）更高，需要更严格的验证集与配比控制

选择原则（可以直接当面试答案）：

  1. 先问"要改的是什么"：改输出格式、语气、任务范式 → 先试 LoRA；要注入大量新知识、要让模型在某个专业域整体变强 → 才考虑全参。
  2. 再问"资源够不够"：LoRA 能在单卡上把实验迭代跑起来，全参微调的每一轮实验都贵得多。
  3. 最后问"部署形态"：如果要多租户 / 多任务共用基座，LoRA 的 adapter 切换能力是结构性优势。

"为什么不做全参微调"在面试里是一个非常强的回答——只要你给的是资源约束与效果预期的取舍，而不是"太贵了"。见下面的项目对接。

常见误区 ​

  • ❌ 「LoRA 的 rank 越大效果越好」。 rank 只是容量旋钮，超过任务所需之后收益递减，还会更容易过拟合（可训练参数变多，小数据上更容易记住样本）。
  • ❌ 「QLoRA 比 LoRA 快」。 反之：它省显存，但反量化有成本，吞吐通常更低。
  • ❌ 「全参微调一定要多机多卡，没别的办法」。 单卡也能全参微调很小的模型；而大模型的决定性因素是优化器状态，ZeRO-1 常常一次就够。
  • ❌ 「用了 DeepSpeed 配置就一定能跑」。 配置与模型结构、卡数、批次大小强耦合；换个卡数或换个基座，原来的配置经常直接失效。配置是实验记录的一部分，必须随实验一起存档。
  • ❌ 「训练 loss 降了就说明成功」。 见 指令微调数据构造 的四条质量判据——没有验证集的训练，是在盲飞。
  • ❌ 「LoRA 可以随便叠，多个 adapter 一起加」。 多个 adapter 的效果不是简单相加，同时启用需要各自的缩放系数与冲突处理，行为难以预测。不要当作默认可用的技巧。

但这一页的判断方法你在项目里是完整用过的，而且用在了同一个位置上："先算账，再选方案"。

① 你的第一个微调候选对象不是生成模型，而是 Reranker ​

这是 微调决策 留下的结论，在实操层面要补一句为什么：

你的 RAG 链路里，精排是延迟的主因——端到端 P50 15.66 s，其中检索（含精排）P50 就占 14.47 s，LLM 生成只有 1.26 s。而精排的耗时来源是 Cross-Encoder 要对每一对 (query, chunk) 前向一次，RERANK_TOP_N = 5 意味着候选池 FUSED_TOP_K = 20 要算 20 对，CPU 上 20 对约 8.5 秒。

这正好落在本页的取舍框架里：

  • 要改的不是"模型知道什么"（那是 RAG 的事），是"模型在这个领域的排序偏好"——用（query, 正例 chunk, 负例 chunk）作为训练信号，让精排在这个语料上更准。这属于"改行为"，是 LoRA / 参数高效微调的典型场景。
  • 但收益要从评测口径验证：你现在的检索三档实测是 ① 纯向量 R@5 64.4% ｜ ② 混合无精排 59.1% ｜ ③ 混合+精排 71.8%，MRR 0.502 → 0.714。也就是说精排目前贡献了 +12.7 pp 的 R@5——先把已经拿到手的这部分用好（比如把精排从"每对一次前向"改成批量化推理，或者换更小的精排模型做粗筛），比训练一个新精排的收益更确定、成本低一个量级。
  • 如果真要做微调，Embedding 侧同样有明确证据支撑：你实测过 bge-m3 不归一化时「语义相反的近义缩写」余弦高达 0.881、反而超过真正同义改写的 0.599。这是一条可量化的失败案例——它同时是"要不要动 Embedding"的判据，也是微调后必须回归的测试项（归一化的收益已经拿到，任何改动都不能把它弄丢）。

② "第一候选是 Embedding / Reranker"在显存账单上的含义 ​

把这一页的算账框架套到这两个候选上，结论很直观：

候选模型规模量级全参可行性LoRA 可行性
Reranker（Cross-Encoder）与 Embedding 同量级（你用的 bge-reranker-v2-m3）小模型，单卡全参也不是不可能当然可以
Embedding（bge-m3）同上，但输出是 1024 维向量同上同上

最后一行才是关键：你的生成侧走的是 OpenAI 兼容协议的 API（config.py:189 里 LLM_MODEL = os.environ.get("RAG_LLM_MODEL", "deepseek-chat")，base_url 是 https://api.deepseek.com/v1）。没有权重，就没有"全参微调"这个选项——这是"用 API"换来的灵活性所付的代价。面试里如实说出这一层，比含糊说"生成模型太大了训不起"精确得多。

③ 正确的顺序是「先补评测，再考虑微调」 ​

理由不是"没有 GPU"，而是一个你已经实测出来的数字（详见 偏好优化与 RL 后训练）：

YYHelp 的 Gate-1 用 40 题 × 2 臂做了配对检验，结论是多智能体相对单智能体没有统计显著收益：任务完成率 40/40 vs 39/40，差 +0.025，置信区间跨零；两臂 39/40 同对同错 → 有效判别样本 n_eff = 1；功效分析给出 +5 pp 需要 76 题。

这条结论直接决定了微调的优先级：如果你现在去微调，训完你没有任何工具能判断它是否变好了。40 题、n_eff = 1 的评测集，连 +5 pp 都测不出来。在测量精度不够的时候做优化，得到的是一个无法归因的结果。

而你手上其实已经有搭评测集所需要的一切：评测集本身有 8 个字段（qid / type / question / query_used / answerable / gt_chunk_ids / gt_hint / notes），五类题型分布是 single_hop 12 / synonym 8 / unanswerable 8 / multi_hop 6 / exact_term 6——这套结构本身就是"训练集该覆盖哪些类别"的维度表（见 指令微调数据构造）。

④ 如果真要在单卡上跑一次微调，第一步做什么 ​

不是装 DeepSpeed，也不是配分布式——按本页的顺序，第一步是冒烟实验：

  1. 选最小可行配置：Reranker 这类小模型做 LoRA，用几十条样本先跑几十步。
  2. 只验证四件事：print_trainable_parameters() 的比例对不对；单步显存峰值多少；loss 是否在下降；checkpoint 存完能不能 load 回来跑一步前向。
  3. 把这次冒烟的所有配置（基座、rank、alpha、target_modules、序列长度、batch、随机种子）连同显存实测值一起存档——因为这一页最核心的结论就是：没有普适最优配置，只有"你在哪张卡、哪个数据上实测出来的配置"。

一句话总结这一节：你没有跑过训练，但你已经在同一个位置做过"先算账、再选方案"的决定——精排 20 对 8.5 秒告诉你瓶颈在检索侧，n_eff = 1 告诉你测量精度不够。这两条结论指向的都是"先补测量、再动参数"，而不是"先上一个微调"。 面试里这么讲，比编一个训练经历强得多。

面试怎么问（≥3 组） ​

Q1：给你一张 24G 卡，微调一个 7B 模型，你怎么做？

A（要点，按这个顺序说）：先算账再选方案。训练显存分四块——权重、梯度、优化器状态、激活值，其中优化器状态是最大的一块（Adam 每个参数要存一动一静两份状态）。全参微调 7B 在单张 24G 上装不下的主要原因不是权重，是优化器状态。而 LoRA 恰恰省的正是"梯度 + 优化器状态"——可训练参数只剩零头，所以单卡可行。因此首选 LoRA；如果 LoRA 的 fp16 基座权重仍然装不下，再降级到 QLoRA（4-bit 存冻结基座），代价是吞吐下降。 加分句：「我会先算再试，而不是先跑再 OOM。而且我会先跑 30 步的冒烟实验：打印可训练参数量比例、记单步显存峰值、确认 loss 在降、确认 checkpoint 能存能 load——这四件事全过再上全量数据。我项目里的习惯也是这样：判据要能自动复核，而不是靠人记得。」 别说：「跑 LoRA 就行」——后面的"为什么 LoRA 省得下来"你答不上来，这一问就废了。

  • 追问（一层）：LoRA 省的是哪几块显存？为什么？
  • 追问（二层）：如果换成 72B、两张 80G 卡呢？你会怎么改方案？
  • 追问（三层）：同样显存预算下，你会把预算花在"更长序列"还是"更大 batch"上？为什么？

Q2：r、alpha、target_modules 你怎么定？

A（要点）：这三个参数没有普适最优值，我的做法是定扫的策略而不是背数字。 ① r 是容量旋钮，从较小值起步，在自己的验证集上对比；改风格与格式通常小配置够，注入新知识往往要更大容量。② alpha 必须和 r 绑在一起看——因为步长里有 的缩放，只改 r 不改 alpha 会让"容量"与"更新幅度"两个变量纠缠，实验没法归因，所以常见做法是保持两者比例不变再扫 r。③ target_modules 的影响常常比 r 更大——它决定注入点的数量，而 r 只决定每个注入点的上限；在注入点很少的前提下把 r 调大，收益远小于把注入点铺开。 加分句：「还有一个细节：具体写哪些模块名不能凭记忆——不同基座的注意力层命名不一样，我会直接 print(model) 看实际层名，或者查官方文档的模板配置。猜参数的教训我踩过一次：getattr(llm, "model", "") 在 graph/plan.py 和 graph/supervisor.py 里逐字复发过——猜参数的写法会在多个副本里同时错，而且不报错。」 别说：「r=8、alpha=16 是标准配置」——只要面试官问"你的数据上验证过吗"，这句话立刻变成减分项。

  • 追问（一层）：为什么 alpha 要和 r 一起改？
  • 追问（二层）：小数据集上把 r 调大，你预期会看到什么现象？
  • 追问（三层）：如果验证集只有 40 题，你怎么判断 rank 该调大还是调小？

Q3：全参微调和 LoRA，你选哪个？

A（要点）：按三个问题依次判断：① 要改的是什么——改输出格式/语气/任务范式，先试 LoRA（改行为）；注入大量新知识、让模型在某个专业域整体变强，才考虑全参（改知识）。② 资源够不够——LoRA 能在单卡上把实验迭代跑起来；全参微调每一轮实验都贵得多，通常要 ZeRO 配多卡。③ 部署形态——要多任务共用基座、要能热切换，LoRA 的 adapter 是结构性优势（全参是"改了就改了"，每个任务一份完整权重）。另外遗忘风险上全参更高：基座被冻结时，LoRA 对通用能力的破坏相对可控。 加分句：「我还会补一条现实的约束：如果模型是通过 API 调用的，全参微调根本不在选项里——没有权重就没有微调。我项目里的生成侧就是这样，走 OpenAI 兼容协议调 deepseek-flash / deepseek-v4-pro，base_url 指向 https://api.deepseek.com/v1。所以真要动参数，我的候选只可能是自己部署的 Embedding 或 Reranker。」 别说：「全参效果肯定比 LoRA 好」——在有低秩限制的前提下这只是方向性判断，且没有考虑数据量与评测精度。

  • 追问（一层）：LoRA 合并回基座之后，推理延迟会变吗？
  • 追问（二层）：多个 LoRA adapter 能同时启用吗？效果能相加吗？
  • 追问（三层）：你怎么判断一次微调是"改了行为"还是"注入了知识"？

Q4：DeepSpeed 的 ZeRO 三级分别切什么？你会选哪级？

A（要点）：ZeRO-1 切优化器状态，ZeRO-2 再切梯度，ZeRO-3 再切模型权重。选级的原则是"够装下就行"，不是越高越好——切得越多，通信与聚合代价越大；ZeRO-3 每层前向都要临时聚合权重，ZeRO-Infinity 把状态搬到 CPU / NVMe 会受带宽限制。因为优化器状态本来就是最大的一块，ZeRO-1 常常一次就够。 加分句：「另外两个容易混的维度我会分开讲：ZeRO 是"把重复的副本切开"，TP / PP 是"把模型本身切开"。TP 切单层内的矩阵、每层都要通信、对带宽要求最高，通常只在单机内做；PP 切不同层、代价是流水线气泡。并行方式的参数名与组合支持情况以各框架官方文档为准——ms-swift 的文档提到支持 Megatron 的 TP/PP/CP/EP 组合，但具体配置我不会凭记忆写。」 别说：「ZeRO-3 最强所以用 ZeRO-3」——这会把通信代价与吞吐损失全带上，而且往往并不必要。

  • 追问（一层）：为什么优化器状态是最大的一块？
  • 追问（二层）：梯度累积和增大 batch 有什么本质区别？改梯度累积时还要一起改什么？
  • 追问（三层）：混合精度里 fp16 和 bf16 你选哪个？为什么？

Q5：训练跑到一半崩了，怎么办？

A（要点）：这要靠 checkpoint 管理，不是靠运气。三条硬要求：① 可续跑——存的不能只有权重，还要有优化器状态与步数，否则续跑等于重新开始；② 存得下——LoRA 的 adapter 只有几十 MB 量级，全参微调则要考虑存盘空间与频率（7B 的 fp16 权重本身就有十几 GB 量级）；③ 能验真——存完必须至少 load 一次跑一步前向。 加分句：「第 ③ 条我会特别强调，因为**"脚本报成功"不等于"文件可用"**。我在项目里吃过同一类亏：设了环境变量但 import 时机不对，结果不生效、而且不报错——后来的判据就升级成"配置注入的时机是契约的一部分"。存 checkpoint 也一样：不 load 一次，你就不知道它能不能用。」 别说：「重新跑一遍就行」——这是把可观测性问题当运气问题。

  • 追问（一层）：除了权重，checkpoint 里还必须存什么？
  • 追问（二层）：怎么保证续跑之后的学习率调度是对的？
  • 追问（三层）：如果训练日志只记了 loss，出问题时你还缺什么信息？
