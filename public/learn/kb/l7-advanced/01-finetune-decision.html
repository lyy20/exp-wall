微调决策：什么时候该微调 ​

覆盖知识点：L7-01 ｜ 面试频率：高 ｜ 建议学时：3h

一句话说清 ​

「该不该微调」不是一个技术问题，是一个把目标拆成「缺知识」还是「缺行为」的问题：缺知识（模型不知道你的私有事实、事实又天天变）优先走 RAG；缺行为（输出的格式、口径、风格、领域术语不稳定）才轮到微调；两者都不缺就先改 prompt。这条判据的落脚点不是「哪个更先进」，而是三条路线的代价差一到两个数量级，而微调多出来的那部分代价大部分花在数据和评测上，不是花在 GPU 上。所以真正会拦住你的往往不是显存，是你拿不出一个能判断"变好了没有"的评测集。

为什么必须学（面试官视角） ​

这是大模型岗位最高频的选型题，也是最能一眼分出「做过」和「背过」的题。面试官问它的形式通常是现成的：

  • 「你的项目为什么不做微调？」——这是一道送分题，前提是你能说出三条具体的否定理由（数据、评测、收益），而不是「没时间」。
  • 「如果让你优化你的意图分类 / 拒答判断，你会微调吗？微调哪个模型？」——考的是你知不知道该微调的不一定是生成模型（见下文「该微调的候选排序」）。
  • 「RAG 和微调能不能一起用？」——考你是否理解两者修的根本不是同一个东西。

答错的典型形态有三种，都会被直接判定为经验不足：

  1. 把 RAG 和微调当同类竞品（「RAG 更便宜所以用 RAG」）——它们一个是注入上下文，一个是改参数，修的不是一个维度。
  2. 把微调当"知识注入手段"（「把公司文档拿去微调，模型就学会了」）——这是最危险的一种：微调不保证事实准确，而且知识一变就要重训。
  3. 把「没有 GPU」当主要理由——面试官会立刻追问「那租一张 A100 呢？」。真正的硬约束是数据和评测，这两样租不到。

这一页的定位：L7 是「面试权重中、大模型开发岗为高」的一层，所以这一页的目标是能接住追问、能画出一棵决策树，不是让你现在就去开一次训练。训练侧的机制原理见 指令微调 SFT 与 LoRA / QLoRA，本页不重复。

核心内容 ​

L7-01 三条路线的能力边界 ​

先把三条路线各自改的是什么列清楚。这张表是后面所有判断的底座：

维度Prompt 工程RAG微调（SFT / LoRA）
改的东西输入文本输入上下文模型参数
能修「模型不知道」❌✅⚠️ 能记住，但不保证准确、且知识一变就过期
能修「输出不稳定」⚠️ 部分（格式约束越复杂越脆）❌✅ 这是它的强项
需要标注数据0 条gt 答案或 gt 片段（评测用）数百～数千条高质量样本

失败时的可回滚性改回 prompt 即可换索引版本换 checkpoint / adapter
主要成本项工程与试错检索运行时延迟与存储造数据的人力 + GPU 小时

⚠️ 上表的量级是"起步"量级，不是报价。具体到你的场景，用「先估最贵的那一项（造数据）」的方式反推可行性。

判据一：缺知识还是缺行为 ​

这是唯一的第一问，其余判据都要排在它后面：

  • 缺知识：模型确实不知道（你的私有文档、上周的政策变更、内部的字段口径）。→ 首选 RAG，因为它把「知识」从参数里搬到了可增删改查的外部存储上。
  • 缺行为：模型知道该说什么，但说得不合你的规矩（该输出 JSON 却输出解释、该用「亲亲」的口吻却像在写公文、该先索取订单号却直接给结论）。→ 首选 prompt，prompt 压不住再考虑微调。

为什么"先 prompt 后微调"：prompt 的试错成本是分钟级、可回滚、零标注；微调的试错成本是「造数据 + 训练 + 评测」一条链，任何一环错了都要重来。在没把 prompt 打到极限之前就上微调，等于用一个天级周期去解决一个分钟级就能解决的问题。

一个反直觉的边界：微调也能注入知识——把领域语料做继续预训练（continual pretraining）确实是主流做法之一。但要注意两件事：① 它注入的是分布，不是可检索的条目——你没法「删掉微调进去的某一条过期事实」（RAG 删一个 chunk 就行）；② 面试里说「我用微调注入了知识」几乎一定会被追问「知识更新了怎么办」，而这个问题在 RAG 上有标准答案，在微调上没有。所以当知识是时效性/私有性的时候，RAG 是唯一能给你"可撤销"的方案。

判据二：时效性与变更频率 ​

知识变更频率建议
每天到每周变只能 RAG。微调的周期追不上
每季度到每年变RAG 仍更划算（改索引 vs 重训），除非同时缺行为
基本不变（领域术语、行业话术、输出规范）微调开始划算——"不变的东西"才值得写进参数

这条判据可以直接在面试里当成一句结论用："能让它变的走 RAG，不变且值得反复使用的走微调。"

判据三：你手上有哪些资源（这条才是真正的门槛） ​

按紧缺程度排序，从最缺到最不缺：

  1. 评测集与判据——最缺。没有它，你训完无法判断是变好还是只是换了一批错法。
  2. 高质量标注数据——次缺。要的是「同一个输入-输出口径」下的样本，不是随便抓一批对话。格式见 指令微调数据构造。
  3. GPU 与显存——反而不是最缺的。LoRA 在单卡上的显存门槛比全参微调低一个量级（机制见 指令微调 SFT 与 LoRA / QLoRA），实在没有就租。
  4. 时间与工程链路——训练脚本、checkpoint 管理、推理侧加载 adapter、回滚方案。

为什么把评测排在第一：训练本身是一次优化，优化必须有目标函数和验证集。没有验证集的训练，本质上是在盲调一个你无法测量其效果的系统——你唯一能观测的是 loss 下降，而 loss 下降和「上线效果变好」之间没有必然关系（模型可能只是学会了更啰嗦）。

判据四：代价差一个数量级，但差在哪要说清楚 ​

常见的错误说辞是「RAG 便宜、微调贵」，然后举不出依据。正确的拆法是把三个方案各自的钱和时间花在哪讲出来：

该微调的候选排序：不一定是生成模型 ​

这是应届简历上最容易做出差异化、也最容易被面试官认可的一个判断：在 RAG 系统里，最该微调的通常不是生成模型，而是检索侧的小模型。

理由是收益/成本比：检索侧的 Embedding 与 Reranker 是判别式小模型（编码器结构，参数量远小于生成模型），微调它有三个好处——① 训练数据可以从线上日志自动构造（正例 = 被点击/被采纳的片段，负例 = 召回了但没被用的片段，即所谓 hard negative），不需要人工写；② 训练成本是分钟到小时级；③ 它的评测指标是现成的、可计算的（Recall@k / MRR / nDCG），不像生成模型那样要依赖 LLM-as-judge。

⚠️ 但这一步有一个前置条件：微调检索模型必须先把"检索失败"和"排序失败"分开。如果你的问题里有大量「正确答案根本不在召回集里」的情况，微调 Reranker 是无效的——Reranker 只能在候选集内部重排，它救不回没召回的。判据是先看 R@k 的绝对值：召回率低就先修召回（切块、混合检索、查询改写），召回率已经很高而 MRR 低，才轮到 Reranker。

长上下文是不是第四条路？ ​

是，而且面试官很爱问。长上下文修的是"检索链路的工程成本"，不是"知识时效性"：它省掉了外挂检索器，但代价是延迟与成本随长度增长、以及注意力在长输入上的有效利用问题（不要断言某个具体衰减规律，这高度依赖模型与任务）。实务上的判断是：窗口够用且文档量小（一两次会话能塞完）时，长上下文是最省事的；一旦文档量、权限隔离、增量更新这三件事里出现任何一件，你就需要一个检索层。

常见误区 ​

  • ❌ 「微调能让模型学到新知识」当作默认前提。 微调更擅长的是行为与格式；把知识写进参数会带来「不可撤销」与「需要重新训练」两个硬伤。
  • ❌ 「数据越多越好」。 数据质量与口径一致性比条数重要。同一口径的几百条高质量样本，通常胜过口径混乱的几万条（这一条在 02 页 展开）。
  • ❌ 「LoRA 一定不损失效果」。 LoRA 是低秩约束下的近似，它省的是显存与训练参数量；能不能达到全参微调的效果取决于任务与秩的选取，不能默认等价。
  • ❌ 「有 GPU 就能微调」。 缺的是数据和评测，不是卡。
  • ❌ 「先上线再看效果」。 生成模型上线后的 A/B 需要大规模样本才能出显著结论（原因见下面的自家项目部分），而你在投递期没有这个样本量。

代码：把判据写成可执行的检查脚本 ​

这是伪代码级别的决策脚本，作用是把上面的判据固化成一组必须回答的问题，避免自己在「想微调」的时候跳过关键项：

python
# 伪代码：微调可行性自检（不产生任何训练动作，只输出"缺什么"）
from dataclasses import dataclass

@dataclass
class FinetuneGate:
    has_eval_set: bool          # 有评测集吗
    eval_metric: str | None     # 指标是什么（必须可计算）
    eval_n: int                 # 样本量
    n_train_samples: int        # 同口径训练样本条数
    defect_kind: str            # "knowledge" | "behavior"
    knowledge_volatile: bool    # 知识会变吗
    prompt_saturated: bool      # prompt 已经打到极限了吗
    has_gpu: bool

def decide(g: FinetuneGate) -> list[str]:
    blockers: list[str] = []
    if g.defect_kind == "knowledge" and g.knowledge_volatile:
        return ["不走微调：知识会变 → RAG（可撤销、可增量）"]
    if not g.prompt_saturated:
        blockers.append("prompt 还没打到极限：先做 prompt 与后处理校验")
    if not g.has_eval_set or not g.eval_metric:
        blockers.append("没有评测集/指标：先补评测，否则训完无法验收")
    if g.eval_n < 30:
        blockers.append(f"评测集只有 {g.eval_n} 条：先做功效分析再定样本量")
    if g.n_train_samples < 300:
        blockers.append(f"同口径样本仅 {g.n_train_samples} 条：先造数据（见 02 页）")
    if blockers:
        return ["暂不微调"] + blockers
    hint = "可以试点：优先 LoRA，并准备一个'不改任何东西'的对照组"
    if not g.has_gpu:
        hint += "；无本地 GPU 则租单卡，LoRA 的显存门槛低于全参"
    return [hint]

和你自己的项目对上号 ​

先说一句必须摆在最前面的话：你的两个项目都没有做过任何微调，也没有训练过任何参数。 你不是「做得少」，是在这一项上目前是零。所以这一节不写「我在哪里用到了微调」，而是写清三件事：为什么没做、这个不做的理由在面试里站不站得住、如果要做第一步做什么。

事实：两个项目都只用了推理侧的模型 ​

项目用到的模型用途是否训练过
科研文献 RAGbge-m3（Embedding，1024 维，归一化后内积=余弦）文档与查询向量化否
科研文献 RAGBAAI/bge-reranker-v2-m3（Cross-Encoder）20 对候选精排否
科研文献 RAGdeepseek-chat（.env 里的名字，源码注释提醒需与官方当前模型名核对）生成否
YYHelp v2deepseek-v4-pro / deepseek-flash（灰度路由的两个模型）规划、分派、专家生成、裁判否

代码层面可以自证：rag-demo/ 下没有 peft / Trainer / TrainingArguments / DeepSpeed / optimizer.step() 的任何调用——它是纯推理链路（ingest.py 建向量、retrieve.py 检索、generate.py 生成、service.py 服务化）。

为什么没做：三条理由，按硬度排序 ​

1）没有能验收微调的评测集——这是最硬的一条。

YYHelp 的 Gate-1 实验是40 题 × 2 臂，结论是「多智能体相对单智能体没有统计显著的收益」：完成率 multi 40/40 vs single 39/40（t p=0.323、Wilcoxon p=1.0），每问 tokens 的 t 检验与 Wilcoxon 结论打架（p=0.409 vs 0.017）→ 判 NSC；墙钟 20.9 s vs 9.9 s（2.11×）才是唯一确定的退化。更关键的一刀是：两臂 39/40 同对同错 → 有效判别样本 n_eff = 1。功效分析给出的是「要检出 +5pp 需要 76 题」。

这组数字对微调决策的意义是直接的：如果 40 题里只有 1 题能区分两个方案，那么任何小于这个量级的效果差异都测不出来。而微调的典型收益常常就是几个百分点。用这个评测集去验收微调，得到的结论无论正负都不可信。 所以正确顺序是：先把评测集做大做对，再谈训练——这也正是 L6 那一层存在的理由（见 /kb/l6-eval-observability/）。

2）两个项目的问题定位都不在"行为"，而在"知识"与"工程"。 科研文献 RAG 的实测瓶颈是极清楚的：端到端 P50 15.66 s，其中检索（含精排）14.47 s、LLM 生成只有 1.26 s——92% 的时间在检索侧，而精排 20 对在 CPU 上要 8.5 s。这是一个工程优化问题，不是模型能力问题：微调生成模型对这个数字一点帮助都没有。它要的是 GPU/ONNX/批处理或换更小的 reranker。

3）知识是"会变"的那一类。 科研文献库会扩（实测就从 55 篇扩过），YYHelp 的 KB 与政策口径也会变。按判据二，能让它变的走 RAG——这也是两个项目本来就在做的事。

如果真要微调，第一个候选不是生成模型 ​

按「收益/成本比」排，你自己这两个项目里的微调候选顺序是：

  1. Reranker（bge-reranker-v2-m3） ——最强的候选。理由：RAG 的瓶颈就在检索侧；精排 20 对要 8.5 s，而同一个任务上"换了更小的模型"和"换了更快的内核"是可叠加的；更重要的是一条实测事实——加精排前后 R@5 从 59.1% 提到 71.8%（+12.7 pp）、MRR 从 0.502 到 0.714，说明排序这一环的收益是实的、并且可测。微调它需要的负样本可以从候选集里自动构造（召回了但没进上下文的那一批），不需要人工标注。
  2. Embedding（bge-m3） ——次选。它的收益体现在召回而不是排序，前置换库/换切块的成本更低，所以先做完切块与混合检索的消融，再考虑训 Embedding（否则你分不清提升来自数据还是来自模型）。
  3. 生成模型 ——排最后。理由就是上面三条。

并且第一步都必须是「补评测」，不是「写训练脚本」：对检索侧而言，第一步是把 R@k / MRR 的口径钉死（现在的 R@10 会被标注窗口构造性地压到等于 R@5，这种口径问题不修，训完也读不出结论）。

一个可以直接背的诚实答法 ​

「我这两个项目没有做过微调，只用了推理侧的模型。原因是：① 我的评测集是 40 题、两臂 39/40 同对同错，有效判别样本只有 1，这个规模无法验收一次微调；② 我定位到的瓶颈是检索侧的精排耗时（8.5 s / 20 对，CPU），生成模型微调对它没有帮助；③ 我的知识是会变的那一类，RAG 的可撤销性比微调更合适。如果要做，我会先补评测集与功效分析，然后第一个候选是 Reranker 而不是生成模型，因为它的训练数据可以从候选集自动构造、指标现成、训练成本低。」

这段话的价值不在「我做了什么」，而在**「我把判据用在了自己的系统上，并且得出了一个否定的、可执行的结论」**。

面试怎么问（≥3 组） ​

Q1：你的项目为什么不做微调？

A（要点）：给三条可核查的理由，按硬度排序——① 评测侧：40 题、n_eff = 1、+5pp 需要 76 题，测不出几个百分点级别的收益；② 瓶颈侧：P50 15.66 s 里 14.47 s 在检索、生成只占 1.26 s，微调生成模型不解决这个数；③ 知识侧：语料与政策会变，RAG 可撤销、微调要重训。 加分句：「我把它当成一道选型题：缺知识走 RAG、缺行为才微调。我这两个项目的问题是知识和工程，不是行为，所以在没有评测集之前做微调，是把一个分钟级能试错的问题换成一个天级周期的盲调。」 别说：「没时间」「没有 GPU」「微调太贵了」——这三句都会被一句「那给你一张卡呢」打穿。

  • 追问（一层）：那你觉得在你这套系统里，哪个模型最该微调？
  • 追问（二层）：如果微调 Reranker 之后 R@5 没涨，你怎么判断是模型的问题还是数据的问题？
  • 追问（三层）：你怎么保证微调 Reranker 的收益不是来自「换了一个模型」这个混淆变量？

Q2：RAG 和微调能不能一起用？

A（要点）：能，而且修的是两个不同的维度——RAG 管「这次回答能看到什么事实」，微调管「模型一贯怎么组织回答」。所以组合起来的典型形态是「微调过格式与口径的模型 + 外面挂检索」。 加分句：「真正要小心的不是能不能一起用，而是归因：两个一起改，你无法知道收益来自哪一边。所以我如果要做，会先固定检索侧，只训格式；或者反过来，先训检索模型，生成侧一个字不改。」 别说：「一起用效果最好」——没有任何依据时不要给方向性结论。

  • 追问（一层）：如果一定要选一个先做，你选哪个？依据是什么？
  • 追问（二层）：你的知识更新了，检索层怎么处理？微调层怎么处理？
  • 追问（三层）：怎么设计一组实验，把「检索变好」和「生成变好」在人看不到答案的情况下分开？

Q3：长上下文窗口越来越大了，是不是就不需要 RAG 和微调了？

A（要点）：长上下文优化的是检索链路的工程复杂度，不是知识时效性。三个会把「全塞进上下文」打掉的具体条件：文档量大到塞不下（你的语料是 55 篇 / 5325 块）、权限隔离（不同用户能看的片段不同，必须按人过滤）、增量更新（改一个片段要重建索引还是重训？）。 加分句：「还有一个成本事实：上下文长度直接进 token 成本。我的实测单次是 1290 prompt token，如果改成全语料塞入，成本和延迟都会随长度线性上扬——所以长上下文能省掉一层工程，但省不掉检索的必要性。」 别说：「长上下文会取代 RAG」——这是应届生最容易跟着短视频说的错话，且可以直接被 5325 块这个数字反驳。

  • 追问（一层）：什么情况下你会真的选择长上下文而不做检索？
  • 追问（二层）：长上下文下，你原来的 Recency / 位置偏差问题变了没有？
  • 追问（三层）：如果客户要求「答案必须能指到原文第几块」，长上下文方案怎么给引用？
