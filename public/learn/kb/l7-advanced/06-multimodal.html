多模态模型与 VLM 应用、多模态微调与拼接 ​

覆盖知识点：L7-09、L7-10 ｜ 面试频率：中 ｜ 建议学时：9h

一句话说清 ​

VLM 的结构可以用一句话概括：一个视觉编码器把图像编码成向量，一个投影层把这些向量映射到语言模型的词嵌入空间，然后它们就和文字 token 一起排在同一条序列里。 所以从语言模型的角度看，图片只是"特殊的 token"——它不懂图像，它只看到一段比平时更长的输入。理解了这一点，就能推出 VLM 工程上的三个要点：视觉 token 数量决定成本（一张图可能吃掉几百到上千个 token 位置）、分辨率提升的代价是 token 数量而非显存（因此有视觉 token 压缩）、坐标定位是"语言输出"而不是"检测框输出"（因此格式约束比模型选型更关键）。多模态微调（L7-10）则围绕"冻结哪一塔、训哪一塔"展开——拼接的本质是让两个各自预训练好的模块在中间对齐，所以最常训练的恰恰是中间那个投影层。

为什么必须学（面试官视角） ​

多模态在应届生面试里的典型问法不是"讲讲 CLIP"，而是场景题：

  1. 「你有一堆 PDF，里面有表格和图，怎么让模型读懂？」——考的是你对"图文混排"工程现实的认识。
  2. 「让模型在一张图里找出某个东西的位置，怎么做？」——考的是你对 VLM 输出形态的理解（坐标是文本）。
  3. 「一张图占多少 token？」——考的是成本意识，这一问答不出来就直接暴露没实际用过。

⚠️ 本节与其他页不同的风险是"信息时效"：多模态模型的规格（支持的图像分辨率、视觉 token 机制、是否支持视频）迭代极快，各家的处理方式也不统一。所以这一页刻意不写任何模型的参数量、层数、上下文长度与视觉 token 上限——只讲机制。凡是要给具体数字的地方，一律以对应模型的官方文档为准。

三段各自的角色：

组件作用常见处理方式
视觉编码器把图像切成 patch → 编码成特征序列通常是 ViT 类结构，多为冻结
投影层把视觉特征维度映射到语言模型的嵌入维度常是可训练的那一层（参数量相对最小）
语言模型接收拼接后的序列，生成文本可冻结、可 LoRA、可全参

"为什么这样设计"：这三段是分别预训练好再拼起来的——视觉编码器在图像任务上学过、语言模型在文本上学过，中间用一个小投影层做对齐。这样做的好处是不需要从头训一个多模态模型，代价是中间的模态鸿沟必须靠数据和训练来搭桥。这就解释了为什么"拼接"在工程上是"训最少的东西、用最多的现成能力"。

图像怎么变成 token：数量决定成本 ​

典型流程是：图像 → 切成固定大小的 patch → 每个 patch（或若干 patch 合并后）对应一个视觉 token → 这些 token 与文本 token 拼在一起送进语言模型。

从这条链路能推出四个工程结论：

  1. 图像分辨率越高 → patch 越多 → 视觉 token 越多 → 输入序列越长。 所以"能不能看清小字"和"多少钱一次"是同一个旋钮的两端。
  2. 视觉 token 与文本 token 争抢同一个上下文窗口。 一张高分辨率图可能占掉上下文里相当可观的一段，留给文本的空间相应变少。
  3. 视觉 token 也进入 KV Cache，因此它同时影响显存与并发上限（机制见 推理优化全景）。
  4. 由此产生了"视觉 token 压缩"这一整类做法：把相邻 patch 的特征合并、或在投影层做下采样，用看得没那么细换取更少的 token 与更低的成本。

这句是本节最该背下来的判据：

提高图片清晰度与降低单次成本，是同一个参数的两端。任何"既要用最高分辨率、又要控制成本"的方案，都必须包含压缩或裁剪策略。

⚠️ 具体一张图占多少 token，取决于模型的分辨率策略、patch 大小、是否做分块（tiling）以及是否压缩——这些参数与换算方式以对应模型的官方文档为准。 不要报一个具体数字当通用答案。

坐标定位：模型输出的是文本，不是检测框 ​

这是 VLM 与传统目标检测在工程上最大的差别，也是最好考的追问点：

  • 传统检测模型输出的是结构化的框结构（坐标张量 + 类别 + 置信度），可以直接喂给下游程序。
  • VLM 输出的是文本。要让它在图上定位，通常的做法是约定一种坐标的文本表示（例如把坐标归一化到某个整数区间后按固定顺序写成字符串），然后在提示词里明确要求使用这种格式。

由此推出的四条工程要点：

  1. 格式一致性是硬约束。 提示词里规定的坐标区间、顺序（先 x 后 y）、是否归一化，必须与解析代码完全一致。只要有一处不一致，输出就会"看起来是坐标但全错"，而且不报错——这与项目里"契约不一致且不报错"是同一类风险。
  2. 模型可能在"看起来合理"的位置编一个框。 所以在工程上必须验证输出坐标在合法区间内、且对应区域与问题相关，而不能直接相信。
  3. 更好的做法是"先定位、后裁剪、再细看"：让模型给出大致区域 → 程序裁出该区域 → 再把裁剪后的高分辨率图送回去问细节。这样既省 token，又比一次性看全图更准。 这是把"分辨率 vs 成本"这对矛盾拆开处理的实用手法。
  4. 模型的定位能力与它的分辨率策略强相关。 想看小字就必须有足够的分辨率或分块策略——这不是提示词能解决的问题。

多图、图文混排与"文档理解" ​

多图输入在结构上只是"多个视觉 token 段 + 文本 token"的拼接，但要处理两个新问题：图的顺序与指代（模型怎么知道"第二张图"是哪一张）与总量控制（图越多，token 越容易超预算）。

文档理解（PDF / 扫描件 / 报表）是多模态最常见的落地场景，也是最容易被低估的场景，因为它的难点往往不在模型，而在前处理：

难点具体表现处理方向
版面双栏、页眉页脚、跨页表格版面分析先切区域，再分别处理
表格行列语义、合并单元格表格结构识别，或输出成结构化格式再解析
图与正文的关系图注、引用、图中标签把图注与图一起送进上下文，而非只送图
分辨率小字号、细线条分块放大（先定位区域再裁剪）
成本一页一图，几百页先做便宜的文字抽取，只对必要的页/区域走视觉模型

最后一行是工程上最重要的取舍：不要把所有页都送进视觉模型。合理的做法是先用便宜的文字抽取（含 OCR）把文档转成文本，只在"抽取结果不可靠"或"内容本身是视觉的"（图、表、公式、版式）时才走视觉模型。这是一个分级处理的架构，成本差着数量级。

L7-10 多模态微调：训哪一塔 ​

三种可训练范围 ​

范围训什么适用场景代价
只训投影层冻结视觉塔与语言模型，只训中间的对齐层模态对齐（让视觉特征接上语言模型）、新领域图像的分布适配最便宜、最不容易破坏原有能力
投影层 + 语言模型（LoRA 或全参）视觉塔仍冻结要改输出行为：领域术语、输出格式、坐标约定中等；这是最常见的组合
连视觉塔一起训三塔全动图像分布与预训练分布差异极大（例如特定仪器成像、特定图纸）最贵、最容易灾难性遗忘；且视觉塔通常在极高分辨率或大规模数据上预训练过，小数据集上去训它往往得不偿失

"为什么"：冻住的塔保留原有能力，动的塔承担新任务。 训得越多，越容易把预训练能力冲掉——这与 LoRA / QLoRA 实操 里"可训练参数量越大越容易过拟合"是同一条逻辑，只是这里的风险更集中在视觉塔的高质量预训练会被小数据破坏。

⚠️ 各家框架对多模态微调的可训练模块命名与支持情况差异很大（有的把投影层叫 aligner、有的叫 connector、有的是多层 MLP）。具体模块名与配置项以对应框架与模型的官方文档为准，不要凭记忆写。

多模态 LoRA 的特殊之处 ​

多模态场景下用 LoRA 有几个和纯文本不一样的地方：

  1. 注入位置的判断变了。 在纯文本模型上，target_modules 的选择相对自由（见 LoRA 那一页）；在多模态模型里，把 LoRA 注进视觉塔往往是不划算的——视觉塔的参数结构与训练目标与语言侧差异大，收益通常不如"投影层 + 语言侧"的组合。
  2. 数据量的门槛不同。 纯文本微调几百到上千条就能看出行为变化（见 指令微调数据构造）；多模态任务因为多了"看图"这个维度，同样复杂度的任务往往需要更多样本——因为模型要同时学"看什么"与"怎么说"。
  3. 评测必须分两层。 一层测感知（有没有看对：颜色、数量、位置、文字内容），一层测表达（有没有按要求的格式说对）。只测后者会掩盖"看图看错了但恰好蒙对了"的情况。

拼接的三种思路 ​

思路做法特点
投影层对齐（主流）冻结两塔，只训中间小投影层成本最低；两塔的预训练能力都保住
交叉注意力注入在语言模型层内加入对视觉特征的交叉注意力融合更充分，但结构与训练都更复杂
早期融合从一开始就在统一架构里处理多模态上限可能更高，但需要从头预训练，成本量级完全不同

应届生面试里只需要说清一件事：主流的"拼接"走的是第一条路——训最少的参数、用最多的现成能力。 后两条属于"预训练阶段的设计选择"，不在"拿现成模型做应用"的范围内。

常见误区 ​

  • ❌ 「VLM 能像检测模型一样输出结构化的检测框」。 它输出的是文本；坐标的格式、区间、顺序全靠提示词与解析代码约定，"看起来是坐标但全错"是这个环节最典型的 bug。
  • ❌ 「分辨率越高越好」。 分辨率提高直接抬高视觉 token 数量，进而抬高成本、缩短可用上下文、拉高显存占用。必须配压缩或裁剪策略。
  • ❌ 「多模态微调一定要训视觉塔」。 大多数场景训投影层 + 语言侧就够；把视觉塔冻住通常更稳。
  • ❌ 「一张图就是一个 token」。 它是一段 token，数量与分辨率、patch 策略、是否分块有关。
  • ❌ 「把 PDF 全页丢给视觉模型就等于文档理解」。 这是最贵的做法；正确做法是分级——先便宜的文本抽取，只对必要的页/区域走视觉。
  • ❌ 「多模态微调只要看最终回答对不对」。 必须分层评测：先测感知，再测表达。

和你自己的项目对上号 ​

先说清楚事实：你没有用过任何多模态模型，也没有做过多模态微调。 你的两个项目输入输出全是文本：科研文献 RAG 处理的是论文（抽取成 5325 块文本后做检索与问答），YYHelp 是纯文本的多轮客服对话；生成侧走的是 OpenAI 兼容协议的文本模型。没有调用过任何视觉模型、没有处理过图像输入、没有训过任何塔。

但这一页有一处和你的系统咬得非常紧——而且是一个你现在就能说清楚的真实缺口。

① 你的语料是论文，而论文里最有信息量的东西恰恰不是文本 ​

你的 RAG 语料是 55 篇科研文献、切成 5325 块。论文的结构特点是：结论在图里、数据在表里、公式在版式里。而你的抽取链路是纯文本的——图像和表格结构在这一步就已经丢失了，检索器再怎么调也找不回来。

这意味着你系统里存在一类"结构性不可回答"的问题：问「图 3 里哪条曲线在 20 epoch 之后反超」这类问题，无论检索做得多好都答不出来，因为答案从来没进过索引。这不是检索质量问题，是数据表示问题。

用本页的框架，你已经有能力把这个缺口讲得很精确：

你现有的事实多模态视角下的含义
语料 55 篇 / 5325 块，三档切块切块是纯文本的；图与表结构在切块前已丢失
检索三档 R@5 64.4% / 59.1% / 71.8%、MRR 0.502 → 0.714这个数字衡量的是文本块的检索质量，不覆盖图表类问题
端到端 P50 15.66 s、检索占 14.47 s成本结构已经偏紧——再往链路里塞视觉模型，必须先算账

最后一行是这一节对你最实用的判断：如果要补上图表这条链路，不能对所有页面都走视觉模型——那会让本已占 92% 的检索开销进一步膨胀。正确的做法恰好就是本页那张分级图：先做便宜的文本抽取，只在"内容本身是视觉的"（图、表、公式）时才走视觉模型，并且只覆盖必要的页与区域。 你现有的延迟账单（15.66 / 14.47 / 1.26 s）是判断"这笔成本加不加得起"的现成依据——这是你比大多数候选人多出来的东西：你不是在谈多模态的可能性，你有一个可以拿来算账的系统。

② 你已经在"分级处理"这件事上做过同类决策 ​

本页最核心的工程取舍是**"不要把所有页都送进昂贵的模型"。而这个思路在你的项目里已经落地过两次**：

  1. CI 只跑不需要模型的那一层——因为装 torch 要下 4.4 GB 的 bge-m3，会让 CI 从秒级变成十分钟级并且依赖外网。判据是一样的：把"重资源"和"逻辑验证"分开，让贵的路径只在必要时才走。
  2. 路由分层：YYHelp 里简单任务用 deepseek-flash、多智能体链路用 deepseek-v4-pro——按请求的复杂度分配成本（MODEL_SIMPLE_DEFAULT / MODEL_MULTI_DEFAULT）。

所以你在这一节的答法可以是：「多模态的成本控制和我项目里的两条既有决策是同一个模式——先分级、再调用。我不会把 55 篇论文全量转成图像送进视觉模型，而是先做文本抽取，只对抽取失败的页和图表区域走视觉，并且用我已有的延迟账单来判断这笔开销加不加得起。」

③ 坐标定位那个坑，你在项目里踩过同型的 ​

本页强调"VLM 的坐标是文本输出，格式不一致会得到'看起来对但全错'的结果，而且不报错"。这类"契约不一致 + 静默失败"的坑在你的项目里有三个同型实例，可以直接引用：

  • FIND_IN_SET 是函数而不是列比较，走不了 B-tree 索引——DDL 看着没问题，问题池涨到 10 万行后"按原因统计"从 20 ms 变成 4 s，是 EXPLAIN 才暴露出来的。
  • 环境变量在 import 之后才设置就不生效，而且不报错——后来的判据升级成「配置注入的时机是契约的一部分」。
  • getattr(llm, "model", "") 在 graph/plan.py 与 graph/supervisor.py 逐字复发——猜参数的写法在多个副本里同时错。

所以对坐标定位这件事，你的态度应该和这些一致：不依赖"看起来对"，而是解析时校验坐标在合法区间内、对应的裁剪区域确实包含被问的对象，并且把"格式约定"写进提示词与解析器的同一处，而不是两边各写一遍。

④ 如果真要动多模态，第一步做什么 ​

不是装一个 VLM，而是先确认"哪些问题是现在答不了、但多模态能答的"。 具体动作：

  1. 从评测集里筛出"结构性不可回答"的题。你的评测集有 8 个字段，其中 gt_chunk_ids 指出标准答案落在哪一块——如果某类题的 gt_chunk_ids 经常为空、或者标准答案本身来自图表，那就是多模态要补的缺口。五类题型里 multi_hop（6 题）与 exact_term（6 题）最可能落在这里。
  2. 只对这批题做小规模试点：抽 10 张页码走一次视觉处理，人工核对结果，记录"视觉处理让哪几题从答不出变成答得出"。
  3. 用同一条口径算成本：视觉处理一页要多少 token、加进链路之后 P50 会涨多少。这个数字必须和现有的 15.66 s 放在一起报，否则无法判断值不值得。
  4. 不要一开始就做微调——按本页的取舍，训投影层 + 语言侧才是起点，而在"这批题是否真的答不出"被证实之前，训任何东西都没有评测依据。

一句话总结这一节：你没碰过多模态，但你有两样别人没有的东西——一个"图表信息根本没进索引"的真实缺口，和一份可以用来算账的延迟账单。 面试里把这两样讲出来，比说"我了解 Qwen3-VL"实在得多。

面试怎么问（≥3 组） ​

Q1：VLM 是怎么"看懂"图片的？

A（要点）：三段式——视觉编码器把图像切成 patch 编码成特征序列，投影层把这些特征映射到语言模型的嵌入维度，然后视觉 token 与文本 token 拼成同一条序列送进语言模型。对语言模型来说，图片只是"一段特殊的 token"——它并不真的"看"，只是注意力作用在一段更长的输入上。正因为三段是分别预训练好再拼的，中间那个小投影层往往才是需要训练的那一层。加分句：「我会强调这个结构带来的一个直接后果：图片占的不是"一个位置"，而是一段序列。所以提高分辨率、多图输入、长文档理解，最后都变成同一个问题——视觉 token 数量。而视觉 token 也进 KV Cache，所以它同时影响显存和并发上限，不只是"输入变长"这么简单。」 别说：「VLM 就是把 CLIP 接在 GPT 上」——这句话不算错，但它没有解释为什么接入点选在嵌入层、以及为什么投影层是关键，一追问就断了。

  • 追问（一层）：为什么称它是"拼接"？哪一部分最常被训练？
  • 追问（二层）：视觉 token 会影响推理的哪些方面？
  • 追问（三层）：为什么说"提高清晰度"和"降低成本"是同一个旋钮的两端？

Q2：让模型在一张图里找出某个东西的位置，怎么做？

A（要点）：关键认知是：VLM 输出的是文本，不是检测框。 要给它的坐标定一种文本表示（比如归一化到某个整数区间、按固定顺序写），并在提示词里明确要求这个格式。工程上必须注意三件事：① 提示词里的区间、顺序、是否归一化，必须与解析代码完全一致——不一致会得到"看起来是坐标但全错"的结果，而且不报错；② 解析时必须校验坐标合法，因为模型可能在看起来合理的位置编一个框；③ 更好的做法是"先定位、后裁剪、再细看"——让它给大致区域，程序裁出来，再把高分辨率的小图送回去问细节，既省 token 又更准。 加分句：「第三点其实是在拆解一个矛盾：要看小字就必须有分辨率，分辨率就意味着 token 成本。先裁剪再细看等于只在真正需要的区域付高分辨率的钱。这个思路我在项目里用过同型的——判据要能自动复核，而不是靠人眼看输出像不像坐标。我吃过三次'契约不一致还不报错'的亏：FIND_IN_SET 走不了索引、env 设置时机不对就不生效、getattr(llm,"model","") 在两个文件里逐字复发。所以坐标格式这件事我会把约定写在一处，解析时校验，而不是两边各写一遍。」 别说：「用 YOLO 取框再喂给模型」——这是一种可行架构，但它抄的是检测模型的路子；面试官问 VLM 的定位就是想听"输出是文本"这个认知。

  • 追问（一层）：坐标为什么要归一化？
  • 追问（二层）：如果模型给的框位置合理但不包含目标对象，你怎么发现？
  • 追问（三层）：图和图注应该一起送进上下文吗？为什么？

Q3：一张图占多少 token？这对系统设计有什么影响？

A（要点）：它是一段 token，具体数量取决于模型的分辨率策略、patch 大小、是否分块以及是否做压缩——这些参数与换算方式以对应模型的官方文档为准，我不报通用数字。 但影响是确定的：视觉 token 与文本 token 争抢同一个上下文窗口，同时也占用 KV Cache，所以它同时影响成本、可用上下文长度、显存与并发上限。 加分句：「所以我在设计上会做两件事：一是压缩或裁剪——用 '先定位区域再裁剪放大' 的方式只在必要区域付高分辨率的钱；二是分级处理——文档理解不要把所有页都送进视觉模型，先用便宜的文字抽取，只在抽取不可靠或内容本身是视觉的（图、表、公式）时才走视觉。这两条加起来，成本能差一个数量级。而且这个判断我可以说得很具体：我现在的端到端 P50 是 15.66 s，其中检索占 14.47 s、生成只有 1.26 s——成本结构已经很紧，往链路里加视觉之前，我必须先算这笔账。」 别说：报一个具体数字"一张图 xx 个 token"——不同模型的策略不一样，这句话一出口就会被追问是哪个模型、什么分辨率。

  • 追问（一层）：视觉 token 多了，对本已紧张的上下文有什么影响？
  • 追问（二层）：多图输入会带来什么新问题？
  • 追问（三层）：如果只能选一个，你会先优化分辨率还是先优化图的数量？依据是什么？

Q4：多模态微调要训哪一部分？

A（要点）：按"要改什么"分三档。只训投影层——适合模态对齐与新领域图像的分布适配，最便宜、最不破坏原有能力。投影层 + 语言模型（LoRA 或全参）——适合改输出行为（领域术语、输出格式、坐标约定），这是最常见的组合。连视觉塔一起训——只在图像分布与预训练分布差异极大时才考虑，代价是贵且容易灾难性遗忘，而视觉塔通常是在极大规模数据上预训练过的，小数据集上训它往往得不偿失。原则就是：冻住的塔保留能力，动的塔承担新任务。加分句：「我会补两点多模态特有的注意。一是评测必须分两层：一层测感知（有没有看对：颜色、数量、位置、文字内容），一层测表达（格式对不对）——只测表达会掩盖"看图看错了但恰好蒙对了"。二是数据量门槛更高：纯文本微调几百到上千条能看出行为变化，多模态因为多了"看图"这个维度，同样复杂度的任务通常要更多样本。还有，具体的可训练模块名各框架差异很大（有的叫 aligner、有的叫 connector），我会查官方文档，不凭记忆写。」 别说：「全都训，效果最好」——这既贵又最容易把预训练能力冲掉，而且没有任何验证支撑。

  • 追问（一层）：为什么最常训的是投影层？
  • 追问（二层）：怎么判断该不该解冻视觉塔？
  • 追问（三层）：多模态 LoRA 和纯文本 LoRA 在注入位置的选择上有什么不同？
