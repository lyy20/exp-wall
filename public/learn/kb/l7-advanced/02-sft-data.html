指令微调数据构造 ​

覆盖知识点：L7-02 ｜ 面试频率：高 ｜ 建议学时：5h

一句话说清 ​

微调的上限由数据决定，而数据的核心不是「多少条」，是口径是否统一：同一种提问方式、同一套回答标准、同一段长度区间。工程上有四条主线——把样本组织成框架认得的格式（单轮三元组 / 多轮 messages）、只让 loss 落在回答上（prompt 部分要掩码）、控制长度分布与 prompt 长度（否则截断会静默吃掉一半样本）、去重与配比（重复样本会把模型拖向过拟合、配比失衡会让它遗忘通用能力）。数据量级在数百到数千条这个区间就足以改变行为——前提是它们同口径。

为什么必须学（面试官视角） ​

「你做过微调吗」「数据怎么来的」这两问几乎总是连着出现。面试官在这一节想听的不是「我用了 5000 条数据」，而是下面这四类判断：

  1. 数据从哪来——人工写、业务日志筛、还是强模型合成？三种来源的偏差不同。
  2. 怎么保证口径一致——有没有标注规范？同一条指令的两个回答能不能都对？
  3. 怎么防止模型学坏——重复样本、超长样本截断、只学格式不学内容、灾难性遗忘，各自怎么处理？
  4. 数据量和效果的关系——这是最能看出是否真做过的一问，因为它没有标准答案，只有取舍依据。

这页的主要风险是"看起来懂了"：格式（Alpaca / ShareGPT）是最容易记住也最容易忘记细节的部分，而真正决定成败的是掩码、长度分布、去重、配比这四件事——它们全都不体现在格式文档里。

核心内容 ​

L7-02 样本的组织格式 ​

单轮三元组（Alpaca 风格） ​

最朴素的形态是三条字段：

json
{"instruction": "把下面这句话改写成更克制的客服语气", "input": "你必须马上给我退款！", "output": "我理解您很着急，我先帮您确认订单状态，再看能走哪个退款流程。"}
1
  • instruction：任务描述。要写成"指令"而不是"问题"——这是指令微调与预训练数据最大的形式差别。
  • input：任务的可选输入。空 input 也是合法的（此时它是纯指令任务）。
  • output：期望回答。

⚠️ 字段名以各框架官方文档为准。instruction / input / output 是 Alpaca 风格的通行命名，但不同框架在配置文件里可能用 prompt / query / response 这类别名并做字段映射；具体的映射配置项名称与默认值请以官方文档为准，不要凭记忆写。

多轮对话（messages 风格） ​

带 role 的列表是更通用的形态，也是现在的主流：

json
{"messages": [
  {"role": "system", "content": "你是电商客服助手，回答前先确认订单号。"},
  {"role": "user", "content": "我的订单还没到"},
  {"role": "assistant", "content": "好的，请提供订单号，我帮您查一下物流状态。"},
  {"role": "user", "content": "12345"},
  {"role": "assistant", "content": "订单 12345 显示昨天已到达本市分拨中心，预计今天派送。"}
]}

三种形态在实践中的取舍：

形态优点代价适用
单轮三元组构造简单、便于按任务计数表达不了多轮依赖与「拒绝/追问」这类行为格式与风格对齐
多轮 messages与推理时的实际输入形态一致需要处理截断（从哪一轮开始截）对话系统、Agent
带思维链的单轮能教「先想再答」推理侧要不要输出这段要提前定推理任务

为什么优先选「与推理时形态一致」的格式：训练时模型看到的序列长什么样，推理时就该长什么样。如果训练用单轮三元组、推理用带 system 的多轮模板，模型的行为边界（什么时候追问、什么时候拒答）就从来没被训练过。

Agent 轨迹样本 ​

带工具调用的样本本质上还是 messages，只是 assistant 的消息里多了结构化的调用请求、并且多出 tool 角色的返回。关键判断是"要不要把工具返回值也做进训练目标"——通常不：工具返回是环境给的，不是模型要学的输出。

各框架对工具调用样本的字段与模板支持差异较大，具体字段名与模板名以官方文档为准。

数据量、质量与配比 ​

「多少条够」这个问题该怎么答 ​

没有普适数值，但有三条可用的定位方法：

  1. 按任务复杂度定：单一格式对齐（比如「必须输出 JSON」）通常用几百条就能看出行为变化；涉及多轮、多工具、多种边界的组合行为，需要上千条量级。
  2. 按维度覆盖定：更可靠的做法是先列维度表（任务类型 × 难度 × 边界情况），再按维度抽样，每个格子至少有若干条。这样数据的规模由覆盖面决定，而不是由手上有多少素材决定。
  3. 按评测集反推：你的验证集有多少类问题，训练集就要覆盖这些类。训练集覆盖不到的类别里，微调后不会变好——而且可能变差（见下面的灾难性遗忘）。

四条质量判据 ​

判据做法违反后的症状
口径一致写标注规范：同一问题两个回答只能有一个合格模型学会"两边都对"的模棱两可语气
长度可控统计 output 的 token 长度分布，掐掉长尾模型变啰嗦；长样本被截断后学成残句
无重复精确去重 + 近重复去重过拟合到重复样本的措辞，泛化下降
无泄漏训练集与验证集按样本指纹隔离验证集指标虚高，上线打回原形

为什么"口径一致"排第一：SFT 的目标函数是最大化标注回答的似然。如果同一类输入的标注回答风格不同（一次写 3 行、一次写 30 行），模型学到的就是一个混合分布，表现是"时好时坏"。这不是模型的缺陷，是数据定义不清。

灾难性遗忘与配比 ​

微调是分布切换（原理见 指令微调 SFT 与 LoRA / QLoRA）。如果你的数据 100% 是某种窄任务，模型在那一类上会变强，在没被覆盖的通用能力上会退化。

处理方式有三条，按推荐度：

  1. 在训练集里掺入一定比例的通用指令数据（例如常见的开源指令集），让模型每步都能看到"别的任务也要会做"——这是 LoRA 场景下最常用的做法。
  2. 用 LoRA 而不是全参，并且在推理时可以按需切换/卸载 adapter（全参微调是"改了就是改了"，没有这个灵活性）。
  3. 在评测里保留一组"通用能力回归"题，训练前后都跑一遍，用数字证明没退化。

不要给固定配比数字。配比取决于你的目标、基座与数据量，"通用:领域 = x:y" 这种说法在没有自己的消融之前不要当结论说。正确表述是「配比要在自己的验证集上扫，并且必须包含通用能力回归项」。

去重与清洗的具体做法 ​

去重分两层：精确重复（完全相同的字符串）与近重复（只改了几个词、或者同一模板生成的换皮样本）。

python
import hashlib
import re

def norm(s: str) -> str:
    """归一化：去多余空白、全角转半角、统一小写（中文不受影响）"""
    s = s.strip().lower()
    s = re.sub(r"\s+", " ", s)
    return s

def fingerprint(instruction: str, output: str) -> str:
    """精确去重指纹：注意不要放时间戳、不要放随机 id"""
    raw = norm(instruction) + "\x1f" + norm(output)
    return hashlib.sha256(raw.encode("utf-8")).hexdigest()

def dedup_exact(records: list[dict]) -> tuple[list[dict], int]:
    seen, kept = set(), []
    for r in records:
        fp = fingerprint(r["instruction"], r["output"])
        if fp in seen:
            continue
        seen.add(fp)
        kept.append(r)
    return kept, len(records) - len(kept)

近重复没法靠哈希解决，两种常用手段：n-gram / MinHash 签名（快，适合十万级）与向量相似度（准，但需要跑一遍 Embedding）。实战里的优先级是：先做精确去重（几乎零成本），再对 instruction 字段做近重复检测——因为"同一个指令的多个换皮输出"是最常见的污染形态。

⚠️ 指纹里绝不能放时间戳或自增 id。放了之后同一个内容每批都算出不同指纹，去重等于没做。这是数据管线里最典型的"看着跑了、其实没生效"的 bug。

长度分布、截断与 loss 掩码 ​

截断是静默的 ​

所有训练框架都有一个最大序列长度参数（cutoff_len 之类的名字）。超过它的样本会被截断——而截断通常不报错。于是：一条 8000 token 的长样本放进 2048 的上限里，模型看到的是半句话，学会的是在半句话之后继续生成。

必须做的两件事：① 统计训练样本的 token 长度分布（不是均值）；② 显式决定超长样本的命运——丢弃、还是把超长部分做成多段、还是提高上限。默认行为是截断，而静默截断是数据侧最贵的坑。

loss 掩码：为什么不能全序列算 loss ​

SFT 的损失通常只计算 assistant 回答部分的 token，system 与 user 部分被掩成 -100（PyTorch 交叉熵的忽略索引）。原因是：prompt 本来就"已知"，如果对 prompt 也算 loss，模型会被训练去"预测用户会问什么"——这不是你要的行为，而且会稀释真正要学的回答分布。

用 transformers 的 tokenizer 做一次掩码，最小示意如下（这是标准用法，不涉及任何训练框架的私有 API）：

python
from transformers import AutoTokenizer

tok = AutoTokenizer.from_pretrained("your-base-model")  # 模型名以官方文档为准

messages = [
    {"role": "system", "content": "你是电商客服助手。"},
    {"role": "user", "content": "订单还没到"},
    {"role": "assistant", "content": "请提供订单号，我帮您查物流。"},
]

# 只把最后一条 assistant 作为"要学的部分"
prefix = tok.apply_chat_template(messages[:-1], tokenize=False, add_generation_prompt=True)
target = messages[-1]["content"] + tok.eos_token

p_ids = tok(prefix, add_special_tokens=False)["input_ids"]
t_ids = tok(target, add_special_tokens=False)["input_ids"]

input_ids = p_ids + t_ids
labels = [-100] * len(p_ids) + t_ids       # prompt 位置掩码，answer 位置保留
assert len(input_ids) == len(labels)

数据来源三条路线的偏差 ​

来源偏差形态什么时候用
人工撰写慢、贵，但口径最可控行为规范类（该拒答什么、该用什么语气）
业务日志筛选有真实分布，但只包含"发生过的"，缺负例与边界多轮对话、意图覆盖
强模型合成（蒸馏）快、量大，但会继承教师模型的错误与风格；同质化严重格式与任务泛化，见 蒸馏与数据合成

这三条路线的取舍原则：用合成数据扩量、用人工数据定标准。合成数据能覆盖长尾任务，但「什么算合格」这件事必须由人来定义——否则你只是把教师模型的判断标准抄了一遍，且不知道它错在哪。

常见误区 ​

  • ❌ 「格式对了就能训」。 格式只是入场券。掩码、长度、去重、配比这四件事才是效果变量。
  • ❌ 「数据越多越好」。 重复与低质样本会把模型往两个方向同时拉：过拟合到重复措辞 + 在真实分布上变差。
  • ❌ 「验证集可以从训练集里随机切」。 必须按指纹切（近重复样本会跨集合泄漏），否则验证指标是虚的。
  • ❌ 「loss 下降说明训得好」。 loss 只在训练分布上衡量拟合程度。分布外行为、格式稳定性、通用能力退化，loss 一个都测不出来。
  • ❌ 「先用小数据跑通再扩量」。 小数据跑通只能验证管线通不通，不能验证数据够不够——这两个结论经常被混为一谈。

和你自己的项目对上号 ​

照旧先说清事实：你的两个项目都没有构造过 SFT 训练数据，也没有跑过任何训练。 但这一页讲的东西，你在两个项目里已经用同样的思路做过一遍——只是对象不是训练集，而是评测集与埋点数据。把这三处对上号，你在面试里就能把"没做过微调"讲成"我懂数据质量这一套，只是还没用到训练上"。

① 你的评测集就是"口径一致性"的活例子 ​

YYHelp 的评测集是 data/yyhelp/eval/questions.jsonl，40 题，字段是 qid / type / question / query_used / answerable / gt_chunk_ids / gt_hint / notes。这套字段本身就是一份标注规范：

  • type 把题目分成五类（single_hop 12 / synonym 8 / unanswerable 8 / multi_hop 6 / exact_term 6）——这就是 SFT 里说的"先列维度表再按格子抽样"；
  • answerable 为真 32 题、为假 8 题——这就是负例与正例的口径分离；
  • gt_chunk_ids 给出正确答案落在哪一块——这就是"标准答案必须可核查到具体片段"。

而你在评测里踩过的两个坑，在训练数据上是同型问题：

  • 裁判失败不能填 0（要剔除并报告 dropped_multi / dropped_single）。对应到训练数据：不完整的样本不能用默认值补齐——补齐等于"把测量工具坏了记成被测对象的缺陷"，在数据侧就是给模型灌入了一批错的监督信号。
  • 同一批题跑两遍必须逐题一致（采集器的可复现性断言）。对应到数据侧：一个不能复现的数据管线，产出的训练集是不可信的——你无法知道这次训练用的到底是哪一版数据。

② 飞轮的"检索快照"就是"数据要保留生成它的上下文" ​

YYHelp 数据飞轮是三入口 → 一张问题池表（issue_pool 的 trigger_flags 是 weak_evidence / self_eval_fail / user_downvote），快照有 9 项必需字段，缺失时 _validate_snapshot 返回缺失项而不是抛异常，并拒绝写入。

这条设计对训练数据的启示是直接的：一条 bad case 记录如果只有「问题 + 差答案」，你没法用它做任何事后分析；只有连检索到的片段、模型给出的理由、判定的依据一起留下来，它才能变成一条可用的训练样本。采样时就决定了的字段，事后补不回来。 这也是为什么飞轮里 issue_replay 要独立成第三张表——「线上发生」和「离线实验」必须可区分，混在一起你就无法判断一条样本的真实来源。

③ 如果真要造第一版 SFT 数据，第一步是什么 ​

不是写训练脚本，也不是先抓数据，而是先定一份标注规范。 具体动作可以落到这三个：

  1. 从已有评测集出发扩维度表：现在 5 类（single_hop / synonym / unanswerable / multi_hop / exact_term）× 难度 × 边界情况，先把空格子列出来——空格子就是你现在数据覆盖不到的类别。
  2. 从飞轮问题池里按 trigger_primary 抽样：user_downvote 与 self_eval_fail 这两类是现成的"负例来源"，weak_evidence 更像检索问题（不该拿去做 SFT，该回去修检索）。
  3. 先写 20 条人工样本，把"合格"定义清楚，再用强模型批量扩写——顺序不能反。反过来做的话，你会先得到 5000 条，然后发现没有人能说清其中哪一条符合标准。

一句话总结这一节：这一页的机制你还没有在训练上落地，但你已经在评测与飞轮上把"口径、快照、可复现、不填补"这四条纪律执行过一遍了。 面试里如实这么说，比编一个「我用了 5000 条数据」强得多。

面试怎么问（≥3 组） ​

Q1：如果你要微调，数据从哪来？

A（要点）：三条路线各有偏差：人工撰写口径最可控但慢；业务日志筛选有真实分布但只有"发生过的"、缺负例；强模型合成快但会继承教师的错误与风格、同质化重。组合原则是「合成扩量、人工定标准」。 加分句：「我现在的日志侧已经有可用的入口了——飞轮的问题池按 trigger_primary 分了三类（weak_evidence / self_eval_fail / user_downvote），其中 user_downvote 与 self_eval_fail 就是现成的负例来源。但我会先写 20 条人工样本把'合格'定义清楚，再批量扩写——顺序反过来的话，我会先得到 5000 条、然后发现没人能说清哪条符合标准。」 别说：「拿 GPT 生成一批就行」——这句话会直接引出「那你怎么知道合成的数据是对的」这个你答不上来的追问。

  • 追问（一层）：合成数据的质量怎么保证？
  • 追问（二层）：如果教师模型在某一类问题上系统性答错，你的数据集会出现什么现象？怎么发现？
  • 追问（三层）：你怎么衡量"这批数据比上一批好"？有没有可能数据更好了、模型反而更差？

Q2：数据要多少条才够？

A（要点）：没有普适数值，给三条定位方法——按任务复杂度定（单格式对齐几百条量级可看出行为变化，多轮+多工具+多边界需要上千条量级）、按维度覆盖定（先列维度表、再按格子抽样，规模由覆盖面决定而不是由手上素材决定）、按评测集反推（验证集有哪些类，训练集就要覆盖这些类，否则那一类不会变好、可能变差）。 加分句：「我把它反过来问：我的验证集能测出什么级别的差异。我现在的评测集是 40 题、两臂 39/40 同对同错、有效判别样本只有 1，功效分析说检出 +5pp 要 76 题——在这个测量精度下，讨论数据量没有意义，因为训完也测不出来。所以我的顺序是先补评测集，再定数据量。」 别说：「越多越好」或者报一个具体的"最佳条数"。前者错，后者无法核实。

  • 追问（一层）：那你说几百条够，几百条能做到什么、做不到什么？
  • 追问（二层）：少量多次迭代（先训 200 条看效果再补）和一次凑够 2000 条，你选哪个？
  • 追问（三层）：如果数据只有 200 条但每一条都要人工写，你怎么排优先级？

Q3：SFT 的 loss 是怎么算的？为什么不能对整个序列算？

A（要点）：SFT 用的还是下一 token 预测的交叉熵（与预训练同一个目标函数，差别在数据形态与损失范围）。通常只对 assistant 回答的 token 算 loss，prompt（system + user）位置掩成 -100 忽略。原因：prompt 本来就是已知输入，对它算 loss 等于训练模型去预测"用户会问什么"，这不是目标行为，而且会稀释真正要学的回答分布。 加分句：「掩码这件事还有个连带要求：训练与推理必须用同一套 chat template。模板不一致的话，模型在训练时见到的那串特殊 token 和推理时的对不上，学到的东西用不上——这跟我项目里设了 env 却不生效是同一类 bug：契约不一致、而且不报错。」 别说：「框架会自己处理」——面试官问这个就是想看你知道不知道 -100 的含义。

  • 追问（一层）：-100 是什么？为什么是这个值？
  • 追问（二层）：如果我把 system prompt 也算进 loss，会有什么后果？
  • 追问（三层）：多轮对话里，如果第二轮用户开始跑题，这段样本还能用吗？你会在数据侧怎么处理？

Q4：数据里去重怎么做？为什么要去重？

A（要点）：分两层——精确重复用归一化后的哈希指纹；近重复用 n-gram / MinHash 签名或向量相似度。重复样本会让模型过拟合到那几句措辞上，同时在真实分布上泛化变差。 加分句：「指纹里绝不能放时间戳或自增 id——放了之后同一内容每批算出不同指纹，去重等于没做。这类'看着跑了、其实没生效'的坑我在飞轮里踩过同型的：FIND_IN_SET 是函数不是列比较，走不了索引，DDL 看着没问题、EXPLAIN 才告诉你 type=ALL。判据：去重有没有生效，要看去重前后的条数差，不能看脚本跑没跑完。」 别说：「用集合去一下重就行了」——那只覆盖精确重复。

  • 追问（一层）：近重复为什么必须处理？它会造成什么具体症状？
  • 追问（二层）：验证集能不能从训练集里随机切？
  • 追问（三层）：如果去重后数据只剩三分之一，你怎么办？
