偏好优化（DPO / ORPO / SimPO）与 RL 后训练、GRPO ​

覆盖知识点：L7-05、L7-06 ｜ 面试频率：中 ｜ 建议学时：11h

一句话说清 ​

SFT 教模型"该怎么答"，偏好优化教它"在两个都能答的版本里偏好哪个"。 DPO 把 RLHF 里的「训奖励模型 + 跑 PPO」压缩成在偏好对数据上做一次分类式的训练，因此不需要奖励模型、不需要在线采样、不需要 RL 循环——它是当前最易落地的偏好优化方法；ORPO 与 SimPO 又各自去掉了 DPO 里的某个部件（参考模型、或长度偏置）。GRPO 属于另一条路：不给"人类偏好"，而是给可自动验证的奖励（答案对不对、代码跑不跑得通），用组内相对优势替代价值网络，是"用 RL 提升推理能力"的主流做法。这一节的核心能力是：看懂"奖励信号从哪来"，并知道没有可靠评测就做不了后训练。

为什么必须学（面试官视角） ​

这一节在面试里几乎不会问公式，问的是判断力。三个高频切入角度：

  1. 「DPO 和 PPO 有什么区别？」——想听你讲清"去掉了什么、代价是什么"，而不是背论文摘要。
  2. 「偏好数据从哪来？怎么保证标注质量？」——这一问直接关联到"你的项目有没有评测能力"。
  3. 「GRPO 为什么火？」——想听"可验证奖励"这个概念，以及它只在奖励可自动验证时成立这个前提。

⚠️ 本节最危险的地方是"记得住名词、说不出边界"。ORPO / SimPO / GRPO 这几个词现在人人都能说，但能说清"它们在什么条件下不适用"的人很少。这一页把重点放在边界上。

核心内容 ​

L7-05 偏好优化的共同前提：你需要"两个答案" ​

所有偏好优化方法共享同一个数据前提：一个输入配一对（或一组）回答，并标出哪个更好。最小形态是三元组：

json
{"prompt": "请把这句话改写成更克制的客服语气：你必须马上给我退款！",
 "chosen": "我理解您很着急，我先帮您确认订单状态，再看能走哪个退款流程。",
 "rejected": "抱歉，我无法处理这个请求。"}
1
2
3

这里有一个必须讲清的判断：偏好对里的 rejected 不是"错误答案"，而是"我们不要的行为"。在上面的例子里，rejected 语法正确、态度也没问题，问题在于它没有完成任务。这个区分很重要——因为偏好优化只能推开"你不想要的"，不会自动拉向"你想要的"；如果 rejected 里混进了"其实也能接受"的回答，模型会被推着远离一些本来没问题的行为（过度校正）。

为什么二选一比打分更可靠：人类对"A 和 B 哪个更好"的判断一致性，显著高于"给这个回答打 1–5 分"。这也是 RLHF 与 DPO 原理 里那条结论的实操含义：你的标注规范要围绕"配对比较"来写，而不是围绕"打分标准"来写。

DPO 去掉了什么、留下了什么 ​

一句话回顾（原理与该页已给出的推导见 RLHF 与 DPO 原理）：

DPO 把"带 KL 约束的最大化奖励"这个 RL 问题，解析地变形为在偏好对上做一次分类。 因此它没有：显式的奖励模型、在线采样、PPO 的 RL 循环。它有：一个冻结的参考模型（用来约束新模型不要偏离基座太远）。

于是 DPO 的实际代价清单是：

项目DPO 的情况
显存要同时放策略模型和参考模型——这是它最大的显存开销来源
训练稳定性比 PPO 好得多（没有 RL 循环的方差）
数据需求静态偏好对。数据是离线准备好的，训练中不会探索新行为
会不会外推过头有可能。参考模型的 KL 约束是唯一的"刹车"，刹车力度由超参控制

"静态数据"是 DPO 最本质的局限：它只能学到"你给它的那些对比"，不会自己去发现更好的回答。PPO 那条路虽然难训，但它的在线采样确实会探索数据里没有的答案——这是两者真正的结构差异，不是"哪个效果好"。

ORPO 与 SimPO：各自去掉了 DPO 的一个部件 ​

方法去掉/改动了什么得到什么代价
DPO—稳定性好、实现简单需要参考模型（显存翻倍量级）+ 通常要先做 SFT
ORPO去掉参考模型，把 SFT 与偏好优化合成一步省一份参考模型显存；一步到位，不需要先 SFT是另一种目标，与 DPO 的取舍不完全等价；行为差异要在验证集上看
SimPO去掉参考模型，并把长度因素从目标里处理掉不需要参考模型；缓解"越训越长"的长度偏置同样需要在自己的数据上验证

"为什么长度偏置是个真问题"：偏好优化的目标按序列似然（对数概率之和）来算，而更长的回答天然更容易拿到更高的总对数似然——于是模型会学到一个捷径：把话说长。这不是"模型变啰嗦了"这种风格问题，是目标函数本身给了一个可被利用的漏洞。SimPO 这类方法的设计动机之一就是把这个漏洞堵上。

⚠️ 不要给 DPO / ORPO / SimPO 的具体超参数值（例如 β 取多少）。这类值的正确来源是原论文设定 + 你自己的验证集，且不同实现、不同基座、不同数据上的最优值不同。面试里说"我会在验证集上扫"，比背一个数字专业得多——这正是 RLHF 与 DPO 原理 已经确立的纪律。

偏好优化还有一个必须监控的量：被选中的回答与参考模型的偏离程度。 偏离太小说明没学到，偏离太大往往伴随通用能力退化。在评测集上同时跑"偏好指标"和"通用能力回归"是最低要求。

L7-06 GRPO：换一种奖励信号 ​

为什么需要另一条路 ​

DPO 那一路的奖励信号是人类偏好。它有两个天花板：

  1. 贵：偏好标注是人力密集的。
  2. 不可扩展：数学题、代码题这类任务，"哪个答案对"是能自动判定的——让人去看反而更慢、更容易错。

于是有了第二条路：用可自动验证的奖励（verifiable reward）做 RL 后训练。规则是：模型对一个 prompt 生成一组（group）答案 → 用规则或程序判定每个答案的奖励（对/错）→ 组内归一化得到每个答案的相对优势 → 用这个优势去更新策略。

GRPO 相对 PPO 去掉了什么 ​

PPO 需要一个与策略模型规模相当的价值网络（critic） 来估计状态价值、算优势。这又是一份几乎翻倍的显存与训练成本。GRPO 的做法是：不训价值网络，用"同一 prompt 下这组答案的奖励统计量"当作基线——把某个答案的奖励减去这组奖励的均值、再除以标准差，就得到它的相对优势。

这就是 GRPO 的核心机制：用"组内比较"替代"训练一个价值模型"。 组内比较天然就是一个 baseline 估计，而且与答案质量无关的难度差异会被自动消掉（难题整组都低分，减掉组均值后看不出差别）。

⚠️ GRPO 的实现细节差异很大——组大小怎么定、优势怎么归一化、KL 项怎么加、采样温度怎么设，各家开源实现的处理都不完全一致（ms-swift 的文档里就列了 GRPO / DAPO / GSPO / SAPO / CISPO / RLOO / Reinforce++ 这一整族变体）。具体实现细节以对应框架与论文的官方说明为准，不要凭记忆写。

可验证奖励的三个前提（这一段是本节最值钱的部分） ​

「用可验证奖励做 RL」听起来无懈可击，但它成立需要三个前提同时满足：

前提含义不满足时会怎样
判定确实可自动执行有确定性程序能给出对/错判定本身要靠模型打分 → 你只是把一个不可靠信号换了层皮
奖励信号稠密到能学习一组答案里必须有对错之分整组全对或全错 → 组内优势全为 0 → 这一批样本对更新没有任何贡献
奖励没有被钻空子奖励函数与真实目标是同向的模型学会满足判分器而不解决问题（奖励黑客）

第二条最容易被忽略，也最常见：如果模型对某类题已经全对了，那类题就不再产生梯度——训练自动把注意力挪到还没全对的题上。这既是优点（自动聚焦难点），也是风险（难题如果整组全错，同样不产生梯度，模型就永远学不会它）。这就是为什么这类方法依赖一个难度分布良好的题库。

奖励黑客：为什么"可验证"不等于"不可钻" ​

只要奖励是从"答案的某个可检查属性"算出来的，模型就可能去优化那个属性本身。 典型的钻空子形态：格式投机（学会输出判分器偏爱的那套格式却不给出结论）、样例过拟合（记住训练题库的答案）、以及依赖判分器的实现细节（判分器的正则、边界条件、超时阈值）。

防御手段是按性价比排序的三条：

  1. 保留一组没进训练题库的题做验证——训练奖励涨了而验证奖励不涨，就是钻空子的信号（这与项目里的"训练集与验证集必须按指纹隔离"是同一条纪律）。
  2. 在奖励里加格式与长度之外的约束（比如要求引用证据），让"只满足形式"不足以得分。
  3. 定期人工抽查高分样本。自动判分可以大规模用，但不能免除抽查。

每一步的判据都是"评测说了算"，而不是"loss 说了算"。 这一点在偏好优化上尤其硬：偏好优化会让模型变得更"讨喜"，而讨喜与正确不是一回事。

为什么这一章的真正主题是"评测" ​

把这一页和 指令微调数据构造 连起来看，会得到一个共同的结论：

后训练的每一环都在消费评测能力。 偏好数据要靠人来判定"哪个更好"（这是评测）；GRPO 要靠程序判定"对不对"（这也是评测）；而"训练没训坏"这件事，只能靠通用能力回归集来证明（还是评测）。

换句话说：没有可靠的评测，你就没有奖励信号；没有奖励信号，后训练无从谈起。 这不是一句正确的废话——它直接决定了工程上的投入顺序：先做评测集，再谈微调与后训练。

常见误区 ​

  • ❌ 「偏好数据里的 rejected 就是错误答案」。 rejected 是"不想要的行为"，不一定是错的；混入"其实也能接受"的回答会造成过度校正。
  • ❌ 「DPO 比 PPO 好」。 它们是不同结构：DPO 用静态离线数据、不要奖励模型；PPO 在线采样、会探索数据外的新行为。该说"DPO 更易落地、PPO 有探索能力"。
  • ❌ 「ORPO / SimPO 是 DPO 的升级版」。 它们去掉的是不同部件（参考模型、长度偏置），得到的是不同的取舍，不构成全面替换。
  • ❌ 「GRPO 只要有对错判分就能用」。 还需要难度分布良好（否则组内优势恒为 0）与判分器不可被钻空子。
  • ❌ 「偏好优化能提升事实正确性」。 它优化的是"偏好"，不能凭空注入模型不知道的知识。要注入知识，回去看 微调决策 里的 RAG 选项。
  • ❌ 「奖励涨了就成功了」。 必须区分训练奖励与留出集奖励——前者涨、后者不涨就是奖励黑客。

和你自己的项目对上号 ​

先把事实摆明：你的两个项目都没有做过偏好优化，也没有做过任何 RL 后训练。 没有偏好对数据、没有奖励模型、没有策略梯度。这一页对你来说不是"我做过什么"，而是"我为什么没做、以及我已有的能力离它有多远"。 而这两者之间的距离，恰好是你项目里最有价值的一段证据。

① Gate-1 的结论就是"没有可靠评测就做不了后训练"的实例证明 ​

这是本节与你的项目最直接的接口。YYHelp 的 Gate-1 A/B 用 40 题 × 2 臂 = 80 条配对样本比较了「多智能体」与「单智能体」两条链路，结论是没有统计显著收益（NSC）：

指标多智能体单智能体差值 / 比率检验判定
任务完成率40/4039/40+0.025，CI [−0.024, +0.074]t p 0.323、Wilcoxon p 1.0NSC
每问 tokens5,783.76,243.3+459.6，0.93×t p 0.409 / Wilcoxon p 0.017NSC（两检验打架）
每问墙钟20.9 s9.9 s−10.95，CI [−14.79, −7.12]，2.11×t p 1.9e-6、Wilcoxon p 8.7e-7、Holm 校正后仍拒绝REGRESSION

为什么这张表与偏好优化是同一类问题：

  • 两臂 39/40 同对同错 → 有效判别样本 n_eff = 1。 这是最刺眼的数字：40 个题里只有 1 个题的答案在两臂间不同，其余全部一致。在偏好优化的语境里，这等于"你手上 40 个 prompt 里只有 1 个能产生有意义的 chosen/rejected 对比"——剩下 39 个的"两个回答"是一样的，构成不了偏好对。
  • 功效分析给出的结论更硬：检出 +5 pp 需要 76 题，+10 pp 需要 17 题，+20 pp 数学上无解（需要的样本量发散）。也就是说，这份评测集的测量精度不足以支撑任何"改进了 x%"的说法。
  • 门禁的判定纪律本身就是后训练该用的纪律：三态 verdict（IMPROVEMENT / NSC / REGRESSION / INCOMPARABLE，退出码 0/0/1/2）、两个检验必须同向显著才算数、全零差判 NSC 而不判 INCOMPARABLE（"不是无法检验，是检验正常完成且确定无差异"）、裁判失败不填 0 而要剔除并报告（dropped_multi / dropped_single）。

把这四条搬到后训练上，每一条都有对应物：

Gate-1 的纪律后训练上的对应物
两个检验同向显著偏好指标与通用能力回归必须同向不退化，只看一个不算
全零差判 NSC组内奖励全为 0 时不要当作"训练失败"，那是这批样本没有梯度
裁判失败不填 0、要剔除并报告判分器出错时样本要丢弃而非给默认奖励，否则把仪器故障学成模型缺陷
自检 [6] 可复现性：同批题跑两遍逐题一致训练必须记录随机种子与数据版本，否则你无法知道这次训的是哪一版数据

② 你的问题池就是"未来的偏好对来源"，但现在还不够格 ​

飞轮里的三入口（weak_evidence / self_eval_fail / user_downvote）已经在按原因分类收集坏样本——而 user_downvote 与 self_eval_fail 这两类，正是偏好对里 rejected 的天然来源（因为它们是"用户/系统认为不行"的答案）。所以你的数据管线方向是对的。

但它现在还不能直接拿来做偏好优化，理由是具体的、可检验的：

  1. 只有"坏"的一端，没有"好"的一端。偏好对需要 chosen。你的池子里记录的是"发生了什么、哪里不好"（快照 SNAPSHOT_REQUIRED 有 9 项必需字段，缺项时 _validate_snapshot 返回缺失项并拒绝写入），但没有人写下"这条应该怎么答才对"。这一列现在不存在。
  2. weak_evidence 根本不该进偏好数据。它的成因是检索没找到，不是生成不好。拿它做偏好优化等于让模型去记"检索失败时该怎么编"——这是把一个检索问题错误地转成了生成问题。这一条是可以直接当面试答案的判断。
  3. 规模差着数量级。40 题的评测集、n_eff = 1，连判断一次改动都要 76 题才能看到 +5 pp，更不用说构造一批能改变行为的偏好对。

③ GRPO 这类方法在你的场景里连"可验证"这一关都过不了 ​

可以做一个很干净的推理（这段适合直接背）：

  • GRPO 类方法的前提是奖励可自动且确定性地验证（答案对不对、代码跑不跑得通）。
  • 你的主场景是客服多轮对话。什么算"答对了"？有没有解决用户的问题。这不是一个能靠程序判定的谓词——甚至不是靠一次 LLM 打分就能稳定判定的（你自己的 Gate-1 就用了 deepseek-v4-pro 做裁判、temperature=0.0、json_object 输出、回答截断 1500 字符，而且仍然要处理裁判失败的剔除）。
  • 因此：GRPO 那条路在你的场景里，卡在"判定可自动执行"这个第一前提上。 而它反而是数学题、代码题这类场景最适合——因为那里的判分是确定性的。

这段推理的价值在于：它证明的不是"你做不到"，而是**"你知道这类方法的适用边界在哪"**。面试里能讲清"什么场景用不了 GRPO"的人，远比能背 GRPO 公式的人少。

④ 如果真要做第一步，做什么 ​

不是先找偏好数据，而是先把评测集从 40 题扩到能测出差异的量级。 具体动作可以直接引用你已有的判据：

  1. 按功效分析定规模：+5 pp 需要 76 题。这是下限，不是目标。
  2. 按题型分布补齐：现在五类是 single_hop 12 / synonym 8 / unanswerable 8 / multi_hop 6 / exact_term 6——偏科明显（synonym 与 exact_term 各只有 6–8 题）。补齐时优先补判别力高的类别，也就是两臂容易产生分歧的那些。
  3. 先测出 n_eff 再谈别的：在扩题之后重跑一次两臂对照，看有效判别样本从 1 涨到多少。如果新的题集还是几乎全一致，那说明题目难度不够，而不是模型已经足够好。
  4. 同时建"通用能力回归集"：后训练最容易挂的地方不是"目标指标没涨"，而是目标指标涨了、别的能力塌了。这一组题必须独立于训练用数据。

一句话总结这一节：你没有做过偏好优化，但你做过的 Gate-1 恰好就是它的前置条件那一环——而你的结论是"现在的评测精度不够"。 面试里如实这么说，讲的是判断力；编一个"我做过 DPO"，一问超参怎么定的就崩。

面试怎么问（≥3 组） ​

Q1：DPO 和 PPO 有什么区别？

A（要点）：DPO 把「带 KL 约束的最大化奖励」解析地变形为在偏好对上做分类，因此没有奖励模型、没有在线采样、没有 RL 循环，只需要一个冻结的参考模型做约束——所以稳定得多、也更易落地。PPO 走的是完整 RL 路径：训奖励模型、在线采样、用价值网络估计优势。 结构性差异在数据上：DPO 用的是静态离线偏好对，只能学到你给它的那些对比；PPO 的在线采样会探索数据里没有的答案。所以不是"哪个更好"，是"要不要探索能力"的取舍。DPO 的显存代价主要来自要同时放策略与参考模型。 加分句：「我还会提一句 DPO 的目标函数有个可被利用的漏洞：它是按序列总对数似然算的，更长的回答天然更容易拿到更高的总分——所以模型会学到一个捷径叫"把话说长"。SimPO 那类方法的设计动机之一就是把长度因素从目标里处理掉。」 别说：「DPO 是 PPO 的简化版/升级版」——这句话会立刻引出"简化了什么、代价是什么"，而你如果只说了"不需要奖励模型"就没了。

  • 追问（一层）：DPO 需要参考模型，那参考模型是干什么用的？
  • 追问（二层）：偏好数据里的 rejected 一定是错的吗？如果不是，会有什么后果？
  • 追问（三层）：你要怎么判断一次 DPO 训练"训过头了"？

Q2：偏好数据从哪来？

A（要点）：三条来源——人工标注（一致性最高但最贵，适合定标准）、业务日志筛选（有真实分布，但只有"发生过的"，缺负例）、模型合成（快，但会继承教师模型的偏好与偏见）。共同要求是：偏好对里的 rejected 不是"错误答案"，而是"不想要的行为"；混入"其实也能接受"的回答会导致过度校正，模型被推离一些本来没问题的行为。 加分句：「我会顺带说一个我自己项目里得到的教训：偏好数据的前提是"两个回答确实有区别"。我做过一次 40 题 × 2 臂的配对检验，结果是两臂 39/40 同对同错，有效判别样本只有 1——也就是说 40 个 prompt 里只有 1 个能产生有意义的 chosen/rejected 对比。所以对我们这个场景，缺的不是标注预算，是能产生分歧的样本。」 别说：「用 GPT 生成就行」——立刻会被问"那你怎么知道它的偏好是对的"，以及"模型把自己的偏好蒸馏回自己会发生什么"。

  • 追问（一层）：一条数据要满足什么条件才算合格的偏好对？
  • 追问（二层）：如果 rejected 里混了 10% 其实可接受的回答，你预期看到什么现象？
  • 追问（三层）：你怎么衡量偏好数据的质量？有没有可能数据更好了、模型反而更差？

Q3：GRPO 是什么？为什么受关注？

A（要点）：GRPO 属于用可验证奖励做 RL 后训练这一路。机制是：对一个 prompt 生成一组答案 → 用规则或程序判定每个答案的奖励 → 组内归一化得到相对优势（减组均值、除标准差）→ 用这个优势更新策略。它相对 PPO 去掉了价值网络——不训 critic，用"同一 prompt 下这组答案的奖励统计"当基线，省下一份与策略模型同规模的显存与训练成本。组内比较还有个好处：与题目难度无关的差异会被自动消掉。 加分句：「但它成立有三个前提，我一般会连着说：① 判定确实可自动执行；② 奖励信号稠密到能学习——如果一组答案整组全对或全错，组内优势恒为 0，这批样本不产生任何更新；③ 奖励没被钻空子。第二条最容易被忽略，它也解释了为什么这类方法依赖一个难度分布良好的题库。而且 ms-swift 的文档里 GRPO 已经不是单个算法了，而是 GRPO / DAPO / GSPO / SAPO / CISPO / RLOO / Reinforce++ 一整族变体——具体实现细节我会去查对应框架与论文，不凭记忆说。」 别说：「GRPO 比 PPO 好训所以更好」——漏掉"只在奖励可验证时成立"这个前提，这一问就只能拿一半分。

  • 追问（一层）：为什么用组内均值当基线是合理的？
  • 追问（二层）：如果某类题模型已经全对了，训练会发生什么？
  • 追问（三层）：什么是奖励黑客？你会怎么发现它？

Q4：GRPO 和 DPO 该选哪个？

A（要点）：先看奖励信号能不能自动验证。任务有确定性判分（数学、代码、可执行校验）→ GRPO 这一路可行；任务是开放式生成、好坏只能靠人判断（客服对话、写作、摘要）→ 只能走 DPO 这一路（离线偏好对）。这个判断在选方法之前，不是之后。加分句：「以我自己的场景为例：客服多轮对话里，"答对了"意味着"解决了用户的问题"，这不是一个能靠程序判定的谓词——我的 Gate-1 里连用强模型做裁判（deepseek-v4-pro、temperature=0.0、json_object 输出、回答截断 1500 字符）都还要处理裁判失败的剔除。所以 GRPO 这条路在我的场景里，卡在第一个前提上：判定不可自动执行。它反而最适合数学题和代码题。能说清"什么场景用不了"，比会说这个方法的原理更有用。」 别说：「都可以试」——这是把方法选择当成调参问题，面试官会立刻转向"那你凭什么决定先试哪个"。

  • 追问（一层）：如果一定要在开放式任务上用 GRPO，你会怎么造奖励？
  • 追问（二层）：用 LLM-as-judge 当奖励，风险在哪？怎么控制？
  • 追问（三层）：奖励模型和裁判模型能不能是同一个模型？为什么？

Q5：这一整套后训练，你觉得最容易被低估的环节是什么？

A（要点）：评测。后训练的每一环都在消费评测能力——偏好数据要靠人判定"哪个更好"（评测）、GRPO 要靠程序判定"对不对"（评测）、"没训坏"只能靠通用能力回归集证明（评测）。没有可靠评测就没有奖励信号，没有奖励信号就没有后训练。 所以工程上的投入顺序应该是先建评测集，再谈微调。 加分句：「这条我有实测数字支撑。我的评测集是 40 题，一次性改动跑出来两臂 39/40 同对同错、有效判别样本 n_eff = 1，功效分析说检出 +5 pp 需要 76 题。在这个测量精度下，我去做任何后训练，训完都没有任何工具能判断它变好还是变坏——那得到的就不是一个可归因的结果。所以我后来的顺序是：先把评测集扩到能测出差异，再谈动参数。」 别说：「调参最重要」或者「数据最重要」——这两个答案都对但都没答到点上；面试官问的是顺序。

  • 追问（一层）：通用能力回归集为什么必须独立于训练数据？
  • 追问（二层）：如果你的评测集也是用强模型生成的，会不会有系统性偏差？
  • 追问（三层）：小样本评测里，为什么"两个检验同向显著"比"单个检验显著"重要？
