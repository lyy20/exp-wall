离线索引流水线 ​

一句话：把 55 篇 PDF 变成两份可比、可回滚、可复算的索引产物。

这一页要回答什么 ​

  • 「你的数据是怎么进库的？」——要求从 PDF 一直讲到 bm25.pkl，每一步说得清输入输出。
  • 「为什么用 FAISS 的 IndexFlatIP？为什么不用 HNSW / IVF？」——要求拿实测数字回答，而不是「FAISS 比较流行」。
  • 「你改了切块参数，怎么保证不出事？」——要求说出产物隔离、清单、回滚与一致性自检的设计。

读完这一页你应该能：画出离线全链路；说出 rebuild_bm25.py 存在的意义（以及它省掉了什么代价）；说清「索引错位会静默返回无关文本」这件事是怎么被防住的。

一、它要解决什么问题 ​

在线链路能有多快、多准，完全由离线这一步决定。而离线这一步有三个绕不开的麻烦：

  1. 它慢。真实切片吞吐是 2.92 块/秒（544 块 / 186 秒，exp10_real_throughput.py），全量重建一次是以十分钟为单位的。任何一次误操作都要付出这个代价。
  2. 它不可逆。切块参数、清洗规则、embedding 模型，任何一项改了，旧索引就与旧结论一起作废。清洗规则甚至带版本号：CLEANING_RULE_VERSION = "v2-page-number-by-proximity"（config.py:307）——规则一改就必须重新 ingest，否则你会在两份不可比的索引上比较指标。
  3. 它的错误是静默的。最典型的两种：FAISS 返回的下标没能映射回 chunk_id，于是不报错、但返回无关文本（exp05_index_consistency.py 里有一个 --demo-misalign 参数专门演示这件事）；清洗规则把表格里的整数单元格当成页码删掉，表格类问题从此永久答不对（NOTES 坑 37，v2-page-number-by-proximity 的由来）。

所以离线流水线的设计目标不是「跑通」，而是：可复算（每份产物能追溯到源数据）、可回滚（改坏了能退回去）、可隔离（试参数不会污染线上索引）。

2.2 每个选择的「为什么」 ​

选择为什么这样选为什么不选另一个
PyMuPDF（fitz）按坐标重建阅读顺序双栏论文用朴素抽取会把左右栏交错，块顺序错乱不用简单的「左栏全取、再右栏全取」拼接：实测论文版面里有跨栏的图表与通栏标题，必须按 block 的坐标做「条带（strip）」式重建（exp13_p15_layout.py）。量化判据是相邻块中心 y 的回跳次数——正确顺序应当单调递增（exp03_parse_naive.py）
清洗规则带版本号清洗规则改动会让指标不可比；版本号是「这份报告基于哪套规则」的唯一凭据不用「改了就算了」：坑 37 就是清洗规则误删表格整数单元格导致的，修完以后此前基于旧索引写的结论全部失效
结构感知切片 + 长度约束 + 硬切兜底章节边界是最可靠的语义边界，但块又不能超过模型输入限制不用纯固定长度切：会切断公式与定义；也不用纯章节切：单章过长时无法入模
bge-m3，normalize_embeddings=True归一化后内积等于余弦相似度，所以可以用内积索引不省这一步：exp02_embedding_fail.py 实测，不归一化时「语义相反的近义缩写」（CTRIP-SAC vs PER-SAC，只差两个字母）余弦相似度高达 0.881，反而超过真正的同义改写 0.599。归一化必须与建索引时保持一致
FAISS IndexFlatIP（精确检索）本地、零外部依赖、精确；且向量搜索根本不是瓶颈不换 ANN：exp31_index_scaling.py 实测 精排 20 对约 8.5 秒（CPU），而 Flat 搜索在 52 万块量级仍是毫秒级——换 ANN「换来的是速度，代价是召回损失，在 RAG 里直接体现为召回率下降」，在这里是纯亏。设计文档的口径是「FAISS 单机零依赖、性能好，规模上百万才需要 Milvus」
rank-bm25 而非 Elasticsearch5325 块规模下自建索引完全够用，零服务依赖，且分词可控不用 ES/Lucene：引入一个服务只为了 5000 条倒排，运维成本远超收益
分词 = 中文二元组（config.tokenize）零依赖，且对中文查询有基本召回能力不用 jieba：config.py:354 的原文是「更彻底的做法是 jieba 分词；bigram 零依赖且效果够用」。注意这只解决分词质量，解决不了跨语言的 df=0——那是原理性边界，见 ⑤ 检索层

一个必须自己发现的坑：索引与查询必须调同一个函数。ingest.py:342-349 与 retrieve.py:149-156 各留了一个 _tokenize() 薄封装，内部都是 from config import tokenize。如果哪天有人只改了其中一处，BM25 不会报错，只会静静地变差。

2.3 rebuild_bm25.py：为什么需要一个只重建 BM25 的入口 ​

out/bm25.pkl 的结构是：

python
{"bm25": BM25Okapi 对象, "chunk_ids": [...], "tokenizer": "config.tokenize/cjk-bigram", "rebuilt_at": "..."}
1

rebuild_bm25.py（main() 在 :38-82）只做一件事：用已有的 chunks.jsonl 重建 BM25 索引，不重跑向量化。

它的价值在于成本不对称：

  • 改分词方式、改 BM25 参数，切片完全没变，没有理由重跑 30—75 分钟的向量化；
  • 但也正因为「用的是同一份 chunks」，它有一个前提：只有当切片产物没变时才用它。如果切片变了，用 rebuild_bm25.py 会得到一份与 FAISS 索引不同源的 BM25 索引——两份索引指向的块集合不一致，而这种错误在检索时不会报错。

它还带一条备份策略：重建前把旧索引备份为 bm25.pkl.pre_bigram_bak，并且只在备份不存在时才备份（避免第二次重建把「原始版本」覆盖掉）。

五、踩过的坑 / 做过的取舍 ​

现象根因怎么定位到的怎么修的教训
吞吐实测 23.41 块/秒，看起来漂亮但完全不真实用 [一句短文本] * 64 这种重复短句测的，高估 9 倍换成真实 chunk 重测得真实值 2.92 块/秒；扩库预估改用 2.63 块/秒实验设计错误比代码错误更隐蔽：输入不像真实数据，测出来的数就没有意义
块长度超出配置上限（1132 > 1024）_hard_split 的兜底路径与上限约束之间有缝对全库块长度做分布统计（平均 763 字符，最长 1132）记录并复核；结论是必须对产物做实测量，不能相信配置配置写了上限，不等于产物满足上限
ingest.py --chunk 1024 直接覆盖 out/产物目录没有隔离，--chunk 只是改了参数手动跑一次发现的加 RAG_OUT_TAG 环境变量做目录隔离；exp17 才敢用 out vs out_1024 两套索引做对比破坏性操作的默认行为必须是安全的
--chunk 1024 实际切的是 2048 字符CHUNK_CONFIGS["1024"]["max_chars"] = 1024 * 2（config.py:158），键名指 token 名义值对着 config.py 核参数记录为坑 40，写文档时必须注明字段名/参数名引用前先核对源码——这个项目里已发生过两次名字与行为不一致
out/MANIFEST.json 记录的块数是 5470清单没有强制更新机制，最后一次去重没同步与 eval/report.md:129 的 5325 比对记录为已知过期产物自检文件也需要被自检

六、面试深挖：追问链 ​

第一条：为什么用 Flat 而不是 ANN？

  • Q：你用的什么向量库？为什么不用 HNSW / IVF？
  • A：FAISS 的 IndexFlatIP，精确检索。理由是实测：我的链路里向量搜索根本不是瓶颈——exp31_index_scaling.py 实测 Cross-Encoder 精排 20 对在 CPU 上要 8.5 秒，而 Flat 搜索在 52 万块量级还是毫秒级。换 ANN 换来的是速度，代价是召回损失，在这个链路上是纯亏。
  • 追问：那你什么时候会换 ANN？
  • A：当向量搜索的时间量级接近精排的时候。我做过分档实测：523 块（真实规模）、1 万、10 万、30 万，--big 还能追加到 100 万，并在 10 万档额外建了 HNSW 和 IVF 来比 recall@10。判据就是这一条：搜索耗时相对精排耗时是否可忽略。可忽略就不换。
  • 追问：那你为什么不用 Milvus 这种「标准答案」？
  • A：因为它的成本项不在我要解决的问题上。Milvus 解决的是分布式、多租户、海量向量；我这里 5325 块、单机、零外部依赖，引入一个服务只为了替代一个毫秒级的本地调用。设计文档里写的口径是「规模上百万才需要 Milvus」。有意思的是，我另一个项目 YYHelp 确实用了 Milvus——因为那边的语料是合成电商条款 + 46 张表格，检索策略不同，而且需要服务端的分词与融合算子。

第二条：改了参数怎么保证不毁掉已有结论？

  • Q：你说清洗规则一改就必须重新 ingest。那你改坏了怎么办？
  • A：三层。产物隔离：RAG_OUT_TAG 决定产物写进 out{tag}/，试参数不会碰线上目录。清单：write_manifest() 记录 chunks_sha256、embedding 模型名、prompt 版本、gt 块数与 sha256，所以任何一份产物都能追溯到它是哪套参数跑出来的。回滚清单：rollback.py 基于 MANIFEST 做回退。
  • 追问：那 MANIFEST 本身可信吗？
  • A：不完全可信，这是一个已知问题。out/MANIFEST.json 里现在还写着 n_chunks: 5470、gt_blocks: 37，而当前是 5325 块 / 206 gt 块——它没跟上最后一次去重。文件里明明写着「改了清洗规则 / 切片参数 / 模型后必须重新 ingest 并把本文件一起更新」，但没有强制机制。所以我得出的结论是：回滚清单也需要一条「与源数据是否一致」的机械检查，思路和 corpus.py:122-168 的 verify() 一样。
  • 追问：那这条检查你实现了吗？
  • A：没有，这是一个明确的未完成项。现在的替代做法是人工交叉核对——这次就是这样发现问题的。面试里我不会把它说成已解决：它是我从这次踩坑里总结出的下一步动作，而不是已有实现。

第三条：为什么索引错位是静默的？怎么防？

  • Q：你提到过索引错位会返回无关文本。具体是什么机制？
  • A：FAISS 的 search() 返回的是行号（第几行向量），不是我的 chunk_id。所以生产代码里必须做一次映射：cid = _S.chunk_list[int(i)].chunk_id（retrieve.py:170）。如果这份 chunk_list 的顺序与建索引时不一致——比如重新排序过、或者用了别的切片产物的 meta——那么映射不会报错，只会返回另一个块的正文。检索看起来「成功」了，答案却是错的。
  • 追问：你怎么证明这件事真的会发生？
  • A：我写了一个可以复现的演示：exp05_index_consistency.py --demo-misalign。故意制造错位之后，检索仍然正常返回结果、没有任何异常，但返回的文本与查询无关。另外我会做一致性自检：拿已知的 chunk_id 反查它应该在哪一行，再验证 search 返回的行号是否落回同一个 id。
  • 追问：那 chunk_id 本身可靠吗？它是什么格式？
  • A：格式是 文献前缀:p页码:c序号，例如 SCIS:p2:c010、SCIS:p11:c052。它是全链路唯一的稳定标识——向量下标、BM25 行号、评测报告里的 gt_chunks，最后都要回到它。也正因为如此，任何一次重新切片都会让它全部失效，这就是为什么换切片配置后不能直接比较 Recall@5，只能比相对趋势。
