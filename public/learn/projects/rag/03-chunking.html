切块策略 ​

一句话：切块是整条链路里参数最敏感的一步，也是「换把尺子就能让指标变好看」的重灾区。

这一页要回答什么 ​

  • 「你的 chunk 怎么切的？chunk_size 多少？overlap 多少？」——要求给出真实生效的字符数，而不是配置键名。
  • 「512 和 1024 你试过吗？哪个更好？」——要求先回答「这两个数字能不能比」，再回答结论。
  • 「你的表格和公式是怎么处理的？」——要求如实说明抽取是有损的，以及损失长什么样。

读完这一页你应该能：说清三层切块结构各自的职责；说清「512 档实际是 1024 字符」这个换算错在哪、谁推翻的；说清为什么 _abl_512fixed 和 _abl_1024fixed 的 R@5 不能直接比。

一、它要解决什么问题 ​

切块要同时满足两个互相拉扯的约束：

  • 块要够大：一个定义、一段公式推导、一张表的上下文必须落在同一块里，否则检索回来的东西无法回答任何问题；
  • 块要够小：块的字符数决定了送进 prompt 的 token 数，也决定了向量能表达多少语义——块越长，向量越像「整章的摘要」，区分度越低。

而这两个约束的最优解，只能靠实验定，不能靠感觉定。这一页记录的正是三次实验的结论，其中包括一次明确的「这两个数字不能比」。

二、方案与实现 ​

那个 * 2 的依据，是注释里的一句「中文约 1 字 ≈ 1 token 的粗略换算」——而这句话被实测推翻了。exp01_token.py 测出的真实字符/token 比是：中文约 1.2—1.3，纯英文可达 3+。也就是说：

  • 「512 档切出 1024 字符」既不是 512 token，也不是中英一致的 token 数；
  • 中英混排的语料下，同样一个「512 档」，中文块的 token 数约是英文块的 2.4 倍还多。

这条不是抠字眼：exp18b_token_budget.py 专门测真实切片的 token 数分布，因为送进 prompt 的上下文会不会超窗，取决于真实 token 数，而不是配置里的数字。

2.3 三档消融：512 vs 1024 vs 「事实完整性」 ​

实验设计有三个层次，越往后越诚实：

实验口径结果与结论
exp04_chunk_size.py事实完整性：已知答案的关键串是否完整落在同一块内。比 5 种切法：①固定无重叠 ②固定 + 15% 重叠 ③段落优先 + 15%（本项目实现）④固定 max=2048 ⑤段落优先 max=2048这是唯一与检索器无关的口径，测的是「切法本身有没有把答案切碎」。未实测：事实清单只记录了这个脚本的目的与方法，没有读到它的输出数字，因此**【待核对：5 种切法各自的事实完整率】**。验证命令：python exp04_chunk_size.py
exp17_chunk_compare.py512 档（out/）vs 1024 档（out_1024/）直接比 Recall@5⚠️ 无法直接比。换配置后 chunk_id 全变、gt 对不上；当时的处理办法是只比相对趋势并在报告里注明限制
exp30_slice_compare.py用与切片无关的证据口径：覆盖率@k（top-k 块里能「整段包含」探针的占比）+ probe 级 MRR✅ 这才是正确做法。它抓到了一个关键现象，见下

exp30 抓到的现象是：1024 档的粗切会把相邻的两个 gt 块合并成一块——gt 从 36 块降到 30 块。分母变小了，Recall@5 自然变高。

这直接解释了消融表里的这一对数字：

报告R@5gt 块数gt 密度
_abl_512fixed.md ③ 组68.8%36 块1.57 块/题
_abl_1024fixed.md ③ 组76.8%30 块1.30 块/题

按报告自己的纪律，这两行不可直接比较，更不能得出「1024 更好」。因为 Recall@5 = |gt ∩ top5| / |gt|，分母是 gt 块数——粗切让分母从 36 掉到 30，这个「提升」里有相当一部分是换尺子换出来的。

2.4 表格与公式：抽取是有损的 ​

这一节必须写得非常具体，否则面试官会认为你在回避问题。实测的损失形态（eval/report.md:132）：

原文：  mn = { 1e-8, if aₙ ∉ A′ ;
                1,    else
抽取后：( 1e-8, if an < A′ mn = 1, else.

2
3

三个损失同时发生：分情形公式被线性化、∉ 被识别成 <、下标丢失（aₙ → an）。注意第二个：这不只是「格式难看」，它是语义反转——∉ A′（不属于）变成了 < A′（小于）。任何依赖这个公式作答的问题，都会得到错误答案，而链路不会报错。

其他两类损失：

  • 表格列序错位：双栏解析下表格的行列关系可能被打乱；ingest.py:171 的注释记录了 p15 的 6 个块（指标定义 / 公式 / Table 2 / 结论 / 致谢）全被标成 'References'。
  • section 标签「偏移一格」：曾以为是标签错位，后来用 SCIS:p15:c065 实测证明根因是块跨越了章节边界，不是偏移（坑 35 更正了坑 13 的结论）。也就是说，一个块里同时含有上一节末尾和下一节开头，本来就是合法形态。

因此有一条硬纪律：表格类事实优先引用正文（eval/report.md:132）。

section 标签的问题还有一个具体来源：正则里 $ 写在了 (?:A|B) 内部，只锚定了 B 分支，结果造出 235 个假章节标签（坑 6，exp11_section_quality.py 记录为 BUG-6）。而 IEEE 系论文用 II. SYSTEM MODEL / A. State Space 这种编号，早期只认阿拉伯数字，导致 5 篇语料里有 2 篇的 section 覆盖率是 0%（126 块与 117 块两篇全丢，exp12_heading_formats.py）。

四、一次真实的数据流走一遍 ​

以 512 档处理一篇 16 页的中文期刊文献（《基于安全强化学习的多无人机编队与避障控制》，实测 n_chunks=35、第 1—16 页）为例：

步骤输入输出参数实际值
1一页的 block 列表重建顺序后的页文本按坐标条带式重建
2页文本去页眉页脚文本v2-page-number-by-proximity
3连续页文本流「当前章节标题」状态章节正则（含 II. / A. 形式）
4累积中的缓冲一块 Chunk上限 1024 字符
5相邻两块重叠 153 字符int(1024 * 0.15)
6缓冲 < 60 字符继续累积，不产块MIN_CHUNK_CHARS = 60
7单块 > 1024 字符硬切成多块_hard_split(text, 1024, 153)
8全部块35 条记录平均长度 763 字符（全库实测），最长 1132 字符

第 8 步那两个数字值得停一下：全库平均块长 763 字符，最长 1132 字符，而配置上限是 1024。最长块超出了上限——这就是坑 10「块长度会超出配置上限」。配置写了上限，不等于产物满足上限。

五、踩过的坑 / 做过的取舍 ​

现象根因怎么定位到的怎么修的教训
「512 档 = 512 token」这个换算从头就是错的注释里写「中文约 1 字 ≈ 1 token」，据此 ×2 得 1024 字符exp01_token.py 实测真实字符/token 比不改配置（改动会作废全部指标），但在文档里明确写清实际生效的字符数，并新增 exp18b 测真实 token 分布推断要量，不能靠注释里的经验值。这是本项目的「第四次我的推断错了」
用 --chunk 1024 比 Recall@5，比出来一个「更好」粗切把相邻两个 gt 块合并成一块，gt 从 36 降到 30，分母变小exp30_slice_compare.py 的覆盖率@k 与 probe 级 MRR（与切片无关的口径）结论改为「两者不可直接比较」，只比相对趋势并在报告里注明限制Recall@k 的分母是 gt 块数；换尺子之后比数字，等于没比
表格里的整数单元格被当成页码删掉清洗规则按「孤立数字 = 页码」判定，表格单元格也是孤立数字发现表格类问题全部答不对，回头查清洗规则规则改为 v2-page-number-by-proximity（按邻近性判页码）「看起来像页码」和「是页码」是两件事
5 篇语料里有 2 篇 section 覆盖率 0%早期章节正则只认阿拉伯数字编号，不认 IEEE 的 II. / A.exp12_heading_formats.py 逐篇统计覆盖率扩充正则；假标签问题另行修 $ 锚定语料换一批，正则就可能全废
块长度 1132 > 配置上限 1024硬切兜底路径与上限约束之间有缝对全库块长做分布统计记录为已知问题必须对产物做实测量

六、面试深挖：追问链 ​

第一条：chunk_size 怎么定的？

  • Q：你的 chunk_size 是多少？
  • A：配置里的键名是 "512"，但实际生效的是 1024 字符上限、153 字符重叠（15%）。因为配置里有一个 ×2 的换算——注释写「中文约 1 字 ≈ 1 token」，所以按 token 名义值乘了 2。
  • 追问：那这个换算是准的吗？
  • A：不准，而且实测推翻了它。我用 tokenizer 真的量过：中文的字符/token 比约 1.2—1.3，纯英文可以到 3+。所以「512 档切出 1024 字符」既不是 512 token，也不是中英一致的 token 数——在中英混排语料里，同样一档，中文块的 token 数大约是英文块的 2.4 倍以上。
  • 追问：那你为什么不直接把换算改对？
  • A：因为改了就要重跑全部指标。我现在有 16 份消融报告、一套 130 题的评测集，切片参数一改，chunk_id 全部失效、gt 全部对不上。我的处理是：不改线上参数，但把真实字符数写进文档，另外写了一个 exp18b_token_budget.py 专门测真实切片的 token 数分布——因为上下文会不会超窗取决于真实 token 数，不取决于配置里的数字。要不要改是个需要单独排期的决定，不是顺手改一行。

第二条：1024 是不是比 512 好？

  • Q：你试过更大的块吗？效果怎么样？
  • A：试过 1024 档。原始结果看起来是 1024 更好：512 档 ③ 组 R@5 68.8%，1024 档 76.8%。但这两行不能比。
  • 追问：为什么不能比？不都是 R@5 吗？
  • A：因为 Recall@5 = |gt ∩ top5| / |gt|，分母是 gt 块数。粗切会把相邻的两个 gt 块合并成一块——实测 gt 从 36 块降到 30 块，密度从 1.57 块/题变成 1.30 块/题。分母变小，分数自然变高。我专门写了一个实验（exp30_slice_compare.py）用与切片无关的口径去比：覆盖率@k（top-k 块里能整段包含探针的占比）+ probe 级 MRR。这才是可比的。
  • 追问：那你最后选了哪个？
  • A：保持 512 档作为线上默认，理由不是「它更好」，而是①它是全部现有指标与 gt 所对应的那一档，换档会让所有历史结论作废；②切块档位的收益在这个项目里不是最大瓶颈——真正的瓶颈是精排那 8.5 秒和中文查询的稀疏路失效。这也是我在这个项目里学到的一条：先分清哪个数字变了、是系统变好了还是尺子变了。

第三条：表格和公式怎么办？

  • Q：科研论文里全是公式和表格，你的系统怎么处理的？
  • A：抽出来是有损的，这个我不回避。一个具体例子：分情形公式 mn = {1e-8, if aₙ ∉ A′; 1, else} 被抽成 ( 1e-8, if an < A′ mn = 1, else.——分情形结构被线性化、∉ 被识别成 <、下标丢失。注意 ∉ 变 < 是语义反转，不只是格式问题。
  • 追问：那你还怎么敢给引用？引用了也是错的。
  • A：所以有一条硬纪律：表格类事实优先引用正文。我的引用校验只能验「编号合法性」——即模型引用的 [n] 是否落在上下文范围内；不能验「引用的内容是否真的支持这个结论」，后者需要 NLI 或人工复核。这两件事我在报告里是分开写的，不会含糊成「引用已校验」。
  • 追问：为什么不上一套版面分析工具专门处理表格？
  • A：成本收益不划算。我的表格类问题占比不高，而引入表格识别会带来一个新的风险源：识别错的表格比线性化的表格更危险——线性化的表格至少还能看出是乱码，识别错的表格会给你一个看起来很整齐但数字错了的结果。我更愿意把规则定成「表格类事实优先引用正文」，并在界面与文档里显式说明这个限制。如果语料换成财报类，这个取舍就要反过来，那时候必须上专业版面分析。
