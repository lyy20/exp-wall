科研文献 RAG 项目地图 ​

一句话：先用 18 秒看清这个项目是什么、由哪些模块组成、后面 14 页该怎么读。

这一页要回答什么 ​

  • 「你这个项目是做什么的？」——要求三句话说完，且不出现「大概」「类似」「一个 RAG 系统」这种糊话。
  • 「这个项目你是怎么组织的？」——要求说清离线与在线两条链路，以及每条链路上有哪些模块。
  • 「你另一个项目跟这个什么关系？」——要求说清两者的分界线，而不是「都是 AI 应用」。

读完这一页你应该能：不看笔记画出模块地图；说出这个项目与 YYHelp 最本质的一条差异；知道 15 页里哪几页是自己现在最该补的。

一、它要解决什么问题 ​

做这个项目的起点是一句很具体的抱怨：方向相关的论文越攒越多，但真正要查一个数的时候，只能靠 Ctrl+F 加脑子里的模糊记忆。比如「CTRIP-SAC 那篇里安全距离取了多少米」「那篇编队控制的论文用的是几维动作空间」——这类问题有三个共同点：

  1. 答案就在你自己下载过的 PDF 里，不需要联网、不需要模型有世界知识；
  2. 关键词搜不到：你记的是「安全距离」，论文里写的是 a safe distance ranging from 15m to 30m；
  3. 答错比不答更糟：科研场景下，一个编造的数字比一句「查不到」有害得多。

所以这个项目的目标不是「做一个能聊天的 PDF 助手」，而是：给定一批你真正读过的论文，问它事实性问题，它要么给出带出处编号的答案，要么明确说答不了，并且这两件事都有可复算的数字支撑。

不做这一步会怎样？——只会得到一个 demo：能答，但你不知道它什么时候会胡编；你知道它改了之后「感觉变好了」，但拿不出任何一个可以对比的数字。这个项目从第一天起就把「评测集 + 消融 + 回归门禁」当成和检索链路同等的一等公民，这也是它最值得写进简历的地方。

2.2 两条链路，只有两条 ​

离线链路只跑一次：data/*.pdf → extract_pages → 逐页清洗（clean_page_text，规则带版本号 CLEANING_RULE_VERSION = "v2-page-number-by-proximity"）→ chunk_pages 结构感知切块 → bge-m3 向量化（normalize_embeddings=True）→ 同时落两份索引：FAISS IndexFlatIP 与 rank-bm25 的 BM25Okapi。

在线链路每次提问都走一遍：retrieve() 里 dense 取 20、sparse 取 20 → rrf_fuse 融合成 20 → CrossEncoder 精排取 5 → build_context 拼上下文 → LLM 出 JSON → check_citations 校验编号。

为什么强调「只有两条」：面试官问「你这系统的架构是什么」，如果你答成一堆模块罗列，他会认为你没理解自己的系统。这个项目的本质是一条离线数据管道 + 一条在线查询管道，service.py / app.py / qa.py 只是同一套在线管道的三个入口（HTTP、GUI、CLI）。

四、一次真实的请求/数据流走一遍 ​

输入：一个纯中文问题「多智能体强化学习里怎么处理环境的非平稳性？」

步骤输入形态输出形态落在哪个模块
1问题字符串归一化后交给两路retrieve()（retrieve.py:255）
2问题字符串1024 维 np.float32 向量dense_search（retrieve.py:162）
3问题字符串中文二元组 token 列表config.tokenize（config.py:361-374）
4两路各 20 条 Hit融合后 20 条 Hit（带 RRF 分数）rrf_fuse（retrieve.py:215）
520 条候选精排后 5 条（带 Cross-Encoder 分数）rerank（retrieve.py:242）
6top1 分数一个浮点数，用于与 REFUSE_THRESHOLD 比较top1_score（retrieve.py:339）
75 条块 + 元数据一段带 [1] 文献 [A]｜第 x 页｜章节 头的上下文build_context（generate.py:84-119）
8上下文 + 问题JSON {"answer":"…","citations":[…],"insufficient":false}_call_llm（generate.py:192）
9citations 列表(是否通过, 非法编号列表)check_citations（generate.py:272-291）

注意第 3 步：这个问题是纯中文的，而语料是英文的。这正是第 ⑤ 页要讲的核心冲突——BM25 是单语词频模型，中文 token 在英文语料里 df=0，分数全为 0，整条稀疏路会被静默跳过。这也解释了为什么项目里有一个 57 条的中英术语映射表。

五、踩过的坑 / 做过的取舍 ​

现象根因怎么定位到的怎么修的教训
「知识库规模」在不同文档里是 55 篇 / 56 篇 / 5 篇三个数16 份消融报告的「§五 已知限制」是模板文本，全部照抄了早期的「5 篇」；out/MANIFEST.json 没跟上最后一次去重逐份报告与 doc_index.json、doc_sources.json 交叉比对定口径：以 55 篇 / 5325 块 + 日期为准，其余标为历史值模板化的「已知限制」章节会腐烂；任何规模数字必须带日期或版本
项目定位写成「面向人工智能领域科研文献」设计文档的早期表述偏大；实际语料是 AI 的具体子方向（无人船 / MARL）对照 app.py 界面文案与 doc_index.json 实际文献标题对外统一说「USV / MARL / 路径规划 / 安全 RL 方向的文献」定位句写大了，第一个追问就会崩；宁可窄而准
回滚清单 MANIFEST.json 记录的是去掉重前的 5470 块文件自称「改了切片参数就必须同步更新」，但没有强制机制与 eval/report.md:129 的 5325 块对不上记下来：派生文件需要一条「与源数据是否一致」的机械检查（对照 corpus.py:122-168 的 verify()）自检文件自己也会过期
机器生成的 gt 报告 ③ 组 R@5 = 100.0%gt 取自 ③ 组自己的 top-5，循环依赖报告顶部被强制加上警告后复核_machine_report.md 顶部自写「🚫 本报告不可作为结论」用被测系统产出的标注，会让指标彻底失去意义

六、面试深挖：追问链 ​

第一条：这个项目到底解决了谁的什么问题？

  • Q：一句话说清你这个项目做什么。
  • A：给一批自己读过的科研论文建索引，回答事实性问题，答案带出处编号，资料不够时明确拒答；并且检索质量、拒答质量都有一套 130 题的评测集和可复算的数字。
  • 追问：这些论文你为什么不直接喂给长上下文模型？
  • A：两个原因。一是超出问题本身：55 篇 PDF、5325 块，全塞进上下文既不经济也不稳定；二是这个项目的价值在可核对——我要的是每句话后面能指到「第 15 页 4.3 节」，而不是一段流畅但无法验证的文字。检索链路让我可以把「引用编号是否合法」做成程序化校验。
  • 追问：那你为什么不干脆做成 Agent，让它自己决定要不要检索？
  • A：因为这是单轮事实问答，加编排只会增加不确定性与成本，不会提升正确率（这是项目里的明确结论）。Agent 化的价值在需要多步工具调用和副作用处理的场景；这里每一步都是确定的：检索、精排、拼上下文、调模型、校验。什么时候该上 Agent，我在另一个项目里做了——那是有真实工具副作用的电商客服场景。

第二条：你怎么组织这个系统的？

  • Q：讲一下整体架构。
  • A：两条链路。离线一条：解析、清洗、切块、向量化、写 FAISS 和 BM25 两份索引。在线一条：双路召回各取 20，RRF 融合成 20，Cross-Encoder 精排取 5，拼上下文，调 LLM 出 JSON，校验引用编号。HTTP、Streamlit 界面、CLI 三个入口共用同一条在线链路。
  • 追问：为什么检索和生成要分成两条链路，而不是边检索边生成？
  • A：因为离线链路是可以懒的，在线链路不能。切块参数、清洗规则、embedding 模型，任何一项变了都必须重新走一遍离线链路——清洗规则甚至带版本号（v2-page-number-by-proximity），因为清洗规则变过就会让结果不可比。而在线链路里每一步都要能在一次调用内走完，不做循环，才能保证延迟可测、失败可归因。
  • 追问：那 qa.py、app.py、service.py 三个入口重复代码了吗？
  • A：没有，它们都调 retrieve() 和 answer_question()。这里有一个具体的教训：service.py 里 from retrieve import retrieve 必须在模块顶层写，写成函数内 import 会让测试里的模块级 monkeypatch 失效，导致「离线测试」偷偷加载了 4.4GB 模型，延时从 0.1 秒变成 40 秒。可测性也是设计的一部分：依赖必须能在模块层面被替换。

第三条：这个项目和你另一个项目什么关系？

  • Q：你两个项目都是 AI 应用，是不是同一个东西换了个皮？
  • A：不是。分界线在有没有状态和图。这个项目是直线流程、无状态，每次问答独立，唯一的「状态」是进程内的缓存和一个与对话无关的配额计数器。YYHelp 是 LangGraph 的状态图，有对话状态、业务槽位、检索快照，还有 interrupt() 暂停等待人工确认。
  • 追问：举一个只有 YYHelp 才有的技术问题。
  • A：节点重跑与副作用。interrupt() 所在的节点在 resume 时会从头重跑，实测副作用计数从 1 变成 2。所以有一条纪律：不能在 interrupt() 之前写审计日志、建工单、发短信、累加计数器——那里的节点只允许读 state、算条件、调 interrupt、返回状态更新。这个项目里没有这类问题，因为 LLM 调用是「读」，重试安全。
  • 追问：那这个项目的工程量花在哪？
  • A：评测与数据管道。54 条踩坑记录里过半是数据与标注问题：清洗规则把表格里的整数单元格当页码删掉、块跨越章节边界导致 section 标签错、同一篇论文被导入两次而文件名判重和字节判重都拦不住、独立盲标 gt 之后 Recall 从 87% 掉到 71%。检索算法本身反而相对标准。
