定位与语料 ​

一句话：说清「为什么是这批论文」，以及语料如何决定了一个系统能答什么、不能答什么。

这一页要回答什么 ​

  • 「你的语料是什么？从哪来的？有多少？」——要求给出带日期的具体数字，而不是「大概几十篇论文」。
  • 「你为什么选科研文献这个题？」——要求说出这个题在技术上逼出了哪些必须解决的问题。
  • 「你的评测集里怎么会有『不可回答』的题？是凑的吗？」——要求说清负样本的构造逻辑，以及它为什么会失效。

读完这一页你应该能：说清 55 篇 / 5325 块这个数字的来历与有效期；说清 doc_index.json 与 doc_sources.json 各自解决什么问题；说清「负样本的有效性是语料的函数」这句话的具体含义。

一、它要解决什么问题 ​

这个项目的定位句在源码里写得很直白：

「科研文献 RAG 服务：PyMuPDF 解析 → 结构感知切片 → 双路召回 → RRF → 精排 → 引用校验 + 拒答」（service.py:70-71，FastAPI 的 description）

面向的具体方向是无人船 / 多智能体 RL / 路径规划 / 编队控制 / 安全 RL（app.py:478-521）。为什么偏偏是这批文献？因为它同时逼出四类问题，而这四类问题恰好覆盖了 RAG 工程里最容易被问倒的部分：

语料的性质逼出来的问题落在哪一页
中英混排（含 2 篇中文期刊）稀疏检索在跨语言时静默失效：中文 token 在英文语料里 df=0，分数全为 0，整条稀疏路被跳过而不报错⑤ 检索层
双栏 PDF + 公式 + 表格朴素抽取会把左右栏交错、把表格线性化、把 ∉ 识别成 <③ 索引 / ④ 切块
专业术语密集用户记的是中文术语（「安全距离」），论文里是英文短语（a safe distance ranging from 15m to 30m）⑤ 检索层
你自己也没读完有些问题「库里有这个词但没有答案」——这天然构成不可回答问题集本页第五节

反过来说，如果语料换成一批结构规整的中文产品文档，前三类问题一个都不会出现，这个项目也就没什么可讲的。

运行环境（含一个诚实的负面事实） ​

设计阶段的机器是 RTX 4070 (12GB) + i7-12700KF + 32GB RAM（output/rag-项目设计.md:87）。但实测全程没用上 GPU：torch==2.14.0 装的是 PyPI Windows 的 +cpu 轮子，cuda_available=False。这条被写进了 NOTES 坑 3。它带来的直接后果就在第 ⑥ 页：值 8.5 秒的 Cross-Encoder 精排是在 CPU 上跑的。

这个「负面事实」不要藏。面试官问「你精排 8.5 秒是不是太慢了」，正确答法是「这是在 CPU 上、20 对的耗时；我确实没把 GPU 用起来，因为装的是 CPU 轮子，这是一个已记录的已知问题，而不是算法问题」。

二、方案与实现 ​

顶层三个字段：

}

每篇文献 8 个字段：doc / title / n_chunks / page_from / page_to / pdf / pdf_mb / first_text。

  • title 来自 config.doc_title()：5 篇是人工填的，其余从首块正文抽取或回退到文件名——不是全量人工核对。
  • pdf 是归一化匹配的结果：用 norm_key() 归一化后互为前缀匹配（pk.startswith(k) or k.startswith(pk)），多个候选取归一化长度最接近的那个；匹配不到则为 null（corpus.py:46-54）。
  • first_text 是首块正文归一空白后截 200 字符，专门给人看的：用来人工核对「这条索引记录到底对应哪篇 PDF」。

实测样本（可以拿去对）：COLREGs 那篇 n_chunks=86 / 第 1—13 页 / pdf_mb=3.79；A review of path planning for unmanned surface vehicles n_chunks=119 / 第 1—22 页；《基于安全强化学习的多无人机编队与避障控制》n_chunks=35 / 第 1—16 页 / pdf_mb=20.67。

生成逻辑在 corpus.py:57-90 build_index()；这个文件是**「文献级」视图的 sidecar**，与检索用的 chunk_meta.json 是两回事。

2.2 data/doc_sources.json：出处与可信度 ​

顶层：n_docs: 55、n_chunks: 5325、n_direct: 52、n_search: 3、n_verified: 47。每篇的字段是 doc / title / doi / kind / scope / url / verified / note / crossref_title / verify_against / verified_against。

字段取值含义
kind"doi" / "arxiv" / "search"这篇是走 DOI、arXiv 还是只有学术搜索链接
scope"first_pages" / "fulltext"当初是按首页还是全文纳入的
verified布尔是否通过 Crossref 标题核验（共 47 篇通过）

它解决的不是检索问题，而是合规与可核对问题：app.py:3-9 明确写了两条理由——只给出处链接，不提供全文下载（版权）。app.py:120-129 的 source_badge() 据此渲染四种徽章：DOI 已核验 / DOI 未通过标题核验 / arXiv / 仅有学术搜索链接。

为什么这个设计值得单独讲：把「这篇文献的元数据是否可信」做成界面上的显式状态，而不是默默展示一个链接。这和整个项目的评测纪律是同一条思路——可信度必须能被看见，不能被假设。

2.3 为什么这个语料天然拥有「不可回答问题集」 ​

这是本页最值得讲的一点。评测集里 6 道「不可回答」的题不是随便编的，而是从语料里长出来的。最典型的例子是 U07：

「多智能体 RL 中如何处理环境的非平稳性？」

设计理由（exp16_u07_check.py docstring）：库里有这个词，但没有答案——相关论文只在 future work 里提到「多 USV 协同」，并没有讨论非平稳性的处理方法。也就是说，这个问题在检索层面看起来是命中主题的（能召回相关块），但在答案层面根本没有支撑。这正是最考验系统的负样本类型：一个只会「检索到相关块就开始编」的系统，会在这里输得一败涂地。

它带来的连锁反应很值得注意：

  1. 它证明了拒答必须是程序层的：如果只靠模型自述「资料不足」，模型看到「有多智能体、有协同」的段落，很可能就顺着答了。
  2. 它会失效：扩库之后，新增的文献里如果有人讨论了 MARL 非平稳性，U07 的资格立刻没了。实测中确实复核出这道负样本在扩库后已经可以回答，于是把它转成了多跳题，负样本从 7 道变成 6 道。
  3. 它训练出了一条纪律：负样本的有效性是语料的函数，不是永久属性。

四、一次真实的请求/数据流走一遍 ​

以「这篇《基于安全强化学习的多无人机编队与避障控制》在库里有多少块？」这条元数据问题为例，走一遍语料 sidecar 的链路：

步骤输入输出模块
1中文标题字符串归一化 keycorpus.norm_key()（corpus.py:46）
2归一化 key该篇的 n_chunks / page_from / page_to / pdf_mbcorpus.load_index()（corpus.py:93）
3doc key本地 PDF 绝对路径corpus.pdf_path()（corpus.py:99）
4索引内容 + 磁盘上的 PDF一致性核对结果corpus.verify()（corpus.py:122-168）
5整库统计篇数、块数、页数区间corpus.overview()（corpus.py:109）

实测该篇的输出是：n_chunks=35、第 1—16 页、pdf_mb=20.67、first_text 里含「中国科学: 信息科学 SCIENTIA SINICA Informationis … 国防科技大学智能科学学院」——first_text 的作用在这一步体现得最清楚：它让你不用打开 PDF 就能确认这条索引记录没有对错文件。

五、踩过的坑 / 做过的取舍 ​

现象根因怎么定位到的怎么修的教训
报「56 篇 5470 块」，但实际有效语料是 55 篇 5325 块同一篇论文被导入两次：文件名不同（同名判重失效）+ PDF 字节不同（sha1 判重失效），但抽取出的正文完全相同对全库正文做指纹比对判重升级为四层（同名 / 字节 / 正文指纹 / 高相似 8-gram Jaccard）；已进库的用 dedupe_corpus.py 清理——从 FAISS 读回向量重建，不重新编码判重的对象应该是语义内容，不是文件
7 道「不可回答」题里，U07 扩库后其实已可回答训练语料变了，问题的可回答性就变了独立会话（不看检索分数）读原文复核U07 转为多跳题；拒答准确率反而从 85.7% 升到 100%负样本的有效性是语料的函数，不是永久属性
title 字段有 5 篇是人工填的、其余是启发式抽取早期为了快速跑通，只人工核对了 5 篇；自动抽取会填错逐篇比对 first_text保持现状，但明确写清覆盖率，不假装全量人工核对自动填错比不填更糟；宁可说「覆盖 5 篇」
索引里 pdf 字段为 null归一化 key 匹配不到磁盘文件用 corpus.verify() 核多候选取归一化长度最接近的文件名匹配是启发式，必须有 verify() 兜底

六、面试深挖：追问链 ​

第一条：语料为什么这么选？

  • Q：你为什么选科研文献这个语料？
  • A：因为它同时逼出四类必须解决的问题：中英混排让稀疏检索静默失效、双栏 PDF 让抽取顺序错乱、专业术语让字面匹配失效、而「我也没读完」这一点天然造出了不可回答问题集。换成结构规整的中文文档，这四类问题一个都不会出现。
  • 追问：那你为什么不干脆只留英文文献，绕开跨语言问题？
  • A：因为跨语言问题不是「多出来的麻烦」，而是这个项目最有价值的一条发现。实测数据显示：原始 BM25 跨语种 R@5 只有 8.3%，加领域术语表到 29.2%，而先用 LLM 把中文问题翻成英文检索式再到 70.8%。这三个数字说明的是同一件事——不要用 BM25 做跨语种召回。如果语料是纯英文的，我就拿不出这组数据。
  • 追问：中英混排里那 2 篇中文文献，是刻意加进去的吗？
  • A：不是刻意设计的，但它的作用比预期大得多。它制造了一个假阳性温床：中文查询的 BM25 top-20 会全部命中那 2 篇中文文献——注意，不是因为主题相关，而是因为语言相同。扩库后混合检索 R@5 从 64.5% 崩到 29.2%，根因就是它。这条我总结成一句话：同语言 ≠ 同主题。

第二条：评测集里的负样本是怎么来的？

  • Q：你那 6 道「不可回答」的题是凑的吗？
  • A：不是。每一道都是从语料里长出来的，判据是「库里有这个词，但没有答案」。最难的 U07 是「多智能体 RL 中如何处理环境的非平稳性」——相关论文只在 future work 里提了多 USV 协同，根本没讨论处理方法。这种题专门打「检索到相关块就开始编」的系统。
  • 追问：你怎么确认它真的不可回答？自己看一眼觉得没有就算了？
  • A：没用「看一眼」这个标准。复核方式是换一个独立会话、不看任何检索分数、直接读原文，正因为这样才复核出扩库后 U07 其实已经可以回答——新加入的文献里有人讨论了这个主题。这也是为什么负样本集从 7 道变成 6 道，而拒答准确率反而从 85.7% 升到 100%。
  • 追问：那如果负样本本来就不该存在，你的「拒答准确率 100%」是不是自欺欺人？
  • A：这是一个必须在面试里主动说清的点。拒答准确率的分母只有 6 道题，标成 100% 并不意味着拒答机制完美，只能说明「在这 6 道上都拦住了」。所以我更看重另外两个指标：误拒率 7.3%（124 道可回答题里被错误拒掉的比例）和漏拒 0。而且误拒率还被拆成了两层——只靠程序层阈值是 1.6%，加上模型自述「资料不足」是 6.5%，差的那约 5% 就是模型自述的过度触发。

第三条：语料规模变过，你的结论还成立吗？

  • Q：你的语料从 5 篇扩到 55 篇，之前写的结论还有效吗？
  • A：分两类。结构性结论仍然成立——比如「RRF 的 rank 从 0 还是从 1 开始不会让排序错乱」「块长度会超出配置上限」。所有绝对指标全部作废，必须重测。项目里有一条明文纪律：报数必须带 gt=<版本>｜密度=<块/题> 这把尺子，因为 Recall@5 的分母是 gt 块数，密度不同的两份报告根本不可比。
  • 追问：具体到哪个结论被推翻了？
  • A：最典型的是「混合检索一定优于纯向量」。5 篇语料上，纯向量 R@5 62.3%、混合 64.5%，融合确实有帮助；扩到 56 篇之后，纯向量 49.3%、混合掉到 29.2%，比不用融合还差。同一个系统、同一套代码、同一个融合公式，只是语料变大了，结论就反过来了。
  • 追问：那你怎么保证以后不会再被同样的事坑一次？
  • A：靠两件事。第一，语料规模数字必须带日期或版本，因为库里有三套数字在流通（55 篇真值、56 篇去重前中间态、5 篇过期模板文本）。第二，报告必须带标尺节，而且标尺留空就要显式写「未标注！跨版本比较一律无效」——这是当前主报告的真实状态，标尺节里的 gt 版本是空的，我选择把它如实留空，而不是补一个看起来完整的版本号。
