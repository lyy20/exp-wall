回归门禁与 CI ​

一句话：门禁只测确定性断言，把"已知未达标"和"真实失败"分开统计——否则 gates 会在一周内被大家学会忽略。

这一页要回答什么 ​

  • 「你怎么防止改动把功能改坏？」——要能说出门禁测什么、不测什么，以及为什么不做端到端答案质量门禁。
  • 「有失败用例怎么办？直接跳过吗？」——要求答出 known_issues 机制：有据可查的已知问题单独统计，只有真实失败才影响退出码。
  • 「你的 CI 跑得动吗？」——要求说清离线、不装 torch、10 分钟超时这三条约束是怎么来的。

读完这一页你应该能：讲清回归用例的三类断言；讲清"已知问题"为什么必须与真实失败分开；说清三态退出码的约定与出处。

一、它要解决什么问题 ​

没有门禁的项目有一个典型症状：每次改动都在偷偷变坏，而第一个发现的是用户。

但门禁做过头也一样致命——如果一个门禁需要 40 秒加载 4.4GB 的模型、跑 20 分钟、还依赖 LLM 的随机输出，它的下场只有两个：要么被从 CI 里删掉，要么被大家养成"红了也照合并"的习惯。门禁的价值等于"真的会被执行"的那部分。

所以本项目定的设计取舍是一句话：回归门禁必须便宜、确定、可重复。（eval_regression.py 的 docstring 原文）

这条取舍直接决定了三件事：

决定内容
只测确定性断言三条断言全部不依赖 LLM
不测答案质量答案对不对需要 LLM 裁判，引入成本与不确定性 ⇒ 属 exp23_answer_accuracy.py 的职责（手动跑）
已知问题单独记账否则门禁会长期红着，然后被忽略

二、方案与实现 ​

2.1 三条断言：全部不依赖 LLM ​

eval_regression.py:60-79 只检查三件事：

断言判据为什么它是确定性的
① refused程序层阈值判定：refused_by_threshold = t1 < REFUSE_THRESHOLD阈值比较是纯数值比较，与 LLM 无关
② gt_in_topkgt 块是否进 top-k（纯检索）只跑检索，不调生成
③ 引用编号的提取从答案文本抽 [n]纯字符串处理

核心判定代码（eval_regression.py:60-79）：

python
k = c.get("top_k", 5)
hits = retrieve(c["question"], final_k=max(k, 10))
t1 = top1_score(hits)
refused_by_threshold = t1 < REFUSE_THRESHOLD
ok_notref = (not refused_by_threshold) == c["expect"]["not_refused"]
ok = ok_gt and ok_notref

两处值得注意：

  • final_k=max(k, 10)：用例里的 top_k 是判定深度，但请求时至少取 10 个——这样同一个用例既能判 top_k=5 的命中，也能给出"gt 在第几名"的名次信息（供基线对比用）。
  • ok_notref 比较的是"程序层拒答"与"期望"，而不是"模型拒答"。这刻意把可判定的一部分（阈值）与概率性的一部分（模型行为）分开——后者在 exp21 里用受控实验单独测。

明确不检查"答案对不对"：那需要 LLM 裁判、引入成本与不确定性。这条边界不是偷懒，是为了让门禁能在没有 API Key、没有 GPU 的机器上跑。

2.2 已知问题与真实失败：为什么必须分开统计 ​

两个数据文件（eval_regression.py:83-93）：

文件用途
eval/regression/cases.jsonl（5536 B）用例集
eval/regression/known_issues.json（1629 B）已知未达标（有据可查）

分开统计、逐条打印 reason，只有 real_fails 影响退出码。

known_issues.json 里当前有 3 条，每条都带性质与下一步动作：

题号gt 块性质与 next_action
S08SCIS:p2:c010（EKF 定义处）在 top-10 之外，属召回/排序失败；人工核对 verdict=confirm；next_action = 提高 DENSE_TOP_K 或对 EKF 类术语加 BM25 权重后复测
S13SCIS:p11:c052（含 3 m/s 与一维动作空间，逐字可查）next_action = 该块含数学记号 ψt，PDF 抽取后变形 ⇒ 向量与 BM25 都难匹配，考虑符号归一化
M06["SCIS:p6:c031", "SCIS:p7:c035"]扩库 5→56 篇后新出现的召回失败：干扰项增加 10 倍后掉出 top-5，同一套代码在 5 篇语料上是通过的；next_action = 查询侧术语扩展 + 符号归一化，不要靠调 top_k 掩盖

为什么不能直接删掉这 3 个用例（这是这一节最关键的判断）：

  1. 删掉等于丢掉信息。M06 那条写着"同一套代码在 5 篇语料上是通过的"——这是关于脆性的证据，删了以后扩库带来的系统性风险就没人记得。
  2. 删掉会掩盖"红线在哪"。留给改的人一句"这几题现在不行"，比让门禁长期红灯然后被忽略强得多。
  3. 但留着红也不行。所以处理方式是三分类：通过 / 已知问题（不计入失败） / 真实失败。第三类才让门禁变红。

判定纪律：known_issues 不是"豁免名单"，而是带 next_action 的待办。每条必须写清"这是什么性质的问题 + 下一步怎么验证修好了"。没有 next_action 的已知问题，就是在给自己开后门。

2.4 基线对比：只比名次，不比分数 ​

--baseline 参数（eval_regression.py:98-111）：只看 first_gt_rank 名次变化（名次变小 = 变好）。CLI 另有 --id（逗号分隔题号）方便单题复查。

为什么比名次而不是比分数：分数受模型版本、归一化方式、批次影响；名次是序数，抗量纲漂移。而且名次变化指向动作——名次从 3 掉到 12 说明"排不上来"，从"找不到"变成"第 2 名"说明"召回修好了"。

2.5 四层验证链：不止一个回归脚本 ​

单靠 eval_regression.py 盖不住全局。项目的离线验证是四层（run_all_checks.py:46-66，共 19 项）：

层覆盖代表脚本
A 静态语法检查——全部 .py 文件run_all_checks.py 内置
B 单元可观测性 + CI 门禁（离线）ci_checks.py
C 集成服务层（健康 / 限流 / 超时 / SSE）service_tests.py
D 数据切片对照等需要额外产物的检查exp17_chunk_compare.py（需 out_1024/）

三条配套纪律：

  1. 有 SKIP 态，不是非黑即白（run_all_checks.py:22-23）：D 层 exp17 需要 out_1024/ 目录，不存在时标 SKIP 而不是失败。这与评测报告里"缺数据用 — 而不是 0"是同一条纪律——"不适用" ≠ "失败"，也 ≠ "通过"。
  2. 退出码 0 = 全部通过（run_all_checks.py:20），失败则 return 1（run_all_checks.py:157）。全量验收实测 PASS 17 / FAIL 0——17 是运行时通过的项数，检查表登记 19 项，差额来自 SKIP（需额外产物的检查）。
  3. 自检必须重新读产物（坑 52）：早先的自检脚本读的是"自己的记录"而不是产物，于是出现"自检报告的事实"与"产物的事实"不一致。自检报告不是证据，产物才是。 这与 corpus.py:122-168 的 verify() 是同一思路。

run_all_checks.py:12-14 还写了一句很值得抄的话：

本项目已修的 26 个问题里，好几个正是"某个分支从没被执行过"。

这句是四层检查存在的理由：静态层保证文件能被导入（编译期错误早发现）、单元层保证纯函数行为、集成层保证 HTTP 语义、数据层保证产物一致。四类问题有不同的发现方式，不能指望一个脚本全包。

为什么不装 torch 是设计而不是妥协：装了 torch 就要下 4.4GB 的 bge-m3，CI 从"秒级"变成"十分钟级 + 依赖外网"，任何一次网络抖动都会让门禁变红——那门禁就死了。取舍是：CI 只跑不需要模型的那一层（A/B/C 中判定不依赖模型的检查），需要模型的检查留给本地 run_all_checks.py。

2.7 一个反例：测试跑的不是被测量的那条路径 ​

坑 46 值得单独记：测"成本熔断"时用的是不会花钱的请求——因为程序层拒答的成本是 0。于是预算线永远触不到，测试永远绿，而熔断逻辑从没被验证过。

教训：测试用的是不是"被测量那条路径"，必须自己验证。 这类错误比断言写错更难发现——断言本身没错，只是它断言的那件事没被触发。

同源的另一条是坑 42：threading.local 里的 trace_id 不跨线程，于是 HTTP 层有 trace、业务日志里全空。这个 bug 的隐蔽性在于"HTTP 访问日志看起来一切正常"——又一条"看起来通过了，其实测的不是那条路径"。修法是 obs.propagate(tid)(fn) 包装器。

五、踩过的坑 / 做过的取舍 ​

现象根因怎么定位到的怎么修的教训
测"成本熔断"永远不触发用的是程序层拒答请求，成本是 0检查测试走的是不是那条会花钱的路径端到端测试改用真实调用路径测试用的是不是被测量那条路径，必须自己验证
业务日志里 trace_id 全空threading.local 不跨线程HTTP 日志正常、业务日志空 ⇒ 对比两层obs.propagate(tid)(fn) 包装器"看起来通过了"可能是"测的不是那条路径"
自检报告与产物不一致自检读的是自己的记录，不是产物拿产物和报告对不上才发现自检改为重新读取产物自检报告不是证据，产物才是（与 corpus.verify() 同思路）
自检显示"gt_chunks 已回填 124/23"分母硬编码，换题集后没跟着变换题集规模后数字对不上分母改为动态计算自检脚本里的常数，就是下一次的假通过
ci_checks.py 未读源码，CI 具体项无法给行号本轮只确证了文件存在与依赖清单—如实写"未逐行读"，只给已确证的四条不确定的地方不要用"应该"填上

六、面试深挖：追问链 ​

第一条：你的门禁为什么不测答案质量？

  • Q：回归门禁都检查什么？
  • A：只检查确定性断言，一共三类：程序层拒答（top1_score < REFUSE_THRESHOLD 的纯数值比较）、gt 块是否进 top-k（纯检索，不调生成）、以及引用编号的提取（纯字符串处理）。明确不检查"答案对不对"。
  • 追问：为什么不测答案质量？那不是最重要的吗？
  • A：因为门禁必须便宜、确定、可重复，而答案质量判定要引入 LLM 裁判——它带来成本、不确定性，还有随机性（同一个 prompt 每轮中招的题都不一样，这在坑 27 里吃过一次亏）。答案质量的评测我放在 exp23_answer_accuracy.py 里手动跑。取舍是这样：门禁的作用是"拦住确定性的退化"，不是"证明质量没问题"。一个 20 分钟、偶尔因为网络抖动变红的门禁，一周内就会被大家学会忽略。
  • 追问：那你怎么保证门禁绿了不会给人错误的安心感？
  • A：回归脚本结尾一定会打印一句边界声明："这批用例只覆盖确定性断言。答案质量请看 exp23_answer_accuracy.py（手动跑）。" 我觉得这句声明和断言本身一样重要——没有边界声明的门禁，会被当成"质量已保证"的证据，那比没有门禁更危险。

第二条：现在还有 3 道题是失败的，你怎么处理？

  • Q：我看你有 known_issues.json，里面记着 3 个问题。这是不是相当于给自己开了豁免名单？
  • A：不是豁免名单，是带 next_action 的待办。S08 是 EKF 术语那条块的召回/排序失败，下一步是提高 DENSE_TOP_K 或者对 EKF 类术语加 BM25 权重后复测；S13 那条块含数学记号 ψt，PDF 抽取后变形了，向量和 BM25 都难匹配，下一步是符号归一化；M06 写的是"扩库 5 篇到 56 篇后新出现的召回失败，同一套代码在 5 篇语料上是通过的"，下一步是查询侧术语扩展 + 符号归一化，而且我特意写了不要靠调 top_k 掩盖。
  • 追问：为什么不干脆把这 3 个用例删掉？门禁不就全绿了吗？
  • A：因为删掉等于丢掉信息。M06 那条记录的是关于脆性的证据——它证明"5 篇语料上通过的代码，在 56 篇上会失败"。这个信息比当天门禁是不是绿的更值钱。而且删掉之后，"红线在哪"就没人记得了，下次扩库还会再踩。所以我的做法是三分类：通过 / 已知问题 / 真实失败，只有第三类影响退出码，前两类都打印出来。
  • 追问：那怎么防止 known_issues 慢慢变成垃圾桶？
  • A：靠准入条件：进这个名单的每一条必须写清两件事——这是什么性质的问题（是召回失败，还是解析把公式弄坏了）、下一步怎么验证修好了。没有 next_action 的条目不许进。S08 那条还额外记了人工核对结论 verdict=confirm。要求写清 next_action，等于强迫自己承认"我知道它为什么坏、也知道怎么修"，而不是"先记下来以后再说"。

第三条：你的 CI 里为什么不装 torch？

  • Q：你的 CI 具体跑什么？
  • A：.github/workflows/ci.yml，ubuntu-latest + Python 3.12，timeout-minutes: 10，push 和 PR 都触发。依赖清单只有 numpy rank-bm25 fastapi uvicorn httpx pydantic 这几个——不装 torch、不下模型。
  • 追问：不装 torch，那检索和模型相关的检查怎么跑？
  • A：CI 只跑不需要模型的那一层。本地有一份 run_all_checks.py 做四层检查：A 静态（全部 .py 语法）、B 单元（可观测性与门禁，离线的 ci_checks.py）、C 集成（服务层的健康/限流/超时/SSE，service_tests.py）、D 数据（切片对照等需要额外产物的检查）。全量验收实测 PASS 17 / FAIL 0。需要模型的检查留在本地跑，因为 CI 装 torch 就要下 4.4GB 的 bge-m3。
  • 追问：那 CI 的门禁是不是太弱了？
  • A：我认为**"能一直跑"比"看起来很全"重要**。装 torch 的代价是 CI 从秒级变成十分钟级加依赖外网，任何一次网络抖动都会让它变红——红几次以后大家就会开始无视它。另外我吃过一次更隐蔽的教训：有一次测试偷偷加载了 4.4GB 模型，因为函数内 import 让模块级 monkeypatch 失效，一个本该 0.1 秒的用例变成 40 秒，测试输出里出现了 Loading weights: 100%。从那以后我把"可测性"当成设计的一部分：依赖必须能在模块层面被替换。而且这四层里还有一个细节我很在意——D 层需要 out_1024/ 的检查在目录不存在时标 SKIP 而不是失败，跟评测报告里"缺数据用 — 而不是 0"是同一条纪律。
