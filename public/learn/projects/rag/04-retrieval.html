检索层 ​

一句话：这一页记录一条被自己的实测推翻的常识——「混合检索一定优于纯向量」是有前提的。

这一页要回答什么 ​

  • 「你用什么检索？混合检索比纯向量好吧？」——要求答出「不一定」，并给出前提条件与实测数字。
  • 「你的 Recall@10 和 Recall@5 一样？那说明你排序很好？」——要求识别出这是标注窗口造成的构造结果，而不是靠猜。
  • 「RRF 那个 k 取多少？rank 从几开始？」——要求说清一个抄了三处、从没验证过的因果句是怎么被推翻的。

读完这一页你应该能：画出双路检索 + 融合 + 自检的完整流程；说清「同语言 ≠ 同主题」这句话的具体机制；说清 SPARSE_MODE=overlap 为什么是「让配置自己判断该不该生效」。

一、它要解决什么问题 ​

单路检索有两个已知的盲区，而这个语料两个都踩：

  • 纯向量不擅长精确的字面匹配。exp02_embedding_fail.py 给了一个极端例子：CTRIP-SAC 与 PER-SAC 只差两个字母、语义相反，余弦相似度高达 0.881，反而超过真正同义改写的 0.599。要区分这种「近义缩写」，必须靠字面匹配。
  • 纯字面匹配不认识同义表达。用户记的是「安全距离」，论文写的是 a safe distance ranging from 15m to 30m。

所以项目用了双路：dense（FAISS 稠密）+ sparse（自建 BM25），再用 RRF 融合。教科书到这里就结束了——但本项目在扩库之后发现，融合本身可能是有害的。

2.2 Sparse 路：BM25 与它的原理性边界 ​

rank-bm25 的 BM25Okapi，索引在 ingest.py 建、查询在 retrieve.py:184 用；分词真源是 config.tokenize()：英文按词、数字原样、中文二元组（不足两字退单字）。二元组的例子：「安全距离」→ 安全 / 全距 / 距离。

两个必须写清的行为：

  1. 全 0 分等于空结果：if scores[i] <= 0: continue（retrieve.py:188）——BM25 全 0 分时返回空列表，这是静默降级。
  2. 一次警告 + 一个计数器：空结果用 _SPARSE_EMPTY（retrieve.py:127）计数，sparse_empty_count()（:138）可读，reset_sparse_empty()（:143）可重置，首次出现时打印一次警告（:200-209）。

为什么要计数，而不是只打一条日志？ ——源码注释（retrieve.py:123-126）写得很清楚：消融实验里「混合检索」那一组，如果大部分题上 BM25 都是空的，那么这一组的指标其实反映的是纯向量，报告里必须说清。一个只打一次的日志，不足以支撑这句话；一个可以读取的计数器才行。这是「可观测性要服务结论，而不是服务日志量」的一个具体例子。

BM25 的原理性边界（retrieve.py:193-209 注释）：BM25 是单语词频模型。中文 token 在英文语料里 df=0，分数全为 0，于是被过滤掉。换成 jieba 也救不了——「仿真环境」再怎么正确分词，英文语料里也没有这个词。这是原理性的能力边界，不是分词质量问题。

实测严重性：13/13 纯中文查询的 BM25 返回空（坑 30）。也就是说，当你用中文提问时，「混合检索」实际上退化成「纯向量」，而且不报错。

RRF_K = 60（config.py:165），每路深度 20/20，融合后 FUSED_TOP_K = 20（config.py:166）。

代码注释里原来写着一句话：「rank 从 0 开始会让排序错乱」。exp24_rrf_check.py（2026-09-27）验证的结果是：这句话是错的。

  • 1/(60+0) = 0.016667，1/(60+1) = 0.016393——0 起点下第 1 名的分数更高；
  • 两种起点都是单调递减函数，所以在 3 个真实查询上给出了完全相同的排序。

要求 rank 从 1 开始的真正理由只是「对齐公式定义与业界实现」，不是「否则会乱」。

真正会出问题的写法是：两路用了不同的起点（一路 0-based、一路 1-based），这会给其中一路带来系统性偏置：

而 时「第 1 名 vs 第 2 名」的分数差只有 0.000264 —— 偏置比一个名次格子的宽度还大。在近似并列时它会翻转名次，而且不报错。

教学价值是项目里的一句原话：「注释里的因果句也要有证据，不能继承一句就一直抄。」

2.4 SPARSE_MODE=overlap：让配置自己判断该不该生效 ​

SPARSE_OVERLAP_K = 20

1
2

模式语义什么时候用
always只要稀疏路有结果就融合（原行为）纯英文、失效场景互补的语料
overlap（默认，线上）两路 top-20 的交集 ≥ 2 才融合，否则丢掉稀疏路、退回纯 dense不确定两路是否互补时
never从不融合（等价纯向量）作为对照基线

实现（retrieve.py:294-316）：

python
if use_sparse and SPARSE_MODE != "never":
    sparse = sparse_search(query)
    if sparse and SPARSE_MODE == "overlap":
        top_d = {h.chunk.chunk_id for h in dense[:SPARSE_OVERLAP_K]}
        top_s = {h.chunk.chunk_id for h in sparse[:SPARSE_OVERLAP_K]}

        if ov < SPARSE_OVERLAP_MIN:
            sparse = []            # 两路各说各话 ⇒ 不参与融合
if sparse:
    fused = rrf_fuse([dense, sparse])
else:

设计思想一句话：「两路 top-20 交集低于 2」是「这两路在这个查询上互不认可」的可观测信号。与其让人去猜什么时候该关掉稀疏路，不如把这个判断写成配置项，让系统自己判断该不该生效。

触发这段设计的实测数字（config.py:173-176 注释 + exp34_fusion_diagnosis.py）：

语料① 纯向量 R@5② 混合（无精排）R@5③ 混合 + 精排 R@5
5 篇（523 块，全英文）62.3%64.5%（融合有帮助 ✅）74.6%
56 篇（5470 块，含 2 篇中文）49.3%29.2%（比纯向量还差 ❌）59.7%

根因：中文查询的 BM25 top-20 全部来自那 2 篇中文文献。注意——不是因为主题相关，而是因为语言相同。在失败查询上，两路 top-20 的交集是 0，于是 RRF 融合把 dense 的好结果挤掉了。

一句话总结：同语言 ≠ 同主题。

修法就是 SPARSE_MODE=overlap，指标回到 47.9%（旧题集口径，_abl_overlap.md §二）。

「教科书说混合检索一定优于纯向量，我的实测否定了这一点……『混合检索有效』是一个有前提的结论，前提是两种检索器的失效场景互补。」

——output/05-面试准备-RAG数据.md:44-48

2.5 术语表扩展：只作用于稀疏路的一个领域补丁 ​

glossary.py 的 TERM_MAP（glossary.py:25-79）是 57 条中文→英文映射，分四组（指标/算法、方法与模块、动作空间/约束、环境 + 其它常问）。接口 expand(query) -> (expanded_query, hits)（:94-106），命中的术语一并返回供可观测；开关 RAG_QUERY_GLOSSARY 默认开（:91）。

实测增益（全量消融，23 题人工核对版 gt）：② 组 R@5 62.3% → 64.5%、R@10 66.7% → 73.2%；③ 组 R@5 73.2% → 74.6%、R@10 73.2% → 79.0%、MRR 0.696 → 0.702。不增加延迟——它只作用于 BM25 路，不增加精排候选数。

代价要诚实写：这是领域补丁，换语料就失效；术语表要人工维护（用人力换召回）；映射错了会引入噪声。通用做法是「翻译后再检索」或「训一个跨语言稀疏模型」。

exp35_crosslingual.py 的五路对照给出了最干净的答案（R@5）：

路径R@5说明
原始 BM258.3%中文 token 在英文语料 df=0；仅有的命中来自那 2 篇中文文献（语言噪声）
+ 领域术语表（当前线上策略）29.2%部分缓解
+ LLM 查询翻译（先翻成英文检索式）70.8%跨语种需要语义桥

结论一句话：不要用 BM25 做跨语种召回。

2.6 retrieve() 的参数与一个死参数 ​

参数语义注意

verbose=True 是最值得在面试里展示的一个开关——它打印的不只是「检索到了什么」，还有「排序改变了什么」。

2.7 Recall@10 == Recall@5：一个被 bug 藏起来的真实事实 ​

评测报告里曾经出现「Recall@10 恒等于 Recall@5」。第一反应是「说明我的排序完美——top10 里该有的 top5 里都有了」。这个解释是错的，真相分两层：

  1. 坑 24（死参数）：top_k 这个参数从未被使用——它只在函数签名里出现过 1 次。所以 retrieved[:10] 和 retrieved[:5] 取到的是同一个列表。
  2. 坑 34（标注窗口）：把参数修好之后，两列数字仍然相等。根因在评测集的构造：exp15_gt_evidence.py 的候选块只取 retrieve()[:5]（--topn 5 是默认值），也就是说标注时人只看了前 5 个候选。凡是「答案落在第 6—20 位」的题，gt 根本不可能被标出来。

修好之后，报告里立刻出现了一个之前被这个 bug 抹掉的事实：

不做精排时，R@10 比 R@5 高 11—14 个百分点。

这句话的工程含义是：「答案其实已经被召回了，只是没排进前 5」。它同时解释了两件事——为什么精排能带来明显收益（③ 组 R@5 71.8% vs ② 组 59.1%），以及为什么「扩大召回深度」本身不解决问题（召回里已经有了，问题在排序）。

这条结论在修复前是不可见的：一个 bug 把一个真实事实从报告里删掉了，而报告看起来一切正常。

六、面试深挖：追问链 ​

第一条：混合检索为什么反而更差？

  • Q：混合检索一般都比纯向量好吧？
  • A：不一定，我在自己的语料上实测出了反例。5 篇全英文语料时，纯向量 R@5 62.3%、混合 64.5%，融合确实有帮助；扩到 56 篇（含 2 篇中文文献）后，纯向量 49.3%、混合掉到 29.2%，比不用融合还差。同一个系统、同一套代码、同一个融合公式。
  • 追问：那根因是什么？
  • A：中文查询的 BM25 top-20 全部来自那 2 篇中文文献——不是因为主题相关，而是因为语言相同。中英混排语料下，中文 token 在英文文档里 df=0，于是「中文文档」这个特征反而成了唯一能得分的特征。在失效的查询上，两路 top-20 交集是 0，RRF 把稀疏路那些无关但被排在前面的结果加权进融合，把 dense 真正相关的结果挤了下去。
  • 追问：那你为什么不干脆关掉稀疏路？
  • A：因为它在别的查询上确实有用——纯英文查询时混合是有效的。所以我没做成一个全局开关，而是加了 SPARSE_MODE=overlap：两路 top-20 交集 ≥ 2 才融合，否则丢掉稀疏路退回纯 dense。逻辑是「如果两个检索器在这个查询上互不认可，那这次融合就没有依据」。这句判断被写成了配置项，让系统自己决定该不该生效。修复后指标回到 47.9%。

第二条：Recall@10 等于 Recall@5 说明什么？

  • Q：我看到你的报告里 R@10 和 R@5 一样。是不是说明你的排序特别好？
  • A：恰恰相反，这是一个 bug 把真实事实藏起来了。第一层原因是 top_k 参数从未被使用，所以取 [:10] 和 [:5] 是同一个列表；修好参数之后，两列数字仍然相等。
  • 追问：为什么修好了还相等？
  • A：因为根因在标注窗口。生成 gt 候选的脚本默认只取 retrieve()[:5]，也就是说标注的人只看了前 5 个候选。凡是答案落在第 6—20 位的题，gt 根本不可能被标出来——R@10 在数学上就不可能高于 R@5。这不是排序好，这是评测集被标注流程构造出来的。
  • 追问：修好之后你看到了什么？
  • A：看到了一个之前看不见的事实：不做精排时，R@10 比 R@5 高 11—14 个百分点。它的含义是「答案其实已经召回了，只是没排进前 5」。这一句话同时解释了另外两件事——为什么精排能带来明显收益，以及为什么单纯加大召回深度不解决问题，因为问题不在召回、在排序。这是我这个项目里最有价值的一次发现：一个 bug 会把真实结论从报告里删掉，而报告看起来一切正常。

第三条：RRF 的 k 和 rank 起点。

  • Q：RRF 的公式是什么？k 取多少？
  • A：，我取 k = 60，rank 从 1 开始，每路深度各 20，融合后取 20。
  • 追问：为什么 rank 要从 1 开始？从 0 开始会怎样？
  • A：代码注释原本写着「rank 从 0 开始会让排序错乱」。这句话是错的，我验证过：1/(60+0) = 0.016667 比 1/(60+1) = 0.016393 更大，0 起点下第 1 名分数更高；两种起点都是单调递减，在 3 个真实查询上给出了完全相同的排序。要求从 1 开始只是为了对齐公式定义与业界实现。
  • 追问：那真正的风险在哪？
  • A：在两路用不同起点。一路 0-based、一路 1-based 时，会给其中一路带来约 0.000273 的系统性偏置（r=1、k=60 处），而 k=60 时「第 1 名 vs 第 2 名」的分数差只有 0.000264——偏置比一个名次格子的宽度还大。近似并列时会翻转名次，而且不报错。这件事教给我一条更一般的纪律：注释里的因果句也要有证据，不能继承一句就一直抄。
