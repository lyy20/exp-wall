⑭ 与 YYHelp 的对照 ​

一句话：前作解决「检索准不准」，YYHelp 解决「多轮对话能不能可靠地把事办完」。

这一页要回答什么 ​

面试官最常问的一句是「你这两个项目有什么区别？」——他要的不是功能清单，而是你知不知道自己为什么写了两遍不同的东西。

这一页要回答三个真实问法：

面试官会这样问他在验证什么
「你两个项目有什么区别？」你是否有「问题类型决定架构」的判断力，而不是「学一个框架就用一个框架」
「那你第二个项目是不是就是加了个 LangGraph？」你能否说清哪些是真正变的、哪些只是换了个壳
「两个项目里你觉得哪个更难？为什么？」你有没有把难度当作可分解的东西（状态？副作用？并发？），而不是感觉

读完这一页你能答出：一句话定位差 + 13 个维度逐条对照 + 哪些代码是被复用而非重写的——最后一条最重要，因为它决定了你是在「堆项目」还是在「造资产」。

一、一句话说清差异 ​

两个项目都做 RAG，但它们优化的目标函数不同：

  • 前作（科研文献 RAG 问答）：一次问答的质量。切块怎么切、混合检索怎么融合、精排要不要上、拒答阈值定在哪。所有工作围绕一个可测的数字——Recall@k。
  • YYHelp（电商客服多轮 Agent）：一段对话能不能可靠地把事办完。谁处理这轮、给专家看几个工具、什么时候该停、多智能体到底值不值。所有工作围绕一个更难测的数字——任务完成率，以及一个更硬的指标——墙钟。

一句话对照：

前作（RAG 问答）YYHelp（客服 Agent）
核心问题找不找得到找到了之后谁来用、用几个工具、什么时候停
控制流直线：问题 → 检索 → 生成 → 校验状态图：分叉 / 汇合 / 循环
单次交互一问一答，无状态多轮，有状态，可中断可恢复
世界影响只读有写操作（查订单、建工单），需要幂等键与人工确认
失败方式答错 / 拒答答错 / 超预算 / 把用户的订单改坏

这就是为什么第二个项目不是「加了个框架」。 只读 + 无状态 + 单轮，和可写 + 有状态 + 多轮，是两个不同的问题类别——后者的每一处复杂度都来自「状态」与「副作用」，而不是来自「模型更强了」。

二、13 个维度逐条对照 ​

维度前作（RAG 问答）YYHelp为什么变
控制流直线「问题 → 检索 → RRF → 精排 → 生成 → 引用校验 + 拒答」LangGraph 状态图：分叉 / 汇合 / 循环，plan 与 reflect 可跳过、可触发多轮任务的路径不唯一，直线流程无法表达「这轮不需要检索」
状态无状态，每次请求独立会话持久化 + 中断恢复；CSStateV2 = v1 全字段 + 14 个新字段用户说「那刚才那个订单呢」，前作里这句话没有指代对象
副作用只读检索 + 生成查订单 / 建工单等写操作，配幂等键与人工确认写错了不能靠「再问一次」挽回
向量库FAISS IndexFlatIP（进程内、单文件）Milvus 单库承载 dense + sparse 两路前作规模（55 篇 / 5325 块）用 FAISS 足够；YYHelp 需要独立 collection 管理与索引重建
稀疏检索rank-bm25 自建，中文需先分词，靠自检机制兜底Milvus 内置 BM25 + sparse 向量（中文用 jieba）前作踩过中文 BM25 静默失效（见 ⑬ 工程踩坑实录 坑 47），结论带到 YYHelp
编排框架手写顺序调用LangGraph 主图 + 条件边 + state reducer需要可中断、可恢复、可枚举终止条件
会话记忆无双层：近 N 轮保原文 + 更早压成摘要；长期记忆跨会话（SQLite 真相源 + 可选 Milvus，独立 collection yyhelp_memory_v1）上下文窗口装不下整段对话，也不能每次都全塞
可观测自研 JSONL 追踪自研 JSONL + Langfuse v4 双后端显式降级（一个后端挂了会明确降级并留痕）多轮 + 多专家的调用链必须能回放，否则「哪一步错了」无法定位
数据闭环无飞轮：三入口入池 + 检索快照 + 离线重放前作只在开发期用评测集改进检索；YYHelp 要让线上失败自动变成新评测题
评测检索指标（Recall@k、拒答准确率）+ 消融对照表在上面的基础上加回归门禁：可进 CI、三态退出码前作的指标是给人看的，YYHelp 的指标要能卡住合并
失败处理一档拒绝：拒答三档兜底 + 三入口入池客服场景不能拒答完就算完，得有事可做
持久化单文件索引清单（SQLite）MySQL + SQLite 降级，配双 DDL 列集合对齐断言有两个存储后端时，「两张表结构不一致」会变成静默 bug，所以用断言钉死
外部协议无（HTTP 接口）MCP：mcp/server.py 222 行，register_tools:124 / make_fresh_server:184，只依赖 mcp + anyio，不依赖 langgraph工具被别的 client 复用，协议层不能拖上编排依赖

四、一次业务请求在两个项目里分别是什么样 ​

前作（无状态，一句话走完全程）：

用户问「这篇论文报告的 Recall@5 是多少」→ 查询重写 → dense 与 BM25 两路各取 top-k → RRF 融合 → 精排 → 取前若干块拼上下文 → LLM 生成 → 校验引用编号是否合法 → 若不可回答则拒答。整个过程中没有任何东西被记住，第二次问必须把上下文再说一遍。

YYHelp（有状态，同一件事要跨轮）：

用户说「我要退款」→ plan 判断是否需要规划（complexity="simple" 时跳过）→ supervisor 决定这轮交给 refund_flow（若涉及订单信息则先 order_ops）→ 专家只看见自己那 1–3 个工具 → 写操作前人工确认 + 幂等键 → 输出写进 expert_outputs[专家名] → 若结果不足且命中四条显式触发之一，进入 reflect（只允许重试 1 次，防止反思变成绕过预算的通道）→ 未终止则回到 supervisor（实测 40 题里 37 题 1 轮、3 题 2 轮，均值 1.075 轮；上限 DISPATCH_LIMIT = 2，到上限强制 finalize(source="quota")）→ 持久化 state。

同一句「好的」在前作里没有意义，在 YYHelp 里是一个必须被正确解析的指代。

五、做过的取舍：哪些是复用，哪些是重写 ​

这一节是防「注水」的：如果两个项目的技术栈全都一样，说明第二个项目没有增量；如果全都不同，说明你不知道哪些东西本来就不该变。

明确复用的部分（变了会被质疑乱动）：

复用的东西为什么不该变
Embedding 仍是 bge-m3中文检索的性价比选择没有被新事实推翻，换模型只会引入新变量
精排仍是 bge-reranker-v2-m3同上；前作消融已证明精排有正收益（混合 + 精排 R@5 71.8% vs 混合无精排 59.1%，124 题口径）
RRF 融合思路多路召回的融合方式与「找不找得到」无关
LLM 调用仍是 OpenAI 兼容协议换的是模型与网关，不是客户端协议
拒答阈值思路前作的 top1 中位数分离（可回答 0.9617 vs 不可回答 0.0127）支持了「存在一个可用阈值」

明确重写的部分（变了才有讨论价值）：控制流（直线 → 状态图）、状态（无 → CSStateV2 的 14 个新字段）、副作用处理（只读 → 写操作 + 幂等键）、评测的用途（给人看 → 卡合并）。

唯一一条重叠的坑：中文 BM25 静默失效。两个项目都踩到了同一条原理（中文分词缺失时，稀疏路会以一个「看起来在工作」的姿态给出接近随机的结果），但这条坑记在前作侧，YYHelp 直接继承了结论（用 Milvus 内置 BM25 + jieba），不再重踩。

另一个值得一提的「复用决策」是不复用：YYHelp 没有引入 langgraph_supervisor 这个现成轮子——不是因为它不好，而是因为（1）当时环境里它没装；（2）它会把已经验收过的可靠性资产换掉。判断轮子该不该用的标准是「它会不会替换掉我已验证的东西」，而不是「它是不是官方的」。

六、面试深挖：追问链 ​

Q1｜「那你第二个项目是不是就是加了个 LangGraph？」 ​

是，也不是。 换框架只占很小一部分——v1 → v2 一共 30 项变更，其中只有架构层前 4 项是 A/B 的被测变量，其余 26 项都是背景改造（state 层 4、测试与工程纪律层 6、工具与协议层 4、检索与知识库层 2、服务与可观测层 4）。

那被测变量是哪 4 个？ ① multi 臂含 plan / supervisor / memory / reflect 四个节点，single 臂没有；② 决策者：supervisor（LLM + 规则约束）vs v1 nlu 的 9→5 映射；③ 工具菜单：tools_for(spec.name) 每专家 1–3 个 vs V1_TOOL_NAMES 全量 5 个；④ system prompt：专家自己的 vs v1 通用人设。

那结论是什么？ 40 题 × 2 臂配对实测（2026-10-02）：完成率 multi 40/40 vs single 39/40（t 检验 p=0.323，不显著）；每问 tokens 5,783.7 vs 6,243.3（p=0.409，不显著，multi 反而省约 7%）；每问墙钟 20.9 s vs 9.9 s = 2.11×（p=1.9e-6，Holm 校正后拒绝原假设，判为 REGRESSION）。所以我的决定是「在 Gate-1 样本上不切换到 multi」，而不是「multi 更好」。

Q2｜「两个项目的指标，你更信哪一个？」 ​

更信前作的检索指标，因为它有明确的口径边界；YYHelp 的完成率指标我不敢当真——40 题里两臂同对同错 39 对，有效样本量 n_eff = 1。

那你还报这个结论？ 报，但报的是限制而不是收益：这是一个否定性结论——「在 Gate-1 样本上不切换」。功效分析算出要检出 +5pp 需要 76 题、+10pp 需要 17 题，而 40 题根本不够。

什么情况下你会改这个决定？ 三条同时满足才重跑：① 评测集跨域 / 多步题占比 ≥ 30%，且完成率天花板不饱和（现在裁判 79/80 判 1，已经饱和）；② 检索层缺陷（B25 类：正确答案在库里但两臂都检索失败）已修复；③ 有真实墙钟容忍度或并行版落地。注意第一条——如果连题都做对了，再扩样本也测不出差异。

Q3｜「你前作有个 R@10 == R@5，YYHelp 里有没有同类问题？」 ​

有同类方法问题，但结论不同。前作那条被查出是构造结果（标注窗口只取 retrieve()[:5]），修完后 ①② 组出现 11–14 个百分点的增量，③ 组仍然相等（71.0% = 71.0%）。YYHelp 的完成率也有构造问题——天花板效应：裁判在 79/80 上判 1。

你怎么发现的？ 因为它不可能：两臂几乎完全同分，先怀疑测量而不是庆祝。去看裁判的判定分布，发现几乎所有题都判「完成」。

同样的教训在两个项目里怎么表述？ 「指标长期不变，先怀疑它的分辨率。」 前作是分辨率被封顶（标注窗口），YYHelp 是上限被封顶（天花板）。两次都不是模型的问题。

Q4｜「你说 YYHelp 更难，难在哪？给个可检验的说法。」 ​

难在状态和副作用，不在模型。可检验的说法：前作一次请求的全部状态活在函数调用栈里，进程重启后不留任何东西；YYHelp 的 CSStateV2 有 14 个新字段需要被 reducer 正确合并，且写操作必须幂等——同一句「帮我退款」被重复投递两次，结果必须一样。

那你为「难」付出了什么代价？ 墙钟。串行 + DISPATCH_LIMIT = 2 让每问墙钟从 9.9 s 涨到 20.9 s。串行的代价不在 token 而在墙钟——tokens 反而略降，但用户等的时间翻倍。

为什么不并行？ 有三条判据支持串行：写操作有顺序依赖（「先改址再退款」与「先退款再改址」结果不同）；专家输出是彼此的输入（R24 实测）；串行是次数问题（上限能直接封顶），并行是扇出问题。我也考虑过一对恰好无依赖的只读工具 search_kb + query_logistics，但有收益不等于该做——没有证据表明并行版能压住墙钟之前，不做。
