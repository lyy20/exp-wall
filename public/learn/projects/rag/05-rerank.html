重排与上下文组装 ​

一句话：精排是整个系统里最贵的一步，而首字延迟几乎等于检索耗时——所以优化方向不该是 LLM。

这一页要回答什么 ​

  • 「你为什么加 Rerank？值吗？」——要求给出加与不加的指标差，以及那一步的延迟代价。
  • 「你的端到端延迟是多少？瓶颈在哪？」——要求说出「检索 P50 14.47 s vs LLM 生成 P50 1.26 s」这组数字，而不是「大概十几秒」。
  • 「上下文你是怎么拼的？」——要求说清「为什么来源要用论文标题」「为什么标题只声明一次」。

读完这一页你应该能：说清 top_k 与 top_n 的关系；说清那 8.5 秒花在哪、为什么不能靠换模型解决；说清为什么「优化 LLM」在这个系统里是错的方向。

一、它要解决什么问题 ​

检索层交出 20 条候选之后，还有两个必须做的动作：

  1. 重排。20 条候选是用两个「粗粒度」检索器选的（一个比语义、一个比字面），它们的排序不适合直接送进 prompt。Cross-Encoder 把「问题 + 每一块正文」拼在一起过一遍模型，给出一个语料内的相关性分数——这一步比向量检索准得多，也贵得多。
  2. 组装。模型看到的不该是 20 段裸文本，而是一段带出处编号、带页码章节、能支撑引用校验的结构化上下文。

这两步的取舍完全不同：重排是拿延迟换准确率，组装是拿注意力预算换可核对性。

二、方案与实现 ​

那 8.5 秒有个很有说服力的来历：30 道题评测时多花了 4 分钟，折算下来每道题约 8 秒——而且更关键的是，answer_question() 早期会对同一批 hits 重复精排。这直接催生了一个接口设计：answer_question(..., hits=...) 允许把已经精排好的结果传进来，避免重复计算。

为什么这 8.5 秒值得付：加精排前后，③ 组 R@5 71.8% vs ② 组 59.1%，差 12.7 个百分点；MRR 从 0.502 提到 0.714（按两者之比计算约 +42%，这个百分比是我从两个原始数字算出来的，不是报告里直接写的）。而 LLM 生成只要 1.26 秒（P50）。用 8.5 秒换 12.7 个点的召回，在离线评测口径下是划算的——但在交互口径下不划算，这正是 2.4 节要讨论的冲突。

为什么要区分「融合后 20」和「最终 5」：20 是给精排看的（候选越多，精排越能发挥作用），5 是给模型看的（上下文预算有限）。这两个数字调的是完全不同的东西——一个影响召回，一个影响注意力。

评测和线上用的是不同的深度：

  • 评测时 final_k = max(k, 10)（eval_regression.py:60-79）——因为要算 R@10；
  • /ask 的 top_k 默认 10，范围 ge=1, le=20（service.py:229-234）；
  • /retrieve 默认 10，范围 ge=1, le=50（service.py:320-324）。

⚠️ final_k 必须可配置，这不是洁癖：原来它是写死返回 5 个，于是 retrieved[:10] == retrieved[:5]，Recall@10 恒等于 Recall@5——两个评测列被一个固定值变成了同一列。详见 ⑤ 检索层。

2.3 精排分数的两个语义陷阱 ​

陷阱一：分数性质必须先判定，再定阈值。 exp06_rerank_scores.py 给出的判据是：

  • 出现明显负数或 > 1 ⇒ 输出是 logits，阈值必须重新改造（脚本里给了 1/(1+exp(-raw)) 的 sigmoid 换算，exp06:79）；
  • 全部落在 [0, 1] 且分布分散 ⇒ 已经是概率，阈值 0.30 的语义正确。

本项目的实测结果是后者，所以 0.30 这个阈值可以直接用。如果跳过这一步，你会在 logits 上套一个概率阈值，得到一堆「全部拒答」或「全部通过」。 阈值扫描区间是 [0.05, 0.6]。

陷阱二：只有 Cross-Encoder 的分数能做拒答阈值。 use_rerank=False 时 retrieve() 返回的是 RRF 融合分数（实测区间约 0.016—0.033），量纲完全不同。拿它去比 0.30，会让每一道题都被拒答（retrieve.py:274-276）。

评测脚本用一行条件挡住了这个错误：refused = (use_rerank and t1 < threshold)。所以报告里 ①② 组的拒答三列是 「不适用」（渲染为 —），不是「测出来是 0」。这个区别非常重要——「不适用」和「0」在读者眼里是完全不同的两件事。

实测的分数分布（③ 组，top1）：

类别nmin中位数max
可回答1240.04110.96170.9999
不可回答60.00180.01270.2502

2.4 延迟账：瓶颈在哪，不在哪 ​

output/latency_report.md（30 题样本）与 output/05-面试准备-RAG数据.md:77-83：

阶段P50P90P99
检索（dense + BM25 + RRF + 精排）14.47 s18.44 s30.74 s
LLM 生成1.26 s1.87 s2.82 s
端到端（用户等待）15.66 s19.58 s32.26 s
冷启动67.3 s——

把这几个数字放在一起，能得出三个结论：

  1. 检索占端到端的约 92%（14.47 / 15.66，比例由我按 P50 相除算出），LLM 只占约 8%。如果只盯着 LLM 做优化——换更快的模型、压缩 prompt、上投机采样——最多也只能改善 8%。
  2. 流式首字延迟 ≈ 检索耗时：实测 TTFT 是 14.90 / 10.00 / 14.86 秒。也就是说，用户打开流式界面之后，那十几秒里屏幕上什么都没有——因为此时还没有调用 LLM，还在精排。
  3. 冷启动 67.3 秒不能混进 P50。报告里明确标注了这一点。

所以「优化 LLM」是错误的方向。 正确的方向按收益排序是：① 让精排快起来（GPU、ONNX/量化、批处理、或用更小的 reranker）② 让用户更早看到东西（例如先返回检索到的来源列表再流式出答案）③ 在这里谈 LLM 优化。

但这两条优化本项目都没有做——事实清单里没有对应的实测数字。诚实的说法是「我知道瓶颈在哪、也知道该往哪修，但没修」。

2.5 上下文组装：两个由实测踩出来的设计点 ​

build_context()（generate.py:84-119）的设计点都来自两个字：误拒。

设计点一：来源必须用论文标题，不能用文件名。 早期上下文头部写的是「来源：SCIS 第 15 页」。SCIS 是 PDF 文件名的词干，模型无从知道这就是 CTRIP-SAC 那篇论文。在「不得猜测、只能依据资料」的约束下，模型的合理反应就是——拒答。这不是模型能力问题，是上下文写法问题。

设计点二：标题只声明一次，不要每块重复。 论文标题约 140 字符，5 块就是 700 字符，占上下文约 17%；而且同一串长文本重复 5 遍会稀释注意力。所以改成在开头做一次文献图例：

  • 单文档：「本次资料全部来自同一篇文献：{doc_title}」
  • 多文档：「本次资料来自以下文献：[A] {title1} [B] {title2}」

然后每块的头部是 [{rank}] {tag}第 {page} 页（若有 section 再追加 ｜{section}），单文档时 tag 为空。最终用 "\n\n".join(blocks) 拼接。

最终形态是这样（generate.py 里的真实格式）：

2.7 预热：做了，但没生效 ​

这条本该属于服务化那一页（⑫ 服务化与性能），但它本质上是一个延迟问题，放在这里更连贯。

预热本身是对的：RAG_WARMUP=1（默认开）时，@app.on_event("startup") 里的 _warmup()（service.py:82-119）在后台线程中依次触碰 _S.embedder（bge-m3）、_S.reranker、_S.chunk_list、_S.faiss_index、_S.bm25。

为什么必须是后台线程：如果同步预热，uvicorn 要等 30+ 秒才监听端口，编排系统会认为启动失败直接重启。

但它没生效（service.py:73-78 记录的实测教训）：预热线程确实在跑，可是 /health 立刻返回 200。于是编排系统（或压测器）在模型加载完之前就把流量导了进来——第一个请求照样等 48 秒。

根因是：/health 只回答「进程活着」，没有回答「能不能接流量」。修法是把两者分开：

  • liveness：进程是否活着（/health 的 200）；
  • readiness：是否可以接流量——ready = warm_state in ("done", "skipped") and not budget_out，通过 detail["ready"]["warmup_state"]（pending / done / skipped）与 warmup_ms 暴露。

一句话教训：编排系统会严格按 200 立刻导流量，所以 readiness 必须显式门控就绪状态，不能靠「进程起来了」代替「能干活了」。

六、面试深挖：追问链 ​

第一条：精排值不值？

  • Q：你为什么要加 Rerank？有没有数字支撑？
  • A：有。加精排前后，③ 组 R@5 71.8%，② 组（混合但无精排）59.1%，差 12.7 个百分点；MRR 从 0.502 提到 0.714。代价是单次精排约 8.5 秒（20 对，CPU）。
  • 追问：8.5 秒换 12 个点，你觉得这笔账划算吗？
  • A：要看口径，而且必须分开说。离线评测口径下划算——准确率是首要目标。在线交互口径下不划算——端到端 P50 是 15.66 秒，其中 14.47 秒在检索侧，LLM 只占 1.26 秒；用户要等十几秒才看到第一个字（流式 TTFT 实测 14.90 / 10.00 / 14.86 秒）。所以我的结论不是「精排不该加」，而是「精排的工程实现必须优化」：GPU、批处理、ONNX/量化，或者换更小的 reranker。
  • 追问：那你优化了吗？
  • A：没有。这是我这个项目里最明确的一个「知道该做但没做」的项。原因是实测环境里 torch 装的是 CPU 轮子、cuda_available=False，我没把 GPU 用起来；换 reranker 又会影响全部历史指标。所以现在的状态是：瓶颈已定位、优化路径已列清、但没有实测数字支撑。面试里我不会把它说成已完成。

第二条：端到端延迟与瓶颈。

  • Q：你的系统端到端延迟多少？瓶颈在哪？
  • A：端到端 P50 15.66 秒、P90 19.58、P99 32.26。拆开看：检索（含精排）P50 14.47 秒，LLM 生成 1.26 秒。也就是说 92% 的时间在检索侧，LLM 只占 8%。冷启动 67.3 秒，我在报告里明确把它排除在 P50 之外。
  • 追问：那你为什么不去优化检索？
  • A：因为「检索」里 8.5 秒是精排、其余是向量与 BM25 的毫秒级操作——优化对象很明确，就是精排那一颗。而更根本的一点是：即使把精排优化到零，用户仍然要等 LLM 生成完才能看到内容——所以真正的解法是流式把检索阶段的中间结果先吐给用户（先给来源列表，再给答案）。这个方案我没有做，因为流式接口当时只解决了「答案逐 token 输出」这一段。
  • 追问：那压测数据支持你这个判断吗？
  • A：支持。并发 1/2/4/8 时 RPS 是 0.15 / 0.20 / 0.25 / 0.40，P50 是 7.5 / 13.7 / 25.7 / 45.8 秒——延迟随并发线性上升、吞吐饱和。这是典型的 CPU 排队特征，说明瓶颈是算力而不是代码。⚠️ 但我要说清口径：每档只有 3—8 个请求，所以分位数不能写进 SLA；能站得住的只有「延迟线性增长、吞吐饱和」这个结构性结论。

第三条：上下文怎么拼，token 预算怎么控？

  • Q：你怎么拼上下文？
  • A：先给一个文献图例（单文档就说「本次资料全部来自同一篇文献：标题」，多文档用 [A] [B] 标注），然后每块带一个头部 [序号] 文献 [A]｜第 x 页｜章节，最后 "\n\n" 拼接。两个细节都是被误拒事件逼出来的：来源必须用论文标题而不是文件名，标题只声明一次不重复。
  • 追问：为什么标题不能每块重复？重复几遍不是更清楚吗？
  • A：反而更糟。论文标题约 140 字符，5 块就是 700 字符，占上下文约 17%；而且同一串长文本重复 5 遍会稀释注意力。改成声明一次之后，既省了这部分预算，也让每块的头部只剩下真正有区分度的信息——编号、页码、章节。
  • 追问：那你怎么保证上下文不超 token 上限？
  • A：靠间接控制，不是靠 token 预算计算，这一点我说清楚：精排后只取 5 块、每块 ≤ 1024 字符、标题去重，这三条给了上界；然后用 exp18b_token_budget.py 测真实切片的 token 数分布，用 exp18a_context_inspect.py 把「模型实际看到的上下文」原样打出来核对。没有找到按 token 动态裁块的实现——所以如果语料块变长或换成 token 密度更高的语言，这个缺口会暴露出来。实测单次用量是 1290 prompt + 36 completion token，当前离上限还有余量，但这不构成「已经做了预算管理」的结论。
