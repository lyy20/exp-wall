面试深挖与口径 ​

一句话：三档陈述背熟、五个方向答透、黑名单上的数字一个都不报。

这一页要回答什么 ​

面试里这个项目会以三种形式出现，每种形式的时间预算完全不同：

面试官会这样问你的时间预算这一页给你什么
「简单介绍一下你这个项目？」30 秒（他在判断要不要往下问）一段可以背的定位句 + 三个数字
「详细讲讲你做了什么？」2 分钟（他在找可以深挖的钩子）按「数据 → 检索 → 生成 → 评测」讲四层
「这个项目你展开说说，我随时打断。」5 分钟（他在找你的判断力）一条含三次「我改了主意」的主线
「这个数怎么来的？」任何时长报数模板：数字 + 口径 + 比较对象 + 是否含精排
「这个你做过吗？」（你的答案是「没有」）任何时长四步答法：承认 → 指方向 → 说理由 → 给方案

目标是：任何一档陈述都不超时，且每个数字都带得住口径。

一、三档陈述 ​

1.1 30 秒版（背下来，一字不改） ​

我做了一个面向 AI 领域科研文献的 RAG 问答系统，目标是答案可溯源、不可回答时敢拒答。语料是 55 篇论文、5325 个切片，检索走 dense + BM25 双路召回、RRF 融合、再加 bge-reranker-v2-m3 精排。评测集 130 题（124 可回答 + 6 不可回答），目前可引用的一组数字是：纯向量 R@5 64.4%、混合无精排 59.1%、混合加精排 71.8%，都是 124 题口径；拒答准确率 100.0%，误拒率 7.3%。我知道还有一个数字看起来更漂亮——R@10 等于 R@5——但那条查出来是标注窗口造成的构造结果，我不敢当卖点。

这一段的切法：规模 + 三档对照 + 拒答 + 一句自我否定。自我否定不是谦虚，它是最强信号——它证明你知道自己的数字是怎么来的。

1.2 2 分钟版（四层，每层 30 秒） ​

第一层：数据（30 秒）。原始导入 59 篇 PDF，清洗后 55 篇有效、5325 块，平均切片 763 字符。清洗里踩过两个坑——一是表格里的整数单元格被当成页码删掉，导致表格类问题永久答不对，因为数据在入库阶段就已经不完整；二是同一篇论文被导入两次，按文件名和按字节判重都拦不住（两次下载文件名不同、PDF 元数据不同），最后改成按正文语义判重。数据侧的结论：清洗的误删不可逆。

第二层：检索（40 秒）。双路 top-20 → RRF（RRF_K = 60）→ 精排 top-5。这层最关键的一步是稀疏路的自检机制：取两路 top-20 的 chunk_id 求交集，交集小于 2 就判定「两路各说各话」，把稀疏路置空、退回纯 dense。触发它的是扩库后的实测——混合检索 R@5 从 64.5% 崩到 30.6%，根因是中文查询的 BM25 top-20 全部来自那两篇中文文献：中文分词缺失时，BM25 以为自己在按「主题」匹配，实际在按「语言」匹配。同语言不等于同主题。

第三层：生成与拒答（25 秒）。拒答分两层：阈值层（top1 < 0.30）和 prompt 层。分开测是为了误拒率归因：仅阈值层 1.6%，加上 prompt 层 6.5%——多出来的部分是 prompt 造成的，不是阈值。引用校验只验编号合法性，验不了「引用的内容是否真支持这个结论」，那需要 NLI 或人工复核，我没做。

第四层：评测（25 秒）。这层我投入最多，因为我先做错了一次：早期 R@5 与 R@10 完全相等，我一度以为「排序饱和了」，后来查出机器 gt 的候选只取 retrieve()[:5]，标注窗口把 R@10 的分辨率封顶了。换成独立盲标的 gt 后，①② 组才出现 11–14 个百分点的 R@10 − R@5 增量。教训：指标长期不变，先怀疑测量方法，别庆祝。 时延也一样——端到端 P50 15.66 秒，分解后检索占 14.47 秒、LLM 只占 1.26 秒，瓶颈是 CPU 精排 20 对约 8.5 秒，不是模型慢。

1.3 5 分钟版（主线：三次「我改了主意」） ​

五分钟不要平铺细节，用三次改主意串起来——面试官记不住参数，但记得住「你什么时候发现自己是错的」。

第一次改主意：我以为检索是瓶颈，数据才是。 表格类问题一直答不对，我第一反应是调 prompt。改了两轮没用，回去把出问题的原文块打印出来，和 PDF 原始表格逐格对照——数字在入库阶段就被清洗规则删掉了。从此我的排查顺序是「先看数据管道，再看模型」。

第二次改主意：我把一个漂亮的指标判为造假。R@5 与 R@10 完全相等，看起来是「排序已经饱和」的好消息。我先问了一句「这个指标是在什么窗口上构造出来的」，然后去读标注脚本而不是看模型输出——标注工具只取 retrieve()[:5]，人只看了前 5 个候选，所以 gt 不可能落在第 6 名以后。量化证据：top-10 窗口审计 23 题，gt 名次在 1–5 位 21 道、6–10 位 0 道、>10 位 2 道。「6–10 位一道都没有」就是构造结果的特征。修正后暴露了真实增量：不做精排时 R@10 比 R@5 高 11–14 个百分点。

第三次改主意：我差点按错误的检查工具去改坏正确的东西。 我写了一个 gt 审计工具，它报出 8 道题的 gt 是错的。我没有直接改——因为「8 道同时错」这个比例本身可疑，改成逐字读原文。结果是 8 道全是假警报：工具的全角数字没做 NFKC 归一、中点被误判、PDF 抽掉下标导致 N_ob 匹配不上 Nob。加了 _norm_for_clue()（NFKC + 中点→小数点 + 去下划线）后 8 道题命中率全回到 100%。结论：审核工具报警时，先验证审核工具——错误的检查工具比没有检查工具更危险，因为它会指使你去破坏正确的东西。

收尾一句：这个项目我最有把握的不是某个数字，而是这三次改主意的过程——它们说明我能在没有人告诉我「你错了」的时候自己发现。

三、五个最可能的追问方向与答法 ​

方向一｜「你的评测集可信吗？」（最可能，也最致命） ​

可信度分三层，我分开说。 题集 130 题（可回答 124 + 不可回答 6），gt 206 块、密度 1.66 块每题，覆盖 9 类主题，其中 6 类是旧题没碰过的。新 100 题是从语料块出题得到的（N001–N100）。已知问题三条：3 道题（S08 / S13 / M06）记在 known_issues.json 里未达标；多跳题严格准确率只有 27.8%，样本太小，只能当线索不能当结论；131 题的答案准确率我这个口径没有——报告里明确写「本报告未含，需人工判定」。

那你怎么保证 gt 是对的？ 三道工序：机器辅助找候选 → 我从语料出发用关键词 / 数值全库搜索（exp29_chunk_search.py，独立于检索结果）→ 人工确认。独立性是硬要求：机器 gt 那次就是用 retrieve() 的结果当标准答案再评 retrieve()，报告直接标「不可作为结论」，那一版数字我全部弃用。

如果我要抽查，你让我怎么查？ 抽查 gt 块里是否真的含答案，用「答案里的数字 + 拉丁词是否出现在 gt 块里」做粗筛——但注意这条粗筛会假阴性：PDF 抽取会吃掉下标，答案写 N_ob、原文是 Nob，我实测 S06 与 M06 都因此被误判成错，逐字读原文后证明 gt 是对的。所以机械工具只负责把原文摆出来，判对错必须回到原文。

方向二｜「混合检索怎么反而比纯向量差？」（考的是你懂不懂降级） ​

因为中文 BM25 在这个语料上是失效的，而不是弱。② 组（混合无精排）R@5 59.1%，比 ① 组纯向量 64.4% 低 5.3 个百分点——同一 124 题口径。根因是查询语言分布：中文查询的 BM25 top-20 全部来自那两篇中文文献，也就是「同语言 ≠ 同主题」。混合检索的常见直觉是「两路各有所长」，前提是两路都在按主题检索；当其中一路实际在按语言检索时，它的贡献是噪声。

那你怎么发现的？ 扩库后混合检索 R@5 从 64.5% 崩到 30.6%，我先用单字 / bigram 分词做了个中间态验证（29.2%），确认是分词而非权重问题，再去看 BM25 命中的块来自哪几篇文献——两篇，全是中文那两篇。

修法为什么选「自检后放弃」，而不是调 BM25 参数？ 因为参数调不出「按主题匹配」。SPARSE_MODE 三档实测：always R@5 30.6% / R@10 59.7% / MRR 0.621；overlap（交集 < 2 就丢稀疏路）47.9% / 61.8% / 0.636；never 49.3% / 57.6% / 0.595。注意 never 的 R@5 最高——单看 R@5 会得出「干脆别用 BM25」，但 never 的 R@10 反而最低，说明它只是把答案挤进了更靠前的位置而不是真的召回了更多东西。所以我选了 overlap：它不是在「用不用 BM25」之间选，而是让系统在每一题上自己判断这次该不该信它。

方向三｜「15 秒的延迟你怎么优化？」（考的是你先分解还是先动手） ​

我先分解再优化，顺序是刚性的。实测（30 题）：检索 P50 14.47 s、LLM 生成 P50 1.26 s、端到端 P50 15.66 s、冷启动 67.3 s。首字延迟 ≈ 检索耗时（14.90 / 10.00 / 14.86 s），也就是说用户等的不是模型在写字，而是在等模型开始写。再往下分解：瓶颈是 CPU 精排 20 对约 8.5 秒。LLM 只占 1.26 秒——优化它对这个延迟几乎没意义。

那你优化了什么？ 三件，按收益排序：① 预热 + readiness 分离——预热线程本来就有，但 /health 在模型加载完之前就返回 200，编排系统照常导流，第一个真实请求仍然等 48 秒；改成显式区分 liveness / readiness 并支持门禁（RAG_REQUIRE_WARM=1 时预热未完成返回 503）后，A/B 实测首个业务请求 42.1 s → 6.9 s，代价是启动期 31.3 s。② 精排可配置——消融已证明它带来 R@5 +12.7 个百分点，所以是「用延迟换准确率」的显式选择，不是默认打开。③ 检索缓存——但这是进程内的，跨进程没做，属于未完成项。

那 P95 能写进 SLA 吗？ 不能。 压测每档只有 3–8 个请求，分位数在这个样本量上没有统计意义；可用的只是结构性结论——并发 1→8 时 P50 从 7.5 s 涨到 45.8 s，说明是排队而不是并行加速。

方向四｜「拒答 100% 是不是在吹？」（考的是你会不会自己拆自己的数） ​

不是吹，但它证明的东西很窄，我主动说清楚。 不可回答的题只有 6 道，拒答准确率 100.0% 就是 6/6——样本量太小，它证明的是「没有漏拒」，不是「拒答很准」。比它更有说服力的是分数分布：可回答题（n=124）的 top1 分数中位 0.9617，不可回答题（n=6）中位 0.0127——两个分布几乎不重叠，说明阈值 0.30 落在一条很宽的沟里，而不是卡在刀尖上。

误拒率 7.3% 是怎么来的？ 7.3% 是阈值层和 prompt 层合起来的效果，所以我做了分层测试来归因：仅阈值层 1.6%，加上 prompt 层 6.5%（另一次实测 5.6%）。多出来的部分是 prompt 造成的——prompt 层拒答过度触发约 5%，我在项目里把它标为「设计决策点」而不是 bug：宁可多拒一点，也不能编。但我知道这个取舍是用误拒换漏拒，代价是真实的。

为什么不用一个更复杂的判定器？ 因为我先试过更简单的路——「用关键词规则判断问题是否在语料范围内」——它比我预期的更不可靠：规则表是人工维护的，语料一换就要重写，而分数分布是从数据里自己长出来的。选阈值不是因为它更先进，而是它可测。

方向五｜「哪些没做完？如果再给你两周做什么？」（考的是自知与优先级） ​

四处明确的未完成，我按「影响面试官判断的程度」排序：① 答案准确率没做人工校准——当前口径下这个数字是缺的，报告里写「需人工判定」；② 引用校验只能验编号合法性，验不了「引用的内容是否真支持结论」（需要 NLI 或人工复核）；③ 表格与公式抽取是有损的，设计稿要求的「表格独立成块 + 标题前缀」没有实现，现状是线性化抽取 + 引用正文兜底；④ 检索缓存是进程内的，跨进程持久化没做。

两周你会先做哪个？ 先做 ①。因为 ②③④ 都是能力的边界，我能说清边界在哪；① 是证据的缺口——一个「不知道答案对不对」的问答系统，其他指标再漂亮也不能证明它有用。而且 ① 的工程量可估：校准 130 题的答案准确率要的是人工时间，不是新技术。

有没有你故意不做的事？ 有——我没做 Agent 化工具编排。理由是单轮事实问答不需要 Agent，加编排只增加不确定性与成本；这个项目的瓶颈在检索层（混合检索反而掉 5.3 个百分点、表格数据被误删），不在「谁来调工具」。同一个判断我后来在另一个项目里做了反向选择——那个是电商客服多轮场景，有状态、有写操作、有跨轮指代，所以才需要编排。

service.py 注释里的「首个请求 48 秒」源码注释属注释自述，没保留原始日志「48 秒来自我的代码注释；我另有一组脚本输出的 A/B 实测，是 42.1 s → 6.9 s」

报数模板（背下来）：

「这个数字是 X，口径是 N 题 / gt 206 块 / 密度 1.66 块每题，比较对象是 ①②③ 三组同题对照，含精排（或：不含精排）。」

四个要素缺一个，这个数就不要报。 尤其是「是否含精排」——59.1% 与 71.8% 是同一批题上含与不含精排的差别，漏掉一个词就变成两个互相矛盾的数字。

五、被问到不会的怎么答 ​

第一步：明确承认，不铺垫、不绕。 「这个我没做过」——五个字说完，不要加「但是这个……」。面试官问「你做过吗」，是在测你的自我认知是否准确；铺垫会让答案显得像回避。

第二步：说清「我知道什么」。 把边界画出来：「我知道它要解决的是 X 问题，也知道有两个主流做法 A 和 B，但哪一版好、工程上代价多大，我没有实测数据。」

第三步：给出你不做的理由（如果有）。 这一步是加分项，但必须是真理由。可以直接用的一条：「单轮事实问答不需要 Agent，加编排只增加不确定性与成本」——这是这个项目里我明确记为「未做」的主动决策，不是遗漏。

第四步：给出可估的方案。 「如果现在要做，我会先……因为那一步能最快证伪。」——落点在「能最快证伪」，不是「能最快做完」：这说明你的顺序是按信息量排的，不是按工作量排的。

一个完整的例子（被问「你有没有做 RAG 的在线评测 / 自动标注」）：

「没做过。 在线评测的常见做法是拿真实流量做影子评估再抽人判，自动标注一般用 LLM 当裁判。但LLM 裁判的校准我没做过——我项目里就有反面例子：旧的答案准确率是 LLM 裁判打的，没人工校准，所以那个数字我不敢引用。如果现在要做，我会先量同一批题上 LLM 裁判与人工判的一致率——它低，后面所有自动评测都是白做的。」

三条禁忌：

  1. 不要编。 被追问三层是常规操作，编出来的第一层就撑不住第二层。
  2. 不要说「我们」。 个人贡献边界要清楚：「这部分是我做的，那部分是我参考 exp30_slice_compare.py 的写法自己实现的。」
  3. 不要把「没做」说成「不必要」。 顺序是「承认 → 给理由」；先讲理由会被听成找借口。

六、自检清单 ​

  • [ ] 30 秒版能一字不改背下来，且三个数字都带口径
  • [ ] 报任何一个数字时，我能立刻接上「题数 / gt 版本 / 密度 / 比较对象 / 是否含精排」
  • [ ] 我能说出至少 5 个黑名单数字，以及每一个为什么不能报
  • [ ] 被问到没做过的事时，我能在 5 秒内说出「这个我没做过」，并且不接「但是」
