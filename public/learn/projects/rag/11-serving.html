服务化与性能 ​

一句话：首字延迟约等于检索耗时，瓶颈在 CPU 精排不在 LLM——优化 LLM 是错方向。

这一页要回答什么 ​

  • 「你这个系统能上线吗？QPS 多少？」——要能给出实测延迟分解，并说清为什么并发上限是 2。
  • 「服务启动慢怎么处理？」——要求答出"预热做了但没生效"的完整因果链，以及 liveness 与 readiness 必须分开。
  • 「线上出问题了你怎么查？」——要求说出 trace_id 怎么跨线程传递、日志为什么不默认记原文、成本怎么记账。

读完这一页你应该能：讲清延迟瓶颈在哪一段、讲清并发上限 2 的来源与代价、讲清"健康检查必须查依赖"与 readiness 分离为什么是两回事。

一、它要解决什么问题 ​

能跑通的 demo 与能接流量的服务，差的不是"多写几个接口"，而是四类只在真实运行时才暴露的问题：启动（模型加载 30+ 秒，编排系统以为启动失败，或把流量导进没准备好的进程）、延迟（用户等 15 秒才看到第一个字）、资源（并发上去延迟线性恶化，不设上限就整台机器一起排队）、账（无鉴权时任何人刷接口都在花你的钱，一个循环脚本就能打光预算）。

service.py:60-68 的注释把第四条写得直白：无鉴权时任何能访问端口的人都能让部署者的账户花钱——每条设计都是被具体事故逼出来的。

为什么健康检查要查依赖：如果 /health 只证明"进程活着"，它给出的信号就是误导性的——编排器看到 200 就导流量，而进程可能缺索引、没 Key、模型没加载完。它要回答的是"我现在能不能正确服务请求"，不是"我还在不在"。 状态码刻意只对致命问题（缺索引、未就绪）返回 503，其他问题只列进 problems 不改码——因为那些情况下服务仍然能干活（预算耗尽时检索仍可用，见 2.7）。

为什么用后台线程（这一步是对的）：同步预热会让 uvicorn 等 30+ 秒才监听端口，编排系统会以为启动失败并杀掉容器。但预热还是没生效——service.py:73-78 记录了实测教训：预热线程确实在跑，但 /health 立刻返回 200 ⇒ 编排器 / 压测器看到 200 就导流量 ⇒ 第一个请求照样等 48 秒 ⇒ 必须区分 liveness（进程活着）与 readiness（能接流量）。

关键不是"忘了预热"，而是"暴露了就绪信号但信号是错的"：后台线程预热本身没问题，问题是没有任何东西告诉编排器"现在还不能接流量"——/health 的 200 覆盖了"模型还在加载"这个事实。项目落地：detail["ready"] 暴露 warmup_state（pending/done/skipped）+ warmup_ms；RAG_WARMUP=1 默认开（关掉则 state="skipped"）；RAG_REQUIRE_WARM=1 时未就绪追加"未就绪"并把状态码变 503。

可迁移性最强的一条：任何"启动时加载大资源"的服务都会遇到它——预热不是目的，"让编排器知道能不能接流量"才是目的。

2.5 并发：为什么上限是 2，以及 SSE 为什么不能用信号量 ​

并发档位实测（loadtest.py → _b15_loadtest.txt → output/05-面试准备-RAG数据.md:92-100）：

并发RPSP50说明
10.157.5 s基准
20.2013.7 s以此设并发上限（RAG_MAX_CONCURRENCY 默认 2）
40.2525.7 sRPS 已饱和
80.4045.8 s延迟涨 6 倍只换 2.7 倍吞吐

读法：P50 随并发线性上升、RPS 很快饱和 ⇒ 这是 CPU 排队，不是代码里的锁或 IO。并发 8 换来的 2.7 倍吞吐要用 6 倍延迟去换，对交互式问答不值得，所以上限取 2。

⚠️ 诚实标注：每档只有 3—8 个请求，P50 这些分位数不能写进 SLA；但"延迟随并发线性增长、吞吐饱和"这个结构性结论在任何样本量下都成立。

两条并发实现，为什么不一样：/ask 用 asyncio.Semaphore(MAX_CONCURRENCY)（service.py:121）；/ask/stream 在线程池跑，用不上 asyncio.Semaphore ⇒ 线程安全计数器 _inflight={"n":0} + _inflight_lock（:136-137）、_try_acquire（:140-145）/ _release（:148-150）。刻意不用信号量私有属性 _value——那是 CPython 内部实现，会随版本变，依赖一个不承诺的接口早晚会炸。

2.7 成本：事前查预算 + 事后记账（必须承认它不是硬约束） ​

on_done 回调让服务层在"真实花了多少钱"确定之后记账——流式路径的成本只有流结束才知道。因此熔断必然是：

事前查预算 + 事后记账 ⇒ 允许一次请求的超出。

这点必须写进文档，不能假装是硬约束。 任何"先查后记"的设计都一定会超一点点，把这句话说清楚比假装精确更值钱。

/retrieve 不计费（只受限流），只有 /ask 与 /ask/stream 花钱（guard.py:18-21）。

2.8 延迟分解：优化 LLM 是错方向 ​

分阶段时延基准（bench_latency.py --n 30，30 题样本，output/latency_report.md → output/05-面试准备-RAG数据.md:77-83，实测）：

阶段P50P90P99
检索（dense + BM25 + RRF + 精排）14.47 s18.44 s30.74 s
LLM 生成1.26 s1.87 s2.82 s
端到端（用户等待）15.66 s19.58 s32.26 s
冷启动（不能混进 P50）67.3 s——

⭐ 最反直觉也最好用的一条：流式首字延迟（TTFT）≈ 检索耗时（实测 14.90 / 10.00 / 14.86 s）。它推翻了"流式能救体验"的直觉：流式的作用是让生成阶段的等待被摊开，但如果 TTFT 基本等于检索耗时，用户点下去之后的十几秒屏幕上是没有任何东西的，流式一点忙都帮不上。

因果链：TTFT ≈ 检索耗时 ⇒ 瓶颈在检索不在生成 ⇒ 检索里最贵的是 CPU 精排 20 对约 8.5 秒（exp31 的向量库选型判据也用它）⇒ "优化 LLM"（换模型、调参数、加缓存）在这一层完全无效。要改善体验得动精排：减少对数、换更轻的模型、或挪到 GPU。

本页最有面试价值的一句话："实测首字延迟≈检索耗时，检索里最贵的是 CPU 精排 20 对约 8.5 秒，而 LLM 生成 P50 只有 1.26 秒——所以在这个系统里优化 LLM 是错方向。"

两条告警设计纪律：① send_alert() 总是写一行到 logs/alerts.jsonl（{"ts","level","key","title","detail","trace_id": obs.current_trace()}）——即使没配 webhook，本地留痕是底线；② webhook 在后台线程（threading.Thread(target=_post, daemon=True, name="alert")）——主链路绝不等待。

钉钉那个坑值得单独记：钉钉"自定义关键词"安全设置要求消息必须包含该关键词，否则静默拒收（errcode 310000）——不报错、不回执、告警就这么没了，所以代码支持 RAG_ALERT_PREFIX。"告警发出去了"和"告警被收到了"是两件事。

为什么 JSONL 不是文本日志：文本日志只能"读"，JSONL 能过滤与聚合——想知道"今天多少次请求 top1 < 0.30"，文本要写正则，JSONL 一行 jq 就完了。为什么日志失败绝不能拖垮主流程：可观测性是辅助能力，不是依赖。日志写不进去不该让用户拿不到答案；span 的 return False 同理——不吞异常，异常路径也要留痕。

隐私纪律：默认不记 prompt 原文，也不记用户问题原文，只记 question_len / top1 / chunk_ids / token 数这类"可归因但不含内容"的字段；真要排查才开 RAG_LOG_PROMPTS=1（log_prompts_enabled() :144-145）。取舍是默认保护内容、需要时显式打开——科研问答的场景里，用户问题本身就可能是未发表的想法。

2.12 缓存：做了，但没做全（如实写） ​

app.py 侧用 Streamlit 缓存装饰器缓存 corpus_overview（:63）/ eval_stats（:69）/ report_head（:82）/ sources_index（:104）；service.py 侧未读到显式检索缓存实现；检索缓存是进程内的，未做跨进程持久化（output/05-面试准备-RAG数据.md:165）。

设计蓝图要求「先做进程内 LRU……要能说出缓存命中率」（rag-项目设计.md:103），但 未找到命中率统计的实现，/health 与 /quota 里也没有缓存字段。缓存的效果只能靠命中率证明——主动说"这是我知道但还没做的"，比被问出来强。

六、面试深挖：追问链 ​

第一条：你这个系统延迟多少？瓶颈在哪？

  • Q：你这个服务的响应延迟是多少？
  • A：分阶段实测（30 题样本，bench_latency.py --n 30）：检索 P50 14.47 秒（P90 18.44 / P99 30.74），LLM 生成 P50 1.26 秒，端到端 P50 15.66 秒；冷启动 67.3 秒，我从不把它混进 P50 里报。
  • 追问：那你怎么优化？
  • A：先定位到段。我还测了流式首字延迟——三次实测 14.90 / 10.00 / 14.86 秒，基本等于检索耗时，方向就此定死（用户点下去后十几秒屏幕上是没东西的）。再往检索里拆，最贵的是 CPU 精排 20 对约 8.5 秒（做向量库选型时算出来的）⇒ 要改善体验得动精排：减少对数、换更轻的模型、或挪到 GPU。
  • 追问：那 LLM 呢？换个更快的模型有用吗？
  • A：在这个系统里"优化 LLM"是错方向。生成 P50 只占端到端的不到十分之一；就算把生成降到 0，端到端还是 14 秒多。选型上也吃过同一个教训——IndexFlatIP 在 52 万块规模下仍毫秒级，换 ANN 就是优化一个本来不慢的环节。先测分解再优化。

第二条：你说做了预热，为什么第一个请求还要等 48 秒？

  • Q：启动慢的问题你是怎么解决的？
  • A：我在 startup 事件里起了一个后台线程做预热，依次触碰 embedder（bge-m3）、reranker、chunk_list、faiss_index、BM25。用后台线程是必须的——同步预热会让 uvicorn 等 30+ 秒才监听端口，编排系统会以为启动失败杀掉容器。
  • 追问：那预热生效了吗？
  • A：没有。 预热线程确实在跑，但 /health 立刻返回 200——编排器看到 200 就把流量导进来，第一个请求照样等 48 秒。现象就是"预热做了但没用"。
  • 追问：根因是什么？怎么修？
  • A：根因不是"忘了预热"，而是"暴露了就绪信号但信号是错的"：后台线程预热本身没错，错在没任何东西告诉编排器"现在还不能接流量"。修法是把 liveness（失败重启）和 readiness（失败只摘流量）分开：在 detail["ready"] 暴露 warmup_state（pending/done/skipped）与 warmup_ms，RAG_REQUIRE_WARM=1 时未就绪追加"未就绪"并把状态码变成 503。
  • 追问：那你还漏了什么？
  • A：漏了持续健康度——/health 只做一次性依赖探测（索引产物、Key、预算），没查磁盘水位也没持续探测上游。所以严格说它是"就绪探测"而不是"健康度监控"。

第三条：并发上来怎么办？你的上限是多少？

  • Q：这个服务能扛多少并发？
  • A：压过四档（loadtest.py）：并发 1 → RPS 0.15 / P50 7.5 秒；并发 2 → RPS 0.20 / P50 13.7 秒；并发 4 → RPS 0.25 / P50 25.7 秒（RPS 已饱和）；并发 8 → RPS 0.40 / P50 45.8 秒（延迟涨 6 倍只换 2.7 倍吞吐）。所以上限设成 2。
  • 追问：你怎么判断瓶颈在哪？不是代码里的锁吗？
  • A：看形状：P50 随并发线性上升、同时 RPS 很快饱和，两条合起来指向 CPU 排队——每个请求都要占满 CPU 做精排，加并发只让它们排队。是锁或 IO 问题的话形状不会是这样。所以我没改代码，而是把上限设在延迟可接受的位置。
  • 追问：那这些分位数能写进 SLA 吗？
  • A：不能——每档只有 3—8 个请求，分位数没有统计意义。能说的是结构性结论：延迟随并发线性增长、吞吐饱和、瓶颈在 CPU，这些在任何样本量下都成立。要写 SLA，先把每档打磨到 100 个以上请求。
  • 追问：/ask 和 /ask/stream 的并发控制为什么不一样？
  • A：/ask 用 asyncio.Semaphore，但 /ask/stream 在线程池里跑，用不上 asyncio 的信号量，所以用线程安全计数器 _inflight 加一把锁，配 _try_acquire / _release。刻意没用信号量的私有属性 _value（CPython 内部实现，会随版本变）。释放放在 try/finally：客户端中途断开也必须 _release()，不然跑几轮就把并发位漏光，而上限是 2，漏两次服务就等于死了。
