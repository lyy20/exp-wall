生成与引用溯源 ​

一句话：引用校验能证明「编号合法」，不能证明「这句话真的被资料支持」——这条界线必须写清楚。

这一页要回答什么 ​

  • 「你的答案怎么保证不乱编？」——要求区分「编号合法性校验」与「事实归属校验」，并说清后者没做。
  • 「『资料不足』是你的 prompt 里写的一句话，那句话怎么定？」——要求说出 M08 那个案例：模型已经答对了却自报资料不足。
  • 「你为什么流式不也用 JSON mode？」——要求说清 JSON mode 与逐 token 输出在原理上冲突。

读完这一页你应该能：画出从 prompt 到最终答案的 5 条返回路径；说清 normalize_citations 与 check_citations 的分工以及那些脏输入会怎么被处理；说清 generate.py 与 streaming.py 的边界在哪。

一、它要解决什么问题 ​

生成层要同时满足三个互相冲突的要求：

  1. 结构化：程序要拿到 answer 和 citations 两个字段，才能做引用校验；
  2. 可核对：每个事实性陈述后面要带 [n]，而且 n 必须在上下文范围内；
  3. 流式：用户要尽早看到字。

第一条和第三条原理上冲突——response_format={"type":"json_object"} 必须等整个 JSON 生成完才能解析，而增量文本永远不是合法 JSON。这个冲突就是本页最值得讲的技术判断。

temperature 为什么是 0.1 而不是 0：拒答行为是概率性的，同一个 prompt，23 道可回答题里每轮都有 3 道被误拒，但中招的题每轮不同（S01/S15/M08 → S15/M05/M08）。保留一个可调的 temperature 开关（RAG_LLM_TEMPERATURE）是为了做可控对照实验；同时明确写着「温度降低会减少但不保证消除随机性」。

重试纪律：只对幂等操作重试。LLM 调用是「读」，重试安全；真实系统里「写」类工具调用（下单、写库）绝不能自动重试——那会重复副作用。

2.2 错误分层：为什么必须分，不分会出哪两种事故 ​

generate.py:122-170 定义了四个异常类。不分层会造成两种事故：

  • 把 400（参数错）也重试 ⇒ 同一个必然失败的请求打三次，白花钱；
  • 把 429 / 5xx 当致命 ⇒ 一次网络抖动就让整个请求失败。
错误分类处置为什么
401 / 403LLMConfigError配置错，立刻告诉人怎么修，不重试，退出码 2重试一万次也不会好
400LLMRequestError是我们的 bug，不重试例如 prompt 里没有出现 'json' 字样
429LLMTransientError可重试，尊重 Retry-After上游明确告诉了你该等多久
5xx可重试与 429 同类上游故障
超时 / 连接错可重试与 429 同类网络抖动

_classify(exc)（generate.py:153-170）按 status_code / status 与异常名兜底；_retry_after_seconds(exc)（:173-189）读 retry-after / Retry-After 头。

2.3 prompt 结构：四条要求，第三条改过一版 ​

PROMPT_TEMPLATE（generate.py:33-49）的四条要求：

  1. 只用资料，不得引入外部知识；
  2. 每个事实性陈述后必须标来源编号 [1] / [2]；
  3. 【资料不足分级判据】
    • a) 只要资料能支持问题里的任意一个关键要点 → 必须回答，并在末尾用一句话指出未涵盖部分（例：「资料未给出 X」），不得因为部分缺失就整体拒答；
    • b) 只有资料完全无法支撑任何关键要点时，才输出「根据提供的资料无法回答该问题」；
  4. 只输出 JSON，格式 {"answer": "...", "citations": [编号列表], "insufficient": true|false}。

第 3 条为什么写成「分级」——这是一次实测驱动的修改（generate.py:51-57，2026-09-28）。

原来的写法是一句话：「若资料不足以回答问题，必须回答『无法回答』」。实测后果是 B8 那批误拒里最典型的 M08：模型已经答对了（给出了 35.3% / 64.9% 两个正确数值），却因为「问题的另一部分资料没覆盖」而输出 insufficient=true ⇒ 整题被判误拒。

根因不是模型能力，而是「足够」这个词从来没被定义——模型只好自己定义，而且定得偏保守。

结论一句话：「够不够」是一个阈值，凡是阈值就必须被写清楚。

2.4 引用溯源：能验什么，不能验什么 ​

prompt 要求每个事实性陈述标 [n]，并输出 citations 数组。程序侧做两件事：

归一化 normalize_citations(raw) -> (list[int], dropped)（generate.py:294-347）——处理模型返回的各种形态：

text
[1, 2]   "[1][2]"   "1"   1   ["1", 2]   [[1], [2]]   null   字段缺失
1

合法性校验 check_citations(citations, n_context)（generate.py:272-291）：

python
bad = [c for c in citations
       if isinstance(c, bool) or not isinstance(c, int) or c < 1 or c > n_context]
1
2

两个必须记住的细节：

  • bool 必须先挡掉：bool 是 int 的子类，不挡的话 True 会被当成编号 1。
  • 纵深防御：虽然 normalize_citations 已经挡住了 bool，但 check_citations 是公开函数，别人可以绕过归一化直接调——校验层不该依赖调用方守规矩（同步体现在练习文件 practice/p3_check_citations.py）。

三类必须记住的失败模式（全部来自 test_generate_mock.py 的实测脏输入）：

输入旧行为危害
["1", "2"]citations=[] 且 citation_ok=True，报「✅ 引用校验通过」失败伪装成通过
[1, "2"]静默丢掉 "2"少了一条引用，没人知道
nullfor c in None → TypeError 崩溃崩溃
顶层返回数组（如 [{"answer": ...}]）obj.get → AttributeError 崩溃崩溃

修法：normalize_citations 改成报告被丢弃的项，answer_question 追加两道「不通过」判定（NOTES 坑 21）。「把无法识别的引用悄悄丢掉」等于「把失败伪装成通过」。

还有一个已知盲点必须写出来：check_citations([], n) 恒返回 (True, []) —— 空列表永远通过。所以「答案没给引用」这件事必须由调用方单独判失败。

界面上按三态展示（app.py 问答页、generate.py:main()）：非法编号（「上下文里没有这些来源 → 模型在编引用」）/ 校验未通过 / ✅ 通过。

⚠️ 本页最重要的一句诚实声明：引用校验只能验编号合法性——即「引用的 [n] 是否落在上下文范围内」。它不能验「引用的内容是否真的支持这个结论」。后者需要 NLI（自然语言推理）模型或人工复核，本项目两种都没做（eval/report.md:134）。所以正确的说法是「引用编号已校验」，不能说「引用已校验」——这两句话在面试里差别很大，后者一问就穿。

2.5 JSON mode 的三条实测边界 ​

exp07_json_mode.py 用四个**从「明确」逐步退化到「含糊」**的探针：

探针设计意图
1明确给出完整 schema（字段名、类型、示例）——基线
2只说「用 JSON 回答，包含答案和来源」——测字段名漂移
3说「citations 字段格式如 [1]、[2]」——最容易诱发字符串而非数组
4完全不说 JSON，只要「简短回答」——测 JSON mode 是否强制了 JSON

最后一步是闭环：把每个探针的原始输出直接喂给生产校验层（normalize_citations + check_citations），看它是否被拦下、是否被错误地判成「✅ 校验通过」。

三条实测边界（NOTES 坑 32）：

  1. 字段漂移：字段名不按 schema 来；
  2. 元素类型漂移：citations 给成字符串而不是数组；
  3. 「prompt 里必须有 json 字样」：这是 400 错误的常见原因，也是错误分层里把 400 归为「我们的 bug」的具体依据。

「开了 JSON mode = schema 校验通过」是新手最常见的误解：JSON mode 只保证「能解析」，不保证字段名、不保证元素类型。

2.6 JSON mode 与流式的原理冲突 ​

streaming.py 的 docstring 把这件事讲得很清楚：response_format={"type":"json_object"} 那条路必须等整个 JSON 生成完才能解析，与「逐 token 吐给用户」在原理上冲突——增量文本永远不是合法 JSON。

两条出路：

出路做法代价
(a) 本项目选择流式走纯文本 prompt；引用由程序在流结束后从完整文本里抽取并校验没有 JSON mode 的语法保证；引用抽取靠正则、格式更依赖 prompt 约束
(b) 假流式先拿完整答案，再切块吐给用户首字延迟一点没降，纯表演

本项目选 (a)：引用用 re.findall(r"\[(\d+)\]", answer) 从完整答案里抽编号，然后走同一套 normalize_citations + check_citations（streaming.py:65-190）。换来的是首字延迟从「整段生成完」降到「第一个 token」——虽然本项目的 TTFT 仍然受限于检索耗时（见 ⑥ 重排与上下文组装），但至少 LLM 这一段不再是串行阻塞。

2.8 解析容错与 5 条返回路径 ​

宽松解析 _parse_json_loose(text)（generate.py:259-269）：先剥 ```json 围栏（re.sub(r"^```(?:json)?|```$", "", text, flags=re.M)），失败则用 re.search(r"\{.*\}", text, re.S) 兜底。

顶层必须是 dict：模型可能返回数组（如 [{"answer": ...}]），此时 obj.get 会 AttributeError 崩溃 ⇒ 非 dict 时报 llm_output_not_object。解析失败时返回的 Answer 里，answer 字段会带上 (JSON 解析失败：...) 原文：{raw[:300]}，refuse_reason="llm_output_unparsable"——把原始输出前 300 字符留在答案里，是排障时最有用的一条信息。

为什么要单独抽一个 _obs_kw(usage)（generate.py:452-463）：answer_question 有 5 条 return 路径，如果每条都手写一遍 trace_id 与 usage，早晚会漏一条——而漏掉的那条恰恰是「出问题的那条」（解析失败 / 模型拒答）。这是「重复代码的代价不是写起来累，而是会漏」的一个具体例子。

2.9 退出码：拒答不是错误 ​

qa.py 与 generate.py 共用一套退出码：

码含义
0正常——包含拒答。拒答是正常结果，不是错误
1未预期的错误
2配置错误（如未设置 API Key）

report_config_error(e)（generate.py:478-495）打印干净的提示并返回 2。为什么不直接让 RuntimeError 冒出去：用户会看到二十几行 Python 栈，而真正有用的那句话埋在末尾——把可操作的信息从栈里救出来，是 CLI 的责任。

CLI_CONFIG_ERROR_HINT（generate.py:469-475）里有一条很实用的提示：检索（向量 + BM25 + RRF + Rerank）不需要 Key，只有最后一步调 LLM 生成才需要；可以先 python retrieve.py "问题" -v 验证检索链路。

六、面试深挖：追问链 ​

第一条：怎么保证答案不乱编？

  • Q：大模型会编，你怎么保证你的答案不乱编？
  • A：分三层。约束层：prompt 要求只用资料、不得引入外部知识，每个事实性陈述必须标来源编号。校验层：程序检查引用的编号是否落在上下文范围内——上下文只有 5 块，编号只能是 1 到 5，出现 6 就是「上下文里没有这个来源」，界面明确提示「模型在编引用」。拒答层：资料完全无法支撑时输出拒答。
  • 追问：那如果模型引用了 [3]，但第 3 块的内容其实不支持这句话呢？
  • A：这种情况我的校验抓不到，必须说清楚。我的校验只能验编号合法性，不能验事实归属——即「引用的内容是否真的支持这个结论」。后者需要 NLI 模型或者人工复核，本项目两种都没做。所以我的正确表述是「引用编号已校验」，而不是「引用已校验」。这两句话在面试里差别很大，我不想含糊过去。
  • 追问：那你为什么不加 NLI？
  • A：成本收益不划算，而且会引入一个新的不确定源。NLI 模型本身有错误率，用它自动判定「引用是否支持结论」，等于把「引用可信」变成一个概率性的属性；而现在这个属性是确定性的。如果要做，我的做法是把它做成评测侧的工具而不是生产链路的门禁——用它在离线标注里找可疑样本，而不是在线上直接拦答案。这个也属于「想清楚了但没做」的项。

第二条：prompt 里的「资料不足」怎么定义？

  • Q：你的拒答 prompt 是怎么写的？
  • A：现在是分级判据：只要能支持问题里的任意一个关键要点就必须回答，并指出未涵盖的部分；只有完全无法支撑任何关键要点时才拒答。
  • 追问：为什么写得这么啰嗦？一句话不就行了？
  • A：因为一句话的版本实测出过事故。原来写的是「若资料不足以回答问题，必须回答『无法回答』」。有一道题模型已经答对了——给出了 35.3% 和 64.9% 两个正确数值——却因为问题的另一部分资料没覆盖，输出 insufficient=true，整题被判误拒。
  • 追问：那你怎么确认这是 prompt 的问题，而不是模型能力问题？
  • A：因为模型答对了数值，说明它有能力。真正的根因是「足够」这个词从来没被定义——模型只好自己定义，而且定得偏保守。我的总结是：「够不够」是一个阈值，凡是阈值就必须被写清楚。改成分级判据之后，同类误拒明显减少。顺带一个更重要的认识：拒答行为是概率性的——同一个 prompt，23 道可回答题里每轮都有 3 道被误拒，但中招的题每轮不同。「同一个率、不同的集合」，这就是随机过程的签名。所以判据只能是全量指标，不能是单次输出。

第三条：流式为什么不能用 JSON mode？

  • Q：你流式是怎么做的？也用 JSON mode 吗？
  • A：不能用，这是原理冲突。response_format={"type":"json_object"} 必须等整个 JSON 生成完才能解析，而流式的目的是逐 token 吐给用户——增量文本永远不是合法 JSON。
  • 追问：那你怎么解决的？
  • A：流式换一条纯文本 prompt（版本号 v2-stream-20260928，和 JSON 那条 v2-分级不足-20260928 不是同一条），引用由程序在流结束后从完整文本里用正则抽编号，然后走同一套 normalize_citations + check_citations。
  • 追问：那代价是什么？你付出了什么？
  • A：三个代价，我说清楚。第一，没有 JSON mode 的语法保证，引用抽取靠正则、格式更依赖 prompt 约束。第二，prompt 出现了两个版本，需要同步维护，而且流式那条的拒答检测只能靠比对文本是否等于拒答话术。第三，用量上报依赖 stream_options={"include_usage": True} 的最后一个 chunk；如果开流首次失败走了降级重试，那条路径拿不到 token 数——我记了一条 stream.retry_no_usage 事件明确标注，不能假装有数。另一条出路是「假流式」（先拿完整答案再切块吐），但那首字延迟一点没降，纯表演，我没选。
