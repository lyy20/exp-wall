拒答与护栏 ​

一句话：拒答分两层——程序层是零成本的确定性判据，模型层是概率性的兜底，两者的误拒率必须分开测量。

这一页要回答什么 ​

  • 「你怎么知道该拒答？」——要求给出判据、阈值、以及阈值是怎么标定出来的。
  • 「你的误拒率是多少？」——要求答出两个数（1.6% 与 6.5%），并说清差在哪。
  • 「模型自己说资料不足，这算不算数？」——要求识别出这是一个设计决策点，而不是 bug。

读完这一页你应该能：画出双层拒答的完整判定顺序；说清 0.30 这个数字的来历与它成立的前提；说清「拒答准确率 100%」这句话的分母只有 6 道题。

一、它要解决什么问题 ​

这个项目里有一类题是故意答不出来的——设计原则是「库里有这个词，但没有答案」（详见 ② 定位与语料）。对这类题，系统必须明确拒答，而不是顺着检索到的相关段落编一段话出来。

拒答本身有两个方向的风险，而且它们是对立的：

风险表现代价
漏拒该拒的没拒，编出一段看着很流畅的答案最严重：科研场景下一个编造的数字比一句「查不到」有害得多
误拒能答的拒了用户觉得「这系统什么都不肯说」，产品不可用

所以「拒答」不是一个开关，而是一个阈值——而凡是阈值，就必须标定、必须验证、必须说清口径。

二、方案与实现 ​

2.1 两层结构 ​

程序层（第一道）模型层（第二道）

2.2 阈值只对精排分数成立 ​

这是一个必须写进文档的前提，因为它一旦被误用，后果是「每一道题都被拒答」：

  • use_rerank=True：返回 Cross-Encoder 相关性分数，这个分数可以做阈值；
  • use_rerank=False：返回的是 RRF 融合分数，实测区间约 0.016—0.033。拿它比 0.30，全军覆没。

评测脚本用一行条件挡住了这个错误：

python
refused = (use_rerank and t1 < threshold)
1

所以主报告里 ①② 组的拒答三列渲染成 —（不适用），而不是「测出来是 0」。

这里有一个更一般的工程判断：「不适用」和「0」是两件完全不同的事。把不适用渲染成 0.0%，读者会以为「测过了，是 0」，从而得出错误结论。这个项目的原则是缺数据时宁可留空——因为「缺数据时显示 0，比留空更糟」。

2.3 0.30 是怎么定出来的 ​

流程：先用阈值扫描找到可分点，再取 0.30。扫描区间是 [0.05, 0.6]（exp06_rerank_scores.py docstring），入口是 evaluate.py --sweep。

依据是两类分数的分布重叠程度（eval/report.md:91-110）：

组类别nmin中位数max
① 纯向量可回答1240.53280.65830.7898
① 纯向量不可回答60.48430.55020.5973
② 混合无精排可回答1240.02620.03230.7331
② 混合无精排不可回答60.02980.54220.5871
③ 混合 + Rerank可回答1240.04110.96170.9999
③ 混合 + Rerank不可回答60.00180.01270.2502

为什么是精排分数：只有 ③ 组形成了清晰的分隔——可回答的中位数 0.9617 vs 不可回答的中位数 0.0127（比值近 76 倍，由两个中位数相除算出）。

⚠️ 但两类的取值区间并没有完全分离：可回答题的最小值是 0.0411，落在不可回答题的最大值 0.2502 之下，重叠区间是 [0.0411, 0.2502]。所以准确的说法是「可分的是分布，不是每一个样本」——0.30 这个阈值是统计意义上的安全点，不是一条能把两类样本一刀切开的线。

①② 组的两类分布则严重重叠，报告自己的读法是：

「两类分数的分布重叠越少，阈值越可靠。若重叠严重，说明 Rerank 分数不足以单独做拒答判定，应以 prompt 层拒答为主。」

⚠️ 口径：上表的 n 是「评测时的可回答题 124 / 不可回答题 6」。不可回答只有 6 道，所以基于它算出来的任何比率，分母都很小——这一点在汇报里必须说。评测深度是「请求 10 个候选、实际取回最多 10 个」（eval/report.md:51）。

2.4 拒答话术与状态标记 ​

层用户看到的程序侧字段
程序层「根据提供的资料无法回答该问题。」refuse_reason 形如 rerank_top1=0.0127 < 阈值 0.3
模型层模型自己输出的兜底句refuse_reason="llm_self_reported_insufficient"
流式路径同上citation_note="模型自述资料不足"

程序层的 refuse_reason 里带着实测分数——这是一个有意的设计：用户与排障者能直接看到「离阈值有多远」，而不是只知道「被拒了」。

2.5 怎么验证拒答是有效的 ​

验证分五件独立的事，每一件都对应一个具体的否证能力：

手段做什么能否证什么
三指标分离分别统计 拒答准确率（不可回答题上正确拒答的比例）/ 误拒率（可回答题上错误拒答的比例）/ 漏拒（该拒没拒的数量）防「把三件事混成一个总分」——混了以后你永远不知道该修哪一环
阈值扫描evaluate.py --sweep 扫 [0.05, 0.6]防「拍一个阈值」：能看出换阈值时两个指标怎么此消彼长
逐层归因exp08_refuse_reality.py：在全部不可回答题上一题一题数「程序层拦了几道 / 模型层额外拦了几道 / 两道都失效几道」防「只知道整体拦住了，不知道是谁拦住的」
受控变量实验exp21_refuse_experiment.py：V0 现状 / V1 点名方法名 / V2 放宽「不得猜测」/ V3 去掉表格乱码行，一次只改一个变量防「改了一处，以为好了，其实没变」——实测确实出现过「改了一处后误拒率没降、出问题的题换了」
负样本有效性复核exp16_u07_check.py + check_negatives.py：扩库后重新确认「是否真的不可回答」防「拿一道其实可以回答的题当负样本」——实测确实复核出 1 道
端到端反馈app.py 反馈入口四选项（👍 正确 / 🤔 部分正确 / 👎 错误 / 🚫 该答却没答）→ badcase.py --from-answers防「只有离线评测，没有真实使用信号」

2.6 两层是怎么分工的：把误拒率分开测 ​

这是本页最值得讲的一条测量设计：

口径误拒率出处
仅阈值层（只看程序层的 top1 < 0.30）1.6%eval/report.md:135、output/05-面试准备-RAG数据.md:54
阈值层 + prompt 层自述6.5%（另一次运行 5.6%）eval/report.md:135、app.py:478-521
③ 组（124 题口径，双层）误拒率 7.3% / 拒答准确率 100.0% / 漏拒 0eval/report.md:43

1.6% 与 6.5% 之间的那约 5 个百分点，就是模型层自述拒答带来的额外误拒。

这个数字的意义在于：它把一个含糊的问题变成了一个可以决策的问题——「该不该让模型自述一票否决？」eval/report.md:135 的原话是：

「prompt 层自述拒答是概率性的、且会过度触发：同一套题实测『仅阈值层』误拒 1.6%、而『阈值层 + prompt 层』误拒 6.5% ⇒ 约 5% 的可回答问题被模型自述的『资料不足』挡掉。这是设计决策点（该不该让模型自述一票否决），不是 bug；要改就先定策略，再改 generate.py 的分级判据。」

⚠️ 三行数字属于不同批次，不要混着用：1.6% / 6.5% 来自同一段结论里的对照测量；7.3% / 100.0% / 0 来自 124 题（gt 206 块 / 1.66 块每题）的 ③ 组报告。报数时必须带上各自的口径与题集规模。

还有一条口径变化要记住：旧口径（30 题）的拒答准确率是 85.7%，U07 转题之后变成 100%。这两个数不是「进步」，是负样本集换了一道题。

2.7 模型层行为的随机性：一个率、两个集合 ​

config.py:195-199 的注释记录了一次很有说服力的观察：同一个 prompt，23 道可回答题里每轮都有 3 道被误拒，但中招的题每轮不同（S01/S15/M08 → S15/M05/M08）。

「同一个率、不同的集合」就是随机过程的签名。

这条观察带来两条纪律：

  1. 判据只能是全量指标（误拒率 / 拒答准确率 / 漏拒数），不能是单次输出；
  2. 温度降低会减少但不保证消除随机性——所以提供了 RAG_LLM_TEMPERATURE 开关用于做可控对照实验，而不是把温度当解药。

坑 27 就是这条纪律的反面教材：一次误诊，把「概率性拒答」当成了「确定性成因」，改了一处之后误拒率没降、出问题的题换了。

2.9 「评测即产品」：拒答能验证到什么程度 ​

拒答有效性的可信度，最终取决于评测集本身的纪律。这个项目在这件事上做得比链路本身更讲究，四条值得单独记住：

纪律做法
gt 独立盲标换会话、不看检索分数地读原文复核。实测后果：Recall 从 87% 掉到 71%，并推翻了两条已有结论——但这是好事，因为原来那个数是被检索结果锚定出来的
机器 gt 自我否定用检索结果构造的 gt 报告，顶部自己写着「🚫 本报告不可作为结论」
报告强制带标尺每份报告必须写清 gt 版本 + 密度（块/题）；主报告的标尺节里 gt 版本是空的，就如实留空并注明「跨版本比较一律无效」
已知问题与真实失败分开统计回归门禁只测确定性断言；known_issues.json 里的 3 条（S08 / S13 / M06）单独统计、逐条打印 reason，只有真实失败影响退出码

最后一条特别值得说：如果把 3 条已知问题也算成失败，回归门禁就会永远红着，然后所有人都不再看它——门禁的价值不在于严格，而在于可信。

步骤输入输出数值

五、踩过的坑 / 做过的取舍 ​

现象根因怎么定位到的怎么修的教训
报告里 ①② 组的拒答列显示 0.0%无精排时返回的是 RRF 融合分（区间 0.016—0.033），拿它比 0.30 会让每一道题都被拒；渲染层又把「不适用」写成了 0对照 use_rerank 两个分支的返回语义判据加 use_rerank and ...；报告改用 — 表示不适用「不适用」和「0」是两件事；缺数据时显示 0 比留空更糟
一次误诊：改了 prompt 里一处措辞，以为误拒会降把「概率性拒答」当成了「确定性成因」改完后误拒率没降，而且出问题的题换了（S01/S15/M08 → S15/M05/M08）改用受控变量实验（V0—V3，一次只改一个变量）；判据改为全量指标；加 RAG_LLM_TEMPERATURE 做对照「同一个率、不同的集合」是随机过程的签名；单次输出不能当判据
测「成本熔断」时永远触不到预算线测试用的是程序层拒答那条路径，成本是 0检查请求实际走了哪条返回路径端到端测试必须用真的会花钱的路径测试用的是不是「被测量那条路径」，必须自己验证
7 道负样本里有 1 道其实已可回答训练语料变了，问题的可回答性就变了独立会话（不看检索分数）读原文复核U07 转为多跳题；负样本 7 → 6 道；拒答准确率 85.7% → 100%负样本的有效性是语料的函数，不是永久属性
硬编码的分母让自检「看起来通过」自检脚本里写着固定的分母（gt_chunks 已回填 124/23）换题集规模后数字对不上分母必须动态计算自检脚本里的常数，就是下一次的假通过

六、面试深挖：追问链 ​

第一条：0.30 这个阈值怎么来的？

  • Q：你的拒答阈值 0.30 是怎么定的？
  • A：扫描 + 看分布重叠标定出来的，不是拍的。先用 evaluate.py --sweep 在 [0.05, 0.6] 区间扫描，再看两类分数的分布：在加精排的那一组里，可回答题的 top1 中位数是 0.9617，不可回答题是 0.0127，差近 76 倍，分布几乎不重叠，所以 0.30 落在中间很安全。
  • 追问：那前两组为什么不用这个阈值？
  • A：因为不能用。纯向量组两类分数严重重叠（可回答中位 0.6583 vs 不可回答 0.5502），报告自己的读法就是「若重叠严重，说明 Rerank 分数不足以单独做拒答判定，应以 prompt 层拒答为主」。混合无精排那组更极端，它返回的是 RRF 融合分，实测区间只有 0.016—0.033，拿它比 0.30 会让每一道题都被拒。
  • 追问：那你怎么保证报告不会让人误读？
  • A：评测脚本里加了一条判据 refused = (use_rerank and t1 < threshold)，所以那两组的拒答三列渲染成 —，表示不适用，而不是 0。我曾经把「不适用」渲染成 0.0%，这是一类很典型的错误——它会让读者以为「测过了，是 0」。这个项目的原则是缺数据宁可留空。另外我必须主动说的一个口径问题：不可回答题只有 6 道，所以基于它算的比率分母很小，说 100% 的时候一定要带这个前提。

第二条：误拒率是多少？

  • Q：你的误拒率是多少？
  • A：有两个数，必须分开说。只看程序层阈值，误拒率 1.6%；加上模型层自述「资料不足」，误拒率 6.5%（另一次运行 5.6%）。差的那约 5 个百分点，就是模型自述拒答带来的额外误拒。另有一组 124 题口径的报告写的是误拒率 7.3%、拒答准确率 100.0%、漏拒 0——这三行属于不同批次，不能混着用。
  • 追问：为什么要把两层分开测？
  • A：因为混在一起测，你就无法做决策。如果只报一个 6.5%，我无法回答「该不该保留模型层自述拒答」；拆开之后问题就变成了「为了兜住漏拒，值不值得多付 5 个点的误拒」。这是一个产品判断，而分开测量让这个判断有了数字依据。
  • 追问：那你的结论是保留还是不保留？
  • A：当前保留，并且我在报告里把它明确标成「设计决策点」而不是 bug。保留的理由是：程序层只看得见 top1 分数，看不见「资料是否覆盖问题里的每一个关键要点」；而模型层恰好能补这一点——比如资料给了 A 却没给 B，程序层的分数可能仍然很高。要改的话，先定策略，再改 generate.py 的分级判据，而不是顺手删掉一层。

第三条：模型自述拒答可靠吗？

  • Q：让模型自己说「资料不足」，这件事可靠吗？
  • A：不可靠，它是概率性的。有一个很有说服力的观测：同一个 prompt、23 道可回答题，每轮都有 3 道被误拒，但中招的题每轮不同——第一轮是 S01/S15/M08，第二轮是 S15/M05/M08。同一个率、不同的集合，这就是随机过程的签名。
  • 追问：那你凭什么用它？
  • A：我用它做兜底，不做主判据。主判据是程序层的阈值：确定性、零成本、可复现。模型层只在程序层放行之后起作用，职责是补程序层看不见的那一类（资料不全但 top1 分数很高）。所以顺序不能反：先程序层，后模型层。
  • 追问：那你怎么验证它不是随机地在乱拒？
  • A：三条。第一，判据只能是全量指标——误拒率、拒答准确率、漏拒数，不看单次输出。第二，受控变量实验：V0 现状 / V1 点名方法名 / V2 放宽「不得猜测」/ V3 去掉表格乱码行，一次只改一个变量；这里我踩过一个坑——一开始改了 prompt 里一处措辞，以为误拒会降，结果误拒率没降、出问题的题换了，根因就是把概率性现象当成了确定性成因。第三，温度开关（RAG_LLM_TEMPERATURE）用来做对照；但我要说清：温度降低会减少、不保证消除随机性，它不是解药。

七、自检清单 ​

  • [ ] 能不看代码说出双层拒答的顺序，并说清为什么程序层必须在前（零成本 + 确定性）。
  • [ ] 能说出至少 2 个「为什么这样选」：为什么阈值只对精排分数成立；为什么把「不适用」渲染成 — 而不是 0。
  • [ ] 能说出至少 1 个坑与根因：一次误诊把「概率性拒答」当成确定性成因，定位手段是发现「误拒率没降、出问题的题换了」。
  • [ ] 涉及的每个数字都能说出处：0.9617 / 0.0127 来自 eval/report.md:91-110（③ 组，n=124 / n=6）；1.6% 与 6.5% 来自 eval/report.md:135；7.3% / 100.0% / 0 来自 eval/report.md:43（124 题 / gt 206 块 / 1.66 块每题）。
