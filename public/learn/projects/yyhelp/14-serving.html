⑮ 服务化与 API ​

一句话：这一页讲清三个端点的分工、SSE 为什么必须手写三个响应头、鉴权为什么必须排在限流前面，以及 liveness 与 readiness 为什么绝不能合成一个探针。

这一页要回答什么 ​

服务化这一块，面试官的问题集中在「边界」与「顺序」上：

  1. 「你的 API 有哪些端点？为什么流式和非流式分成两个？」——考的是协议设计，不是「我会写 FastAPI」。
  2. 「你用了 SSE？为什么不用 WebSocket？」——考的是你是否理解 SSE 的工程细节，尤其是那三个响应头。
  3. 「限流和鉴权哪个先？」——是送分题还是送命题，取决于你有没有想过顺序。
  4. 「你的健康检查怎么写的？」——答「返回 {"status": "ok"}」直接出局，那什么都没验。

读完这一页，你能答：三个端点的职责与共用路径、SSE 三个响应头各自防什么、拒答与正常回答为什么共用 token 事件、鉴权与限流的正确顺序及其反例、liveness 与 readiness 的判据差别、容器化约束（非 root、uid 10001、8080），以及版本矩阵与验收口径。

一、它要解决什么问题 ​

1.1 一个「能跑的函数」离「能用的服务」差三件事 ​

检索、生成、Agent 循环做完，只说明函数是对的。要变成别人能调的服务，还差三件事：

差什么不做会怎样
协议调用方不知道说什么、收什么；流式体验做不出来，用户盯着空白等 7 秒以上
边界没有限流就是「谁都能把账单刷爆」的接口；没有探针，编排系统不知道这个实例能不能收流量
依赖隔离把「进程还活着」和「业务是否可用」混成一个信号，探针会同时骗过你和编排系统

1.2 v2 的服务层：从「没有」到「有」（2026-10-09 更新） ​

⚠️ 这一节在 2026-10-09 被改写

本页早期版本写的是「v2 代码树里没有 api/ 子包，承载 HTTP 的仍是 v1 的 yyhelp/api/app.py」——那个落差已经补上了：本轮实现了 code/yyhelp_v2/serve/app.py（405 行，FastAPI），v2 现在有自己的服务层，并有验收文档与实测记录。

v2 服务层现在有四个文件：

文件职责是不是 HTTP
serve/app.pyv2 的 HTTP 服务：/health（双探针）、/chat、/chat/stream（SSE）、鉴权、限流、并发闸、X-Trace-Id 中间件✅ 是
serve/routing.py灰度打标 + 模型路由 + 成本记账❌ 库函数

v1 的 api/app.py（947 行）仍然在——它是 v1 基线的一部分，冻结不动；v2 的服务层是独立实现，两者共享同一条「服务层职责不进工厂」的分工原则（eval/run_ab.py:251 是示范位置：A/B 需要的「这次走哪条路」标记加在服务层，不塞进 Agent 的图工厂）。

v2 服务层的四件必须说清的事（面试会追问）：

设计点做法为什么
双探针GET /health 分 liveness / readiness：前者只证明进程活着；后者额外检查 llm_configured + graph_build_ok + v1 KB 导入是否可用判据见 2.6：探针不能只查进程，否则依赖挂了仍报健康
鉴权在限流之前请求先过鉴权，再过滑动窗口限流反过来会让未鉴权请求消耗配额（见 2.4）
并发闸BoundedSemaphore 限制同时在跑的请求数本机 CPU 形态下并发不提升吞吐只增延迟，闸门保护尾延迟
程序层拒答超范围问题在图之外直接拒答零 LLM 成本——实测拒答路径 ~1 s 返回

服务层实测数字（2026-10-09，loadtest_b2.py，6 并发 × 3 轮 = 18 请求）：

于是这一页的结构是三层：

层内容出处

二、方案与实现 ​

2.1 三个端点，一条主干 ​

三个端点不是三套逻辑，而是一条主干 + 三种出口：

端点方法行依赖 LLM 才能就绪吗职责
/healthGET:696不需要探针：probe 默认 "liveness"
/askPOST:811真实生成需要一次问答，非流式返回
/ask/streamPOST:824真实生成需要同一次问答，SSE 逐帧返回

事实清单里有一句很关键的话：/health 与拒答路径都不需要 LLM 依赖，/ask 的真实生成需要（模块 docstring）。它把「探针」与「业务」的依赖面切开了——这是 2.6 节的前提。

两个业务端点共用主干 answer_question(question, *, trace_obj=None, ...)(:458)。共用是刻意的：各写一套，程序层拒答(:401)、LLM 前闸门(:442)、就绪检查(:533-535)、生成(:554)、成本记账就会出现两份实现、两份偏差。共用之后，「同一句话在流式与非流式下答案不一致」这类 bug 在结构上不存在。

2.2 SSE：三个必需响应头，缺一即坏 ​

响应头值少了会怎样
Cache-Controlno-cache中间层（浏览器 / 反代）可能缓存这条响应，第二个用户拿到的可能是第一个人的答案
X-Accel-BufferingnoNginx 一类反代会缓冲响应，逐帧流式退化成「全部生成完再一次性吐出」——流式的意义就没了
Connectionkeep-alive长连接被提前关掉，流到一半断掉

实现方式必须说准，说错会被认为在抄旧文档：

  • 原实现是 StreamingResponse(media_type="text/event-stream")，要自己拼帧、自己保活。
  • 目标形态 fastapi.sse.EventSourceResponse——FastAPI ≥ 0.135 已内置（模块 docstring 原话：「内置实现帮你处理了 keepalive 与帧格式」），实测可用。
  • 因此不需要装 sse-starlette。旁证：starlette 1.7.0、fastapi 0.141.1，基线未被 mcp 依赖污染（mcp>=1.28,<2 是另一条独立约束）。

自己拼帧的一侧能看到实现：_sse(event, data) -> str(:887) 把 (event, data) 拼成帧，_chunks(s, n) -> Iterator[str](:882) 切片。两者可测——selftest()(:903) 与 _parse_sse(raw) -> list[dict](:1058) 就是「发出去的帧能不能解析回来」的自检闭环。

2.3 拒答与正常回答共用同一个 token 事件 ​

程序层拒答（programmatic_refusal(:401)）与正常生成，用的是同一个 token 事件。为什么不分成 refusal 与 token 两种？

方案调用方代码代价
区分事件类型必须写两个分支：一个处理拒答、一个处理正文每个客户端都要正确处理两条路径；漏一条就出现「拒答时界面空白」
共用一个 token 事件（本项目）只要一个累加器：把 token 追加进缓冲区客户端更简单；拒答与答案在协议上同构，降级路径不是特殊路径

这与可观测那一页同一种思路：拒答不发 LLM，但这条路同样要留痕（v1 在 LLM 未就绪时打 skipped="llm_not_ready"，见可观测）。把特殊路径做成普通路径的一个实例，而不是需要额外分支的新协议。

2.4 鉴权必须在限流之前 ​

限流阈值在代码里是一行常量：

python
RATE_LIMIT_PER_MIN = int(os.environ.get("YYHELP_RATE_LIMIT_PER_MIN", "60"))
1

也就是默认 60 次/分钟（api/app.py:120），由 class RateLimiter(:345) 实现，实例 RATE = RateLimiter(RATE_LIMIT_PER_MIN)(:393) 挂在主干上。并发另有一条判据：并发上限本质是成本闸门——「并发 4 × 每条 2000 token，就是上界」（docstring :121）。限流管频率，并发上限管同一时刻的成本敞口。

然后是顺序问题，这是整页最该记死的一条：

鉴权必须在限流之前。

顺序反了会怎样？限流变成拒绝服务放大器。

  • 正确（鉴权 → 限流）：未通过鉴权的请求在鉴权层被拒，不消耗配额。攻击者拿无效 token 打一万次，被拒的是他自己。
  • 错误（限流 → 鉴权）：所有请求先吃掉一个配额，才轮到鉴权判断是否合法。于是攻击者无需有效凭证就能把全局限额打到 0——合法用户随后全部 429。你为自保加的限流，变成别人手上的攻击工具。

限流状态还要可观测，实现里两处：响应模型带 rate_left: int = 0(:604)，/health 报出当前阈值(:448)。

鉴权细节本页必须标一个【待确认】：v1 有独立的 webapp/auth.py（326 行）管前端鉴权；但 api/app.py 内部的鉴权细节（头名称、token 来源）未逐行确认。

【待确认：/ask 与 /ask/stream 的鉴权方式（header 名称 / token 来源）】 验证命令：Select-String -Path code\yyhelp\api\app.py -Pattern 'Depends|Header|Authorization|api_key|verify' -Context 2,2

三件值得单独拎出来讲的事：

  1. PYTHONUNBUFFERED=1 不是可选项。 stdout 被缓冲时日志会攒在缓冲区，崩溃那一刻丢掉的恰恰是最后几行。
  2. 非 root、显式 uid 10001。 用 useradd --uid 10001 而不是让系统随便分配，是为了让挂载卷的属主在重建镜像后依然稳定：uid 随机变动会让数据卷突然不可写。
  3. --workers 1 + 健康检查走 127.0.0.1:8080。 单 worker 意味着限流器是进程内状态、不需要额外一致性方案（代价是扩容后每实例独立计数，这个边界要自己讲清）。健康检查打回环地址，验的是容器内部进程状态。

另外两个与「上线会不会翻车」直接相关的细节来自 deploy/docker-compose.yml：

  • 日志必须有上限。 组合文件写了 logging: {driver: json-file, ...}(:72)。不给上限，容器的 json 日志会无声把盘写满，最后表现为「服务莫名其妙挂了」。
  • 依赖栈行号：mysql:83（mysql:8.4.11，容器名 yyhelp-mysql，宿主端口 3307）、etcd:145、minio:182、milvus:253、postgres:345、clickhouse:371、redis:424、langfuse-worker:455、langfuse-web:549、yyhelp-api:602。

注意最后几个：这个 API 部署不需要 Langfuse 与 Milvus 全部在线——镜像只 COPY code/ 与 deploy/。可观测走默认 JSONL 路径（可观测 2.1），Langfuse 是增强路径。

2.6 liveness 与 readiness 必须分开 ​

/health 的签名是 def health(probe: str = "liveness")(:696-697)：同一个端点、两种语义，由 ?probe= 切换。

探针要回答的问题谁在意怎么办
liveness这个进程还活着吗？容器编排进程死了就重启它
readiness现在这一秒，它能真的回答用户吗？负载均衡 / 路由就绪 → 收流量；不就绪 → 先摘掉，别重启

有一句必须背下来的判据：

探针要验业务最依赖的那一次真实调用，不是「对象能构造出来」。

实现里就是这么做的：?probe=readiness 验真实回答所依赖的东西是否就绪(:133)，状态位 self.llm_ready: bool = False(:138) 在就绪时置 True(:331)、失效时置回 False(:334)。liveness 只需证明进程还在正常响应 HTTP。

合成一个探针会踩到具体的坑（事实清单有本机实测症状记录，:487 附近原注释指出 liveness 与 readiness 的区别正是为避免误判）：

  • 依赖没起好 → 探针失败 → 编排判定实例不健康 → 重启。
  • 重启解决不了问题：新实例的依赖同样没起好 → 继续失败 → 再重启。
  • 结果是 CrashLoopBackOff：一个本来只是「暂时答不了问题」的实例，被自己的探针反复杀掉，永远起不来。

另一种同样有害的做法是永远返回 200 的探针：编排以为一切正常，流量继续打进来，错误率 100% 却没有自愈动作。探针的价值不在「返回了什么」，而在它验的是不是真实依赖。

四、一次真实的请求走一遍 ​

用一条具体调用：POST /ask，正文 {"question": "我的订单怎么还没到"}。

#环节代码在干什么观察点
1进入@app.middleware("http")(:675) 建 trace_id 上下文后续所有 span 挂在这棵树上
2鉴权排在限流之前顺序见 2.4；实现细节见【待确认】

五、踩过的坑 / 做过的取舍 ​

现象根因处置教训
流式「看起来是流式」，实际是等生成完一次性吐出反代缓冲了响应（缺 X-Accel-Buffering: no）补齐三个 SSE 必需响应头流式不是「用了 SSE 类型」就成立，链路上每一层都要放行
按旧文档去装 sse-starlette，白多一个依赖FastAPI ≥0.135 已内置 fastapi.sse，keepalive 与帧格式都替你处理改用内置实现加依赖前先确认框架本身有没有内置
容器里崩溃时日志尾部丢失stdout 被缓冲ENV PYTHONUNBUFFERED=1（Dockerfile.api:36）容器日志的默认行为不是你想要的
探针把「依赖没起好」误判成「实例不健康」，实例被反复重启liveness 与 readiness 被合成一个信号拆开两个 ?probe=，readiness 验真实依赖探针要验业务最依赖的那一次真实调用
卷在重建镜像后突然不可写运行用户 uid 随机分配，挂载卷属主对不上useradd --uid 10001 yyhelp（:74）显式固定涉及挂载卷的 uid 必须固定

六、面试深挖：追问链 ​

Q1（表层）：你为什么把流式和非流式做成两个端点？

A：因为它们是两种协议，不是两种参数。/ask(:811) 一次性返回 JSON，/ask/stream(:824) 返回 SSE 帧流（_sse(event, data)(:887) 拼帧）。合成一个端点用参数切换，调用方就得在同一个响应上判断「这次是 JSON 还是事件流」——协议在运行期变得不确定，客户端反而更复杂。 追问（中层）：那两个端点会不会出现「同一句话答案不一致」？

A：结构上不会，因为两端点共用主干 answer_question(question, *, trace_obj=None, ...)(:458)。程序层拒答(:401)、LLM 前闸门(:442)、就绪检查(:533-535)、生成(:554) 全在主干里，各写一套才会出现两份偏差。 追问（深层）：共用一个函数，那流式是怎么「流」出来的？

A：主干产出完整结果，流式出口再用 _chunks(s, n)(:882) 切片、_sse(event, data)(:887) 逐帧发送——同源、不同出口。代价是首字延迟没做到「边生成边推」，这是当前实现的边界，不是「已经优化过」的卖点。

Q2（表层）：为什么用 SSE 而不是 WebSocket？

A：因为需求是单向的：服务端推、客户端只收。SSE 是普通 HTTP 请求，能直接复用已有的鉴权、限流、trace_id 中间件(:675)；WebSocket 需要一次协议升级，上面那些中间件的语义都要重新定义一遍。 追问（中层）：那 SSE 的工程细节你踩过哪些？

A：三个响应头是最常踩的——Cache-Control: no-cache 防中间层缓存、X-Accel-Buffering: no 防反代缓冲、Connection: keep-alive 维持长连接。少任何一个，用户看到的行为都会从「逐字出现」退化成「转圈之后一次性出现」。 追问（深层）：你怎么证明发出去的帧是对的？

A：靠一对自检：selftest()(:903) 造帧，_parse_sse(raw) -> list[dict](:1058) 解析回来。没有解析端自检的流式协议等于没有协议——你只能靠肉眼看浏览器，那不叫验证。

Q3（表层）：限流为什么要放在鉴权之后？

A：因为顺序反了，限流会变成拒绝服务放大器。先限流的话，攻击者不需要任何有效凭证就能把全局限流额度打到 0，合法用户随后全部 429。 追问（中层）：那限流本身的值是怎么定的？

A：RATE_LIMIT_PER_MIN = int(os.environ.get("YYHELP_RATE_LIMIT_PER_MIN", "60"))(:120)，默认 60 次/分钟，由 class RateLimiter(:345) 实现。另外还有一条关于并发的判据：并发上限是成本闸门——「并发 4 × 每条 2000 token，就是上界」（docstring :121）。频率和并发敞口是两件事，得分开设。 追问（深层）：你现在这个限流器，横向扩容时会出什么问题？

A：会退化成每实例独立计数——--workers 1（Dockerfile.api:97）让计数器是进程内状态，N 个实例就是 N × 60 次/分钟。这个边界必须主动讲清楚：单实例部署下它是准确的，扩容后它只是「每实例的自我保护」，要精确全局限流得引入共享存储。

Q4（表层）：liveness 和 readiness 你为什么要分开？

A：因为它们回答两个不同的问题：liveness 问「进程还活着吗」（失败 → 重启），readiness 问「现在这一秒它能真的回答用户吗」（失败 → 摘流量，不重启）。合成一个，就会出现「依赖没起好 → 探针失败 → 重启 → 依赖还是没起好」的循环。 追问（中层）：那 readiness 到底该验什么？

A：一句话判据：探针要验业务最依赖的那一次真实调用，不是「对象能构造出来」。 实现里 ?probe=readiness(:133) 验的是真实回答所依赖的东西，状态位 self.llm_ready(:138) 在就绪时置 True(:331)、失效时置回 False(:334)。 追问（深层）：反过来，一个永远返回 200 的探针有什么害处？

A：它让编排系统以为一切正常，流量继续打进来，错误率 100% 却没有任何自愈动作。探针的价值不在「返回了什么」，而在它验的是不是真实依赖——这与 可观测 里「降级必须可见」是同一条原则。

Q5（表层）：上线前你验到了哪一步？

A：能确证的是测试基线：pytest code/yyhelp_v2 -q = 36 passed in 79.73s，v1 基线 126 passed in 14.50s（引用 v1 基线必须带日期：审计日 125 passed，Day1 修 state.py 后 126 passed）。上线前端到端压测没做（台账里的 B2）。 追问（中层）：那你的验收判据是什么？

A：p95 延迟 < 3s、错误率 < 1%、无 5xx 激增。必须主动交代：模型单次实测 7.76s（deepseek-v4-pro，另有一个模型实测挂起），所以「p95 < 3s」当前不可能满足。判据写下来是一回事，按现状不成立是另一回事——我不会把「写了判据」讲成「达标了」。 追问（深层）：那你下一步准备怎么补？

A：三步。一把压测真跑起来，拿到 p95 与错误率的真实数字；二明确「3s」对应哪条路径（非流式与流式的延迟口径不同，不写口径的数字没有意义）；三先解决模型侧单次耗时——单次要 7.76s，压测只会证明这一点，而不是发现新问题。
