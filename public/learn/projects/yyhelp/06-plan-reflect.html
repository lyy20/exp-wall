计划与反思节点 ​

一句话：plan 怎么拆任务、什么时候拆，reflect 什么时候触发、为什么只能重试一次。

这一页要回答什么 ​

这两个节点是多智能体臂里最容易被面试官追着问的地方，因为它们的失败模式很具体：

  1. 「你的 plan 节点总是会拆任务吗？」——如果答「是」，接下来一定被问「那简单的问候语也走一次模型规划？成本谁出」。
  2. 「reflect 什么时候触发？重试几次？重试会不会绕过预算？」
  3. 「这两个节点在 single 臂里存在吗？」——这是验证你对自己的对照实验是否清楚的一道题。

读完这一页，你能答：plan 的策略闸（SIMPLE_MARKERS / MULTI_MARKERS / JOINERS）、PLAN_MIN_STEPS=2 / PLAN_MAX_STEPS=3 夹住的含义、source 三态、reflect 的四条触发谓词与两种策略、双重闸的设计理由，以及一条很值钱的教训——诊断输出必须报告实际路径。

一、它要解决什么问题 ​

1.1 一个「总是规划」的 plan 节点是净亏损 ​

规划的价值来自「一个请求需要多个专家接力、且顺序有讲究」。如果每一条输入都先花一次模型调用去排计划，那么：

  • 纯查询（「订单 1001 到哪了」）白花一次调用；
  • 计划本身还会变成一种约束：_with_rules 里有「与 plan 一致性」这条约束，一旦计划排错，后面的派发会被一个错误的计划锁住。

所以 plan 的第一件事不是「怎么拆」，而是「要不要拆」。decide_policy(state, *, mode="multi") -> PlanPolicy（plan.py:244）就是这道策略闸，它用三组标记词做判定：SIMPLE_MARKERS（:229）、MULTI_MARKERS（:235）、JOINERS（:241）。

1.2 反思是「给自己一次修正机会」，不是「自我对话」 ​

reflect 的定位很窄：上一次专家的执行出了问题，给它一次修正机会。它不负责「让 Agent 更聪明」，也不负责「多想想」——那类设计的问题是无法界定什么时候结束。所以它的设计里有两件必须说清的事：什么算「出了问题」，以及重试几次、会不会绕过预算。

二、方案与实现 ​

2.1 plan：一个策略闸 + 三条出口 ​

plan_decision(state, *, llm=None, ...)（plan.py:451）的整体形状是「先判要不要规划，再判谁来规划，最后校验」：

情况走哪条source 取值说明
complexity="simple"跳过规划——直接进入 supervisor，不产生模型调用
模型可用且需要规划_model_plan(state, *, llm)（:520）"model"真正调模型排计划
外部注入了计划校验注入内容"injected"评测或测试用的确定性计划
模型不可用/纯规则模式_rule_plan(state, *, note)（:490）规则兜底不依赖模型也能出计划

source 为什么要区分三态？ 因为「这个计划是怎么来的」决定了它的可信度与归因方式：模型出的计划可能不合理（需要 validate_plan 校验），注入的计划是确定的（用于评测），规则兜底的计划是保守的。如果只有一个 source="ok"，事后就无法回答「这道题的计划到底是模型排的，还是我兜底出来的」。

2.2 plan：拆到什么程度 ​

validate_plan(obj, *, source="model", ...)（plan.py:312）做校验，步数由两个常量夹住：

  • PLAN_MAX_STEPS=3（plan.py:132）
  • PLAN_MIN_STEPS=2（:135）
  • PLAN_CANDIDATE_EXPERTS（:138）限定计划里能出现的专家

为什么上限定 3？ 因为整条链路的派发配额 DISPATCH_LIMIT=2 —— 计划的上限必须小于等于执行层的上限，否则计划天然不可执行：模型排出 5 步，执行到第 2 步就被 dispatch_quota 强制 finalize，剩下的计划变成永远不执行的死信息，还会污染「计划完成度」这类指标。

为什么下限定 2？ 因为「一步就能做完的事」不该走规划（那就是 complexity="simple" 的路径）。PLAN_MIN_STEPS=2 的含义是：规划只用于真正的多步任务；如果模型排出一个 1 步计划，那说明这次规划的入口判断错了，不是计划本身有问题。

normalize_complexity(obj)（:291）负责把复杂度标签归一化——标签是要被下游读的字段，不能让模型自由发挥字符串。

辅助函数（都在 plan.py）：

函数行号用途
planned_dispatch_limit(state, *, mode="multi"):575按计划算这次能派几次
next_planned_expert(state):607计划里的下一个专家
current_step_target(state):627当前步的目标
is_planned_target(state, exit_name):638校验「这次派发是否符合计划」
plan_progress(state):666计划进度，供 trace 与自检读

2.3 reflect：四条触发谓词 ​

last_expert_record(state)（supervisor.py:705）取出上一次专家的执行记录，交给 detect_trigger(rec)（reflect.py:101）。四条触发（REFLECT_TRIGGER_NAMES，:79）：

触发名含义为什么它算「出了问题」
model_error模型调用异常回答不是模型给的，是错误码给的
tool_error工具调用失败该拿到的信息没拿到，答案缺依据
empty_answer答案为空用户拿到空字符串
no_progress没有推进与「没有 HANDOFF、没有新工具调用」同类

四条谓词的顺序即优先级，而且它们互斥。 「互斥」这一点很重要：如果两条同时成立、又没有优先级，detect_trigger 的返回值就不稳定，下游策略选择（retry_same 还是 switch_expert）就会抖动——同一个输入两次跑出不同行为，是 Agent 项目里最贵的一类 bug。

2.4 reflect：两种策略 + 双重闸 ​

检测到问题之后，plan_reflection(state)（reflect.py:179）决定怎么办，策略有两种（:87-88）：

  • retry_same：原专家重试——适用于 tool_error 这类「同一件事再来一次可能就成了」的情况；
  • switch_expert：换一个专家——适用于「这个专家根本干不了这件事」。

然后 reflect_patch(state, *, memory_store=None)（:317）把反思结果写进 state（reflections 用 add_records 追加），route_after_reflect(state)（:391）决定回 supervisor 还是收尾。

双重闸：

  1. REFLECT_MAX_RETRIES=1（state_v2.py:593）——最多重试一次；
  2. 共享预算——budget_exhausted_why_v2(budget, *, retry_count=0, ...)（:596）；
  3. 外加配额闸 dispatch_quota（supervisor.py:334）。

为什么重试次数要收进预算判定函数的签名？ §16 第 16 项的原话是：反思重试不能成为绕过预算的通道。如果重试是「预算体系旁边的另一个计数器」，就必然存在「步数没超、token 没超、但我重试了很多次」的组合，而这恰恰是预算体系要拦的东西。把 retry_count 收进签名，等于强制每一次预算判定都必须回答「这次重试算不算」。

为什么上限是 1 而不是 3？ 因为反思的收益曲线在第一轮就掉下来了：第一次重试是「换个方式再试一次」，第二次之后模型往往只是重复第一种失败方式。而每一次重试都真实消耗预算——在没有证据表明「第二次重试能救回更多题」之前，把它设成 1 是保守但可辩护的选择。这个数目前没有实测支撑（见第五节末「未实测」）。

2.5 hint 的注入方式 ​

反思结果怎么影响下一次执行？靠 _reflect_hint 这个 state 字段，注入点是：

  • render_reflect_hint(state, record=None)（reflect.py:268）生成提示文本；
  • apply_reflect_hint(msgs, state)（supervisor_core.py:266）把它插进 messages。

这里有两个真实踩到的坑，都关于**「改参数/原地改对象」**：

  • render_reflect_hint 后来加了 record 参数——参数改名/加参数之后必须 grep 残留变量，否则会留下调用点还在用旧名字（这次就是这么发现的）。
  • apply_*_hint 是原地修改 messages 的。所以自检里要断言「行为改变」时，必须先快照文本再比较——直接比较「修改前保存的那个列表对象」和「修改后的列表对象」比较的是同一个对象，断言恒真。

同理，memory 节点也有 apply_memory_hint(msgs, state)（supervisor_core.py:240）。两个 hint 的机制同构：state 里存事实，注入时由渲染函数决定怎么呈现。

2.6 什么时候被跳过 ​

  • plan 被跳过：complexity="simple" 时跳过规划（plan.py 的策略闸）。另外 single 臂根本没有 plan 节点——它只有 triage → expert_<出口> → finalize。
  • reflect 被跳过：① 没有命中四条触发谓词（正常路径）；② 已经重试过（retry_count 到 REFLECT_MAX_RETRIES=1）；③ 配额已用尽（dispatch_quota 判定到限）；④ single 臂根本没有 reflect 节点。

一个必须如实说的事实：两条臂都没跑过「真的触发反思」的路径。 eval 的 Gate-1 结果里，没有任何一条记录走完了「专家出错 → reflect → 重试」这个完整流程——reflect 的处理路径是靠自检覆盖的（假模型驱动），不是靠真实评测数据覆盖的。

还有一个更刺眼的实测分歧：复杂度判定在两条口径下差别极大——规则判定 simple 3 / multi 37（40 题），而实测 live 判定 simple 34 / multi 0（34 题）。规则认为 37 道题需要多步、真实运行里几乎全部被判为「一步搞定」。这个分歧本身就是一个待查项（见第五节末「未实测」）。

四、一次真实的请求走一遍 ​

输入：「我要退货，顺便问下运费怎么算」——一个天然跨 refund_flow 与 kb_faq 的请求。

  1. triage 把它落到某个出口（比如 refund_flow）。输入形态：字符串；输出：IntentResult → IntentOut | None + 原因。
  2. decide_policy：这类输入同时含事务词与知识词，很可能不满足「simple」——于是不跳过规划。
  3. _model_plan → 计划 JSON。经 validate_plan 与 normalize_complexity 之后，state["plan"] 是一个 list[dict]，长度 ∈ [2, 3]，里面的专家名必须来自 PLAN_CANDIDATE_EXPERTS；source="model"。
  4. supervisor 第 1 次派发：planned_dispatch_limit(state, mode="multi") 按计划算出可派次数；is_planned_target(state, exit_name) 校验这次派发是否落在计划上——这是 _with_rules 约束 C「与 plan 一致性」的判据。
  5. expert_refund_flow 执行：它只看得见 query_refund_policy 与 create_ticket。假设这次工具调用失败 → ExpertOutcome.termination 落成 tool_error。
  6. route_after_expert 命中失败信号 → 进 reflect。
  7. detect_trigger(rec) 返回 "tool_error"；plan_reflection 选 retry_same（同一个工具再试一次通常能过瞬时错误）；reflect_patch 把这条反思追加进 state["reflections"]，写 _reflect_hint，retry_count 变成 1。
  8. route_after_reflect：should_retry=True，且预算判定（budget_exhausted_why_v2(budget, retry_count=1)）认为还有余量 → 回 supervisor。
  9. 第 2 次执行：这次工具成功，专家回答末行输出 HANDOFF: kb_faq；dispatch_quota 此时 used=1 < 2，允许再派。
  10. expert_kb_faq 用 search_kb 回答运费问题，没有 HANDOFF。
  11. 收尾：route_after_expert → finalize → summarize(state)。两个专家的答案都留在 expert_outputs 里（merge_dict 合并），反思记录留在 reflections 里（add_records 追加）。

这条链路里最值得注意的一步是第 7 步：反思不直接改答案，它只往 state 里写「发生了什么、下次注意什么」。真正改变行为的是 _reflect_hint 被注入到下一次的 messages 里——反思是状态，不是动作。

五、踩过的坑 / 做过的取舍 ​

#现象根因怎么定位到的怎么修的教训
1--plan "订单 1001 到哪了" 打印「模型计划：complexity=simple source=model」，但一次模型调用都没发生标签写死成 print("模型计划：...")，描述的是「这条命令想走哪条路」，不是「实际走了哪条路」对照 source 字段的真实取值改成三态标签：策略闸（未调用模型） / 规则兜底（--no-model） / 模型诊断输出必须报告实际路径：一个会撒谎的诊断工具比没有诊断更糟
2自检断言「行为改变」时好时坏apply_*_hint 原地修改 messages；断言前后读到的是同一个列表对象断言里比较了对象身份而非内容先快照文本再比较自检里比较「对象」和比较「内容」是两件事
3调用点还在用旧参数名render_reflect_hint 加了 record 参数，但调用点没全改改名后 grep 残留变量补齐调用点参数改名要 grep 残留变量，语言本身不会替你检查
4断言 budget_exhausted 失败v1 budget_exhausted_why 返回的是不带前缀的 step_budget（前缀是在 run_react 里拼的）跑自检时值对不上断言照抄实现返回值，不照抄想象中的规范断言照抄实现返回值——照抄「我以为的规范」会把一个正确的实现判成错的
5建图后取节点边表报错LangGraph 的 edges 是对象不是元组自检里直接解包失败用 [(e.source, e.target) for e in g.get_graph().edges]读一个第三方对象之前先读它的定义

取舍一：为什么 plan 的步数上限是 3，而不是直接等于 DISPATCH_LIMIT=2？ 计划是「意图」，派发是「执行」。计划排 3 步而只执行 2 步，是可以解释的（第一步就把两件事一起办了）；但计划排 5 步而只能执行 2 步，是结构性不自洽。上限取 3 是给计划留一点余量，同时保证不会离执行上限太远。

取舍二：为什么反思要区分 retry_same 和 switch_expert？ 这两种失败的性质不同：tool_error 往往是瞬时的（同一件事再来一次就好），no_progress 则说明这个专家干不了这件事（再试还是不行）。用同一种策略处理两种问题，会让其中一半场景白花预算。

取舍三：为什么 reflections 用追加而不是覆盖？ 它和 handoff_log 同属「历史记录」类字段。反思记录的价值恰恰在于「这道题被反思了几次、每次的原因是什么」——覆盖掉就回答不了这个问题。

待核对与未实测（如实登记） ​

  • REFLECT_MAX_RETRIES=1 这个取值没有实测支撑。 想验证它，要跑的是一条对比实验：REFLECT_MAX_RETRIES ∈ {1, 2, 3} 在含有失败题的评测集上的「救回率 vs 额外预算」，判据是「救回率增益是否显著高于额外 token/墙钟成本」。当前评测集里没有走完完整反思路径的样本，所以这个实验还做不了。【待核对：反思路径的真实触发率与救回率】
  • 复杂度判定的口径分歧未查清。 规则判定 simple 3 / multi 37（40 题）vs 实测 live simple 34 / multi 0（34 题）。口径不同（一个是规则、一个是实跑），但差这么多说明至少有一边的判定逻辑或数据流有问题。要验证它就该跑：同一批 40 题，分别用 --no-model（走规则）与真模型各跑一遍 plan 节点，把 source 与 complexity 逐题打出来对账。【待核对：复杂度判定的分歧根因】
  • 两条臂都没跑过完整的「专家出错 → reflect → 重试 → 恢复」链路（真实评测数据层面），reflect 的覆盖来自自检的假模型驱动。

六、面试深挖：追问链 ​

Q：你的 plan 节点总是会拆任务吗？

不是。decide_policy 是一道策略闸，用 SIMPLE_MARKERS / MULTI_MARKERS / JOINERS 三组标记词判定复杂度，complexity="simple" 时跳过规划、不产生任何模型调用。真要规划时，步数被 PLAN_MIN_STEPS=2 和 PLAN_MAX_STEPS=3 夹住，计划里的专家只能从 PLAN_CANDIDATE_EXPERTS 里选。

那为什么上限是 3 而不是更多？因为执行层的派发配额 DISPATCH_LIMIT=2。计划的上限必须与执行层的上限自洽，否则模型排出 5 步、执行到第 2 步就被强制收尾，剩下 3 步是永远不执行的死信息。

那 source 为什么要分三态？「这个计划怎么来的」决定了它的可信度：模型排的要校验，注入的是确定的（用于评测），规则兜底的是保守的。只有一个 source="ok" 的话，事后没法回答「这道题的计划到底是模型排的还是兜底出来的」。

Q：reflect 什么时候触发？重试几次？

四条触发谓词：model_error、tool_error、empty_answer、no_progress，顺序即优先级且互斥。策略有两种：retry_same 与 switch_expert。重试上限 REFLECT_MAX_RETRIES=1，而且这个计数被收进 budget_exhausted_why_v2(budget, *, retry_count=0, ...) 的签名。

为什么重试次数要和预算绑在一起？因为不绑的话，反思就是一条绕过预算的通道：步数没超、token 没超，但我通过「重试」多跑了很多轮。把它收进签名，等于强制每次预算判定都要回答「这次重试算不算」。

那 1 次够吗？说实话：这个数没有实测支撑。 想验证要做 REFLECT_MAX_RETRIES ∈ {1,2,3} 在含失败题评测集上的「救回率 vs 额外成本」对比。当前评测集里没有走完完整反思路径的样本，所以这个实验还做不了——这是我在项目里明确标注的未实测项之一。

Q：为什么四条触发谓词必须互斥？

因为策略选择依赖触发名：retry_same 与 switch_expert 是针对不同性质的失败。如果两条谓词同时成立又没有优先级，detect_trigger 的返回值就不稳定，策略选择随之抖动——同一个输入两次跑出不同行为，是 Agent 项目里最贵的一类 bug，因为它不可复现。

那顺序是怎么定的？REFLECT_TRIGGER_NAMES 里的顺序就是优先级。model_error 最靠前，因为模型都没跑通的时候，「答案为空」是它的结果而不是独立问题——按结果触发会让根因被掩盖。

Q：反思是怎么改变下一次行为的？

它不直接改答案，而是往 state 里写事实：reflections 用 add_records 追加，_reflect_hint 存本次反思的提示，下次执行时由 render_reflect_hint 渲染、apply_reflect_hint 注入到 messages。反思是状态，不是动作。

为什么不做成「直接重写 prompt」？因为那样反思就变成了一次不可观测的副作用，事后没法回答「这道题被反思了几次、每次注入的是什么」。留在 state 里，它才是可观测、可回滚、可对比的。
