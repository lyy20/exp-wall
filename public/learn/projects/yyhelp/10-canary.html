灰度与模型路由 ​

一句话：灰度不是「按百分比分流」，而是「让同一类请求永远落同一边」——做不到粘性，回滚和评测都失去意义。

这一页要回答什么 ​

  • 「你怎么做灰度的？」——要求说出三类可灰度对象、YYHELP_ROUTE_CANARY_PCT、以及粘性分桶为什么是前提而不是优化。
  • 「两个模型怎么分的？」——要求说出 decide_model(state) 的路由依据是 plan 的 complexity，以及 MODEL_TIMEOUT_S = 30.0 / BUDGET_WARN_RATIO = 0.90 这两道闸门在哪一层。
  • 「路由帮你省了多少钱？」——这是本页最容易答崩的一问。要求说出「规则重推 3/40 simple」与「live 判定 34/34 simple」几乎完全相反，以及为什么结论是「路由收益上限恒 = 复杂题 token 份额」。
  • 「deepseek-flash 更便宜更快，为什么不用它？」——要求说出它在实测中挂起，以及「模型选型必须实测」这条判据。

读完这一页你应该能：说清灰度快照的三要素为什么缺一不可；说清「未定价不编数」与「非法 pct 回落到 0」这两条失败方向纪律；说清为什么先校准复杂度判定，再谈路由收益。

一、它要解决什么问题 ​

灰度要解决的是「不敢一次全量切」。但这句话背后有四个必须先答的问题，任何一个答不上，灰度就只是个开关：

问题答错的后果
灰度谁？（切流比例的载体是什么）只灰度模型、不灰度 prompt → 出问题时分不清是模型还是提示词
谁算「同一个请求」？同一个用户刷新两次落到两个模型 → 用户看到前后不一致的答案，且归因数据被污染
怎么知道现在跑的是哪个版本？trace 里只有结果、没有版本 → 事后无法复盘，无法回滚到指定版本
失败时往哪一边倒？非法配置直接放行 → 一次配置手误就是全量切换到未验证路径

模型路由则是另一个问题：不是所有问题都值得用最贵的模型。但「哪些问题简单」这件事本身就是个待校准的判断——本页最重要的发现就在这一点上（见 2.5）。

快照三要素（object_versions()，:106）：prompt 版本 / 索引版本 / 路由策略。

配套的 prompt 版本常量：PLAN_PROMPT_VERSION = "plan-v2"（graph/plan.py:408）、SUPERVISOR_PROMPT_VERSION = "supervisor-core-v2"（graph/supervisor_core.py:203）。纪律是：语义改动必须 +1，灰度快照会把版本写进 trace。

为什么要灰度 prompt，不只是灰度模型：一次「模型回答变差了」的事故，可能是模型换了，也可能是同一模型的 prompt 改了。如果灰度只覆盖模型维度，这两种原因在数据上长得一模一样——你会花很久去查一个根本没错的模型。 为什么版本号要「语义改动必须 +1」而不是「随便改」：版本号是 trace 里的唯一归因键。改了语义不加版本，等于把两组不同行为的数据标成同一组，那么事后复盘时这个维度的数据就废了。这条纪律的代价是「每次改 prompt 要动一行常量」，收益是「事故可归因」。 ⚠️ 一个定位细节（值得学）：stamp_route 是在服务层被调用的（eval/run_ab.py::run_one），不进图工厂。也就是说「打标」是消费者的动作，不是图的动作。这样离线 A/B 采集和线上服务能用同一套打标逻辑，而不需要图知道灰度这件事。

核心性质：同一个 query 稳定落进同一个桶，所以 assign_route_version(query, pct=p) 对同一个 query 永远返回同一个版本。

为什么必须粘性——三条理由，一条比一条重要：

  1. 用户体验：同一个问题刷新两次得到两个不同模型的答案，用户看到的是前后不一致。这在客服场景里是直接的产品缺陷。
  2. 评测可信：A/B 的前提是「同一批问题分别跑两个版本」。如果不粘性，一次对照里同一个 query 可能两边都跑过、也可能两边都没跑，配对检验的分母就烂了。
  3. ⭐ 回滚可预期：回滚的语义是「让新增流量回到旧路径」。若分桶不粘，回滚之后仍在飞行中的请求会跳到另一条路径上——你无法回答「回滚完成了吗」这个问题，因为没有任何时刻是稳定的。

分桶为什么按 query 而不是按 user_id：本项目是离线/评测驱动的灰度（eval/run_ab.py::run_one 传的就是 query），主键选 query 才能让离线复现与线上一致。这是一个可讨论的取舍：真实客服系统通常按 user_id 分桶更合理（同一用户的体验一致），本项目按 query 是因为它的第一消费者是评测管线。这条边界要主动说清，不能假装它是普适最优解。

2.3 失败方向：非法 pct 回落 0 ​

块 8 定下的四条判据里有两条直接关于失败方向：

#判据含义
①未定价不编数price_for_model(model) -> tuple[float|None, float|None]（:190）未定价返回 None，不填一个「大概」的数
②⭐ 灰度失败方向指向旧路径非法 pct 回落 0 = 全基线
③成本边界明示报成本时必须说清口径与边界
④旧格式缺 prompt/completion 拆分 → 绝对成本只报区间total 全按 in 价 = 下界／全按 out 价 = 上界

⭐ ②这条是本页最该背下来的一条设计原则：配置异常时，系统应该退回到「你最确信的那条路径」，而不是「最新那条」。 道理很直白：灰度分流是为了验证新路径，所以它的默认值是「不验证」——也就是 0%。如果非法 pct 被当成 100% 或抛异常中断，一次配置手误的后果就是全量切到未验证路径（或被一个手误打挂）。「回落到最保守的状态」是所有开关类配置的正确默认方向。 ④ 这条也值得单独学：只有 total_tokens、没有 prompt/completion 拆分时，不是不给结论，而是给区间：全按输入价算得下界，全按输出价算得上界。有边界的估计 > 没有数。

成本记账的其他符号：PRICE_ENV_IN = "YYHELP_PRICE_{model}_IN_PER_M"（:186）、PRICE_ENV_OUT（:187）、record_usage(...)（:211）、estimate_usd(model, prompt_tokens, completion_tokens) -> float|None（:240）、cost_report(budget) -> dict（:248，按模型维度拆分）、cost_compare_records(...)（:303，回放对比 / 比价）。

⭐ 还有一个很实用的符号：_PLAN_TRACE_RE = re.compile(r"\[plan\] complexity=(\w+)")（:287）、parse_plan_complexity_from_trace(trace_tail)（:290）—— 从 trace 里把「模型判出来的复杂度」抠回来。它的存在意义是区分「规则判的」与「模型判的」，而这正是 2.5 节能发现问题的手段。

结论（写进台账 B23）（原文）：「模型路由要先校准『复杂度判定』本身；判据不校准，路由只是把误判成本放大。收益上限恒 = 复杂题 token 份额。」

⭐ 这两句话是本页的核心判据，值得逐字理解：

  • 「判据不校准，路由只是把误判成本放大」：路由本身不产生任何信息，它只是把 plan 的判定转换成模型选择。所以 plan 判错的比例会被路由原样放大到成本上：判错成 simple 的复杂题会走便宜模型 → 答不好 → 反思重试 → 成本反而更高（重试本身也要钱）。
  • 「收益上限恒 = 复杂题 token 份额」：注意这个「恒」字。路由的省钱逻辑是「把简单题从贵模型挪到便宜模型」，所以它能省的最多就是「原本花在简单题上的那部分钱」。如果简单题只占 5.4% 的 token，那么无论路由多聪明，上限就是 5.4% 左右。这条上限与路由算法无关，是数据结构决定的。 可迁移形式：任何「按类型分流」的优化，先量目标类型的占比，再谈优化。占比 5%，再精妙的分类器也只值 5%。

⚠️ 这条为什么必须标「未验证」：上面的 live 判定只覆盖了 34 题（不是 40 题的全量），且样本是旧格式数据；台账把它登记为 B23（未核销）。所以正确的说法是：「实测观察到两个来源几乎相反」，而不是「规则路由无效」。

顺带一条工具教训：本仓库的 JSONL 不能用 PowerShell 解析 —— Get-Content | ConvertFrom-Json 必失败（GBK 控制台乱码 + 长 answer 刷爆 stderr）→ 解析 JSONL 一律用 Python。

2.6 ⚠️ deepseek-flash 在实测中挂起（B18） ​

实测环境事实（2026-10-02）：本机网关只有 flash 挂起，v4-pro 正常，7.76 s/次（来源：eval/run_ab.py:67；03-台账 B18）。

这件事的面试价值极高，因为它把一句正确的原则（「便宜快的模型先试」）和一次真实的观察（「它挂起了」）撞在了一起。要讲透的是三层：

第一层：默认值和实测结论是两件事。MODEL_SIMPLE_DEFAULT = "deepseek-flash" 是代码里的默认值，它表达的是设计意图（简单题用便宜模型）。而 B18 记录的是实测事实（本机网关下它挂起）。二者不矛盾：默认值定义「应该走哪」，环境事实定义「这台机器上现在能不能走」。

第二层：一个「更便宜更快」的模型挂起，说明选型必须实测。 「flash」这个词本身就是一种关于速度的假设。而实测给出的答案与词面含义相反：挂起的正是它，稳定的是那个「更重」的 v4-pro（7.76 s/次，有明确数字）。

可迁移判据：「模型选型必须实测」不是「跑个 benchmark」，而是「必须在你的部署环境里、用你的调用方式、跑通一次真实请求」。 原因在于：模型名的语义（flash / pro / turbo）是供应商的，而延迟、可用性、限流、网关行为是你的环境的。这两者之间没有任何契约。 这条与我上一页写的那条是同一个道理：transport_check.py「下午能跑通、晚上连续 3 次全红」，代码一行没改 → 验证结论必须带时间戳与环境，否则它会静默过期。

第三层：挂起与超时的关系（这才是工程点）。 挂起的唯一防线是 MODEL_TIMEOUT_S = 30.0（graph/agent.py:159）。没有它，一次挂起就是整个请求永不返回——这是比「答错」严重得多的事故类型。而 30 秒这个数量级是相对 7.76 s/次的实测留了约 4 倍余量：

（这个 3.9 倍是我按 P50 口径用 / 相除算出的比例，不是清单里的数字。）

为什么余量要留数倍而不是 1.5 倍：模型延迟的分布是右偏的（长尾），P50 与 P99 可以差好几倍。用 P50 的 1.5 倍做超时，会把大量正常的慢请求误杀成超时；而每一次误杀都会触发一次重试，重试又是一次真实调用。所以超时阈值的标定要看分位数，不是看均值。 ⚠️ 诚实边界：本项目没有 v4-pro 的 P99 数据，只有「7.76 s/次」这一个速度数字。所以我只能说「30.0 的绝对值和 3.9 倍余量是合理的」，不能说它经过分位数标定。这是一条应主动说明的未验证项。

⭐ 「演练」这个词是关键：回滚不是「把 pct 改回 0」，而是一次要被执行、被断言的过程。演练至少要回答三个问题：

  1. 改回 0 之后，新请求是不是全落 v1？（分流生效）
  2. 同一个 query 改回 0 之后是不是稳定落 v1？（粘性在回滚后仍然成立）
  3. 快照里能不能看出「这个请求发生在上线期还是回滚后」？（版本打标生效）

可迁移判据：任何「开关」都要有一条演练路径。 没演练过的回滚，和没有回滚的区别只是心理上的。这也解释了为什么第 1 组自检会和「粘性分流」写在一起 —— 粘性正是回滚语义成立的前提（见 2.2 第 3 条）。

另外注意第 4 组的措辞：「账本归并 + 未定价不编数」——「不编数」这件事是有断言的，不是口头约定。第 5 组「回放对比比价单调性」同理：比价函数的单调性（价格越高的模型，比价结果越大）被写成了断言。

四、一次真实的请求走一遍 ​

输入：一条待处理的 query，环境变量 YYHELP_ROUTE_CANARY_PCT 处于灰度期（示例取到非 0 值）。

步骤输入输出耗时 / 规模关键点
1环境变量canary_pct() 的整数值——非法值回落 0 = 全基线（失败方向指向旧路径）
2querysticky_bucket(query) 的桶号——同一 query 稳定同桶，这是回滚语义的前提
3桶号 + pctv1 或 v2——ROUTE_V1 / ROUTE_V2
4object_versions()快照三要素——prompt 版本 / 索引版本 / 路由策略
5state + query打好标的 state——在服务层调用，不进图工厂
6进图plan 节点产出 complexity——路由依据就在这里
7statedecide_model(state) 的模型名——deepseek-flash 或 deepseek-v4-pro
8一次模型调用模型响应v4-pro 实测 7.76 s/次上限由 MODEL_TIMEOUT_S = 30.0 兜住
9累计 token预算检查阈值 BUDGET_WARN_RATIO = 0.90留 10% 余量做降级收尾

第 8 步是唯一有实测数字的一步，也是唯一会挂住的一步。 B18 记录的就是这一步：flash 挂起、v4-pro 7.76 s/次。其余九步都不会失败——它们只是「决定」和「记录」。所以这个系统里唯一需要环境实测的地方，恰好就是它唯一会挂住的地方。

六、面试深挖：追问链 ​

第一条：灰度为什么必须粘性？

Q：你的灰度是怎么做的？

A：三个维度都能灰度：prompt 版本、索引版本、路由策略。开关是环境变量 YYHELP_ROUTE_CANARY_PCT（serve/routing.py:68），分流走 sticky_bucket(query)（:91）+ assign_route_version(query, *, pct=None)（:96），返回 v1 或 v2。每次请求都会用 object_versions()（:106）打一份快照三要素、用 stamp_route(state, query)（:128）写进 state 和 trace。

追问（中层）：sticky_bucket 这个「粘性」是必须的吗？直接随机分流会怎样？

A：必须。三条理由，一条比一条严重。① 用户体验：同一个问题刷新两次落到两个模型，答案前后不一致——在客服场景这是产品缺陷。② 评测可信：A/B 是配对检验，前提是「同一批问题分别跑两个版本」。不粘性的话，一次对照里同一个 query 可能两边都跑过、也可能两边都没跑，配对检验的分母就烂了。③ ⭐ 回滚可预期：回滚的语义是「新增流量回到旧路径」。若分桶不粘，回滚后仍在飞行中的请求会跳路径——你无法回答「回滚完成了吗」，因为没有任何时刻是稳定的。

追问（深层）：那你为什么按 query 分桶，不按 user_id？

A：这是有代价的取舍，不是普适最优解。本项目按 query 是因为它的第一消费者是评测管线——eval/run_ab.py::run_one 传的就是 query，按 query 分桶才能让离线复现与线上一致。但真实客服系统按 user_id 分桶通常更合理，因为「同一个用户前后看到不同模型」比「同一个问题被不同模型回答过」更伤体验。我把这条边界写清楚，是因为如果被问「你按什么分桶」，答「按 query」而说不出为什么，听起来就像没想过。

第二条：路由到底省了多少钱？

Q：两个模型路由之后，成本降了多少？

A：我给不出一个可信的降幅数字，而这本身就是结论。 我用 Gate-1 的 40 题 × 2 臂样本（multi 231,348 tokens / single 249,730 tokens）把「哪些题是 simple」用两种办法各判了一遍：规则重推（decide_policy 离线）判出 simple 3 / multi 37；live 判定（从 trace 里抠到 34 题）判出 simple 34 / multi 0——几乎完全相反。按规则算，简单题 token 份额只有 5.4%，比价约 0.973，几乎没收益；按 live 算比价 ≈ 0.50，但那个数字建立在「plan 判得对」这个前提上，而 R24（跨域、两个专家、17,034 tokens）已经被观察到被判成 simple。

追问（中层）：所以你的路由是没用的？

A：不是「没用」，是收益被一个更上游的问题卡住了。台账里我把结论写成 B23：「模型路由要先校准『复杂度判定』本身；判据不校准，路由只是把误判成本放大。」路由本身不产生任何信息——它只是把 plan 的判定翻译成模型选择。所以 plan 判错的比例会被原样放大到成本上，而且更糟：判错成 simple 的复杂题会走便宜模型 → 答不好 → 触发反思重试 → 重试本身也要钱。所以错误路由不是零收益，是负收益。

追问（深层）：那路由的理论上限是多少？

A：「收益上限恒 = 复杂题 token 份额」 —— 注意这个「恒」字。路由省钱的逻辑是「把简单题从贵模型挪到便宜模型」，所以它能省的最多就是「原本花在简单题上的钱」。如果简单题只占 5.4% 的 token，那么无论分类器多聪明，上限就在 5.4% 附近。这条上限与算法无关，是数据结构决定的。 我把这条推广成一句可迁移的判据：任何「按类型分流」的优化，先量目标类型的占比，再动手优化。占比 5%，再精妙的分类器也只值 5%。 顺便一句工程纪律：我这份样本是旧格式（只有 total_tokens、没有 prompt/completion 拆分），所以绝对成本我只报区间——全按输入价算下界、全按输出价算上界。

第三条：一个「更便宜更快」的模型，为什么最后没用它？

Q：你代码里默认简单题走 deepseek-flash，实际用上了吗？

A：它在实测中挂起。 环境事实是（实测 2026-10-02）：本机网关只有 flash 挂起，而 deepseek-v4-pro 正常，7.76 s/次。注意「挂起」不是「变慢」——是不返回。

追问（中层）：那你凭什么说「flash 更快」这个直觉是错的？

A：我不需要证明「flash 更慢」——我只需要指出**「flash」这个词表达的是供应商的语义假设，而不是我环境里的事实**。延迟、可用性、限流、网关行为全是部署环境的属性，模型名和它们之间没有任何契约。所以我得出的判据是：模型选型必须实测，而且「实测」的定义不是跑个公开 benchmark，而是「在你的部署环境里、用你的调用方式、跑通一次真实请求」。这一页最反讽的地方是：这个系统里唯一需要环境实测的一步，恰好就是它唯一会挂住的一步 —— 其余九步都只是「决定」和「记录」。

追问（深层）：挂起这件事，工程上怎么兜？

A：唯一防线是 MODEL_TIMEOUT_S = 30.0（graph/agent.py:159）。没有它，一次挂起就是整个请求永不返回——比「答错」严重得多的事故类型。30 秒相对 7.76 s/次 留了约 3.9 倍余量（这个倍数是我按 P50 口径相除算出的比例，不是清单里的数字）。为什么留数倍而不是 1.5 倍：模型延迟分布是右偏的，P50 和 P99 可以差好几倍，用 1.5 倍做超时会把大量正常的慢请求误杀成超时，而每次误杀都触发一次重试——重试又是一次真实调用。所以超时阈值要看分位数标定。⚠️ 但这里我必须诚实：本项目没有 v4-pro 的 P99 数据，只有「7.76 s/次」这一个速度数字，所以我说「30.0 和 3.9 倍余量是合理的」，不能说它经过了分位数标定。另外还有一道不同失败模式的闸门：BUDGET_WARN_RATIO = 0.90（:185），它在 90% 预算处告警，留 10% 余量做降级收尾——一个防挂死，一个防超支。

第四条：回滚演练到底在演什么？

Q：回滚怎么做？演练过吗？

A：selftest()（serve/routing.py:401）的第一组就是「粘性分流 + 回滚演练」。回滚不是「把 pct 改回 0」这一个动作，演练至少要回答三个问题：① 改回 0 后新请求是否全落 v1（分流生效）；② 同一 query 改回 0 之后是否仍然稳定落 v1（粘性在回滚后仍然成立）；③ 快照里能否看出「这个请求发生在上线期还是回滚后」（版本打标生效）。

追问（中层）：这三条里哪条最容易漏？

A：第 ③ 条。前两条只验「开关有效」，第 ③ 条验的是「事后可复盘」。如果没有版本戳，回滚之后你手里只有一堆「结果」，分不清哪些来自上线期、哪些来自回滚后——这时候你连「回滚有没有生效」都无法从数据上判断。所以我把 prompt 版本也纳进了可灰度对象，并且定了「语义改动必须 +1」的纪律：版本号是 trace 里唯一的归因键，不 +1 就等于把两组不同行为标成同一组，那个维度的数据当场作废。

追问（深层）：为什么打标放在服务层，不放图里？

A：因为 stamp_route 是在服务层被调用的（eval/run_ab.py::run_one），不进图工厂。这样做的收益是：离线 A/B 采集和线上服务共用同一套打标逻辑，而图本身不需要知道「灰度」这个概念存在。这符合这个项目的一条总纪律——被测的东西不该知道自己在被测。如果图里到处 if canary: ...，那测出来的就不再是「多智能体的效果」，而是「多智能体在灰度分支下的效果」。
