① 项目地图 ​

一句话：YYHelp 是一套电商客服多轮对话 Agent，v2 用「Supervisor + 5 专家串行编排」替换 v1 的单 Agent，并用配对盲测回答「多智能体到底值不值」。

这一页要回答什么 ​

  • 面试官会怎么问这一块：
    • 「你这个项目一句话是什么？解决谁的什么问题？」
    • 「18 页文档，你自己最想让我看哪一页？」
    • 「你还有一个 RAG 项目，为什么不合并成一个？」
  • 读完这一页应该能答上来什么：
    • 用 40 字说清项目定位，并说出它的工程量级（26 文件 / ≈ 9,957 行 / 最大单文件 1,827 行）。
    • 说清 18 页的阅读顺序，以及哪几页是面试加分核心（③ 演进史、⑤ 执行循环）。
    • 说清它与 RAG 项目的定位差异：一个是「检索质量」，一个是「编排决策质量」。

一、它要解决什么问题 ​

电商客服是最典型的「多轮 + 有状态 + 有副作用」场景：同一个用户会在一条会话里先问「我的订单到哪了」，再问「那能退吗」，再问「退货地址寄哪个」。这三句需要三种完全不同的能力（订单查询 / 退款政策检索 / 售后流程办理），而它们必须是同一条会话上下文里的同一个 Agent。

v1 的做法是：先做 NLU 意图识别，把 9 类意图映射到 5 个出口，然后让一个通用 Agent 拿着全量 5 个工具去 ReAct。这在小规模下能跑，但有两个结构性代价：

代价具体表现
工具越权面大一个只需要答 FAQ 的请求，模型手里也握着 create_ticket、query_logistics 这些写/查操作工具
system prompt 长通用人设要同时解释 5 个工具的适用场景，prompt 变长，成本与跑偏概率同时上升

v2 要回答的不是「能不能做得更好」，而是一个可被证伪的工程问题：把大菜单拆成窄菜单、把一次决策拆成 supervisor 多次决策，收益是否大于成本。

二、方案与实现 ​

2.1 一句话架构 ​

YYHelp v2 把 v1 的单 Agent 电商客服升级为 Supervisor + 5 专家串行编排（graph/supervisor.py），叠加长期记忆（graph/longterm.py）、主动反思（graph/reflect.py）、显式 plan（graph/plan.py）、灰度与模型路由（serve/routing.py），并用同一套出口定义 + 同一个 ReAct 内核的 mode="single" 作为对照臂（graph/supervisor_core.py::run_single），最后用任务级盲测裁判 + 配对检验 + Holm 校正 + 功效分析（eval/task_metrics.py）回答「多智能体到底值不值」。

最后一句的答案是：当前结论是「不切换」（否定性结论）。这是这套材料里最值钱的一条，详见 ③。

2.4 两条贯穿全项目的纪律 ​

这两条比任何单个技术点更像「面试可讲的东西」：

  1. 导入方向单向（graph/__init__.py）：yyhelp_v2.* 可以 import yyhelp.*（v1），v1 绝不 import yyhelp_v2.*。
    • 为什么：对照臂要求 v1 是冻结基线。README 原话是「A/B 对比的前提是基线不变」。
  2. 三条项目特有纪律（README.md）：
    • ① 自检必须被运行（防护力 = 被执行的断言数）；
    • ② A/B 两组除被测变量外全冻结；
    • ③ 不需要 LLM、不需要网络（每模块一个 --selftest）。

2.7 与 RAG 项目的定位差异（预告） ​

维度YYHelp 项目RAG 项目
回答的问题编排决策质量：谁处理、菜单多大、何时终止、多智能体值不值检索质量：切块、混合检索、RRF、精排、recall@k
核心变量mode="single" vs mode="multi" 的 4 行差异切块粒度、dense/sparse 权重、rerank 是否开启
评测主体任务级盲测裁判 + 配对检验（40 题 × 2 臂）检索指标（recall@k / MRR）与端到端正确率
交叉点v2 复用 v1 的检索层：yyhelp_v2 目录下没有 retrieve/ 和 kb/v1 的检索层细节归属 RAG 项目页

一句话：RAG 项目管「找不找得到」，YYHelp 管「找到了之后谁来用、用几个工具、什么时候停」。 两个项目的坑也基本不重叠——唯一重叠的一条是中文 BM25 静默失效，那条记在 RAG 侧。

六、面试深挖：追问链 ​

Q1（表层）：你的项目一句话是什么？

A：一套电商客服多轮对话 Agent。v1 是单 Agent + 全量 5 工具；v2 改成 Supervisor 调度 5 个各有 1–3 个工具白名单的专家，然后用同一套出口、同一个 ReAct 内核做 mode="single" 对照臂，用配对盲测判断这次重构值不值。最新一轮是 120 题 × 2 臂。

追问（中层）：那重构的结果是变好了吗？

A：没有，而且最新一轮是统计显著地更差。 完成率 multi 63.3% vs single 77.5%（−14.2pp，t p=0.00053，Holm 校正后仍显著 → REGRESSION）；每问墙钟 24.7s vs 17.3s（1.43×，p≈0）；只有 tokens 是省 12.5%（4,708 vs 5,379，p=0.00034 → IMPROVEMENT）。结论：不切换。 追问（深层）：这个结论是第几次拿到？

A：第四轮。 第一轮（40 题）拿到的是「完成率 100% vs 97.5%，不显著、墙钟 2.11× 显著更差」，我当时的表述是「不证」而不是「证否」。但那个数字是假的——做人工锚定抽样时查出三层根因：检索后端从来没接上（跑的是关键词替身）、向量路因环境变量指向空目录而静默降级、裁判 rubric 把「礼貌拒答」判成完成任务。修完之后完成率掉到 60-75%（这才是真实水平），再修生成层缺陷到 70%/70%「打平」，最后扩样到 120 题才显出显著差异。

所以这一页的价值不只是结论，是这条链条：① 自变量清单可枚举（两臂只有 4 行不同）；② 三层根因都有「怎么发现 + 怎么修 + 怎么防复发」；③ 防复发做成了代码闸门（preflight 三道 + 裁判锚定 5 题 + 参考事实注入）；④ 扩充样本量是因为功效分析算出来 n=40 的可检出边界是 ±14pp，不是为了让结论变显著。完整链条见 架构对比实验。

Q2（表层）：这项目多大？

A：v2 28 个文件、≈ 9,957 行，最大单文件 graph/supervisor.py 1,827 行；冻结的 v1 基线 104 个 py 文件 / 21,274 行。

追问（中层）：9,957 行里最多的是什么？

A：不是业务逻辑，是自检与断言。v2 有 16 个自检入口，v1 有 14 个，合计 30 条，全部由 test_selftests.py 用 subprocess 统一跑；longterm.py 一个模块的 selftest 就有 10 组。项目纪律里写死了「防护力 = 被执行的断言数」。 追问（深层）：断言多就等于质量好吗？

A：不等于，而且我踩过反例。v1 有 11 个 selftest 从来没被 pytest 执行过——state.py 的 budget_warnings 缺陷因此「红了不知道多久」。一个从不执行的断言，防护力与「没有断言」完全相同，但它会让你以为有防护，这比没有更危险。所以 v2 建了总闸，并且额外写了点名断言（test_mcp_selftest_is_registered）来防「把条目从清单里删掉导致少跑一个用例仍然全绿」。

Q3（表层）：你还有一个 RAG 项目，为什么不合成一个？

A：两者回答的是不同问题。RAG 项目问的是「检索质量」——切块、混合检索、RRF、精排、recall@k。YYHelp 问的是「编排决策质量」——一次请求该由谁处理、工具菜单该多大、什么时候终止、多智能体值不值。YYHelp v2 里检索层是直接复用 v1 的，yyhelp_v2 目录下没有 retrieve/ 和 kb/。

追问（中层）：那 YYHelp 里的检索有问题，算哪个项目的问题？

A：算 v1 的。有一条很典型：中文 BM25 静默失效——只写 enable_analyzer=True 会落到 default standard analyzer，sparse 路静默返回空、不报错。修法是 analyzer_params={"tokenizer":"jieba"} 加回归测试。这个坑属于检索层，我在 RAG 项目的页面里讲；在 YYHelp 里它的身份是「v2 为什么不动检索层」的理由。 追问（深层）：一个静默失效的检索路，你怎么知道它当时真的失效了？

A：靠症状的反常倒推。召回结果里 sparse 路贡献恒为空、融合后排序与纯 dense 路完全一致，这种「太干净」的表现就是信号。项目里留了 kb/sparse_diag.py 专门做这个诊断，回归断言在 kb/test_kb_retrieval.py:246。教训是：静默失败比报错失败危险，因为它不产生任何需要处理的异常。

Q4（表层）：为什么 v1 冻结、另起一个 v2 目录？

A：因为对照臂必须是不变的基线。README 写的理由是「A/B 对比的前提是基线不变」。所以 v2 放进 yyhelp_v2/，v1 目录只读；唯一的代码改动是 graph/state.py 的 budget_warnings 缺陷和一个 run_react 的签名补丁——两处都必须改，因为前者是红的自检，后者是会让实验结论失真的 bug。

追问（中层）：改基线不就破坏了「基线不变」吗？

A：所以我把改动逐条列出来并且说明为什么它不污染对比：budget_warnings 是让红着的自检变绿（修之前它根本没被执行，谈不上是基线行为）；run_react 加的是一个带默认值的可选形参，且 v1 全仓库 14 处调用都显式传了 llm=，这条分支从未被执行过。「基线不变」的准确含义是「被测行为不变」，不是「一个字节都不许动」，但这个区别必须自己讲清楚，不能等面试官问。 追问（深层）：那你怎么证明这两个改动真的没影响对照结果？

A：靠出口集合与内核的同源性做结构性检查：两臂的落点集合必须一致（single 复用 expert_agent_free 这个节点名），_VALID_EXITS 在 run_ab.py:424 独立校验；ReAct 内核是同一个 run_react，差异只在参数（prompt / 工具菜单 / 预算）。判据是「同一个语义只允许有一处实现」。这是能断言的，不是文字承诺。
