核心执行循环 ​

一句话：这一页讲清主图怎么转、靠什么停、state 每一轮怎么合。

这一页要回答什么 ​

面试官在 Agent 项目上最爱问的三个问题：

  1. 「你这个循环怎么保证不会转圈？」——这是 Agent 的一个经典崩溃点，答不出闸门的细节就等于没写过 Agent。
  2. 「它什么时候停？有几种停法？」——「答完了就停」是错的。
  3. 「多轮之间 state 怎么合并？为什么有的字段是覆盖、有的是追加？」

读完这一页，你能答：四道闸的参数与各自触发的终态、主图 9 条边里的两条回环边各自的闸、supervisor → expert → reflect 三种收尾组合的判据，以及 REDUCER_MATRIX 这套「字段与 reducer 唯一真源」的设计。

一、它要解决什么问题 ​

1.1 Agent 循环的三个失效模式 ​

第一，转圈不停。 工具调用失败之后，模型的本能是「再试一次」；再试一次还是失败，它还会想再试一次。步数闸能拦住它，但拦住的时候预算已经白烧掉了——所以「重复动作检测」必须是一道独立的闸，不能指望步数闸兜底。

第二，悄无声息地恶化。 这是比转圈更隐蔽的一种：循环没有超步数、每一次都以「正常拿到回答」结束，但它其实是擦着预算边过去的。v1 原来的 budget_exhausted_why() 只在硬停时给原因，所以所有 answered 都被当成「正常」——日志里一切正常，恶化过程完全不可见。v1 后来加了 budget_warnings（BUDGET_WARN_RATIO=0.90，graph/agent.py:164-188），但这个缺陷不是被测试发现的，v2 是靠总闸保证它被执行到。

第三，停下来但说不清为什么。 如果终态只有一个「结束」，那么「模型客户端不可用」和「答完了」在下游看起来一模一样。

1.2 「必须三态、必须显式、必须能说明原因」 ​

v1 graph/agent.py:50 的小节标题就是这么写的。落到代码里是一个 Termination 常量类（graph/agent.py:124-131）：

终态常量字面值触发点
ANSWERED"answered"正常拿到最终回答
STEP"budget_exhausted:step_budget"步数预算耗尽
TOKEN"budget_exhausted:token_budget"token 预算耗尽
WALL"budget_exhausted:wall_budget"墙钟预算耗尽
LOOP"loop_detected"相同 (tool, args) 第 2 次出现
MODEL_ERROR"model_error"模型调用异常
NO_TOOL"no_tool"模型既不给答案也不调工具

外加一个不是终态的哨兵值 "continue"（graph/agent.py:889）：循环判据只有一条——agent_termination == "continue" 就再来一步，否则结束。把所有终止原因的判断都收敛到 agent_termination 这一个字段上，这样下游不需要理解十种停止原因的语义，只需要读一个字段。

二、方案与实现 ​

2.1 四道闸 ​

防止转圈需要四道闸，缺一道都不行（graph/agent.py:53-60）：

闸参数触发后的终态为什么不能省
步数max_steps=6budget_exhausted + step_budget最硬的一道。没有它，模型可以永远调工具
tokenmax_tokens=12000budget_exhausted + token_budget单步就能烧掉几千 token；只限步数挡不住
墙钟max_wall_s=60budget_exhausted + wall_budget步数没超，但某次调用卡 30 秒 × 6 次 = 用户早走了
重复动作相同 (tool, args) 第 2 次loop_detected模型「再试一次」的本能；预算闸也能停，但会白烧掉剩余预算

max_wall_s=60 和 MODEL_TIMEOUT_S=30.0（graph/agent.py:159）是配套的：单次模型调用最多 30 秒，墙钟 60 秒——给两次机会，不是给六次。

为什么四道闸的终态都归到 budget_exhausted:<原因> 这一个前缀下？ 因为下游要区分的是「正常答完」与「没答完但停了」这两大类；具体是哪类预算耗尽的，是给人和诊断工具看的。前缀让「机器判据」稳定，「后缀」让「人类排查」有信息——两者不要混在一个字段语义里。

为什么「接近上限」不塞进 termination？ graph/agent.py:242-246 写了理由：termination 是单值的（这一次为什么停），而「是否接近过上限」是独立的另一个事实。塞进去会让它变成多值，下游所有 == "answered" 的判断都要改。所以 budget_warnings 与 termination 并列存在。

2.3 三类终止条件 ​

这一页最该背下来的一段：终止不是一个条件，而是三族条件。

第一族：预算耗尽。 dispatch_quota(state, *, mode="multi") -> tuple[int, int]（supervisor.py:334）在每次派发前算 (used, limit)，limit 来自 DISPATCH_LIMIT=2（:199）。到限就强制 finalize，source="quota"。这一族的关键动作是：配额必须写进 prompt。supervisor_system_prompt(*, used=0, limit=2)（supervisor_core.py:205）把「你已经派了 1 次，最多 2 次」直接告诉模型——能被事前告知的约束，不要只做事后拦截。事后拦截只能拦住结果，事前告知能让模型主动收敛。

第二族：反射重试上限。 REFLECT_MAX_RETRIES=1（state_v2.py:593）+ budget_exhausted_why_v2(budget, *, retry_count=0, ...)（:596）。这条设计的理由写在 §16 的第 16 项：反思重试不能成为绕过预算的通道。所以预算判定函数本身把 retry_count 收进签名——重试次数是预算判定的一部分，不是旁边的一个计数器。

第三族：专家交出控制权 / 不再需要回环。 route_after_expert（supervisor.py:717）看三件事：

  • 专家输出里有没有合法的 HANDOFF: <出口名>；
  • 配额还有没有剩；
  • 有没有命中四类失败信号。

三种组合分别指向：「有 HANDOFF 且配额未满」→ 回 supervisor 再派一次（跨域接力就是靠这条实现的）；「命中失败信号」→ 进 reflect；「其他」→ 直接 finalize。

为什么每一个回环边都要有自己的闸？ ADR-1 的判据是一句话：「每一个回环边都要有自己的闸。只在一侧检查，另一侧就是一个能绕过去的循环入口。」代码里这道双闸是：supervisor 侧的 dispatch_quota（步数/派发次数）+ 专家侧的 route_after_expert（HANDOFF 合法性）。少任何一侧，循环就能从另一边进去。

2.4 plan 节点的策略闸 ​

plan 不是无条件规划。decide_policy(state, *, mode="multi") -> PlanPolicy（plan.py:244）先做策略闸，依据是 SIMPLE_MARKERS（:229）/ MULTI_MARKERS（:235）/ JOINERS（:241）三组标记词。complexity="simple" 时跳过规划——一步能办完的事不值得开一次模型调用去排计划。

真要规划时，_model_plan(state, *, llm)（:520）出计划、validate_plan(obj, *, source="model", ...)（:312）校验，步数被 PLAN_MIN_STEPS=2（:135）/ PLAN_MAX_STEPS=3（:132）夹住，计划里的专家只能从 PLAN_CANDIDATE_EXPERTS（:138）里选。source 字段区分 "model" / "injected" / 规则兜底——这一步的形态是 list[dict]，写进 state["plan"]。

2.5 state schema 与 reducer ​

CSStateV2 继承 v1 的 CSState（v1 是 28 字段、其中 9 个带 reducer）并新增 14 个字段（state_v2.py:399-484）。字段与 reducer 的关系有唯一真源 REDUCER_MATRIX（:515），另外三个符号是它的查询接口：field_reducers（:544）、reduce_writes（:558）、以及 set_field(state, name, value) -> dict（:701）——set_field 按矩阵决定「直接写」还是「过 reducer」。

字段语义reducer
plan计划步骤列表覆盖（overwrite，:204）
current_step走到第几步覆盖
handoff_log转交留痕add_records（:228）
expert_outputs每个专家/轮次的输出merge_dict 合并
reflections反思记录add_records
memories_recalled本轮召回的记忆覆盖
retry_count重试次数覆盖
route_version / model_used / model路由与模型留痕覆盖
_next_expert / _memory_hint / _reflect_hint / _reflect_dispatch内部传递位覆盖

为什么 plan 是覆盖而 handoff_log 是追加？ 因为它们回答的问题不同：plan 回答「当前这张计划是什么」（旧计划必须被替换，否则下游读到两张计划），handoff_log 回答「都发生过哪些转交」（它是审计日志，任何一条被覆盖掉就丢失了证据）。reducer 不是风格问题，是语义问题：字段的语义决定了它是「当前值」还是「历史记录」。

一个反直觉的细节：OVERWRITE = None（state_v2.py:294）——「无 reducer」在 LangGraph 里就是默认的覆盖行为，用 None 显式表达出来是为了让 REDUCER_MATRIX 里每一行都有值，不留空白格。空白格最容易被人误读成「忘了写」。

2.6 run_react 与 iterate_react 的分工 ​

v2 不重写 ReAct 内核，而是复用 v1 graph/agent.py 的两个函数：run_react（:405）负责「跑一轮，返回结果」，iterate_react 负责「按 agent_termination 决定要不要再来一步」。两者分工的关键是：循环次数由 state 里的字段驱动，而不是由函数内的 while 局部变量驱动——这样中断、恢复、外部观测才可能做到。

这里有一个真实事故值得记住：v1 的 run_react 不传 llm= 时会抛 NameError: name 'state' is not defined，然后被 except Exception 吞成 termination="model_error"——伪装成「模型客户端不可用」。根因是函数体里写了 llm = _resolve_llm(state, llm)，但签名里没有 state 形参（state 只存在于 iterate_react 的作用域）。修法是给签名加 state: dict | None = None（向后兼容），回归测试是 test_run_react_without_llm_reports_model_error_not_nameerror（含红/绿对照）。

为什么这个 bug 能活这么久？ 因为 v1 全仓库 14 处调用都显式传了 llm=，这条分支从未被执行。它同时印证了另一条纪律：except Exception 把异常归一成「业务错误码」是有代价的——如果归一化用错了错误码，排查方向会被带偏整整一轮。

四、一次真实的请求走一遍 ​

输入：「订单 1001 到哪了，另外我想问下换货政策」（一个纯查询 + 一个领域知识问题，天然可能需要跨两个专家）。

  1. new_state_v2(query, mode="multi") → CSStateV2，14 个新字段取 _NEW_DEFAULTS（:632）的默认值。输入形态：一个字符串；输出形态：带 14 个新键的 dict。
  2. triage：classify(...) → IntentResult → validate_intent(raw) → IntentOut | None + 原因字符串；出口经 INTENT_TO_EXIT 落到 5 个出口之一。shape：(IntentOut | None, str)。
  3. plan：decide_policy 判定复杂度。含连接词（JOINERS）的这类输入很可能被判为 multi 需要规划；若 complexity="simple" 则直接跳过、不产生任何模型调用。规划成功时 state["plan"] = [{"expert": ..., "goal": ...}, ...]，步数 ∈ [2, 3]（PLAN_MIN_STEPS / PLAN_MAX_STEPS 夹住）。
  4. supervisor 第 1 次派发：dispatch_quota → (0, 2)；prompt 里已经写着「最多 2 次」。_model_decision 输出 {"next": ..., "reason": ..., "confidence": ...}，validate_decision 校验字段，_with_rules 上三重约束。注意约束 A 是去重：同一出口被重复派发会被拦成 source="dedup" 并直接 finalize。
  5. expert_order_ops 执行：run_expert 只给它 tools_for("order_ops") 的工具（1–3 个，比全量 5 个少），tools_visible 记进 ExpertOutcome.trace。它查完订单，回答末尾输出一行 HANDOFF: kb_faq。
  6. route_after_expert：解析出合法 HANDOFF、配额 used=1 < 2 → 回 supervisor。
  7. supervisor 第 2 次派发：dispatch_quota → (1, 2)；派 kb_faq。这次专家答完没有 HANDOFF。
  8. 收尾：route_after_expert 既没有 HANDOFF 也没有失败信号 → finalize → summarize(state) 从 expert_outputs 取两个专家的答案拼成最终答复。expert_outputs 用的是 merge_dict，所以两个专家的输出都在，没有互相覆盖。
  9. END，回给 API 层。

关键观察：整条链路里，budget.steps（分派次数）是单调递增的。这是 ADR-1「循环单向性」的实现方式——不是靠「记得别转回去」，而是靠一个只增不减的计数器 + 到限强制 finalize。

五、踩过的坑 / 做过的取舍 ​

#现象根因怎么定位到的怎么修的教训
1图能编译，请求一发就直接结束memory 节点有一条指向 __end__ 的边，被编译成替换主链路跑图时链路直接到 END删边，memory 只连 supervisor回环/收尾节点不能直连 END；reflect → __end__ 是同一族教训，已固化成 reflect.py 自检 [5]
2建图成功，运行时 KeyError: 'agent_memory'add_conditional_edges(source, path_fn, path_map) 第三参是「path_fn 返回值 → 目标节点」的映射表；首版让 route_by_exit 返回节点名却把 EXIT_TO_NODE 当 map 传（v1 graph/build.py:149-176）报错形态 During task with name 'triage' and id 'a06e0b0c-...'让返回值与 map 的键落在同一个命名空间装配错误必须靠运行图来验：能 import、能编译，纯函数单测测不出它
3不传 llm= 时报「模型客户端不可用」run_react 签名叫 _resolve_llm(state, llm) 但签名里没有 state 形参 → NameError 被 except Exception 吞成 termination="model_error"加了「不传 llm」的用例才暴露签名加 `state: dictNone = None`
4反思重试看起来能无限跑反思是绕过预算的通道看预算判定函数签名里没有重试次数budget_exhausted_why_v2(budget, *, retry_count=0, ...) 把重试收进预算判定，并设 REFLECT_MAX_RETRIES=1新加的回环必须重新过一遍预算判定，否则它就是一条绕过预算的路
5断言「行为改变」的自检时好时坏apply_*_hint 是原地修改 messages断言前后读的是同一个列表对象先快照文本再比较自检里比较「对象」和比较「内容」是两件事

取舍一：为什么不把重试次数做成独立于预算的计数器？ 那样「反思重试」就成了预算体系之外的第二套配额，两套配额之间必然出现「能绕过」的组合。把它收进 budget_exhausted_why_v2 的签名，等于强制每次预算判定都必须回答「这次重试算不算」。

取舍二：为什么 plan 用覆盖而不是追加？ 因为 plan 的语义是「当前计划」。追加会让下游读到多份互相冲突的计划，而且「哪份是当前的」要靠额外字段回答——能被一个字段表达的语义，不要靠字段之间的关系去推断。

取舍三：为什么不重写 ReAct 内核？ 「同一个语义（终止条件）只允许有一处实现」（§16 第 5 项）。两臂共用同一个 run_react，差异只在参数（prompt / 工具菜单 / 预算）。重写一份等于在对照实验里引入一个说不清的混淆项。

六、面试深挖：追问链 ​

Q：你的 Agent 循环怎么保证不转圈？

四道闸：步数 max_steps=6、token max_tokens=12000、墙钟 max_wall_s=60、重复动作（相同 (tool, args) 出现第 2 次判 loop_detected）。前三个触发后统一归到 budget_exhausted:<原因>，第四个单独归到 loop_detected。

为什么重复动作要单独一道闸？预算闸也能停下它，但那时剩余预算全被白烧了。重复动作检测的价值是在花掉预算之前就把「这条路径走不通」暴露出来——它的成本是一次哈希比较。

那「参数不同」的情况会不会误杀？不会，判据是 (tool, args) 一起比。自检里专门有一条「同工具不同参数（1001 / 1002）必须判 answered，否则是误杀」。

Q：它什么时候停？

三族条件。第一族预算耗尽：dispatch_quota 每次派发前算 (used, limit)，DISPATCH_LIMIT=2，到限强制 finalize 并标 source="quota"；而且这个数写在 prompt 里，让模型事前收敛而不是事后被拦。第二族反射重试上限：REFLECT_MAX_RETRIES=1，并且重试次数被收进 budget_exhausted_why_v2 的签名，防止反思变成绕过预算的通道。第三族专家交出控制权：route_after_expert 看有没有合法的 HANDOFF: <出口名>，没有就收尾。

那跨域问题怎么处理？不是 supervisor 一次派两个专家，而是一个专家在回答最后一行输出 HANDOFF: <出口名>，由它触发下一次派发。这是设计决定：一次派两个专家，两个答案谁负责收口、冲突谁裁决，都没有答案；串行接力则每一步都有一个明确的负责人。

Q：state 多轮之间怎么合？

字段和 reducer 的唯一真源是 REDUCER_MATRIX，set_field() 按它决定「直接写」还是「过 reducer」。plan、current_step 是覆盖，handoff_log、reflections 是 add_records 追加，expert_outputs 是 merge_dict 合并。

为什么不能统一用一种？因为字段语义不同：plan 是「当前值」，handoff_log 是「历史记录」。如果 handoff_log 也覆盖，第二次转交就会把第一次的证据抹掉，事后无法回答「这次会话总共转交过几次」。

那 OVERWRITE = None 是什么意思？在 LangGraph 里「无 reducer」就是默认覆盖；显式写成 None 是为了让 REDUCER_MATRIX 每行都有值，不留空白格——空白格最容易被读成「忘了写」。

Q：每一个回环边都要有自己的闸，为什么？

ADR-1 的原话是「只在一侧检查，另一侧就是一个能绕过去的循环入口」。代码里的双闸是 supervisor 侧的 dispatch_quota 加专家侧的 route_after_expert。

那「循环单向性」怎么保证？靠一个单调递增的计数器 budget.steps：它只增不减，到 DISPATCH_LIMIT 就强制 finalize。不依赖「记得不要转回去」这种约定。
