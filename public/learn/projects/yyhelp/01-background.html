② 背景与需求 ​

一句话：这一页说清 YYHelp 要解决谁的什么问题、需求边界划在哪里、以及哪些事情本项目故意不做。

这一页要回答什么 ​

  • 面试官会怎么问这一块：
    • 「为什么选电商客服这个场景？换个场景你的架构还成立吗？」
    • 「你的知识库和评测数据是哪来的？有真实用户吗？」
    • 「你说覆盖了 9 类意图，这 9 类的划分依据是什么？」
  • 读完这一页应该能答上来什么：
    • 说清客服场景的三个结构性难点（多轮指代 / 有副作用 / 政策类与事实类知识混用），并说明它们分别落在哪个模块。
    • 主动交代诚实边界：合成语料、无真实用户、评测集自标。
    • 说清需求书要求做的四件事，以及为什么「不做检索层」也是需求的一部分。

一、它要解决什么问题 ​

1.1 场景本身的三个结构性难点 ​

客服对话不是「一问一答」，它有三种麻烦叠在一起：

难点具体形态落地在哪个模块
多轮指代「那它什么时候到？」——"它"是上一句提到的订单号triage 复用 v1 的 nlu/intent.py 做指代消解 + 意图识别
有副作用退款、建工单是写操作，调两次和调一次结果不同v1 graph/tools.py 的幂等键 + 四道闸；MCP 侧刻意只暴露只读工具
两类知识混用「7 天无理由能不能退定制款」是政策事实（知识库）；「我上次说要用顺丰」是用户事实（记忆）知识库 = yyhelp_kb_v1；记忆 = yyhelp_memory_v1，物理隔离

第三行是这套系统里最容易被忽视、但最容易被面试官抓住的一点。有一条明确的设计判据：

不做「看到记忆就不再检索知识库」——记忆是用户事实、知识库是政策事实，冲突时必须两个都摆出来让下游发现矛盾；用记忆短路知识库 = 把幻觉升级成「有据可依的幻觉」。

1.2 不做这个会怎样（v1 的量化代价） ​

v1 已经能跑，所以 v2 的立项不能是「v1 不能用」，只能是「v1 的结构在某个方向上封顶」。可量化的那一面：

现象数字口径
工具菜单是全量的每专家可见 1–3 个 vs 单臂 5 个experts.py:140，工具全集 = V1_TOOL_NAMES（5 个，sorted）
每问 tokensmulti 4,708 vs single 5,379，省 12.5%120 题 × 2 臂配对，t p=0.00034 → IMPROVEMENT
每问墙钟multi 24.7s vs single 17.3s，1.43×同上 120 题，t p≈0 → REGRESSION
完成率multi 63.3% vs single 77.5%，−14.2pp同上 120 题，t p=0.00053、Holm 校正后显著 → REGRESSION
分派轮次37 题 1 轮 + 3 题 2 轮（均值 1.075）15-ADR-1

⚠️ 上表口径已于 2026-10-09 更新为最新一轮（120 题）。第一轮（40 题）的数字是 multi 5,783.7 vs single 6,243.3 tokens、20.9s vs 9.9s（2.11×）、完成率 40/40 vs 39/40，那一版已被证伪（检索后端未接入 + 裁判放水），完整四轮链条见 架构对比实验。

读法：tokens 确实省了 12.5%，但完成率低 14.2 个百分点、延迟高 43%——两个都是统计显著的回归。 所以「v1 结构封顶」这个判断在后来的 A/B 里没有得到支持，反而被显著否定。这一页只交代「为什么要立项」，「立完项结论是什么」在 ③。

1.3 需求书要求做的四件事 ​

v2 的施工依据是 output/项目六需求书-YYHelp v2.md。四件被点名的技术嵌入：

  1. 多智能体编排（需求书 §四 嵌入 1）：把单 Agent 升级为 Supervisor + 专家。
  2. 跨会话长期记忆（§四 嵌入 2）：验收判据是「跨两个独立会话」——同一件事在两个独立会话里被记住，才算数。
  3. 显式 plan（§四 嵌入 3）：complexity="simple" 时必须跳过规划——这是硬要求，不是优化。
  4. 反思不能是死代码（§八-5 原文点名：「只写 state 没人读 = 死代码」）。

第 3、4 条的共同特点是：它们规定了「什么时候不做」。这类需求比「要做什么」更难满足，因为不去实现它是没有症状的——所以每条都必须配一条可断言的证据（trace 里能看到 skip、reflect 的产物必须改变下一次调用）。

二、方案与实现 ​

2.1 需求边界：做什么 / 不做什么 ​

决定为什么
做编排层（supervisor / 专家 / plan / reflect）需求书点名，且这是本项目要回答的核心问题
做长期记忆需求书点名，验收判据是「跨两个独立会话」
做评测框架（配对盲测 + 统计检验）没有它，整个项目就只是「用了更多框架的客服系统」
做 MCP 作为第二种消费形态把 v1 的「判断」变成实测证据（v1 结论是「不引入 MCP」，依据只是需求书二手结论）
不做自己的检索层v1 冻结。yyhelp_v2 目录下没有 retrieve/ 和 kb/
不做自动记忆合并 / 总结见 ⑧。合并是「不可逆的信息损失」，在没有评测手段前不做
不用记忆短路知识库见 1.1 第三行
不改多智能体的默认开关结论是不切换，所以默认不启用并行化的下一步升级

2.3 技术选型总览（为什么选它 / 为什么不选另一个） ​

选择为什么选它为什么不选另一个
LangGraph 做编排图结构 = 可被断言的拓扑（reflect.py 的自检 [5 图可达性] 直接读 g.get_graph().edges）；条件边把「谁决定下一步」显式化手写 if-else 状态机：拓扑无法被断言，回环边没有闸就变成死循环
手搓 supervisor，不引入 langgraph_supervisor⚠️ 环境事实：langgraph_supervisor 未安装。三条理由：① create_react_agent 是薄封装 ② 重装一套 = 放弃已验收的可靠性资产 ③ 多一个依赖 = 多一个版本风险面直接装包：省事，但把「已验收的出口集合 + 同一个 ReAct 内核」这两个 A/B 前提交出去
MCP 作为第二种消费形态（2 个只读工具）一套工具多消费者复用、跨语言、权限可独立管控、工具可独立部署与升级原生 tool：零序列化开销、调试栈最浅、可被 checkpointer 序列化的边界最简单——两者不是替代关系，所以都做
SQLite 作长期记忆真相源（Milvus 可选）记忆是用户数据不是检索产物：知识库 chunk 丢了可以重切，用户说过「以后都用顺丰」丢了没有任何地方能重建直接用 Milvus 当真相源：向量索引是「从真相源重建的派生物」，可用性要求必须低于真相源
默认 use_milvus=False① 几百条规模下 SQLite 全表扫描 + 本地打分更快（省一次跨进程调用与一次 embed 网络往返）② 让 --selftest 真正离线 ③ Milvus 挂掉不影响主链路这条要求默认就满足默认开 Milvus：自检依赖外部服务，且是把可选依赖变成必需依赖
fastapi.sse.EventSourceResponseFastAPI ≥0.135 已内置，实测可用；不需要 sse-starletteStreamingResponse(media_type="text/event-stream") 是 v1 的做法，keepalive 与帧格式要自己管

上表最后一行有个前提值得单说：v1 用的是手写 SSE，v2 换成内置实现。「不装一个包」在这里是一个真实收益——少一个依赖就少一个版本风险面，而这个项目已经因为「依赖版本」吃过一次亏（见 ③ 的 MCP 那条）。

三、⚠️ 诚实边界（必须主动说，别等问） ​

这一段是这一页最重要的部分。主动交代边界不会减分，被追问出来才减分。

边界事实影响什么不影响什么
知识库是合成语料9 doc / 163 chunk，非真实电商政策库「检索质量」结论只在合成语料上成立，不能外推到真实业务语料编排层的结论（谁决策、何时停）与语料来源关系较弱
无真实用户没有线上流量，没有真实会话分布无法回答「真实用户的意图分布是否与我的 40 题一致」配对 A/B 是组内比较，不需要外部流量即可成立
评测集由本人标注40 题的 gt 来自自标存在标注者偏见；unanswerable 8 题的判定标准是我定的裁判是盲测的（temperature=0.0），且两臂同题比较，偏见对两臂方向一致
复杂度判定分歧很大规则判定 simple 3 / multi 37（40 题）；live 判定 simple 34 / multi 0（34 题）plan 的「跳过」逻辑在两套判定下行为差异极大这条本身就说明「复杂度判定未校准」，是已知缺口不是未知风险

与之对应，台账里把未实测项分成三档，其中 C 档是结构上不可验证——缺的是客观条件（真实用户、公网、多卡、账单），不是缺时间：

C 档：❌ 永远为「未实测」，除非那些条件被真正提供。缺的条件包括：公网地址 / 真实用户 / 价格表账单核对 / Milvus 集群 / 多卡 / 真实 QPS。

把「我做不到」和「我没时间做」分开写，是这套材料里我很看重的一点。逐条对应关系在台账原文里，本页不展开。

现象根因怎么定位到的怎么修的教训
中文 BM25 静默失效：sparse 路恒返回空，但不报错只写 enable_analyzer=True → 落到 default standard analyzer看召回结果「太干净」：融合后排序与纯 dense 完全一致analyzer_params={"tokenizer":"jieba"} + 回归测试（kb/test_kb_retrieval.py:246）静默失败比报错失败危险，它不产生需要处理的异常

六、面试深挖：追问链 ​

Q1（表层）：为什么不选一个更"AI"的场景，比如写作助手？

A：因为这个场景必须做对几件难事，而这些难度是天然的验收条件：① 多轮指代——「它」指什么，错了整条链路都错；② 有副作用——退款调用不能重复，逼出幂等键；③ 两类知识混用——政策事实和用户事实必须分开存。写作助手这三条一条都没有。

追问（中层）：那这三点你分别怎么验？

A：① 指代消解靠 triage 复用 v1 nlu，validate_intent 的存在理由写得很直白：「不做校验的后果：路由走到 INTENT_TO_EXIT[bad] → KeyError → 整个请求 500」。② 副作用靠工具层的幂等键，另外 MCP 侧刻意只暴露 2 个只读工具，写操作不暴露，并配负向断言。③ 两类知识分两个 collection：yyhelp_kb_v1 与 yyhelp_memory_v1，物理隔离。 追问（深层）：物理隔离是"好习惯"还是"有具体后果"？

A：有具体后果。如果放一起，会出现一个很难查的失效模式：政策 chunk 和用户记忆在同一个向量空间里按相似度竞争，某次召回里「用户偏好顺丰」压过了「7 天无理由政策」，于是答案变成一个看起来有依据、其实答错了的回复。而且这种错误不报错、不进异常列表，只能靠 trace 逐条看召回来源才能发现。隔离之后，两类东西的召回是可分别观测、可分别开关的。

Q2（表层）：你的评测数据可靠吗？

A：不可靠，我先把边界说清楚：知识库是合成语料（9 doc / 163 chunk）、没有真实用户、40 题的 ground truth 是我自己标注的。这三条决定了「检索质量」的结论不能外推到真实业务。

追问（中层）：那你的 A/B 结论还能信吗？

A：A/B 结论的强度与「语料是否真实」关系不大，因为它是配对比较：40 题同时喂给两臂，比较的是同一批题上的差异，外部效度的问题被组内设计消掉了一部分。而且我把统计口径全写出来了——t 检验、Wilcoxon、Holm 校正、效应量 dz=−0.89，都是可复核的。 追问（深层）：那这个 A/B 最大的弱点是什么？

A：有效样本量 n_eff = 1。两臂在 40 题上同对同错 39/40，只有 1 题有分歧。所以完成率的差异本质上只由 1 个数据点支撑，这比 p 值更能说明问题。功效分析也算过：要检出 +5pp 需要 76 题，+10pp 需要 17 题，+20pp 在 ψ=0.025、δ=0.025 下数学无解。我知道我的结论在哪个样本量上才站得住——这是这个项目里我最想让人看到的一点。

Q3（表层）：需求书要求做多智能体，但你的结论是不切换，这算没做完需求吗？

A：不算。需求书 §四 嵌入 1 要求的是「实现多智能体编排」，我做完了——supervisor、5 个专家、plan、reflect、memory 全部落地并且有自检。结论是另一回事：需求书没有规定结论必须是「多智能体更好」。项目里那句定性写得很明确，A/B 要回答的是「多智能体到底值不值」，当前答案是**「不切换」**。

追问（中层）：那你为什么不直接把多智能体删掉？

A：因为它现在是一个可被开启的形态，不是一个死代码。两个 mode 共用同一个 ReAct 内核与出口集合，切换成本是一次参数；MODE_REPORT（supervisor.py:1151）与 PARALLEL_UPGRADE_CRITERIA（:1174）记录了每种 mode 的形态与**「何时该升级到并行」的触发条件**。 追问（深层）：什么条件下你会改主意？

A：两条。① 跨域题占比上去——现在只有 3/40 = 7.5%，判据是 < 10% 就算低；跨域需要多次分派时，单 Agent 的「一次决策定生死」才会真正暴露。② 数据规模上去——现在 37/40 的题 1 轮就结束（均值 1.075），多智能体的价值在「需要多步」的任务上，而我的题集里这种题不够多。这两条都是可观测的指标，不是我事后找的借口。
