检索层 ​

一句话：这一页要讲的不是「怎么搭一个混合检索」，而是「混合检索里哪些失败是不报错的」——中文 BM25 静默返回空、跨路分数不可比、表格被切散，三件事都不会抛异常。

这一页要回答什么 ​

  • 「你用的是 Milvus 还是 ES？为什么？」——要求说清「一个 collection 里同时放 dense 与 sparse」这个选择的代价，而不是只报一个产品名。
  • 「混合检索你怎么融合两路？」——要求说出 RRF 用 rank 不用 score 的原因，以及那条实测为负的 BM25 分数。
  • 「中文检索有什么坑？」——要求说出「只写 enable_analyzer=True 会静默返回空、不报错」，以及回归测试写在哪。
  • 「知识库怎么切的？」——要求说清「为什么表格不能被拆散」「为什么每块都带 heading_path」。

读完这一页你应该能：说清 dual-write 与 server-side hybrid 的区别；说清 sparse 字段为什么不能由客户端写入；说清切块的三个约束不是「最佳实践」而是被断言卡住的验收项。

一、它要解决什么问题 ​

客服知识库里的问题天然分两类：

问题类型例子靠什么召回
语义类「东西没收到怎么办」dense 向量：字面不重合但语义接近
字面类「999 丹的订单」「新疆」「满 99 包邮」sparse（BM25）：数字、地名、专有名词，语义模型容易糊掉

只用 dense：满 99 包邮 和 满 199 包邮 在向量空间里几乎重合，但业务上差一个量级。 只用 sparse：用户说「没收到货」，知识库写「物流延误」，字面零重合，直接漏召回。

所以必须两路都上、再融合。而要讲清这页的技术含量，得先立三个不报错的失败模式：

  1. 中文 BM25 静默失效 —— 稀疏路返回空列表，search() 正常返回、没异常、没 warning。
  2. 跨路分数不可比 —— BM25 分实测是负值（如 -0.6633），RRF 混合路是 0.03 量级。谁要是写 dense_score + sparse_score，得到的是一堆噪声。
  3. 切块把表格切散 —— 表头在一块的末尾、数据行在下一块的开头，检索命中了「半张表」，模型只能看到 | 地区 | 运费 | 而没有数据行。

这三条的共性：它们都不产生异常。所以它们不会出现在报错日志里，只会出现在「答得不对」的结果里。

为什么这样选：融合放在服务端，而不是客户端拉两路结果自己合。 客户端融合意味着两次网络往返 + 两次 limit 传输，而且两路各自的 limit 必须手动对齐才能保证融合公平。服务端 hybrid_search 一次往返、一套 limit 语义。 为什么不选「双库双路」（dense 存 Milvus、sparse 存 Elasticsearch）：那是最常见的工业做法，但代价是两条索引链路、两套一致性保证、两个健康检查、两份分词配置。本项目 KB 规模只有 163 chunk / 9 doc（实测，data/yyhelp/kb/chunks.jsonl，93,656 B），为了这个规模引入第二个存储引擎，运维复杂度是纯负债。规模决定架构，不是反过来。

配置侧：RRF_K = int(_env("YYHELP_RRF_K", "60"))（config.py:176）—— 可覆盖，默认取原论文推荐值 60。

⚠️ 代码注释里记了一条跨实现差异：retrieve/hybrid.py:85 附近记录「但 Qdrant 默认是 2 —— 不同实现不一致」。这条的价值在于：k 是 RRF 的唯一超参，而不同向量库的默认值差 30 倍。如果直接把 Qdrant 的参数搬到 Milvus（或反之），融合排序会变，而不会有任何报错。这正是「默认值也是一种接口契约」的实例。

RRF 的形式是 score = Σ 1/(k + rank_i)，只用名次。请看下一节的实测数字，就知道为什么不能用分数。

2.4 ⭐ 跨路分数不可比（实测记录） ​

retrieve/hybrid.py:353-356 的实测记录：

路实测分数量纲
dense相似度（metric_type="IP"）与其他路不可比
sparse（BM25）负值，如 -0.6633BM25 的 IDF 项在语料里可正可负
hybrid（RRF）≈ 0.03 量级1/(k+rank) 的和，k=60 时天然是小数

原文判据：「跨路比分数是没有意义的，只能比名次 —— 这正是 RRF 用 rank 不用 score 的原因。任何时候都不许写 dense_score + sparse_score 这种融合。」（retrieve/hybrid.py:353-356）

这条为什么值得单独占一节：混合检索最容易被随手写错的实现就是「加权分数和」：

python
# ❌ 错误的融合：两路分数量纲完全不同
final = 0.7 * dense_score + 0.3 * sparse_score
1
2

它的危险在于能跑、能返回结果、看起来还有排序。但因为 BM25 分是负数、RRF 是 0.03 量级，0.3 * (-0.6633) 会把排在后面的稀疏命中拖成负分，于是「加权」实际变成了「谁的分数量级大谁说话」。要发现它，只能靠把两路分数分布打出来看——也就是 2.4 这张表。

更进一步的推论：任何跨路分数都不可加，所以阈值也只能挂在单路分数上。精排（下一节）之所以能设阈值，是因为它输出的是同一模型对每一对的打分，同量纲。

2.5 ⭐ 中文 BM25 静默失效：表现、根因、修法与回归 ​

表现（retrieve/hybrid.py:19-23 与 kb/milvus_lite_probe.py:108-110 记录）：

「text 字段必须显式配 jieba analyzer。实测（见 kb/sparse_diag.py）：只写 enable_analyzer=True 时，默认 analyzer 是 standard，中文被当成整句 → 稀疏路静默返回空（不报错）」

拆开说清这条链路：

  1. enable_analyzer=True 只是打开分析器，用的还是 default = standard analyzer；
  2. standard analyzer 对中文不做分词，把「运费怎么算」当成一个 token；
  3. 查询侧同样被切成「运费怎么算」这一个 token，与文档里那一个 token 的实际拼写必然对不上（文档里是一整段正文）；
  4. 于是 search(..., anns_field="sparse") 返回 空列表 —— len(results) == 0，results 本身是合法返回值，没有任何异常。

修法一行：analyzer_params={"tokenizer":"jieba"}（retrieve/hybrid.py:147-148）。

怎么定位到的：专门写了对照诊断脚本 kb/sparse_diag.py（94 行）：

  • build(client, name, with_analyzer, Function, FunctionType, ...)（:38）—— 建两个 collection，一个带 analyzer、一个不带；
  • try_search(client, name, query) -> tuple[str, list, str]（:69）—— 同一个 query 打两边，比对返回。

这是一次受控变量实验：唯一的自变量是 analyzer 配置，其他全同。所以「sparse 路为空」这个结论不会被别的因素污染。

修完必须留断言，否则它会退化回去：

  • kb/test_kb_retrieval.py:246 —— test_sparse_path_actually_uses_chinese_tokenizer：把「中文分词真的生效」写成回归测试；
  • 同文件另有 test_recall_at_k_empty_gt_is_nan_not_zero（:165）、test_four_paths_all_return_results（:231）、test_trace_snapshot_has_fields_required_by_flywheel（:259）、test_evaluate_respects_answerable_flag（:280）。

test_recall_at_k_empty_gt_is_nan_not_zero 那条值得单独点：没有 gt 的题，recall 必须是 NaN 而不是 0。因为 0 会把「没标注」算成「没召回」，直接把指标拉低——这和 RAG 项目页里「『不适用』和『0』是两件事」是同一类错误。

2.7 知识库侧：切块是结构感知的 ​

⚠️ 同 2.1：v2 无自己的切块代码，复用 v1 的 kb/chunk_md.py（440 行）。

从符号与断言可确证的三条策略（kb/chunk_md.py）：

策略证据符号行
按 Markdown 块切（标题层级驱动）_split_blocks(md_text)、chunk_markdown(md_text, doc, ...):148、:260

过长表格按上限打包_pack_table(lines, max_chars):236

为什么表格必须整张（或按行）留在同一块里：运费、退款时效这类客服知识几乎全在表格里。表头 | 地区 | 首重 | 续重 | 与数据行 | 新疆 | 25 | 12 | 分属两块时，被召回的可能是一张没有列名的表。模型看到的是一堆数字，于是要么猜、要么拒答。而切块是在索引期一次性做完的，这个错误不会在查询期暴露成异常——只会表现为「答案缺斤少两」。 为什么每块必须带 heading_path：02-退换货政策 里的「7 天」和 03-退款时效 里的「7 天」是两个不同概念。没有标题路径，模型无法知道这条规则属于哪一节；带上 02-退换货政策 > 无理由退货 > 时效，引用才可核对。 为什么不做定长切块（如固定 512 字符带重叠）：定长切块实现最简单、块长最均匀，但它会把表格切断、把标题和它的正文分开。对 FAQ 型语料，结构信息的价值高于块长均匀性。

实际语料与切块结果（本次实测）：

自检里两条最关键的断言：

这组字段的设计意图：query_used 与 query 同时记录 —— 说明「喂给检索的 query 可能是改写过的」，原始 query 与检索用 query 必须分开留痕，否则离线重放会对不上。rrf_k 与 rerank_model 进 trace —— 让融合参数与精排模型版本随每次检索一起落盘，这是「结论能追溯到配置」的最小必要信息。

另有一套独立指标在 eval/metrics.py（331 行）：recall_macro_one(:71)、hit_at_k_one(:92)、reciprocal_rank(:105)、dcg_at_k_one(:121)、ndcg_at_k_one(:147)、aggregate_micro(:185)、evaluate_run(run, k)(:206)、report_checklist(missing=())(:281)。

⚠️ 两套指标并存是事实，不是笔误：retrieve/hybrid.py 内的是检索器自带（跑得快、够用），eval/metrics.py 是评测侧（多了 nDCG、micro 聚合、清单校验）。面试里如果被问「你的 recall 是怎么算的」，必须说清是哪一套的哪一种口径（macro 还是 micro、分母是全部题还是 answerable 题）。这也正是事实清单要求「报数必带口径」的原因。

2.9 ⭐ 为什么 v2 不再实现一遍检索层 ​

yyhelp_v2 目录下没有 retrieve/ 与 kb/。这不是遗漏，是纪律：

理由说明
对照臂要求基线不变A/B 对比的前提是基线不变（README.md）。如果 v2 顺手改了检索层，mode="single" vs mode="multi" 的差异里就混进了检索差异，「多智能体值不值」这个问题就不可答了
被测变量要可枚举两臂的差异被压缩到「只有 4 行不同」，检索层同源是前提
成本重写一遍检索层不会产生任何新结论，只会产生新的不确定性

代价也必须说清：检索层的缺陷会原样继承。实测缺陷 B25：R06 的正确答案就在 KB 里（05-支付与发票#0005：普通订单 15 分钟自动取消），但两臂都检索失败 → 于是有一个必须写进结论的边界：

「完成率指标受检索层约束，架构对比结论不能外推到检索修复后。」（16-ADR-3 相关口径）

这句话应该在面试里主动说出来。它证明的不是「我的检索有问题」，而是「我知道我的结论在什么条件下才成立」。

四、一次真实的检索走一遍 ​

输入：一条已经过 triage 改写的问题（KB 规模：163 chunk / 9 doc）。

步骤输入输出关键点
1用户原话query + query_used（改写后）两个都进 trace，离线重放要用改写后那句
2query_useddense query 向量Embedding 模型的产物
3query_used 原文sparse 查询 token 序列分词在服务端做，用 text 字段的 jieba analyzer
4两个 AnnSearchRequestdense 候选 + sparse 候选sparse 请求带 param={"metric_type":"BM25"}、limit=self.candidates
5两路候选融合候选（source="hybrid"）RRFRanker(k=60)；分数约 0.03 量级
6融合候选每条带 rerank_scoresource="rerank"；只有这一步的分数能设阈值
7精排后列表前 N 条 Hit每条带 dense_rank / sparse_rank / rerank_score
8Hit 列表trace 快照给下游飞轮做归因（RetrievalTrace 字段见 2.8）

第 5 步是这页的核心。 如果第 3 步的 jieba 配置缺失，整条 pipeline 不会报错：第 4 步的 sparse 请求会返回空列表，第 5 步的融合退化成「纯 dense 排序 + RRF 给了个固定名次」，第 6、7 步照常输出。整条链路看起来完全健康。

五、踩过的坑 / 做过的取舍 ​

现象根因怎么定位到的怎么修的教训
稀疏路静默返回空，无任何异常只写 enable_analyzer=True → 落到 default standard analyzer → 中文被当成整句、不切词写 kb/sparse_diag.py 做对照实验：建两个 collection（带/不带分析器），同一 query 打两边analyzer_params={"tokenizer":"jieba"}（retrieve/hybrid.py:147-148），并在 kb/test_kb_retrieval.py:246 写回归测静默失败比报错失败危险：它不产生需要处理的异常，只会让你以为「检索就是这样」
想自己传 sparse 向量，报字段冲突sparse 是 is_function_output —— 由服务端的 BM25 Function 生成读 schema 定义（retrieve/hybrid.py:150/155-156）只传 text，让服务端算字段的「谁写」属性是 schema 的一部分，不是使用细节
融合分与 dense 分混着比BM25 分实测为负（-0.6633），RRF 约 0.03，dense 是 IP 相似度——三者量纲不同把三路分数分布打出来看（:353-356 的实测记录）融合只用 rank（RRF）；阈值只挂在单路（精排）分数上跨路比分数没有意义；任何 dense_score + sparse_score 都是错的
换向量库后融合排序变了，但没报错RRF 的 k 在不同实现里默认值不同（hybrid.py:85 注释记「Qdrant 默认 2」）对照两边文档 + 打排序结果参数显式化：RRF_K = int(_env("YYHELP_RRF_K", "60"))（config.py:176）默认值也是接口契约；跨实现迁移必须显式传参
表格类知识召回后答案缺数据行切块把表头与数据行分到了两块实测语料切块结果，检查 kind 与 heading_path_is_table + _pack_table 保证表格不拆散（kb/chunk_md.py:229/236）索引期犯的错不会在查询期报错，只会表现为答案不完整
v2 想顺手优化检索，被拦下对照臂要求基线不变README.md 纪律「A/B 对比的前提是基线不变」v2 目录下不建 retrieve/、kb/结论的可解释性优先于单点收益；代价是缺陷继承（见 B25）

六、面试深挖：追问链 ​

第一条：为什么单库双路，不拆成两个库？

Q：你的混合检索是怎么部署的？Milvus 还是 ES？

A：单库双路。一个 Milvus collection 里同时放 dense（FLOAT_VECTOR，AUTOINDEX + IP）与 sparse（SPARSE_FLOAT_VECTOR，SPARSE_INVERTED_INDEX + BM25），两个 AnnSearchRequest 交给服务端 hybrid_search 配 RRFRanker(k=60) 融合。融合在服务端一次往返完成，客户端不拉两路。

追问（中层）：业务上更常见的是向量库 + ES 各管一路，你为什么不分？

A：因为规模撑不起第二个引擎。我的 KB 是 163 chunk / 9 doc（实测 data/yyhelp/kb/chunks.jsonl，93,656 B）。拆成两个库，我要多维护：两条索引写入链路、两套一致性保证、两个健康检查、两份分词配置——而且两边的分词配置必须对齐，否则同一个「新疆」在两边切法不同，融合就是在合两种不同的东西。单库的代价是被 Milvus 的版本约束绑住：内置 BM25 要 2.5.0+、Function API 要 2.6.x，环境实测 pymilvus 3.0.2 / milvus-lite 3.2.1。这个代价我认，因为它是一次性的，而双库的运维代价是持续性的。

追问（深层）：那如果 KB 涨到 100 万 chunk 呢？

A：这个规模下我会重新评估，但判据不是「哪个更快」，而是「哪条链路的瓶颈真的出现了」。要看的第一个指标是稀疏路的延迟与内存：BM25 的倒排索引在 163 chunk 上完全无感，在百万级上就成了主要成本项，而我这套代码里没有任何百万级的压测数据——所以我不会给数字，我会说这是待实测项（对应实验：在 100 万 chunk 语料上分别测 sparse-only 与 dense-only 的 P50 / P99 与内存占用，再决定是否分库）。现在能说的是：分布式化的第一选择不是拆存储，是给 Milvus 加副本与分片。

第二条：中文 BM25 为什么会静默失效？

Q：中文检索你踩过什么坑？

A：稀疏路静默返回空。只写 enable_analyzer=True 时，分析器是 default 的 standard analyzer，对中文不切词——把「运费怎么算」当成一个 token。查询侧切出来也是这一个 token，与文档里的整段正文对不上，于是 search() 返回空列表。它不报错，不抛异常，不写 warning，len(results) == 0 是一个完全合法的返回值。

追问（中层）：那你怎么发现的？常规测试会漏掉吗？

A：常规「返回不为空」的测试不会漏，但常规开发会漏——因为纯 dense 路一直在正常工作，答案看起来也还行，只是稀疏路的贡献恒为 0。我是专门写了一个对照实验才发现并确认的：kb/sparse_diag.py 建两个 collection，唯一自变量是 analyzer_params，同一个 query 打两边比返回（build(...) 在 :38，try_search(...) 在 :69）。修法是 analyzer_params={"tokenizer":"jieba"}（retrieve/hybrid.py:147-148），并且写了回归测试 kb/test_kb_retrieval.py:246——断言的名字就叫「sparse 路真的用了中文分词器」，防止某次重构把它改回去。

追问（深层）：为什么这个 bug 特别值得讲？

A：因为它是一个**「零信号失败」。工程的直觉是「出错了会有异常」，但这个 bug 的每一条链路都合法：schema 建成功、insert 成功、search 返回成功、融合成功。它的唯一症状是排序质量下降**，而排序质量下降在没有 ground truth 对照时是看不出来的。所以它逼出的两条纪律是：① 对「静默降级」要专门设计对照实验，不能靠报错来发现问题；② 修完必须落一条会被执行的断言——否则它一定会退化回去，而且退化时不报警。顺带说一个同类：sparse 字段是 is_function_output（retrieve/hybrid.py:150），意味着分词配置是索引期属性。所以这个坑的根因在「索引怎么建的」，不是在「查询怎么发的」——定位时报错位置常常不是根因位置。

第三条：融合为什么必须用 rank，不能用 score？

Q：两路分数你怎么融合的？加权可以吗？

A：加权不行，必须用 rank。RRF 的形式是 Σ 1/(k + rank)，k=60（retrieve/hybrid.py:85、config.py:176）。依据是实测的三组数字：dense 是 IP 相似度；sparse 的 BM25 分实测是负值，比如 -0.6633；RRF 融合分在 0.03 量级。三个量纲放在一起做加权和，等于让量级最大的那一路单方面决定排序。

追问（中层）：负数这个事有多严重？加权一下会怎样？

A：会让「加权」这个动作名存实亡。设想 0.7 * dense + 0.3 * sparse：一条被稀疏路排第 1 的命中，BM25 分可能是 -0.6633，乘 0.3 之后是 -0.199；而一条 dense 分不高但为正的命中会在总分上反超它。也就是说，稀疏路越确信的命中被惩罚得越狠。最麻烦的是它跑得通、有排序、看起来正常——只有把两路分数分布打出来才能发现（那三行实测记录就在 retrieve/hybrid.py:353-356）。

追问（深层）：那 RRF 就万无一失吗？它有什么代价？

A：RRF 有两个明确代价。① 丢掉分数幅度信息：两路都排第 1 的命中与「一路第 1、一路第 100」得分差距被压缩得很小，k 越大压缩越狠——k=60 是个偏保守的选择，等价于「名次差异被强平滑」。② k 是跨实现不一致的超参：代码注释里记了「Qdrant 默认是 2」（retrieve/hybrid.py:85），差 30 倍，迁移时不显式传参就会静默改变排序。所以我把它做成可配置的 YYHELP_RRF_K，默认 60。如果哪天要调它，唯一的正确方法是拿评测集跑 recall/MRR 对照——而不是凭手感。顺带说清一条边界：RRF 之后还能设阈值的只有精排分数，因为精排是同模型对每对打的同量纲分；融合分不能当拒答阈值用。
