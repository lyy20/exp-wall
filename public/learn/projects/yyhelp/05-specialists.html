专家与工具可见性 ​

一句话：5 个专家各自能看见哪些工具，以及这套「看不见」是怎么被验证的。

这一页要回答什么 ​

面试官问多智能体，最锋利的一刀通常落在这里：

  1. 「你说每个专家只拿到部分工具——你凭什么相信它真的看不见别的工具？」这个问题在问你的验证手段，不是在问你的设计。答不好，前面讲的分层都会被打折。
  2. 「工具全暴露给所有专家不就行了？为什么要分？」——这是在问你对「能力边界」的收益有没有真实的判断。
  3. 「跨领域的问题谁处理？」——兜底策略与去重规则。

读完这一页，你能答：5 个专家的出口/名字/工具子集逐条对照表、ExpertSpec 的装配期契约校验、能力边界的两层验证（schema 层 + 执行期层）、以及一条很值钱的教训——不要用 tool_calls 判断「工具有没有被执行」。

一、它要解决什么问题 ​

1.1 「多智能体」到底多在哪里 ​

如果 5 个专家都能调用全部工具、都能处理全部问题，那么「多智能体」就退化成了「同一个模型换 5 个人设前缀」，只是把 token 花在了自我介绍上。多智能体的实质收益必须落在「每个专家看到的世界更小」上：更小的工具集、更窄的职责、更短的 prompt。

这条判断有一个可检验的落点：工具集变小会让 prompt 变短。实测的编排开销对比里，multi 臂每问 tokens 5,783.7 vs single 臂 6,243.3（40 题 × 2 臂 = 80 条记录，配对 t 检验 p=0.409，不显著；来源：eval Gate-1，2026-10-02，deepseek-v4-pro）。注意口径：这个差值是「编排结构 + 工具可见性 + 专家 prompt」三件事合起来的净效果，不能单独归因给工具可见性——这不是甩锅，这是报数时必须交代的归因边界。

1.2 出口是共享坐标系 ​

5 个专家的 exit_name 必须与 v1 的 EXITS 一一对应（experts.py:157 的注释原话：「这就是『A/B 共享同一套出口定义』的落点」）。真源在 v1 yyhelp/graph/build.py:128：

python
EXITS = ("kb_faq", "order_ops", "refund_flow", "service_ops", "agent_free")
1

EXPERTS 元组的顺序与 EXITS 一致，「便于对照与本文件的自检」（experts.py:190）。理由很硬：single 臂要复用 v1 的 9 类意图 → 5 出口映射，如果 v2 自己再定义一份出口元组，就会出现「v1 说映射到集合 A、v2 建图说映射到集合 B」这种没人能发现的分叉。共享的坐标系只能有一个定义。

二、方案与实现 ​

2.1 5 个专家 ​

exit_namename（state 键）display工具子集工具数
kb_faqkb_expert知识问答专家search_kb1
order_opsorder_expert订单专家query_order、query_logistics2
refund_flowrefund_expert退款专家query_refund_policy、create_ticket2
service_opsservice_expert事务专家query_order、query_logistics、create_ticket3
agent_freefree_expert自由规划专家tuple(V1_TOOL_NAMES) —— 全量 5 个，刻意为之5

v1 工具全集（V1_TOOL_NAMES，experts.py:140）= ("create_ticket", "query_logistics", "query_order", "query_refund_policy", "search_kb")。每个专家的工具数落在 1–3 个，只有兜底专家拿全量 5 个。

每个专家还有两个给模型看的字段：

  • duty：职责一句话，会拼进专家自己的 system；
  • out_of_scope：边界说明，写清「什么不该找它」。experts.py:171-173 的原话是——「这是减少误分派的正面手段：告诉模型『这个专家不做什么』，比只说『它做什么』更能收敛分派」。

举例，order_expert 的 out_of_scope 是「不处理退款、不建工单、不开发票（那是事务专家的事）」；refund_expert 是「不查物流轨迹、不处理发票」；free_expert 是「（无 —— 这就是兜底专家）」。

两个「为什么」都写在 docstring 里（experts.py:147-155）：

  • 为什么 frozen=True：专家的工具子集是装配期的事实，不是运行时状态。可变的话，某个节点「顺手」改一下 expert.tools，就会造成「同一张图里两个请求看到不同的工具集」——而症状是间歇性的工具不可用，极难复现。判据：装配期的事实必须不可变。
  • 为什么工具用 tuple 而不是 list：frozen=True 只管住「字段不能重新赋值」，管不住「list 内部被改」。tuple 从语法上阻止了 append。

__post_init__ 里做三项构造期校验（experts.py:176-187）：

  1. unknown = [t for t in self.tools if t not in V1_TOOL_NAMES] → 声明了 v1 不存在的工具就 raise ValueError。这是「工具并集 == v1 全量工具集」这条结构性断言的第一道保险：专家不可能凭空发明一个工具。
  2. if not self.tools → 「没有任何工具 —— 那它无法行动」，直接报错。
  3. 重复项检查（len(set(self.tools)) != len(self.tools)）。

为什么校验放在构造期？ 原话是「构造期能拦下的错误，不要等到运行时」。这和 plan.py 那个「写了一个应该存在但其实不存在的符号」是同一族问题：名字错了不会当场报错，只会在某个更晚的时刻以别的形态炸出来。

2.3 可见性怎么控制 ​

控制点是 tools_for(expert_or_exit)（experts.py:283）与 schemas_for(expert_or_exit, *, all_schemas=None)（:294）。执行路径上的顺序是：

  1. run_expert 拿到这个专家对应的 ExpertSpec；
  2. 工具名字集合 = tools_for(spec.name)；
  3. 发给模型的 schema 集合 = schemas_for(...) 按名字过滤出来的那部分；
  4. 执行工具时，仍然回头查白名单——schema 过滤不是唯一防线。

对照臂 run_single（supervisor_core.py:104-116）用的是另一条路径：tools_menu = V1_TOOL_NAMES（全量 5 个）、schemas = schemas_for(DEFAULT_EXPERT.name)。它的自检 [1] / [4] 断言菜单与 schema 名集合都等于全量 5 个——控制变量也要有断言，否则它随时会被某次「顺手优化」改掉。

2.4 为什么不全暴露 ​

第一，工具描述会占 prompt。 5 个工具的 name + description + schema 是一段固定开销。tools_digest(*, max_desc=0)（supervisor_core.py:174）在给 supervisor 看工具清单时把描述截断——上层只需要知道「有哪些工具」，不需要知道每个工具的参数细节。

第二，全暴露会让「选错工具」变成默认失败模式。 refund_expert 只看见 query_refund_policy 与 create_ticket 时，「能不能退」这个问题只能走政策查询 + 建工单；如果它同时看得见 query_logistics，它就可能先去查物流——一次错误的工具调用在 ReAct 循环里会花掉一步预算，而步数预算只有 6。

第三，可见性本身是可观测的。 ExpertOutcome 里有 tools_visible 字段（expert_run.py:153），并且 trace 里也带着——「这个专家当时能用哪些工具」是和回答一起被记录下来的。事后归因时不需要猜。

2.5 可见性怎么验证：两层 + 一条反面教材 ​

第一层，schema 层（结构断言）：发给模型的 schema 名集合必须逐个等于这个专家声明的 tools。自检里的形态类似：

python
sent = sorted(s["function"]["name"] for s in rec[0]["tools"])
assert sent == sorted(o3.tools_visible)
1
2

这一层证明「请求里真的只带了它该带的东西」。

第二层，执行期层（防御纵深）：即使有人绕过 schema 硬造一个越权调用，执行期也必须拒绝。验证方式是手工构造一个不在白名单里的调用，断言两件事——回灌的信息里出现「未知工具」、并且这个工具确实没有被执行（yyhelp/graph/agent.py:604-610 的处理路径）。

为什么需要第二层？ 因为 schema 过滤是「不告诉模型有这个东西」，而防御纵深要回答的是「模型自己编了一个」的时候会怎样。这两件事的失效模式不同：前者失效于提示词注入或 schema 拼接错误，后者失效于工具分发没有二次校验。

一条反面教材：不要用 tool_calls 判断「工具有没有被执行」。 v1 yyhelp/graph/agent.py:625 的 tool_calls.append 写在 if c.name not in tools / else 分支的外面——它记录的是「模型请求过的工具」，包括那些被拦下的未知工具。所以 len(outcome.tool_calls) > 0 完全不能证明「有工具被成功执行」。字段名会骗人，要拿执行结果本身当证据（校验 OBS 里同时存在「未知工具」与 INVALID_ARGS 这类标记）。

还有一条更该记住的：不要用「假模型调越权工具会被拒」来当判据。 原话是——「假模型是我自己写的脚本，它可以无视 schema 硬造调用；真模型不能（schema 是 API 层硬约束）。拿脚本的越权行为去证明系统边界，测到的是我自己，不是系统」。这句话值得每个写 Agent 测试的人背下来：测试替身的能力上界决定了这个测试能证明什么。

四、一次真实的请求走一遍 ​

输入：「订单 1001 到哪了？」

  1. triage → INTENT_TO_EXIT 把它落到出口 order_ops。
  2. supervisor（multi 臂）：dispatch_quota 返回 (0, 2)；决策结果 _next_expert = "order_ops"。
  3. 节点名换算：expert_node("order_ops") → "expert_order_ops"（supervisor.py:217）。反向换算是 exit_for_node("expert_order_ops") → "order_ops"（:210）。
  4. run_expert 装配：expert_by("order_expert") → ExpertSpec；tools_for → ("query_order", "query_logistics")；schemas_for → 只含这两个函数的 schema。
  5. prompt 组装：expert_system_prompt(spec, exit_choices=None)（expert_run.py:189）用三段式模板（我是谁 / 我不做什么 / 我何时交出去）。其中工具清单（以 - 开头的行）直接从 spec.tools 生成，描述取工具自己 docstring 的首行（截 80 字符），不另外写一份。
  6. ReAct 执行：交给 v1 的 run_react，并且必须传 state=state——不传会踩到那个 NameError 被吞成 model_error 的坑。
  7. 协议与解析：HANDOFF_MARK="HANDOFF:"（:103）、HANDOFF_RE（:108）从回答末行解析目标出口；parse_handoff(text, *, allowed)（:231）只接受 allowed 里的出口，非法目标留痕但不执行。
  8. 产出 ExpertOutcome（:153）：expert / exit_name / answer / handoff_to / termination / steps / prompt_tokens / completion_tokens / total_tokens / elapsed_ms / tool_calls / errors / trace / tools_visible。
  9. 下游：summarize(state) 从 expert_outputs["order_expert"] 取答案；route_after_expert 看有没有 HANDOFF 决定收尾还是再派一轮。

注意第 8 步的 tools_visible：它让「这个专家当时能看见什么」成为一条可与回答对账的记录。面试官问「你怎么知道它没越权」，你可以直接指这个字段。

五、踩过的坑 / 做过的取舍 ​

#现象根因怎么定位到的怎么修的教训
1以为「假模型能调越权工具」能证明边界假模型是我自己写的脚本，可以无视 schema 硬造调用；真模型不能（schema 是 API 层硬约束）反问「这个测试到底在测谁」放弃这条判据，改用 schema 名集合的结构断言拿脚本的越权行为去证明系统边界，测到的是我自己，不是系统
2专家 prompt 里的工具数有一天和 spec.tools 不一致工具清单若「另写一份」，两处描述必然漂移expert_run 自检 [1 prompt] 断言：prompt 里 startswith("- ") 的行数 == len(spec.tools)工具行直接从 spec.tools 生成，描述取工具 docstring 首行两处表示同一个事实，早晚会漂移；能生成的就不要手写
3以为 tool_calls 非空就代表工具被执行了agent.py:625 的 tool_calls.append 在 if c.name not in tools / else 的外面，记录的是模型请求过的工具（含被拦下的未知工具）读执行分支的位置改用执行结果本身当证据（OBS 里出现「未知工具」与 INVALID_ARGS）字段名会骗人：判断「有没有执行」要看执行结果，不要看请求记录
4反复出现「工具不可用但无法复现」的怀疑怕 expert.tools 被运行时改写设计期就用 frozen=True + tuple 从语法上堵住ExpertSpec 不可变 + 构造期校验装配期的事实必须不可变；间歇性 bug 的预防成本远低于定位成本

取舍一：为什么 agent_free 拿全部工具？ 它是兜底专家，职责是「处理无法归入其它四类的开放请求（投诉、闲聊、跨域组合）」。它的 duty 里还有一句约束：「你可以使用全部工具，但必须先判断再调用，不要为了显得勤快而多调」。全量工具是刻意的——如果兜底专家也没有全量工具，就会出现「没有任何专家能处理某类请求」的死角，而这类死角在评测里表现为「某几道题永远答不对」，很难归因。

取舍二：为什么停止信号是 HANDOFF: 文本标记，而不是新加一个工具？ 如果为「转交」加一个工具，那么「工具并集 == v1 全量工具集」这条结构性断言立刻变复杂（并集里会多出一个不属于 v1 的东西），而且控制流会渗进工具层。用文本标记则把「控制流」和「能力」分得干干净净：工具层只管能力，交接由协议层解析。

取舍三：out_of_scope 为什么不省？ 它是「减少误分派」的正面手段。只说「你负责什么」，模型在边界情况上会自行推断；明确说「你不处理退款」，边界情况就有了一条可判定的规则。

未实测（如实登记） ​

专家菜单选择准确率尚未实测。VISIBILITY_CASES（experts.py:361）定义了 9 条探针，isolation_report()（:315）给出隔离报告，但目前只跑到「结构上每个专家只看见 1–3 个工具」这一层；「用真模型跑这 9 条探针 + 跨域样例，看它是否选对工具」这件事还没做过。要验证它，判据应当写成两条同时成立：选对率 ≥ 阈值 且 越界调用 = 0。

六、面试深挖：追问链 ​

Q：你说每个专家只看得见部分工具，凭什么相信？

两层证据。第一层是结构断言：发给模型的 schema 名集合，排序后必须逐个等于这个专家声明的 tools，自检里直接比较 sorted(s["function"]["name"] for s in rec[0]["tools"]) 与 sorted(outcome.tools_visible)。第二层是防御纵深：手工构造一个不在白名单里的调用，断言回灌里出现「未知工具」并且它确实没被执行。

那这两层分别防什么？第一层防「schema 拼错了/提示词注入让模型看到不该看的工具」；第二层防「模型自己编了一个工具名」。它们的失效模式不同，所以都要有。

那「假模型调越权工具被拒」能当判据吗？不能。假模型是我自己写的脚本，它可以无视 schema 硬造调用，真模型不能——schema 是 API 层硬约束。拿脚本的越权行为去证明系统边界，测到的是我自己，不是系统。

Q：为什么不全暴露工具？

三个理由。工具描述占 prompt；全暴露会让「选错工具」变成默认失败模式（一次错调在 ReAct 里要花掉一步预算，而步数上限只有 6）；可见性本身可观测，tools_visible 会跟着回答一起被记录。

那兜底专家为什么又全暴露？因为它是「处理无法归入其它四类的开放请求」的兜底，职责是消掉死角。兜底专家拿全量工具，在评测里的表现是「不出现『没有任何专家能处理』的题」。

那这不是和前一条矛盾吗？不矛盾：窄菜单是给「有明确职责的专家」的，兜底专家的职责就是「没有明确职责的请求」，它的工具面必须宽。两者的目的不同——前者为了收敛、后者为了兜底。

Q：跨域的问题谁处理？

不是 supervisor 一次派两个专家，而是「真正的跨域由一个专家在回答最后一行输出 HANDOFF: <出口名> 触发」（规则 2）。执行顺序是串行的：A 专家先答，答完把控制权交出去，supervisor 再派 B。

那如果 A 反复交回去呢？有两个闸：dispatch_quota 的 DISPATCH_LIMIT=2，以及去重规则——_with_rules 的约束 A 会拦住「重复派同一个出口」，把这次拦成 source="dedup" 并直接 finalize。

为什么不做并行派发？一次派两个专家，两个答案谁负责收口、冲突谁裁决，都没有答案。串行接力让每一步都有一个明确的负责人；并行是下一步的升级方向，前提是先把「收口与裁决」想清楚。

Q：HANDOFF 为什么不做成工具？

如果为「转交」加一个工具，工具并集就不再等于 v1 全量工具集，那条结构性断言立刻变复杂；而且控制流会渗进工具层——工具层应该只管能力，不管编排。

那文本标记不会解析错吗？会，所以 parse_handoff(text, *, allowed) 只接受 allowed 里的出口，非法目标留痕但不执行。留痕这一点很重要：误解析如果不留痕，你只会看到「某道题答得莫名其妙」，看不到「它想转给一个不存在的出口」。

那正则宽松一点会不会更好？这里的选择是宁可严格——HANDOFF_RE = re.compile(r"HANDOFF:\s*\**\s*([A-Za-z_]+)") 只允许 ASCII 单词字符，中文目标名不会被误吞成非法出口。
