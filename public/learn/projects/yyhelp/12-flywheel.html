数据飞轮 ​

一句话：飞轮最难的一步不是收集坏问题，而是判断该对系统做什么 —— 同一个「被拒答 30 次」的现象，可能对应两个动作完全相反的根因。

这一页要回答什么 ​

  • 「数据飞轮到底是啥？」——概念层，先读第〇章：为什么「推了一千次」和「飞轮转了一千圈」不是一回事；以及「训练型飞轮」与「知识型飞轮」的区别（YYHelp 是后者，选它的三条理由）。
  • 「怎么讲给不懂技术的人听？」——第七章：一句话版 / 三十秒版 / 两分钟版三种深度的口语脚本，加上四个必被追问的问题与三句别说的话。
  • 「收集坏案例不就行了？」——要求说清飞轮真正的技术难点在归因：补知识是分钟级还是天级、调参数还是补知识，判错方向的代价是不对称的。
  • 「快照为什么要存两套 chunk id？」——这是本页的核心考点。要求说出 retrieved_chunks（候选，含 rank/score）与 final_context_chunk_ids（真正拼进 prompt 的）为什么要分开存，以及两者的差集代表什么。
  • 「你怎么知道是知识库缺东西，还是检索没召回？」——要求说出 replay.py 的五态判定与「只用快照」和「真跑重放」两种能力的区别。
  • 「为什么要多一个 trigger_primary 列？」——要求说清 SET 类型 + FIND_IN_SET 为什么走不了索引，以及这个修法付出了什么代价。

读完这一页你应该能：说清「三入口一张表」而不是三张表的理由；说清一次失败的归因链路（快照 → 判定 → 修复动作）；说清哪些部分是实测过的、哪些只是写在注释里的设计意图。

⚠️ 先说清页面边界：v2 没有飞轮代码。飞轮全部在 v1 的 yyhelp/flywheel/（pool.py + replay.py + schema.sql），本次是逐段读代码核对（不是只 grep 符号）。v2 侧唯一的连接点是 test_selftests.py 把 yyhelp.flywheel.pool 与 yyhelp.flywheel.replay 纳入统一自检清单 —— 也就是说这两条自检在 v2 的纪律下仍然会被定期执行。 另一个必须提前说明的事实：pool.py 的实际行数是 993 行、replay.py 是 610 行、schema.sql 是 294 行。事实清单 §12 开头记的是 864 / 535 / 231 行 —— 两者不一致，以代码为准，清单的数字已过期。

〇、先把「飞轮」这个词说清楚 ​

这一节不讲代码，只讲这个词到底在说什么。因为如果这一节没通，后面所有实现细节都只是在背。

「飞轮」的原意：靠惯性，不靠力气 ​

管理学里的「飞轮效应」说的是一个很朴素的物理直觉：一个很重的轮子，前几圈推起来极其费劲，但每一圈推的力气都被存进了惯性里；过了某个点，同样的力气能推得更快，再往后它自己就转起来了。

判断一个东西是不是飞轮，不看它转得多快，只看一件事：

这一圈产生的东西，有没有变成下一圈的燃料？

两个对照，差别一眼就出来：

❌ 不是飞轮✅ 是飞轮
典型形态客服工单系统数据飞轮
这个月收到1000 条投诉1000 条投诉
干了什么一条条处理掉，清空队列每条拆成「为什么答不出来」，原因写回系统
下个月同类投诉还是 1000 条降到 700 条

左边那个没有飞轮：它的产出是「工单关闭」，这只让队列变短，不改变系统行为。右边那个才有飞轮：它的产出是「系统的某个部分被永久改了」—— 补了一段知识、改了一个参数、修了一处拼装逻辑。下一圈它面对的是不同的系统，不是同一个系统。

所以「推了一千次」和「飞轮转了一千圈」是两件完全不同的事。

「数据飞轮」的定义 ​

把线上每一次失败，变成一条能永久复用的、可执行的改进指令；让同一个失败不再以同样的方式发生第二次。

三个字拆开看：

  • 数据 —— 不是「大数据」。飞轮的原料是失败的记录，不是成功记录，也不是用户画像。原料的质量，直接决定它能不能转。
  • 飞 —— 转起来才算数。一次性的离线 badcase 分析、一份月度复盘报告，都不是飞轮：它们有产出，但产出没有回流。
  • 轮 —— 闭环。改完必须回到线上，并且能被下一次失败验证。没有回线，就是一口永远收不满的井。

⭐ 数据飞轮有两种常见形态，别混着讲 ​

这个词在业界被用在两种完全不同的东西上，混着讲很容易被追问到崩：

(A) 训练型飞轮(B) 检索 / 知识型飞轮
失败样本流向标注成训练样本 → SFT / DPO / RL → 改模型权重归因 → 补知识库 / 调检索参数 / 修 prompt → 不动权重
典型场景有训练能力的团队：自动驾驶、大厂基座模型、意图分类模型知识密集的 RAG / Agent 应用：客服问答、文档助手
见效周期周级到月级（要攒量、要训练、要重跑评测）分钟级（调参）到天级（补知识）
可回滚性差（换权重不可逆，历史基线全部失效）好（删掉补的那段知识就回到原状）
本项目 YYHelp❌ 没做✅ 就是这个
你的 RAG 项目❌ 没做❌ 也没做（科研文献的知识是外部给定的，没有「业务方」可以补，所以那里不需要状态机）

YYHelp 为什么是 (B) 而不是 (A)，有三条硬理由，都可以直接摆上台面：

  1. 样本量根本不够。 我的评测集只有 40 题，而且两臂 39/40 同对同错 —— 能稳定复现的失败本来就少；而 SFT 起步要几百到几千条带正确答案的样本。一条「用户不满意」不等于一条训练样本 —— 中间缺的恰恰是「正确答案是什么」，而这件事只能靠人工审核补。
  2. 归因没做完就去训练，等于让模型学错东西。 大多数失败是「正确片段根本没喂给模型」，这时候微调只会让模型学会不看资料直接编 —— 那是把一个检索问题训练成幻觉。
  3. 判据本身很简单：把正确答案直接塞进 prompt，它能不能答对？ 能 → 问题在检索，不该动模型；不能 → 才轮到模型能力。这个问题不需要训练就能回答，所以它必须先回答。

可迁移判据：微调是修复阶梯的最后一格，不是第一格。 顺序是「补知识 → 调检索 / 拼装 → 改 prompt 与闸门 →（最后）改模型」。跳级去微调，是用一个昂贵且不可逆的动作，去掩盖一个便宜的、可回滚的问题。

AI 应用为什么比传统软件更需要它 ​

传统软件的 bug 是可复现的：同样的输入必然同样的输出，加日志、写单测就能定位。LLM 应用把这三件事全打破了：

传统软件LLM 应用
同样的输入 → 同样的输出同样的输入，今天答对明天答错（解码非确定性）
日志里有完整调用栈日志里通常只有「问题 + 答案」，中间发生了什么不可见
「正确答案」写在代码里「正确答案」在知识库里，而知识库随时可能缺、可能乱

最后一行后果最重：它意味着「答错」这一个现象有四类根因、四种修法 ——

  1. 知识库里没有这条知识 → 找业务方补（天级）；
  2. 有，但没检索上来（rank > top_k）→ 调 top_k / 加重排（分钟级）；
  3. 检出来了，但被截断 / 去重掉了 → 查上下文拼装（分钟级）；
  4. 正确片段已经在 prompt 里，还是答错 → 查闸门阈值 / prompt / 生成（别动检索）。

⭐ 这四行就是「为什么需要飞轮」的全部答案。 如果没有在失败那一刻把证据存下来，你无法区分这四行，只能凭直觉挑一个动作 —— 而第一行的成本比第二行高一个数量级。成本不对称的完整对照在下一章。

一、它要解决什么问题 ​

飞轮要回答一个业务问题：「哪些问题我们答不好，为什么答不好，改完有没有变好」。

第一句是收集，第三句是验证，第二句才是难点。因为同一个「同一个问题被拒答 30 次」的现象，可以有两个动作完全相反的根因：

根因正确动作成本做错的代价
知识库里没有这条知识请业务方补知识 → 回库 → 重建索引 → 重跑基线天级（要等人）不补则永远答不上
知识库有，但没被检索到（rank > top_k / 索引问题）调 top_k / candidates / 加重排分钟级去补一条已经存在的知识 —— 做无用功，且造成重复内容污染知识库

⭐ 注意「成本」那一列是不对称的：天级 vs 分钟级。 这不是「两种方案各有优劣」，而是判错方向会浪费一个数量级的人力：把「参数问题」误判成「知识缺口」，你会派人写一份知识库里已经有的文档，然后重建索引，然后发现毫无改善。

为什么没有快照时这个判断做不了：审核者只能去知识库里手工搜一下，发现「明明有这条」，于是（错误地）开始调 embedding 模型 —— 而真实原因可能完全不是那个（可能是重排把名次压下去了，也可能是候选被截断了，也可能是答案进了 context 但闸门阈值没过）。 可迁移判据：归因能力必须被设计进数据结构，不能指望人现场推理。 如果你在事后需要「翻日志 + 猜」，说明你在当时少记了一个字段。飞轮的检索快照，本质是把归因所需的证据在失败发生的那一刻就固化下来。

二、方案与实现 ​

2.1 三入口：为什么是同一张表 + trigger 字段，而不是三张表 ​

代码里的三入口真源是 TRIGGERS = ("weak_evidence", "self_eval_fail", "user_downvote")（pool.py:92），DDL 层对应 issue_pool.trigger_flags 的 SET('weak_evidence','self_eval_fail','user_downvote')（schema.sql:37）与从表 issue_occurrence.trigger 的 ENUM(同上)（schema.sql:93）：

入口键含义载体
weak_evidence检索证据弱被拒答闸门判定证据不足
self_eval_fail生成前自评没过自评环节拦下
user_downvote用户点踩user_feedback = -1

为什么是一张表（pool.py:11-16 + schema.sql:22-25）：审核者的工作台是「按被问频次排序待处理问题」。三张表意味着：

  1. 每次开工作台都要 UNION 三个结果集再排序；
  2. 「同一问题既被拒答又被点踩」会在三张表里各占一行 —— 人工流程变复杂，且容易漏审。

⭐ 代价是明确的：单表需要一个 SET 列（trigger_flags）存多个原因，而 SET 无法走索引（查单个成员要 FIND_IN_SET）→ 所以另设 trigger_primary 列。这条修法在 2.5 节细讲，它是本页最有教学价值的一处。

双表分工（schema.sql:13-20）：

表存什么角色
issue_pool去重后的「一个问题」审核者的工作对象
issue_occurrence每次发生（含检索快照）证据层
issue_replay离线重放的结论只增的批处理产物（flywheel/replay.py 会写它）

为什么主表/从表必须分开：单表会退化成两种反模式之一 —— ① 每次发生插一行 → 「被问频次」要靠 COUNT(*) 现算，审核排序键无法索引； ② 只有一行、把每次发生的原文拼进一个 TEXT 列 → 频次与证据都不可查询。 原文里的判据值得记：「这不是『规范化洁癖』，而是审核工作台的查询形态决定的」 —— 「近 7 天待审核、按被问频次倒序」必须是一条能走索引的 SQL。

issue_replay 为什么是独立的第三张表（schema.sql:155-156）：replay 是只增的批处理产物，与线上问题池的生命周期不同；混进 issue_occurrence 会让「线上发生」与「离线实验」无法区分。

幂等入池（Store.enqueue，pool.py:349-358）的四处非显然写法：

#写法为什么
1不用「先 SELECT 再 INSERT」，用 INSERT ... ON DUPLICATE KEY UPDATE（MySQL）/ ON CONFLICT ... DO UPDATE（SQLite）并发下两个请求会同时发现「不存在」→ 插两行；把竞态交给数据库的唯一索引解决
2max/min_confidence 用 GREATEST/LEAST（SQLite 侧 MAX/MIN 标量函数）增量维护不每次去扫从表算 —— 审核队列要按频次排序，扫从表会拖慢它
3json.dumps(..., ensure_ascii=False)保证中文在库里直接可读（人工审核要查库）
4快照必须过校验才写retrieval_snapshot 置空/写成 {} 是「看起来有、实际没有」，这类 bug 直到某天要 replay 才暴露 —— 所以在写入时就拦

第 4 条的报错文案本身就是判据：「检索快照缺字段 [...] —— 拒绝写入（宁可不入池，也不要空快照）」。

归一化与指纹（normalize_question，pool.py:147；fingerprint，:167）：

动作不做的后果（具体症状）
NFKC 全半角统一「退货Ａ」与「退货A」变成两个问题
去空白/标点末尾多个问号就变成新问题，频次全被摊薄
实体占位化「订单1001能退吗」与「订单1002能退吗」分成两条 → 频次永远上不去
lower英文大小写差异造成分池

⚠️ 顺序不能换：必须先 NFKC（否则全角数字匹配不到 \d），再实体替换（否则标点会打断数字串），最后去标点与空白。

⚠️ 指纹里绝不能放时间戳/会话 id（pool.py:170-171）：那会让每次都是新指纹，症状是 ask_count 永远是 1 —— 飞轮退化成流水账，频次统计完全失效。

⭐ 实体占位化踩过两次同类坑（pool.py:124-132，代码里专门记着「避免第三次」）：

写法症状根因
\b\d{11}\b"订单1002能退吗" 不被占位，"订单 1001 能退吗？" 被占位Python re 的 \b 是「\w 与非 \w 之间」，而中文汉字属于 \w、数字也属于 \w → 单 与 1 之间不存在词边界
只做单遍替换"订单1001能退吗" → "订单<NUM8>能退吗"（1001 被拆成两部分）替换按模式顺序做：<ORDER> 模式先匹配了 1001，产出带数字的占位符 <ORDER>，随后 <NUM> 模式又把这新产生的数字匹配掉

修法：用环视断言 (?<!\d) / (?!\d)（只排除数字相邻，不管中文），并用占位符不兼容的形式避免二次匹配。

⭐ 这条判据对中文场景极其重要：在中文文本里，\b、(?<!\w)、(?!\w) 这类基于 \w 的边界几乎全都不可靠 —— 因为汉字属于 \w。正确做法是只对你要保护的那一类字符做相邻判断（这里就是数字）。 代码里还留了一个更细的实测证据（pool.py:135-139）：快递单号 "SF1234567890到哪了" 里数字后面紧跟汉字 到 → 错误的边界下得到 'sf<NUM>到哪了'（前缀与数字分离），正确的边界下得到 '<TRACK>到哪了'。

2.2 ⭐⭐ 检索快照：为什么「两套 chunk id 必须分开存」 ​

snapshot_from_trace(trace, *, final_context_chunk_ids=(), query_original="")（pool.py:189）把 retrieve.hybrid.RetrievalTrace 转成飞轮快照。代码里写明三处刻意的设计，每一处都对应一类无法排查的故障：

#设计不这么做则哪类故障永远查不出来
1query_used 与 query_original 分开存多轮场景下「检索不准」经常其实是「改写把语义改丢了」。只存原始问题，这个根因永远查不出来
2retrieved_chunks（候选，含 rank/score）与 final_context_chunk_ids（真正拼进 prompt 的）分开存两者之差 = 「召回了但没喂给模型」，那是参数问题；只存后者会掩盖裁剪 bug
3embedding_model + index_version 必须存它们是「这批 badcase 是不是重建索引之前的」的唯一凭据

⭐ 第 2 条是本页最该背下来的一条，因为它的两个方向都会误导人（schema.sql:141-144）：

  • 只存 final_context：裁剪 / 去重 / 长度截断的 bug 会被完全掩盖；
  • 只存 retrieved：会误判「模型没用上我们给它的资料」（其实是被裁掉了）。

两者的差集就是「召回了但没喂给模型」的部分 —— 那是参数问题，不是知识库问题。

⭐ retrieved_chunks 里为什么保留 rank 而不是只留 chunk_id（pool.py:205-207）：

「正确切片排在 rank 6 而 top_k=5」与「根本没召回」是两类完全不同的修复动作（改参数 vs 补知识）。少了 rank 就只能猜。

差集被物化成一个字段（_excluded，pool.py:239）—— excluded_from_context：

症状（如果不算它）：审核者只能对着 retrieved_chunks 与 final_context_chunk_ids 手工做集合差，而这一步在几百条记录上根本做不完。

快照最小字段集（SNAPSHOT_REQUIRED，pool.py:183-186，9 项）：schema_version / query_used / query_original / top_k / retrieved_chunks / final_context_chunk_ids / embedding_model / index_version / retrieval_strategy。

  • 真建 milvus-lite 临时集合、真检索、真重放；
  • ⚠️ embedding 用 HashEmbedder（确定性替身，无语义能力） → 自检验证的是排序机制与重放判定逻辑，不代表 bge-m3 的真实检索质量；
  • _find_breaking_top_k(r, query, gt)（:350）—— 扫描出「刚好会漏掉」的那个 top_k，而不是把 rank=6、top_k=5 写死。

⭐ 为什么扫而不写死（:353-358）：本自检用 HashEmbedder（字符 bigram 替身），名次由字符重叠决定，不同语料/不同维度下正确切片的名次会变。如果硬写「rank=6、top_k=5」再断言，这个自检就会在改动语料后变成「为了通过而改期望值」——那就不是测试了。扫描的做法让断言变成：「存在一个 top_k，使得正确切片被截掉，且增大 top_k 能救回」——这是机制层面的断言，与具体语料解耦。

⭐⭐ 「为了通过而改期望值」是评测/自检里最常见的腐化方式，而这段代码给出了一个通用解法：把「具体数值断言」升级成「存在性断言 + 扫描」。 对比一下两种写法的失效模式：

写法语料/配置变化后人的反应
硬写 assert rank == 6变红改期望值（因为「测试坏了」比「代码坏了」更容易接受）→ 测试名存实亡
扫描 + assert 存在这样的 top_k仍然绿，且仍然在测机制无需改动 → 测试长期有效

判据：如果一个测试的期望值是可以「顺手改一下」就能变绿的，那它保护的是「期望值」，不是「机制」。

⚠️ 另一个真实的 Windows 坑（_build_demo_retriever，:328-333）：不能复用同一个 .db 文件名 —— milvus-lite 在进程内持有文件句柄，上次运行退出后句柄释放有延迟，unlink() 会抛 PermissionError: [WinError 5] 拒绝访问。原文强调：「这不是『文件正被使用』的偶发问题，而是每次第二次运行都会踩。」 修法：用带时间戳/pid 的唯一文件名。更通用的教训：在 Windows 上，「先删再建」的测试夹具要改造成「每次换新名字」。

v2 侧的唯一连接点：yyhelp_v2/test_selftests.py 的条目清单里包含 "yyhelp.flywheel.pool" 与 "yyhelp.flywheel.replay"（:90-91）。而 SELFTEST_TIMEOUT_S = 60 这个数的依据之一就是 yyhelp.flywheel.replay 是 v1 最慢的自检：2.61 s（另一个依据是 v2 首个 mcp.selftest 的 2.84 s，见 ⑩ 页）。

⭐ 这两个数字合起来说明一件事：60s 不是拍出来的，而是「实测最慢者 × 约 20 倍」得出的余量。原文对旧的 180 的评价是：「180 是『没量过』时的保守值，量过之后就该收紧。」可迁移判据：超时值是一个应该被「量过之后收紧」的参数。 拍一个大数看起来安全，实际后果是真实挂起时要等 3 分钟才报错（在本仓库里就是 CI 白等 3 分钟）。

⭐ 第 5 步是整个飞轮的枢纽：它不需要模型、不需要数据库、不需要网络（纯函数零依赖），却把「猜」变成了「读」。原文说得很直白：「这是本文件里最重要的 30 行 —— 它把『猜』变成『读』。」

为什么能做到这一点：因为证据在失败发生的那一刻就已经被固化下来了（第 1 步）。所以第 5 步只是读一个已经存在的 JSON。 ⭐ 这就是「把归因成本从「事后」挪到「当时」」的收益：当时多存几个字段的代价几乎为零，事后重建这些信息的代价是不可能（因为当时的状态已经过去了）。 可迁移判据：任何「事后要归因」的系统，都必须在「当时」把归因所需的字段落盘。 这不是可选的优化，而是能力的有无。

六、面试深挖：追问链 ​

第一条：快照为什么要存两套 chunk id？（本页核心考点）

Q：你在飞轮里存了什么？

A：检索快照，9 项最小字段集：schema_version、query_used、query_original、top_k、retrieved_chunks、final_context_chunk_ids、embedding_model、index_version、retrieval_strategy。其中最关键的是两套 chunk id 分开存 —— retrieved_chunks 是检索阶段返回的候选（含 rank、score、dense_rank、sparse_rank、rerank_score），final_context_chunk_ids 是真正拼进 prompt 的。

追问（中层）：为什么不能只存后者？反正「喂给模型的就是这些」。

A：因为只存一边会让两个方向的归因都错。只存 final_context，裁剪/去重/长度截断的 bug 会被完全掩盖 —— 你永远不知道「本来召回到了却没喂进去」。反过来只存 retrieved，你会误判「模型没用上我们给它的资料」（其实是被裁掉了）。而两者的差集就是「召回了但没喂给模型」的部分 —— 那是参数问题，不是知识库问题。我还把这个差集物化成了一个字段 excluded_from_context，因为不物化的话，审核者只能对着两个列表手工做集合差，而这一步在几百条记录上根本做不完。

追问（深层）：那 rank 呢？为什么要保留名次而不只留 chunk id？

A：因为**「正确切片排在 rank 6 而 top_k=5」与「根本没召回」是两类完全不同的修复动作** —— 前者改参数、分钟级，后者补知识、天级。少了 rank 就只能猜。 这两类动作的成本差一个数量级，判错方向会实打实浪费人力，所以判定表里我把它印在 reason 里：「注意这个动作是分钟级，而『补知识』是天级 —— 判错方向的代价不对称。」 还有两个字段也是一样必须存的：query_used 与 query_original 分开，因为多轮场景下「检索不准」经常其实是「改写把语义改丢了」，只存原始问题这个根因永远查不出来；embedding_model + index_version 则是「这批 badcase 是不是重建索引之前的」的唯一凭据。我给这三处都写了自检断言 —— 比如 snap["query_used"] == snap["query_original"] 就直接 fail，因为字段存在不等于它在被使用。

第二条：你怎么判断是知识库缺东西还是检索没召回？

Q：收集到坏案例之后你做什么？

A：做归因，而且分成两层。第一层是 rerank_snapshot(snapshot, correct_chunk_ids) —— 只用快照，不执行检索，纯函数零依赖。判定表四行：正确切片一条都不在 retrieved_chunks 里 → kb_gap（补知识，别调参数）；在但 rank > top_k → param_issue（改 top_k / candidates / 加重排）；在且 rank <= top_k 但不在 final_context_chunk_ids → context_trim（查拼装逻辑）；在且进了 context 仍被拒答 → unknown（检索不是根因）。第二层是 replay_with_retriever(...) —— 真跑一遍检索，回答「换成新配置之后这条知识能不能上来」，这是「改参数到底有没有用」的证据而不是猜测。

追问（中层）：为什么是五种结论而不是三种？

A：因为三态不足以表达，而且多出来的两个不是凑数。VERDICTS 是五个：param_issue、kb_gap、context_trim、improved、unknown。原文的理由是：「没有它们，代码就只能把这两种情况硬塞进『参数问题』，导致建议错误的修复动作。」 具体来说 —— context_trim 如果被塞进 param_issue，你会去调 top_k，但真正该查的是上下文拼装（去重、token 预算截断、模板拼接），调参数永远调不好。unknown 如果被塞进 param_issue，你会去调检索，但那条 case 的检索其实完全正常（证据命中、进了 context），根因在闸门阈值、prompt 或生成。代码里专门标了：「检索没问题时不要改检索 —— 把这类 case 归到『检索差』会导致永久调不好。」

追问（深层）：判断归因体系好不好，你有什么标准？

A：我有一条很实用的检验：把每个结论对应的修复动作写出来，看它们的成本是否同量级。 如果两个结论的修复动作一样，它们根本不需要是两个结论；如果成本差一个数量级，它们必须是两个结论 —— 而且分错类的代价会实打实地体现为浪费人力。这条标准同时解释了「为什么是五态」和「为什么不是十态」：improved 是重放之后才有的结论（它属于第二层能力），所以它必须是一个独立取值；而「模型没遵守 prompt」这类结论我没有单列，因为它对应的动作与 unknown 一致（都指向查生成侧）。 我还把「单条归因」和「批量评测」明确分工了：批量的 evaluate.py 回答「整体在哪个水平」，单条重放回答「这一题该怎么修」。没有后者，你只能看到指标涨跌，却不知道下一行代码该写什么。

第三条：trigger_primary 为什么要加？

Q：你说设计里最教学价值的一处修法是什么？

A：是 trigger_primary 这一列。issue_pool.trigger_flags 是 SET('weak_evidence','self_eval_fail','user_downvote') 类型，查单个成员要写 FIND_IN_SET('user_downvote', trigger_flags) —— 而 FIND_IN_SET 无法走 B-tree 索引，因为它是函数、不是列比较，于是退化成全表扫描。症状：问题池涨到 10 万行后，运营看板的「按原因统计」从 20ms 变成 4s。修法：增设 trigger_primary 列（取首次入池的原因），对它单独建索引。代价：只记「主导原因」，多原因同时存在时统计会略有偏差 —— 这是刻意的取舍，因为「哪个原因最多」这个问题的答案不需要精确到多原因分配。

追问（中层）：那你怎么验收它？

A：两条 EXPLAIN 对照，而且它们查的是同一个业务问题（各原因各多少条），只有写法不同 —— 于是唯一的变量就是「用函数还是用列」：① EXPLAIN SELECT COUNT(*) FROM issue_pool WHERE FIND_IN_SET('user_downvote', trigger_flags); → 期望 type=ALL、key=NULL；② EXPLAIN SELECT COUNT(*) FROM issue_pool WHERE trigger_primary='user_downvote'; → 期望 type=ref 或 range、key=idx_trigger_primary。 但我要主动说明口径：「20ms → 4s」和「10 万行」这两个数字来自 schema.sql 里索引 2 的注释，是设计意图的量化表述，本次没有实测记录 —— 注释里的验收命令还写着「需先造 ≥10 万行」，意思是这两项验收尚未执行。所以我不会说「我实测过」，我会说「这是设计时记录的预期症状，验收方式是这两条 EXPLAIN + 10 万行计时」。把「设计意图」和「实测结果」分开说，这件事本身就是可信度的一部分。

追问（深层）：那为什么一开始不用三张表，就不用 SET 了？

A：因为审核者的工作台是「按被问频次排序待处理问题」。三张表意味着每次开工作台都要 UNION 三个结果集再排序，而且「同一问题既被拒答又被点踩」会在三张表里各占一行 —— 人工流程变复杂，且容易漏审。漏审的代价比索引慢得多。 所以这是一个**「查询形态决定表设计」的取舍：我先看审核者的真实工作流（按频次排序的单一队列），再决定单表 + trigger 字段，然后为这个决定付了索引的代价**（增设 trigger_primary）。反过来说，如果工作流是「分别看三个原因的队列」，那三张表反而更好 —— 表设计要跟着查询走，不是跟着「第几范式」走。 我还在设计里写了一条反向的边界提醒：idx_review_queue 的列序是 (status, ask_count DESC, last_seen_at)，但如果真实查询是「近 7 天 + 按频次」，正确顺序应该改成 (status, last_seen_at, ask_count DESC) 并接受排序开销 —— 因为 MySQL 8 无法用同一索引同时完成「范围过滤 + 另一列排序」。原文的结论是「必须用 EXPLAIN ANALYZE 验证你选的那一条」。索引的列序取决于查询形态，而查询形态会变。

第四条：这个飞轮跑通了吗？

Q：你实测到什么程度？

A：分两半说。SQLite 路已在本机真跑 —— pool.py --selftest 真建库、真写三入口，输出落在 output/yyhelp-day3-验收.txt 的 F1；replay.py --selftest 也真跑了，真建 milvus-lite 集合、真检索、真重放，输出在 G1/G2。MySQL 端到端未执行验证 —— 本机实测无 MySQL 服务/客户端，schema.sql 未在 MySQL 上执行过，验收命令写在文件末尾。

追问（中层）：那你凭什么说 MySQL 路是对的？

A：我没说它对，我说的是契约对齐已被机械验证。--schema-parity 会断言 MySQL 段与 SQLite 段在三张表上的列集合完全相等（不是包含），这是防 DDL 漂移的机械手段。另外唯一的语义差异都有显式等价实现：SET 位或 → 应用层、ON UPDATE → 应用层显式 SET updated_at、ENUM 校验 → CHECK (col IN (...))，而所有 SQL 都写成「常量 + 方言适配」 —— Store.ph 是唯一必须方言化的东西（? vs %s），业务代码里不散落 if mysql。 但有一条我必须标注为未验证，而且它恰好是 MySQL 路最核心的语义：trigger_flags | VALUES(trigger_flags) 是否真是按位或语义。验收方式是连续插两次不同的 trigger_flags 再 SELECT，期望 ask_count=2、trigger_flags 含两个成员；如果只含一个，说明 | 不是按位或，得改成应用层计算。schema.sql 里原文标了「这是必须实测的一条」。

追问（深层）：那你怎么没有「全部验证完再写代码」？

A：因为**「验证完所有东西再动手」是一个不可达的停止条件**。我用的停止条件是：清单上每一项都被分到三类之一 —— A 类「可验证且已验证」、B 类「可验证但未验证」（本机能验、只是还没做，有排期）、C 类「结构上不可验证」（缺客观条件）。区别很重要：B 类不是缺时间，是缺一次执行；C 类永远会是「未实测」。 所以我这一页的未验证清单里，MySQL 三项属于 B 类（能验、有命令、有期望值），而「10 万行下的真实耗时」也属于 B 类 —— 它的验收命令已经在注释里写好了，只差造数据。我把它们列出来而不是藏起来，因为一个诚实的 B 类清单比一个含糊的「已验证」有说服力得多：面试官问「你实测到什么程度」，我能一条条说清哪些是 A、哪些是 B、B 的验收命令是什么。

七、怎么把它讲给别人听 ​

前面六章是「你知道什么」，这一节是「你怎么说出来」。区别很大：懂一个东西的标志不是能列出细节，而是能用三种深度把它讲通，并且三种深度之间不打架。

7.1 一句话版（对完全不懂技术的人） ​

就是把「用户在哪儿被我们坑了」，变成一张自动排好序、直接能派活的工单 —— 而且工单上带着出事当时的完整现场。

要点：这句话里不要出现「飞轮」「检索」「快照」任何一个词。 它的作用是让对方愿意听第二句，不是让他一次听懂。

7.2 三十秒版（对 HR、面试开场、非技术面试官） ​

AI 客服答错，最难的不是修，是知道该修哪儿。 同一个「答不出来」，可能有两种完全不同的原因：一种是知识库里真没这条知识，得找业务方补，要几天；另一种是知识库里有，只是检索没把它捞上来，调个参数就行，几分钟。这两种修法成本差一个数量级，判错方向就要白干几天。 所以我做了个数据飞轮：三个入口 —— 被拒答、生成前自评没过、用户点踩 —— 自动把失败丢进一个池子，而且每条都带着出事当时的检索快照：当时召回了哪些片段、各排第几、哪些真正喂给了模型。 有了快照，判断就不用猜了，读一下就知道该补知识还是该调参数。改完回到线上，下一次同类失败就是它的验证。

⚠️ 这三十秒里唯一必须说出口的数字是「天级 vs 分钟级」，因为它是整个设计存在的理由。别在这里报延迟、报 token —— 那些属于两分钟版和深挖环节。

7.3 两分钟版（技术面，被问到「讲讲你这个项目」时） ​

结构固定四段，顺序不能换：痛点 → 三步闭环 → 最难的一步 → 诚实的边界。

(1) 痛点（约 25 秒） LLM 应用的失败和传统 bug 不是一类东西。传统 bug 可复现、有调用栈；LLM 答错的时候，日志里只有问题和答案，中间检索到了什么、喂给模型什么、模型为什么这么答，全都不可见。而且「正确答案」不在代码里，在知识库里 —— 所以同一个「答错」，可能是缺知识、可能是检索差、可能是拼装截断、可能是模型没听话，四种修法。如果不把证据存下来，失败一旦发生就永久消失了。

(2) 三步闭环（约 50 秒） 第一步是收集：三个入口汇到一张表 —— 检索证据弱被拒答、生成前自评没过、用户点踩。之所以是一张表加一个 trigger 字段而不是三张表，是因为审核者的工作台是「按被问频次排序的单一队列」；三张表每次开工作台都要 UNION 再排序，而且同一个问题既被拒答又被点踩会在三张表里各占一行，人工流程会漏审。代价是单表要用 SET 类型存多个原因，而 SET 走不了索引，所以我又加了一列 trigger_primary。 第二步是去重：问题先归一化 —— 全半角统一、去标点空白、把订单号和快递单号替换成占位符 —— 再算指纹。这一步不做，「订单 1001 能退吗」和「订单 1002 能退吗」就是两条记录，频次永远上不去；做了之后，一千条投诉可能只是十二个问题被问了一千次 —— 那审核人力就有杠杆了。 第三步是归因：只用快照跑一个纯函数，四行判定表 —— 正确片段一条都不在召回里，是知识缺口，补知识、别调参；在但名次超过 top_k，是参数问题，改 top_k 或者加重排；在且名次够但没进最终 context，是拼装被截断，查去重和长度预算；进了 context 还是答错，那说明检索没问题，别动检索，去查闸门阈值和 prompt。

(3) 最难的一步（约 25 秒） 最难的不是收集，是归因，而且难在数据结构上。快照里我存了两套 chunk id：retrieved_chunks 是检索返回的候选，带 rank 和 score；final_context_chunk_ids 是真正拼进 prompt 的。为什么不能只存后者？因为只存喂进去的那份，裁剪和长度截断的 bug 会被完全掩盖 —— 你永远不知道「本来召回到了却没喂进去」。反过来只存候选，你会误判「模型没用上我们给它的资料」。 两者的差集就是「召回了但没喂给模型」的那部分 —— 那是参数问题，不是知识库问题。我还把这个差集物化成了一个字段，因为不物化的话，审核的人要对着两个列表手工做集合差，这在几百条记录上根本做不完。

(4) 诚实的边界（约 20 秒） 这套东西我建起来了：SQLite 路自检真建库真写过三个入口，milvus-lite 上的离线重放也真跑通了（不过那把用的是确定性替身 embedding，不代表 bge-m3 的真实检索质量）。但我没有证明它让指标变好了 —— 我的 A/B 只有 40 题，两臂 39/40 是同对同错的，有效样本量基本等于 1，任何提升都不显著。所以我能说的是「机制是对的、链路是通的」，不能说「效果提升了」。要证明它，得先定义一个能测的指标，比如同类问题的 30 天复发率 —— 这是我下一步要补的。

⭐ 这四段的权重是反直觉的：第 (4) 段最短，但它是最能加分的。因为绝大多数候选人会在第 (2) 段吹到第 (3) 段就被问穿；主动交出边界的人，反而让面试官相信前面三段是真的。

7.4 大概率被追问的四个问题 ​

追问一句话骨架别掉进去的坑
「这不就是收集 badcase 吗？」收集是最简单的一步。难的是同一个现象对应两种动作相反、成本差一个数量级的根因，判错就要白干几天 —— 所以难点在归因而非收集别顺着说「对，就是 badcase 管理」，那等于承认没有技术含量
「那你为什么不拿这些数据去微调？」三句话：样本量不够（一条 badcase 不是一条训练样本，缺的正是正确答案）；归因没做完就训练，会让模型把检索缺陷学成幻觉；判据是「把正确答案塞进 prompt 能不能答对」，能就说明不该动模型别答「以后会做微调」—— 那是在承认现在这套只是过渡方案
「快照为什么非要存两套 chunk id？」只存 context → 掩盖裁剪 bug；只存候选 → 误判「模型没用上资料」；两个方向都会误导，差集才是参数问题的证据展开细节见 2.2 节，别在这里把 DDL 也讲了
「这套东西真的有用吗？」机制建成 ≠ 效果证明。我能给的是链路可跑 + 归因可读；证明效果需要「同类问题复发率」这类指标和足够大的样本，我没有★ 不要为了好看编一个提升百分比 —— 这是最容易被反问击穿的地方

7.5 三句别说的话 ​

  • ❌ 「我搭了个数据飞轮，持续迭代模型效果。」 —— 「持续迭代」没有任何证据支撑，而且暗示了一个没验证的因果。一旦被问「涨了多少」，就全塌了。
  • ❌ 「数据飞轮就是收集用户反馈去训练模型。」 —— 这是 (A) 训练型飞轮的定义，你做的是 (B)。这句一说，面试官会顺着问「那你训了多少条、用什么框架」，当场露底。
  • ❌ 「我用 MySQL 存问题池，用 sha256 做去重。」 —— 这是逐条复述实现，会把技术面直接拽进 DDL 细节，把你从「设计者」降格成「记录员」。先讲为什么，再讲用什么。
