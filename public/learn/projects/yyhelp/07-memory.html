记忆机制 ​

一句话：三层记忆各自存什么、长期记忆的写入门槛与召回打分，以及一条反直觉的 state_only 策略。

这一页要回答什么 ​

记忆是 Agent 项目里最容易做错的一块，因为它看起来只是「把用户说过的话存起来、下次取出来」。面试官通常这样切：

  1. 「你的记忆存在哪？为什么存在那？」——在问你的真相源判断。
  2. 「凭什么一条记忆值得被写进去？凭什么它下次被召回？」——在问门槛与打分。
  3. 「召回的内容直接拼进 prompt 了吗？」——这是这一页的核心考点。答案是：没有，而且理由不是我省事。

读完这一页，你能答：三层记忆的边界、写入门槛与半衰期的逐类型差异、W_SIM 0.55 + W_OVERLAP 0.25 + W_DECAY 0.20 这套打分、RECALL_POLICY="state_only" 的三条理由与它的代价，以及一条很硬的判据——能算出来的东西不要存。

一、它要解决什么问题 ​

1.1 三层记忆，各自解决一个不同的问题 ​

longterm.py:11-17 把记忆分成三层：

层内容生命周期归属
第 0 层近 N 轮原文（滑动窗口 squeeze）本次会话v1 graph/memory.py，v2 不动
第 1 层会话内摘要 summary本次会话v1 的 summary，v2 不动
第 2 层跨会话长期记忆活过会话结束v2 graph/longterm.py，本页主题

为什么前两层完全不动？ 因为它们是「上下文管理」，不是「记忆」。前者解决的是「窗口放不下」，后者解决的是「会话结束了，用户说过的话还在不在」。把两件事混在一起改，会让「窗口策略」的回归测试变成「记忆系统」的回归测试——测的东西和改的东西不一致，是最常见的工程失控方式之一。

1.2 「记忆是用户数据，不是检索产物」 ​

这句话是整个设计的判据（longterm.py:44-57）：

知识库 chunk 丢了可以重切，用户说过「以后都用顺丰」丢了没有任何地方能重建。

由此推出的两个结论：

  • 真相源必须是可审计、可导出、可单条删除的存储 → SQLite，DEFAULT_DB = Path(os.environ.get("YYHELP_MEMORY_DB", r"D:\yyhelp\data\yyhelp_memory.db"))（:180-182）。
  • 向量索引是从真相源重建的派生物，所以它的可用性要求必须低于真相源 → Milvus 是可选的，默认 use_milvus=False。

⚠️ 这里有个 Windows 环境变量大小写不敏感导致的真实教训：代码用 os.environ.get 而不是 os.getenv——本项目实测过一次同类问题。在 Windows 上，两个只差大小写的环境变量名是同一个变量，这会让「本地跑得好、服务器上取到别的值」这类问题变得很难解释。

二、方案与实现 ​

2.1 存储：真相源与索引分离 ​

角色实现集合/路径默认状态
真相源SQLiteYYHELP_MEMORY_DB，默认 D:\yyhelp\data\yyhelp_memory.db开
向量索引Milvus（可选）集合 yyhelp_memory_v1关（use_milvus=False）
知识库（对比）Milvus集合 yyhelp_kb_v1——

记忆集合 yyhelp_memory_v1 与知识库集合 yyhelp_kb_v1 物理隔离。为什么必须隔离？因为两者的生命周期与权限完全不同：知识库是政策文档，谁都能读、重建成本低；记忆是用户数据，需要支持「单条删除」。把它们放在同一个集合里，任何一次「重建知识库」的操作都有可能顺手清掉用户记忆。

为什么默认不开 Milvus？（longterm.py:487-494）三条理由：

  1. 几百条规模下 SQLite 全表扫描 + 本地打分更快——省一次跨进程调用与一次 embed 网络往返。在这个数据规模上，向量库是负数收益。
  2. 让 --selftest 真正离线。如果自检依赖 Milvus 集群，那么「跑自检」就变成「先起一个服务」——最后的结果就是没人跑自检。
  3. Milvus 挂掉时主链路不受影响这条要求，默认就满足了。可用性要求必须低于真相源，而「默认不依赖它」是满足这条要求最省事的方式。

2.2 写入门槛：四类内容、四道不同的线 ​

MIN_CONFIDENCE_BY_KIND（longterm.py:131-136，:131-140 含未知 kind 兜底）：

kind门槛为什么是这个数
preference0.60写错代价小，而且用户下一句就会纠正（「我不要顺丰」）
fact0.75写错会一直误导，但通常能被后续对话否证
solution0.80写错会替代一次真实检索——而检索结果可核对、有引用，记忆没有引用
correction0.85写错等于把用户的纠正反过来覆盖成错误，最坏的一种污染
未知 kind0.85不认识的类型按最严的门槛处理

门槛不是「调参空间」，是「错误代价的排序」。 这条线的逻辑很直白：一条错误记忆的代价 = 它有多难被纠正 × 它会造成多大范围的影响。correction 之所以最严，是因为它一旦写错，系统会把「用户明确纠正过的事」记成相反的值——后续再也不会有人纠正它。

2.3 半衰期：两类内容永不衰减 ​

HALF_LIFE_DAYS（longterm.py:145-150）：

kind半衰期（天）理由
preference90.0偏好会变（换了地址、换了收货习惯）
solution180.0解决方案的时效性比偏好更长
factNone用户事实不该过期（「我的订单号是……」）
correctionNone用户的纠正不应该随时间失效

fact 和 correction 不衰减，这一条是刻意的：衰减的前提是「这条信息会过时」。用户说「我住杭州」不会因为过了 90 天就不成立。把不衰减的内容也套上衰减曲线，等于主动把正确记忆丢掉。

2.4 召回打分：三项加权 ​

召回参数（longterm.py:153-174）：

常量值说明
RECALL_TOP_K3最多召回 3 条
RECALL_MIN_CONFIDENCE0.55低于此不进入打分
RECALL_MIN_SCORE0.25总分低于此不返回
DECAY_FLOOR0.30衰减下限
W_SIM0.55语义相似度权重
W_OVERLAP0.25关键词重合权重
W_DECAY0.20时间衰减权重
HASH_DIM64离线降级 embedder 的维度

score_memory(query, item, *, qvec, tvec, sim=None, now=None) -> tuple[float, float, float, float]（:392）返回 (总分, 相似度, 关键词重合, 衰减)。

两个细节值得单独说：

① 余弦相似度夹到 [0,1]：s = max(0.0, min(1.0, s))。 负余弦会让加权和变成一个「惩罚项」，把整体分数推到 0 以下——那样 RECALL_MIN_SCORE=0.25 这道闸就失去意义。加权和里的每一项都必须有界，否则权重就不是权重了。

② 三项权重之和为 1，而且注释明确写着「不要把它当成『调参空间』」。 它的作用不是「调到最好」，而是让「语义近但完全不沾边」的记忆拿不到高分：一条记忆可能和 query 向量很近（比如都是关于「快递」），但内容完全不沾边——这时候如果只看向量，它就会挤掉真正有用的那条。W_OVERLAP 存在的意义就是给「字面也不沾边」的候选扣分。

衰减在召回时算，不做后台任务（decay(kind, created_at, *, now=None) -> float，:367）：

python
age_days = max(0, (now - created_at) / 86400)
hl = HALF_LIFE_DAYS.get(kind)
return 1.0 if hl is None else max(DECAY_FLOOR, 0.5 ** (age_days / hl))

衰减落在 [0.30, 1.0]（下限就是 DECAY_FLOOR）。为什么不做一个「定期降权」的后台任务？原话是——后台任务引入「记忆状态取决于上次任务跑没跑」的隐式依赖，任务挂了过期记忆照样被召回，而且没有任何症状。判据：能算出来的东西不要存。

2.5 两个离线/降级组件 ​

char_overlap(query, text) -> float（:346）是字符 2-gram 的重合率（Jaccard 变体）。为什么不用 v1 的 KeywordOverlapReranker？ 因为它按空格分词，对中文几乎恒为 0 或 1——中文句子内部没有空格，切出来的「词」要么是整句、要么什么都没有。中文文本的重合度必须按字符 n-gram 算。

_HashEmbedder（:303）是一个极简确定性 embedder，用于离线自检与降级。为什么不用 v1 的 HashEmbedder？ 因为它需要 retrieve.embed 这一整条依赖链，会把「记忆模块的自检」变成「整条检索链路可用的自检」。两者算法一致（字符 2-gram 哈希 + L2 归一化），所以排序趋势一致，但绝对分数不可外推——这句话很重要：不能拿离线自检的分数去论证线上召回的分数。

2.6 幂等：指纹而不是前缀 ​

MemoryItem.id 默认由指纹派生（f"m_{fp[:16]}"），所以同内容同 id，写入天然幂等。

为什么不用「取前 N 字符比较」？ 因为 CJK 文本的前缀往往相同：「用户偏好使用顺丰快递发货」与「用户偏好使用中通快递发货」前 8 个字一模一样。取前缀会把两条相反的偏好判成重复——这是一个会把数据静默弄错的实现方式。

为什么归一化里不做去标点？ 因为标点承载语义：「不要顺丰」和「要顺丰」只差一个「不」，但「不好用！」和「好用！」的差别全靠标点。去掉标点会让指纹把相反的语义判成同一条。

2.7 RECALL_POLICY = "state_only"：召回但不拼进 prompt ​

这是这一页最反直觉的一条。RECALL_POLICY = "state_only"（longterm.py:810）：召回结果写进 state["memories_recalled"]，但不直接拼进 prompt。三条理由（:790-810）：

  1. 可观测性。 拼进 prompt 后，记忆就从「结构化数据」变成「一段文本的一部分」，trace 里再也回答不了「这次召回了哪几条、哪几条被过滤了、为什么」。
  2. 可回滚。 记忆写错时要重跑请求；留在 state 里，可以在 finalize 前一条 retract() 掉它。拼进 prompt 之后就没有「撤回」这个动作了——模型已经看过了。
  3. 可对比。 要做「有记忆 vs 无记忆」的 A/B，记忆是 state 字段时，对照臂只要把 memories_recalled 置空即可，两种模式跑的是同一条代码路径。如果记忆被拼进 prompt，对照臂就得维护一个「不拼记忆的 prompt 版本」——那就变成了两条代码路径，实验立刻失去可比性。

代价必须如实说：模型看不到记忆。所以「用上了记忆」在当前实现里只到「能召回、能留痕」为止。项目用 render_memory_hint(res, *, max_items=3)（:839）与 recall_for_state(state, *, store=None, top_k=3, with_hint=...)（:813）提供了一个显式开关，并把它记进未实测清单——而不是偷偷拼进去让指标好看。

还有一条设计判断：不做「看到记忆就不再检索知识库」。 因为记忆是用户事实，知识库是政策事实，两者冲突时必须两个都摆出来让下游发现矛盾。用记忆短路知识库，等于把幻觉升级成「有据可依的幻觉」——那比没有依据的幻觉更难被发现，因为它带着一条看起来很正当的理由。

2.8 写入门槛之外还有两道 ​

除了 MIN_CONFIDENCE_BY_KIND，还有：

  • 长度闸（:889-904）：correction ≤ 200 字符、preference ≤ 120 字符、solution ≤ 300 字符。为什么长度也算一道闸？ 因为长文本更可能是「整段对话的摘要」而不是「一条可复用的记忆」。记忆的价值在于短、准、可复用。
  • 同类抽取上限 2 条/会话（:906-915）。防止一次长对话里抽出十条同类型的记忆，把记忆库变成对话记录。

抽取的可信度也是逐类型给的（:889-904）：correction 0.92、preference 0.70、solution **0.80**；反思写入的置信度是 **0.90**（longterm.py:889-904；reflect.py:92-94`）。reflection 是唯一一个由系统自己产生的记忆来源，所以它的置信度必须显式给定——不能默认「系统写的就可信」。

2.9 不做自动记忆合并/总结 ​

§7.8 明确：不做自动记忆合并或总结。理由属于同一族判断：自动合并会引入一个没有症状的错误通道——两条记忆被合并错了，你不会收到任何告警，只会在某天发现「系统记错了我的偏好」。而单条记忆的写入与删除是可审计、可回滚的。

四、一次真实的请求走一遍 ​

两轮会话，展示长期记忆的完整生命周期。

第一轮：用户说「以后都用顺丰，不要中通」。

  1. memory 节点先召回（第一轮通常召回不到什么）：recall_for_state(state, store=None, top_k=3, with_hint=...) → 结果写进 state["memories_recalled"]。输入：CSStateV2；输出：最多 3 条记忆的列表。
  2. 正常走 supervisor → 专家 → finalize。
  3. 会话结束，抽取候选。这条内容会落成 kind="preference"、置信度 0.70（抽取侧给的值）。
  4. 过闸：长度 ≤ 120 ✓；门槛 preference 需 0.60，0.70 ≥ 0.60 ✓；本会话同类数 ≤ 2 ✓。
  5. 算指纹：归一化后 sha256 → id m_<前16位>。注意归一化不去标点——所以这条 preference 与「不要顺丰，用中通」不会是同一个 id。
  6. 写入 SQLite；如果开了 Milvus，索引可选重建。

第二轮（新会话）：用户问「我这单发什么快递？」

  1. memory 节点召回：候选集按 RECALL_MIN_CONFIDENCE=0.55 先过滤，再逐条打分 0.55×相似度 + 0.25×字符2-gram重合 + 0.20×衰减。
    • preference 的半衰期是 90 天，衰减项 = max(0.30, 0.5 ** (age_days/90))；
    • 「发什么快递」与「以后都用顺丰」的字符 2-gram 重合不算高，但语义相似度会拉分——这正是 W_SIM 占 0.55 的原因。
  2. 过闸：总分 ≥ RECALL_MIN_SCORE=0.25 才返回；最多取 TOP_K=3 条。
  3. 结果写进 state["memories_recalled"]，但不拼进 prompt（RECALL_POLICY="state_only"）。所以这一轮模型看不到「以后都用顺丰」这条记忆——它的答案只能来自知识库检索和订单查询。
  4. 这就是当前实现的诚实边界：记忆是「被召回、被留痕」的，不是「被使用的」。要让它被使用，需要把 with_hint 打开（走 render_memory_hint），而这条路径尚未实测。

关键观察：第 3 步是这个设计里最容易被误读的一步。看到 memories_recalled 里有内容，很容易以为「记忆生效了」。没有生效——它只是被记录了下来。这个区别就是「可观测」与「有效果」的区别，面试时如果被问到，应该主动区分。

2中文文本的「关键词重合」恒为 0 或 1v1 的 KeywordOverlapReranker 按空格分词，中文句内无空格打分结果全是极端值自实现 char_overlap，按字符 2-gram 算照搬一个为英文设计的组件，会在中文上静默失效
3两条相反的偏好被判成重复如果用「取前 N 字符」做去重，「用户偏好使用顺丰快递发货」与「用户偏好使用中通快递发货」前 8 字相同检查指纹实现用 content_fingerprint（归一化 + sha256），并在归一化里保留标点前缀相等不等于语义相同；CJK 文本尤其如此
4离线自检的分数被拿去论证线上召回离线用的 _HashEmbedder 与线上 embedder 不是同一个对账两个 embedder 的算法明确写清「排序趋势一致，但绝对分数不可外推」降级组件可以替代排序，不能替代分数
5记忆状态看起来「随机」地不对若用后台任务定期降权，任务挂了过期记忆照样被召回且没有任何症状从设计上排除衰减在召回时计算（decay()），不存衰减值能算出来的东西不要存——存了就要维护，维护就会有「上次跑没跑」的隐式依赖

取舍一：RECALL_POLICY 为什么不做成「拼进 prompt」？ 三条理由（可观测、可回滚、可对比）已经在 §2.7 展开。这里补一条最实际的：做 A/B 的时候，记忆拼进 prompt 就意味着对照臂要维护两个 prompt 版本，实验从「一条路径两个参数」变成「两条路径」，可比性当场消失。

取舍二：为什么不做自动记忆合并/总结？ 合并会引入一个没有症状的错误通道：两条记忆被合并错了不会有任何告警，只会在某天表现为「系统记错了」——而那时已经无法回溯是哪一次合并出的错。单条写入 + 指纹幂等，保留了「可单条删除」这条能力。

取舍三：为什么用 SQLite 而不是直接上向量库？ 见 §2.1 三条理由，最核心的是第 3 条：向量索引是从真相源重建的派生物，它的可用性要求必须低于真相源。默认不开它，这条要求就自动满足了。

未实测（如实登记） ​

  • RECALL_POLICY="state_only" 意味着「用上了记忆」这件事本身没有被验证。 项目提供 render_memory_hint() 作为显式开关，但开与不开的效果对比没有跑过。要验证它，实验该这么设计：同一批含「用户偏好」的题目，两臂分别是 with_hint=False / with_hint=True，指标是「偏好遵守率」，判据是「提升显著 且 没有引入新的错误偏好」。【待核对：记忆 hint 开与不开的偏好遵守率】
  • 召回参数（RECALL_TOP_K=3 / RECALL_MIN_SCORE=0.25 / 三项权重）没有实测支撑。 注释本身就写着「不要把它当成调参空间」——它们的作用是排除明显不相关的候选，而不是「调到最优」。
  • 存储侧的三项缺口：① data/yyhelp/kb/chunks.jsonl 的生成命令未确认（候选入口是 kb_build/build.py 或 kb/chunk_md.py --build，未验证哪条实际生成）；② v1 api/app.py 的鉴权实现细节（header 名 / token 来源）未定位到中间件，webapp/auth.py（326 行）未读；③ C1–C6 六条「结构上不可验证」的原文条件与验收方式未逐字读到。

六、面试深挖：追问链 ​

Q：你的记忆存在哪？为什么？

真相源是 SQLite（YYHELP_MEMORY_DB，默认 D:\yyhelp\data\yyhelp_memory.db），Milvus 只做可选的向量索引，默认关（use_milvus=False），集合名 yyhelp_memory_v1，与知识库 yyhelp_kb_v1 物理隔离。

为什么真相源不是向量库？判据是「记忆是用户数据，不是检索产物」：知识库 chunk 丢了可以重切，用户说过「以后都用顺丰」丢了没有任何地方能重建。所以记忆必须落在可审计、可导出、可单条删除的存储里；向量索引是从真相源重建的派生物，它对可用性的要求必须低于真相源。

那为什么默认不开 Milvus？三条：几百条规模下 SQLite 全表扫描 + 本地打分更快（省一次跨进程调用与一次 embed 往返）；让 --selftest 真正离线；Milvus 挂掉不影响主链路这条要求默认就满足了。在这个数据规模上，向量库是负数收益。

Q：凭什么一条记忆值得写进去？

三道闸。长度闸：correction ≤ 200、preference ≤ 120、solution ≤ 300 字符。门槛闸：MIN_CONFIDENCE_BY_KIND 里 preference 0.60、fact 0.75、solution 0.80、correction 0.85，未知 kind 按 0.85。再加每会话同类上限 2 条。

门槛为什么不是统一一个数？因为门槛排的是「错误代价」：correction 写错等于把用户明确纠正过的事记成相反的值，后续再也不会有人纠正它，所以最严；solution 写错会替代一次真实检索，而检索结果可核对、有引用、记忆没有引用，所以次严；preference 写错用户下一句就会纠正，所以最松。

那长度为什么也算一道闸？因为长文本更可能是「整段对话的摘要」，而不是「一条可复用的记忆」。记忆的价值在于短、准、可复用——长度是最便宜的代理指标。

Q：召回的内容直接拼进 prompt 了吗？

没有。 RECALL_POLICY = "state_only"：召回结果写进 state["memories_recalled"]，不拼进 prompt。

为什么不拼？三条理由。可观测性：拼进去之后记忆从结构化数据变成一段文本，trace 里再也回答不了「这次召回了哪几条、哪几条被过滤了、为什么」。可回滚：留在 state 里可以在 finalize 前 retract() 掉，拼进 prompt 之后模型已经看过了，没有「撤回」这个动作。可对比：做「有记忆 vs 无记忆」的 A/B 时，记忆是 state 字段的话，对照臂只要把它置空，两种模式跑的是同一条代码路径。

那代价是什么？模型看不到记忆。 所以「用上了记忆」在当前实现里只到「能召回、能留痕」为止。项目用 render_memory_hint() 提供显式开关，并把它记进未实测清单，而不是偷偷拼进去让指标好看——这是我认为必须如实说的一点。

Q：衰减为什么在召回时算，而不是后台任务定期降权？

因为后台任务会引入「记忆状态取决于上次任务跑没跑」的隐式依赖：任务挂了，过期记忆照样被召回，而且没有任何症状。回忆时现算就没有这个状态——decay(kind, created_at, now) 是个纯函数，1.0 if hl is None else max(DECAY_FLOOR, 0.5 ** (age_days/hl))，落在 [0.30, 1.0]。

那为什么不存衰减值？判据是「能算出来的东西不要存」。存了就要维护，维护就有「谁负责更新、多久更新一次、更新失败怎么办」这一串问题，而收益只是省一次浮点运算。

那为什么 fact 和 correction 的半衰期是 None？因为衰减的前提是「这条信息会过时」。用户说「我住杭州」不会因为过了 90 天就不成立，用户的纠正也不应该随时间失效。给不衰减的内容套上衰减曲线，等于主动把正确记忆丢掉。
