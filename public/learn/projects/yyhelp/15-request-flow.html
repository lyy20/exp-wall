一次请求的数据流全景 ​

一句话：一个 HTTP 请求进来、到 SSE 的最后一个 token 出去，中间只做两件事——每一跳往 state 里写字段，或者在写不下去的时候按一条写死的规则失败。

这一页要回答什么 ​

前面十三页把每个模块单独拆过了：意图识别、检索、工具、记忆、调度、反思、评测。这一页把它们串成一条线，回答三个具体问题：

  1. 一个请求到底经过哪些跳？ 顺序是什么，哪一跳是入口，哪一跳是出口。
  2. 每一跳往 state 里写了什么？ 谁写的、字段名是什么、下一跳读的是哪个字段。
  3. 每一跳失败会怎样？ 是整条链崩掉、还是静默降级、还是留痕继续。

第 3 个问题是这一页的重点。前十三页里出现的真实缺陷，绝大多数不是「代码写错了」，而是「失败得没有形状」——异常被吞成 model_error、中文检索静默返回空、写入的字段没有 reducer。串起来看才看得出来这些坑的共性。

它要解决什么问题 ​

先说清一个容易误解的事实：yyhelp_v2 最初没有服务层，2026-10-09 已补上 serve/app.py（405 行 FastAPI：/chat、SSE、/health 双探针、鉴权 + 限流 + 并发闸）；v1 的 yyhelp/api/app.py（947 行）仍是 v1 基线的一部分。v2 服务层下另有 serve/routing.py（灰度打标 + 模型路由 + 成本记账，是库函数不是 HTTP 服务）与 serve/bottleneck.py（离线实验脚本）。所以：

  • 接入层（鉴权、限流、探针、SSE 帧）属于 v1，v2 没有重写，也不打算重写。
  • v2 的改动全部发生在「图内部」：triage 之后多出 plan / memory / supervisor / reflect，专家出口从「确定性节点」变成「带窄工具菜单的 ReAct 回合」。
  • 灰度打标是在服务层打的（eval/run_ab.py:251 是已确证的调用点），这决定了「线上怎么挂这只标」是一条还没验证的路径（见文末待确认清单）。

把这条链拆清楚，收益是具体的：面试官问「你这个请求从进来到出去花了多少 token、哪一步最贵」时，答不上来说明你只知道模块、不知道数据流。 而数据流恰恰是 Agent 岗位最常被追问的一层。

方案与实现 ​

一次真实请求走一遍 ​

用两条例子里真实存在的测试串走一遍，不构造新例子。

第一条："订单 1001 到哪了"（order_query → order_ops）。

意图层判成 order_query，出口 order_ops，needs_kb=False——这一档根本不进检索。order_ops 专家的窄菜单里有 query_order，schema 是 QueryOrderArgs（tools.py:417）：order_no: str + user_id: str = "u_001"。模型发起调用后走 _run_read（:818）：先算幂等键 _idem_key(tool, args, *, thread_id="", scope="")（:294）查 IDEMPOTENCY_STORE（:278），命中就直接回放首次结果并标 duplicate=True，不执行 fn；未命中才真跑。返回值经 parse_observation（:791）解析、包进 <untrusted_data> 再进模型。

order_no 校验失败的样子也是写死的（_validate_order_no，:469）：空值 → ToolError("INVALID_ARGS", "缺少 order_no（订单号）", detail="示例：order_no=1001")；长度不在 3~32 → ToolError("INVALID_ARGS", f"订单号长度应为 3~32，你给的是 {len(v)} 位：{v!r}", detail="正常订单号形如 1001")。错误信息里带修法示例，是给模型看的，不是给人看的——模型拿到 detail 能自己改参数重试。

复杂度判定为 simple 时，plan 节点整段跳过；模型计划路径的 CLI 会打印成三态标签之一：模型 / 规则兜底（--no-model） / 策略闸（未调用模型）。这三个标签本身就是一次 bug 的产物，见踩坑表第 6 行。

第二条："运费怎么算"（faq_kb → kb_faq）。

出口 kb_faq，needs_kb=True，进检索。混合检索两路并行：稠密路走向量，稀疏路走 BM25，两路结果按 RRF k=60 只用排名融合，再精排。MCP 侧的同一次往返用的就是这个参数组合：("search_kb", {"query": "运费怎么算", "top_k": 3})（mcp/client.py:145-263 自检 B）。工具返回必须满足 mcp_text.lstrip().startswith("<untrusted_data>")——协议边界上照样套注入隔离，不因为「换了个传输方式」就省掉。

跨域那一类长什么样：Gate-1 的 40 题里，转交只发生 3 次（R11 / R18 → agent_free，R24 → order_ops），全部在 2 轮内收尾；每问平均分派轮次 1.075（37 题 1 轮 + 3 题 2 轮）。R24 的类型是「先查政策、拿结论再查订单」——专家在回答最后一行输出 HANDOFF: <出口名>，由 parse_handoff(text, *, allowed)（expert_run.py:231）解析，非法目标留痕忽略。【待确认：R24 的题面原文】，验证命令见文末。

整条链的成本形状（Gate-1 40 题 ×2 臂 = 80 条，平台 deepseek-v4-pro，单次实测 7.76s/次）：每问 token，multi 5,783.7 vs single 6,243.3（差 +459.6，ratio 0.93×）；每问墙钟，multi 20.9s vs single 9.9s（差 −10.95s，2.11×）。串行的代价不在 token 而在墙钟——这一条是整页最值得记住的结论：多出来的那一跳不是更贵，是更慢。

三层追问链 ​

① 为什么一个请求要分这么多跳，而不是一个 prompt 直接问模型？

因为每一跳都在关掉一类不确定性：意图识别把 9 类输入映射成 5 个确定分支，检索把「答什么」变成可核对的行，工具把「订单状态」变成可验证的事实，配额闸把「循环」变成有上界的计数。

那这些跳里，哪一跳是你不敢去掉的？

validate_intent（nlu/intent.py:168）不能去。它上面一行就是 INTENT_TO_EXIT[bad]，而 INTENT_TO_EXIT 是个普通 dict——不做校验的后果是 KeyError → 整个请求 500，源文件 :173 的注释写得很直接。其它跳降级最多是答得差一点，这一跳降级是整条请求不可用。

② 这条链上如果某一跳变慢，你怎么知道是它？

看 trace：每跳都有 span，_iso(ns)（obs/trace.py:267）给的纳秒级时间戳能算出每段耗时；stats(path=None)（:621）与 percentile(xs, q)（:603）给分布，不只看均值。而且 trace_tail（最后 3 行、每行截 120 字符）会被写进每题的采集记录，所以「哪一跳慢」在离线数据里也能复盘。

那如果 trace 里就是没有那一跳的 span 呢？

那就说明这一跳根本没被执行，或者执行了但它的观测没写回 state——这正是 react_messages 永远是 [] 那个坑的形态。所以规程是：trace 里缺一条你以为该有的记录时，先怀疑「观测没落盘」，而不是先怀疑「没执行」；两者的修法完全不同，前者改观测，后者改逻辑。判断方法也很机械：拿执行结果本身当证据（比如工具返回里出现 "未知工具" 或 "INVALID_ARGS"），而不是拿「记录里有没有这条」当证据。

③ v2 多了 plan / supervisor / reflect 三个环节，值吗？

数据上不值得吹：完成率 multi 40/40 vs single 39/40，均值差 +0.025，CI [−0.024, +0.074]，t 检验 p 0.323、Wilcoxon p 1.0 → NSC；token 每问还少了 459.6（0.93×）；但墙钟从 9.9s 涨到 20.9s（2.11×，Holm 校正后仍显著）→ 回归。

那这不是白做了？

不是，但结论必须说准。token 变少意味着「多一跳 ≠ 更贵」，多出来的那跳用更少的 token 把活干完了；墙钟翻倍是串行的固有代价，而 ADR-1 已经论证过为什么不并行（写操作有顺序依赖、专家输出是彼此的输入）。真正要说清的是边界：两臂同对同错 39/40 → 有效样本量 n_eff = 1，这个对比实际上没有判别力，所以「架构更好」这句话在这一版数据上不成立；成立的是「架构没有变差，且成本形状从 token 换成了墙钟，这个交换是自觉的」。
