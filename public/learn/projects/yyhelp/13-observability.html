⑭ 可观测 ​

一句话：这一页讲清 trace 为什么要做成「自研 JSONL 默认 + Langfuse 增强」的双后端，以及降级为什么不能抛异常。

这一页要回答什么 ​

面试官在可观测这一块最常问的三个问题：

  1. 「你为什么要自己写一套 trace？现成的 Langfuse 不是开箱即用吗？」——考的是你有没有想过不引入依赖的代价，以及你知不知道该观测什么。
  2. 「可观测组件本身挂了怎么办？」——这是可观测设计的唯一一道生死题，答「重试」「告警」都是错的。
  3. 「你的 trace 里到底记了什么？出了问题你怎么用它定位？」——考的是字段设计，不是「我打了日志」。

读完这一页，你能答：双后端的分工与缝合方式（同一个 trace_id）、init(prefer="auto") 的选择逻辑、降级路径的事件名清单（8 类可确证的失败归因标签）、trace 里真实存在的字段来源、Langfuse 接入踩到的版本断层，以及「可观测要回答的三个问题」怎么映射到具体字段。

一、它要解决什么问题 ​

1.1 没有 trace，这个系统是不可调试的 ​

客服 Agent 的一次提问不是一次函数调用，而是一条多跳链路：HTTP 进入 → 限流 → 检索（dense + sparse → RRF → 精排）→ 程序层拒答闸门 → LLM 前闸门 → 依赖就绪检查 → 生成 → （若走 Agent 循环）图内 triage → 路由 → 专家 → 工具 → 反思 → 出口。

这条链路上任何一跳出问题，外部症状都是同一个：「答得不对」或「很慢」。没有 trace，下面三种完全不同的故障无法区分：

症状可能的真因没有 trace 时
回答慢检索慢 / 模型慢 / 反思重试到上限只能靠猜
回答错检索没召回 / 专家派错 / 模型答错只能靠猜
答得很贵反思反复重试 / 预算擦边才停完全不可见

第三行是核心动机：「没花钱」和「花了多少」都必须在 trace 里留痕。v1 api/app.py:535 在 LLM 未就绪时打 skipped="llm_not_ready"——「这次生成被跳过、一分钱没花」这件事本身就是被记下来的。

1.2 为什么不全押 Langfuse ​

Langfuse 能给你 UI 和聚合视图，但它是外部依赖：要起 langfuse-web / langfuse-worker / postgres / clickhouse / redis 五个容器（见 deploy/docker-compose.yml）。两个问题：

  1. 离线场景直接失效。 跑 pytest、跑自检、跑离线 A/B（eval/run_ab.py）时，你不可能要求一个 Langfuse 栈在线。而恰恰离线跑批最需要「这次为什么慢」的答案。
  2. 审计场景需要可 grep 的原始数据。 有些分析必须直接在文件上做、不能在 UI 上点：v2 的 eval/run_ab.py 把每个问题的 trace_tail（最后 3 行，每行截 120 字符）与 trace_routing（[routing] 开头的行）直接抄进了评测记录；serve/routing.py:290 的 parse_plan_complexity_from_trace(trace_tail) 还用正则 \[plan\] complexity=(\w+)（:287）从 trace 文本里抠真实复杂度。

第二点是最强的论据：离线评测管线依赖 trace 的文本形态。trace 若只存在于 Langfuse 的 ClickHouse 里，「用 trace 反查真实路由判定」这条通道就断了。

二、方案与实现 ​

2.1 双后端：一个默认路径 + 一个增强路径 ​

v1 obs/langfuse_v4.py（474 行）的类结构就是答案：

类 / 函数行职责
class Backend:122后端抽象
class JSONLBackend(Backend):133默认路径：落 JSONL 文件
class LangfuseBackend(Backend):164增强路径：上报 Langfuse
class _LFSpan:246Langfuse span 的包装

事实清单的原话判据是：JSONLBackend（默认，落文件）+ LangfuseBackend（可选），init(..., prefer="auto") 自动选择。

「prefer="auto"」这四个字符是这一页的题眼：默认走本地，装了且配了才走 Langfuse。选择依据不是「哪个更好」，而是「当前环境能不能用」——langfuse_installed() 判包在不在，langfuse_configured() 判 host/key 配没配。

2.2 两条路径用同一个 trace_id 缝起来 ​

两个后端要能交叉对照，前提是同一张请求在两边是同一个 id。v1 obs/trace.py（674 行）里的 id 生命周期是一整组函数：

  • new_trace_id()(:158) — 造 id
  • current_trace_id()(:170) / set_trace_id(:174) — 读/写上下文
  • propagate(trace_id)(:179) — 跨调用传播（这条是关键，没有它，跨模块的 span 会各自为政）
  • find_trace(trace_id, path=None)(:570) — 按 id 反查

而「一次请求 = 一个 trace」的落点，在服务层是 api/app.py:675 的 @app.middleware("http")——trace_id 中间件在 HTTP 入口就把上下文建好，后面的所有 span 都挂在这棵树上。

2.3 显式降级：trace 失败绝不抛异常 ​

这是这一页最重要的一条设计判据，事实清单把 v1 的原话记下来了：

判据（v1 已定，v2 继承）：可观测降级不抛异常。

「不抛异常」不是「忘了写 try」，而是一条明确的立场：可观测组件不能反过来把主流程搞挂。

理由可以一层一层推：

  1. 可观测是旁路，不是主链路。 用户问的是「我的订单什么时候到」，不是「你的 trace 落盘成功了吗」。为记日志把一次成功的回答变成 500，是拿可用性换日志。
  2. 失败是常态，不是异常。 Langfuse 五个容器里任何一个没起、磁盘满、网络抖——开发机上每天都在发生。如果这些都抛异常，你只能「先把可观测关掉」，那它永远长不出来。
  3. 降级必须可见。 静默吞异常是另一种错误——你会「以为自己在观测，其实什么都没记」。所以做法是：不抛，但写一条事件。本次需求给定的落盘标识是 observability_degraded；可确证的同类失败归因标签见 2.4 的表。

2.5 可观测要回答哪三个问题 ​

把上面所有字段按「问题」而不是按「模块」重排，就是这一页最该背的表：

要回答的问题靠哪组字段典型用法
① 出错了没有2.4(c) 的失败归因标签 + end_trace(status=…)按事件名 grep trace 目录，reflect_exhausted 突然变多 → 反思环节出问题
② 慢在哪一跳Span 的起止（_iso 单调时钟）+ span(name, kind) 的层级 + percentile(xs, q)对同一 span 名算 p95，找最长的那一跳；serve/bottleneck.py 的并发实验用同一思路
③ 花了多少 tokenusage_from_response(resp) + _sum_usage(spans) + cost_usd(...)每问 token 与成本分布；serve/routing.py 侧还有 record_usage(...)(:211) 与 cost_report(budget)(:248)

三个问题的答案全部来自上面的字段：失败归因标签（2.4c）答「出错了没有」；_iso 单调时钟 + span(name, kind) 层级 + percentile(xs, q) 答「慢在哪一跳」；usage_from_response + _sum_usage + cost_usd 答「花了多少」。第三问在 v2 里被放大：serve/routing.py 的模型路由本质就是**「这次该不该花这么多钱」的决策**，决策对不对只能靠 trace 记账回答。

2.6 接 Langfuse v4 踩的坑：v2 legacy API 的三个成员不存在 ​

这是本次接入最硬的一个坑，也是简历上最值得写的一条版本事实：

Langfuse v2 legacy API 里的 trace / span / generation 三个成员，实测全部不存在。

按 v2 旧写法调 lf.trace(...)、lf.span(...)、lf.generation(...)，在这套环境里会直接失败（AttributeError 一类），而不是「不推荐但能用」。这解释了 obs/langfuse_v4.py 里的 _LFSpan(:246) 包装类：接入层不能假定客户端对象上有那几个方法，必须先探测、再适配。

需要把两个 generation 分清楚，否则会在面试里说错：

  • obs/trace.py 侧的 t.generation("generate", model=C.LLM_MODEL)（v1 api/app.py:567）是自研 trace 的 API，它存在、能用。
  • Langfuse 客户端对象上的同名成员，才是「实测不存在」的那个。

五、踩过的坑 / 做过的取舍 ​

现象根因怎么定位到的怎么修的教训
接 Langfuse 时按 v2 legacy 写法调 trace / span / generation，三个成员实测全不存在客户端 API 已换代，旧成员不是「废弃但可用」而是根本不存在实测调用（本次接入记录）加 _LFSpan(:246) 包装层，不再直接假定客户端有那几个方法；失败则走 JSONL 或写降级事件版本断层要按「存在性」验，不能按「文档说废弃了」验
预算告警曾经是一个真实缺陷budget_warnings 被加进 CSState（state.py:436）但 state.py:538 与 new_state()(:476-504) 没跟上v1 state.py --selftest 红着，且从未被 pytest 执行（test_selftests.py 未覆盖）修复后 v1 基线从 125 passed 变成 126 passed（引用时必须带日期，见附录 A 第 6 条）一个从未被执行的自检等于不存在；观测能力自己也需要被观测
只有硬停可见，接近耗尽不可见原来的日志把 answered 都当成「正常」，其中一部分是擦着预算边过去的对照硬停日志（出现 budget_exhausted:step_budget）与正常日志（只有 answered）加第三层 budget_warnings(probe, ratio=BUDGET_WARN_RATIO)(:188)，BUDGET_WARN_RATIO = 0.90(:185)告警必须独立于终止原因
Langfuse 方案看起来「装了就能用」，但离线跑批用不了五个容器（postgres / clickhouse / redis / worker / web）都在 docker-compose.yml 里，离线环境没有它们设计评审阶段就识别出来定 JSONLBackend 为默认默认路径必须零依赖，增强路径才是可选的

六、面试深挖：追问链 ​

Q1（表层）：为什么要自研 JSONL trace，不直接用 Langfuse？

A：因为默认路径必须零第三方依赖。Langfuse 要五个容器（postgres / clickhouse / redis / langfuse-worker / langfuse-web），离线跑 pytest、跑自检、跑 eval/run_ab.py 时它不可能在线。而离线跑批恰恰最需要「这次为什么慢」。所以 v1 就定了双后端：JSONLBackend(:133) 是默认、LangfuseBackend(:164) 是可选，init(..., prefer="auto") 自动选。 追问（中层）：那两边的数据怎么对齐？你不会有两套互相对不上的记录吧？

A：靠同一个 trace_id 缝。id 的生命周期在 obs/trace.py 里是一整组函数：new_trace_id()(:158) 造、set_trace_id(:174) 写上下文、propagate(trace_id)(:179) 跨调用传播、find_trace(trace_id, path=None)(:570) 反查；服务层则用 api/app.py:675 的 HTTP 中间件在入口建好上下文。所以 Langfuse 不是替换品，是叠加品——Langfuse 那一路也会写 JSONL，任何一条 trace 都能被本地 grep 到。 追问（深层）：propagate 这一步如果省了会怎样？

A：跨模块的 span 会各自为政，拿不到父 trace 的 id，一个请求碎成几棵互不关联的树——那就退化成「多了几行日志」，find_trace(trace_id) 与 _sum_usage(spans) 都失去意义。所有「每问 token / 成本 / 墙钟」的聚合，都依赖「一次请求 = 一个 trace 一棵树」这个不变量。

Q2（表层）：可观测组件自己挂了怎么办？

A：判据是 v1 就定下来的、v2 继承：可观测降级不抛异常。trace 或 Langfuse 上报失败时，不把异常抛给主流程，而是降级写一条事件（本次需求给定的标识是 observability_degraded），主流程照常返回。

追问（中层）：为什么不干脆重试到成功？A：因为可观测是旁路。用户问的是「我的订单什么时候到」，不是「trace 落盘成功了吗」。为记日志把本该成功的回答变成 500，是拿可用性换日志。且失败在开发机上每天都在发生，若都抛异常，你只能先把可观测关掉。 追问（深层）：那怎么保证你不会「以为自己记了，其实一条都没记」？

A：靠「降级必须可见」这条配套原则：不抛，但一定要写一条事件。同类做法在代码里有旁证——expert_run.py:361-375 对非法转交目标的处理是「忽略并留痕」；longterm.py::write 把记忆写入失败归成 gate="store" 与 gate="unexpected" 两类；longterm.py::_index_put 单独记 index_error（已写进 SQLite 但 Milvus 索引失败，两种一致性的差别必须分开记）。status()(:551) 与 selftest()(:423) 则是给「观测能力自身」做的体检入口。

Q3（表层）：一次请求慢，你怎么在 trace 里找到是哪一跳慢的？

A：按 span 名分组算分位。写侧是 span(name, kind="span", **kw)(:526) 开 span、class Span(:279) / class SpanRec(:202) 记、Tracer(:350) 串；读侧是 percentile(xs, q)(:603) 与 stats(path=None)(:621)。对同一个 span 名取 p95，最长的那一跳会自己浮出来——这就是「慢在哪一跳」这个问题的完整答案。 追问（中层）：你还记了 _iso(ns)(:267) 和 _iso_wall(:273) 两个时间戳，为什么不只记一个？

A：因为一个不够用。算间隔必须用单调时钟：墙钟会被 NTP 往前或往回校正，一旦回拨，耗时就会出现负值。跨系统对齐必须用墙钟：飞轮的 first_seen_at / last_seen_at 要和 trace 的时间戳对齐，否则「这条问题是什么时候被看见的」就对不上，重放归因会指错方向。 追问（深层）：如果只记墙钟，你会踩到什么？

A：两个具体坑。一是 p95 会被个别负耗时或巨大耗时污染，stats() 给出的分布不可信；二是和飞轮对不齐——飞轮的一整张表就是靠时间戳把「问题池」和「trace」缝起来的，一旦有一边漂了，重放归因就会指错方向。

Q4（表层）：你说的「花了多少 token」是怎么算出来的？

A：不在调用点手写。usage_from_response(resp)(:121) 从模型响应里反解 usage，_sum_usage(spans)(:540) 跨 span 汇总，cost_usd(*, model="", input_tokens=0, output_tokens=0, ...)(:100) 按模型算钱。v2 侧还有一条成本线在 serve/routing.py：record_usage(...)(:211) 与 cost_report(budget)(:248)，价格来自 YYHELP_PRICE_{model}_IN_PER_M(:186) / PRICE_ENV_OUT(:187)，由 price_for_model(model)(:190) 解析、estimate_usd(...)(:240) 估算。 追问（中层）：为什么让代码去「反解」，而不是让调用方自己上报 token 数？

A：因为调用方会忘、会记错、会在异常分支漏记。而 usage 是响应里带的客观事实——从响应反解，等于让记账口径跟着事实走，而不是跟着人的自觉走。这和「可观测要回答三个问题」的第三问是同一件事：这个问题必须有一个不依赖人工纪律的答案。 追问（深层）：成本记账里最容易出现系统性偏差的地方在哪？

A：在「判定」和「实际」不一致的地方。灰度打标与模型路由要按复杂度决定用哪个档位的模型，而复杂度判定本身可能是错的——事实清单里就有一条：规则判定 simple 3 / multi 37，live 判定 simple 34 / multi 0。这两套口径差这么远，成本报表按哪套算，结论会完全不同。这也是台账里 B23 那条「模型路由要先校准『复杂度判定』本身」的由来——判据不校准，路由只是把误判的成本放大。

Q5（表层）：你这条 trace 还能干嘛？除了给人看。

A：它是评测管线的输入。eval/run_ab.py 把每个问题的 trace_tail（最后 3 行、每行截 120 字符）与 trace_routing（[routing] 开头的行）直接抄进评测记录；serve/routing.py::parse_plan_complexity_from_trace(trace_tail)(:290) 再用正则 \[plan\] complexity=(\w+)(:287) 从 trace 里把模型真实判定的复杂度抠出来。 追问（中层）：为什么要从 trace 里抠，而不是直接从 state 读？

A：因为这是「事后审计」而不是「当时取值」。评测要回答的是「当时模型到底判成了什么」，这是已经发生的事实，必须来自不可改写的落盘记录；从 state 读会把「现在的逻辑」和「当时的判定」混起来，改一次代码就污染一次历史结论。 追问（深层）：这条通道断了会怎样？

A：run_ab.py 的评测记录就只有结果、没有过程——你能看到 A 臂赢或输，但说不出为什么，也就无法把差异归因到「路由判错了」还是「专家答错了」。事实清单里 B17「判决『分派错 / 专家答错』」之所以还在未实测清单上，一部分原因就是这类归因需要人工抽检一致率来兜底，不能只靠聚合数字。
