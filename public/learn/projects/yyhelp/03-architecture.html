本页目录

总体架构 ​

一句话：这一页讲清 v2 的分层、依赖方向，以及 mode 对照臂是怎么装出来的。

这一页要回答什么 ​

面试官在项目页上最常问的三个问题：

  1. 「你这套东西分了哪几层？层与层怎么依赖？」
  2. 「你说你做了单智能体和多智能体的对照实验，这个『对照』在代码里是怎么切开的？」——这是最容易被问到崩的一个，因为很多人只会说「我加了个开关」，说不出开关切开的到底是什么。
  3. 「为什么图骨架和内核要分成两个文件？」

读完这一页，你能答：五层结构、单向依赖、四个门面文件各自的真源、mode="single" / mode="multi" 逐维度差异表（六个维度里只有前四个是被测变量），以及为什么「出口定义在 v1 里」这条看起来别扭的设计是刻意的。

一、它要解决什么问题 ​

1.1 为什么不直接改 v1，而要另开一个 code/yyhelp_v2 ​

2026-10-01 的现状审计给出的结论是：v1 的编排逻辑能跑，但它没法支撑一个「可比较的实验」。原因有三条：

第一，v1 的多智能体能力是散在条件边里的，没有显式结构。 v1 的 graph/build.py 只有 7 个节点，"多个智能体"体现为几条条件边加一组工具，专家边界、工具可见性、派发配额都没有一个可以画出来的东西。要做 A/B，被测变量必须先是「一个能被指认的结构」，否则「multi 臂」到底是什么，说不清。

第二，v1 缺对照臂。 没有 single/multi 两条同源路径，就永远只能给出「我觉得多智能体更好」这种话。v2 的架构第一考量的不是「怎么更强」，而是「怎么让差异可归因」。

第三，v1 的工程底座有硬伤。 40 个根目录工具脚本、12 个功能重复的评测记录器、11 个从未被 pytest 执行的 selftest。不改出一个新目录，改动就会和这些历史包袱纠缠。

1.2 架构的第一判据是「能不能做 A/B」」 ​

所以 v2 的目录不是「更漂亮的重构」，而是为实验服务的脚手架：哪两个变量是要测的（编排结构与工具可见性）、哪些东西必须两臂完全一样（ReAct 执行内核、四道闸、三类终止条件）、哪一条差异是为了让实验干净而故意加的（run_single 走 v1 的通用人设、不做 HANDOFF 解析）。

这条判据在代码里的落点就是 MODE_REPORT（graph/supervisor.py:1151）与 PARALLEL_UPGRADE_CRITERIA（:1174）——模式的能力差异被写成了一个字典而不是靠注释描述，这样「single 臂到底少了什么」随时可以先打印出来再跑实验。

依赖方向是单向的：编排层依赖专家定义与执行体，专家执行体依赖工具与状态；工具层与记忆层不反向依赖编排层。入口层只负责「把输入装进 state、把图吐出来的 state 变成响应」，不参与任何路由决策。

这条约束不是洁癖，它直接对应 v2 建设期踩到的两个真实 bug：

  • plan.py 出现过循环 import（bug #9 之一）；
  • plan.py 曾经写 EXITS 的导入路径指向 yyhelp_v2.graph.experts，而这个符号在 experts.py 里根本不存在——名字写错了，但错误在 import 期未必立刻暴露，最后是在跑图时以别的形态炸出来的。

2.4 mode 的两个取值：逐维度对照 ​

Mode = Literal["single", "multi"]（supervisor.py:195）、MODES = ("single", "multi")（:196）。两臂的差异不是「差不多」，而是可逐条列出的：

维度mode="multi"mode="single"性质

决策者supervisor（LLM 决策 + 规则约束）v1 nlu 的 9 类意图 → 5 出口映射被测变量
工具可见性tools_for(spec.name)，每专家 1–3 个V1_TOOL_NAMES 全量 5 个被测变量

图上的落点（节点名）expert_<出口>复用同一个节点名 expert_agent_free实现细节
state 输出键expert_outputs[<专家名>]expert_outputs["single_agent"]（SINGLE_AGENT_KEY，supervisor_core.py:97）实现细节
ReAct 内核v1 run_reactv1 run_react（完全相同）控制变量
四道闸 + 三类终止条件v1 原样v1 原样（完全相同）控制变量

最后两行是这张表的重点：两臂共用同一个执行内核、同一套闸门与终止条件，所以任何观测差异都只能归因到上面几行。如果连 ReAct 内核都各写一份，「multi 更快/更慢」就同时混入了「内核实现差异」这个混淆项，实验直接作废。

「节点名」与「输出键」为什么分开设计，值得单独说一句：run_single 复用了 expert_agent_free 这个节点名（否则建图要为一个模式开一条完全平行的节点链），但它的输出不能假装自己是 agent_free 专家跑出来的（那样下游统计就分不清「谁答的」）。于是节点名复用、输出键另开 single_agent——结构复用、语义不污染。

2.5 出口定义为什么在 v1 里 ​

EXITS 的真源是 v1 yyhelp/graph/build.py:128：

python
EXITS = ("kb_faq", "order_ops", "refund_flow", "service_ops", "agent_free")
1

v2 不重新定义一份，而是从 v1 导入。理由是：v1 的 nlu/intent.py:69 的 INTENT_TO_EXIT 已经把这个映射写死成 9 类意图 → 这 5 个出口，而 v2 的 single 臂必须复用 v1 的意图映射——如果 v2 自己再定义一份出口元组，就会出现「v1 说 9 类意图映射到 A 集合、v2 的建图说映射到 B 集合」这种没人能发现的分叉。出口是两臂共享的坐标系，共享的坐标系只能有一个定义。

同一条原则还体现在 eval/run_ab.py:424 的 _VALID_EXITS：评测侧也要校验「图里出现的出口名是否合法」，它同样对着这一份定义。而 plan.py 曾经把导入路径写成 from yyhelp_v2.graph.experts import EXITS——experts.py 里没有这个符号。这条错误的形态很典型：不是逻辑错，是「我凭记忆写了一个应该存在但其实不存在的名字」。

四、一次真实的请求走一遍 ​

以 mode="multi"、一句跨领域的输入为例（下面每一步标出输入形态 → 输出形态）：

  1. 入口：请求体 → CSStateV2（new_state_v2(query, *, mode="multi", **kw)，state_v2.py:668）。此时 14 个新字段由 _NEW_DEFAULTS（:632）填默认值：plan=[]、current_step=0、handoff_log=[]、expert_outputs={}、reflections=[]、retry_count=0、memories_recalled=[]、route_version=""、model_used=""、model=""、_next_expert=""、_memory_hint=""、_reflect_hint=""、_reflect_dispatch={}。
  2. triage：classify(utterance, recent=None, *, rule_confidence=0.95) 返回 IntentResult，再经 validate_intent(raw)（intent.py:168）校验，得到 IntentOut | None 和一个原因字符串；出口经 INTENT_TO_EXIT 落到 5 个出口之一。
  3. plan：decide_policy 先判定复杂度；complexity="simple" 跳过规划，否则 _model_plan 出计划、validate_plan 校验，PLAN_MIN_STEPS=2 / PLAN_MAX_STEPS=3 夹住步数。source 会记成 "model" / "injected" / 规则兜底之一——这一步的形态是 list[dict]，写进 state["plan"]。
  4. supervisor：dispatch_quota(state) 先算 (used, limit)，limit 来自 DISPATCH_LIMIT=2，而且这个数已经写进了 prompt（supervisor_system_prompt(*, used=0, limit=2)）——能被事前告知的约束，不要只做事后拦截。然后 _model_decision 或 _rule_decision 出决策，validate_decision 校验，_with_rules 再上三重约束（去重、与计划一致、配额）。
  5. 专家：run_expert 只给这个专家 tools_for(spec.name) 的工具（1–3 个），跑完返回 ExpertOutcome。这个结果是被追溯的：trace 里带着 tools_visible，tools_visible 与真正发给模型的 schema 名集合是同一个集合。
  6. 回环或终止：route_after_expert 看三件事——专家输出里有没有合法 HANDOFF: <出口名>、配额还有没有剩、有没有命中四类失败信号。三种组合分别指向 supervisor / reflect / finalize。
  7. 出口：finalize 调 summarize(state) 取 expert_outputs 拼答复。注意 expert_outputs 的 reducer 是 merge_dict（跨轮合并，每个专家/轮次一个键），所以多轮派发的结果不会互相覆盖。

五、踩过的坑 / 做过的取舍 ​

#现象根因怎么定位到的怎么修的教训
1bottleneck 块实测并行收益只有 1.02×块构造本身持有 GIL，并行度被构造阶段吃掉并发度 8、取 3 次中位数重测，得到 6.41×；对不上说明测的是构造不是热点把构造移出被计时区间基准测试里测错对象比没有测试更危险：1.02× 会让人得出「并行没用」的反向结论
2pypure 空函数把性能热点测错空函数不产生开销，计时区间量不到真实成本与真实函数对比复测用真实实现重测占位实现不能进性能基准
3图能编译、请求一发就结束memory 节点有一条指向 __end__ 的边，被编译成替换主链路跑图时链路直接到 END删掉该边，memory 只连 supervisor回环/收尾节点不能直连 END；reflect → __end__ 是同一族教训（在 reflect.py 自检 [5] 里固化成断言）

取舍一：为什么不把专家执行体合进 supervisor.py？ 1,827 行已经太大。但它更大的问题是：supervisor.py 是唯一知道节点名的地方，一旦专家执行逻辑也写进去，「专家定义 → 执行 → 建图」这三件不同生命周期的东西会被绑在一个文件的 import 图里，任何一处改动都得重新验证整个图。

取舍二：为什么不给 single 臂建一条平行的节点链？ 那样两条链会各自漂移，「控制变量」这条实验前提就守不住了。复用 expert_agent_free 节点名、另开 single_agent 输出键，是用最小的结构代价换回可归因性。

取舍三：MCP 层为什么不放在编排层里？ mcp/ 只依赖 mcp + anyio，不依赖 langgraph。工具服务不应该知道「谁在编排、编排成什么样」——这既是分层原则，也是「工具并集 == v1 全量工具集」这条结构性断言能成立的前提。

六、面试深挖：追问链 ​

Q：你这套架构分层是怎么定的？

按「谁在什么时间知道自己需要什么」定的：入口层只知道怎么把 HTTP 变成 state；编排层是唯一知道节点名与边的地方；专家层只知道自己那 1–3 个工具；工具与存储层完全不依赖上层。依赖是单向的，所以 experts.py 是纯数据、expert_run.py 是纯流程，supervisor.py 才需要同时看见两者。

那 supervisor_core.py 为什么单独存在？因为它做的是 prompt 构造与消息列表注入这类纯字符串操作，不需要图；把它拆出来，supervisor_system_prompt(*, used, limit) 才能被单独自检（比如断言配额数字真的出现在 prompt 文本里），否则只能通过跑一遍图来看 prompt 长什么样。

Q：你说做了单/多智能体对照，这个对照在代码里怎么切的？

一个 mode 参数（Literal["single", "multi"]）在 build_supervisor_graph 里切两件事：节点集合和决策者。multi 有 plan/supervisor/memory/reflect 四个节点、决策者是 LLM 加规则约束、每专家只见 1–3 个工具；single 没有那四个节点、决策者是 v1 的 9 类意图到 5 出口的映射、菜单是全量 5 个工具。两臂共用一个 ReAct 内核、一套闸门和三类终止条件。

那两臂的 state 一样吗？不完全一样：multi 用 CSStateV2（14 个新字段），single 沿用 v1 的 CSState，这是有意保留的不对称——对照实验要测的是编排结构，不是 state 字段数量。但输出键必须分开：single 写 expert_outputs["single_agent"]，不能占 agent_free 的键，否则统计时「谁答的」就分不清了。

Q：memory 节点为什么不能直接连 __end__？

在 LangGraph 里，__end__ 是一条真实的终止边：memory → __end__ 会被编译成「memory 执行完就结束这次调用」，也就是替换掉主链路，而不是「顺便收个尾」。我们发现时是图能编译、请求一发就直接返回。

那你怎么保证以后不再犯？把这条固化成断言。reflect.py 的自检 [5] 就明确检查「reflect 不能直连 __end__」，memory 侧是删边加进边表检查。同一族教训出现两次之后，它就不再是「注意事项」而应该是一条能被运行的自检。

Q：mode 这个开关为什么不做成运行时动态切换？

因为它是实验因素，不是产品开关。MODES = ("single", "multi") 是建图期参数，一旦允许运行时热切换，就会有人在一个会话里切两次，expert_outputs 就同时混进了 agent_free 和 single_agent 两种来源，评测口径立刻失效。要做灰度，那是 serve/routing.py 的事——灰度灰度的是流量，不是架构。
