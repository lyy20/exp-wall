项目深挖预演 ​

面试里真正决定生死的不是「你会什么」，而是面试官顺着你的项目往下问三层，你能不能站住。 这一页把两个项目里最容易被打穿的地方，连同「问到了怎么答」一次性摊开。

一、电梯陈述（背两种长度） ​

30 秒版 —— YYHelp

面向电商客服的多轮对话 Agent。我用 LangGraph 把 9 类意图分流到 5 个出口，各子流程汇合到同一个 ReAct 内核；重点不是把检索做准，而是让多轮对话能可靠地把事办完——所以做了会话状态持久化、中断恢复、写操作的幂等键和人工确认。最后用 40 对配对盲测回答了一个问题：多智能体到底值不值。

30 秒版 —— 科研文献 RAG

面向 AI 领域科研文献的检索增强问答服务：混合检索 + 重排序 + 引用溯源 + 双层拒答，外面套一套分层评测集。最有意思的是这个领域的边界天然给了我一批真正不可回答的题——知识库里只有 RL / USV / 控制方向文献，你问它 Transformer 的 KV Cache 显存怎么估，它必须拒答，而不是拿 RL 论文硬凑。

2 分钟版：在上面基础上各加三件事——「遇到的三个具体故障」「每个故障我怎么定位的」「最后用什么数字证明修好了」。下面的追问链就是素材库。

二、开场就会被问的三个问题 ​

问题错误答法正确答法
「这个项目是你一个人做的吗？」「我们团队做的」先说清哪几块是你独立完成的，再说明哪几块是参考/协作。含糊过去，后面每句话都会被怀疑
「大概多少人用？」编一个 DAU「没有真实用户，知识库是合成语料，评测集是我自己标注的」——这句直接说出来，比被戳穿强一百倍
「这个项目有什么不足？」「没什么不足」直接背「未实测清单」里那三条。主动交出边界是加分项

三、YYHelp 追问链 ​

链 1：多智能体——最容易被问、也最能加分 ​

Q：你这个多智能体系统比单智能体好多少？

A：最新一轮（120 题）的答案是可以下定论的：没有更好，反而显著更差。 完成率 multi 63.3% vs single 77.5%（−14.2pp，t p=0.00053、Wilcoxon p=0.0032，Holm 校正后仍显著）；墙钟 24.7 s vs 17.3 s（1.43×，p≈0）；只有 tokens 是 省 12.5%（4,708 vs 5,379，p=0.00034）。结论：不切换。

Q：这个结论是第几次拿到？

A：第四轮。 第一轮 40 题拿到的是「完成率 40/40 vs 39/40 不显著、墙钟 2.11× 显著更差」，我当时说的是「不证」不是「证否」。但那轮的完成率数字是假的——做人工锚定抽样时查出三层根因：① 检索后端从来没接上（跑的是关键词替身）；② 向量路因环境变量指向空目录而静默降级；③ 裁判 rubric 把「礼貌拒答」判成完成任务。修完后完成率掉到 60-75%，这才是真实水平；再修生成层缺陷到 70%/70% 打平；最后扩样到 120 题才显著。

Q：扩样是不是为了让结论变显著？

A：不是，是功效算出来的。 n=40 时置信区间是 ±14pp，真实的 −14.2pp 刚好落在可检出边界外——「测不出不等于没差异」这句话在当时那版结论里就写着。ψ=0.208 时测 +5pp 需 652 题、+10pp 需 161 题，小幅差异我到现在也判不了。扩样用的是同 40 题的三个问法变体（语义一致、gt 复用），不是为了凑数——顺带还暴露了机制：换问法后 multi 掉 6.7pp、single 升 7.5pp，说明 multi 的脆弱点在分派鲁棒性，不在模型能力。

注意：这条链的关键不是背数字，是能讲清「数字为什么变过三次」——面试官问「40 题够吗」或者「你确定这个结论吗」时，主动交代四轮链条的人，和只会背一个数的人，可信度完全不同。

链 2：写操作与副作用 ​

Q：你说做了写操作，具体怎么保证不重复下单/重复建单？

A：写操作走幂等键 + 人工确认两步：先按业务参数算出幂等键，同一个键重复提交不产生第二个副作用；需要确认的动作会让图中断，等人确认后再恢复。

Q：那你的工具是怎么定义的？

A：@tool 装饰器 + pydantic 入参校验。校验失败是不炸图的——错误被当成工具结果写回 state，让 Agent 有机会改参数重试。

Q：MCP 那边呢？你把写操作也暴露给 MCP 了吗？

A：没有，这是刻意的。 MCP server 只暴露 2 个只读工具（search_kb、query_order），另外 3 个（create_ticket、query_refund_policy、query_logistics）明确禁止暴露。理由：幂等键和人工确认必须由我自己的编排层统一管，把它们交给外部的 MCP 通道就等于把副作用的一致性交出去了。

这一问是高危题。如果你的简历上写了"建工单"，面试官很可能顺着 MCP 这条线问下来——所以上面这个答案要在面试前说顺。

链 3：中文检索那个静默故障 ​

Q：检索层遇到过什么坑？

A：Milvus 的默认 analyzer 会让中文查询的 BM25 静默返回空——不报错、不抛异常，只给你一个空列表。我切到 jieba 分词后才恢复命中。

Q：你怎么发现一个"不报错"的故障的？

A：因为我在配置类开关上都配了**「能失败的断言」**——光验"没报错"等于没验。中文分词这件事就是活例子：如果我当时只写了一个 try/except 看它没抛异常，这个 bug 会一直挂着。

Q：具体怎么配的？

A：analyzer_params={"tokenizer": "jieba"} 写在建 collection/索引的地方。另外注意 Milvus 是 2.5.0 起才引入 BM25，Function API 是 2.6.x 起——版本不满足时行为不一样。

链 4：编排层的装配错误（最"真"，面试官最爱） ​

Q：LangGraph 的条件边你有什么踩过的坑？

A：有一个很典型的：add_conditional_edges(source, path_fn, path_map) 的第三个参数是「path_fn 的返回值 → 目标节点」的映射表。我第一版让 route_by_exit 返回的是节点名，却把 EXIT_TO_NODE 当成 map 传进去，结果 KeyError: 'agent_memory'。

Q：那这个 bug 难查吗？

A：难在它「能 import、能编译、一跑就崩」。 纯函数单测测不出来——因为 route_by_exit 自己返回得没错，错的是装配关系。

Q：所以你的结论是什么？

A：装配错误必须靠运行图来验，不能靠读代码。 这条后来变成了我的纪律之一。

同类还有一处：v1 有 11 个 selftest 从未被 pytest 执行过——代码写下了、函数也在，就是没人跑。所以 state.py 的一个缺陷"红了不知道多久"。「写下 ≠ 执行」。

链 5：可观测性为什么不能影响主链路 ​

Q：你为什么自己写 JSONL trace，不直接用 Langfuse？

A：两个都接了，但 JSONL 是默认路径、Langfuse 是增强路径，用同一个 trace_id 缝合。JSONL 零第三方依赖、离线可审计。

Q：那观测组件挂了会怎样？

A：写入失败绝不抛异常，只在业务事件里写一条 observability_degraded。观测面炸了不应该把主链路带崩。

Q：这跟"可观测"的目标不冲突吗？失败了你还观测什么？

A：冲突，所以要显式降级——不是静默失败。降级本身是一条可被查询、可被告警的事件，而不是"什么都没发生"。

四、科研文献 RAG 追问链 ​

链 1：拒答（这个项目的招牌） ​

Q：拒答怎么做的？

A：双层。 程序层用重排后的 top1 分数 < 0.30 直接拒答，零成本；模型层再自报 insufficient 兜底。

Q：0.30 这个阈值怎么定出来的？

A：不是拍的。可回答题的 rerank top1 分数中位数 0.9617，不可回答题是 0.0127——两堆分数完全可分，阈值放在中间任何位置结果都一样，我选了 0.30。

Q：那两层各自的代价你测过吗？

A：测过，而且分开测：程序层误拒率 1.6%，模型层 6.5%。所以程序层是主力，模型层只是兜底——因为它们成本差三个数量级。

链 2：混合检索一定会更好吗（最能体现判断力） ​

Q：混合检索一定比单路好吗？

A：不一定，我实测崩过。 扩库之后混合检索的 R@5 从 64.5% 掉到 29.2%。

Q：根因是什么？

A：中文查询的 BM25 top-20 全部来自那两篇中文文献——知识库里大部分是英文文献。所以稀疏路给出的是一堆"同语言但不同主题"的结果，把融合结果整体带偏了。

Q：你怎么修的？

A：加了一个自检失效机制：两路 top-20 的交集小于 2 时，丢掉稀疏路，只走向量路。取交集是个很朴素的信号——两路都认为相关才说明这条召回可信。

Q：这个 2 是怎么定的？

A：这是拍的，我承认。 我当时的依据是"交集为空或近乎为空就说明两路没有共识"。更好的做法是拿验证集扫一遍 0/1/2/3 看哪个点收益最大——这一步我没做。

链 3：Recall@10 == Recall@5（最会暴露"你有没有真看数据"） ​

Q：你的 recall@10 和 recall@5 一样，是排序特别完美吗？

A：不是，那是我自己标注窗口造成的构造结果。 我的机器 ground truth 候选只取了 retrieve()[:5]，人工标注时人只看了前 5 个——所以 R@10 在数学上不可能高于 R@5。

Q：发现之后呢？

A：把候选窗口放大重标，立刻暴露出一件事：不做精排时，R@10 比 R@5 高 11–14 个百分点。也就是说排序损失一直存在，只是被我的评测口径掩盖了。

Q：这件事教了你什么？

A：评测口径会制造假的结论。 我现在所有报告都强制带「gt 版本 + 标注密度」这个标尺，而且机器标注出的报告顶部我自己写了一句「🚫 不可作为结论」。

链 4：性能瓶颈（反直觉） ​

Q：首字延迟多少？瓶颈在哪？

A：实测 14.90 / 10.00 / 14.86 秒。反直觉的地方是——瓶颈不是 LLM。

Q：那是哪？

A：CPU 上的精排，20 对大约 8.5 秒。 而 LLM 生成的 P50 只有 1.26 秒。

Q：那你一开始的优化方向对吗？

A：不对。我一开始想的是换更快的模型——这是被这份延迟分解否掉的。如果没做分解，我大概会花几天换模型然后发现没变快。

链 5：服务冷启动 ​

Q：服务启动怎么处理的？

A：后台线程预热模型——不预热的话 uvicorn 要等 30 多秒才监听端口。

Q：那预热生效了吗？

A：没有，这是我踩的坑。 预热做了，但 /health 秒回 200，编排系统在模型加载完之前就把流量导进来了，第一个请求照样等 48 秒。

Q：正确做法？

A：liveness 和 readiness 分开。 liveness 只回"进程活着"，readiness 必须验"业务最依赖的那一次真实调用能不能过"。探针要验的是真实调用，不是"对象能构造出来"。

三句可以放心用的话：

  1. 「这个我没测过。我的判断是……如果让我验证，我会这样验……」
  2. 「这个数字我记不精确。我能确定的是它的口径是……」
  3. 「这块我确实没做过，我只了解原理层面。」

一句永远不要说的话：「我们当时……」——只要你说了「我们」，面试官下一句一定是「你们几个人？你负责哪部分？」

六、数字口径速查（面试前扫一眼） ​

数字必须一起说的口径
指标值
------
多智能体完成率63.3% vs 77.5%（−14.2pp）
多智能体墙钟1.43×（24.7s vs 17.3s）
多智能体 tokens省 12.5%（4,708 vs 5,379）
分派鲁棒性原题 70% → 变体 63.3%（multi）；70% → 77.5%（single）
功效+5pp 需 652 题 / +10pp 需 161 题 / +20pp 需 39 题
四轮链条100/97.5（假）→ 60/75 → 70/70 → 63.3/77.5
v1 11 个 selftest 从未执行自检入口总数 v1 14 + v2 16 = 30
RAG R@5 64.5% → 29.2%扩库前后的同一评测集对比，macro 口径
RAG 拒答 1.6% / 6.5%分别是程序层与模型层的误拒率，分开测
RAG 首字延迟 14.9 s精排 8.5 s + LLM P50 1.26 s；单机 CPU 精排
R@10 − R@5 = 11–14pp不做精排时的差值；做精排后差值收窄

三个红线

  1. 不报没口径的数。 「recall@5 是 64.5%」这句话本身没有信息量。
  2. 不说空洞形容词。 「极大地提升了效率」= 告诉面试官你没数据。
  3. 不编。 你两个项目的"未实测清单"里那几条，主动说出来是加分，被问出来是减分。
