工程与系统设计题 ​

系统设计题的通关方式只有一条：把需求问清楚，再给方案。 一上来就画架构图的人，会被面试官在最关键的取舍点上问穿。这一页每道题都按同一套骨架写： 题目 → 先问清需求 → 分层方案 → 关键取舍 → 追问链 → 常见错误答法。 所有数字都来自你自己的两个项目（YYHelp v2 与科研文献 RAG），带口径写在正文里；没有出处的量级都标了「以实测为准」。

一、设计一个 RAG 问答服务 ​

先问清需求（这一步是加分动作，不是客套） ​

不要说「那我开始了」，而是先问四件事：

  1. 知识库规模和更新频率——几万块还是几亿块？每天增量还是季度重建？这一条决定索引选型（Flat 还是 ANN、要不要增量索引）。
  2. 质量要求与失败定义——答错和拒答哪个更贵？有没有合规或引用可核对的要求？这一条决定要不要拒答闸门和引用核验。
  3. 延迟目标与并发量——首字延迟目标是多少秒、峰值 QPS 多少？这一条决定精排放在 CPU 还是 GPU、要不要缓存。
  4. 权限模型——所有人看到同一份知识库，还是按用户/租户隔离？这一条决定检索层要不要带过滤条件。

问完之后给一句判断，把主动权拿回来：「按你说的量级，这个系统的瓶颈大概率不在向量检索，而在精排和生成的串行等待——我会按这个假设先设计，如果压测推翻了再调。」

五层职责（面试时按这个顺序讲，每层一句话）：

层职责关键设计点
接入层鉴权、限流、并发闸门、trace_id顺序不能换：鉴权在限流之前
编排层查询改写、多路检索、融合、精排、拒答判定每个可跳过的步骤都要能关掉（消融实验需要）
模型层LLM 调用、超时、重试、降级超时预算要加上游剩余预算一起算
数据层向量索引 + 稀疏索引 + 元数据索引与查询必须调同一个分词函数
观测层trace、指标、成本归因写入失败绝不抛异常

关键取舍 ​

  • Flat vs ANN：我的实测结论是先别换 ANN。理由是精排 20 对要 8.5 秒（CPU），而 Flat 搜索在 52 万块量级仍是毫秒级——换 ANN 省下来的时间在总延迟里看不见，却要付出召回损失。什么时候必须换？当检索本身成为瓶颈时（通常是千万块以上），并且换之前要建一套「ANN vs Flat 的 recall 对比」——换索引是要拿召回换延迟的，这个交换必须被量化。
  • 精排放哪：Cross-Encoder 精度高但贵。放 CPU 便宜但慢（这就是我 8.5 秒的来源），放 GPU 快但要占显存。先确定精排是不是瓶颈——在我的链路上它是。
  • 拒答闸门放程序层还是模型层：程序层零成本零延迟、可解释；模型层灵活但每次都花钱。两者成本差三个数量级，所以主力必须是程序层。
  • 离线与在线分离：索引构建绝不能在请求路径上做。这条不是优化，是架构底线。

追问链 1：从架构问到「你怎么知道它变好了」 ​

Q：这套架构里你怎么测？

A：分三层。检索层测 recall@k 与 MRR，分母是人工标注的 ground truth 块；生成层测忠实性（答案能不能被引用块支撑）与切题度；端到端测任务完成率和延迟。而且每份报告必须带「gt 版本 + 标注密度」这个标尺——因为我的评测口径曾经制造过假结论。

Q：什么假结论？

A：Recall@10 和 Recall@5 相等，看起来像「排序已经完美、扩召回没用」。实际是我的机器 gt 候选只取了前 5 个、人工标注时人只看了前 5 个——R@10 在数学上不可能高于 R@5。把候选窗口放大重标之后，立刻暴露出「不做精排时 R@10 比 R@5 高 11 到 14 个百分点」。

Q：这件事对系统设计有什么影响？

A：影响在评测必须是系统的一部分，不是项目结束后的补作业。我的设计里因此多了两样东西：一是每次改动都能跑的分层评测脚本，二是一条纪律——机器生成的 gt 报告顶部必须写「不可作为结论」。因为一份口径错的报告比没有报告更危险：它会让整个团队往错的方向优化。

常见错误答法 ​

错误说法问题改成什么
直接开始画架构图没问需求就下结论，面试官会挑一个你假设错的前提穷追先问规模、质量要求、延迟目标、权限模型
「切块就按 512 字符固定切」忽略文档结构，表格和公式会被切散「结构感知优先，表格绝不拆散；固定长度作为兜底」
「上 ANN 提升性能」没判断瓶颈在哪「先测检索占端到端延迟的比例，我的实测里它不是瓶颈」
「用大模型兜底，答不出来就让它自己判断」把拒答交给最贵且最不可靠的部件「程序层阈值拒答是主力，模型层只是兜底」
「评测就抽几条看看」没有可重复、可比较的口径「分层评测集 + 每次改动跑一次 + 报告带标尺」

二、设计一个多轮对话 Agent 的服务端 ​

先问清需求 ​

  1. 会话长度与状态规模——平均几轮？要保留多久？决定状态存哪、要不要摘要压缩。
  2. 是否有写操作——只读问答和「帮你下单」的安全性要求差一个数量级。决定要不要人工确认与幂等。
  3. 并发模型——每用户串行还是允许并行？决定会话级锁的粒度。
  4. 中断恢复要不要支持——用户关掉页面再回来，对话要不要接着走？

分层方案 ​

四件事必须分开讲，因为它们是四个不同的问题：

问题方案关键点
会话状态存哪生产用外部存储（关系库或 KV），进程内只做缓存多 worker 时进程内状态会丢；uvicorn --workers 4 等于四份状态
会话内并发同一会话串行、跨会话并行同一 thread 并发写会互相覆盖；用会话级锁或乐观版本号
超时分层预算：总预算 → 每步预算 → 每次模型调用预算上游慢的时候不能还按原来的超时重试，否则超时叠加
中断恢复每一步把状态持久化，恢复时从最后一致点续跑关键是有没有「已执行的副作用」记录，否则恢复会重复执行

我实际用的是图式编排：把 Agent 拆成状态图里的节点，每一步流转后落一个检查点；需要确认的动作让图中断，等外部输入再恢复。这样「恢复」不是重跑，而是从检查点继续。

关键取舍 ​

  • 状态放进程内 vs 外部：进程内快、零依赖，但多 worker 下就是错的。我的 MCP 服务暴露的写操作刻意收窄，就是为了避免跨进程一致性问题。
  • 中断恢复 vs 无状态重试：中断恢复复杂但体验好；无状态重试简单但会把已经做过的副作用再做一次——所以幂等键是中断恢复的前置条件，不是可选项。
  • 乐观锁 vs 悲观锁：会话级悲观锁实现简单，代价是同一会话完全串行；乐观版本号并发好，但要处理冲突重试。对客服场景，串行是可接受的，因为用户本来就是一次问一句。

追问链 2：会话状态与并发 ​

Q：两个请求同时修改同一个会话，会怎样？

A：会互相覆盖。具体表现是「用户刚确认的信息丢失了」，而且不会报错。我的处理是会话级串行：同一 thread_id 的请求排队，跨会话并行。这样最坏情况是同一用户等待，不会出现状态错乱。

Q：那如果用户开两个标签页同时发问？

A：这是同一会话并发，我的策略是后到的请求要么排队、要么拿到一个明确的「会话忙」响应——绝不能两个都悄悄跑。这里有个细节：排队要有上限，否则一个卡住的请求会把后续全部堵死。所以要配一个队列长度 + 等待超时。

Q：你怎么验证这套机制真的生效？

A：并发发两个写请求，断言副作用只发生一次。 这条断言必须能失败——如果我把会话锁去掉，它必须变红。这就是我一直强调的：只验「没报错」等于没验。

常见错误答法 ​

错误说法问题改成什么
「会话状态放内存字典就行」多 worker 下直接错「进程内只做缓存，真源放外部存储；并说清 worker 数量这一前提」
「并发用全局锁保护」粒度太粗，吞吐被一锅端「会话级串行、跨会话并行」
「超时统一设 60 秒」没有预算概念，重试会叠加「总预算 → 每步预算 → 单次调用预算，逐级收紧」
「失败了就重试整个流程」有写操作时等于重复执行「幂等键 + 检查点恢复，而不是整流程重放」
不谈「同一会话并发写」面试官会认为你没想过状态一致性主动把这个问题说出来并给出策略

三、限流怎么做 ​

先问清需求 ​

问一件事就够：「限流的目的是保护后端，还是做配额计费？」目的不同，实现完全不同——保护后端看的是瞬时并发，计费看的是周期累计。

分层方案 ​

① 算法选型：滑动窗口 vs 取整分钟

我不推荐「计数器 + 取整分钟」——它在边界处会放行两倍流量：59 秒发满 60 个、61 秒再发满 60 个，两秒内实际过了 120 个。

滑动窗口的做法是用一个 deque 存每次请求的时间戳：每次先弹出窗口外的旧时间戳，再看窗口内的个数是否超限。代码只有 20 行，边界问题直接消失。

python
import time
from collections import deque
import threading

class RateLimiter:
    """滑动窗口限流：用 deque 存时间戳，而不是「计数器 + 取整分钟」。

    取整窗口在边界处会放行 2 倍流量（59 秒 60 个 + 61 秒 60 个 ⇒ 两秒 120 个）。
    """
    def __init__(self, per_min: int) -> None:
        self.per_min = per_min
        self._hits: dict[str, deque[float]] = {}
        self._lock = threading.Lock()

    def allow(self, key: str, now: float | None = None) -> tuple[bool, int]:
        """返回 (是否放行, 剩余额度)。"""
        now = now if now is not None else time.time()
        with self._lock:
            dq = self._hits.setdefault(key, deque())
            while dq and now - dq[0] > 60.0:      # 弹出窗口外的旧时间戳
                dq.popleft()
            if len(dq) >= self.per_min:
                return False, 0
            dq.append(now)
            return True, self.per_min - len(dq)

② 顺序：鉴权必须在限流之前

这一条单独成段，因为它是最容易被做反、后果最严重的一条：

如果限流在鉴权之前，攻击者可以用没有任何权限的请求把配额吃光，合法用户就被挤出去了——限流从一个保护机制变成了拒绝服务放大器。

正确顺序：鉴权 → 限流 → 并发闸门。未授权的请求返回 401，且不消耗限流额度。这条我实现为一个统一的前置依赖，并在注释里写死了「顺序不能换」。

③ 分布式限流

单进程内存版在 uvicorn --workers 4 下每个 worker 各有一份计数，实际放行量变成 4 倍。所以：

  • 单进程/单机小流量：内存版够用，但必须把「多 worker 会放大」写进注释，否则「我配了 60/min」是假的。
  • 多实例：用共享存储（Redis 的计数 + 过期）或直接在网关层限流。
  • 更稳的做法是「网关粗粒度 + 应用细粒度」两层：网关挡住洪峰，应用按用户/租户做精细配额。

关键取舍 ​

选择好处代价
内存滑动窗口零依赖、精确多 worker 失效
Redis 计数跨实例一致多一次网络往返，Redis 变成依赖
网关限流最早挡住、不占应用资源粒度粗，拿不到业务维度的信息
令牌桶允许突发、平滑参数（容量/速率）需要调，且解释成本高

返回码语义也是设计的一部分：401 = 你没带对 Key，重试无用；429 = 太频繁，可以退避重试，并给 Retry-After。前端要按状态码分流——别让 401 和 429 在客户端被当成同一类错误重试。

追问链 3：限流的边界与失效 ​

Q：你的限流是按什么维度做的？

A：按客户端 IP。但我要主动说清这个选择的两个边界：一是 NAT 后的多个用户会共享 IP，可能被误伤；二是按 IP 可以伪造。更合理的维度是「按 API Key 或用户 ID」，IP 只作为无身份请求的兜底。

Q：那你怎么保证限流不会被绕过？

A：不能保证完全不被绕过，只能限制爆炸半径。 限流在任何架构里都有绕过路径（换 IP、多 Key）。所以我把它定位成「防误用和防失控」，不是安全边界。真正的安全边界是鉴权 + 配额（按账号计的预算上限）——配额是累计量，换 IP 也没用。

这一条我是有实践依据的：我的 RAG 服务除了限流还有一个每日预算熔断，超限返回 402 且 readiness 变 false。因为限流防的是「太快」，预算防的是「太多」，两个不同的问题。

Q：配额熔断了，服务算不算挂了？

A：不算。 这是一个很重要的区分：预算耗尽不是故障，是主动的自我保护。 所以我的就绪判定里把 budget_exhausted 单独作为一个状态，它会让服务拒绝新的生成请求但不影响健康检查——否则编排系统会以为进程死了，反复重启一个「只是因为花超了钱」的服务。

常见错误答法 ​

错误说法问题改成什么
限流写在鉴权之前限流变成 DoS 放大器「鉴权 → 限流 → 并发闸门」，并说明未授权请求不消耗额度
「用计数器每分钟清零」边界处放行两倍滑动窗口 deque，并解释为什么
「配了 60 次/分钟就够了」没提多 worker 放大「单个 worker 60；多 worker 会放大成 N 倍，多实例必须换共享存储或网关」
只说限流不说配额两者解决不同问题「限流防太快、配额防太多；429 可重试、402 不可」
把所有拒绝都返回 429客户端会无脑重试，越试越挤401 不可重试、429 带 Retry-After、402 不可重试

四、缓存策略 ​

先问清需求 ​

「你想省什么？」——省延迟、省钱、还是省后端压力？这三个目标的缓存策略不一样。

分层方案 ​

层级缓存什么命中收益风险
精确缓存完整请求 → 完整响应延迟接近 0、零 token 花费命中率低（问题措辞稍变就不中）
语义缓存向量化的相似问题 → 响应命中率高误命中——把形似但不同的问题答错
前缀缓存公共前缀的 KV降低 prefill 算力需要在推理框架层开启，跨进程不共享
进程内缓存热数据、模型对象最快多实例不一致

我认为对问答场景最该先做的其实是「流程内的重复消除」：同一个请求里不要把同一个问题精排两遍。我的 RAG 项目里精排单次约 8.5 秒，脚本按问题逐条跑时会出现同一问题重复精排，于是后来把已算好的结果通过参数传进去——这是零风险的「缓存」，因为它不引入任何一致性问题。

关键取舍 ​

  • 语义缓存的阈值是它全部的难度：相似度阈值调高 → 命中率下降；调低 → 会把「退款政策是什么」和「退货政策是什么」当成同一个问题。所以语义缓存必须带「误命中率」这个指标，并且要能对命中结果做人工抽检。
  • 缓存失效策略：知识库更新后，语义缓存里的旧答案不会自动失效。必须有基于文档版本号的失效机制，否则会出现「文档已改、答案还是老的」——这类错误比慢更严重，因为它静默。
  • 缓存污染：如果缓存 key 里不含用户/租户维度，A 用户查到的内容可能被返给 B。多租户场景下，权限维度必须进 key，这一条是安全底线而不是性能问题。

追问链 4：语义缓存的错误模式 ​

Q：你的语义缓存怎么保证不答错？

A：我不把它当默认开启的功能。 我的判断是：语义缓存的收益是「省钱和降延迟」，代价是「可能返回一个形似但不同的答案」，而这个错误的性质是静默的——用户不会知道拿到的是另一个问题的答案。

Q：那你怎么决定要不要开？

A：看这类错误在你的业务里贵不贵。FAQ 场景（问题高度重复、答案边界清晰）可以开，配一个较高的相似度阈值 + 抽检；开放式分析场景我不开。而且必须先有评测集才能开——没有评测集你就无法测量误命中率，那就是在盲开。

Q：如果一定要开，你会加什么护栏？

A：三条。① 只缓存高置信度结果（模型回答里带明确依据的才进缓存）；② 缓存 key 里带知识库版本，文档更新即整体失效；③ 记录命中日志并抽检——把缓存命中当成一个需要被观测的、有对错的行为，而不是纯粹的优化。

常见错误答法 ​

错误说法问题改成什么
「加缓存就能提速」没说清省的是什么「先说清目标是延迟、成本还是后端压力」
「语义缓存命中率高所以更好」只谈收益不谈误命中「命中率要和误命中率一起看，且误命中是静默错误」
「缓存 key 只用问题文本」多租户场景下是数据泄露「权限/租户维度必须进 key」
「文档更新后缓存会自然过期，不用管」TTL 之前会返回旧答案「版本号进 key，或索引更新时主动失效」
忘了提「同一个请求内的重复计算」这是零风险的优化却被忽略「先消除请求内的重复计算，那个不引入一致性问题」

五、可观测：trace / span / generation 三层 ​

先问清需求 ​

「你上线后最想回答哪些问题？」——「这一次为什么答错了」「哪一个环节最慢」「这个月花了多少钱」。观测的设计要从问题反推，而不是从 SDK 的功能列表正推。

分层方案 ​

三层结构：

层是什么记录什么
trace一次完整请求的生命周期trace_id、入口信息、整体耗时与状态
span内部一个步骤（检索、精排、生成、工具调用）步骤名、耗时、输入输出摘要、父子关系
generation一次模型调用模型名、prompt/补全的摘要、token 计数、耗时

关键设计点：trace_id 在入口就定下来，并回写到响应头，这样用户报障时能直接给出一个可查的 ID。这看起来是小细节，实际上是「可观测」和「有日志」的分界线。

自研 JSONL vs 第三方 SDK——我的取舍是两个都接，但默认路径是自研：

  • JSONL 是默认路径：零第三方依赖、离线可审计、格式完全可控。
  • 第三方 SDK 是增强路径：可视化好、生态集成好，但它是外部依赖。
  • 两条路用同一个 trace_id 缝合，出错时可以互相印证。

最重要的一条纪律：观测写入失败绝不抛异常。 观测面炸了不应该把主链路带崩。但——必须显式降级，不能静默失败：「写不进去」这件事本身要作为一条事件被记录和告警。

关键取舍 ​

选择好处代价
自研 JSONL零依赖、可离线审计、完全可控没有现成 UI，要自己写查询
第三方 SDK开箱即用、可视化好外部依赖、可能影响主链路、有成本
全量记录事后可查存储成本、PII 风险
摘要记录便宜、安全事后复现困难

PII 与密钥：trace 里最容易夹带的就是原始输入输出。脱敏必须发生在写入前，而不是查询时——因为一旦落盘，损失就已经发生了。

追问链 5：观测不能影响主链路 ​

Q：你为什么自己写 JSONL，不直接用 Langfuse？

A：不是二选一，是主备关系。 JSONL 是默认路径、Langfuse 是增强路径，用同一个 trace_id 缝合。JSONL 零第三方依赖、离线可审计——当第三方服务挂了或者额度用完时，我仍然有完整的本地记录。

Q：那观测组件挂了会怎样？

A：写入失败绝不抛异常，只在业务事件里写一条降级标记。观测面炸了不应该把主链路带崩。

Q：这跟「可观测」的目标不冲突吗？失败了你还观测什么？

A：冲突，所以要显式降级，而不是静默失败。 降级本身是一条可被查询、可被告警的事件，不是「什么都没发生」。这两句话的差别就是「有观测意识」和「只接了个 SDK」的差别。

还有一个真实代价我要主动说：自研路径有额外的写入开销。 我的埋点是每请求若干个 span，自研实现的单请求耗时明显高于第三方 SDK 的异步 flush——自研的代价就是这部分开销要自己扛，我接受它的理由是「离线可审计」在这个项目里权重更高。这是一个有代价的选择，不是白拿的。

常见错误答法 ​

错误说法问题改成什么
「接了 Langfuse 就有可观测了」把工具当成能力「说清三层结构，以及每层解决什么问题」
「观测代码不会出问题」实际会（网络、配额、序列化）「写入失败不抛异常，且显式降级并告警」
「日志越多越好」成本与 PII 风险「按问题反推要记什么，脱敏在写入前做」
trace_id 只在内部用用户报障时无法定位「入口生成、响应头回传、日志贯穿」
不记录 token 计数成本无法归因「generation 层必须记 token，这是成本归因的唯一数据源」

六、成本归因：token 账怎么算 ​

先问清需求 ​

「你关心的是总量、还是某个功能/某个用户的开销？」——没有归因维度的成本数字是没法用来做决策的。

分层方案 ​

  1. 计量点：每一次模型调用都记 prompt_tokens 与 completion_tokens，和 trace_id 绑定。这是唯一可靠的数据源——不要用「字符数 × 系数」估算，我的实测就推翻过这类换算（中文约 1.2–1.3 字符/token、英文 3+）。
  2. 归因维度：至少三个——会话/用户（谁在用）、功能/端点（哪条链路贵）、模型（贵的模型用在哪）。这三条交叉起来才能回答「这个月为什么涨了」。
  3. 预算与告警：
    • 软阈值 → 告警（通知，不阻断）
    • 硬阈值 → 熔断（返回明确错误码 + readiness 变化）
    • 熔断状态必须能被区分于故障，否则编排系统会去重启一个只是花超了钱的服务。
  4. 成本优化的定位顺序：先看归因，再动手。常见错误是先去换小模型，而实际上大头可能在「重试」或者「上下文塞得太大」。

关键取舍 ​

  • 按会话归因 vs 按用户归因：会话粒度细、便于定位异常对话；用户粒度便于配额。两个都要有，成本很低（就是多打一个字段）。
  • 采样 vs 全量计量：token 计量本身很便宜，应当全量；而记录完整的输入输出内容成本高、有 PII 风险，可以采样。
  • 熔断的粒度：全局熔断最简单但会伤害正常用户；按 key/租户熔断更公平，代价是要维护每个 key 的计数。

追问链 6：成本异常怎么定位 ​

Q：你的服务某天成本突然翻倍，你怎么查？

A：先分维度拆，再定位到具体会话。 按端点拆——看是不是某条链路（比如流式端点）的调用量涨了；按模型拆——看是不是路由把请求都打到了贵模型上；按 token 拆——看是请求数涨了还是单个请求的上下文变大了。最后一层才是看具体会话。

Q：如果请求数没涨、单请求 token 也没涨，但总成本涨了呢？

A：那就是重试。这类「总量涨但没人在用更多」的情况，最常见的原因就是失败重试——而且它有双重代价：付了两次钱，还可能制造了两次副作用。所以我会先看失败率和重试计数。

Q：那你怎么防重试把成本放大？

A：给重试加预算。 三点：① 重试次数上限很小；② 退避要带抖动，避免同一时刻的重试潮；③ 重试要在总超时预算之内——不然超时会叠加，用户等 3 倍时间还给你付了 3 倍钱。这一条和「失败处理」那题是同一个问题，我会放在一起讲。

常见错误答法 ​

错误说法问题改成什么
「我们用的大模型很便宜」没有归因数据「给出计量点 + 归因维度 + 熔断阈值」
「按字符数估算 token」我的实测推翻过这类换算「从 API 返回的 token 计数取，不要估算」
「超预算就整个服务停掉」伤害正常用户，且会被误判成故障「按 key/租户熔断，且熔断状态与故障状态分开」
「成本高就换小模型」没定位就动手「先按端点/模型/token 三向拆分，最后看会话」
忽略重试的成本放大静默的成本漏口「重试预算 + 退避抖动 + 计入总超时」

七、灰度发布与模型路由 ​

先问清需求 ​

「你要验证的是一个假设，还是一个改动？」——没有可证伪的假设，灰度就只是一次「上了也没出事」的仪式。

分层方案 ​

  1. 分桶：用稳定的哈希把请求分到 A/B 组。粘性分桶是必要的——同一个用户/会话必须始终落在同一组，否则多轮对话里模型来回切换，体验和指标都不可比。
  2. 打标：路由决策要在请求进入时就固定下来，并写进 trace。不要中途改判，否则「这条记录属于哪个臂」就说不清了。
  3. 模型路由的判据：简单请求走小模型、复杂请求走大模型。判据本身要做消融——我的项目里就有一个未验证项：规则判定与模型判定的复杂度分歧（同一批题上两者给出的分布不一致），这个分歧还没通过人工盲标解决，所以我的路由到底以谁为准是待定的。
  4. 衡量成功的指标：至少三类——质量（任务完成率）、成本（token 或费用）、延迟（P50/P95）。只看质量会把成本炸掉。

关键取舍 ​

  • 按用户分桶 vs 按请求分桶：按用户粘性好、体验一致；按请求样本量大、能更快出结论。多轮对话场景必须按会话/用户分桶。
  • 先小流量再放量 vs 一步到位：前者稳但慢，后者快但风险集中。关键是每一档都要有明确的放量判据，而不是「看着没问题就放」。
  • 灰度的统计判据：单看均值会骗人。我的做法是配对检验 + 效应量 + 多重比较校正，并且判定是三态的：显著改善 / 显著回归 / 无显著变化——最后这个状态很重要，它诚实地表达「我没测出来」，而不是硬把噪声当结论。

追问链 7：灰度「成功」的定义 ​

Q：你怎么判断灰度成功？

A：三个指标都要看，而且要先定义判据再开跑。我的做法是：配对比较同一批任务在两个臂上的表现，同时看质量、tokens、墙钟，用多重比较校正控制整体错误率，只有「两个检验同向显著且效应量达标」才算改善。

Q：如果质量涨了但延迟也涨了，算成功吗？

A：取决于业务约束，所以这必须事先说定。 我遇到过类似的情况：多智能体版 tokens 省 12.5%，但完成率低 14.2 个百分点、墙钟是 1.43 倍（120 题配对，完成率 t p=0.00053、墙钟 p≈0，Holm 校正后都显著）。所以我的判据是「延迟不超过某个倍数 + 主指标不能倒退」，结论是：不切换。

Q：这个结论你确定吗？样本量够不够？

A：这个结论是四轮才拿到的，而且我把过程留下了。 第一轮 40 题得出的其实是「不显著」（完成率 100% vs 97.5%、墙钟 2.11×），我当时说的是「不证」不是「证否」。但那轮数字后来被我查出是假的——检索后端没接上、向量路静默降级、裁判把礼貌拒答判成满分。修完三层根因后完成率掉到 60-75%，再修生成层到 70%/70% 打平，最后扩样到 120 题才显著。

扩样不是我为了显著去凑的：n=40 时置信区间是 ±14pp，真实的 −14.2pp 刚好在边界外，这是功效算出来的。ψ=0.208 时测 +5pp 需 652 题，小幅差异我到现在也判不了——这个边界我会主动说。

常见错误答法 ​

错误说法问题改成什么
「灰度就是切 5% 流量看看」没有假设、没有判据「先定义要验证的假设和成功判据，再定分桶与放量」
按请求分桶多轮对话里模型来回切，指标不可比「按会话/用户粘性分桶」
「指标涨了就是好」没控制多重比较，也没看效应量「配对检验 + 效应量 + 校正；判定分三态」
「没测出差异说明改动无效」可能是样本量不足「报功效分析与所需样本量，说清是『不证』而非『证否』」
中途改判路由记录归属说不清「请求进入时固定路由决策并写进 trace」

八、幂等性与写操作安全 ​

先问清需求 ​

「这个写操作重复执行的后果是什么？」——重复建单可接受的话不需要幂等；重复扣款、重复退款、重复发信不可接受。

分层方案 ​

幂等键的设计要点（这一段是这题的核心）：

幂等键必须从「业务语义字段」算出来，不能直接用请求体的 hash。

因为请求体里含不影响业务语义的字段——时间戳、trace_id、随机 nonce。body 变一个字节键就变，重试就会重复执行，幂等直接失效，而且是静默失效。

正确做法三步：

  1. 选字段：用户标识 + 动作类型 + 业务主键（订单号等）；
  2. 归一化：剔除噪声字段、统一大小写与空白、稳定排序后序列化；
  3. 定作用域：键在哪个范围内唯一（进程内、会话内、全局）。作用域说错等于没有幂等——我实测有效的范围是「同进程同参数」，跨进程还没验证。

执行语义：命中已有键时回放之前的结果（并标记为重复），而不是重新执行，也不是报错。

两道防线：

机制解决什么不解决什么
幂等键重试导致的重复副作用用户/模型误操作
人工确认误操作（包括被注入诱导的操作）确认后的重试重复

这两个必须同时有，因为它们防的是不同的事件。

关键取舍 ​

  • 幂等存储放哪：进程内字典最简单，但重启就没了、跨进程不共享；持久化存储可靠，但要考虑清理策略（键不能无限增长）。至少要把「本实现的有效范围」写清楚，这比假装它是全局的强。
  • 失败时是否登记：只在成功后登记。如果失败也登记，用户重试会拿到一个「看起来成功但实际没做」的结果——比重复执行更糟。
  • 人工确认的粒度：确认信息要以人能读懂的摘要呈现（改了什么、影响谁、多少钱），否则用户会无脑点确认。

追问链 8：写操作的全链路安全 ​

Q：你的客服 Agent 建单是怎么做的？

A：写操作走幂等键 + 人工确认两步。先按业务参数算幂等键，同一个键重复提交不产生第二个副作用；需要确认的动作会让图中断，等人确认后再恢复。工具本身用装饰器定义，参数用 schema 校验，校验失败不炸图——错误被当成工具结果写回状态，让 Agent 有机会改参数重试。

Q：校验失败不抛异常，那会不会掩盖真正的 bug？

A：这是个好问题，我的处理是区分「参数不合法」和「程序出错」。参数不合法是预期内的（模型给错参数很正常），应该回给模型让它改；程序出错（比如字段名写错）必须暴露。我踩过一个非常典型的坑：getattr(llm, "model") 这个写法在同一个文件的两处逐字复发了同一个错误——它返回的是默认值而不是真实模型名，不报错但结果是错的。所以判据是：能用 schema 表达的问题走「回给模型」，其余一律当异常。

Q：那如果确认之后写操作失败了，用户重试呢？

A：幂等键兜住。 这就是为什么两步都要有：确认解决「要不要做」，幂等解决「做了几次」。而且我强调过：失败不登记——否则用户重试会拿到一个假的成功结果。

我还主动交代残余风险：我的幂等实现只在同进程同参数范围内被验证过（实测二次调用返回同一个 ticket、审计记录 1→1），跨进程和跨 thread_id 的碰撞没有验证，它在我明确的未实测清单上。

常见错误答法 ​

错误说法问题改成什么
幂等键用请求体 hash噪声字段让键不稳定，静默失效「业务语义字段 + 归一化 + 明确作用域」
「加了幂等就安全了」幂等不防误操作「幂等防重复，人工确认防误操作，两者都要」
失败也登记幂等键重试会拿到假成功「只在成功后登记」
「参数校验失败就抛异常」模型给错参数是预期内的，抛异常会把图炸掉「校验失败作为工具结果回给模型，程序错误才抛」
不说幂等的有效范围让人误以为它是全局的「明确说清作用域，未验证的部分主动交代」

九、失败处理：重试、熔断、降级 ​

先问清需求 ​

「你更怕慢还是更怕错？」——这决定重试策略。对有副作用的操作，宁可失败也不要重试（除非有幂等）。

分层方案 ​

三类机制各司其职：

机制触发条件作用参数要点
重试瞬时故障（网络抖动、429）提高成功率指数退避 + 抖动；次数上限小；计入总超时预算
熔断下游持续失败快速失败，不拖垮自己阈值要按错误率而不是单次错误
降级依赖不可用保核心功能必须能显式说出来，不能静默

重试的三条纪律：

  1. 只重试幂等或可重试的错误。401 和 402 重试一万次也没用。
  2. 退避必须带抖动。固定退避会让所有失败请求在同一时刻一起重试，把下游再打一次。
  3. 重试预算要计入总超时。否则「总超时 60 秒」会变成实际等待 180 秒。

降级路径要能说得出来：每个外部依赖失效时，用户看到什么、系统记什么。「降级后服务仍然可用」这句话必须有具体形态——比如模型服务不可用时，程序层拒答路径仍然可用、健康检查仍然可用。

关键取舍 ​

  • 快速失败 vs 兜底重试：对用户可感知的交互路径，快速失败往往更好（等 3 次重试不如立刻告诉用户）；对离线批处理，重试收益明显。
  • 降级的体验代价：降级等于给用户一个更差的答案。要说清降级到哪一档（换小模型？返回缓存？直接拒答？），因为不同档对用户的意义完全不同。
  • 熔断的恢复：熔断后怎么恢复？需要半开探测——放少量请求试探，成功则恢复，否则继续熔断。没有恢复机制的熔断会变成永久性故障。

终止条件（Agent 场景必答） ​

任何 Agent 循环都必须有明确的终止条件，而且是多类：

  1. 成功终止：得到最终答案；
  2. 预算终止：轮次上限、token 上限、时间上限、成本上限——四类都要有，只设轮次不够（一轮里可能烧掉很多 token）；
  3. 异常终止：工具连续失败、模型持续给不出合法输出、被外部信号打断。

「我自己写的循环不会死循环」是一句危险的自信。 终止条件要写成可测试的断言：构造一个必然无法完成的场景，断言它在规定的轮次内停下来。

追问链 9：超时与降级 ​

Q：模型调用超时了怎么办？

A：分场景。交互式请求：超时就快速失败，给用户一个明确的提示和可行的下一步，不要让他在那儿等到 3 分钟；离线批处理：退避重试，因为有整晚的时间。

Q：重试会不会把成本放大？

A：会，而且这是成本异常的一个主要来源。所以我的重试有三个约束：次数上限很小、退避带抖动、计入总超时预算。另外有个反直觉的点：重试的收益常常被高估——如果失败的原因是「上游普遍过载」，重试只会加重拥塞。

Q：那你怎么知道该熔断还是该重试？

A：看失败是「单点抖动」还是「系统性故障」。 单点抖动：少数请求失败、延迟正常 → 重试有效。系统性故障：错误率整体抬升、延迟也涨 → 应该熔断，因为重试会雪上加霜。这个判断需要错误率这个指标是实时可见的——所以熔断依赖观测，观测依赖埋点，这两件事是连着的。

常见错误答法 ​

错误说法问题改成什么
「失败就重试三次」没区分错误类型，也没说退避「只重试幂等/瞬时错误；指数退避 + 抖动」
重试不计入总超时用户等待时间被放大「重试预算包含在总预算内」
「超时就返回空」静默失败，用户不知道发生了什么「明确失败 + 可执行提示，并记录事件」
熔断没有恢复机制变成永久故障「半开探测 + 恢复条件」
Agent 只设轮次上限一轮可能烧掉大量 token「轮次 + token + 时间 + 成本四类预算」

十、liveness vs readiness ​

先问清需求 ​

「探针是给谁看的？」——编排系统用它决定要不要重启（liveness）和要不要导流量（readiness）。这两个决定完全不同，所以探针必须分开。

分层方案 ​

探针回答的问题检查什么检查失败时编排怎么做
liveness进程还活着吗进程/事件循环是否正常重启容器
readiness能接流量吗最依赖的那次真实调用能不能过摘掉流量，不重启

我踩过的真实坑，也是这一题的题眼：

我在服务里加了后台线程预热模型。预热确实在跑，但 /health 立刻返回 200 —— 于是编排系统/压测器在模型加载完之前就把流量导进来了，第一个请求照样等 48 秒。等于「预热做了但没用」。

这个 48 秒来自 service.py 源码注释里的自述实测，我没有保留原始日志——引用它时我会主动说明这一点，而不是把它当成一份实验证据。

修法是区分 liveness 与 readiness：liveness 只回「进程活着」，readiness 必须门控「业务真的就绪」。我的实现里的判据是一个显式状态，比如「预热状态属于完成或合法跳过，且预算没有被耗尽」才返回就绪。

一条必须记牢的话：探针要验的是「真实调用」，不是「对象能构造出来」。 模型对象构造成功不代表它能跑一次推理——权重可能是懒加载的。

关键取舍 ​

  • readiness 检查太重的代价：如果 readiness 每次都真跑一次推理，探针本身就会消耗资源，甚至在高频探测下变成负载。折中是首次真跑一次、之后看状态位，或者用很轻的真实调用（比如一次极小的检索）。
  • readiness 失败要不要重启：不要。readiness 失败只是「现在不能接流量」，可能是上游依赖没就绪——重启只会让冷启动再来一遍。
  • 「不适用」不等于「失败」：我的项目里有一个刻意的设计——当某个检查在当前模式下不适用时，返回的是「不适用」而不是 false。把「不适用」当失败会制造假告警，假告警会让人开始忽略告警。

追问链 10：探针的语义 ​

Q：/health 返回 200 有什么问题？

A：问题在于「200 回答的是哪个问题」。 如果它回答的是「进程活着」，那编排系统拿它当「可以接流量」用，就会在模型加载完成前导流量——我实测的第一个请求等 48 秒就是这么来的。所以 200 本身不是 bug，把两种语义混成一个端点是 bug。

Q：那正确的 readiness 该检查什么？

A：检查业务最依赖的那一次真实调用能不能过。 我的服务在 readiness 里检查的是「必要依赖是否可用」——没有索引、没有模型配置这一类，直接返回 503 并带上具体原因。带上原因很重要：线上排障时，「503 因为没有可用的索引」比一个 503 有用一百倍。

Q：那和限流、预算熔断这些状态怎么协调？

A：要放在同一个就绪判据里，但状态要分开表达。 我的判据是「预热完成 + 预算未耗尽」。注意这里有个细节：预算耗尽和依赖故障是两种不同的不可用，前者是主动保护、后者是被动故障。它们都应该让 readiness 变 false，但告警级别和处理方式不同——一个是「该加预算了」，一个是「该修依赖了」。

常见错误答法 ​

错误说法问题改成什么
「一个 /health 端点到哪都能用」混淆了两种语义「liveness 与 readiness 分开，各自回答自己的问题」
readiness 只检「服务能响应请求」那和 liveness 没区别「检真实调用，不检对象构造」
模型预热靠后台线程就完事流量会在预热结束前进来「预热 + readiness 门控，两件事都要做」
readiness 失败就重启冷启动再来一遍，问题更糟「readiness 失败摘流量，不重启」
把「不适用」当成失败制造假告警「三态：通过 / 失败 / 不适用」

十一、容器化与部署 ​

先问清需求 ​

「这个镜像要给谁跑？」——本地演示、单机部署、还是编排系统管理？要求不一样，交付形态就不一样。

分层方案 ​

关注点做法为什么
基础镜像选精简版（如 python:3.12-slim），按需再上更瘦的镜像小 → 拉取快、攻击面小
构建方式多阶段构建，构建依赖不进运行镜像编译工具链不该出现在生产镜像里
运行用户非 root（我的镜像用 uid 10001 的专用用户）容器逃逸的影响面直接变小
依赖锁定锁版本，且镜像用 digest 钉tag 是可变的，digest 不是
配置注入环境变量注入，密钥不进镜像镜像会被复制、被推送
持久化数据用卷，不写在容器文件系统里容器会被重建

一个必须讲的坑（我最容易讲出细节的地方）：

我在 compose 文件里给 MinIO 的镜像写了注释，说「用 digest 钉版本」——但 image: 那一行实际没带 digest，还是滚动 tag。

这是「注释写了、代码没做」的经典样本，而且它是我自己的校验脚本抓出来的：我写了一个静态检查脚本，专门断言 compose 文件的语义（比如镜像行必须带 digest、端口不能撞、必须声明健康检查）。如果没有这个脚本，这个不一致会一直挂着，直到某天上游改了 tag 导致环境重建失败。

这一条给我的纪律是：文档里的承诺必须有一条能失败的断言盯着，否则它只是愿望。

另一条经验：「能在本机跑起来」和「能被别人跑起来」之间的差距，几乎全在这张表里。

关键取舍 ​

  • 单容器 vs 多容器编排：单容器（应用 + 依赖都在一个进程侧）简单但不隔离；compose 多服务清晰但启动顺序、健康依赖要显式声明。
  • 镜像体积 vs 构建速度：多阶段构建镜像小但构建慢；开发期可以用简单构建，发布时切多阶段。
  • 健康检查放容器内还是应用内：容器健康检查指令适合做「端口通不通」这类粗检；业务就绪必须由应用的 readiness 端点提供。

追问链 11：部署语义的坑 ​

Q：compose 启动顺序能保证吗？

A：不能靠 depends_on 保证「依赖已经准备好」，它只保证启动顺序，不保证就绪。 数据库进程起来了但还没接受连接，这是很常见的窗口。所以要么配健康检查 + 依赖健康状态，要么应用侧自己带重试与就绪判断——我的做法是后者：应用连不上依赖时不崩溃，但 readiness 返回未就绪并说明原因。

Q：还有哪些「看起来对、实际不对」的部署写法？

A：三个我记着的。① 镜像不钉 digest（就是上面那个，注释说钉了、实际没钉）；② 多 worker 下用进程内限流/状态（数字是对的，语义是错的）；③ 迁移脚本只在一份 DDL 上改——如果项目有主实现和降级实现两套 schema，改一份忘一份，测试环境用 SQLite 通过、线上用 MySQL 直接报 Unknown column。

Q：第 ③ 个怎么防？

A：用一条断言把两套 DDL 的列集合对齐。 我的项目里有 MySQL 与 SQLite 两套实现（宿主端口用 3307 避让原生实例），做法是解析两份建表 DDL、提取列名集合、断言两边相等。这条断言的价值是：它会在你忘记同步的那一刻失败，而不是等到线上查询报错。这就是我说的「配置类改动必须配能失败的断言」。

常见错误答法 ​

错误说法问题改成什么
「用 latest 方便」不可复现「锁版本，且镜像用 digest 钉」
默认 root 运行安全面太大「专用非 root 用户 + 显式 uid」
密钥写进镜像或 compose 明文泄露面不可控「环境变量或密钥管理注入，镜像里不留」
「depends_on 保证依赖就绪」概念错「它只管启动顺序；就绪要靠健康检查或应用侧重试」
「本地跑通了就是能部署」缺了非 root、持久化、探针这些「按上面的关注点表逐条过」

十二、数据库选型与降级 ​

先问清需求 ​

「这个数据的读写比例、并发量、以及能不能容忍丢？」——三个问题定选型。

分层方案 ​

为什么要有降级实现：不是「为了炫技」，而是为了让系统在依赖不可用时仍然能被验证、能被演示、能跑测试。我的项目同时有 MySQL 与 SQLite 两套实现：

  • MySQL（宿主端口 3307）：生产形态，字符集用 utf8mb4 配对应的排序规则（中文 + emoji 备注都需要它），并且显式固定时区——默认跟随系统时区会让「最近一次出现时间」这类字段和 trace 时间戳对不齐。
  • SQLite：降级与离线验证形态。好处是零依赖、可随项目分发、测试不需要起容器；代价是方言不同、并发写弱。

两套实现的最大风险是「漂移」：改了 MySQL 的 DDL 忘了改 SQLite，于是本地全绿、线上报 Unknown column。所以必须有一条双 DDL 列集合对齐断言。

一次真实的性能教训（这题最好讲的故事）：

我的问题池表用 SET 类型存「入池原因」的多个标志位。运营看板要按单个原因统计——查单个成员要写 FIND_IN_SET(...)，而 FIND_IN_SET 是函数，不是列比较，无法走 B-tree 索引，直接全表扫描。问题池涨到 10 万行之后，这个统计从 20ms 变成 4s。

修法不是调参，是改数据模型：在主表上增设 trigger_primary 列存「首次入池的主导原因」，对它单独建索引。验收方式是 EXPLAIN：改之前 FIND_IN_SET 那条走全表扫描，改之后按 trigger_primary 查的 type 是 ref 或 range 且 key 命中新索引。

这条经验的可迁移部分是：「把多值字段塞进一个列」省了建表的麻烦，代价是查询退化成全表扫描。 什么时候值得额外冗余一列？当有一个查询维度会被频繁用作过滤或分组时。

关键取舍 ​

选择好处代价
规范化多值（关联表）完全可索引、语义干净写入变复杂、join 成本
SET/逗号分隔多值写入简单、一列搞定按单值过滤无法走索引
冗余一个「主值」列常见查询可索引需要维护一致性（什么时候更新它）
SQLite 降级零依赖、可离线验证方言差异、并发弱、有漂移风险

降级实现的价值边界要说清：它保证的是「逻辑正确性和可测试性」，不保证「性能可比」。拿降级实现的性能数字去推生产性能是错的。

追问链 12：慢查询的定位过程 ​

Q：运营说看板变慢了，你怎么查？

A：按「先量、再定位、再改」三步。先量：确认是所有查询慢还是某一个页面慢，拿到具体 SQL；再定位：对那条 SQL 跑 EXPLAIN，看 type 是不是 ALL（全表扫描）、rows 估算多大、有没有用到索引；再改：如果根因是「函数包住了列」，那不是加索引能解决的，必须改查询或改数据模型。

Q：FIND_IN_SET 为什么不能走索引？

A：因为索引建立在列值上，而 FIND_IN_SET(flag, col) 是对每一行求一个函数值再判断真假。只要列被函数包住，B-tree 就没法用它做范围定位。 同类问题还有 WHERE DATE(created_at) = '...' 这种写法——把函数从列上挪到常量那一侧（写成范围条件）就能走索引。

Q：那你怎么保证改完真的变快了？

A：用 EXPLAIN 做验收，而不是用「感觉快了」。 我的判据很具体：修改前那条 SQL 的 EXPLAIN 是 type=ALL，修改后走 trigger_primary 查询的 type 是 ref 或 range 且 key 命中新建索引。这是一个能失败的断言——如果索引没建上或者条件写错，它立刻不成立。

同时我主动交代口径：20ms → 4s 这个量级是文档里的记录，不是我今天重新测出来的数字；10 万行是当初描述问题规模的口径。报数字时把「哪来的」一起说清，比数字本身重要。

常见错误答法 ​

错误说法问题改成什么
「慢查询加索引就行」函数包住列时加索引无效「先 EXPLAIN 看 type 和 key，再决定改查询还是改模型」
用 FIND_IN_SET 做过滤还指望它快函数比较无法走 B-tree「冗余一个可索引的列，或改成关联表」
「我们有 SQLite 降级版，所以很稳」降级不保证性能可比「说清降级保证的是可测试性，不保证性能」
只改一份 DDL双实现漂移，本地绿线上红「双 DDL 列集合对齐断言」
报性能数字不说来源无法被验证「带口径：什么规模、什么量级、来自哪次记录」

十三、CI 门禁 ​

先问清需求 ​

「门禁要挡住什么？」——要挡住「看起来通过但其实没验」的改动。

分层方案 ​

  1. 确定性断言优先：能写成确定性断言的，绝不写成「看着正常」。比如：双 DDL 列集合对齐、compose 语义检查、必需响应头存在性、接口契约字段存在性。
  2. known_issues 与真实失败分开统计：已知问题（比如某个已知会失败的用例）应该被显式标记并按类别统计，而不是被 skip 掉藏起来。「跳过」和「已知失败」是两种不同的信息：前者会让人忘记它，后者会让人看见它。
  3. 三态退出码：我的评测门禁用三态退出码——改善 / 回归 / 无显著变化 / 不可比较。这个设计的价值是：把「没测出差别」和「测出变差了」区分开。如果只有 0/1 两态，「无显著变化」要么被算成通过（掩盖了噪声），要么被算成失败（制造假回归）。

关键取舍 ​

  • 门禁跑得越全越好 vs 越跑越慢：全量评测会拖慢每次提交。折中是分级：提交时跑快断言（秒级），合并前跑评测（分钟级），定期跑全量。
  • 阈值怎么定：固定阈值简单但会随着评测集变化失准；相对阈值（对比基线）更适应变化，但基线本身要可复现。我的做法是相对比较 + 配对检验，并要求评测配置（采样参数、gt 版本）冻结。
  • 「不可比较」这个状态：它存在的意义是防止拿两把不同的尺子比数字。我的评测报告里明确写了这条纪律：跨越了不同 gt 版本、题集、语料的表格不能横向连读。CI 里同理——口径变了就该阻塞，而不是比出一个数。

追问链 13：门禁的可信度 ​

Q：你的 CI 会不会「假绿」？

A：会，而且我踩过。最典型的是「写下了但从未执行」：我的 v1 里有 11 个自检入口从来没有被测试框架执行过——代码写了、函数也在，就是没人跑。所以 state.py 里的一个缺陷「红了不知道多久」。

Q：你怎么发现一个「没跑」的测试？

A：统计「登记了多少个入口」和「实际执行了多少个」然后断言两者相等。 我的口径是：自检入口总数 v1 14 个 + v2 16 个 = 30 个，逐个断言被执行。这类断言的价值在于它能失败——漏登记一个入口，它立刻变红。

Q：还有什么让门禁失效的方式？

A：两类我特别警惕。第一类是「判据本身写错了」：比如我做过一个基准测试，结论是「并发加速只有 1.02 倍」，看起来像「GIL 让并行毫无收益」——但真实原因是我的脚手架在被测函数内部重建了一个 52 MB 的大对象，那段构造本身就持有 GIL，把并行收益掩盖了。把块移到模块级预建之后，加速比变成 6.41 倍。所以：基准测试的脚手架本身会污染结论。

第二类是「测的不是要发布的东西」：单元测试全绿但装配关系错了。我遇到过一个条件边的装配错误——路由函数返回了节点名，却把映射表当参数传错，运行时报 KeyError: 'agent_memory'。这个错误能 import、能编译，纯函数单测测不出来，因为函数自己返回得没错，错的是装配关系。结论：装配错误必须靠运行整个图来验证，不能靠读代码或单测。

常见错误答法 ​

错误说法问题改成什么
「我们有测试，覆盖率还行」覆盖率不等于有效性「举出至少一条能失败的断言，以及它抓到了什么」
把已知失败 skip 掉问题被藏起来「known_issues 独立分类统计，与真实失败分开」
门禁只有 0/1 两态无显著变化被迫二选一「三态或四态退出码：改善/无显著变化/回归/不可比较」
「跑个基准测出并行收益不大」脚手架可能污染结论「先验证被测函数真的在跑、且测量不掺入构造开销」
单测全绿就合并装配错误测不出来「装配关系要用运行整个流程来验证」
