一、Agent 的本质：workflow 与 agent 的边界，什么时候不该用 Agent ​

面试官为什么问 ​

这是 Agent 岗位的第一道分水岭。答「Agent 就是能自己用工具的 LLM」的人，会被归类为「只写过 demo」；能说出「我这里哪些部分是 workflow、哪些才是 agent、为什么」的人，才像做过真系统。

标准答案 ​

区别不在「用不用工具」，而在「谁决定下一步」：

WorkflowAgent
控制流开发者预先定义（分支、顺序、循环边界）模型在运行时决定下一步做什么
可预测性高：路径可枚举、可审计低：同一输入的路径可能不同
可测性可以给单条路径写断言只能给「终止条件」「工具边界」「结果质量」写断言
适合步骤与分支有限、需要可审计、写操作有顺序依赖步骤数或组合方式无法预先枚举
成本可预估（调用次数固定）波动大（取决于模型选择）

判据：如果你能把它的流程图完整画出来、并且分支数量是有限的，那它就是 workflow——这时候上 Agent 只会换来不可预测性和更高的成本。

我的项目里两者是并存的，而且边界画得很清楚：

  • 意图识别 → 出口映射是 workflow：INTENT_TO_EXIT 把 9 类意图映射到 5 个出口。这一层必须是确定性的——业务要求路由可预测、可审计、可复盘。
  • 专家内部的 ReAct 循环才是 agent：不知道要查几次订单、要不要交叉验证物流，所以交给模型。

什么时候不该用 Agent —— 四条：

  1. 单次工具调用就能解决：这是 workflow，包一层 ReAct 只是多花一次模型调用；
  2. 流程可枚举且分支有限：比如「身份证校验 → 查库 → 返回」，画得出流程图就别上 Agent；
  3. 延迟预算极小：我实测多智能体比单智能体墙钟 1.43×（最新一轮 120 题；首轮 40 题是 2.11×），这是确定代价；
  4. 副作用不可逆且无法人工确认：钱、权限、数据删除——这些要么放到确定性流程里，要么加人工确认点。

追问链 ​

Q：Agent 的「四要素」是什么？

A：模型 + 工具 + 循环 + 状态。 四者缺一不可，而且每一环都有它的专属坑：

  • 模型：决定「下一步做什么」，所以它的输出必须是可校验的结构化对象；
  • 工具：它的边界就是系统的能力边界，也是越权风险的入口；
  • 循环：必须有闸——没有配额的回环就是死循环；
  • 状态：跨步骤传递的东西，必须显式声明（否则它散落在局部变量里，没法检查也没法恢复）。

Q：那为什么很多 Agent demo 只有「模型 + 工具」也能跑？

A：因为 demo 不需要为「跑出第 8 轮」负责。 我的项目里循环上限是 DISPATCH_LIMIT = 2，而且在两条路径上各设一道闸（见第九节）。

Q：你说的「闸」是同一个检查写两遍吗？

A：不是，是两个不同位置的回环入口。我的 ADR 里写的判据是：「每一个回环边都要有自己的闸。只在一侧检查，另一侧就是一个能绕过去的循环入口。」 图里 supervisor 侧有一道配额检查，专家侧的 route_after_expert 还有一道——因为它能连续输出 HANDOFF: 把控制权转回来，只挡一侧根本挡不住。

常见错误答法 ​

  • ❌ 「Agent = LLM + 工具 + 记忆」——漏掉了「循环」和「闸」，而这正是工程量的所在。
  • ❌ 「能用 Agent 就用 Agent，显得先进」——技术选型按需求，不按时髦度。
  • ❌ 「我们用 LangGraph，所以我们是 Agent」——框架 ≠ 架构，决策权在谁手里才是判据。
  • ❌ 讲不出自己系统里「哪部分是 workflow、哪部分才是 agent」——说明你没画过自己系统的图。

二、ReAct：循环结构、为什么它能工作、什么时候不收敛 ​

面试官为什么问 ​

ReAct 是 Agent 的基本循环，也是唯一一个「论文级概念 + 工程级细节」都能问的题。答原理的人很多，答得出「三重不动点问题」的人极少。

标准答案 ​

循环结构：

  1. 模型看到 system + 历史 + 用户问题，输出一段文本；
  2. 从这段文本里解析出 Action（工具名 + 参数），Thought 是模型自己写出来的推理（起解释与约束下一步的作用）；
  3. 系统执行工具，把结果作为 Observation 追加回消息历史；
  4. 回到第 1 步，直到模型不再调工具、或撞到某个闸。

为什么它能工作：因为每次工具结果都被写回上下文，模型在下一轮看到的是「我做了什么 + 得到了什么」。这让它能把一个大问题降解成一串「看到新信息再决定」的小决策——每一步都不需要预测全局，只需要看当前证据决定下一步。这是它能处理「步骤数无法预先枚举」的问题的根源。

它什么时候不收敛 —— 三重不动点问题（这是我要重点讲的）：

ReAct 有一个结构性的坏不动点：当工具反复返回同样的结果时，模型会反复做出同样的决策。因为它的输入（上下文）在「Action → Observation」这一对上是周期性重复的：同样的 Action、同样的 Observation、同样的推理、同样的下一个 Action。上下文本身不会自我修正，所以这个循环可以无限进行下去。

我项目里的应对是四道闸 + 三态终止：

  • 步数闸：单次 ReAct 的步数上限；
  • 分派配额闸：DISPATCH_LIMIT = 2；
  • 反思重试闸：REFLECT_MAX_RETRIES = 1；
  • 共享预算闸：budget_exhausted_why_v2。

追问链 ​

Q：Observation 直接拼进上下文有什么风险？

A：注入风险，而且它比"工具返回脏数据"严重得多。 工具返回的内容可能是用户可控的文本（比如知识库里的会话记录、工单备注）。一旦它作为 Observation 进上下文，模型就可能把里面的话当成指令执行。

我的做法是 v1 就定下的注入隔离边界：工具结果包在 <untrusted_data> 区块里，明确标识为「数据」而不是「指令」。v2 的 MCP 适配层复用它、不重写——因为这是同一条边界，重写一遍只会产生第二个真源。

Q：包一层标签就够了吗？

A：不够，但它是必要的第一层。 我的立场是：注入隔离不能只靠 prompt 标签，它还有第二层——工具白名单 + 参数面收窄 + 写操作人工确认。

Q：那真正可靠的防线是什么？

A：让被注入的内容「即使被当成指令也无法造成伤害」。 具体就是：工具按风险等级暴露（只读全开、写操作收窄）、写操作必须有确认点和幂等键、参数里不接受「我代表谁」这类身份字段（见 MCP 那一节的 user_id）。Prompt 层的标签是降低概率，权限层的收窄是限制后果——两层的定位不一样。

Q：你怎么判断一次 ReAct 循环「该停」？

A：三态终止，而不是「模型说完了就停」：

① 模型自然收尾（不再请求工具）；② 闸触发（步数/配额/预算）；③ 异常终止（模型错误、工具错误）。

三种终结都要能明确归因——我的自检里专门有一条断言 termination 字段的来源，因为「因为撞到配额而结束」和「因为答完了而结束」在日志里长得一样，但在复盘时含义完全相反。

Q：那你怎么看「让模型自己决定什么时候停」？

A：作为主路径可以，作为唯一机制不行。 我项目里发生过「误归因」：我先把某个问题判成「概率性拒答」，改了一处之后误拒率没降、出问题的题换了——率没变、集合变了，说明我改的那个东西根本不是主因，那个问题其实是确定性成因。「模型自主决定」的东西，一定要有一条独立的、确定性的兜底路径。

常见错误答法 ​

  • ❌ 「ReAct = Reasoning + Acting」——只背了名字，说不出循环里每一步的输出是什么。
  • ❌ 「加了 max_iterations 就不会死循环」——只有一个计数器只挡住了无处可去的那一类。
  • ❌ 「Thought 是框架帮模型生成的」——Thought 是模型自己写出来的文本，框架只解析 Action。
  • ❌ 不做注入隔离，说「工具返回的是我们自己的数据」——知识库/工单里的文本本身就是用户可控的。

三、Function Calling：模型只输出结构化意图 ​

面试官为什么问 ​

这是**「有没有踩过真实工程坑」**的验金石。答不出「谁真正执行了工具」「错误怎么回灌」的人，一定没在真系统里调过。

标准答案 ​

最重要的一句话：模型只输出结构化的调用意图，真正执行的是你的代码。

模型的职责是「告诉你要调什么工具、传什么参数」——它产出一个 JSON（工具名 + 参数），然后你的程序去做校验、执行、把结果回灌。模型不执行任何东西，它也看不到执行过程。

我这里的实现：工具用 @tool 装饰 + StructuredTool.invoke()；参数用 pydantic 类型定义；schema 按专家过滤（schemas_for(expert)）。

schema 设计原则：

原则具体做法理由
只写业务必需的字段参数面「只收不扩」每一个参数都是一个能被误用的入口
描述里写清语义与示例比如订单号的示例与长度范围模型靠描述猜语义，描述模糊它就给错参数
刻意不加 JSON Schema 约束关键字范围校验放到校验层见下方追问链
错误信息要能指导修正错误里带「示例：order_no=1001」回灌的目标是让模型自己改对，不是让它知道错了

错误怎么回灌给模型：工具错误不抛出、不炸图，而是作为工具结果（Observation）写回 state。这样模型下一轮能看到「这个工具失败了，失败原因是 X」，然后自己改参数重试。我的一条硬纪律是：校验失败不炸图。

追问链 ​

Q：为什么刻意不加 JSON Schema 的约束关键字（比如 minimum、maxLength）？

A：两条理由，都不是「懒得写」：

① 厂商兼容性不一致：strict 模式与约束关键字的支持在部分厂商会直接 400； ② 错误信息会变难回灌：schema 越「花」，模型给错参数后你收到的错误越抽象——「schema 校验失败」这种话对模型修正参数毫无帮助。

所以我的做法是：schema 只声明形状，范围校验放在校验层，由校验层给出人类可读、可直接照做的错误。

Q：校验层的错误长什么样？

A：比如订单号为空时报 缺少 order_no（订单号），并且带上一行 示例：order_no=1001；长度不对时报「订单号长度应为 3~32，你给的是 N 位」，同样带示例。

Q：为什么错误信息要写「示例」，而不是只写「不合法」？

A：因为回灌的目的不是通知，是修正。模型看到「不合法」只知道要改，但不知道改成什么；看到「长度应为 3~32」它才知道自己多输了还是少输了。这是把错误设计成模型可执行的输入。

Q：那如果模型反复给错参数呢？

A：那就要靠循环闸兜底，不能指望它一定改对。这就是为什么「错误回灌」和「步数闸」必须同时存在——前者提高成功率，后者限制失败代价。

Q：你怎么确认工具真的被调用了？

A：不要用 tool_calls 字段判断「有没有执行」。 我踩过这个坑：某个框架里 tool_calls.append 写在 if c.name not in tools / else 分支的外面，它记录的是「模型请求过的工具」，包括被拦下的未知工具——字段名会骗人。

我后来改用执行结果本身当证据：观测里同时出现「未知工具」和「参数非法」两个标记，才算证明「不仅被拦住了，而且拦在正确的位置」。

Q：那你为什么不用「假模型调越权工具会被拒」来测边界？

A：因为那测的是我自己，不是系统。 假模型是我自己写的脚本，它可以无视 schema 硬造调用；真模型不能，因为 schema 是 API 层的硬约束。拿一个不受约束的假模型去证明「系统会拦住越权调用」，证明的只是我脚本的行为。

Q：那正确的边界测试要怎么做？

A：在「schema 层」和「执行期层」各做一次，而且两层要分开验：

① schema 层：断言实际发给模型的工具 schema 集合 == 该专家的可见工具集合； ② 执行期层（防御纵深）：手工构造一个不在白名单里的调用，验证它被回灌「未知工具」且不崩溃、也不执行。

这属于「能力边界落在两层」——因为 schema 是给模型的声明，执行期是真正的强制，两者可能漂移。

常见错误答法 ​

  • ❌ 「模型会去调用 API」——执行的是你的代码。
  • ❌ 「参数校验交给模型自己保证」——模型给的参数必须程序侧校验，而且校验失败不能炸图。
  • ❌ 工具执行失败直接抛异常——正确做法是把错误写回 state 让模型自己修。
  • ❌ 用 tool_calls 字段证明「工具被执行了」——那个字段记的是模型请求过的调用。

四、工具设计：数量是不是越多越好，与工具可见性收窄 ​

面试官为什么问 ​

工具设计是 Agent 效果的第二杠杆。「工具越多越好」是大多数人的默认答案，也是错的——这一题就是让面试官看你有没有被真实系统教育过。

标准答案 ​

工具数量不是越多越好。我给每个专家的可见工具只有 1—3 个（工具全集是 5 个，对照单智能体路径用全量 5 个）。

工具描述怎么写——三条：

  1. 描述必须和实现同源。我的专家 prompt 里的工具清单直接从 spec.tools 生成，工具描述取工具自己 docstring 的首行、截 80 字符，不另写一份。理由是防「能力边界两处表示漂移」——写两份迟早会不一致，而不一致的表现是「prompt 说能做、实际做不到」。
  2. 写清「什么时候用」而不只是「是什么」。模型选工具靠的是用途匹配，不是名字。
  3. 不写多余的越权提示。描述里不需要声明权限——权限靠 schema 和执行层强制，不靠描述。

工具可见性收窄的三条理由（这是本节的真正考点）：

理由机制后果
① 上下文膨胀每个工具的 schema 都要进 prompt工具一多，system 段吃掉大量 token，注意力被稀释
② 选错工具相似工具越多，选择歧义越大模型在「查退款政策」和「查物流」之间摇摆
③ 越权副作用可见即可调用把写工具暴露给不需要它的专家，等于扩大了误调用面

三条理由的优先级不一样：① 是成本问题、② 是质量问题、③ 是安全问题。我项目里 create_ticket 是唯一写操作，它不进 MCP、也不给所有专家可见——这是按风险等级画的边界，不是按「技术可行性」画的。

追问链 ​

Q：你的可见性是靠什么保证的？

A：三层。

① 生成层：专家 prompt 的工具清单从 spec.tools 直接生成； ② 声明层：发给模型的 schema 按专家过滤，并有断言「prompt 里的工具行数 == 该专家工具数」； ③ 审计层：9 条可见性探针（VISIBILITY_CASES）覆盖单域与跨域请求，外加一个工具归属映射（工具名 → 持有它的专家元组）与隔离报告。

Q：还有一个「工具并集 == 全量工具集」的断言，这是防什么的？

A：防能力丢失。收窄可见性很容易收过头——某个工具谁都看不见，它就成了死代码。这条断言把「收窄」和「丢能力」区分开。

我项目里还有一个具体的设计决定受它影响：专家的停止信号做成 HANDOFF: 文本标记，而不是新增一个「交出去」的工具。理由之一就是「把控制流塞进工具层会让『工具并集 == 全量工具集』这条断言变复杂」——控制流就不该住在工具层。

Q：那这些断言真的跑到过吗？

A：这正是我项目里最值钱的一条教训。 v2 有 16 个自检入口、v1 有 14 个，合计 30 个——但 v1 里有 11 个自检从来没有被 pytest 执行过。

我写下的纪律是：「自检必须被运行：代码的防护力 = 被执行的断言数。」 一段写在文件里但从未跑过的断言，防护力是 0，而它在代码审查里看起来是满分。

Q：还有哪些「可见性」相关的事你没验？

A：专家菜单的「选择准确率」还没实测。 我有的证据是：每个专家的可见工具数与列表正确、9 条探针的可见性判定正确；我没有的证据是「真模型在这些请求上选对了几个入口」。这一项在我的未实测清单里，判据已经写好——选对率 ≥ 阈值 且 越界调用 = 0。面试里我会主动说是待验证项。

常见错误答法 ​

  • ❌ 「工具越多能力越强，把所有工具都给 Agent」——三条代价一条都说不出。
  • ❌ 「可见性收窄是为了省 token」——只说 ①，漏掉 ② 和 ③，而 ③ 才是最重要的那条。
  • ❌ 「工具描述随便写写，模型能看懂」——描述是模型选工具的唯一依据。
  • ❌ 不做可见性审计，也没有「工具并集」断言——收窄之后没人知道有没有收过头。
  • ❌ 说「我们有自检」但自检从没被执行——防护力等于 0。

五、MCP：三层架构、传输、授权、版本演进，以及与原生 tool 的取舍 ​

面试官为什么问 ​

MCP 是 JD 里的高频关键词，也是最容易被人「为了关键词而写」的技术。面试官想听的不是「我知道 MCP」，而是「我知道我该不该用它」。

标准答案 ​

三层架构：

层是什么关键点
Host用户实际在用的应用（IDE、桌面助手、你的 Agent 系统）承载模型与用户界面，是权限决策的主人
ClientHost 内部为每一个 Server 建立的连接器一个 Host 可以有多个 Client，一个 Client 对应一个 Server
Server工具/资源服务的提供方独立进程，可以跨语言、独立部署与升级

最容易说错的一点：这三层不等于三个进程。stdio 模式下 Client 与 Server 是父子进程关系；HTTP 模式下是网络连接。

Server 对外暴露三类原语：tools（可调用的动作）、resources（可读取的数据）、prompts（模板）。我只用 tools——理由是它最成熟、最贴合「把现有工具服务化」的需求，而 resources/prompts 会引入另一套消费模型。

传输方式：

stdioStreamable HTTP
通信本地子进程的标准输入输出单端点 HTTP（同一 URL 承载请求/响应与可选流式）
适用本机、零网络依赖远程服务、可被普通 HTTP 基础设施承载
优势部署最简单、无网络风险可被 LB/网关/鉴权中间件承载、无状态友好
代价进程生命周期管理（见下）需要服务端与连接治理

我两种都实测跑通了（stdio 与 Streamable HTTP，另有已被取代的 SSE）。我选 Streamable HTTP 的时候，官方定位是「自 2025-03 起作为推荐传输」（取代双端点的 HTTP+SSE）——这一点以官方文档为准。

工具发现：Client 连接后先协商工具清单（list_tools），Server 告诉 Client「我有什么」，Client 把这些工具交给 Host/模型。

授权：MCP 把授权明确放在 OAuth 2.1 的框架下。⚠️ 我这一项只读到机制层面，没有真实配置过授权服务器——我的实践是本地 stdio 与本机 HTTP，没到跨组织授权这一步。所以面试里我只会讲「它把授权放在 OAuth 2.1 框架下、涉及资源指示器与令牌受众校验」，细节一律说「以官方文档为准」。

版本演进（版本号取自官方文档目录，实抓）：官方有 draft / 2024-11-05 / 2025-03-26 / 2025-06-18 / 2025-11-25 / 2026-07-28 这一条版本轴。可确证的新增能力分布是：2025-03-26 有 authorization 章节、2025-06-18 已有 elicitation、2025-11-25 已有 tasks、2026-07-28 新增了 MRTR（多轮往返请求）、discover、caching 三类页面。我不会去声称某个能力「在某版本首次引入」——那是二手结论，我核不到一手。

MCP vs 原生 tool —— 该不该用：

原生 @toolMCP
本质同进程内的函数契约跨进程的工具服务协议
优势零序列化、调试栈最浅、契约与实现同仓库一套工具多消费者复用；跨语言；权限可独立管控；可独立部署升级
劣势消费者必须同语言同进程多进程多协议调试、多一层序列化、版本约束要在 CI 里守
该用单消费者、同仓同进程平台化：一个工具服务被 N 个团队/语言/应用消费
别用需要跨团队跨语言复用时单消费者时

我项目的结论：主链路（Agent 循环）继续用原生 @tool；MCP 只作为「工具服务的第二种消费形态」存在，暴露 2 个只读工具。

追问链 ​

Q：为什么 create_ticket（唯一写操作）不暴露给 MCP？

A：四条判据：

① 风险等级不匹配：写操作需要人工确认点与幂等保证，而 MCP 的跨进程边界会让「确认点要跨进程传递」「幂等键的会话域要跨进程对齐」； ② 扩大攻击面：一个能被外部进程调用的写工具，等于把「谁可以退款」从「同进程代码」扩大到「任何能连上 server 的 client」； ③ 与已有边界冲突：项目里已明确「写操作在确定性子流程里，不在 Agent 循环里」； ④ 收益为零：写操作的消费者永远只有本系统的客服流程。

判据式总结：「能暴露」不等于「该暴露」。协议集成的边界应该按风险等级画，不是按技术可行性画。

Q：那你怎么保证「刻意不暴露」这件事不被后人改掉？

A：负向断言。 我的 MCP 自检 A 段有两条清单：期望工具列表（2 个）与禁止工具列表（3 个）——缺工具或泄漏刻意不暴露的工具都判失败。

理由很实在：「刻意不暴露 create_ticket」如果只写在注释和 ADR 里，某天有人往注册函数里加一个工具，不会有任何测试红。 负向断言把「设计边界」变成「回归门禁」。

Q：把工具搬上 MCP 的时候你发现过新的边界问题吗？

A：发现了一个，而且很典型。 原工具的签名里有一个 user_id 参数——它的语义是调用方的身份。原样搬上 MCP 就等于「让任何能连上 server 的 client 指定我查谁的订单」，把原来的越权防御整个短路。

决策是：MCP 版不暴露 user_id，身份由 server 侧注入。 判据：「协议边界上的参数面只收不扩；谁能查谁的是服务端会话事实，不是 client 可传的参数。」

Q：那你还踩过什么 MCP 的坑？

A：三个，都是「症状不指向根因」的那种：

① 资源生命周期：stdio client 要同时管三个资源（子进程、读流、写流），写错方式集中且症状都很怪（任务被销毁、访问已关闭的资源、事件循环已关闭）。唯一能保证三个资源同生共死的写法是 AsyncExitStack。

② 环境变量：Windows 控制台是 GBK，子进程里打印中文或符号会抛编码错误，而报错出现在子进程 stderr，看起来像「server 崩了」。所以我显式传环境（含 PYTHONIOENCODING=utf-8）、用 sys.executable 而不是裸 python（后者可能是应用商店的存根）。判据：宁可显式传环境，不要隐式继承环境。

③ 日志噪声：一次 Streamable HTTP 往返实测往 stderr 打 17 行。我集中治理了 12 个 logger，静音级别定在 WARNING 而不是 CRITICAL（因为真正的协议错误通常以 WARNING/ERROR 报出，压到 CRITICAL 会把它们一起吃掉），并且留了一键打开的开关——「一个只能静音、不能打开的治理，等于删掉了日志。」

Q：MCP 的版本锁定风险具体是什么？

A：我钉的是 mcp>=1.28,<2，实测装到 1.30.0。锁 <2 的原因是实测到的改名：FastMCP 在 2.x 改名 MCPServer，而且官方口径是路径 "gone rather than deprecated"——不是弃用，是直接删掉。

所以 MCP 集成的成本里必须算上版本约束要在 CI 里守这一项。这不是「用好就行」的事。

Q：你在 MCP 上还没做什么？

A：跨语言 client 与多 client 并发都没测。 这两项在我的未实测清单里，验收判据已经写好（跨语言 client 要能用且返回格式一致；多 client 要无串扰、身份隔离正确）。

Q：那如果重来一次，你还会上 MCP 吗？

A：会——但理由和「为了简历关键词」不一样。 我最初对 MCP 的判断是「我的场景不满足它的价值前提」，那是一个判断、没有实测支撑；我后来把它变成了证据（亲手搬一个只读工具上 stdio / Streamable HTTP / SSE 三条传输）。

但今天的结论仍然是「主链路不用它」——因为我的消费者只有自己。ADR 里我写的原话是：单消费者时为了简历关键词上 MCP 是负收益。 这句我面试时也会这么说。

常见错误答法 ​

  • ❌ 「MCP 就是让模型能调工具的协议」——没说清它解决的是「跨进程复用」。
  • ❌ 把 Host / Client / Server 当成三个进程——stdio 模式不是。
  • ❌ 说「MCP 让 Agent 更强大」——它不提升能力上限，它换的是复用形态，单消费者场景是负收益。
  • ❌ 说「我们把所有工具都搬上了 MCP」——没有风险分级，尤其写操作。
  • ❌ 编造 MCP 版本号或某个 API 的首发版本——我全部按官方文档目录的实测版本轴说，不猜首发。

六、编排：状态图 vs 手写循环，条件边与 state schema ​

面试官为什么问 ​

这一题考的是**「你有没有把 Agent 的隐式结构显式化」**。手写循环能跑通，但它跑不出可恢复、可审计、可测的结论。

标准答案 ​

为什么用状态图而不是手写循环：因为 Agent 真正的难点不在循环，而在循环里那几件必须显式表达的事：

手写循环的问题状态图怎么解决
状态散落在局部变量和闭包里state 是显式契约：字段名、类型、reducer 都要声明
转移条件藏在 if/elif 里边是显式转移，条件边是显式函数
循环没有统一出口每个回环边各有一个闸，且终态是具名节点
跑挂了没法恢复配 checkpointer 就能从中断处续跑
没法单测某条路径可以只跑一个子图 + 断言 state 变化

条件边的机制：我项目里的条件是「返回节点名，再配一张映射表」。这里有一个我踩过的装配错误（见下方追问链），它的教训写进了纪律：装配错误必须靠运行图来验，纯函数单测测不出。

state schema 与 reducer：state 的每个字段要声明「多路写入时怎么合并」——覆盖还是追加。这个声明决定了并发/多路写入时的语义。我的 v1 state 有 28 个字段，其中 9 个带 reducer；v2 新加了 14 个字段。

state 形状在汇合点必须一致（这是最容易被忽略的一条）：如果两条路径在某个汇合点汇合，那么它们在汇合前写入的字段类型与语义必须一致。否则会出现「A 路径写 list、B 路径写 dict，到汇合点 reducer 崩了」——而且这种错只有在两条路径都被走到的编排测试里才会暴露。

追问链 ​

Q：你那个装配错误具体是什么？

A：条件边的三参形式是 add_conditional_edges(source, path_fn, path_map)。第一版让 route_by_exit 返回「节点名」，却把 EXIT_TO_NODE 这张表当成 path_map 传进去，运行时直接 KeyError: 'agent_memory'。

关键在于它的症状：这份代码能 import、能编译、一跑就崩，而纯函数单测测不出来——因为 path_fn 本身完全正确，错的是它和 path_map 的装配关系。每个零件都通过了测试，拼在一起才炸。

Q：那条纪律具体是什么？

A：「装配错误必须靠运行图来验。」 从此我的编排自检里必须有一条真跑一遍图的测试，而不是只测节点函数。

Q：这和「写下 ≠ 执行」那条教训是一回事吗？

A：是同一个母题的两个侧面。

「写下 ≠ 执行」讲的是断言写了但没被跑：v1 有 11 个自检从来没被 pytest 执行过，自检入口总数是 v1 14 + v2 16 = 30。防护力 = 被执行的断言数，不是写下的断言数。

装配错误讲的是零件测了但组合没测。两条合起来的判据是：测试要在「真实装配」的层级上跑，而且要证明它真的跑到了。

Q：那你现在怎么保证「真的跑到」？

A：把自检本身纳入统一入口去跑，并且用执行留痕当证据（trace 里出现某个标记、某个字段被真的改过），而不是用「我读过这段代码，它应该会跑」。

Q：state 字段应该放什么、不放什么？

A：我的划分判据是**「它需不需要跨步骤被读到」**：

  • 放 state：对话消息、业务槽位（订单号等）、检索快照、配额计数器、召回的记忆、反思提示；
  • 不放 state：一次性的中间变量、纯函数计算结果、可以被重新算出来的东西。

一条相关的判据我特别喜欢：「能算出来的东西不要存。」

Q：举个具体例子？

A：记忆的时效衰减。 我的实现是在召回时计算衰减，而不是「后台任务定期给过期记忆降权」。理由是：后台任务会引入「记忆状态取决于上次任务跑没跑」的隐式依赖——任务挂了，过期记忆照样被召回，而且没有任何症状。

所以「衰减值」这个字段不该存，它该被算出来。

常见错误答法 ​

  • ❌ 「我们手写 while 循环，更轻量」——能跑，但恢复不了、审计不了、测不了。
  • ❌ 说不出「条件边返回什么、映射表是什么」——这正是会 KeyError 的地方。
  • ❌ 认为 reducer 只是「追加还是覆盖的实现细节」——它是多路写入的语义契约。
  • ❌ 只给节点函数写单测，不跑整图——装配错误全在缝里。
  • ❌ 说「我们有 30 个自检」但没证明它们被跑过——防护力是 0。

七、记忆：短期 / 长期 / 摘要压缩，写入门槛与半衰期 ​

面试官为什么问 ​

记忆是 Agent 里最容易做歪的模块，因为「存得越多」直觉上越好。面试官想听的是：你有没有把「写入」当成一个需要被限制的动作。

标准答案 ​

三层记忆的分界：

层内容归属生命周期
第 0 层近 N 轮原文（滑动窗口）会话内一起会话，或滑出窗口即丢
第 1 层会话内摘要会话内会话结束即弃
第 2 层跨会话长期记忆持久化活过会话结束

摘要压缩的定位在 0 层与 1 层之间：当轮数超过阈值时，把前面的轮次压成一段摘要 + 保留最近几轮原文。它的价值是在有限上下文里保留更长的历史，代价是原文里的细节会丢。

核心设计法则：真相源与向量索引的角色不同。 我的长期记忆用 SQLite 当真相源（可审计、可导出、可单条删除），Milvus 只是可选的向量索引，且默认关闭。判据是：

记忆是「用户数据」，不是「检索产物」。 知识库的块丢了可以重切，用户说过「以后都用顺丰」丢了没有任何地方能重建。所以索引（派生数据）的可用性要求必须低于真相源。

写入门槛 —— 按「写错之后可不可逆」分档，不是按「这条信息重不重要」分档：

kind门槛为什么是这个档
preference0.60写错代价小，而且用户下一句就会纠正
fact0.75写错会一直误导，但通常能被后续对话否证
solution0.80写错会替代一次真实检索——检索可核对、有引用，记忆没有引用
correction0.85写错等于把用户的纠正反过来覆盖成错误，最坏的一种污染

⚠️ 这组数字的定位要说清：它是工程判断，不是行业标准。

半衰期：preference 90 天 / solution 180 天 / fact 与 correction 不衰减。理由对称：用户偏好会变、解决方案会过时，而**「用户是谁」这类事实不该过期**，用户纠错更不该随时间失效。

什么时候该写记忆：我定义了三条写入时机——① 会话结束提取用户偏好；② 反思产出的教训（以 correction 类型落库，置信度 0.90，略高于用户纠错的 0.85，因为是系统自产事实）；③ 已确认的「问题-答案」对。

召回后要不要拼进 prompt —— 我的答案是不拼（RECALL_POLICY = "state_only"）：

召回结果写进 state 字段，不直接拼进 prompt。三条理由：

  1. 可观测性：拼进 prompt 后，记忆就从「结构化数据」变成「一段文本的一部分」，trace 里再也回答不了「这次召回了哪几条、哪几条被过滤了、为什么」；
  2. 可回滚：记忆写错要重跑请求；留在 state 里可以在收尾前一条 retract() 掉；
  3. 可对比：A/B 测「有记忆 vs 无记忆」时，对照臂只要把那个 state 字段置空即可——两种模式跑的是同一条代码路径。

代价必须如实说：模型看不到记忆。 所以「用上了记忆」在这个模块里只到「能召回、能留痕」为止。我提供了一个显式开关去渲染记忆提示并把它记进未实测清单，而不是偷偷拼进去。

追问链 ​

Q：为什么写入要有门槛，而且门槛还分档？

A：因为记忆的价值来自它比检索更便宜也更准；一旦允许无门槛写入，它就变成污染源。

我的记忆污染防线有五条：① 可信度门槛（拦「模型随口推测当事实写进去」）；② 内容指纹去重（拦「同一件事被反复写入、越写越确信」）；③ 时效衰减（拦「过期偏好永久生效」）；④ 作用域隔离（拦「A 用户的偏好被 B 用户召回」）；⑤ 审计表 + 软删除（拦「已经污染了的记忆清不掉」）。

Q：第 ② 条为什么用指纹而不是「取前 N 字符比较」？

A：因为中文文本的前缀常常相同。「用户偏好使用顺丰快递发货」和「用户偏好使用中通快递发货」前 8 个字一模一样——取前缀会把两条相反的偏好判成重复。所以我用归一化后的内容指纹。

还有一个细节：归一化不做去标点——因为标点承载语义（「不要顺丰」和「要顺丰」就是被标点区分开的）。

Q：那指纹查重和可信度门槛，哪个先判？

A：指纹在先，可信度在后，而且顺序是刻意的。

后果很具体：一条置信度 0.99 的重复记忆会被指纹拦下，而不是被当成「合格的新记忆」收下。反过来，你会在审计表里看到「同一内容写入 2 次」而每次都显示「可信度足够」——污染检测的入口就没了。

更一般的原则：闸要按「拦下的成本从低到高」排序（先判内容非空、再判类型合法、再查库去重、最后判置信度）。

Q：还有什么是你「刻意不做」的？

A：两件事，都是主动放弃的：

① 不做自动的记忆合并/总结——让模型定期把多条记忆揉在一起，等于让模型自己给自己授权；一次揉错就永久化，而且原始记录没了。「谁说的、什么时候说的」是判断可信度的唯一依据。

② 不做「看到记忆就不再检索知识库」——记忆是用户事实，知识库是政策事实，两者冲突时必须两个都摆出来让下游发现矛盾。用记忆短路知识库，等于把幻觉升级成**「有据可依的幻觉」**。

Q：记忆召回会不会把别人的偏好串进来？

A：会——所以我有一条作用域过滤，而且这条过滤的默认方向是「少召回」：全局记忆对所有人生效，私有记忆只对本人生效，代码里没有「默认放行」的分支。

判据是：「召回不到」是能很快被发现的故障，而「召回了别人的偏好」是可能几个月都没人发现的故障。

Q：那注入路径呢？谁能看到记忆？

A：supervisor 和执行层都能看到。 理由：用户说「还是用我上次说的那家快递」——记忆是「上次说的那家」的唯一指代来源。所以判据是：指代消解需要的信息必须给到做决策的那一层，不能只给执行层。

另外我特意保证了记忆不是 A/B 的自变量——两臂都装记忆，否则配对检验会把记忆的收益算到「多智能体」头上。

常见错误答法 ​

  • ❌ 「记忆就是存聊天记录」——没区分短期/长期，也没区分真相源与索引。
  • ❌ 「全都存下来，反正向量库能装」——没写入门槛、没有衰减、没有去重。
  • ❌ 「召回后拼进 prompt 就完事了」——丢掉了可观测性、可回滚、可对比三件事。
  • ❌ 把记忆和知识库当同一种数据——用户事实 vs 政策事实，冲突时要都摆出来。
  • ❌ 报了门槛数字却不说它是工程判断——被追问「这是行业标准吗」会很难看。

八、计划与反思：plan-and-execute 的适用场景，反思触发与重试上限 ​

面试官为什么问 ​

规划与反思是**「Agent 能不能处理多步任务」的关键，也是最容易过度设计的地方。面试官想看你的上限意识**：PLAN_MAX_STEPS = 3、REFLECT_MAX_RETRIES = 1 这些数字是拍的还是有理由的。

标准答案 ​

plan-and-execute 的适用场景：任务能被拆成有依赖关系的若干步、而且拆解本身需要全局视角时。我项目的 plan 只在 multi 模式下走，并且有一条硬要求：

complexity="simple" 时跳过规划。

理由是规划本身有成本（一次模型调用 + 一段上下文），对一步就能答完的问题做规划是纯浪费。

PLAN_MAX_STEPS = 3 / PLAN_MIN_STEPS = 2——上下限同时存在，是因为只有上限会让「一步就够」的任务也被硬拆成多步。

反思节点的触发条件：四条触发，顺序即优先级，且谓词互斥：

触发含义应对策略
model_error模型层错误按策略恢复
tool_error工具层错误通常在同一个专家内重试（问题在参数，不在选人）
empty_answer答不出内容可考虑换专家
no_progress没有新进展换路径或收尾

两种策略：retry_same（同专家重试）与 switch_expert（换专家）。策略的选择依据是「错在哪一层」：工具参数错 → 同专家重试；工具选择错 → 换专家。

重试上限怎么设：REFLECT_MAX_RETRIES = 1。理由有三条：① 反思本身也有成本（它要花一次模型调用）；② 第一次反思没修好，继续重试的边际收益很低——如果是确定性成因，重试不会改变结果；③ 它和共享预算、分派配额构成三重闸，任何一重都能兜住。

追问链 ​

Q：反思为什么要「触发条件」而不是每轮都反思？

A：因为每轮反思 = 每轮多一次模型调用。而且大多数轮次是正常的——对正常轮次反思，你付出成本换来的信息是「一切正常」。

我把反思做成条件触发 + 谓词互斥 + 有上限三件事，本质上是把反思从「流程的一部分」变成「异常处理的一部分」。

Q：那反思的产出往哪去？

A：两条路：一条进当前请求，一条进长期记忆。

① 进当前请求：反思的提示渲染成一段文本注入消息； ② 进长期记忆：反思的教训以 correction 类型落库（置信度 0.90，理由是反思是系统自产事实，所以略高于用户纠错的 0.85 门槛让它写得进去），并有自检断言 trace 里出现「反思→记忆」且含「成功」。

Q：反思失败（没修好）你怎么知道？

A：靠归因字段。 我没有把「反思跑过了」当成功——自检要断言的是 trace 里那条标记含「成功」。这是我那条「写下 ≠ 执行」教训的直接应用：「调用了反思」和「反思起了作用」是两件事。

Q：你的规划上限是 3，为什么不是 10？

A：因为上限的作用是「封顶最坏情况」，不是「允许更好情况」。而且我有一个可复用的判据式说法：

「如果未来把上限提高到 3，先回答『3 轮能解决而 2 轮解决不了的是哪些题』——答不出来就不提。」

这句话可以套在任何预算参数上：提上限之前，先拿出「上限不够用」的具体证据。

Q：那你实测下来分派了几轮？

A：37 题 1 轮 + 3 题 2 轮，均值 1.075 轮（首轮 40 题样本；最新一轮 120 题的分派指标见评测页）。也就是说上限 2 在实际样本里几乎没有被逼到——这正是「不选 3」的证据。

常见错误答法 ​

  • ❌ 「每个请求都先规划」——对简单任务纯浪费，而且规划错了会把整条路径带偏。
  • ❌ 「反思每轮都跑，更稳」——成本翻倍，收益近似零。
  • ❌ 「重试 3 次比较保险」——说不清多出来的两次解决了什么问题。
  • ❌ 把「反思执行了」当成「问题修好了」——断言级别搞错了。

九、终止条件：怎么防死循环（至少三类思路） ​

面试官为什么问 ​

这是安全题，也是最能看出「你有没有为最坏情况负责」的一题。答「我设了 max_iterations」的人，会被一句「那如果循环不在那一层呢」打穿。

标准答案 ​

至少三类终止条件，而且要在每个回环边上都设：

类型机制我项目里的值
步数闸单调递增计数器，到顶强制收尾PLAN_MAX_STEPS = 3；ReAct 步数上限
配额闸结构性上限（能派几次专家）DISPATCH_LIMIT = 2
重试闸同一异常的重试次数REFLECT_MAX_RETRIES = 1
预算闸token/费用上限，与前三者共享预算耗尽标记

最关键的一条（这是我最想让你记住的）：

每一个回环边都要有自己的闸。只在一侧检查，另一侧就是一个能绕过去的循环入口。

我项目里闸是两道：supervisor 侧的第一道在派发决策里；专家侧的配额检查拦住「专家连续输出 HANDOFF:」这条回环——因为它能把控制权不断转回来。

为什么配额必须写进 prompt：我项目里有一句判据——「能被事前告知的约束，不要只做事后拦截。」 所以派发上限会作为参数写进 supervisor 的 system prompt。事前告知能减少「模型规划了一条走不通的路」的概率；事后拦截只是兜底。

追问链 ​

Q：怎么保证「到上限就真的停」？

A：计数器的单调性。 我把分派次数做成单调递增计数器，而不是「当前轮次」——因为「轮次」可以被重新推导，而推导出来的东西有可能不递增。到了上限就强制收尾，并把终止来源标成「配额」。

Q：把计数器放 state 里，会不会有并发/多路写入的问题？

A：会，所以这些字段必须带 reducer 声明（见第六节）。这也是我强调「state 形状在汇合点必须一致」的原因——计数器被覆盖成旧值，等于闸失效。

Q：你说「每一个回环边都要有闸」，具体是哪几个回环边？

A：至少三处：① supervisor → 专家 → supervisor（转交回环）；② 专家内部的 ReAct（工具回环）；③ 反思 → 重试（反思回环）。

还有一个我必须诚实讲的：项目里实现过一个工作流级的最大分支数 guard，而且是死代码——我尝试过触发它但没能触发，因为它被执行顺序绕开了。「写了闸」和「闸生效了」是两件事——这又是「防护力 = 被执行的断言数」那条教训的第三次出现。

Q：那你怎么证明闸生效了？

A：用执行留痕当证据，而不是用「代码里有这个 if」。具体做法是让自检断言「终止来源」这个字段——因为「因为撞到配额而结束」和「因为答完了而结束」在日志里长得一样，但在复盘时含义完全相反。

常见错误答法 ​

  • ❌ 「设了 max_iterations 就不会死循环」——只有一个计数器，挡不住别的回环。
  • ❌ 把闸写在一侧就以为封住了——另一侧就是能绕过去的入口。
  • ❌ 约束只做事后拦截，不写进 prompt——错失最低成本的干预点。
  • ❌ 用「当前轮次」当计数值——它可能不单调。
  • ❌ 声称有闸但从未触发过，也不去证明它能被触发——死代码会伪装成防护。

十、持久化与中断：checkpointer 的价值，以及「重启就丢 = 等于没有」 ​

面试官为什么问 ​

这是**「demo 与系统」的分界线**。能跑通的 Agent 很多，能中断续跑、能人工介入、能审计历史的很少。

标准答案 ​

checkpointer 的价值不止「续跑」，它有四个用途：

  1. 中断与恢复：进程挂了、部署重启，能从中断处继续；
  2. Human-in-the-loop：在某个节点暂停，等人确认后再继续；
  3. 时间旅行：回到某个历史状态重放（调试与复盘的关键能力）；
  4. 审计：每一次状态转移都有落盘的记录，能回答「当时系统看到了什么」。

「内存 checkpointer 一重启就丢 = 等于没有」——这句话是这一题的核心。内存实现只能证明「接口是通的」，它不能支撑上面四个用途中的任何一个：进程一重启，历史、暂停点、可回滚性全部消失。

Human-in-the-loop 的实现方式：在状态图的某个节点中断，外部把决策（或修正后的参数）写回并恢复执行。

写操作安全——这是本节的工程重点，三条：

机制做法
幂等键先算幂等键查缓存，命中直接回放首次结果、不执行
人工确认需要确认且未确认 ⇒ 不登记；只在成功后登记
入参校验@tool + pydantic 校验；校验失败不炸图，错误作为工具结果写回 state

幂等键的细节值得讲：它基于稳定参数（去掉时序字段这类「本来就该不同」的部分）——如果键里混进了每次都变的字段，幂等永远不命中，这个 bug 会表现成「幂等失效但没有任何报错」。

追问链 ​

Q：为什么「未确认就不登记」这条顺序很重要？

A：因为登记代表「这件事已经做过了」。如果未确认就先登记，那么用户后来真的确认时，会被当成重复请求直接回放一个从未真实执行过的结果——这在退款场景里就是「告诉用户已退款，但其实一分钱都没动」。

判据式说法：幂等登记的时机必须是「副作用已经发生」之后，不能是「请求已经收到」之后。

Q：那如果执行到一半失败了，幂等键还能回放吗？

A：只在成功后登记就是为了这个：失败不登记 ⇒ 下次重试会真的再执行一次。这比「登记了但没执行」安全——前者是多做一次（可幂等化），后者是假装做了（不可挽回）。

Q：写操作为什么不做成「重试 N 次」就够了？

A：因为重试和幂等解决的不是同一个问题。重试解决「这一次没成功」，幂等解决「成功了但请求被重复提交」。退款、下单这类场景里，重复提交是常态（用户点两下、网关重发、任务重试），所以幂等键是必需的，重试次数不是。

还有一条纪律：写操作不进 Agent 循环的可选工具集，而是走确定性子流程——Agent 决定「要不要退款」，但「怎么退款」是确定性代码。

Q：那你怎么验证持久化真的生效了？

A：用「重启后能续跑」当验收判据，而不是「代码里配了 checkpointer」。理由和我前面说的完全一致：配置存在 ≠ 行为发生。

我项目里同类教训的清单已经有三条了：写了但没被执行的断言、写了但从未被触发的工作流 guard、配了但可能只指向内存的存储。它们的共同点是：「写下来」这个动作太便宜了。

常见错误答法 ​

  • ❌ 「我们配了 checkpointer」——不说后端是什么。内存后端等于没有。
  • ❌ 把 checkpointer 只当「断点续跑」——漏掉 HITL、时间旅行、审计三个用途。
  • ❌ 写操作只做重试不做幂等——没意识到重复提交是常态。
  • ❌ 幂等键混进时序字段——永远不会命中，而且不报错。
  • ❌ 校验失败直接抛异常——把「模型给错参数」这个可恢复情况变成了不可恢复。

十一、多智能体：拓扑分类，以及「更多智能体一定更好吗」 ​

面试官为什么问 ​

多智能体是最容易被吹的部分。这一题你手里有真正的否证数据，答出来会非常亮眼——因为绝大多数候选人只会讲「多智能体更强大」。

标准答案 ​

拓扑分类：

拓扑结构适合
Supervisor一个中心决策者派发给多个执行者任务能被切分成不重叠域；决策集中在派发点
层级（Hierarchical）supervisor 之上还有 supervisor域数很多、需要分层收敛
群聊（Group chat）多个 agent 共享一个对话流，轮流发言需要多方辩论、观点互补
流水线（Pipeline）固定顺序，前一个的输出是后一个的输入步骤确定、只想要分工而不是自主

我的是Supervisor 拓扑：1 个 supervisor + 5 个专家，串行派发，跨域靠专家在回答末尾输出 HANDOFF: 标记触发。

为什么选串行而不是并行（这是 3 条判据，不是偏好）：

  1. 写操作有顺序依赖：「先改址再退款」与「先退款再改址」结果不同（退款按订单当时地址核算运费）→ 并行会产生不可复现的最终状态；
  2. 专家的输出是彼此的输入：跨域请求里第二个专家的 prompt 需要第一个专家的结论（实测有一题是「先查政策 → 再拿结论查订单」）；
  3. 成本形状不同：串行是次数问题（一个上限就封顶），并行是扇出问题（封顶需要「深度 × 宽度」两个预算，且失败归因会复杂化）。

「更多智能体一定更好吗」——用实测数字回答（最新一轮 120 题）：

  • 新发现（这一轮独有）：换问法后 multi 掉 6.7pp、single 升 7.5pp ⇒ multi 的脆弱点在分派鲁棒性，不在模型能力；

追问链 ​

Q：那你现在切换了吗？

A：没有，而且理由比第一版更硬。 第一版是「在当前样本上没测出收益」；现在是 完成率 −14.2pp（p=0.00053）、墙钟 1.43× 都显著更差，只有 tokens 省 12.5% —— 用 12.5% 的 token 换 14.2pp 完成率，对在线客服是亏的。

代价必须由可测的完成率收益来支付——当前没有，而且是负的。

Q：什么条件下你会重跑这个 A/B？

A：三条全满足才重跑：

① 评测集更换（跨域/多步题占比 ≥ 30%，且完成率天花板不饱和）； ② 检索层缺陷已修复； ③ 有真实墙钟容忍度（异步批处理/离线工单），或并行版落地使墙钟代价消失。

这三条是有针对性的：它们分别对应用户前那个「题集不敏感」「完成率受检索层约束」「墙钟是硬伤」三个限制。

Q：你的证据质量还有什么限制？

A：四条，我主动报：

① 题集不敏感（首轮 39/40 同对同错 → n_eff=1；最新一轮扩样后 ψ=0.208，信号才够）； ② 裁判未人工校准； ③ 检索层缺陷——有一题的正确答案在知识库里，两臂都检索失败，说明完成率受检索层约束，不能外推到「检索修好之后」； ④ 样本量只有 40 对（功效表见上）。

Q：那多智能体在你这儿还剩什么价值？

A：结构性的价值是明确的，只是当前题集测不出来：跨域接力（实测有一题成功：政策 → 订单两跳）、工具菜单窄 → 专家 prompt 短（这是 tokens 省 7% 的来源）、以及可以叠加 plan / 反思 / 长期记忆。

但它同时带来墙钟 1.43×（最新一轮 120 题）、固定的编排开销、更大的可观测与归因面。这些是「保留代码不切换」而不是「删掉」的理由——因为结构优势需要一个能测出它的题集才能被证实。

常见错误答法 ​

  • ❌ 「多智能体一定更好」——给不出任何数字，而我这里是显著变慢。
  • ❌ 「我们试过多智能体，没用」——没做功效分析就说「没用」；正确的说法是「这批题测不出差异」。
  • ❌ 只报完成率，不报墙钟和 token——架构决策是三个指标一起看的。
  • ❌ 说「不显著就是没差异」——不显著有两种：真的没差异，和样本不够。必须用 n_eff / 功效分析区分。
  • ❌ 做了 A/B 但没说测不出是哪种：首轮 n_eff = 1（39/40 同对同错）、扩样后 ψ=0.208——不说清就是把「测不出」讲成了「证明了」。

十二、Agent 评测：轨迹评测 vs 最终答案评测，LLM-as-judge 的偏差与校准 ​

面试官为什么问 ​

最终答案对不代表过程对。 面试官问这一题，是在看你会不会把「Agent 的过程质量」当成一个可测对象。

标准答案 ​

两种评测的对象不同：

最终答案评测轨迹评测
测什么结果对不对、有没有解决问题过程合不合理（工具选对了没、步骤多不多、有没有越权）
优点客观、易自动化、和用户价值直接挂钩能定位「为什么对/为什么错」
缺点答案对可能是蒙对的——调错工具也可能凑出正确答案需要标注、成本高、标准难统一
我项目里的角色主判定（盲测裁判 + 配对检验）描述性指标（分派轮次、转交题、工具调用）

我项目里评测管线的关键设计（每一条都有具体理由）：

  1. 两臂答案交错排列（m0, s0, m1, s1, …）→ 防位置偏差；
  2. 不给裁判看 mode 标签，也不给 GT 字段 → 防泄漏；
  3. 裁判只输出 JSON，解析失败时先正则兜底、再失败就记 score=None + 错误原因——不静默；
  4. 缺裁判标签的题剔除并报告——「不悄悄填 0，那会把裁判失败伪装成任务失败」；
  5. 裁判温度 0.0 + 结构化输出，回答截 1500 字符；
  6. 统计判据：配对 t 检验 + Wilcoxon 符号秩检验，两个同向显著且效应量达标才算「改善/退化」，再跨指标做 Holm 校正；
  7. 三态 + 一态退出码：IMPROVEMENT / REGRESSION / NSC / INCOMPARABLE。

LLM-as-judge 的偏差与校准：

偏差表现应对
位置偏差倾向选先出现的那个交错排列
自偏好偏爱同一模型家族的输出记录裁判模型，跨模型复核
长度/风格偏差偏爱更长、更结构化的回答截断长度 + 明确 rubric
标尺漂移人工标注到后面标准变了盲标 + 独立会话复核

最关键的诚实要求：必须报「裁判未人工校准」。 我项目里把这一条写进了证据质量限制——因为用未校准的裁判得出的结论，其可信度上限就是裁判本身的可信度。

追问链 ​

Q：你的裁判凭什么可信？

A：我自己也不认为它「可信」，我认为它「可用且被标注了不确定性」。

我的做法是：裁判的 rubric 明确写清「回答是否实质解决了用户的问题」，并且不以「ground truth 里的可回答标记」为准——实测里有两道题被标成「不可回答」但知识库里其实有答案、两臂都答对了。GT 标注不等于事实。

Q：那裁判失败怎么办？

A：分三步，每一步都不静默：① 先试 JSON 解析；② 失败后正则兜底抓 0/1；③ 再失败记 score=None 并带上原始输出的片段。然后统计时把缺标签的题剔除并报告剔除数。

Q：为什么不直接当 0 分？

A：因为那会把「裁判失败」伪装成「任务失败」。这两种失败的含义完全相反：一个是测量工具坏了，一个是被测系统坏了。混在一起，你会去优化一个根本不存在的问题。

这和我另一条踩坑是同一个母题：「把失败伪装成通过」。 那次是把无法识别的引用静默过滤掉，结果校验报「通过」。静默降级是评测里最危险的一种 bug——它让你在错误的方向上获得信心。

Q：那轨迹评测你做了哪些？

A：分派轮次（37 题 1 轮 + 3 题 2 轮，均值 1.075）、转交题（3/40）、跨域题占比（7.5%）、工具调用与错误（每次专家执行都会产出工具调用、错误、耗时、可见工具清单）。

但我要主动说清一条：「分派正确率」不进配对检验——因为单智能体臂结构上没有 supervisor，这个指标对它无定义。所以它只作 multi 单臂的描述指标。一个在某一臂上无定义的指标，不能拿去做两臂配对检验。

常见错误答法 ​

  • ❌ 只测最终答案，不管轨迹——答案对可能是蒙对的。
  • ❌ 拿 LLM 裁判分数当客观分数——不说裁判模型、温度、抽取方式、一致率。
  • ❌ 裁判解析失败就当 0 分——把测量失败伪装成任务失败。
  • ❌ 把在某臂上无定义的指标拿去做配对检验——统计上没意义。
  • ❌ 声称「效果提升了 5%」但没说 p 值、效应量、样本量。

十三、成本与延迟控制：模型分级路由、预算告警、缓存 ​

面试官为什么问 ​

Agent 的成本是它的死穴——一个循环里可能调很多次模型。面试官想听的是：「你知不知道钱花在哪，以及你做了什么。」

标准答案 ​

模型分级路由：按任务的复杂度选模型——简单走小模型（默认 deepseek-flash），复杂走强模型（默认 deepseek-v4-pro），决策依据来自 plan 输出的复杂度字段。

但这里有一个极其重要的前提，我项目里实测到了：

复杂度判定来源简单复杂比价结论
规则重推（离线）337简单题 token 份额只有 5.4% ⇒ 比价 ≈ 0.973 ⇒ 几乎无收益
live 判定（模型判）340100% 走小模型 ⇒ 比价 = 1/m ≈ 0.50

两个来源的判定几乎完全相反（37/40 multi vs 0/34 multi），而且 live 判定把一个跨域、两专家、17,034 tokens 的题也判成了 simple。

所以结论是：模型路由要先校准「复杂度判定」本身；判据不校准，路由只是把误判成本放大。 收益上限恒 = 复杂题 token 份额。

预算告警：三层预算控制、告警比阈值、以及按模型的成本拆分报告。一条纪律：未定价的模型不编数——查不到价格就返回「未知」，绝不自己填一个看起来合理的数字。

缓存：缓存能省的是重复的输入 token。最有效的一类缓存是 prompt 前缀缓存——把一个稳定的长前缀（system + 工具说明 + 固定示例）放在前面，让服务端复用它。它是唯一一种「不改变行为、只降成本」的优化。⚠️ 具体能力与 API 形态以官方文档为准。

追问链 ​

Q：你的成本记账有什么特别之处？

A：三条：

① 未定价不编数——价格表查不到就返回「未知」，绝不猜； ② 旧格式缺 prompt/completion 拆分时，绝对成本只报区间——全部按输入价算是下界、全部按输出价算是上界； ③ 从 trace 里抠真实复杂度，区分「规则判的」与「模型判的」——这正是我发现上面那个 37 vs 0 反差的方法。

Q：为什么「未定价不编数」这么重要？

A：因为成本数字最容易被当成分母。一旦分母是编的，后面所有的「每问成本」「比价倍数」全都是错的，而且看起来完全正常。

Q：那你的灰度策略有什么讲究？

A：失败方向必须指向旧路径。 我的灰度百分比非法时回落到 0 = 全基线，而不是「全部走新版本」。理由：灰度的目的是降低风险，如果失败会把你整体推向未验证的新路径，那它反而放大了风险。

另外我做粘性分桶（同一个 query 稳定落同一个桶），否则同一个用户反复刷新会看到两种行为——那既影响体验，也让 A/B 数据变脏。

Q：延迟上你踩过什么坑？

A：一个非常典型的教训：并发加速比取决于你能不能让出 GIL。

同一份并发实验，块在函数内构造时测出 1.02×（看起来多线程完全没用），把块改成模块级预建后测出 6.41×（真实收益）。并发度 8、3 次取中位数。

对照实验也很说明问题：另一个「释放 GIL 但需要分配 52 MB 输出」的操作只有 2.13×——释放 GIL ≠ 拿到线性加速，内存分配争用会把收益吃掉。

Q：这条教训是什么？

A：「测出 1.02×」和「这个方案没用」是两件事。 前者是测量对象的错误（我把构造开销也算进了被测段），后者才是结论。我当时的判据是：先确认被测的那段代码，就是我以为的那段代码。

Q：这和 Agent 的成本/延迟有什么关系？

A：它是同一条方法论：我另一个项目里，把「端到端延迟」分解成「检索 / 生成 / 总」之后才发现，首字延迟约等于检索耗时（14.90 / 10.00 / 14.86 s），瓶颈是 CPU 精排 20 对约 8.5 s，而 LLM 生成 P50 只有 1.26 s。

如果没做这个分解，我一定会去「换个更快的模型」——然后发现一点没变快。Agent 侧同理：先知道钱和时间花在哪一段，再优化那一段。

常见错误答法 ​

  • ❌ 「我们做了模型路由，成本降了一半」——分母是「复杂度判得准」这个前提，前提不成立收益是 0。
  • ❌ 成本数字里编了没查到的价格——会让整张表失效。
  • ❌ 灰度失败时「全量走新版本」——把降低风险的手段变成了放大风险。
  • ❌ 说「多线程没用来优化并发」——可能是你测错了。
  • ❌ 「我们加了很多缓存」——说不出缓存命中了什么、命中率多少。

三条红线

  1. 报数必带口径。 样本量、比较对象、检验方法、是否显著——缺一项就别报这个数。
  2. 「不显著」要说清是哪种。 真的没差异，还是样本不够？用 n_eff 与功效分析区分。别把「测不出」讲成「证明了」。
  3. 没做的说没做。 裁判未人工校准、专家菜单选择准确率未测、MCP 跨语言与多 client 并发未测、记忆注入未开、工作流 guard 是死代码——这些主动说出来是加分。
